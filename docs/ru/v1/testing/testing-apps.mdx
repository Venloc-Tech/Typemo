Тесты приложения на Typemo идут на настоящей MongoDB. Ошибки приведения типов, уникальные индексы, транзакции и планы запросов на подделке не воспроизвести. Чтобы такие тесты оставались короткими, в пакете есть две вещи — **фабрики** тестовых данных и **проверки индекса**. Последние роняют тест, когда запрос перестал использовать индекс.

Всё это лежит в отдельном входе `@venloc/typemo/testing`. Сервер для тестов вы поднимаете сами.

## Что понадобится [#prerequisites]

Модель счёта ниже и тест-раннер `bun:test`. С другим раннером код будет тем же. Тестовая база — отдельная, не рабочая, и приложение берёт её адрес из настройки. Если тестам нужны транзакции или подписка на изменения, база должна быть реплика-сетом (несколько серверов MongoDB с копией одних данных, для транзакций хватит и одного).

## Подготовить чистую базу для теста [#clean-test-database]

Каждый тест должен видеть только свои данные. Надёжнее всего завести отдельную базу на набор тестов и чистить коллекции между тестами.

Пустой фильтр в [`deleteMany`](../reference/writes/writes.mdx#delete-many) запрещён — в рабочем коде одна опечатка удалила бы всю коллекцию. А в тесте «удалить всё» как раз и нужно, поэтому пишите это явно через [`Filters.all()`](../reference/policies/violations.mdx#filters.all). Пересоздать базу целиком можно и через драйвер, об этом в разделе [доступ к драйверу](../connection/driver-access.mdx).

<Snippet id="testing/testing-apps/clean-test-database" title="accounts/accounts.test.ts" />

Не пропускайте `syncIndexes`. Он создаёт индексы из схемы, и без них тесты уникальности и плана ничего не докажут. Клиент закрывайте в `afterAll`, иначе раннер не завершится.

## Создавать данные фабриками [#factories]

Скажем, тесту нужны три счёта, а важно в них только одно поле. Фабрика берёт значения по умолчанию из функции от номера (1, 2, …), так что уникальный `title` не конфликтует. В тесте вы переопределяете только то, что нужно.

<Snippet id="testing/testing-apps/factories" twoslash />

`build` только собирает данные, `create` ещё и сохраняет. Счётчик у фабрики общий, поэтому второй вызов получает номер 2. Если номера не должны зависеть от порядка запуска, вызывайте `accountFactory.reset()` между тестами.

Фабрику проверяет компилятор. Переименуйте `balance` в модели, и она перестанет компилироваться — тест не упадёт потом в неожиданном месте. Подробности в справочнике по [`defineFactory`](../reference/testing/testing.mdx#define-factory) и [`Factory`](../reference/testing/testing.mdx#factory).

## Проверить, что запрос использует индекс [#check-index-used]

Бывает, что поле переименовали или поменяли фильтр, и запрос молча начал читать всю коллекцию. [`expectIndexScan`](../reference/testing/testing.mdx#expect-index-scan) выполняет `explain` и бросает [`IndexUsageError`](../reference/testing/testing.mdx#index-usage-error), если индекс не используется.

<Snippet id="testing/testing-apps/check-index-used" title="accounts/accounts.test.ts" />

Для поля без индекса тот же тест падает с `the query is not served by an index: it scans the whole collection (COLLSCAN). plan: COLLSCAN; examined 3 documents, returned 3`.

Если индекса нет намеренно, закрепите это через [`expectCollScan`](../reference/testing/testing.mdx#expect-coll-scan). Тогда тест сломается, когда кто-нибудь добавит индекс или запрос изменится. Сырой отчёт о плане даёт [`explainIndexUsage`](../reference/testing/testing.mdx#explain-index-usage). Как читать план и выбирать индекс, рассказано в руководстве [Скорость запросов](../queries/performance.mdx#test-index).

## Как выбрать [#how-to-choose]

Спросите себя, **что должно сломать тест**.

- **Неверные данные в ответе** — хватит обычных проверок результата.
- **Запрос обязан оставаться быстрым** — добавьте `expectIndexScan` с `maxDocsExamined`.
- **Важен конкретный индекс** — задайте `index`.

## Когда это не нужно [#when-not-to-use]

Не ставьте `expectIndexScan` на каждый запрос. Маленькая коллекция в тесте даёт какой угодно план, так что проверка нужна только там, где скорость входит в обещание приложения. И не зовите эти проверки из рабочего кода — каждая выполняет лишний `explain`.

## Если что-то пошло не так [#troubleshooting]

**Тест уникальности проходит, хотя индекса нет.** Индексы создаёт `syncIndexes`, сами при подключении они не появляются. Вызовите его в `beforeAll`, иначе дубликат вставится без ошибки.

**Фабрика падает с `count must be a non-negative integer`.** `buildMany` и `createMany` принимают только целое неотрицательное число, а получили что-то другое — `TypemoError: defineFactory: count must be a non-negative integer, got -1`. Передавайте число документов, а не длину, которая может уйти в минус.

**`covered: true` не проходит у запроса по индексу.** `expectIndexScan(query, { covered: true })` падает с `it is not covered by the index (it fetches documents)`, если сервер прочитал хотя бы один документ. `findById` и `find` по уникальному полю читают документ целиком, даже когда индекс его уже нашёл.

Покрытым запрос становится, когда `select` просит только поля индекса и без `_id`. Например, `Accounts.find({ title: { $gte: "A" } }).select({ title: 1, _id: 0 })` даёт `covered: true` и `docsExamined: 0`. Подробнее в справочнике по [`explainIndexUsage`](../reference/testing/testing.mdx#explain-index-usage).
