Чтобы проверить документ по схеме, вызовите [`$validate`](../reference/documents/document-api.mdx#validate). Метод соберёт все найденные проблемы в одну [`ValidationError`](../reference/errors/data-errors.mdx#validationerror) и ничего не запишет. Для обычных данных, из которых документ ещё не создан, вроде тела запроса или строки импорта, есть [`Model.validate`](../reference/documents/model-document-methods.mdx#modelvalidate). А [`$save`](../reference/documents/document-api.mdx#save) сам проверяет документ перед каждой записью.

Проблемы собираются все вместе, а не по одной. Человеку, который заполнил форму, нужен список того, что исправить, а не первая ошибка из пяти. Каждая проблема — это запись с путём поля, причиной и сообщением.

## Что понадобится

Товар `Product`. У него обязательное имя с асинхронным валидатором, число с границами и значением по умолчанию и поле с перечислением. Правила полей описаны в разделе [Валидация полей](../schemas/validation.mdx).

```ts twoslash title="models/product.ts"
import { type Defaulted, Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "products" })
export class Product extends Entity {
  @Prop(() => String, {
    required: true,
    validate: async (value: string) => value !== "bad" || "the name is taken",
  })
  name!: string;

  @Prop(() => Number, { min: 0, max: 10, default: 1 })
  size!: Defaulted<number>;

  @Prop(() => String, { enum: ["a", "b"] })
  kind?: "a" | "b";
}
```

## Быстрый путь

```ts twoslash
import { type Defaulted, Entity, Prop, Schema, TypemoClient, ValidationError } from "@venloc/typemo";
@Schema({ collection: "products" })
class Product extends Entity {
  @Prop(() => String, {
    required: true,
    validate: async (value: string) => value !== "bad" || "the name is taken",
  })
  name!: string;
  @Prop(() => Number, { min: 0, max: 10, default: 1 }) size!: Defaulted<number>;
  @Prop(() => String, { enum: ["a", "b"] }) kind?: "a" | "b";
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Products = client.db().model(Product);
// ---cut---
const product = Products.new({ name: "bad", size: 99 });

try {
  await product.$validate();
} catch (error) {
  if (error instanceof ValidationError) {
    console.log(error.issues.map((issue) => [issue.path.join("."), issue.reason]));
    // → [["name", "validator"], ["size", "max"]]
  }
}
```

Ниже разберём, что лежит в каждой проблеме, как проверить данные без документа и когда проверка срабатывает сама.

## Проверить документ

[`$validate`](../reference/documents/document-api.mdx#validate) проверяет весь документ — обязательные поля, границы, перечисления и ваши функции `validate`. Асинхронных валидаторов он дожидается. При успехе метод возвращает `void`, при любой проблеме бросает `ValidationError`, а сам документ не меняет.

Тот же вызов делает и [`$save`](../reference/documents/document-api.mdx#save), так что вручную проверять перед сохранением не нужно. `$validate` пригодится, когда об ошибках нужно узнать **до** записи, например чтобы показать их пользователю.

Каждый пункт в `issues` — объект с четырьмя полями.

- `path` — путь поля, массив сегментов.
- `reason` — причина, например `required`, `min`, `max`, `enum`, `validator` или `cast`.
- `message` — текст.
- `value` — значение.

Полный список причин — в справочнике [`ValidationError`](../reference/errors/data-errors.mdx#validationerror).

```text
ValidationError: Validation failed: "name": the name is taken [validator]; "size": must be at most 10 [max]
```

Пункты идут в том же порядке, что поля в классе. Ошибки `$save` и `Model.validate` упорядочены так же.

## Понять, что документ не сохранится

Типы приводятся при создании, а правила проверяются при проверке. Поэтому документ можно создать, но нельзя сохранить. Здесь `qty` строки заказа не может быть отрицательным (`min: 0`), но добавить такую строку в массив можно. Правило сработает только при `$validate` и `$save`.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, Spec, TypemoClient, Versioned } from "@venloc/typemo";
@Schema({ nested: true })
class Address {
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => String) street?: string;
}
@Schema()
class Line extends Entity {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true, min: 0 }) qty!: number;
}
@Schema({ collection: "orders" })
class Order extends Versioned(Entity) {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => [Line]) lines!: Line[];
  @Prop(() => Address) address?: Address;
  @Prop(() => Spec.map(Number)) fees?: Map<string, number>;
  @Prop(() => String, { hidden: true }) note?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
import { ValidationError } from "@venloc/typemo";
// ---cut---
const order = Orders.new({ customer: "alice", tags: [], lines: [] });
order.lines.push({ sku: "B2", qty: -1 });

try {
  await order.$save();
} catch (error) {
  console.log(error instanceof ValidationError && error.issues[0]?.path.join("."));
  // → "lines.0.qty"
}
```

Путь `lines.0.qty` называет точное место — строку и поле. Документ при этом не записывается ни целиком, ни частично.

## Проверить данные без документа

Если данные приходят снаружи, создавать документ незачем. [`Model.validate`](../reference/documents/model-document-methods.mdx#modelvalidate) приводит и проверяет обычный объект и возвращает готовое значение с подставленными значениями по умолчанию, включая `_id`.

```ts twoslash
import { type Defaulted, Entity, Prop, Schema, TypemoClient, ValidationError } from "@venloc/typemo";
@Schema({ collection: "products" })
class Product extends Entity {
  @Prop(() => String, {
    required: true,
    validate: async (value: string) => value !== "bad" || "the name is taken",
  })
  name!: string;
  @Prop(() => Number, { min: 0, max: 10, default: 1 }) size!: Defaulted<number>;
  @Prop(() => String, { enum: ["a", "b"] }) kind?: "a" | "b";
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Products = client.db().model(Product);
// ---cut---
const value = await Products.validate({ name: "lamp" });
console.log(value.name, value.size);
// → "lamp" 1

try {
  await Products.validate({ name: "bad", size: 99, kind: "z" });
} catch (error) {
  if (error instanceof ValidationError) {
    console.log(error.issues.map((issue) => [issue.path.join("."), issue.reason]));
    // → [["name", "validator"], ["size", "max"], ["kind", "enum"]]
  }
}
```

Обратите внимание на порядок пунктов. Они идут в порядке объявления полей в классе (`name`, `size`, `kind`), хотя валидатор имени асинхронный и заканчивает позже остальных. Порядок не зависит от того, какая проверка закончилась первой, так что список в форме не «прыгает» от запуска к запуску.

Если нужно только привести значения, без проверки правил, есть [`Model.castObject`](../reference/documents/model-document-methods.mdx#modelcastobject). Он останавливается на первой ошибке приведения и значений по умолчанию не подставляет.

## Разобрать ошибку приведения типа

Привести значение к типу поля и проверить его правила — два разных шага, и ошибки у них разные. Значение, которое не приводится к типу, даёт `CastError`. Проверять его по правилам пока бессмысленно — `"abc"` не число, и сравнивать его с `max` нечего. А значение нужного типа, которое нарушает правило, становится пунктом `ValidationError`.

Где появится `CastError`, зависит от того, как значение попало в документ. Методы вроде `Model.new`, `$set` и методов массивов приводят значение сразу, на вызове. Простое присваивание `product.size = "abc"` приводится позже, на ближайшем `$validate()` или `$save()`. Метод бросит `CastError` раньше всякой валидации, и в базу ничего не уйдёт. Ограничения этого поля не проверяются, так что второй, побочной ошибки по тому же полю не будет.

```text
CastError: Cast to number failed at path "size" for "abc" (string): expected a number [type]
```

`Model.validate` ведёт себя иначе, его задача — собрать все проблемы данных снаружи. Значение неверного типа он не бросает, а добавляет в список пунктом с причиной `cast`. Сама `CastError` лежит в `cause` этого пункта. По каждому полю пункт один, и если значение не приводится, его ограничения не проверяются.

```text
ValidationError: Validation failed: "size": Cast to number failed at path "size" for "4" (string): expected a number [type] [cast]
```

Строгость здесь намеренная. `"4"` молча в число не превратится.

## Как выбрать

Спросите себя, **есть ли у вас документ**.

- **Документ уже есть**, создан через `Model.new` или прочитан из базы, — [`$validate`](../reference/documents/document-api.mdx#validate) или сразу [`$save`](../reference/documents/document-api.mdx#save).
- **Есть только данные снаружи**, и нужно понять, годятся ли они, — [`Model.validate`](../reference/documents/model-document-methods.mdx#modelvalidate).
- **Нужно только привести типы** — [`Model.castObject`](../reference/documents/model-document-methods.mdx#modelcastobject).

## Когда это не нужно

Перед `$save` отдельно вызывать `$validate` не нужно, сохранение проверяет документ само. Для изменений через [`updateOne`](../reference/writes/writes.mdx#updateone) документ не нужен вовсе. Как приводятся типы и работают проверки при обновлении, описано в руководстве [Валидация полей](../schemas/validation.mdx).

## Если что-то пошло не так

**Проверка прошла, а сохранение отказало.** `$validate` проверяет данные документа, но не версию и не уникальные индексы. Конфликт версий — это [`VersionError`](../reference/errors/query-errors.mdx#versionerror), а нарушение уникальности — [`DuplicateKeyError`](../reference/errors/server-errors.mdx#duplicatekeyerror). О них сообщает база при записи, заранее их не найти. Ловите эти ошибки вокруг `$save`.

**Из ошибки непонятно, какое поле виновато.** Текст `ValidationError` называет пути, но для формы удобнее разобрать `issues`. У каждого пункта есть `path` и `reason`. Берите `error.issues`, как в примерах выше, а не разбирайте `message`.

## Полный пример

Функция принимает тело запроса, проверяет его и возвращает либо созданный товар, либо список проблем по полям.

```ts twoslash title="products/products.service.ts"
import { type Defaulted, Entity, Prop, Schema, TypemoClient, ValidationError } from "@venloc/typemo";
@Schema({ collection: "products" })
class Product extends Entity {
  @Prop(() => String, {
    required: true,
    validate: async (value: string) => value !== "bad" || "the name is taken",
  })
  name!: string;
  @Prop(() => Number, { min: 0, max: 10, default: 1 }) size!: Defaulted<number>;
  @Prop(() => String, { enum: ["a", "b"] }) kind?: "a" | "b";
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Products = client.db().model(Product);
// ---cut---
export const createProduct = async (body: unknown) => {
  try {
    const value = await Products.validate(body);
    const product = await Products.create(value);
    return { ok: true as const, id: product._id };
  } catch (error) {
    if (error instanceof ValidationError) {
      return { ok: false as const, problems: error.issues.map((issue) => ({ field: issue.path.join("."), reason: issue.reason })) };
    }
    throw error;
  }
};
```

## Если вы пришли из Mongoose

<Callout type="migration">

`doc.validate()` здесь называется `$validate()`, а `Model.validate(obj)` возвращает приведённое значение. Значение, которое не приводится, даёт `CastError`, а у `Model.validate` — пункт с причиной `cast`, а не `invalidate`. Асинхронных валидаторов Typemo дожидается всегда. И `ValidationError` содержит все пункты в порядке полей схемы, а не только первый.

</Callout>
