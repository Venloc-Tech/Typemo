Модуль NestJS получает модели через `TypemoModule.forFeature`. Вы перечисляете классы сущностей, а модуль делает из каждого провайдер, который внедряется через `@InjectModel`. Ниже разберём всё, что можно туда перечислить. Обычные сущности, сущности в другой базе, потомков-дискриминаторов, сущности со статиками плагинов, представления и материализованные результаты. А в конце — как создать для них коллекции и индексы при старте.

## Что понадобится [#prerequisites]

Приложение из руководства [Подключить Typemo к NestJS](./setup.mdx) с сущностью счёта.

```ts twoslash title="accounts/account.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => Number, { required: true, min: 0 })
  balance!: number;
}
```

## Быстрый путь [#quick-start]

Перечислите сущности модуля и включите создание недостающих коллекций при старте.

```ts twoslash title="app.module.ts"
import { Module } from "@nestjs/common";
import { Entity, Prop, Schema } from "@venloc/typemo";
import { TypemoModule } from "@venloc/typemo-nestjs";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
}
// ---cut---
@Module({
  imports: [
    TypemoModule.forRoot("mongodb://localhost:27017", { dbName: "bank", sync: "init" }),
    TypemoModule.forFeature([Account]),
  ],
})
export class AppModule {}
```

Ниже разберём каждый вид записи и выбор `sync`.

## Одна сущность в нескольких модулях [#shared-entity]

Счета нужны и модулю счетов, и модулю отчётов. Перечислите `Account` в [`forFeature`](../../reference/integrations/nestjs.mdx#typemo-module.for-feature) каждого из них. Провайдер модели вызывает `connection.model(Account)` из ядра, а ядро возвращает один объект на сущность и базу. Поэтому оба модуля получают **один и тот же** объект — сравнение внедрённых моделей через `toBe` это подтвердило.

Регистрация по классу закрывает ошибку, которую не ловила регистрация по строке. Два разных класса `Account` в двух модулях — это две модели с двумя токенами, и ни одна молча не займёт место другой.

## Сущность в другой базе [#entity-in-other-database]

Архивные счета лежат в базе `archive` того же кластера. Второй аргумент `forFeature` задаёт цель записи — `{ db }` для базы, `{ client }` для другого клиента.

```ts twoslash title="archive/archive.service.ts"
import { Injectable, Module } from "@nestjs/common";
import { Entity, type Model, Prop, Schema } from "@venloc/typemo";
import { InjectModel, TypemoModule } from "@venloc/typemo-nestjs";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
}
// ---cut---
@Injectable()
export class ArchiveService {
  constructor(@InjectModel(Account, { db: "archive" }) private readonly archived: Model<Account>) {}
}

@Module({ imports: [TypemoModule.forFeature([Account], { db: "archive" })], providers: [ArchiveService] })
export class ArchiveModule {}
```

Цель входит в токен. `@InjectModel(Account)` и `@InjectModel(Account, { db: "archive" })` — две разные модели, и пишут они в разные базы. Имени коллекции в `forFeature` нет. Оно задаётся на сущности (`@Schema({ collection })`), а две регистрации одной сущности с разными коллекциями противоречили бы друг другу.

## Потомки-дискриминаторы [#discriminator-children]

У события есть виды, например переход по ссылке и регистрация, и все они лежат в одной коллекции. Потомки описываются через [`@Discriminator`](../../reference/schemas/discriminator.mdx) как обычно, а в `forFeature` их можно перечислять в любом порядке.

```ts twoslash title="events/events.module.ts"
import { Module } from "@nestjs/common";
import { Discriminator, type DiscriminatorValue, Entity, Prop, Schema } from "@venloc/typemo";
import { TypemoModule } from "@venloc/typemo-nestjs";
// ---cut---
@Schema({ collection: "events" })
export class Event extends Entity {
  declare readonly __t?: DiscriminatorValue<"click" | "signup">;

  @Prop(() => Date, { required: true })
  time!: Date;
}

@Discriminator("click")
export class ClickEvent extends Event {
  declare readonly __t: DiscriminatorValue<"click">;

  @Prop(() => String, { required: true })
  url!: string;
}

@Module({ imports: [TypemoModule.forFeature([ClickEvent, Event])] })
export class EventsModule {}
```

Ядро само знает, что `ClickEvent` — потомок `Event`, и создаёт его модель в коллекции базы. При трёх разных порядках в списке получилась одна коллекция `events`, а у созданного перехода `__t` равно `"click"`. Если в списке только потомок, база компилируется для него в той же коллекции, но провайдера у неё не будет. Чтобы внедрить модель базы, перечислите и её.

## Модель со статиками плагина [#model-with-plugin-statics]

Плагин добавляет моделям статический метод, и сервис хочет вызывать его на внедрённой модели с типом. Запись `{ entity, statics }` внедряет модель, к которой применён [`Model.statics(plugin)`](../../reference/hooks/plugins.mdx#model.statics).

```ts twoslash title="notes/notes.module.ts"
import { Injectable, Module } from "@nestjs/common";
import { Entity, type Model, Plugin, type PluginStatics, Prop, Schema, type SchemaPlugin } from "@venloc/typemo";
import { InjectModel, TypemoModule } from "@venloc/typemo-nestjs";
// ---cut---
const countPlugin = {
  name: "count",
  apply: () => undefined,
  statics: {
    countTitled(this: Model<object>, title: string): Promise<number> {
      return (this as unknown as Model<Note>).countDocuments({ title });
    },
  },
} satisfies SchemaPlugin<undefined, object>;

@Plugin(countPlugin)
@Schema({ collection: "notes" })
export class Note extends Entity {
  @Prop(() => String, { required: true })
  title!: string;
}

@Injectable()
export class NotesService {
  constructor(@InjectModel(Note) private readonly notes: Model<Note> & PluginStatics<typeof countPlugin>) {}

  count(title: string) {
    return this.notes.countTitled(title);
  }
}

@Module({ imports: [TypemoModule.forFeature([{ entity: Note, statics: countPlugin }])], providers: [NotesService] })
export class NotesModule {}
```

Тип параметра вы пишете сами — `Model<Note> & PluginStatics<typeof countPlugin>`. При старте модуль проверяет, что плагин действительно применён к схеме, иначе тип обещал бы метод, которого нет. Без `@Plugin(countPlugin)` на сущности старт упадёт с `ConfigurationError: Note: plugin "count" is not applied to this model's schema`.

## Представление [#view]

Сервису нужны только счета с деньгами, и это условие должно жить в одном месте. Представление описывают через [`TypemoModule.view`](../../reference/integrations/nestjs.mdx#typemo-module.view) и перечисляют в том же `forFeature`.

```ts twoslash title="accounts/accounts.module.ts"
import { Injectable, Module } from "@nestjs/common";
import { Entity, Prop, Schema, type TypedView } from "@venloc/typemo";
import { InjectModel, TypemoModule } from "@venloc/typemo-nestjs";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true, min: 0 }) balance!: number;
}
// ---cut---
@Schema({ collection: "funded_accounts" })
export class FundedAccount extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) balance!: number;
}

const funded = TypemoModule.view(FundedAccount, {
  on: Account,
  pipeline: (p) => p.match({ balance: { $gt: 0 } }).project({ title: 1, balance: 1 }),
});

@Injectable()
export class FundedService {
  constructor(@InjectModel(FundedAccount) private readonly funded: TypedView<FundedAccount>) {}

  titles() {
    return this.funded.find({}).then((rows) => rows.map((row) => row.title));
  }
}

@Module({ imports: [TypemoModule.forFeature([Account, funded])], providers: [FundedService] })
export class AccountsModule {}
```

Внедряется [`TypedView`](../../reference/collections/typed-view.mdx), и он умеет только читать. Конвейер проверяется по классу при компиляции. Если `project` не даст `balance`, определение не скомпилируется. Из двух счетов, `Main` с балансом 5 и `Empty` с 0, представление вернуло только `Main`.

Создаёт представление в базе опция `sync` при старте, о ней ниже. Пока его нет, чтение бросит [`ConfigurationError`](../../reference/errors/configuration-errors.mdx#configuration-error), а не вернёт пустой список.

Класс в базе — что-то одно, модель или представление. Если зарегистрировать `FundedAccount` моделью в одном модуле и представлением в другом, старт упадёт с `ConfigurationError`. Иначе в приложении оказались бы два разных объекта одной коллекции.

## Материализованный результат [#materialized-result]

Сводка по счетам считается дорого, и пересчитывать её достаточно по расписанию. [`TypemoModule.materialized`](../../reference/integrations/nestjs.mdx#typemo-module.materialized) описывает обычную коллекцию, которую заполняет конвейер.

```ts twoslash title="reports/reports.module.ts"
import { Injectable, Module } from "@nestjs/common";
import { Entity, EntityWithId, fn, type Materialized, Prop, Schema } from "@venloc/typemo";
import { InjectModel, TypemoModule } from "@venloc/typemo-nestjs";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true, min: 0 }) balance!: number;
}
// ---cut---
@Schema({ collection: "title_totals" })
export class TitleTotal extends EntityWithId(() => String) {
  @Prop(() => Number, { required: true }) total!: number;
}

const totals = TypemoModule.materialized(TitleTotal, {
  from: Account,
  pipeline: (p) => p.match({ balance: { $gt: 0 } }).group((f) => ({ _id: f.title, total: fn.sum(f.balance) })),
  mode: "replace",
});

@Injectable()
export class TotalsService {
  constructor(@InjectModel(TitleTotal) private readonly totals: Materialized<TitleTotal>) {}

  async rebuild() {
    await this.totals.refresh();
    return this.totals.model.find({}).lean();
  }
}

@Module({ imports: [TypemoModule.forFeature([Account, totals])], providers: [TotalsService] })
export class ReportsModule {}
```

На тех же двух счетах `rebuild()` вернул `[{ _id: "Main", total: 5 }]`. Сам результат не пересчитывается. `refresh()` вызывает ваш код, например задача по расписанию или обработчик.

## Создать коллекции при старте [#create-collections-on-start]

Окружение новое, базы ещё нет, а уникальный индекс должен появиться до первой записи. Опция [`sync`](../../reference/integrations/nestjs.mdx#sync) в корневом `forRoot` решает, что модуль сделает с базой при старте.

- `false` (по умолчанию) — ничего. Запуск приложения базу не меняет.
- `"init"` — [`connection.init()`](../../reference/connection/connection.mdx#connection.init). Создаёт недостающие коллекции, индексы и представления, ничего не меняя и не удаляя.
- `"sync"` — [`connection.syncAll()`](../../reference/connection/connection.mdx#connection.sync-all). Приводит всё к схемам и, например, заменяет индекс, объявленный иначе.

Синхронизация идёт после того, как все модули зарегистрировали модели, для каждой базы, где есть модели из `forFeature`. С `sync: "init"` и сущностью с уникальным полем появились коллекция и индексы `_id_` и `code_1`, а с `sync: false` база осталась пустой. Если индекс в базе объявлен иначе, `"init"` уронит старт с [`SyncError`](../../reference/errors/configuration-errors.mdx#sync-error), а `"sync"` заменит индекс.

## Как выбрать `sync` [#how-to-choose]

Спросите себя, кто в вашем окружении отвечает за схему базы.

- **Есть шаг развёртывания или миграции** — оставьте `false` и вызывайте там `connection.init()` или `syncAll()`. Десять запущенных копий приложения не должны десять раз перестраивать индексы.
- **Отдельного шага нет** — в разработке, тестах или небольшом приложении. Тогда `"init"` безопасен, он только добавляет недостающее.
- **Приложение — единственный владелец схемы**, и замена индекса при выкладке ожидаема. Тогда `"sync"`, но помните, что перестроение большого индекса нагружает сервер.

## Когда это не нужно [#when-not-to-use]

Модулю, которому нужен только сервис другого модуля, `forFeature` импортировать не надо. Модель — внутреннее дело модуля-владельца. Разовую сводку, которую не нужно хранить, считайте агрегацией в сервисе ([`Model.aggregate`](../../reference/aggregation/pipeline.mdx#model.aggregate)), а не материализованным результатом.

## Если что-то пошло не так [#troubleshooting]

**Сущность перечислена дважды.** `forFeature([Account, Account])` или `[Account, { entity: Account, statics }]` падают прямо при вызове — `ConfigurationError: TypemoModule.forFeature: Account is listed twice`. Оставьте одну запись и отдайте статики ей.

**`collection` в записи forFeature.** `forFeature([{ entity: Account, collection: "x" }])` не компилируется, а в обход типов падает с `unknown key "collection" in { entity: Account } (known: entity, statics)`. Коллекция задаётся на сущности.

**Класс без `@Schema`.** Старт падает с `ConfigurationError: NotASchema: not a schema; decorate the class with @Schema()`. А вот потомку-дискриминатору `@Schema` не нужен, он берёт опции базы.

## Полный пример [#full-example]

Модуль счетов — сущность с потомком, представление, сводка и создание коллекций при старте.

```ts twoslash title="accounts/accounts.module.ts"
import { Injectable, Module } from "@nestjs/common";
import {
  Discriminator,
  type DiscriminatorValue,
  Entity,
  EntityWithId,
  fn,
  type Materialized,
  type Model,
  Prop,
  Schema,
  type TypedView,
} from "@venloc/typemo";
import { InjectModel, TypemoModule } from "@venloc/typemo-nestjs";

// сущности
@Schema({ collection: "accounts" })
export class Account extends Entity {
  declare readonly __t?: DiscriminatorValue<"savings">;
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true, min: 0 }) balance!: number;
}

@Discriminator("savings")
export class SavingsAccount extends Account {
  declare readonly __t: DiscriminatorValue<"savings">;
  @Prop(() => Number, { required: true }) rate!: number;
}

// представление и сводка
@Schema({ collection: "funded_accounts" })
export class FundedAccount extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) balance!: number;
}
const funded = TypemoModule.view(FundedAccount, {
  on: Account,
  pipeline: (p) => p.match({ balance: { $gt: 0 } }).project({ title: 1, balance: 1 }),
});

@Schema({ collection: "title_totals" })
export class TitleTotal extends EntityWithId(() => String) {
  @Prop(() => Number, { required: true }) total!: number;
}
const totals = TypemoModule.materialized(TitleTotal, {
  from: Account,
  pipeline: (p) => p.group((f) => ({ _id: f.title, total: fn.sum(f.balance) })),
  mode: "replace",
});

// сервис
@Injectable()
export class AccountsService {
  constructor(
    @InjectModel(Account) private readonly accounts: Model<Account>,
    @InjectModel(SavingsAccount) private readonly savings: Model<SavingsAccount>,
    @InjectModel(FundedAccount) private readonly funded: TypedView<FundedAccount>,
    @InjectModel(TitleTotal) private readonly totals: Materialized<TitleTotal>,
  ) {}

  openSavings(title: string, rate: number) {
    return this.savings.create({ title, rate, balance: 0 });
  }

  fundedTitles() {
    return this.funded.find({}).then((rows) => rows.map((row) => row.title));
  }

  refreshTotals() {
    return this.totals.refresh();
  }
}

// модули
@Module({
  imports: [TypemoModule.forFeature([Account, SavingsAccount, funded, totals])],
  providers: [AccountsService],
})
export class AccountsModule {}

@Module({
  imports: [TypemoModule.forRoot("mongodb://localhost:27017", { dbName: "bank", sync: "init" }), AccountsModule],
})
export class AppModule {}
```

<Callout type="migration" title="Если вы пришли из @nestjs/mongoose">

`forFeature([{ name, schema, discriminators }])` → `forFeature([Сущность, Потомок])`, потомки здесь — обычные записи. `forFeatureAsync` со схемой из фабрики и внедрением нет. Плагины подключаются декоратором `@Plugin` или в `onClientCreate`. Представления регистрируются в том же `forFeature`, а не отдельным списком.

</Callout>
