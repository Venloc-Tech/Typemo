`@venloc/typemo-nestjs` устроен так же, как `@nestjs/mongoose`: корневой `forRoot`, `forFeature` в модулях, `@InjectModel` в сервисах. Отличия — в том, что стоит за этими именами: модель регистрируется классом, а не строкой; схема — сам класс сущности; тип модели выводится; ошибки базы и проверка тела запроса закрыты пакетом. Эта страница — таблица соответствия и порядок перехода.

Если вы переводите и сами модели с Mongoose на Typemo, сначала прочитайте [Пошаговую миграцию](../../migration/step-by-step.mdx): здесь речь только о слое Nest.

## Что предполагается

Приложение на NestJS 12 с `@nestjs/mongoose` и сущности, уже описанные классами Typemo (`@Schema`, `@Prop` из `@venloc/typemo`).

## Быстрый путь

Корневой модуль, модуль фичи и сервис — до и после:

<Compare labels={["@nestjs/mongoose", "@venloc/typemo-nestjs"]}>

```ts
@Module({
  imports: [
    MongooseModule.forRoot("mongodb://localhost/bank"),
    MongooseModule.forFeature([{ name: Cat.name, schema: CatSchema }]),
  ],
})
export class AppModule {}

@Injectable()
export class CatsService {
  constructor(@InjectModel(Cat.name) private catModel: Model<CatDocument>) {}
}
```

```ts
@Module({
  imports: [
    TypemoModule.forRoot("mongodb://localhost:27017", { dbName: "bank" }),
    TypemoModule.forFeature([Cat]),
  ],
})
export class AppModule {}

@Injectable()
export class CatsService {
  constructor(@InjectModel(Cat) private readonly cats: Model<Cat>) {}
}
```

</Compare>

## Соответствие API

| `@nestjs/mongoose` | `@venloc/typemo-nestjs` | Что изменилось |
|---|---|---|
| `MongooseModule.forRoot(uri, options)` | [`TypemoModule.forRoot(uri, options)`](../../reference/integrations/nestjs.mdx#typemomoduleforroot) | опции клиента Typemo; `sync` для коллекций и индексов |
| `MongooseModule.forRootAsync({ useFactory, useClass, useExisting, inject, imports })` | [`TypemoModule.forRootAsync(...)`](../../reference/integrations/nestjs.mdx#typemomoduleforrootasync) | метод класса опций — `createTypemoOptions`; `uri` в результате |
| `connectionName` | `name` | рядом с фабрикой; в результате — ошибка компиляции |
| `retryAttempts`, `retryDelay` | те же | число попыток всего; неисправимые ошибки не повторяются |
| `lazyConnection` | тот же | `onClientCreate` вызывается и при нём |
| `connectionFactory(connection, name)` | [`clientFactory(client)`](../../reference/integrations/nestjs.mdx#clientfactory) | |
| `connectionErrorFactory(error)` | [`clientErrorFactory(error)`](../../reference/integrations/nestjs.mdx#clienterrorfactory) | |
| `onConnectionCreate(connection)` | [`onClientCreate(client)`](../../reference/integrations/nestjs.mdx#onclientcreate) | один раз на клиента, до первой модели |
| `MongooseModule.forFeature([{ name, schema, collection }], connectionName)` | [`TypemoModule.forFeature([Entity], { client, db })`](../../reference/integrations/nestjs.mdx#typemomoduleforfeature) | по классу; коллекция — на сущности; `db` — другая база клиента |
| `discriminators: [{ name, schema, value }]` | потомок `@Discriminator` в том же списке | |
| `MongooseModule.forFeatureAsync` | нет | плагины — `@Plugin` или `onClientCreate` |
| `@InjectModel(Cat.name, connectionName)` | [`@InjectModel(Cat, { client, db })`](../../reference/integrations/nestjs.mdx#injectmodel) | |
| `@InjectConnection(name)` | [`@InjectConnection({ client, db })`](../../reference/integrations/nestjs.mdx#injectconnection) и [`@InjectClient(name)`](../../reference/integrations/nestjs.mdx#injectclient) | подключение к базе и клиент — разные объекты |
| `getModelToken(Cat.name)` | [`getModelToken(Cat)`](../../reference/integrations/nestjs.mdx#getmodeltoken) | символ, а не строка |
| `getConnectionToken(name)` | [`getConnectionToken({ client, db })`](../../reference/integrations/nestjs.mdx#getconnectiontoken), [`getClientToken(name)`](../../reference/integrations/nestjs.mdx#getclienttoken) | |
| `ParseObjectIdPipe`, `IsObjectIdPipe` | [`ParseIdPipe.for(Entity)`](../../reference/integrations/nestjs.mdx#parseidpipe) | любой тип `_id` |
| `@Schema`, `@Prop`, `SchemaFactory`, `raw` | `@Schema`, `@Prop` из `@venloc/typemo` | схема — сам класс |
| `Model<CatDocument>` | `Model<Cat>` | тип выводится из класса |
| `connection.startSession()` + `session` в каждой операции | [`@Transactional()`](../../reference/integrations/nestjs.mdx#transactional) | сессия неявная |
| — | [`TypemoExceptionFilter`](../../reference/integrations/nestjs.mdx#typemoexceptionfilter), [`ValidateBodyPipe`](../../reference/integrations/nestjs.mdx#validatebodypipe), [`PolicyInterceptor`](../../reference/integrations/nestjs.mdx#policyinterceptor) | новое |

## Перейти по шагам

<Steps>
<Step>

### Установите пакет

```package-install
@venloc/typemo @venloc/typemo-nestjs mongodb
```

`@nestjs/mongoose` и `mongoose` пока остаются: модули переводятся по одному.

</Step>
<Step>

### Добавьте TypemoModule.forRoot рядом с MongooseModule.forRoot

Оба модуля могут жить в одном приложении: токены не пересекаются (`TypemoClient:default` и модели-символы против строк `DatabaseConnection` и `CatModel`). Пока идёт переход, приложение держит два пула соединений к одной базе.

</Step>
<Step>

### Переведите модуль

В модуле фичи замените `MongooseModule.forFeature` на `TypemoModule.forFeature([Cat])`, `@InjectModel(Cat.name)` — на `@InjectModel(Cat)` из `@venloc/typemo-nestjs`, тип `Model<CatDocument>` — на `Model<Cat>` из `@venloc/typemo`. Компилятор покажет каждое место, где сервис пользовался API Mongoose: `.exec()`, колбэки, `lean<T>()` с ручным типом.

</Step>
<Step>

### Включите фильтр и пайпы

`app.useGlobalFilters(new TypemoExceptionFilter())` превращает ошибки моделей Typemo в ответы. DTO, которые повторяли поля сущности, заменяет `ValidateBodyPipe.for(Entity)`, а `ParseObjectIdPipe` — `ParseIdPipe.for(Entity)`.

</Step>
<Step>

### Уберите Mongoose

Когда последний модуль переведён, удалите `MongooseModule.forRoot`, пакеты `@nestjs/mongoose` и `mongoose`.

</Step>
</Steps>

## Отличия, которые заметит приложение

**Модели по классу.** `@InjectModel("Cat")` с опечаткой в `@nestjs/mongoose` находится только при старте, а модель, уже созданная на подключении под этим именем, переиспользуется молча — даже с другой схемой. Здесь в декоратор передаётся класс: опечатки нет, а два класса с одним именем — две модели.

**`name` в результате фабрики.** В `@nestjs/mongoose` `connectionName` внутри `useFactory` компилировался, а при старте драйвер отвергал неизвестную опцию, и модуль уходил в повторы. Здесь это ошибка компиляции, а при обходе типов — одна понятная ошибка без повторов.

**`lazyConnection`.** `@nestjs/mongoose` с ним не вызывает `onConnectionCreate` и не сообщает о неудачном подключении. Здесь `onClientCreate` вызывается всегда, а неудача пишется в лог.

**Повторы.** В `@nestjs/mongoose` каждая попытка создаёт новое подключение, и `onConnectionCreate` вызывается на каждую. Здесь клиент один: `onClientCreate` вызывается один раз, расширения регистрируются один раз. Неверный пароль не повторяется.

**Неизвестное поле в теле.** Mongoose в строгом режиме выбрасывает его молча, и запрос без обязательного поля падает 500. В Typemo неизвестное поле — ошибка: без пайпа фильтр отвечает 400 с именем поля, с `ValidateBodyPipe` — 422 со всеми ошибками сразу.

**Ошибки базы.** В `@nestjs/mongoose` фильтра нет: дубликат ключа доходит до клиента как 500. `TypemoExceptionFilter` отвечает 409 с именами полей.

**Коллекции и индексы.** Mongoose создаёт их при компиляции модели (`autoCreate`, `autoIndex`). Typemo не пишет в базу, пока вы не попросите: `sync: "init"` или шаг развёртывания.

## Когда это не нужно

Если приложение остаётся на Mongoose, этот пакет не нужен: он работает только с моделями Typemo. Переводить слой Nest раньше моделей нельзя — `@InjectModel` из этого пакета внедряет модель Typemo.

## Частые ошибки

### Токен модели не найден после замены импорта

`@InjectModel` импортирован из `@venloc/typemo-nestjs`, а модуль всё ещё импортирует `MongooseModule.forFeature`. Замените и `forFeature`: токены двух пакетов разные.

### Класс опций не подходит для useClass

Метод класса опций называется `createTypemoOptions`, а не `createMongooseOptions`, и возвращает `uri` внутри объекта.

## Полный пример

Модуль котов после перехода: модель, сервис, контроллер с пайпами.

```ts twoslash title="cats/cats.module.ts"
import { Body, Controller, Get, Injectable, Module, Param, Post } from "@nestjs/common";
import { type CreateInput, Entity, type IdOf, type Model, Prop, type Ref, Schema, Types } from "@venloc/typemo";
import { InjectModel, ParseIdPipe, TypemoModule, ValidateBodyPipe } from "@venloc/typemo-nestjs";

// схема — это класс
@Schema({ collection: "cats" })
export class Cat extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => String) breed?: string;
  @Prop(() => [Types.ObjectId], { ref: () => Cat, default: () => [] }) kittens!: Ref<Cat>[];
}

// сервис
@Injectable()
export class CatsService {
  constructor(@InjectModel(Cat) private readonly cats: Model<Cat>) {}

  async create(body: CreateInput<Cat>) {
    return (await this.cats.create(body)).$toPlain();
  }

  findOne(id: IdOf<Cat>) {
    return this.cats.findById(id).populate("kittens").orFail().plain();
  }
}

// контроллер
@Controller("cats")
export class CatsController {
  constructor(private readonly service: CatsService) {}

  @Post()
  create(@Body(ValidateBodyPipe.for(Cat)) body: CreateInput<Cat>) {
    return this.service.create(body);
  }

  @Get(":id")
  findOne(@Param("id", ParseIdPipe.for(Cat)) id: IdOf<Cat>) {
    return this.service.findOne(id);
  }
}

@Module({ imports: [TypemoModule.forFeature([Cat])], controllers: [CatsController], providers: [CatsService] })
export class CatsModule {}
```

Это приложение котов из тестов самого `@nestjs/mongoose`, переписанное на Typemo: запуск его тестов («should return created document», «should populate array of kittens») прошёл. Отличие одно: тело с неизвестным полем там даёт 500, а здесь 400 с именем поля.
