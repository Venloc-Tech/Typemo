На границе HTTP приложению нужны три вещи. Превратить ошибку базы в понятный ответ, разобрать id из адреса и проверить тело запроса до записи. Для этого в пакете есть фильтр `TypemoExceptionFilter` и пайпы `ParseIdPipe` и `ValidateBodyPipe`. Все три работают в HTTP-контексте Express.

## Что понадобится [#prerequisites]

Приложение из руководства [Подключить Typemo к NestJS](./setup.mdx). Модель пользователя растёт по ходу страницы, а в начале у неё два поля.

```ts twoslash title="users/user.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true, unique: true })
  email!: string;

  @Prop(() => String, { required: true, minLength: 2 })
  name!: string;
}
```

## Быстрый путь [#quick-start]

Фильтр подключается один раз, а пайпы — на параметрах обработчика.

```ts twoslash title="users/users.controller.ts"
import { Body, Controller, Get, Param, Post } from "@nestjs/common";
import { type CreateInput, Entity, type IdOf, type Model, Prop, Schema } from "@venloc/typemo";
import { InjectModel, ParseIdPipe, ValidateBodyPipe } from "@venloc/typemo-nestjs";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true, unique: true }) email!: string;
  @Prop(() => String, { required: true, minLength: 2 }) name!: string;
}
// ---cut---
@Controller("users")
export class UsersController {
  constructor(@InjectModel(User) private readonly users: Model<User>) {}

  @Post()
  async create(@Body(ValidateBodyPipe.for(User)) body: CreateInput<User>) {
    return (await this.users.create(body)).$toPlain();
  }

  @Get(":id")
  get(@Param("id", ParseIdPipe.for(User)) id: IdOf<User>) {
    return this.users.findById(id).orFail().plain();
  }
}

// main.ts: app.useGlobalFilters(new TypemoExceptionFilter());
```

Ниже разберём каждую часть на задачах.

## Ответить на ошибку базы [#handle-database-error]

Запись нарушила уникальный индекс, документ не нашёлся или база не ответила вовремя. Клиенту нужен понятный статус, а не 500 с текстом сервера. [`TypemoExceptionFilter`](../../reference/integrations/nestjs.mdx#typemo-exception-filter) определяет вид ошибки через [`ErrorClassifier.classify`](../../reference/errors/hierarchy.mdx#classify) и отвечает в том же формате, что и ошибки самого Nest, — `statusCode`, `error`, `message` и поля, зависящие от вида.

```ts twoslash title="main.ts"
import { Module } from "@nestjs/common";
import { NestFactory } from "@nestjs/core";
import { TypemoExceptionFilter } from "@venloc/typemo-nestjs";
@Module({})
class AppModule {}
// ---cut---
const app = await NestFactory.create(AppModule);
app.useGlobalFilters(new TypemoExceptionFilter());
```

Второй пользователь с тем же адресом почты получит 409 с **именами** полей ключа.

```json
{ "statusCode": 409, "error": "Conflict", "message": "Duplicate value", "fields": ["email"] }
```

Значения в ответ не попадают. Поле ключа может быть скрытым или `sensitive`, а чужой адрес почты незачем возвращать тому, кто пытается его угадать.

Остальные виды ошибок отвечают так.

- `orFail()`, который ничего не нашёл, — 404 `{ "message": "Not found" }`.
- Истёкший `timeoutMS` — 504.
- Недоступная база — 503.
- Всё нераспознанное — 500 без текста сервера, потому что в нём бывают адреса узлов и фрагменты данных.

Полная таблица видов и статусов — в справочнике фильтра.

Ошибки «сырого» драйвера, полученные через `client.unsafeDriver()`, фильтр классифицирует так же. Дубликат `_id`, вставленный напрямую драйвером, тоже даст 409. Ответы 500 фильтр пишет в лог Nest вместе с текстом ошибки, чтобы причину можно было найти.

## Свой формат ответа [#custom-response]

Если у API принят свой формат ошибок, унаследуйте фильтр и переопределите [`toResponse`](../../reference/integrations/nestjs.mdx#to-response) для нужных видов.

```ts twoslash title="errors/api-exception.filter.ts"
import type { ErrorClassification } from "@venloc/typemo";
import { TypemoExceptionFilter, type TypemoHttpResponse } from "@venloc/typemo-nestjs";
// ---cut---
export class ApiExceptionFilter extends TypemoExceptionFilter {
  override toResponse(error: unknown, classification: ErrorClassification): TypemoHttpResponse {
    if (classification.kind === "duplicate-key") return { status: 409, body: { code: "ALREADY_EXISTS" } };
    return super.toResponse(error, classification);
  }
}
```

Фильтр ловит только ошибки Typemo и драйвера. `NotFoundException` и другие ошибки Nest, как и ваши собственные, обрабатываются как обычно.

## Разобрать id из адреса [#parse-id]

На маршрут `GET /users/:id` в адрес может прийти что угодно. [`ParseIdPipe.for(User)`](../../reference/integrations/nestjs.mdx#parse-id-pipe) превращает строку в `_id` модели или отвечает 400.

```text
GET /users/not-an-id
→ 400 { "message": "Invalid id: expected ObjectId (not a 24-character hex string)" }
```

Пайп знает тип `_id` модели — `ObjectId`, `UUID`, строка ([`EntityWithId`](../../reference/schemas/base-classes.mdx#entity-with-id)) или число. Числовой `_id` он разбирает строго. `"42"` даёт `42`, а `"42abc"` — 400 `Invalid id: expected number (expected a number)`, а не 42, как вернул бы `parseInt`. Тип параметра — [`IdOf<User>`](../../reference/values/form-types.mdx#helper-types), тот же, что принимает `findById`.

## Проверить тело запроса схемой [#validate-body]

`POST /users` принимает JSON, и его нужно проверить до записи. [`ValidateBodyPipe.for(User)`](../../reference/integrations/nestjs.mdx#validate-body-pipe) проверяет тело самой сущностью — типы, `required`, длины, `min` и `max`, `enum`, валидаторы. Поэтому отдельный класс DTO, который пришлось бы держать в согласии с сущностью, не нужен. Добавим модели возраст и роль.

```ts twoslash title="users/user.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";
// ---cut---
@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true, unique: true })
  email!: string;

  @Prop(() => String, { required: true, minLength: 2 })
  name!: string;

  @Prop(() => Number, { min: 0, max: 150 }) // [!code ++]
  age?: number; // [!code ++]

  @Prop(() => String, { enum: ["user", "admin"] as const }) // [!code ++]
  role?: "user" | "admin"; // [!code ++]
}
```

Тело `{ "email": "bob@x.io", "name": "B", "age": 200, "role": "root" }` получит один ответ 422 сразу со всеми ошибками.

```json
{
  "statusCode": 422,
  "error": "Unprocessable Entity",
  "message": "Validation failed",
  "errors": {
    "name": "must be at least 2 characters long",
    "age": "must be at most 150",
    "role": "must be one of \"user\", \"admin\""
  }
}
```

Пайп возвращает присланные поля, уже приведённые к типам, но без значений по умолчанию — их добавит `create`. Тип параметра — [`CreateInput<User>`](../../reference/writes/input-types.mdx#create-input).

## Неизвестные и запрещённые поля [#unknown-and-forbidden-fields]

Клиент прислал поле, которого у сущности нет, или поле, которое ему задавать нельзя. Неизвестное поле по умолчанию даёт 422 `{ "nickname": "not a field of User" }`. Опечатка вроде `emial` не пропадёт молча, и клиент сразу узнает, что поле не принято. Если API должно терпеть лишние поля, включите `dropUnknown: true`, и они будут выброшены.

Поле, которое клиенту задавать нельзя, например роль или владельца, исключите опцией `omit`.

```ts twoslash title="users/users.controller.ts"
import { Body, Controller, Post } from "@nestjs/common";
import { type CreateInput, Entity, type Model, Prop, Schema } from "@venloc/typemo";
import { InjectModel, ValidateBodyPipe } from "@venloc/typemo-nestjs";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true, unique: true }) email!: string;
  @Prop(() => String, { required: true, minLength: 2 }) name!: string;
  @Prop(() => String, { enum: ["user", "admin"] as const }) role?: "user" | "admin";
}
// ---cut---
@Controller("signup")
export class SignupController {
  constructor(@InjectModel(User) private readonly users: Model<User>) {}

  @Post()
  async signUp(@Body(ValidateBodyPipe.for(User, { omit: ["role"] })) body: CreateInput<User>) {
    return (await this.users.create({ ...body, role: "user" })).$toPlain();
  }
}
```

`role` в теле даст 422 `{ "role": "not allowed here" }`. `pick` делает обратное и принимает только перечисленные поля. Имена в `pick` и `omit` проверяет компилятор.

Строка вместо числа (`"age": "30"`) — тоже 422, потому что ядро не приводит строки к числам. В JSON число приходит числом, и `"30"` в числовом поле говорит об ошибке клиента.

## Частичное обновление [#partial-update]

`PATCH /users/:id` присылает одно поле. `partial: true` проверяет только присланные поля, и обязательного поля может не быть.

```ts twoslash title="users/users.controller.ts"
import { Body, Controller, Param, Patch } from "@nestjs/common";
import { Entity, type IdOf, type Model, Prop, Schema, type UpdateInput } from "@venloc/typemo";
import { InjectModel, ParseIdPipe, ValidateBodyPipe } from "@venloc/typemo-nestjs";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true, unique: true }) email!: string;
  @Prop(() => String, { required: true, minLength: 2 }) name!: string;
  @Prop(() => Number, { min: 0, max: 150 }) age?: number;
}
// ---cut---
@Controller("users")
export class UsersController {
  constructor(@InjectModel(User) private readonly users: Model<User>) {}

  @Patch(":id")
  update(
    @Param("id", ParseIdPipe.for(User)) id: IdOf<User>,
    @Body(ValidateBodyPipe.for(User, { partial: true })) body: UpdateInput<User>,
  ) {
    return this.users.findByIdAndUpdate(id, { $set: body }).orFail().plain();
  }
}
```

Тип тела обновления — [`UpdateInput<User>`](../../reference/writes/input-types.mdx#update-input). В нём нет `_id` и неизменяемых полей, и его принимает `$set`. Пайп отвергает такие поля и во время работы — `{ "_id": …, "createdAt": … }` в теле `PATCH` даёт 422 `"cannot be changed"`. А `{ "age": -1 }` даёт 422 `{ "age": "must be at least 0" }`.

## Как выбрать между ValidateBodyPipe и своим DTO [#how-to-choose]

Спросите себя, совпадает ли тело запроса с документом.

- **Тело — это поля сущности**, при создании или изменении. Берите `ValidateBodyPipe`, он проверит тело той же схемой, что и запись, и правила не разойдутся.
- **Тело другой формы**, например команда «перевести 100 со счёта A на счёт B» или вложенный запрос поиска. Это не документ, опишите DTO своим валидатором. Модель Typemo реализует Standard Schema, так что валидаторы, которые её понимают, могут проверять и документы.

## Когда это не нужно [#when-not-to-use]

Даже если обработчик принимает id и сразу отдаёт его в `findById`, `ParseIdPipe` полезен. Без него неверный id стал бы ошибкой приведения внутри запроса (400 от фильтра с `path: "_id"`), а не понятным ответом о параметре. А вот фильтр не нужен приложению со своим общим обработчиком ошибок. Используйте в нём `ErrorClassifier.classify` напрямую.

## Если что-то пошло не так [#troubleshooting]

**Ответ 500 вместо 409 или 422.** Фильтр не подключён, и ошибка дошла до обработчика Nest по умолчанию. Добавьте `app.useGlobalFilters(new TypemoExceptionFilter())` или `{ provide: APP_FILTER, useClass: TypemoExceptionFilter }`.

**Неизвестное поле в теле без пайпа даёт 400.** Без `ValidateBodyPipe` тело уходит прямо в `create`, и ядро отвергает неизвестное поле ошибкой приведения. Фильтр отвечает 400 `{ "message": "Invalid value", "path": "nickname" }`. С пайпом будет 422 и сразу все ошибки.

**PATCH отвергает createdAt.** Метки времени ведёт ядро, и клиент их не меняет, поэтому `partial` отвечает `"cannot be changed"`. Уберите поле из тела или включите `dropUnknown`.

## Полный пример [#full-example]

Контроллер пользователей — создание без роли, чтение по id и частичное обновление. Фильтр подключён в `main.ts`.

```ts twoslash title="users/users.controller.ts"
import { Body, Controller, Get, Param, Patch, Post } from "@nestjs/common";
import { type CreateInput, Entity, type IdOf, type Model, Prop, Schema, type UpdateInput } from "@venloc/typemo";
import { InjectModel, ParseIdPipe, ValidateBodyPipe } from "@venloc/typemo-nestjs";

// модель
@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true, unique: true }) email!: string;
  @Prop(() => String, { required: true, minLength: 2 }) name!: string;
  @Prop(() => Number, { min: 0, max: 150 }) age?: number;
  @Prop(() => String, { enum: ["user", "admin"] as const }) role?: "user" | "admin";
}

@Controller("users")
export class UsersController {
  constructor(@InjectModel(User) private readonly users: Model<User>) {}

  // создание: роль задаёт сервер
  @Post()
  async create(@Body(ValidateBodyPipe.for(User, { omit: ["role"] })) body: CreateInput<User>) {
    return (await this.users.create({ ...body, role: "user" })).$toPlain();
  }

  // чтение: неверный id — 400, отсутствующий — 404
  @Get(":id")
  get(@Param("id", ParseIdPipe.for(User)) id: IdOf<User>) {
    return this.users.findById(id).orFail().plain();
  }

  // частичное обновление
  @Patch(":id")
  update(
    @Param("id", ParseIdPipe.for(User)) id: IdOf<User>,
    @Body(ValidateBodyPipe.for(User, { partial: true, omit: ["role"] })) body: UpdateInput<User>,
  ) {
    return this.users.findByIdAndUpdate(id, { $set: body }).orFail().plain();
  }
}
```

<Callout type="migration" title="Если вы пришли из @nestjs/mongoose">

`ParseObjectIdPipe` → `ParseIdPipe.for(Entity)`, и он понимает любой тип `_id`, а не только `ObjectId`. Фильтра ошибок в `@nestjs/mongoose` нет, и ошибка уникального индекса доходит там до клиента как 500. DTO с `class-validator` для полей сущности заменяет `ValidateBodyPipe`.

</Callout>
