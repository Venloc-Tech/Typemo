Хук операции — это метод модели, который Typemo вызывает до и после запроса, будь то `find`, `updateMany`, `deleteMany`, `aggregate` или другой. Он нужен, когда правило должно действовать сразу на все пути к данным. Например, не показывать архивные записи, увеличивать счётчик ревизий при каждом обновлении или прогонять запись вхолостую. Хук пишется один раз в модели, и вызывающий код о нём ничего не знает.

Если нужно что-то сделать с документом — привести поле перед сохранением, проверить объект, — читайте руководство [Хуки документа](./document-hooks.mdx). У документа свои события. А если правило следует из смысла модели, как мягкое удаление или изоляция тенантов, для него есть [политики](../policies/soft-delete.mdx), и от хуков они не зависят.

## Что понадобится [#prerequisites]

- Клиент, подключённый по руководству [Подключиться к базе](../connection/connect.mdx).
- Модель счёта, которая будет расти по ходу страницы. `Accounts` — это `client.db().model(Account)`.
- Три счёта в коллекции — `a` и `b` у `alice`, `c` у `bob`.

## Быстрый путь [#quick-start]

Хук — это метод класса с декоратором [`@Pre`](../reference/hooks/pre-post.mdx#pre) или [`@Post`](../reference/hooks/pre-post.mdx#post). Событие называет операцию (`query.find`), а тип `this` — [`OperationHookContext`](../reference/hooks/operation-context.mdx#operation-hook-context). Чаще всего нужны три хука — добавить условие, дописать обновление и подменить результат.

```ts twoslash title="accounts/account.ts"
import { type Defaulted, Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => Boolean, { default: false })
  archived!: Defaulted<boolean>;

  @Pre("query.find")
  onlyActive(this: OperationHookContext<Account, "query.find">): void {
    this.modify({ where: { archived: false } });
  }
}
```

Теперь любой `find` этой модели пропускает архивные счета, даже если вызывающий код о них не думал. Дальше разберём каждое действие хука на задачах.

## Добавить условие ко всем чтениям [#filter-all-reads]

В интерфейсе десяток мест, где читаются счета, и ни одно не должно показывать архивные. Дописать `archived: false` в каждый запрос легко забыть. Хук сделает это один раз.

Метод [`.modify`](../reference/hooks/operation-context.mdx#modify) принимает ключ `where` — условие, которое Typemo соединяет с фильтром вызывающего кода через AND. Значит, хук только сужает выборку и никогда её не расширяет. То, что запросил вызывающий код, остаётся в силе.

```ts twoslash
import { type Defaulted, Entity, Schema, Prop, TypemoClient } from "@venloc/typemo";
import { Pre, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Boolean, { default: false }) archived!: Defaulted<boolean>;
  @Pre("query.find")
  onlyActive(this: OperationHookContext<Account, "query.find">): void {
    this.modify({ where: { archived: false } });
  }
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.db().model(Account);
// ---cut---
const mine = await Accounts.find({ owner: "alice" }).sort({ title: 1 }).plain();
console.log(mine.map((account) => account.title));
// → ["a", "b"]
```

В базу ушёл фильтр `{ owner: "alice", archived: false }`. Если бы у `b` было `archived: true`, в ответе остался бы только `a`. Условие хука проходит те же проверки, что и условие в запросе. Поле должно существовать в модели, а значение проходит приведение типа. Поэтому опечатку в хуке видно сразу, и текст у ошибки понятный.

```text
StrictModeError: filter: "nope" is not a field of Account [unknown-path]
```

Компилятор тоже подскажет, ведь `where` типизирован моделью так же, как фильтр `find`.

Если один метод должен обслуживать несколько чтений, перечислите события списком — `@Pre(["query.find", "query.findOne", "query.countDocuments"])`. Тогда `this` объявляется без второго параметра, а `modify({ where })` подходит всем событиям списка. `findById` запускает событие `query.findOne`, и `exists` тоже.

## Дописать обновление [#extend-update]

При любом обновлении счёта нужно увеличивать счётчик ревизий. Хук `modify` с ключом `update` добавляет операторы к обновлению вызывающего кода.

```ts twoslash
import { type Defaulted, Entity, Pre, Prop, Schema, TypemoClient, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Boolean, { default: false }) archived!: Defaulted<boolean>;
  @Prop(() => Number, { default: 0 }) revision!: Defaulted<number>; // [!code ++]

  @Pre("query.updateMany") // [!code ++]
  bumpRevision(this: OperationHookContext<Account, "query.updateMany">): void { // [!code ++]
    this.modify({ update: { $inc: { revision: 1 } } }); // [!code ++]
  } // [!code ++]
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.db().model(Account);
// ---cut---
const result = await Accounts.updateMany({ owner: "alice" }, { $set: { archived: true } });
console.log(result.modifiedCount);
// → 2
```

Вызывающий код писал только `$set`, а в базу ушли оба оператора — `$set` от него и `$inc` от хука. Поэтому `revision` у обоих счетов стал равен 1. Операторы объединяются по имени. Если `$inc` в обновлении уже был, пути хука допишутся в него.

Перезаписать значение, которое обновление уже пишет, хук не может. Один путь под одним оператором дважды — ошибка, иначе хук молча подменил бы значение вызывающего кода.

```text
QueryError: Account.updateOne: modify(): "$set.title" is already written by the update
```

Обновление конвейером (массив стадий) хуки тоже видят, но дописать в него `update` нельзя. Операторы в конвейер не вставить, и вы получите `QueryError`.

## Изменить выбор полей и сортировку [#change-select-and-sort]

Пусть в списке счетов нужен всегда один и тот же порядок. Ключи `select` и `sort` **заменяют** выбор полей и сортировку целиком, а не дополняют их.

```ts twoslash
import { Entity, Pre, Prop, Schema, TypemoClient, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;

  @Pre("query.find")
  newestFirst(this: OperationHookContext<Account, "query.find">): void {
    this.modify({ select: { title: 1 }, sort: { title: -1 } });
  }
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.db().model(Account);
// ---cut---
const rows = await Accounts.find().plain();
console.log(rows.map((row) => row.title));
// → ["c", "b", "a"]
```

Записи пришли в обратном порядке и только с полями `_id` и `title` — сортировку и проекцию вызывающего кода хук заменил. Поэтому `sort` и `select` в хуках используйте только там, где правило действительно общее.

## Пропустить операцию [#skip-operation]

Скрипт очистки должен уметь работать вхолостую — показать, что собирался сделать, и ничего не удалить. Метод [`.skip`](../reference/hooks/operation-context.mdx#skip) отменяет операцию. Запрос в базу не уходит, а вызывающий код получает переданный вами результат так, будто его вернул сервер.

```ts twoslash
import { Entity, Pre, Prop, Schema, TypemoClient, type OperationHookContext } from "@venloc/typemo";
export const settings = { dryRun: false };
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;

  @Pre("query.deleteMany")
  dryRun(this: OperationHookContext<Account, "query.deleteMany">): void {
    if (settings.dryRun) this.skip({ acknowledged: true, deletedCount: 0 });
  }
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.db().model(Account);
// ---cut---
settings.dryRun = true;
const result = await Accounts.deleteMany({ owner: "bob" });
console.log(result, await Accounts.countDocuments());
// → { acknowledged: true, deletedCount: 0 } 3
```

Хук передал результат удаления в той форме, в какой его вернул бы сервер, и `deleteMany` завершился без обращения к базе. Все три счёта на месте. После `skip` остальные хуки `@Pre` этой операции не запускаются, а хуки `@Post` запускаются и получают тот же результат.

Подложенный результат проходит остаток конвейера как настоящий. Если вы подставили документы для `find`, вызывающий код получит документы вашей модели. А если документ не подходит под схему, будет та же ошибка приведения, что и при чтении из базы. Хук не может вернуть данные, которых не вернул бы сервер.

```ts twoslash
import { Entity, Pre, Prop, Schema, TypemoClient, type OperationHookContext } from "@venloc/typemo";
import { ObjectId } from "mongodb";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;

  @Pre("query.find")
  fromCache(this: OperationHookContext<Account, "query.find">): void {
    this.skip([{ _id: new ObjectId(), title: "cached", owner: "nobody" }]);
  }
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.db().model(Account);
// ---cut---
const rows = await Accounts.find().plain();
console.log(rows.map((row) => row.title));
// → ["cached"]
```

## Измерить операцию [#measure-operation]

Нужно записать, сколько документов вернуло чтение и сколько времени оно заняло. Данные нужны и до операции, и после. Хуки `@Pre` и `@Post` обмениваются ими через `this.locals` — это `Map`, который создаётся заново для каждой операции.

```ts twoslash
import { Entity, Post, Pre, Prop, Schema, TypemoClient, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;

  @Pre("query.find")
  start(this: OperationHookContext<Account, "query.find">): void {
    this.locals.set("startedAt", performance.now());
  }

  @Post("query.find")
  finish(this: OperationHookContext<Account, "query.find">, result: readonly unknown[]): void {
    const startedAt = this.locals.get("startedAt") as number;
    console.log(`${this.model}.${this.operation}: ${result.length} документов за ${Math.round(performance.now() - startedAt)} мс`);
  }
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.db().model(Account);
// ---cut---
await Accounts.find({ owner: "alice" });
// → Account.find: 2 документов за … мс
```

`@Post` получил результат операции аргументом, а время взял из `locals`. У следующего запроса `Map` пустой, и значения разных операций не смешиваются. Если чтение идёт курсором, `@Post` вызывается на каждую порцию, которую база отдала целиком, а `locals` остаётся один на весь курсор.

Для метрик и трассировки в Typemo есть отдельный механизм — [события операций](../observability/events.mdx). Вмешаться в операцию он не может и ничего не стоит, пока нет подписчиков. Хуки для наблюдения нужны, только если вам нужен доступ к `this.locals` или к `modify`.

## Добавить стадии в агрегацию [#add-stages]

Пусть любая агрегация по счетам возвращает не больше десяти строк. Ключ `stages` дописывает стадии в конец конвейера, и они проходят те же шаги, что и стадии построителя.

```ts twoslash
import { Entity, Pre, Prop, Schema, TypemoClient, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;

  @Pre("aggregate")
  capRows(this: OperationHookContext<Account, "aggregate">): void {
    this.modify({ stages: [{ $limit: 1 }] });
  }
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.db().model(Account);
// ---cut---
const rows = await Accounts.aggregate((pipeline) => pipeline.match({ owner: "alice" }));
console.log(rows.length);
// → 1
```

В примере предел снижен до единицы, чтобы результат был виден на трёх счетах. Стадии хука идут после стадий построителя, поэтому предел хука срабатывает последним.

## Хуки операций внутри bulkWrite [#bulk-write-hooks]

Те же хуки вызываются и для операций внутри [`bulkWrite`](../reference/writes/writes.mdx#bulk-write). Каждая операция пакета — `updateOne`, `updateMany`, `replaceOne`, `deleteOne`, `deleteMany` — запускает хуки `query.*` своего отдельного аналога. Номер операции в списке хранит `this.bulkIndex`, а у обычного вызова он `undefined`.

- `modify` меняет только эту одну операцию.
- `skip` для отдельной операции пакета запрещён. Пакет целиком пропускает хук `model.bulkWrite`.
- `@Post` получает не `UpdateResult` и `DeleteResult`, а [`BulkOperationResult`](../reference/hooks/operation-context.mdx#bulk-operation-result). Счётчиков одной операции сервер не сообщает, и они равны `null`.

Поэтому хук `@Post("query.deleteMany")` в примере выше объявляет `deletedCount: number | null`. Порядок и пример — в руководстве [Пакетная запись](../writes/bulk.mdx#bulk-write-hooks).

## Что видит хук [#hook-view]

`this` в хуке операции показывает то, что операция отправит в базу, и в той форме, в какой она это отправит. Значения уже приведены, условия политик добавлены, идентификаторы стали `ObjectId`. Для запроса `find({ owner: "alice" })` хук увидит `filter` как `{ owner: "alice" }`. Для `updateOne({ title: "a" }, { $inc: { balance: 5 } })` — `filter` `{ title: "a" }` и `update` `{ $inc: { balance: 5 } }`.

Ещё в `this` есть `model`, `operation`, `session`, `inTransaction`, `policy` и `operationId`. Поля, которые к операции не относятся, равны `undefined`. Полный список — в справочнике [Контекст операции](../reference/hooks/operation-context.mdx#operation-hook-context).

Изменённая операция заново проходит все политики. Хук, добавивший `where`, не выйдет за границы тенанта и не снимет мягкое удаление. После хука Typemo пересобирает операцию так, будто её написал вызывающий код. Внутри самого хука `this.filter` после `modify` ещё показывает старое значение, а новое увидит следующий хук.

## Как выбрать [#how-to-choose]

Спросите себя, **что правило делает с операцией — меняет её или только наблюдает**.

- **Меняет операцию на всех путях, и это особенность модели** — берите хук.
- **Решает, чьи данные видны или удалять ли по-настоящему** — это уже есть в ядре в виде [политик](../policies/soft-delete.mdx). Хук их только плохо продублирует.
- **Только пишет метрику или журнал** — берите [события операций](../observability/events.mdx), они дешевле и безопаснее.

Между `modify` и `skip` выбирайте по тому, нужна ли операция вообще. Нужна, но в другом виде — `modify`. Не нужна, а результат заранее известен — `skip`. Чтобы запретить операцию, бросьте ошибку из хука.

## Когда это не нужно [#when-not-to-use]

Если условие нужно одному запросу, добавьте его прямо в запрос. Хук нужен там, где правило общее. Чтобы привести значение поля, хватит опций [`@Prop`](../reference/schemas/prop.mdx), они действуют и на чтение, и на запись. А если одно и то же правило нужно нескольким моделям, оформите его [плагином](./plugins.mdx).

## Если что-то пошло не так [#troubleshooting]

**`modify` или `skip` не работают в post-хуке.** Хук `@Post` вызывает `this.modify(...)`, и операция падает.

```text
QueryError: Account.find: modify() is only for pre hooks (the operation already ran)
```

К этому моменту операция уже выполнена, менять её поздно. Перенесите вызов в `@Pre`. С `skip` то же самое — `QueryError: Account.find: skip() is only for pre hooks (the operation already ran)`.

**Хук изменил не то, что ожидалось.** Скажем, `modify({ update: … })` в хуке для `find`. Компилятор такой ключ не примет, а во время работы будет `QueryError: Account.find: modify(): "update" does not apply to find`. У каждого события свои допустимые ключи, они перечислены в справочнике [`OperationChanges`](../reference/hooks/operation-context.mdx#operation-changes). Хук на список событий должен менять только то, что подходит всем событиям списка.

**Хук операции не вызывается при вставке одного документа.** У `insertOne` нет события хука операции. Он запускает хуки документа `document.validate` и `document.save`, как и `create`. Если правило должно сработать при любой вставке, повесьте его на `document.save`, подробнее — в [Хуках документа](./document-hooks.mdx). Для `insertMany` срабатывает хук `@Pre("model.insertMany")`, даже с пустым списком.

**Хук бросил ошибку, и запрос не выполнился.** Так и задумано. Ошибка из `@Pre` отменяет операцию, и до базы дело не доходит. Подробнее — в руководстве [Порядок и ошибки хуков](./order-and-errors.mdx#pre-hook-error).

### Хук операции в классе поддокумента не вызывается [#subdocument-hook-skipped]

Вы объявили `@Pre("query.find")` в классе строки заказа `Line`, который используется только как поддокумент в `Order`, и ждёте, что хук сработает при `Orders.find()`.

```ts twoslash title="orders/order.ts"
import { Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";

@Schema()
class Line extends Entity {
  @Prop(() => String, { required: true }) sku!: string;

  @Pre("query.find") // [!code warning]
  withSku(this: OperationHookContext<Line, "query.find">): void {
    this.modify({ where: { sku: { $ne: "" } } });
  }
}

@Schema({ collection: "orders" })
export class Order extends Entity {
  @Prop(() => [Line]) lines!: Line[];
}
```

Хук не вызовется никогда, и ни компилятор, ни `connection.model(Order)` об этом не скажут. После `Orders.find()` на заказе со строкой счётчик вызовов хука остался на нуле.

Дело в том, что хук операции принадлежит модели. `query.*`, `model.*` и `aggregate` запускают хуки класса, по которому создана модель. У поддокумента своих операций нет, запрос идёт к модели `Order`. Ошибкой это не считается, ведь тот же класс может быть моделью в другом месте приложения, и там хук нужен.

Перенесите хук в класс модели, `Order`. А вот хуки документа (`document.save`, `document.validate`) в классе поддокумента работают. Они запускаются на каждом поддокументе, подробнее — в [Хуках документа](./document-hooks.mdx#subdocuments).

## Полный пример [#full-example]

Все хуки с этой страницы в одном файле — условие ко всем чтениям, ревизия при обновлении, прогон удаления вхолостую и подсчёт результатов чтения.

```ts twoslash title="accounts/account.ts"
import {
  type Defaulted,
  Entity,
  Post,
  Pre,
  Prop,
  Schema,
  type OperationHookContext,
} from "@venloc/typemo";

export const settings = { dryRun: false };

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => Boolean, { default: false })
  archived!: Defaulted<boolean>;

  @Prop(() => Number, { default: 0 })
  revision!: Defaulted<number>;

  // Все чтения пропускают архивные счета.
  @Pre("query.find")
  onlyActive(this: OperationHookContext<Account, "query.find">): void {
    this.modify({ where: { archived: false } });
  }

  // Каждое массовое обновление увеличивает ревизию.
  @Pre("query.updateMany")
  bumpRevision(this: OperationHookContext<Account, "query.updateMany">): void {
    this.modify({ update: { $inc: { revision: 1 } } });
  }

  // Сухой прогон: удаление не уходит в базу.
  @Pre("query.deleteMany")
  dryRun(this: OperationHookContext<Account, "query.deleteMany">): void {
    if (settings.dryRun) this.skip({ acknowledged: true, deletedCount: 0 });
  }

  // Итог удаления в журнал.
  @Post("query.deleteMany")
  logDeleted(this: OperationHookContext<Account, "query.deleteMany">, result: { readonly deletedCount: number | null }): void {
    console.log(`удалено счетов: ${result.deletedCount}`);
  }
}
```

<Callout type="migration">

В Mongoose `pre("find")` получал запрос как `this` и менял его методами запроса вроде `this.where(...)`. А `pre("updateOne")` был сразу хуком документа и запроса, и выбирали между ними флагами. В Typemo у каждого события одна область, а `this` запроса — это контекст, и все его изменения проходят политики. Переписать из хука значение, которое запрос уже пишет, нельзя. Изменить операцию в `post` тоже нельзя, там `modify` бросает ошибку.

</Callout>
