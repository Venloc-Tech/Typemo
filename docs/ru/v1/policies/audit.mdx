Чтобы потом ответить на вопрос «кто и что изменил», включите опцию [`audit`](../reference/policies/schema-options.mdx#audit). Тогда каждая запись в модель оставит строку в отдельной коллекции — **журнале аудита**. Журнал пишется в той же транзакции, что и сама запись, поэтому запись и её след сохраняются вместе или не сохраняются вовсе. Для этого нужен реплика-сет.

## Что понадобится [#prerequisites]

MongoDB, запущенная как реплика-сет — несколько серверов MongoDB с копией одних данных, хотя для транзакций хватит и одного. Проверить это можно через [`client.supportsTransactions`](../reference/connection/typemo-client.mdx#client.supports-transactions), как в руководстве [Подключиться к базе](../connection/connect.mdx#replica-set). Пример — банк с переводами между счетами.

## Быстрый путь [#quick-start]

Включите опцию, а актора передайте в контексте политик.

```ts twoslash title="transfers/transfer.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "transfers", audit: true })
export class Transfer extends Entity {
  @Prop(() => String, { required: true })
  from!: string;

  @Prop(() => Number, { required: true })
  amount!: number;

  @Prop(() => String, { sensitive: "mask" })
  card?: string;
}
```

```ts twoslash
import { Entity, Prop, Schema, TypemoClient, PolicyContext } from "@venloc/typemo";
@Schema({ collection: "transfers", audit: true })
class Transfer extends Entity {
  @Prop(() => String, { required: true }) from!: string;
  @Prop(() => Number, { required: true }) amount!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Transfers = client.connection.model(Transfer);
// ---cut---
await PolicyContext.run({ actor: "user-7" }, () => Transfers.create({ from: "A", amount: 100 }));
```

## Прочитать журнал [#read-log]

По умолчанию журнал лежит в коллекции `<коллекция>_audit`, для `transfers` это `transfers_audit`. Модели у журнала нет, читайте его драйвером через [`client.unsafeDriver()`](../reference/connection/typemo-client.mdx#client.unsafe-driver). В примере ниже в журнале две строки.

- Вставка — `operation: "insertOne"`, `actor: "user-7"`, `document: true` и `documents` со значениями.
- Обновление — `operation: "updateOne"`, `filter: { from: "A" }`, `update: { $set: { amount: 90, card: "?" } }`, `result` со счётчиками сервера и `outcome: "ok"`.

Все поля строки описаны типом [`AuditEntry`](../reference/policies/schema-options.mdx#audit-entry).

```ts twoslash
import { TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
// ---cut---
const trail = client.unsafeDriver().db("app").collection("transfers_audit");
const entries = await trail.find({ actor: "user-7" }).sort({ _id: 1 }).toArray();
console.log(entries.map((entry) => entry.operation));
// → ["insertOne", "updateOne"]
```

В журнал попадает любая запись — `create`, `insertOne`, `insertMany`, `$save`, обновления, замены, удаления, «найти и изменить», `bulkWrite`. Мягкое удаление записывается как удаление с признаком `softDelete: true`. Чтения в журнал не попадают. Свою коллекцию для журнала задайте через `audit: { collection: "transfer_history" }`.

## Спрятать секреты [#hide-secrets]

Значения в фильтре, обновлении и документах маскируются по опции поля [`sensitive`](../reference/schemas/prop.mdx#sensitive). `"mask"` заменяет значение на `?`, а `"hide"` — на `[hidden]`. Поэтому номер карты `5500000000000004` попал в журнал как `"card": "?"`, а поле `note` с `sensitive: "hide"` — как `"[hidden]"`. Сам документ в приложении не меняется, маскируется только журнал.

Есть и третий вариант — своя функция. `sensitive: { mask: (value) => value.slice(-4) }` оставит в журнале последние четыре цифры, и номер `4111111111111111` превратится в `"1111"`. Функцию вызывают только со значением того типа, который объявлен у поля.

Если в фильтре это поле сравнивают через оператор, например `{ pan: { $exists: true } }`, у операнда другой тип. Тогда в журнал без вызова функции идёт `?`, и получается `"filter": { "pan": { "$exists": "?" } }`. Функция не получит того, чего не ждёт, а секрет не просочится через условие.

Маска закрывает значения, а не имена. Название команды и коллекция в событиях команд — [`driver.command.started`](../reference/observability/events.mdx) и соседних — не маскируются. Это не секрет, и без них не понять, что выполнялось. А вот значения полей с пометкой `sensitive` в этих событиях тоже замаскированы по правилу поля.

## История одного документа [#document-history]

Строка журнала называет ровно то, что назвала операция. Запись по фильтру без `_id`, скажем `updateMany({ from: "A" }, …)`, оставит **одну** строку с этим фильтром и счётчиками, без идентификаторов затронутых документов. Поэтому полная история одного документа есть только у записей, которые называют его по `_id` — `updateOne({ _id }, …)`, `$save`, `$deleteOne`.

Нужна история каждого документа при широком фильтре — прочитайте идентификаторы в транзакции и пишите уже по ним. Тогда строка журнала назовёт `_id`.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "transfers", audit: true })
class Transfer extends Entity {
  @Prop(() => String, { required: true }) from!: string;
  @Prop(() => Number, { required: true }) amount!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Transfers = client.connection.model(Transfer);
// ---cut---
await client.transaction(async () => {
  const rows = await Transfers.find({ from: "A" }).select({ _id: 1 }).lean();
  await Transfers.updateMany({ _id: { $in: rows.map((row) => row._id) } }, { $set: { amount: 0 } });
});
```

В строке журнала такой записи окажется `filter: { _id: { $in: [...] } }` со всеми идентификаторами, а у записи по `{ status: "open" }` — только сам фильтр. Транзакция здесь нужна, чтобы чтение идентификаторов и запись по ним видели одно состояние базы, а журнал записался вместе с обновлением.

## Что будет, если журнал не записался [#audit-write-failed]

Если журнал не записался, не выполнилась и вся операция. Она завершится [`AuditError`](../reference/errors/configuration-errors.mdx#audit-error), а транзакция откатится вместе с записью. Скажем, валидатор журнала отвергает любые строки. Тогда `create` вернёт `AuditError: Payment.create: the audit entry could not be written; the transaction is aborted with this error, the write is rolled back`. В `cause` будет `ServerValidationError`, `applied` равно `false`, и документ в базе не появится. В тексте стоит имя метода, который вызвали вы (`create`). Записи без следа так не бывает.

Внутри вашей [транзакции](../transactions/transactions.mdx) запись журнала присоединяется к ней. При откате не остаётся ни записи, ни строки журнала. После `throw` внутри `client.transaction` `countDocuments` равен 0, и строки в журнале тоже нет.

## Как выбрать [#how-to-choose]

Спросите себя, **нужно ли доказать, что изменилось и кто это сделал**. Для денег, прав доступа и персональных данных — да. Для служебных коллекций вроде кэша или сессий журнал только замедлит запись, включать его не стоит.

## Когда это не нужно [#when-not-to-use]

Без реплика-сета запись в модель с `audit` бросит `ConfigurationError`. Текст попросит запустить реплика-сет, и ничего не запишется. Если нужна история отдельных полей, а не всех записей, напишите свой [хук](../hooks/operation-hooks.mdx). Чтения журнал не записывает.

## Если что-то пошло не так [#troubleshooting]

**Запись падает на одиночном `mongod`.** Запись с журналом идёт в транзакции, а одиночный сервер транзакций не умеет. Ошибка такая — `ConfigurationError: Order.create: the model is audited (@Schema({ audit })); an audited write outside a transaction runs in its own transaction so that the write and its audit entry commit together — this needs a replica set or a sharded cluster, and the server is a standalone mongod. Run MongoDB as a replica set (a single-member one is enough).`.

В начале ошибки стоит имя метода, который вы вызвали. Здесь это `create`, а при `insertOne` будет `Order.insertOne`. Запустите MongoDB как реплика-сет.

**В журнале нет актора.** Актор берётся из контекста политик. Если запись сделана вне [`PolicyContext.run`](../reference/policies/policy-context.mdx#policy-context.run) и без `.policy({ actor })`, поля `actor` в строке не будет. Откройте область на входе в обработку запроса.

## Полный пример [#full-example]

```ts twoslash title="transfers/transfers.service.ts"
import { Entity, Prop, Schema, TypemoClient, PolicyContext } from "@venloc/typemo";
@Schema({ collection: "transfers", audit: true })
class Transfer extends Entity {
  @Prop(() => String, { required: true }) from!: string;
  @Prop(() => Number, { required: true }) amount!: number;
  @Prop(() => String, { sensitive: "mask" }) card?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Transfers = client.connection.model(Transfer);
// ---cut---
// перевод от имени пользователя: актор попадёт в журнал
export const makeTransfer = (userId: string, from: string, amount: number, card: string) =>
  PolicyContext.run({ actor: userId }, () => Transfers.create({ from, amount, card }));

// отчёт: кто что менял по счёту
export const historyOf = (account: string) =>
  client.unsafeDriver().db("app").collection("transfers_audit").find({ "documents.from": account }).toArray();
```

<Callout type="migration">

В Mongoose аудит делают плагином, который пишет в отдельную коллекцию без общей транзакции. Сбой журнала оставляет запись без следа. В Typemo журнал пишется в транзакции записи, и сбой откатывает обе.

</Callout>
