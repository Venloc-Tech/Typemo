Чтобы позже ответить на вопрос «кто и что изменил», включите опцию [`audit`](../reference/policies/schema-options.mdx#опция-audit): каждая запись в модель оставляет строку в отдельной коллекции **журнала аудита**. Журнал пишется в той же транзакции, что и запись, поэтому запись и её след фиксируются вместе или не фиксируются вовсе. Ради этого нужен реплика-сет.

## Что предполагается

MongoDB работает как реплика-сет (одноузловой подходит): проверьте [`client.supportsTransactions`](../reference/connection/typemo-client.mdx#clientsupportstransactions), как в руководстве [Подключиться к базе](../connection/connect.mdx#реплика-сет). Примеры используют банк: переводы между счетами.

## Быстрый путь

Включите опцию, а актора передайте в контексте политик:

```ts twoslash title="transfers/transfer.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "transfers", audit: true })
export class Transfer extends Entity {
  @Prop(() => String, { required: true })
  from!: string;

  @Prop(() => Number, { required: true })
  amount!: number;

  @Prop(() => String, { sensitive: "mask" })
  card?: string;
}
```

```ts twoslash
import { Entity, Prop, Schema, TypemoClient, PolicyContext } from "@venloc/typemo";
@Schema({ collection: "transfers", audit: true })
class Transfer extends Entity {
  @Prop(() => String, { required: true }) from!: string;
  @Prop(() => Number, { required: true }) amount!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Transfers = client.connection.model(Transfer);
// ---cut---
await PolicyContext.run({ actor: "user-7" }, () => Transfers.create({ from: "A", amount: 100 }));
```

## Прочитать журнал

Журнал по умолчанию лежит в коллекции `<коллекция>_audit`: для `transfers` это `transfers_audit`. У него нет модели, читать его можно драйвером через [`client.unsafeDriver()`](../reference/connection/typemo-client.mdx#clientunsafedriver). Запуск дал такие строки: вставка (`operation: "insertOne"`, `actor: "user-7"`, `document: true`, `documents` со значениями) и обновление (`operation: "updateOne"`, `filter: { from: "A" }`, `update: { $set: { amount: 90, card: "?" } }`, `result` со счётчиками сервера, `outcome: "ok"`). Поля строки описаны типом [`AuditEntry`](../reference/policies/schema-options.mdx#auditentry).

```ts twoslash
import { TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
// ---cut---
const trail = client.unsafeDriver().db("app").collection("transfers_audit");
const entries = await trail.find({ actor: "user-7" }).sort({ _id: 1 }).toArray();
console.log(entries.map((entry) => entry.operation));
// → ["insertOne", "updateOne"]
```

Записываются все пути записи: `create`, `insertOne`, `insertMany`, `$save`, обновления, замены, удаления, «найти и изменить», `bulkWrite`. Мягкое удаление записывается как удаление с признаком `softDelete: true`. Чтения в журнал не попадают. Свою коллекцию журнала задаёт `audit: { collection: "transfer_history" }`.

## Спрятать секреты

Значения в фильтре, обновлении и документах проходят маскировку по опции поля [`sensitive`](../reference/schemas/prop.mdx#sensitive): `"mask"` заменяет значение на `?`, `"hide"` — на `[hidden]`. Поэтому номер карты `5500000000000004` попал в журнал как `"card": "?"`, а поле `note` с `sensitive: "hide"` — как `"[hidden]"`. Сам документ в вашем приложении остаётся без изменений: маскируется только журнал.

Третий вариант — собственная функция: `sensitive: { mask: (value) => value.slice(-4) }` оставляет в журнале последние четыре цифры (запуск: номер `4111111111111111` попал в журнал как `"1111"`). Функция вызывается только со значением объявленного типа поля. Если в фильтре это поле сравнивают с оператором (`{ pan: { $exists: true } }`), операнд другого типа, и в журнал идёт `?` без вызова функции (запуск: `"filter": { "pan": { "$exists": "?" } }`). Так функция не получает то, чего не ожидает, а секрет не просачивается через условие.

Маска закрывает значения, а не имена. Название команды и коллекция в событиях команд ([`driver.command.started`](../reference/observability/events.mdx) и соседних) не маскируются: они не секрет и нужны, чтобы понять, что выполнялось. Значения полей с пометкой `sensitive` в этих событиях тоже замаскированы по правилу поля.

## История одного документа

Строка журнала называет то, что назвала операция. Запись по фильтру без `_id` (`updateMany({ from: "A" }, …)`) оставляет **одну** строку с этим фильтром и счётчиками, а идентификаторы затронутых документов в неё не попадают. Поэтому история одного документа полна только для записей, которые называют его по `_id`: `updateOne({ _id }, …)`, `$save`, `$deleteOne`. Чтобы получить историю по каждому документу при широком фильтре, прочитайте идентификаторы в транзакции и запишите по ним: строка журнала тогда назовёт `_id`.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "transfers", audit: true })
class Transfer extends Entity {
  @Prop(() => String, { required: true }) from!: string;
  @Prop(() => Number, { required: true }) amount!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Transfers = client.connection.model(Transfer);
// ---cut---
await client.transaction(async () => {
  const rows = await Transfers.find({ from: "A" }).select({ _id: 1 }).lean();
  await Transfers.updateMany({ _id: { $in: rows.map((row) => row._id) } }, { $set: { amount: 0 } });
});
```

Запуск показал, что строка журнала такой записи содержит `filter: { _id: { $in: [...] } }` со всеми идентификаторами, а запись по `{ status: "open" }` — только сам фильтр. Транзакция нужна, чтобы чтение идентификаторов и запись по ним опирались на одно состояние базы, а журнал записался вместе с обновлением.

## Что будет, если журнал не записался

Сбой записи журнала — сбой всей операции: она завершается [`AuditError`](../reference/errors/configuration-errors.mdx#auditerror), а транзакция откатывается вместе с записью. Запуск с журналом, чей валидатор отвергал любые строки, дал `AuditError: Payment.create: the audit entry could not be written; the transaction is aborted with this error, the write is rolled back`; `cause` — `ServerValidationError`, `applied` равно `false`, документ в базе не появился. В тексте имя метода, который вызвали вы (`create`). Так нельзя получить запись без следа.

Внутри вашей [транзакции](../transactions/transactions.mdx) запись присоединяется к ней: при откате не остаётся ни записи, ни строки (проверено запуском: после `throw` внутри `client.transaction` `countDocuments` равен 0 и строки журнала нет).

## Как выбрать

Спросите себя: **нужно ли доказать, что изменилось и кем?** Для денег, прав доступа и персональных данных — да. Для служебных коллекций (кэш, сессии) журнал только замедляет запись, и включать его не стоит.

## Когда это не нужно

Если у вас нет реплика-сета, запись в модель с `audit` бросает `ConfigurationError` (текст просит запустить реплика-сет и ничего не записывает). Если нужна история отдельных полей, а не всех записей, подойдёт собственный [хук](../hooks/operation-hooks.mdx). Журнал не записывает чтения.

## Частые ошибки

### Запись падает на одиночном mongod

Симптом (получен на одиночном `mongod`): `ConfigurationError: Order.create: the model is audited (@Schema({ audit })); an audited write outside a transaction runs in its own transaction so that the write and its audit entry commit together — this needs a replica set or a sharded cluster, and the server is a standalone mongod. Run MongoDB as a replica set (a single-member one is enough).` Имя метода в начале — тот, который вы вызвали (здесь `create`, при `insertOne` будет `Order.insertOne`). Причина: запись с журналом идёт в транзакции, а одиночный сервер их не поддерживает. Запустите MongoDB как реплика-сет.

### В журнале нет актора

Актор берётся из контекста политик. Если запись сделана вне [`PolicyContext.run`](../reference/policies/policy-context.mdx#policycontextrun) и без `.policy({ actor })`, поля `actor` в строке нет. Откройте область при обработке запроса.

## Полный пример

```ts twoslash title="transfers/transfers.service.ts"
import { Entity, Prop, Schema, TypemoClient, PolicyContext } from "@venloc/typemo";
@Schema({ collection: "transfers", audit: true })
class Transfer extends Entity {
  @Prop(() => String, { required: true }) from!: string;
  @Prop(() => Number, { required: true }) amount!: number;
  @Prop(() => String, { sensitive: "mask" }) card?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Transfers = client.connection.model(Transfer);
// ---cut---
// перевод от имени пользователя: актор попадёт в журнал
export const makeTransfer = (userId: string, from: string, amount: number, card: string) =>
  PolicyContext.run({ actor: userId }, () => Transfers.create({ from, amount, card }));

// отчёт: кто что менял по счёту
export const historyOf = (account: string) =>
  client.unsafeDriver().db("app").collection("transfers_audit").find({ "documents.from": account }).toArray();
```

<Callout type="migration">

В Mongoose аудит делают плагином, который пишет в отдельную коллекцию без общей транзакции: сбой журнала оставляет запись без следа. В Typemo журнал пишется в транзакции записи и сбой откатывает обе.

</Callout>
