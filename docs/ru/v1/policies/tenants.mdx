Ваш сервис обслуживает много организаций, а данные лежат в общих коллекциях. Значит, каждая операция должна работать с данными только **одной** организации. В Typemo такую организацию называют **тенантом**. Без защиты типичная ошибка выглядит так — в одном из запросов забыли условие `orgId`, и клиент видит чужие заказы.

Правило включается в схеме двумя частями — опцией [`tenant`](../reference/policies/schema-options.mdx#tenant) и декоратором [`@Tenant()`](../reference/schemas/field-markers.mdx#tenant) на поле тенанта. После этого модель сама добавляет условие по тенанту в каждый запрос и записывает тенанта в каждый новый документ.

Если вы впервые слышите о политиках, начните с [обзора](./overview.mdx). Здесь речь только о разделении данных.

## Что понадобится [#prerequisites]

Клиент, подключённый по руководству [Подключиться к базе](../connection/connect.mdx). Пример — CRM, где заказы принадлежат организациям `acme` и `globex`.

## Быстрый путь [#quick-start]

Включите политику в схеме и пометьте поле тенанта декоратором [`@Tenant()`](../reference/schemas/field-markers.mdx#tenant) и типом [`TenantField`](../reference/schemas/field-markers.mdx#tenant-field). Область [`PolicyContext.run`](../reference/policies/policy-context.mdx#policy-context.run) открывайте там, где организация уже известна.

```ts twoslash title="orders/order.ts"
import { Entity, Prop, Schema, Tenant, type TenantField } from "@venloc/typemo";

@Schema({ collection: "orders", tenant: true })
export class Order extends Entity {
  @Prop(() => String)
  @Tenant()
  tenantId!: TenantField<string>;

  @Prop(() => String, { required: true })
  number!: string;
}
```

```ts twoslash
import { Entity, Prop, Schema, TypemoClient, PolicyContext, Tenant, type TenantField } from "@venloc/typemo";
@Schema({ collection: "orders", tenant: true })
class Order extends Entity {
  @Prop(() => String) @Tenant() tenantId!: TenantField<string>;
  @Prop(() => String, { required: true }) number!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Orders = client.connection.model(Order);
// ---cut---
await PolicyContext.run({ tenant: "acme" }, () => Orders.create({ number: "A-1" }));

const mine = await PolicyContext.run({ tenant: "acme" }, () => Orders.find().plain());
console.log(mine[0]?.tenantId);
// → "acme"
```

Ниже разберём, как это ведёт себя в обычных задачах — описание поля, чтение, запись, тенант из HTTP-запроса, работа по всем тенантам, агрегации, связанные данные и подписки.

## Описать поле тенанта [#define-tenant-field]

Поле тенанта описывают три вещи сразу, и у каждой своя роль.

- [`@Prop`](../reference/schemas/prop.mdx) делает его полем схемы.
- Тип `TenantField<T>` говорит компилятору, что поле заполняет библиотека. Поэтому `create` его не требует, а в результатах чтения оно есть всегда.
- Декоратор `@Tenant()` говорит то же самое **во время работы**. Типы TypeScript при запуске исчезают, и без метки библиотека не узнала бы, какое поле считать тенантом. Угадывать по имени она не станет.

Правила короткие. Опция `tenant: true` называет поле `tenantId`, а `tenant: { field: "orgId" }` — любое другое. Метка `@Tenant()` ставится ровно на это поле и больше ни на какое. Согласованность проверяется дважды. В типизированном коде её проверит компилятор, вот, например, вторая метка на другом поле.

```ts twoslash
// @errors: 1238
import { Entity, Prop, Schema, Tenant, type TenantField } from "@venloc/typemo";
// ---cut---
@Schema({ collection: "notes", tenant: true })
class Note extends Entity {
  @Prop(() => String) @Tenant() tenantId!: TenantField<string>;
  @Prop(() => String) @Tenant() author!: TenantField<string>;
}
// компилятор: @Schema: "author" is TenantField<T>, but the tenant field is "tenantId"
```

Второе поле с `@Tenant()` — ошибка, ведь тенант у документа один. Так же не скомпилируются `@Tenant()` на поле, объявленном не как `TenantField<T>`, и поле `TenantField<T>` в схеме без опции `tenant`.

Во время работы те же правила проверяет сборка модели. Это нужно для JavaScript и для кода, который обошёл типы приведением. Нарушение даёт [`ConfigurationError`](../reference/errors/configuration-errors.mdx#configuration-error) при вызове [`connection.model`](../reference/connection/connection.mdx#connection.model). Модель не создаётся, и ни одна операция не доходит до базы. Тексты этих ошибок собраны ниже, в разделе [Ошибки сборки схемы](#schema-errors).

В пакете [`@venloc/typemo-decorators`](../decorators-tc39/index.mdx) для TC39-декораторов `@Tenant()` называется так же и работает так же.

## Записать данные тенанта [#write-tenant-data]

При вставке указывать тенанта не нужно. Модель берёт его из контекста и сама записывает в документ. Поэтому в типе `create` поля `tenantId` нет, а в прочитанном документе оно есть всегда.

```ts twoslash title="orders/orders.service.ts"
import { Entity, Prop, Schema, TypemoClient, PolicyContext, Tenant, type TenantField } from "@venloc/typemo";
@Schema({ collection: "orders", tenant: true })
class Order extends Entity {
  @Prop(() => String) @Tenant() tenantId!: TenantField<string>;
  @Prop(() => String, { required: true }) number!: string;
  @Prop(() => Number, { required: true }) total!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Orders = client.connection.model(Order);
// ---cut---
export const placeOrder = (tenant: string, number: string, total: number) =>
  PolicyContext.run({ tenant }, () => Orders.create({ number, total }));

const order = await placeOrder("acme", "A-1", 100);
console.log(order.tenantId, order.number);
// → "acme" "A-1"
```

Если всё же указать в документе чужого тенанта, вставка откажет. Документ принадлежал бы не той организации, что операция. Ошибка будет такой — `StrictModeError: Order.create: the document is for another tenant (tenantId: globex) than the operation's (acme) [tenant]`. В тексте назван метод, который вызвали вы (`create`), а не внутренняя операция вставки.

Если области нет, а тенант нужен одной записи, передайте его в параметрах вызова — `Orders.create({ number: "A-1" }, { policy: { tenant: "acme" } })`. Такие же параметры принимают `insertOne`, `insertMany`, `bulkWrite` и `$save`. Значение приводится по типу поля тенанта, так что для `TenantField<ObjectId>` подойдёт и строка.

## Читать данные тенанта [#read-tenant-data]

Любое чтение — `find`, `findOne`, `countDocuments`, `distinct`, курсор — добавляет к вашему фильтру условие по тенанту. В коллекции два заказа у `acme` и один у `globex`.

```ts twoslash title="orders/orders.service.ts"
import { Entity, Prop, Schema, TypemoClient, PolicyContext, Tenant, type TenantField } from "@venloc/typemo";
@Schema({ collection: "orders", tenant: true })
class Order extends Entity {
  @Prop(() => String) @Tenant() tenantId!: TenantField<string>;
  @Prop(() => String, { required: true }) number!: string;
  @Prop(() => Number, { required: true }) total!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Orders = client.connection.model(Order);
// ---cut---
export const listOrders = (tenant: string) =>
  PolicyContext.run({ tenant }, () => Orders.find().sort({ number: 1 }).plain());

const acme = await listOrders("acme");
console.log(acme.map((order) => order.number));
// → ["A-1", "A-2"]
const globex = await PolicyContext.run({ tenant: "globex" }, () => Orders.countDocuments());
// → 1
```

Ваше собственное условие по полю тенанта не заменяет условие политики, выполниться должны оба. Запрос `find({ tenantId: "globex" })` внутри области `acme` вернёт `[]`, а не заказы `globex`. Так из тенанта не «выйти» ни по ошибке, ни подменой.

## Изменить и удалить данные тенанта [#update-tenant-data]

Обновления, удаления и «найти и изменить» получают то же условие. Поэтому `updateMany` или `deleteMany` в области `acme` не заденут заказ `globex`. Само поле тенанта менять нельзя, ведь перенос документа к другой организации — это утечка.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient, PolicyContext, Tenant, type TenantField } from "@venloc/typemo";
@Schema({ collection: "orders", tenant: true })
class Order extends Entity {
  @Prop(() => String) @Tenant() tenantId!: TenantField<string>;
  @Prop(() => String, { required: true }) number!: string;
  @Prop(() => Number, { required: true }) total!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Orders = client.connection.model(Order);
// ---cut---
const removed = await PolicyContext.run({ tenant: "acme" }, () => Orders.deleteMany({ total: { $gt: 60 } }));
console.log(removed.deletedCount);
// → 1  (только заказ A-1 организации acme)

await PolicyContext.run({ tenant: "acme" }, () =>
  Orders.updateOne({ number: "A-2" }, { $set: { tenantId: "globex" } }),
);
// → StrictModeError: Order.updateOne: $set of the tenant field ("tenantId") would move the document to another tenant or lose it [tenant]
```

## Взять тенанта из HTTP-запроса [#tenant-from-request]

Тенанта обычно знает слой, который принимает запрос. Он достаёт организацию из токена и один раз открывает область вокруг всей обработки. Сервисам внутри не нужно передавать тенанта параметром. Область живёт во всей цепочке асинхронных вызовов, так что `await` внутри неё безопасны.

```ts twoslash title="http/handler.ts"
import { Entity, Prop, Schema, TypemoClient, PolicyContext, Tenant, type TenantField } from "@venloc/typemo";
@Schema({ collection: "orders", tenant: true })
class Order extends Entity {
  @Prop(() => String) @Tenant() tenantId!: TenantField<string>;
  @Prop(() => String, { required: true }) number!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Orders = client.connection.model(Order);
// ---cut---
declare const __readToken__: (token: string) => { readonly orgId: string; readonly userId: string };

export const handleListOrders = async (token: string) => {
  const { orgId, userId } = __readToken__(token);
  return PolicyContext.run({ tenant: orgId, actor: userId }, async () => {
    const orders = await Orders.find().plain();
    return { status: 200, body: orders };
  });
};
```

Область берётся, когда операцию **строят**, а не когда её ждут. Запрос, построенный внутри `run`, останется запросом своего тенанта, даже если дождаться его снаружи. А запрос, построенный вне области, тенанта не получит и бросит `StrictModeError`, даже если ждать его внутри `run`. Так запрос из переменной модуля не «подцепит» тенанта чужого запроса. Подробности — в [Контексте политик](./policy-context.mdx).

## Работать сразу по всем тенантам [#all-tenants]

Фоновой задаче или админке иногда нужны все организации. Это разрешено только явно, через `allTenants: true` в контексте или в `.policy()`. По умолчанию «все» быть не может — забытый тенант должен давать ошибку, а не всю коллекцию.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient, Tenant, type TenantField } from "@venloc/typemo";
@Schema({ collection: "orders", tenant: true })
class Order extends Entity {
  @Prop(() => String) @Tenant() tenantId!: TenantField<string>;
  @Prop(() => String, { required: true }) number!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Orders = client.connection.model(Order);
// ---cut---
const all = await Orders.find().policy({ allTenants: true }).sort({ number: 1 }).plain();
console.log(all.map((order) => `${order.tenantId}:${order.number}`));
// → ["acme:A-1", "acme:A-2", "globex:G-1"]
```

`tenant` и `allTenants: true` вместе задать нельзя, контекст не должен сам себе противоречить. Внутри области с тенантом вложенный `run({ allTenants: true })` снимает тенанта, и наоборот.

Тенант обязан быть настоящим значением. Пустая строка, строка из одних пробелов и `null` отвергаются сразу при открытии области, а не на первой операции. Иначе ошибка в коде, который достаёт организацию из токена, выглядела бы как «тенанта нет» и тихо превращалась бы в работу с документами без организации. Текст такой — `PolicyContext.run: the tenant is empty (""); a tenant is a non-empty value, or allTenants: true for cross-tenant work [tenant]`.

Пустой тенант в параметрах записи, `Orders.create(doc, { policy: { tenant: "" } })`, отвергается так же. Текст называет вызванный метод — `create.policy: the tenant is empty (""); …`.

## Агрегации, связанные данные и подписки [#aggregation-populate-change-streams]

В агрегации условие тенанта встаёт в начало конвейера. Стадии [`$lookup`](../reference/aggregation/stages.mdx#lookup), [`$unionWith`](../reference/aggregation/stages.mdx#union-with) и [`$graphLookup`](../reference/aggregation/stages.mdx#graph-lookup) подтягивают документы только того же тенанта, если у класса, названного в стадии, тоже есть политика. Чужая папка не подтянется, даже если ссылка на неё есть. Политику Typemo берёт из самого класса, так что регистрировать модель подтягиваемой коллекции не нужно.

Стадии [`$out`](../reference/aggregation/stages.mdx#out) и [`$merge`](../reference/aggregation/stages.mdx#merge) в коллекцию с тенантом запрещены, они записали бы данные в обход политики. Запросы [`populate`](../populate/basics.mdx) — это операции целевой модели. Они ограничены так же и наследуют контекст родительского запроса. Всё это проверено тестами ядра на настоящем сервере.

Подписка ([`watch`](../reference/change-streams/watch.mdx)) на модель с тенантом без `allTenants: true` запрещена. В событии удаления нет документа, по которому его можно было бы отфильтровать по тенанту. Своего `.policy()` у `watch` нет, поэтому `allTenants: true` задаётся областью, и ошибка подсказывает именно эту форму — `PolicyContext.run({ allTenants: true }, () => Orders.watch())`. События фильтруйте сами.

`estimatedDocumentCount` тоже запрещён, потому что он читает метаданные и посчитал бы всех. Берите `countDocuments()`. Тексты обеих ошибок есть в [Нарушениях политик](../reference/policies/violations.mdx#tenant).

## Как выбрать [#how-to-choose]

Спросите себя, **могут ли документы двух организаций лежать в одной коллекции**.

- **Да** — включайте `tenant`, и разделение станет свойством модели.
- **Организации нужно изолировать физически**, с разными базами и разными требованиями к хранению, — заведите для каждой свою базу через [`client.db(name)`](../reference/connection/typemo-client.mdx#client.db). Политика тогда не нужна.

Совмещать способы можно, но обычно хватает одного.

## Когда это не нужно [#when-not-to-use]

Если организация у вас одна, политика ничего не даёт, зато требует тенанта на каждой операции. Если данные делятся по обычному полю, которое клиент вправе выбирать сам, например по владельцу заметки, пишите это условие в фильтре. Тенант — это как раз то, что клиент выбирать **не должен**.

## Если что-то пошло не так [#troubleshooting]

**Операция без тенанта падает.** Сервис вызвал модель вне области, и безопасное условие построить не из чего. Ошибка такая — `StrictModeError: Order.find: Order is scoped by tenant ("tenantId") and the operation has no tenant; run it inside PolicyContext.run({ tenant }, …) or add .policy({ tenant }) to the query (cross-tenant work: .policy({ allTenants: true })) [tenant]`. Откройте [`PolicyContext.run`](../reference/policies/policy-context.mdx#policy-context.run) вокруг обработки или передайте значения в вызов.

Подсказка в ошибке называет форму, которая есть у вашего вызова. У запроса это `.policy({ tenant })`, а у записи (`create`, `insertOne`, `insertMany`, `bulkWrite`, `$save`) — параметры вызова, `… or pass { policy: { tenant } } in the call's options (cross-tenant work: { policy: { allTenants: true } })`.

**Запрос, построенный заранее, падает без тенанта.**

```ts twoslash
import { Entity, Prop, Schema, TypemoClient, PolicyContext, Tenant, type TenantField } from "@venloc/typemo";
@Schema({ collection: "orders", tenant: true })
class Order extends Entity {
  @Prop(() => String) @Tenant() tenantId!: TenantField<string>;
  @Prop(() => String, { required: true }) number!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Orders = client.connection.model(Order);
// ---cut---
// неправильно: запрос построен вне области, ждём внутри
const query = Orders.find();
await PolicyContext.run({ tenant: "acme" }, async () => query.plain());
// во время работы: StrictModeError … the operation has no tenant … [tenant]

// правильно: строим внутри области
await PolicyContext.run({ tenant: "acme" }, async () => Orders.find().plain());
```

Область берётся при построении запроса, а не при ожидании. Так вы защищены от запроса, который «подцепил» бы чужого тенанта.

### Ошибки сборки схемы [#schema-errors]

Если поле и метка не согласованы, схема с политикой тенанта не соберётся. Компилятор поймает такую схему раньше, а эти тексты вы увидите там, где типов нет или их обошли. Их выдаёт `connection.model`.

```text
ConfigurationError: NoMark: the tenant field "tenantId" must be marked @Tenant() (declare it @Prop(...) @Tenant() tenantId!: TenantField<T>)
ConfigurationError: NoOpt: @Tenant() on "tenantId", but the schema has no tenant policy — add tenant: true (or { field }) to @Schema
ConfigurationError: Two: @Tenant() marks "tenantId", "other"; only the tenant field "tenantId" may be marked
ConfigurationError: Wrong: the tenant field "orgId" must be marked @Tenant() (declare it @Prop(...) @Tenant() orgId!: TenantField<T>)
ConfigurationError: NoField: tenant field "tenantId" is not a field of the class
```

По порядку.

1. Опция есть, а метки нет.
2. Метка есть, а опции нет.
3. Меток две.
4. Опция называет `orgId`, а метка стоит на другом поле.
5. В классе нет поля, которое называет опция.

Исправление всегда одно — опция и метка должны указывать на одно и то же поле.

**Число вместо строки в тенанте.** Тенант приводится по типу поля. Для `TenantField<string>` число `5` даёт `CastError: Cast to string failed at path "tenantId" for 5 (number): expected a string [type]`. Передавайте значение того типа, что объявлен у поля.

## Полный пример [#full-example]

```ts twoslash title="orders/orders.service.ts"
import { Entity, Prop, Schema, TypemoClient, PolicyContext, Tenant, type TenantField } from "@venloc/typemo";

@Schema({ collection: "orders", tenant: true })
class Order extends Entity {
  @Prop(() => String) @Tenant() tenantId!: TenantField<string>;
  @Prop(() => String, { required: true }) number!: string;
  @Prop(() => Number, { required: true }) total!: number;
}

const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Orders = client.connection.model(Order);

// код читателя: организация из токена
declare const __orgOf__: (token: string) => string;

// запись: тенант проставляет модель
export const placeOrder = (token: string, number: string, total: number) =>
  PolicyContext.run({ tenant: __orgOf__(token) }, () => Orders.create({ number, total }));

// чтение: только заказы своей организации
export const listOrders = (token: string) =>
  PolicyContext.run({ tenant: __orgOf__(token) }, () => Orders.find().sort({ number: 1 }).plain());

// отчёт по всем организациям: явно
export const countAllOrders = () => Orders.countDocuments().policy({ allTenants: true });
```

<Callout type="migration">

В Mongoose мультитенантность делают плагином или `pre`-хуком `find`. Любой запрос, который хук не покрывает, — `aggregate`, `lean`, `updateOne` — выдаёт чужие данные. В Typemo политика встроена в конвейер и покрывает каждый путь, включая агрегации и связанные данные. А тенант задаётся контекстом, а не глобальной переменной.

</Callout>
