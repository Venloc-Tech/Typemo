Бывают итоги, которые считаются долго, а нужны часто. Сводка по клиентам, дневная выручка, рейтинг. Пересчитывать их на каждом чтении дорого. **Материализованное представление** подходит к делу иначе. Результат агрегации записывается в обычную коллекцию, оттуда быстро читается и обновляется тогда, когда решите вы.

В Typemo такую пару «источник → результат» описывает `Materialized`. Типы результата проверяются при компиляции, а обновляет его метод `refresh`.

Если вы ещё не работали с агрегациями, начните с руководства [Первая агрегация](../aggregation/first-aggregation.mdx). А если результат должен быть всегда свежим и читают его умеренно, вам нужно не это, а [представление](./views.mdx).

## Что понадобится [#prerequisites]

Клиент из руководства [Подключиться к базе](../connection/connect.mdx) и счета. Нужны итоги по владельцам открытых счетов. В `accounts` три документа.

- Main — владелец alice, баланс 120, открыт.
- Old — alice, 0, закрыт.
- Savings — bob, 500, открыт.

```ts twoslash title="accounts/models.ts"
import { Entity, EntityWithId, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => Number, { required: true })
  balance!: number;

  @Prop(() => Boolean, { required: true })
  closed!: boolean;
}

@Schema({ collection: "owner_totals" })
export class OwnerTotal extends EntityWithId(() => String) {
  @Prop(() => Number, { required: true })
  total!: number;

  @Prop(() => Number, { required: true })
  count!: number;
}
```

Класс результата — обычная сущность, только со своим типом `_id`. [`EntityWithId`](../reference/schemas/base-classes.mdx#entity-with-id) с типом `String` делает `_id` строкой. Здесь это имя владельца, по нему итог находится однозначно. Подробнее о таких идентификаторах в руководстве [Задать свой тип _id](../schemas/custom-ids.mdx).

## Быстрый путь [#quick-start]

Определите результат через [`Materialized.define`](../reference/collections/materialized.mdx#materialized.define), вызовите [`refresh`](../reference/collections/materialized.mdx#materialized.refresh) и читайте через `model`.

```ts twoslash
import { Entity, EntityWithId, fn, Materialized, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => Boolean, { required: true }) closed!: boolean;
}
@Schema({ collection: "owner_totals" })
class OwnerTotal extends EntityWithId(() => String) {
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Number, { required: true }) count!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
// ---cut---
const ownerTotals = Materialized.define(connection, OwnerTotal, {
  from: Account,
  pipeline: (p) =>
    p.match({ closed: false }).group((f) => ({ _id: f.owner, total: fn.sum(f.balance), count: fn.sum(1) })),
});
await ownerTotals.refresh();
console.log(await ownerTotals.model.find().sort({ _id: 1 }).lean());
// → [{ _id: "alice", total: 120, count: 1 }, { _id: "bob", total: 500, count: 1 }]
```

Ниже разберём режимы обновления и типичные задачи.

## Описать результат [#define-result]

Вам нужны итоги, которые читают чаще, чем меняются данные. Опишите класс результата и определите пару. Конвейер собирается тем же строителем, что и обычная агрегация, и сверяется с классом при компиляции. Стадии записи `$merge` и `$out` добавлять не нужно, это сделает `refresh`.

`define` ничего не считает и не создаёт. Пока не вызван `refresh`, коллекции результата в базе нет, после `define` там по-прежнему только `accounts`. Зато определение доступно сразу. [`definition`](../reference/collections/materialized.mdx#materialized-info) показывает источник, цель, режим и стадии.

## Обновить результат [#refresh-result]

Данные изменились, и итоги нужно пересчитать. Вызовите [`refresh`](../reference/collections/materialized.mdx#materialized.refresh) там, где это уместно, — в задаче по расписанию, после пакетной загрузки или в обработчике кнопки в админке. Сам по себе результат не обновляется никогда.

```ts twoslash title="accounts/totals.job.ts"
import { Entity, EntityWithId, fn, Materialized, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => Boolean, { required: true }) closed!: boolean;
}
@Schema({ collection: "owner_totals" })
class OwnerTotal extends EntityWithId(() => String) {
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Number, { required: true }) count!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
const Accounts = connection.model(Account);
const ownerTotals = Materialized.define(connection, OwnerTotal, {
  from: Account,
  pipeline: (p) =>
    p.match({ closed: false }).group((f) => ({ _id: f.owner, total: fn.sum(f.balance), count: fn.sum(1) })),
});
await ownerTotals.refresh();
// ---cut---
export const refreshTotals = async () => {
  await ownerTotals.refresh();
};

await Accounts.updateOne({ title: "Main" }, { $set: { balance: 150 } });
console.log((await ownerTotals.model.findOne({ _id: "alice" }))?.total);
// → 120

await refreshTotals();
console.log((await ownerTotals.model.findOne({ _id: "alice" }))?.total);
// → 150
```

Пока `refresh` не вызван, в результате лежит прежнее значение 120. После вызова — 150. Такова цена материализации, вы платите свежестью за скорость чтения.

## Выбрать режим записи [#choose-write-mode]

Скажем, счёт закрыли, и владелец пропал из выборки. Что делать с его старой строкой в результате? Это решает режим.

По умолчанию работает режим `merge`, и результат **никогда не очищается**. `$merge` вставляет новые строки и обновляет совпавшие, а строки без свежих данных остаются. Например, после закрытия Savings итог bob остался прежним, 500.

Если результат должен в точности повторять конвейер, включите `mode: "replace"`. Тогда коллекция целиком заменяется результатом, и исчезнувшие строки пропадают.

```ts twoslash
import { Entity, EntityWithId, fn, Materialized, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => Boolean, { required: true }) closed!: boolean;
}
@Schema({ collection: "owner_totals" })
class OwnerTotal extends EntityWithId(() => String) {
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Number, { required: true }) count!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
const Accounts = connection.model(Account);
// ---cut---
await Accounts.updateOne({ title: "Savings" }, { $set: { closed: true } });

const totals = Materialized.define(connection, OwnerTotal, {
  from: Account,
  mode: "replace",
  pipeline: (p) =>
    p.match({ closed: false }).group((f) => ({ _id: f.owner, total: fn.sum(f.balance), count: fn.sum(1) })),
});
await totals.refresh();
console.log((await totals.model.find().sort({ _id: 1 }).lean()).map((row) => row._id));
// → ["alice"]
```

Строки bob больше нет, `replace` записал ровно то, что вернул конвейер. Как выбрать режим, рассказано ниже, в разделе «Как выбрать».

## Слить по другому полю [#merge-on-field]

Бывает, что строку результата определяет не `_id`, а другое поле, например название счёта. В режиме `merge` укажите это поле в `on`. Целевой коллекции тогда нужен уникальный индекс ровно по этому полю, иначе сервер не сможет однозначно найти «ту же» строку.

Typemo проверяет индекс перед запуском. Если индекса ещё нет, вы получите понятную ошибку. После [`syncIndexes`](../reference/collections/model-indexes.mdx#model.sync-indexes) `refresh` заработает.

```ts twoslash title="accounts/balances.ts"
import { ConfigurationError, Entity, Index, Materialized, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) balance!: number;
}
@Index({ title: 1 }, { unique: true })
@Schema({ collection: "account_balances" })
class AccountBalance extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) balance!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
// ---cut---
const balances = Materialized.define(connection, AccountBalance, {
  from: Account,
  on: "title",
  pipeline: (p) => p.project({ _id: 0, title: 1, balance: 1 }),
});

try {
  await balances.refresh();
} catch (error) {
  if (error instanceof ConfigurationError) console.log("no unique index yet");
  // → "no unique index yet"
}

await balances.model.syncIndexes();
await balances.refresh();
console.log(await balances.model.countDocuments());
// → 3
```

Полный текст ошибки и остальные значения `whenMatched` — в справочнике по [`refresh`](../reference/collections/materialized.mdx#materialized.refresh).

## Как выбрать [#how-to-choose]

Спросите себя, **должна ли исчезнувшая строка пропасть из результата**.

- **Да** — берите `replace`. Результат всегда равен конвейеру, но каждое обновление целиком перезаписывает коллекцию.
- **Строки нужно копить, а обновлять только изменившиеся** — `merge`, он стоит по умолчанию. Он пишет только то, что вернул конвейер, и старые строки не удаляет, так что «мёртвые» строки придётся убирать самим.

Есть и вопрос раньше — стоит ли материализовать вообще. Если выборка быстрая или её читают редко, лучше подойдёт [представление](./views.mdx). Оно не хранит данных и не устаревает.

## Когда это не нужно [#when-not-to-use]

Если итог считается за миллисекунды, храните только запрос. Материализация добавляет коллекцию, за свежестью которой вам придётся следить. Если результат нужен один раз, хватит обычной [агрегации](../aggregation/first-aggregation.mdx). А если данные результата ещё и правят руками, `refresh` эти правки затрёт в режиме `replace` или смешает с ними в режиме `merge`.

## Если что-то пошло не так [#troubleshooting]

**Результат пустой.** `model.find()` вернул `[]`. Коллекция результата появляется только после первого [`refresh`](../reference/collections/materialized.mdx#materialized.refresh). Вызовите его при запуске или по расписанию.

**В результате остались «мёртвые» строки.** Владелец, у которого больше нет открытых счетов, всё ещё в итогах. Так работает режим `merge`, он коллекцию не очищает. Включите `mode: "replace"` или удаляйте устаревшие строки сами.

**`needs a unique index on exactly these fields`.** Вы сливаете через `$merge` по полю, отличному от `_id`, а уникального индекса по нему нет. Объявите `@Index({ поле: 1 }, { unique: true })` на классе результата и вызовите [`syncIndexes`](../reference/collections/model-indexes.mdx#model.sync-indexes). Или сливайте по `_id`.

**Конвейер не компилируется.** Компилятор называет поля класса результата, которых нет в строках конвейера. Добавьте их в стадию `group` или `project` или уберите из класса. Исключение одно — `_id`. Его можно не выдавать, `$merge` и `$out` присвоят его сами.

## Полный пример [#full-example]

Здесь описан результат и задача, которая его обновляет.

```ts twoslash title="accounts/owner-totals.ts"
import { Entity, EntityWithId, fn, Materialized, Prop, Schema, TypemoClient } from "@venloc/typemo";

@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => Number, { required: true })
  balance!: number;

  @Prop(() => Boolean, { required: true })
  closed!: boolean;
}

@Schema({ collection: "owner_totals" })
class OwnerTotal extends EntityWithId(() => String) {
  @Prop(() => Number, { required: true })
  total!: number;

  @Prop(() => Number, { required: true })
  count!: number;
}

const main = async () => {
  const client = await TypemoClient.connect("mongodb://localhost:27017/app", { name: "main" });
  const connection = client.connection;
  connection.model(Account);

  // определение: итоги открытых счетов по владельцам, результат повторяет конвейер
  const ownerTotals = Materialized.define(connection, OwnerTotal, {
    from: Account,
    mode: "replace",
    pipeline: (p) =>
      p.match({ closed: false }).group((f) => ({ _id: f.owner, total: fn.sum(f.balance), count: fn.sum(1) })),
  });

  // обновление: вызывается по расписанию
  await ownerTotals.refresh();

  // чтение: обычная модель
  const totals = await ownerTotals.model.find().sort({ _id: 1 }).lean();
  console.log(totals.length);

  await client.close();
};

await main();
```

<Callout type="migration">

В Mongoose материализованного представления нет. Его собирают вручную — добавляют к агрегации `$merge` или `$out` и вызывают её по расписанию. В Typemo эта стадия добавляется сама, а пара «источник → результат» типизирована. Строки конвейера сверяются с классом результата, а `$merge` по неуникальному полю отвергается ещё до отправки на сервер.

</Callout>
