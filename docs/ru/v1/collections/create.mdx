Обычная коллекция MongoDB появляется сама при первой записи, и для большинства моделей этого достаточно. Но если в схеме есть параметры коллекции — ограничение размера (`capped`), серверный валидатор, временные ряды, кластерный индекс, правило сортировки строк, — их нужно применить **до первой записи**: у уже созданной коллекции многие параметры не изменить. На этой странице разобрано, как создать такую коллекцию, как узнать, что в базе она устроена иначе, чем в схеме, и как это исправить.

Отличие Typemo от многих библиотек в том, что он не молчит о расхождении. Сама база на повторное создание отвечает «уже существует», и если эту ошибку проглотить, изменённый параметр никогда не дойдёт до сервера. Typemo сравнивает параметры и говорит, что именно отличается.

## Что предполагается

Примеры используют клиент из руководства [Подключиться к базе](../connection/connect.mdx) и две модели: счёт с серверным валидатором и журнал проводок, который хранит не больше ста записей.

```ts twoslash title="accounts/models.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts", validator: true })
export class Account extends Entity {
  @Prop(() => String, { required: true, minLength: 2 })
  title!: string;

  @Prop(() => Number, { min: 0 })
  balance?: number;
}

@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
export class LedgerEntry extends Entity {
  @Prop(() => String, { required: true })
  note!: string;
}
```

## Быстрый путь

При запуске приложения вызовите [`connection.init`](../reference/connection/connection.mdx#connectioninit): он создаёт коллекции всех зарегистрированных моделей с их параметрами. Для одной модели есть [`createCollection`](../reference/collections/collection-manager.mdx#modelcreatecollection) и [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection).

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts", validator: true })
class Account extends Entity {
  @Prop(() => String, { required: true, minLength: 2 }) title!: string;
  @Prop(() => Number, { min: 0 }) balance?: number;
}
@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
const Accounts = connection.model(Account);
const Ledger = connection.model(LedgerEntry);
// ---cut---
await connection.init(); // все модели подключения
await Accounts.createCollection(); // одну модель: true, если создал
await Ledger.ensureCollection(); // одну модель: создаст, сверит или обновит
```

Остальная страница разбирает каждый случай на задачах.

## Создать коллекции при запуске

Ситуация: приложение запускается на новой базе, и коллекции нужны с параметрами из схемы. Зарегистрируйте модели через [`connection.model`](../reference/connection/connection.mdx#connectionmodel) и вызовите `init`.

```ts twoslash title="db/start.ts"
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts", validator: true })
class Account extends Entity {
  @Prop(() => String, { required: true, minLength: 2 }) title!: string;
  @Prop(() => Number, { min: 0 }) balance?: number;
}
@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
// ---cut---
export const prepareDatabase = async () => {
  client.connection.model(Account);
  client.connection.model(LedgerEntry);
  const report = await client.connection.init();
  console.log(report.collections.map((c) => [c.collection, c.options?.result]));
  // → [["accounts", "created"], ["ledger", "created"]]
};
```

`init` создаёт то, чего нет, и ничего не меняет в существующем: если коллекция уже есть и устроена иначе, это сбой, а не молчаливая подмена, и `init` в конце бросает [`SyncError`](../reference/errors/configuration-errors.mdx#syncerror) со всеми сбоями. В отчёте список `created` называет всё, что `init` создал (`"collection accounts"`, `"collection ledger"`), а `inSync` равен `true`. Заодно `init` создаёт индексы: о них — в руководстве [Синхронизировать индексы](./index-sync.mdx).

## Создать коллекцию одной модели

Ситуация: нужна одна коллекция, и вы хотите знать, создана она сейчас или уже была. [`createCollection`](../reference/collections/collection-manager.mdx#modelcreatecollection) возвращает `true`, если создал, и `false`, если коллекция уже есть с теми же параметрами.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "ledger", capped: { size: 65_536, max: 3 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Ledger = client.connection.model(LedgerEntry);
// ---cut---
console.log(await Ledger.createCollection());
// → true
console.log(await Ledger.createCollection());
// → false

for (const note of ["a", "b", "c", "d"]) await Ledger.create({ note });
console.log((await Ledger.find().lean()).map((entry) => entry.note));
// → ["b", "c", "d"]
```

Здесь в журнале хранятся не больше трёх записей, поэтому после четвёртой самая старая, `a`, исчезла: так работает ограниченная коллекция. Это возможно только потому, что коллекция создана с параметрами схемы.

## Не потерять параметры при первой записи

Ситуация: вы описали `capped` или правило сортировки, но забыли создать коллекцию. Сервер сам создаёт коллекцию при первой записи, и создаёт её **обычной**: без ограничения размера и правила сортировки, а превратить обычную коллекцию в ограниченную уже нельзя. Поэтому Typemo не доверяет первой записи: для модели с параметрами, которые задаются только при создании (`capped`, `timeseries`, `clustered`, `collation`), первая вставка, пакетная запись, upsert или сохранение документа проверяют, что коллекция существует. Если её нет, вы получаете [`ConfigurationError`](../reference/errors/configuration-errors.mdx#configurationerror) и ничего не пишется:

```ts twoslash
import { ConfigurationError, Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Ledger = client.connection.model(LedgerEntry);
// ---cut---
try {
  await Ledger.create({ note: "first" });
} catch (error) {
  if (error instanceof ConfigurationError) console.log(error.message);
  // → LedgerEntry.create: the collection "ledger" does not exist, and MongoDB would create it as a plain collection without the options of the schema that can only be given at creation (capped); create it first: await connection.init(), or await LedgerEntry.ensureCollection()
}
```

То же происходит, если первым вызвать [`syncIndexes`](../reference/collections/model-indexes.mdx#modelsyncindexes) или [`createIndexes`](../reference/collections/model-indexes.mdx#modelcreateindexes): индексу тоже нужна коллекция. Поэтому порядок такой: сначала коллекция, потом индексы и данные. [`connection.init`](../reference/connection/connection.mdx#connectioninit) и [`connection.syncAll`](../reference/connection/connection.mdx#connectionsyncall) соблюдают его сами. Проверка идёт один раз для модели, найденную коллекцию Typemo запоминает.

Одна граница: проверка относится только к параметрам «при создании». Для валидатора (`validator: true`) её нет, потому что сервер умеет менять валидатор у существующей коллекции. Первая запись в несуществующую коллекцию со схемой-валидатором создаст обычную коллекцию без валидатора, и [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection) потом покажет это различие и исправит его с `update: true`. Поэтому и для таких моделей создавайте коллекцию при запуске.

## Серверный валидатор

Ситуация: вы хотите, чтобы сервер сам отклонял неправильные документы, даже если запись идёт мимо Typemo (скриптом на драйвере, из другого сервиса). Включите `validator: true` в `@Schema`: Typemo сгенерирует по описанию полей правило сервера (`$jsonSchema`) и поставит его при создании коллекции.

Сам Typemo проверяет данные раньше сервера, поэтому в обычной работе вы получаете [`ValidationError`](../reference/errors/data-errors.mdx#validationerror). Валидатор нужен как последний рубеж: запись через драйвер с коротким названием отклоняется сервером.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts", validator: true })
class Account extends Entity {
  @Prop(() => String, { required: true, minLength: 2 }) title!: string;
  @Prop(() => Number, { min: 0 }) balance?: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
await Accounts.createCollection();
// ---cut---
const raw = client.unsafeDriver().db("app").collection("accounts");
try {
  await raw.insertOne({ title: "x" });
} catch (error) {
  console.log((error as Error).name, (error as Error).message);
  // → "MongoServerError" "Document failed validation"
}
```

По умолчанию валидатор строгий: проверяет все вставки и обновления и отклоняет нарушения. Изменить это можно опциями `validationLevel` и `validationAction` у `validator` (значения `"strict" | "moderate" | "off"` и `"error" | "warn"`), например `validator: { validationAction: "warn" }`. Что именно попадает в правило, показывает сервер: для `Account` оно требует `_id` и `title` (строка не короче двух символов), разрешает `balance` (число не меньше нуля) и запрещает любые другие поля.

## Изменить параметры существующей коллекции

Ситуация: коллекция уже работает, а в схеме параметр изменился. [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection) сравнивает и, если вы разрешили, меняет то, что сервер умеет менять на месте. Допустим, журнал был создан с лимитом 1024 байта, а схема требует 65 536.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Ledger = client.connection.model(LedgerEntry);
await client.unsafeDriver().db("app").createCollection("ledger", { capped: true, size: 1024, max: 100 });
// ---cut---
const plan = await Ledger.ensureCollection({ dryRun: true });
console.log(plan.result, plan.differences);
// → "updated" [{ option: "size", mutable: true, wanted: 65536, actual: 1024 }]

await Ledger.ensureCollection({ update: true });
console.log((await Ledger.ensureCollection()).result);
// → "unchanged"
```

Три шага: `dryRun` показывает различия и ничего не пишет, `update: true` применяет их, а обычный вызов подтверждает, что расхождений нет. Без `update` любое различие — [`CollectionOptionsError`](../reference/errors/configuration-errors.mdx#collectionoptionserror): параметры работающей коллекции не должны меняться случайно. Какие параметры меняются на месте, а какие нет, перечислено в справочнике [`CollectionManager`](../reference/collections/collection-manager.mdx#что-можно-изменить-на-месте).

## Как выбрать

Задайте себе один вопрос: **создаёте ли вы коллекции всех моделей сразу или одной?** Для всех сразу вызывайте [`connection.init`](../reference/connection/connection.mdx#connectioninit) при запуске или [`connection.syncAll`](../reference/connection/connection.mdx#connectionsyncall) в деплое, если нужно ещё и менять существующее. Для одной модели [`createCollection`](../reference/collections/collection-manager.mdx#modelcreatecollection) годится, когда важен ответ «создал ли я сейчас» и любое расхождение должно остановить работу, а [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection) — когда расхождение нужно посмотреть или исправить.

## Когда это не нужно

Если в схеме нет параметров коллекции, создавать её заранее не нужно: она появится при первой записи такой, какая и требуется. Не создавайте коллекции для представлений: у [`TypedView`](./views.mdx) своя проверка, а `init` и `syncAll` вызывают её сами. Схему с `autoCreate: false` `init` и `syncAll` пропускают на шаге параметров коллекции, и `createCollection` у такой модели бросает `ConfigurationError`: так удобно для коллекций, которыми управляет другая система. Метод `ensureCollection` опцию не смотрит и коллекцию создаст, поэтому вызывайте его у такой модели осознанно.

## Частые ошибки

### `ConfigurationError` при первой записи

В тексте есть `the collection "ledger" does not exist, and MongoDB would create it as a plain collection`. У модели параметры «только при создании», а коллекции нет. Вызовите [`connection.init`](../reference/connection/connection.mdx#connectioninit) или [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection) до записи.

### У коллекции со схемой-валидатором нет валидатора

Коллекцию создала первая запись: для валидатора проверки существования нет. Вызовите `ensureCollection({ update: true })`: валидатор применится командой `collMod`.

### `CollectionOptionsError` при создании

Текст называет параметр в скобках: `exists with other options (validator)`; если среди различий есть параметр, который MongoDB изменить не умеет, текст говорит `exists with options MongoDB cannot change (capped)`. Если параметр изменяемый, вызовите `ensureCollection({ update: true })`. Если нет (`capped`, `collation`, вид коллекции), удалите коллекцию и создайте заново: Typemo сам коллекций не удаляет.

### Коллекция не создалась при `init`

Схема объявляет `autoCreate: false`: `init` её пропускает, а в отчёте поле `options` пустое. Уберите опцию или создайте коллекцию вручную: [`createCollection`](../reference/collections/collection-manager.mdx#modelcreatecollection) у такой модели бросает ошибку, а [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection) создаёт.

## Полный пример

Файл запуска: создаёт коллекции, проверяет отчёт и при расхождении останавливает запуск.

```ts twoslash title="db/start.ts"
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";

@Schema({ collection: "accounts", validator: true })
class Account extends Entity {
  @Prop(() => String, { required: true, minLength: 2 })
  title!: string;

  @Prop(() => Number, { min: 0 })
  balance?: number;
}

@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true })
  note!: string;
}

export const start = async (uri: string) => {
  // клиент и модели
  const client = await TypemoClient.connect(uri, { name: "main" });
  const connection = client.connection;
  connection.model(Account);
  const Ledger = connection.model(LedgerEntry);

  // коллекции с параметрами схемы; init бросит SyncError, если что-то не сошлось
  await connection.init();

  // журнал: после запуска нужного размера
  console.log((await Ledger.ensureCollection()).result);
  // → "unchanged"

  return client;
};
```

<Callout type="migration">

В Mongoose `Model.createCollection` молча игнорировал уже существующую коллекцию, даже если её параметры отличались от схемы, и изменённый параметр не доходил до базы. В Typemo [`createCollection`](../reference/collections/collection-manager.mdx#modelcreatecollection) возвращает `false` только тогда, когда параметры совпали, а при расхождении бросает [`CollectionOptionsError`](../reference/errors/configuration-errors.mdx#collectionoptionserror). Менять существующее вы разрешаете явно: [`ensureCollection({ update: true })`](../reference/collections/collection-manager.mdx#modelensurecollection). Коллекции при регистрации модели не создаются: вы вызываете `init` сами.

</Callout>
