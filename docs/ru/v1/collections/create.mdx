Обычная коллекция MongoDB появляется сама при первой записи, и большинству моделей этого хватает. Но бывает, что в схеме заданы параметры коллекции — ограничение размера (`capped`), серверный валидатор, временные ряды, кластерный индекс или правило сортировки строк. Их нужно применить **до первой записи**, потому что у готовой коллекции многие параметры уже не поменять.

Ниже разберём, как создать такую коллекцию, как узнать, что в базе она устроена не так, как в схеме, и как это исправить.

Typemo, в отличие от многих библиотек, о расхождении не молчит. Сама база на повторное создание отвечает «уже существует». Проглотите эту ошибку, и изменённый параметр так и не дойдёт до сервера. Typemo сравнивает параметры и говорит, что именно отличается.

## Что понадобится

Клиент из руководства [Подключиться к базе](../connection/connect.mdx) и две модели.

- Счёт с серверным валидатором.
- Журнал проводок, который хранит не больше ста записей.

```ts twoslash title="accounts/models.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts", validator: true })
export class Account extends Entity {
  @Prop(() => String, { required: true, minLength: 2 })
  title!: string;

  @Prop(() => Number, { min: 0 })
  balance?: number;
}

@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
export class LedgerEntry extends Entity {
  @Prop(() => String, { required: true })
  note!: string;
}
```

## Быстрый путь

При запуске приложения вызовите [`connection.init`](../reference/connection/connection.mdx#connectioninit). Он создаст коллекции всех зарегистрированных моделей с их параметрами. Для одной модели есть [`createCollection`](../reference/collections/collection-manager.mdx#modelcreatecollection) и [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection).

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts", validator: true })
class Account extends Entity {
  @Prop(() => String, { required: true, minLength: 2 }) title!: string;
  @Prop(() => Number, { min: 0 }) balance?: number;
}
@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
const Accounts = connection.model(Account);
const Ledger = connection.model(LedgerEntry);
// ---cut---
await connection.init(); // все модели подключения
await Accounts.createCollection(); // одну модель: true, если создал
await Ledger.ensureCollection(); // одну модель: создаст, сверит или обновит
```

Ниже разберём каждый случай на задачах.

## Создать коллекции при запуске

Приложение запускается на новой базе, и коллекции нужны с параметрами из схемы. Зарегистрируйте модели через [`connection.model`](../reference/connection/connection.mdx#connectionmodel) и вызовите `init`.

```ts twoslash title="db/start.ts"
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts", validator: true })
class Account extends Entity {
  @Prop(() => String, { required: true, minLength: 2 }) title!: string;
  @Prop(() => Number, { min: 0 }) balance?: number;
}
@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
// ---cut---
export const prepareDatabase = async () => {
  client.connection.model(Account);
  client.connection.model(LedgerEntry);
  const report = await client.connection.init();
  console.log(report.collections.map((c) => [c.collection, c.options?.result]));
  // → [["accounts", "created"], ["ledger", "created"]]
};
```

`init` создаёт то, чего нет, а существующее не трогает. Если коллекция уже есть и устроена иначе, это сбой, а не тихая подмена. В конце `init` бросит [`SyncError`](../reference/errors/configuration-errors.mdx#syncerror) со всеми сбоями.

В отчёте список `created` называет всё, что создал `init` (`"collection accounts"`, `"collection ledger"`), а `inSync` равен `true`. Заодно `init` создаёт индексы, о них руководство [Синхронизировать индексы](./index-sync.mdx).

## Создать коллекцию одной модели

Нужна одна коллекция, и важно знать, создана она сейчас или уже была. [`createCollection`](../reference/collections/collection-manager.mdx#modelcreatecollection) вернёт `true`, если создал её, и `false`, если коллекция уже есть с теми же параметрами.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "ledger", capped: { size: 65_536, max: 3 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Ledger = client.connection.model(LedgerEntry);
// ---cut---
console.log(await Ledger.createCollection());
// → true
console.log(await Ledger.createCollection());
// → false

for (const note of ["a", "b", "c", "d"]) await Ledger.create({ note });
console.log((await Ledger.find().lean()).map((entry) => entry.note));
// → ["b", "c", "d"]
```

В этом примере журнал хранит не больше трёх записей. После четвёртой самая старая, `a`, исчезла — так работает ограниченная коллекция. И работает она так только потому, что создана с параметрами схемы.

## Не потерять параметры при первой записи

Скажем, вы описали `capped` или правило сортировки, но забыли создать коллекцию. Сервер создаст её сам при первой записи, только **обычной**, без ограничения размера и правила сортировки. А превратить обычную коллекцию в ограниченную уже нельзя.

Поэтому первой записи Typemo не доверяет. Для модели с параметрами, которые задаются только при создании (`capped`, `timeseries`, `clustered`, `collation`), первая вставка, пакетная запись, upsert или сохранение документа сначала проверяют, что коллекция существует. Если её нет, вы получите [`ConfigurationError`](../reference/errors/configuration-errors.mdx#configurationerror), и ничего не запишется.

```ts twoslash
import { ConfigurationError, Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Ledger = client.connection.model(LedgerEntry);
// ---cut---
try {
  await Ledger.create({ note: "first" });
} catch (error) {
  if (error instanceof ConfigurationError) console.log(error.message);
  // → LedgerEntry.create: the collection "ledger" does not exist, and MongoDB would create it as a plain collection without the options of the schema that can only be given at creation (capped); create it first: await connection.init(), or await LedgerEntry.ensureCollection()
}
```

То же будет, если первым вызвать [`syncIndexes`](../reference/collections/model-indexes.mdx#modelsyncindexes) или [`createIndexes`](../reference/collections/model-indexes.mdx#modelcreateindexes), ведь индексу тоже нужна коллекция. Так что порядок такой — сначала коллекция, потом индексы и данные. [`connection.init`](../reference/connection/connection.mdx#connectioninit) и [`connection.syncAll`](../reference/connection/connection.mdx#connectionsyncall) соблюдают его сами. Проверка выполняется один раз на модель, найденную коллекцию Typemo запоминает.

У проверки есть граница — она касается только параметров «при создании». Для валидатора (`validator: true`) её нет, потому что валидатор сервер умеет менять и у существующей коллекции. Первая запись в несуществующую коллекцию со схемой-валидатором создаст обычную коллекцию без валидатора. [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection) потом покажет это различие и исправит его с `update: true`. Но и для таких моделей лучше создавать коллекцию при запуске.

## Серверный валидатор

Иногда нужно, чтобы сервер сам отклонял неправильные документы, даже если запись идёт мимо Typemo — скриптом на драйвере или из другого сервиса. Включите `validator: true` в `@Schema`. Typemo построит по описанию полей правило сервера (`$jsonSchema`) и поставит его при создании коллекции.

Сам Typemo проверяет данные раньше сервера, так что в обычной работе вы получите [`ValidationError`](../reference/errors/data-errors.mdx#validationerror). Валидатор — последний рубеж. Запись через драйвер с коротким названием сервер отклонит.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts", validator: true })
class Account extends Entity {
  @Prop(() => String, { required: true, minLength: 2 }) title!: string;
  @Prop(() => Number, { min: 0 }) balance?: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
await Accounts.createCollection();
// ---cut---
const raw = client.unsafeDriver().db("app").collection("accounts");
try {
  await raw.insertOne({ title: "x" });
} catch (error) {
  console.log((error as Error).name, (error as Error).message);
  // → "MongoServerError" "Document failed validation"
}
```

По умолчанию валидатор строгий. Он проверяет все вставки и обновления и отклоняет нарушения. Это меняется опциями `validationLevel` и `validationAction` у `validator` со значениями `"strict" | "moderate" | "off"` и `"error" | "warn"`, например `validator: { validationAction: "warn" }`.

Что попало в правило, видно на сервере. Для `Account` оно требует `_id` и `title` (строку не короче двух символов), разрешает `balance` (число не меньше нуля) и запрещает любые другие поля.

## Изменить параметры существующей коллекции

Коллекция уже работает, а параметр в схеме изменился. [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection) сравнивает параметры и, если вы разрешили, меняет то, что сервер умеет менять на месте. Скажем, журнал создали с лимитом 1024 байта, а схема требует 65 536.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Ledger = client.connection.model(LedgerEntry);
await client.unsafeDriver().db("app").createCollection("ledger", { capped: true, size: 1024, max: 100 });
// ---cut---
const plan = await Ledger.ensureCollection({ dryRun: true });
console.log(plan.result, plan.differences);
// → "updated" [{ option: "size", mutable: true, wanted: 65536, actual: 1024 }]

await Ledger.ensureCollection({ update: true });
console.log((await Ledger.ensureCollection()).result);
// → "unchanged"
```

Здесь три шага.

- `dryRun` показывает различия и ничего не пишет.
- `update: true` их применяет.
- Обычный вызов подтверждает, что расхождений больше нет.

Без `update` любое различие даёт [`CollectionOptionsError`](../reference/errors/configuration-errors.mdx#collectionoptionserror), чтобы параметры работающей коллекции не поменялись случайно. Какие параметры меняются на месте, а какие нет, перечислено в справочнике по [`CollectionManager`](../reference/collections/collection-manager.mdx#что-можно-изменить-на-месте).

## Как выбрать

Спросите себя, **создаёте вы коллекции всех моделей сразу или одной**.

- **Всех сразу** — вызывайте [`connection.init`](../reference/connection/connection.mdx#connectioninit) при запуске. Если при деплое нужно ещё и менять существующее, берите [`connection.syncAll`](../reference/connection/connection.mdx#connectionsyncall).
- **Одной, и важно знать, создана ли она сейчас**, а любое расхождение должно остановить работу — [`createCollection`](../reference/collections/collection-manager.mdx#modelcreatecollection).
- **Одной, и расхождение нужно посмотреть или исправить** — [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection).

## Когда это не нужно

Если в схеме нет параметров коллекции, создавать её заранее не нужно. Она появится при первой записи ровно такой, какая требуется. Не создавайте коллекции и для представлений. У [`TypedView`](./views.mdx) своя проверка, и `init` и `syncAll` вызывают её сами.

Схему с `autoCreate: false` `init` и `syncAll` на шаге параметров коллекции пропускают, а `createCollection` у такой модели бросает `ConfigurationError`. Это удобно для коллекций, которыми управляет другая система. `ensureCollection` на эту опцию не смотрит и коллекцию создаст, так что вызывайте его у такой модели осознанно.

## Если что-то пошло не так

**`ConfigurationError` при первой записи.** В тексте есть `the collection "ledger" does not exist, and MongoDB would create it as a plain collection`. У модели есть параметры «только при создании», а коллекции нет. Вызовите [`connection.init`](../reference/connection/connection.mdx#connectioninit) или [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection) до записи.

**У коллекции со схемой-валидатором нет валидатора.** Коллекцию создала первая запись, а для валидатора проверки существования нет. Вызовите `ensureCollection({ update: true })`, и валидатор применится командой `collMod`.

**`CollectionOptionsError` при создании.** Текст называет параметр в скобках — `exists with other options (validator)`. Если среди различий есть параметр, который MongoDB менять не умеет, текст будет `exists with options MongoDB cannot change (capped)`. Изменяемый параметр поправит `ensureCollection({ update: true })`. Неизменяемый (`capped`, `collation`, вид коллекции) — только удаление коллекции и создание заново, и удалять её придётся вам, Typemo коллекции не удаляет.

**Коллекция не создалась при `init`.** Схема объявляет `autoCreate: false`, поэтому `init` её пропускает, а в отчёте поле `options` пустое. Уберите опцию или создайте коллекцию вручную. [`createCollection`](../reference/collections/collection-manager.mdx#modelcreatecollection) у такой модели бросит ошибку, а [`ensureCollection`](../reference/collections/collection-manager.mdx#modelensurecollection) создаст.

## Полный пример

Файл запуска создаёт коллекции, проверяет отчёт и останавливает запуск, если что-то расходится.

```ts twoslash title="db/start.ts"
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";

@Schema({ collection: "accounts", validator: true })
class Account extends Entity {
  @Prop(() => String, { required: true, minLength: 2 })
  title!: string;

  @Prop(() => Number, { min: 0 })
  balance?: number;
}

@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true })
  note!: string;
}

export const start = async (uri: string) => {
  // клиент и модели
  const client = await TypemoClient.connect(uri, { name: "main" });
  const connection = client.connection;
  connection.model(Account);
  const Ledger = connection.model(LedgerEntry);

  // коллекции с параметрами схемы; init бросит SyncError, если что-то не сошлось
  await connection.init();

  // журнал: после запуска нужного размера
  console.log((await Ledger.ensureCollection()).result);
  // → "unchanged"

  return client;
};
```

<Callout type="migration">

В Mongoose `Model.createCollection` молча пропускал уже существующую коллекцию, даже если её параметры отличались от схемы, и изменённый параметр не доходил до базы. В Typemo [`createCollection`](../reference/collections/collection-manager.mdx#modelcreatecollection) возвращает `false`, только когда параметры совпали, а при расхождении бросает [`CollectionOptionsError`](../reference/errors/configuration-errors.mdx#collectionoptionserror).

Менять существующее вы разрешаете явно, через [`ensureCollection({ update: true })`](../reference/collections/collection-manager.mdx#modelensurecollection). И при регистрации модели коллекции не создаются, `init` вы вызываете сами.

</Callout>
