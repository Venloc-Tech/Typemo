Индексы из схемы (`unique`, `index`, [`@Index`](../reference/schemas/index-decorators.mdx#index)) сами в базе не появляются. Typemo создаёт их, только когда вы об этом попросите. Поэтому в каждом приложении есть шаг «привести индексы в соответствие со схемой» — при старте, при деплое или в скрипте миграции. Ниже разберём три варианта этого шага и как выбрать нужный.

**Индекс** — это служебная структура MongoDB, которая ускоряет поиск по полю. Индекс с `unique` к тому же не даёт записать два документа с одинаковым значением. Пока индекса нет, дубликат запишется без ошибки. На новой модели после `create` в коллекции есть только `_id_`.

## Что понадобится

Клиент из руководства [Подключиться к базе](../connection/connect.mdx) и модель счёта с двумя индексами — уникальным названием и индексом по владельцу.

```ts twoslash title="accounts/account.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => String, { required: true, index: true })
  owner!: string;
}
```

## Быстрый путь

Есть три способа для трёх ситуаций.

- **Старт приложения** — [`connection.init`](../reference/connection/connection.mdx#connectioninit) создаст недостающее.
- **Деплой** — [`connection.syncAll`](../reference/connection/connection.mdx#connectionsyncall) приведёт всё в точное соответствие со схемой.
- **Одна модель** — [`syncIndexes`](../reference/collections/model-indexes.mdx#modelsyncindexes).

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
const Accounts = connection.model(Account);
// ---cut---
await connection.init(); // только создаёт недостающее
await connection.syncAll(); // приводит всё в точное соответствие
await Accounts.syncIndexes(); // то же для одной модели
```

Ниже разберём каждый вариант на настоящих задачах.

## Создать индексы при старте

Приложение запускается на новой или уже работающей базе, и индексы из схемы должны существовать. Зарегистрируйте модели и вызовите [`connection.init`](../reference/connection/connection.mdx#connectioninit). Он создаёт недостающее и **ничего не удаляет и не меняет**.

```ts twoslash title="db/start.ts"
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
// ---cut---
export const prepareDatabase = async () => {
  client.connection.model(Account);
  const report = await client.connection.init();
  console.log(report.collections[0]?.indexes?.toCreate);
  // → ["title_1", "owner_1"]
  console.log(report.inSync, report.created);
  // → true ["collection accounts", "index accounts.title_1", "index accounts.owner_1"]
};
```

При первом запуске `init` создал коллекцию и оба индекса и перечислил их в `created`. После успешного `init` база совпадает со схемой, поэтому и здесь `inSync` равен `true`. Второй запуск ничего не создаёт, и `toCreate` с `created` пустые. Сбой `init` выглядит не как `inSync: false`, а как исключение, о нём чуть ниже.

Индекс, которого нет в схеме, `init` оставит, вдруг он нужен другому приложению. А индекс, который есть и в схеме, и в базе, но объявлен по-разному, `init` считает ошибкой. Без вашего согласия менять его нельзя. Скажем, кто-то вручную сделал `owner_1` уникальным. Тогда запуск остановится с [`SyncError`](../reference/errors/configuration-errors.mdx#syncerror), где перечислены все сбои.

```text
SyncError: connection.init() of "app": 1 failure(s) — collection "accounts": Account: 1 index operation(s) failed: create owner_1: index "owner_1" exists on the server with other keys or options; init() never drops or changes an index — run syncIndexes()/syncAll() to replace it
```

Разобрать сбой в коде помогут три поля ошибки.

- `failures` — сбои по коллекциям и представлениям, то есть имя, класс модели и список ошибок.
- `errors` — все исходные ошибки подряд. Здесь она одна, [`IndexSyncError`](../reference/errors/configuration-errors.mdx#indexsyncerror), и та же лежит в `cause`, в `AggregateError`.
- `report` — полный отчёт о том, что нашлось и что сделано.

Напрямую `IndexSyncError` бросает только `syncIndexes`. `init` и `syncAll` заворачивают её в `SyncError`.

## Посмотреть расхождение до деплоя

Вы поменяли индексы в схеме и хотите знать, что случится с базой, до того как выкатывать. [`connection.syncAll`](../reference/connection/connection.mdx#connectionsyncall) с `dryRun: true` ничего не пишет — ни индексов, ни коллекций, ни представлений — и возвращает план.

```ts twoslash title="scripts/check-indexes.ts"
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
connection.model(Account);
const raw = client.unsafeDriver().db("app").collection("accounts");
await connection.init();
await raw.dropIndex("owner_1");
await raw.createIndex({ owner: 1 }, { name: "owner_1", unique: true });
await raw.createIndex({ closed: 1 }, { name: "closed_1" });
// ---cut---
const plan = await connection.syncAll({ dryRun: true });
console.log(plan.collections[0]?.indexes);
// → { toCreate: ["owner_1"], toDrop: ["owner_1", "closed_1"], toModify: [], dryRun: true }
console.log(plan.inSync, plan.created);
// → false ["index accounts.owner_1"]
```

`closed_1` есть в базе, но нет в схеме, поэтому он попал в `toDrop`. А `owner_1` в базе объявлен не так, как в схеме, и его имя стоит и в `toDrop`, и в `toCreate`. Его удалят и создадут заново. Как метод решает, что индекс «тот же», описано в справочнике по [`diffIndexes`](../reference/collections/model-indexes.mdx#modeldiffindexes). Для одной модели такой же план даёт [`diffIndexes`](../reference/collections/model-indexes.mdx#modeldiffindexes).

## Применить изменения

План вас устроил, пора привести базу в соответствие. Вызовите [`connection.syncAll`](../reference/connection/connection.mdx#connectionsyncall) без `dryRun`. Он удалит лишние индексы, пересоздаст изменённые и создаст недостающие. То, что можно поменять на месте, то есть видимость и срок жизни TTL, он изменит без пересоздания.

```ts twoslash title="scripts/sync-indexes.ts"
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
connection.model(Account);
// ---cut---
const report = await connection.syncAll();
console.log(report.failed, report.inSync);
// → false false

const again = await connection.syncAll();
console.log(again.inSync);
// → true
```

Первый вызов изменил базу, поэтому `inSync` равен `false`. Повторный подтверждает, что расхождений не осталось.

При сбое `syncAll`, как и `init`, бросает [`SyncError`](../reference/errors/configuration-errors.mdx#syncerror). У возвращённого отчёта `failed` всегда `false`, а отчёт со сбоями лежит в `error.report`. Так что деплой с непостроенным индексом не пройдёт «успешно», даже если вы ничего не проверяете.

## Индекс не построился

Чаще всего мешают данные, которые уже нарушают уникальность. Допустим, в `accounts` два счёта с названием `Main`. [`syncIndexes`](../reference/collections/model-indexes.mdx#modelsyncindexes) не останавливается на первой ошибке. Он создаёт всё, что получается, а в конце бросает одну [`IndexSyncError`](../reference/errors/configuration-errors.mdx#indexsyncerror) со всеми неудачами. Через `init` или `syncAll` та же ошибка придёт внутри [`SyncError`](../reference/errors/configuration-errors.mdx#syncerror).

```ts twoslash title="scripts/sync-accounts.ts"
import { Entity, IndexSyncError, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
await client.unsafeDriver().db("app").collection("accounts").insertMany([
  { title: "Main", owner: "alice" },
  { title: "Main", owner: "bob" },
]);
// ---cut---
try {
  await Accounts.syncIndexes();
} catch (error) {
  if (error instanceof IndexSyncError) {
    for (const failure of error.failures) console.log(failure.name, failure.action, failure.error.name);
    // → "title_1" "create" "DuplicateKeyError"
  }
}
console.log((await Accounts.listIndexes()).map((index) => index.name));
// → ["_id_", "owner_1"]
```

`owner_1` создан, а `title_1` нет. Сообщение короткое, без служебных подробностей сборки индекса, — `duplicate key on title_1: { title: "Main" } (code 11000 DuplicateKey)`. Длинный текст сервера лежит в `serverMessage` вложенной ошибки. Исправьте дубликаты, удалите или переименуйте один из счетов, и вызовите `syncIndexes` ещё раз. Создастся только недостающий индекс.

## Текстовый индекс и повторный запуск

Бывает, что в схеме объявлен текстовый индекс по нескольким полям, а приложение перезапускается. Сервер хранит у текстового индекса веса полей и сам ставит вес 1 тем, у которых вы его не задали. Typemo учитывает это при сравнении. Сразу после создания такой индекс совпадает со схемой, и второй `init` расхождения не находит и не падает.

```ts twoslash title="posts/start.ts"
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
@Index({ title: "text", body: "text" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
client.connection.model(Post);
// ---cut---
const first = await client.connection.init();
console.log(first.created);
// → ["collection posts", "index posts.title_text_body_text"]

const second = await client.connection.init();
console.log(second.inSync, second.created);
// → true []
```

Явный вес, отличный от единицы (`weights: { title: 5 }`), сравнивается как обычная опция индекса. Поменяли вес в схеме — `syncAll` пересоздаст индекс.

## Исключить модель из `init` и `syncAll`

Иногда коллекцией или её индексами управляет другая система, и приложение не должно их трогать. Опция схемы [`autoIndex: false`](../reference/schemas/schema.mdx#autoindex) убирает индексы модели из `init` и `syncAll`, а [`autoCreate: false`](../reference/schemas/schema.mdx#autocreate) — саму коллекцию. Эти опции читают только два метода подключения. Прямой вызов [`syncIndexes`](../reference/collections/model-indexes.mdx#modelsyncindexes) у модели индексы по-прежнему строит.

```ts twoslash title="legacy/start.ts"
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "legacy", autoIndex: false })
class Legacy extends Entity {
  @Prop(() => String, { required: true, unique: true }) code!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Legacies = client.connection.model(Legacy);
// ---cut---
const report = await client.connection.init();
console.log(report.collections[0]?.indexes);
// → undefined
console.log((await Legacies.listIndexes()).map((index) => index.name));
// → ["_id_"]

await Legacies.syncIndexes();
console.log((await Legacies.listIndexes()).map((index) => index.name));
// → ["_id_", "code_1"]
```

Схему с `autoCreate: false` без индексов и поисковых индексов `init` и `syncAll` пропускают целиком. Это удобно для журнала с параметрами «только при создании» (`capped`, `timeseries`, `clustered`, `collation`), который создаёт и обслуживает его владелец. Пока коллекции нет, `init` и `syncAll` не считают это ошибкой.

Другое дело, если у такой схемы есть индексы, а коллекции нет. Индекс создал бы коллекцию без этих параметров, поэтому вызов остановится с `SyncError`, как описано [ниже](#если-что-то-пошло-не-так).

## Как выбрать

Спросите себя, **может ли этот шаг что-то удалить**.

- **При старте приложение не должно ничего менять в чужой базе** — вызывайте [`connection.init`](../reference/connection/connection.mdx#connectioninit). Он безопасен и остановит запуск, если база устроена иначе.
- **Это шаг деплоя, которым вы управляете** — [`connection.syncAll`](../reference/connection/connection.mdx#connectionsyncall). Он приводит базу в точное соответствие, а о сбоях сообщает одной `SyncError` со всем отчётом.
- **Нужно поправить одну модель** — [`syncIndexes`](../reference/collections/model-indexes.mdx#modelsyncindexes).
- **Нужно только доложить недостающее без сравнения** — [`createIndexes`](../reference/collections/model-indexes.mdx#modelcreateindexes).

## Когда это не нужно

Синхронизация не нужна в тестах с пустой базой, где уникальность не проверяется, и в одноразовых скриптах, которые ничего не ищут. Параметры коллекции вроде `capped` или валидатора индексные методы не трогают, о них руководство [Создание коллекций](./create.mdx). И не запускайте `syncAll` на каждый запрос или в горячем пути приложения. Это команды администратора, их место — запуск и деплой.

## Если что-то пошло не так

**Уникальность не работает.** Запись с дубликатом прошла без ошибки. Индекс из схемы сам не создаётся, и пока вы не вызвали [`init`](../reference/connection/connection.mdx#connectioninit), [`syncAll`](../reference/connection/connection.mdx#connectionsyncall) или [`syncIndexes`](../reference/collections/model-indexes.mdx#modelsyncindexes), в базе есть только `_id_`. Вызовите один из них при запуске.

**Запуск остановился с `SyncError` от `init`.** В сообщении есть `exists on the server with other keys or options`. Индекс с таким именем в базе устроен не так, как в схеме, а `init` ничего не меняет. Посмотрите расхождение через `syncAll({ dryRun: true })`. Если индекс можно удалить и пересоздать, примените `syncAll()`.

**Запуск остановился с `SyncError` и текстом `exists with options MongoDB cannot change`.** Коллекция уже есть, а схема объявляет параметр, который MongoDB у существующей коллекции не меняет, — `capped`, вид коллекции или `collation`. Сообщение называет параметр и выход — `collection "logs": exists with options MongoDB cannot change (capped): drop the collection and create it again`. Текст тот же, что у [`createCollection`](../reference/collections/collection-manager.mdx#modelcreatecollection) и `ensureCollection`, только с именем коллекции. Сам Typemo коллекцию не удалит, так что удалите её и вызовите `init` ещё раз.

**`ConfigurationError` — коллекции нет, а параметры задаются только при создании.** У модели есть `capped`, `timeseries`, `clustered` или `collation`, а коллекции ещё нет. [`syncIndexes`](../reference/collections/model-indexes.mdx#modelsyncindexes) и [`createIndexes`](../reference/collections/model-indexes.mdx#modelcreateindexes) в этом случае ничего не создают — индекс создал бы обычную коллекцию, и параметры потерялись бы. Сначала создайте коллекцию. [`init`](../reference/connection/connection.mdx#connectioninit) и [`syncAll`](../reference/connection/connection.mdx#connectionsyncall) делают всё в правильном порядке, подробнее в руководстве [Создание коллекций](./create.mdx).

## Полный пример

Скрипт деплоя сначала строит план, потом применяет его. Сбой выводится по коллекциям и останавливает деплой.

```ts twoslash title="scripts/deploy-database.ts"
import { Entity, Prop, Schema, SyncError, TypemoClient } from "@venloc/typemo";

@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => String, { required: true, index: true })
  owner!: string;
}

const deploy = async (uri: string) => {
  const client = await TypemoClient.connect(uri, { name: "deploy" });
  try {
    const connection = client.connection;
    connection.model(Account);

    // план: что изменится, ничего не записывая
    const plan = await connection.syncAll({ dryRun: true });
    console.log("planned changes:", plan.created);

    // применение: при сбое syncAll бросит SyncError со всем отчётом
    await connection.syncAll();
  } catch (error) {
    if (error instanceof SyncError) {
      for (const failure of error.failures) console.error(failure.kind, failure.name, failure.errors.map((e) => e.message));
    }
    throw error;
  } finally {
    await client.close();
  }
};

await deploy("mongodb://localhost:27017/app");
```

<Callout type="migration">

В Mongoose индексы по умолчанию строились сами при регистрации модели (`autoIndex`), а `syncIndexes` останавливался на первой ошибке. В Typemo индексы сами не строятся никогда. Вы явно вызываете [`init`](../reference/connection/connection.mdx#connectioninit), [`syncAll`](../reference/collections/sync-all.mdx) или [`syncIndexes`](../reference/collections/model-indexes.mdx#modelsyncindexes). Собираются все сбои, а не только первый, и приходят одной ошибкой [`SyncError`](../reference/errors/configuration-errors.mdx#syncerror).

Сравнение точное. `unique: false` и `sparse: false` на сервере отличием не считаются, правило сортировки строк сравнивается так, как его применяет сервер, а срок жизни TTL и видимость индекса меняются без пересоздания.

</Callout>
