MongoDB хранит документы не в JSON, а в **BSON**. Это двоичный формат, похожий на JSON, только типов значений в нём больше. Поэтому у части значений в базе нет пары ни в JavaScript, ни в JSON — у идентификатора `ObjectId`, 64-битного целого, точного десятичного числа, двоичных данных. Typemo превращает их в понятные типы TypeScript и прямо показывает, где значение остаётся собой, а где становится строкой. Так данные не меняются у вас за спиной.

Ниже разберём, откуда берутся эти типы и зачем для них разные формы результата. Прочитайте страницу один раз, до руководств по [выбору типов полей](../schemas/field-types.mdx) и [чтению данных](../queries/reading-data.mdx). Дальше документация будет ссылаться сюда при каждом новом `ObjectId` или `bigint`. Полная таблица «тип и форма» лежит в справочнике [Формы значений](../reference/values/value-forms.mdx).

## Что такое BSON [#bson]

**BSON** (binary JSON) — формат, в котором сервер MongoDB хранит документы и обменивается данными с драйвером. Как и в JSON, в нём есть объекты, массивы, строки, числа и логические значения. Но у BSON ещё есть отдельные типы для даты, идентификатора, двоичных данных, целых разной ширины и точного десятичного числа. Официальный драйвер `mongodb` превращает их в объекты JavaScript и обратно, а классы для них берёт из пакета `bson`.

Разница между типами важна и для вас, и для базы. Если в поле лежит `ObjectId`, а в фильтре стоит строка из тех же двадцати четырёх символов, документ не найдётся. Для сервера это два разных значения. Сортировка и сравнение тоже смотрят на тип значения, а не на то, как оно выглядит в тексте.

## Почему они не помещаются в JSON [#not-json-safe]

JSON знает только строку, число, логическое значение, `null`, массив и объект. Число в нём — это число JavaScript, то есть double. Посмотрим, что станет с остальными типами, если отдать их в `JSON.stringify` напрямую. Так сделал бы обработчик запроса, который отправляет прочитанную строку клиенту.

<Snippet id="concepts/bson-types/not-json-safe" twoslash />

У каждого значения своя беда, и ни одно не годится клиенту без переделки. `ObjectId` стал строкой, и клиент пришлёт обратно строку, а не идентификатор. `Decimal128` превратился в объект со служебным ключом, двоичные данные — в строку base64, а `Long` — в две половинки числа.

Опаснее всего число за пределами точности double. `9007199254740993` в числе JavaScript молча превращается в `9007199254740992`, без всякой ошибки. Единственное, на чём `JSON.stringify` падает, — это `bigint`, с ошибкой `TypeError: JSON.stringify cannot serialize BigInt.`. Поэтому результат `.lean()` с int64 напрямую клиенту не отдать.

Вот почему Typemo не навязывает одну картину значения на все случаи. Одно и то же сохранённое значение доступно в нескольких **формах**.

- Как в драйвере — для расчётов внутри приложения.
- Как в `.plain()` — обычные данные JavaScript, где типы MongoDB стали строками.
- Как JSON.

Форму выбирают по тому, что будет с данными после чтения. Руководство [Чтение данных](../queries/reading-data.mdx#send-to-client) разбирает этот выбор на задачах.

## ObjectId [#object-id]

`ObjectId` — 12-байтовый идентификатор. Его создают сервер и драйвер для поля `_id`, если вы не задали его сами. Начинается он со времени создания в секундах, так что сортировка по `_id` примерно повторяет порядок создания. В базе это отдельный тип, не строка, а в тексте он записывается 24 шестнадцатеричными символами.

В документе, в результате `.lean()` и в `$toObject()` это экземпляр `ObjectId`, а в `.plain()` и в JSON — строка. Строку принимают обратно все методы записи, фильтры и [`findById`](../reference/query/reading.mdx#model.find-by-id), так что оборачивать строку от клиента в `ObjectId` вручную не нужно. Учтите, что два экземпляра `ObjectId` с одним значением — разные объекты, и `===` между ними даёт `false`. Сравнивайте через `id.equals(other)`.

## Целые числа int32, int64 и double [#int32-int64-double]

В BSON три числовых типа — 32-битное целое, 64-битное целое и double. А в JavaScript число одно, так что драйверу приходится выбирать. Число из поля `Number` ляжет в базу как int32, если оно целое и помещается, и как double, если нет. `Types.Int32` требует именно int32 и не пропустит дробное число или число вне диапазона. `Types.Double` всегда хранит double.

С 64-битным целым всё иначе. Точно хранить его в JavaScript умеет только `bigint`. Поле объявляется типом `BigInt` (`Types.Long` как тип поля не подходит), и во всех формах, где значение остаётся значением, это `bigint`. Ради точности этот тип и существует. Целые больше 2⁵³ в числе JavaScript теряют младшие цифры, поэтому сумма в копейках или счётчик событий, перевалившие эту границу, должны лежать в `int64`.

В `.plain()` и JSON int64 становится **десятичной строкой** `"9007199254740993"`. Она хранит все цифры и спокойно проходит через `JSON.stringify`. Методы записи принимают её обратно, в том числе `$inc`, `$mul`, `$min` и `$max`. Обычное число int64-поле примет, только если это безопасное целое. Иначе будет ошибка с подсказкой — `Cast to Long failed at path "total" for 1152921504606847000 (number): beyond Number.MAX_SAFE_INTEGER the number is already imprecise; pass a bigint (5n) or a decimal integer string ("5") [precision]`.

## Decimal128 [#decimal128]

`Decimal128` — десятичное число с точностью до 34 цифр. Число JavaScript двоичное, и `0.1 + 0.2` в нём даёт `0.30000000000000004`. Для денег это недопустимо, сумма в базе должна быть ровно `19.99`. `Decimal128` хранит десятичную запись как есть и считает по десятичным правилам.

В документе и в результате `.lean()` это экземпляр `Decimal128`, в `.plain()` и JSON — строка вида `"19.99"`. Создавайте значение из строки, `Types.Decimal128.fromString("19.99")`, а не из числа JavaScript. Число потеряло бы точность ещё до того, как попало в `Decimal128`. Методы записи принимают и саму строку `"19.99"` — `create({ weight: "19.99" })` сохранил точное значение.

## Даты и Timestamp [#dates-and-timestamp]

`Date` в BSON — это миллисекунды от 1 января 1970 года по UTC. В JavaScript ему соответствует родной `Date`, поэтому в `.lean()` и `.plain()` он остаётся `Date`, а в JSON становится ISO-строкой `"2026-01-02T03:04:05.000Z"`. Часового пояса у значения нет, он появляется только при показе.

`Timestamp` — не дата, что бы ни подсказывало название. Это служебный тип MongoDB для репликации, пара из секунд и порядкового номера внутри секунды. В `.plain()` и JSON он становится объектом `{ t, i }`. Для моментов времени в своих данных берите `Date`. `Timestamp` объявляют полем, только когда читают чужие данные, где он уже есть.

## Binary, UUID и векторы [#binary-uuid-vectors]

`Binary` — это байты с **подтипом**, который говорит, что внутри.

- Подтип 0 — произвольные данные.
- Подтип 4 — UUID.
- Подтип 9 — вектор.
- Значения от 128 — для ваших нужд.

В документе это экземпляр `Binary`, в `.plain()` — копия `Uint8Array`, в JSON — строка base64.

`UUID` — 16-байтовый идентификатор, который хранится как `Binary` подтипа 4. Typemo отдаёт его классом `UUID` с методами и принимает строку вида `0f8fad5b-d9cb-469f-a165-70867728950e`. В `.plain()` и JSON это та же строка.

**Вектор** — массив чисел одного типа (`int8`, `float32` или упакованные биты) в `Binary` подтипа 9. MongoDB использует его для векторного поиска. В документе он остаётся `Binary`, а в `.plain()` и JSON превращается в обычный массив чисел — клиенту нужны числа, а не байты. Как объявить такие поля, смотрите в справочнике — [`Spec.binary`](../reference/schemas/types-and-spec.mdx#spec.binary) и [`Spec.vector`](../reference/schemas/types-and-spec.mdx#spec.vector).

## Как это выглядит в коде Typemo [#in-typemo-code]

Поле объявляется классом, который соответствует типу в базе. Это `BigInt` для int64, `Types.Decimal128` для точного числа, `Types.UUID`, `Date`. Допустим, датчик пишет показания с точным весом, большим счётчиком и идентификатором устройства.
