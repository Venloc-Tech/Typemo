MongoDB принимает почти любой запрос. Поле с опечаткой в фильтре, `undefined` вместо значения, пустой фильтр в удалении — она либо ничего не найдёт, либо сделает не то, и ничего не скажет. Typemo ведёт себя наоборот. Всё, что нельзя выполнить однозначно, для него **ошибка**, и до базы такой запрос не доходит. Это называется **строгостью**, и она действует всегда. Ни опция, ни режим её не ослабляют.

Ниже разберём, что именно Typemo не пропускает, чем это отличается от самой MongoDB и когда появляется ошибка — при компиляции или при запуске. Страницу достаточно прочитать один раз. Правила каждой политики подробно описаны в разделе [Политики](../policies/overview.mdx).

Примеры построены на банковских счетах. Класс такой.

```ts twoslash title="accounts/account.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => Number, { required: true })
  balance!: number;

  @Prop(() => String)
  status?: string;
}
```

## Неизвестные поля

MongoDB не знает, какие поля бывают у документов, и имя с опечаткой для неё ничем не хуже любого другого. Фильтр `{ ownr: "ann" }` вернёт пустой список, а `updateOne` с `$set: { nope: 1 }` спокойно допишет в документ новое поле. В первом случае вы решите, что счетов нет. Во втором получите документ с мусорным полем. И оба раза без ошибки.

Typemo знает поля класса и сверяет каждый путь — в фильтре, обновлении, проекции и сортировке. Опечатку компилятор остановит прямо в редакторе.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
// @errors: 2561
await Accounts.find({ ownr: "ann" });
```

Компилятор даже подскажет правильное имя (`Did you mean to write 'owner'?`). Если запрос собран на лету и путь компилятору не виден, проверка сработает при запуске и бросит [`StrictModeError`](../reference/errors/data-errors.mdx#strictmodeerror) с причиной `unknown-path`. Сообщение начинается с места ошибки (`filter`, `$set`, `projection`, `sort`), а дальше называет путь и модель.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
const filter: Record<string, unknown> = { ownr: "ann" };
try {
  await Accounts.find(filter);
} catch (error) {
  console.log((error as Error).message);
}
// → filter: "ownr" is not a field of Account [unknown-path]
```

Отдельная история — документы, где лишние поля уже лежат в базе, потому что их записала другая версия схемы. Молча Typemo их не выбрасывает. Сохранение, которое стёрло бы такие поля, бросит ошибку, подробнее об этом на странице [Неизвестные поля](../documents/unknown-fields.mdx). Лишний ключ при создании документа тоже ошибка. `create({ owner: "x", balance: 1, bogus: 1 })` бросит [`CastError`](../reference/errors/data-errors.mdx#casterror) с причиной `unknown-key` и текстом `Cast to Account failed at path "bogus" for 1 (number): not a field of Account [unknown-key]`.

Фильтр из `Record<string, unknown>` компилятор примет, но заглянуть внутрь не сможет. Ключи такого объекта ему неизвестны, и опечатку он не заметит. Поэтому динамические фильтры проверяются только при запуске, как в примере выше, и неизвестный путь даёт `StrictModeError` ещё до базы. Если форма запроса известна заранее, объявите её типом `Filter<Account>`, и опечатку поймает компилятор.

## undefined

В JavaScript `undefined` обычно значит «значения нет», а драйвер MongoDB по умолчанию отправляет его как `null`. Поэтому фильтр `{ owner: undefined }` найдёт документы, где поле пустое или его нет вовсе. А ждут обычно другого — что фильтра по владельцу просто не будет. Так `undefined` из необязательного параметра превращается в выборку чужих или неполных данных.

Typemo не гадает за вас, для него `undefined` — ошибка, а не значение. В фильтре компилятор его не пропустит, ведь тип поля `owner` — `string`, а не `string | undefined`.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
// @errors: 2379
await Accounts.find({ owner: undefined });
```

Если `undefined` всё же добрался до запуска, вы получите [`QueryError`](../reference/errors/query-errors.mdx#queryerror) с точным путём. В сообщении будет и то, что вы, скорее всего, имели в виду.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
const owner: string | undefined = process.env.OWNER;
try {
  await Accounts.find({ owner: owner as string });
} catch (error) {
  console.log((error as Error).message);
}
// → filter: undefined at "owner" (use $exists: false / $unset; undefined is never a value)
```

Документы без значения ищут через `{ owner: { $exists: false } }`, а поле убирают через `$unset`. Оба намерения выражены явно, и спутать их с ошибкой в данных не получится.

## Пустые фильтры

Пустой фильтр `{}` в MongoDB значит «все документы». Для чтения это нормально, для записи опасно. `deleteMany({})` удалит всю коллекцию, а `updateOne({}, …)` и `deleteOne({})` изменят или удалят какой попало документ — тот, что сервер найдёт первым. Получить такой фильтр легко, когда условия собираются из необязательных параметров, а не пришло ни одного. Поэтому Typemo не пропускает пустой фильтр ни в одной операции записи.

- `updateOne` и `updateMany`.
- `deleteOne` и `deleteMany`.
- `replaceOne`.
- `findOneAnd*`.

Пустой литерал `{}` в этих методах остановит уже компилятор.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
// @errors: 2345
await Accounts.deleteMany({});
```

Фильтр, собранный во время работы, может оказаться пустым, а компилятор этого не видит. Такой фильтр остановит проверка при запуске. Здесь он собирается из условий, которых не оказалось.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
const filter: { owner?: string } = {};
try {
  await Accounts.findOneAndUpdate(filter, { $set: { status: "closed" } });
} catch (error) {
  console.log((error as Error).message);
}
// → findOneAndUpdate with an empty filter would change or remove an arbitrary document; pass a filter, or Filters.all() to mean every document on purpose [empty-filter]
```

Если затронуть всё нужно намеренно, скажите об этом явно. `Filters.all()` разрешает «все документы» и вызывается без аргументов. Какие методы проверяются и откуда берётся пустой фильтр, рассказывает руководство [Пустые фильтры](../writes/empty-filters.mdx).

## Неверные типы

MongoDB не сверяет тип в запросе с типом поля. Фильтр `{ balance: "10" }` для неё просто ничего не находит, ведь строка `"10"` и число `10` — разные значения. Typemo не превращает строку в число втихую. Значение либо подходит полю, либо это ошибка.

Компилятор заметит неверный тип и при записи, и в фильтре.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
// @errors: 2769
await Accounts.create({ owner: "ann", balance: "12" });
```

При запуске та же проверка бросает [`CastError`](../reference/errors/data-errors.mdx#casterror), а причина в скобках (`type`) говорит, что не так. Нужна она потому, что данные из HTTP-запроса и из файлов компилятор не видел.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
const body: unknown = JSON.parse('{ "owner": "ann", "balance": "12" }');
try {
  await Accounts.create(body as { owner: string; balance: number });
} catch (error) {
  console.log((error as Error).message);
}
// → Cast to number failed at path "balance" for "12" (string): expected a number [type]
```

С `null` то же самое. Фильтр `{ owner: { $ne: null } }` для поля, которое не может быть `null`, смысла не имеет, и Typemo об этом скажет — `Cast to string failed at path "owner.$ne" for null: null is not a value of this path (it is not nullable); an absent field is { $exists: false }`. Типы с безопасной строковой формой (`ObjectId`, `UUID`, int64) принимают строку, потому что она однозначна. Подробнее — на странице [Типы данных MongoDB](./bson-types.mdx).

## Данные, которые уже лежат в базе

Все проверки выше стоят на пути **в** базу — в запросе, в фильтре, в записи. Значит, документ, записанный моделью, уже имеет объявленные типы, и при чтении Typemo по умолчанию его не перепроверяет. Сверка каждого поля каждого прочитанного документа стоила бы времени на каждом запросе, а в данных модели ничего бы не нашла.

Но в коллекцию пишет не только модель. Бывает скрипт на драйвере, другой сервис, импорт, старая версия схемы. В таком документе поле `balance` может хранить строку `"12"`, и обычное чтение отдаст её вашему коду под типом `number`. На этот случай есть **строгое чтение**, и включают его явно — опцией клиента [`validateReads`](../reference/connection/typemo-client.mdx#validatereads) или вызовом [`.validateReads()`](../reference/query/options.mdx#validatereads) в запросе. Тогда документ сверяется со схемой, прежде чем стать результатом.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
// ---cut---
const client = await TypemoClient.connect("mongodb://localhost:27017/bank", { validateReads: "development" });
const Accounts = client.connection.model(Account);
await client.unsafeDriver().db("bank").collection("accounts").insertOne({ owner: "ann", balance: "12" });

try {
  await Accounts.find({ owner: "ann" }).plain();
} catch (error) {
  console.log((error as Error).message);
}
// → Cast to number failed at path "balance" for "12" (string): the stored value does not match the schema of Account (a document read from the database, checked by validateReads) [type]
```

Ошибка та же, что при записи, — [`CastError`](../reference/errors/data-errors.mdx#casterror) с путём и причиной. Только в тексте сказано, что значение пришло из базы. Значение `"development"` включает проверку везде, кроме `NODE_ENV=production`. В разработке и тестах испорченные данные видны сразу, а в продакшене чтение за проверку не платит.

Это единственная проверка Typemo, которую включают отдельно. Строгость она не ослабляет, а добавляет проверку для данных, которые записал не Typemo.

## Компилятор и время работы

Каждое правило проверяется дважды, и это не дублирование. Компилятор видит ваш код — имена полей в литералах, типы значений, `undefined`, несуществующее поле. Он ловит ошибку, пока вы печатаете. А данные из запроса, из файла и из фильтра, собранного на лету, приходят уже после компиляции. Поэтому те же проверки идут и при запуске, и бросают ошибки из иерархии Typemo с точным путём и причиной.

Отсюда простое следствие. Если типы написаны аккуратно, ошибка при запуске означает **плохие входные данные**, а не вашу опечатку. Ставьте `catch` на границе приложения, там, где входят внешние данные (обработчик запроса, задача из очереди), а не вокруг каждого вызова. Как это устроить, показывает руководство по [обработке ошибок](../errors/handling.mdx), а все причины с примерами собраны в справочнике [`StrictModeError`](../reference/policies/violations.mdx#strictmodeerror).

Строгость не ограничивается этой страницей. Вот ещё что Typemo не пропустит.

- `limit(0)` с ошибкой `limit must be a positive integer, got 0 (number)`. Значение печатается вместе с типом, так что `"3"` сразу видно как строку.
- Обновление, которое после приведения оказалось пустым, — `update: operator "$set" is empty`.
- Запись неизменяемого поля.

Часть проверок вынесена в политики, которые действуют на все операции модели. Среди них [строгие пути](../policies/strict-paths.mdx), [пустые фильтры и лимиты](../policies/filters-and-limits.mdx) и защита от [недоверенного ввода](../policies/untrusted-input.mdx).
