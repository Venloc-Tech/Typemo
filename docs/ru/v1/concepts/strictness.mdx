MongoDB принимает почти любой запрос: поле с опечаткой в фильтре, `undefined` вместо значения, пустой фильтр в удалении. Она либо ничего не найдёт, либо сделает не то, что вы хотели, и не скажет об этом. Typemo устроен наоборот: то, что нельзя однозначно выполнить, он считает **ошибкой** и останавливает до отправки в базу. Эту идею называют **строгостью**, и она действует всегда: ни опция, ни режим её не ослабляют.

Страница объясняет, что именно Typemo не пропускает, чем это отличается от поведения самой MongoDB и на каком этапе ошибка появляется: при компиляции или при запуске. Она читается один раз; правила для каждой политики подробно описаны в разделе [Политики](../policies/overview.mdx).

Примеры используют счета банка. Класс объявлен так:

```ts twoslash title="accounts/account.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => Number, { required: true })
  balance!: number;

  @Prop(() => String)
  status?: string;
}
```

## Неизвестные поля

Сама MongoDB не знает, какие поля бывают у документов, поэтому имя с опечаткой для неё такое же допустимое, как любое другое. Фильтр `{ ownr: "ann" }` ничего не найдёт и вернёт пустой список, а `updateOne` с `$set: { nope: 1 }` спокойно допишет в документ новое поле. В первом случае вы решите, что счетов нет, во втором получите документ с мусорным полем, и оба раза ошибки не будет.

Typemo знает поля класса и сверяет каждый путь: в фильтре, обновлении, проекции и сортировке. Компилятор останавливает опечатку в редакторе:

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
// @errors: 2561
await Accounts.find({ ownr: "ann" });
```

Компилятор даже подсказывает нужное имя (`Did you mean to write 'owner'?`). Если запрос собран динамически и компилятор пути не видит, проверка срабатывает при запуске и бросает [`StrictModeError`](../reference/errors/data-errors.mdx#strictmodeerror) с причиной `unknown-path`. Сообщение начинается с места, где найдена ошибка (`filter`, `$set`, `projection`, `sort`), затем называет путь и модель:

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
const filter: Record<string, unknown> = { ownr: "ann" };
try {
  await Accounts.find(filter);
} catch (error) {
  console.log((error as Error).message);
}
// → filter: "ownr" is not a field of Account [unknown-path]
```

Отдельный случай — документы, в которых лишние поля уже лежат в базе, потому что их записала другая версия схемы. Их Typemo не отбрасывает молча: сохранение, которое их бы стёрло, бросает ошибку, и об этом рассказывает страница [Неизвестные поля](../documents/unknown-fields.mdx). Ошибка возникает и при создании документа с лишним ключом: `create({ owner: "x", balance: 1, bogus: 1 })` бросает [`CastError`](../reference/errors/data-errors.mdx#casterror) с причиной `unknown-key` и текстом `Cast to Account failed at path "bogus" for 1 (number): not a field of Account [unknown-key]`.

Фильтр, который собран из `Record<string, unknown>`, компилятор принимает, но не видит целиком: ключи такого объекта ему неизвестны, и опечатку он не заметит. Поэтому динамические фильтры проверяются только при запуске, как в примере выше: неизвестный путь — `StrictModeError` до обращения к базе. Если форма запроса заранее известна, объявляйте её типом `Filter<Account>`: тогда опечатку остановит компилятор.

## undefined

В JavaScript `undefined` обычно значит «значения нет», а драйвер MongoDB по умолчанию отправляет его как `null`. Поэтому фильтр `{ owner: undefined }` находит документы, у которых поле пустое или отсутствует, а не «не фильтрует по владельцу», как ожидают. Так `undefined` из необязательного параметра запроса превращается в выборку чужих или неполных данных.

Typemo не выбирает за вас: `undefined` не значение, а ошибка. Компилятор отвергает его в фильтре, потому что тип поля `owner` — `string`, а не `string | undefined`:

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
// @errors: 2379
await Accounts.find({ owner: undefined });
```

Если `undefined` всё же дошёл до запуска, вы получите [`QueryError`](../reference/errors/query-errors.mdx#queryerror) с точным указанием пути, а в сообщении — что вы хотели сказать на самом деле:

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
const owner: string | undefined = process.env.OWNER;
try {
  await Accounts.find({ owner: owner as string });
} catch (error) {
  console.log((error as Error).message);
}
// → filter: undefined at "owner" (use $exists: false / $unset; undefined is never a value)
```

Чтобы найти документы без значения, пишут `{ owner: { $exists: false } }`, а чтобы убрать поле, используют `$unset`. Оба намерения выражены явно, и путать их с ошибкой в данных нельзя.

## Пустые фильтры

Пустой фильтр `{}` в MongoDB значит «все документы». В чтении это нормально, а в записи опасно: `deleteMany({})` удаляет всю коллекцию, а `updateOne({}, …)` и `deleteOne({})` меняют или удаляют произвольный документ, какой сервер найдёт первым. Такой фильтр легко получить, когда условия собираются из необязательных параметров, а ни одного параметра не пришло. Поэтому Typemo отвергает пустой фильтр во всех операциях записи: `updateOne`, `updateMany`, `deleteOne`, `deleteMany`, `replaceOne` и `findOneAnd*`.

Пустой литерал `{}` в этих методах останавливает уже компилятор:

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
// @errors: 2345
await Accounts.deleteMany({});
```

Фильтр, собранный во время работы, может оказаться пустым, и компилятор этого не видит: такой фильтр останавливает проверка при запуске. Здесь фильтр приходит из условий, которых не оказалось:

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
const filter: { owner?: string } = {};
try {
  await Accounts.findOneAndUpdate(filter, { $set: { status: "closed" } });
} catch (error) {
  console.log((error as Error).message);
}
// → findOneAndUpdate with an empty filter would change or remove an arbitrary document; pass a filter, or Filters.all() to mean every document on purpose [empty-filter]
```

Если затронуть всё нужно намеренно, это записывается явно: `Filters.all()` разрешает «все документы» и компилируется без аргументов. Какие методы проверяются и откуда берётся пустой фильтр, объясняет руководство [Пустые фильтры](../writes/empty-filters.mdx).

## Неверные типы

MongoDB не сравнивает тип запроса с типом поля: фильтр `{ balance: "10" }` для неё просто ничего не находит, потому что строка `"10"` и число `10` — разные значения. Typemo не приводит строку к числу молча: значение либо подходит полю, либо это ошибка.

Компилятор замечает неверный тип при записи и в фильтре:

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
// @errors: 2769
await Accounts.create({ owner: "ann", balance: "12" });
```

При запуске та же проверка называется [`CastError`](../reference/errors/data-errors.mdx#casterror), а причина в скобках (`type`) говорит, что не так. Она есть потому, что данные из HTTP-запроса и из файлов компилятор не проверял:

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/bank");
const Accounts = client.connection.model(Account);
// ---cut---
const body: unknown = JSON.parse('{ "owner": "ann", "balance": "12" }');
try {
  await Accounts.create(body as { owner: string; balance: number });
} catch (error) {
  console.log((error as Error).message);
}
// → Cast to number failed at path "balance" for "12" (string): expected a number [type]
```

Тот же принцип работает для `null`. Фильтр `{ owner: { $ne: null } }` для поля, которое не может быть `null`, не имеет смысла, и Typemo сообщает об этом: `Cast to string failed at path "owner.$ne" for null: null is not a value of this path (it is not nullable); an absent field is { $exists: false }`. Типы, у которых есть безопасная строковая форма (`ObjectId`, `UUID`, int64), принимают строку, потому что она однозначна: об этом рассказывает страница [Типы данных MongoDB](./bson-types.mdx).

## Данные, которые уже лежат в базе

Все проверки выше стоят на пути **в** базу: в запросе, в фильтре, в записи. Документ, который записала модель, поэтому уже имеет объявленные типы, и при чтении Typemo его по умолчанию не перепроверяет: сверка каждого поля каждого прочитанного документа стоила бы времени на каждом запросе, а для данных модели ничего бы не нашла.

Но в коллекцию пишут не только через модель: скрипт на драйвере, другой сервис, импорт, старая версия схемы. Такой документ может хранить в поле `balance` строку `"12"`, и обычное чтение отдаст её коду под типом `number`. Для этого случая есть **строгое чтение**, которое включают явно: опцией клиента [`validateReads`](../reference/connection/typemo-client.mdx#validatereads) или вызовом [`.validateReads()`](../reference/query/options.mdx#validatereads) в запросе. Тогда документ сверяется со схемой до того, как станет результатом:

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { required: true }) balance!: number;
  @Prop(() => String) status?: string;
}
// ---cut---
const client = await TypemoClient.connect("mongodb://localhost:27017/bank", { validateReads: "development" });
const Accounts = client.connection.model(Account);
await client.unsafeDriver().db("bank").collection("accounts").insertOne({ owner: "ann", balance: "12" });

try {
  await Accounts.find({ owner: "ann" }).plain();
} catch (error) {
  console.log((error as Error).message);
}
// → Cast to number failed at path "balance" for "12" (string): the stored value does not match the schema of Account (a document read from the database, checked by validateReads) [type]
```

Ошибка та же, что при записи, [`CastError`](../reference/errors/data-errors.mdx#casterror) с путём и причиной, но в тексте сказано, что значение пришло из базы. Значение `"development"` включает проверку везде, кроме `NODE_ENV=production`: так в разработке и тестах испорченные данные видны сразу, а в продакшене чтение не платит за проверку. Это единственная проверка Typemo, которую включают отдельно: она не ослабляет строгость, а добавляет проверку к данным, которые Typemo не записывал.

## Компилятор и время работы

Каждое правило проверяется дважды, и это не дублирование. Компилятор видит код, который вы написали: имена полей в литералах, типы значений, `undefined`, поле, которого нет. Он ловит ошибку, пока вы печатаете. Но данные из запроса, из файла и из динамически собранного фильтра приходят уже после компиляции, поэтому такие же проверки выполняются при запуске и бросают ошибки из иерархии Typemo с точным путём и причиной.

Практическое следствие: если вы пишете типы аккуратно, ошибки времени выполнения означают **плохие входные данные**, а не ваши опечатки. Ветку `catch` ставят на границе приложения (обработчик запроса, задача из очереди), где входят внешние данные, а не вокруг каждого вызова. Как это устроить, показывает руководство по [обработке ошибок](../errors/handling.mdx), а полный список причин с примерами — справочник [`StrictModeError`](../reference/policies/violations.mdx#strictmodeerror).

Строгость не ограничивается случаями этой страницы. Typemo отвергает `limit(0)` (`limit must be a positive integer, got 0 (number)`; значение печатается вместе с типом, поэтому `"3"` видно как строку), обновление, пустое после приведения (`update: operator "$set" is empty`), и запись неизменяемого поля. Часть проверок вынесена в политики, которые действуют на все операции модели, в том числе [строгие пути](../policies/strict-paths.mdx), [пустые фильтры и лимиты](../policies/filters-and-limits.mdx) и защита от [недоверенного ввода](../policies/untrusted-input.mdx).
