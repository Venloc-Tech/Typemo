Пакет `@venloc/typemo-sentry` отправляет в Sentry ошибки операций с контекстом — модель, коллекция, шаг, вид сбоя. Ещё он оставляет **breadcrumbs**, короткие записи о том, что происходило перед ошибкой. Открыв событие в Sentry, вы сразу видите, какая операция какой модели упала и можно ли её повторить. Адаптер использует только `@sentry/core`, поэтому одинаково работает с `@sentry/node` и `@sentry/bun`.

Трассировка тут не нужна, спаны в Sentry приходят из [OpenTelemetry](./opentelemetry.mdx). Справочник по пакету — [`@venloc/typemo-sentry`](../reference/observability/sentry.mdx).

## Что понадобится

Sentry уже инициализирован в приложении, с DSN и прочими настройками, а клиент создан как в [быстром старте](../getting-started/quick-start.mdx). Сборка документации не подключает Sentry, поэтому блоки кода на странице не компилируются. Работа адаптера проверена запуском на настоящей базе.

## Быстрый путь

```package-install
@venloc/typemo-sentry @sentry/node
```

```ts title="monitoring.ts"
import * as Sentry from "@sentry/node";
import { TypemoClient } from "@venloc/typemo";
import { TypemoSentry } from "@venloc/typemo-sentry";

Sentry.init({ dsn: "https://public@example.test/1" });

const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "bank" });
const subscription = TypemoSentry.instrument(client);
```

Чтобы охватить все клиенты процесса, вызовите `TypemoSentry.instrument(Typemo)`. Отписаться можно через `subscription.unsubscribe()`.

## Разобрать ошибку в Sentry

Скажем, в Sentry пришло событие `DuplicateKeyError`. Адаптер прикрепил к нему контекст `typemo` и четыре тега. Повторная вставка с тем же уникальным `title` дала теги `typemo.error_class: DuplicateKeyError`, `typemo.classification: duplicate-key`, `typemo.operation: insertOne` и `typemo.model: Account`. В контексте оказались `database: "bank"`, `failedStep: "execute"`, `serverCode: 11000`, `retryable: false` и `transient: false`. Теги удобны для фильтров и правил оповещения, а контекст — для разбора.

Сообщение ошибки в Sentry уже замаскировано — `duplicate key on title_1: { title: "?" } (code 11000 DuplicateKey)`, хотя вызвавший код получил настоящее значение. Так номер счёта или адрес почты наружу не уйдут.

## Понять, что было перед ошибкой

Каждая закончившаяся операция оставляет breadcrumb вроде `Typemo.find (Account)` с категорией `typemo`. В его `data` лежат модель, коллекция, база, длительность, число документов и форма запроса без значений, например `{ filter: { balance: { $gt: "?" } } }`.

У операции уровня базы ([`connection.aggregate`](../reference/connection/connection.mdx#connectionaggregate)) нет ни модели, ни коллекции. Сообщение у неё такое же, как у спана OpenTelemetry, `Typemo.aggregate (database bank)`, а в `data` остаются база, длительность и форма конвейера. Упавшая операция оставляет запись уровня `error` с `failedStep` и `errorKind`.

Повтор и откат транзакции — тоже breadcrumbs, `Typemo.transaction retry` и `Typemo.transaction abort`. В них только имя класса ошибки, потому что сообщение драйвера может цитировать значения.

## Только breadcrumbs или только ошибки

Если ошибки вы уже отправляете сами, отключите их отправку в адаптере.

```ts
TypemoSentry.instrument(client, { captureErrors: false });
```

Или наоборот, `breadcrumbs: false` оставит только ошибки. Если выключить оба, в Sentry не придёт ничего, это проверено. Фильтровать ошибки по виду адаптер не умеет и отправляет все. Шум отсекайте в самом Sentry, через `beforeSend`.

## Одна ошибка — одно событие

Дубликатов не будет, даже если адаптер зарегистрирован дважды или вы сами вызвали `captureException` для той же ошибки. `@sentry/core` помечает уже отправленные исключения.

## Не отдать данные пользователей

По умолчанию (`sensitive: "mask"`) значения в сводке и в ошибках `CastError`, `ValidationError`, `DuplicateKeyError` и `ServerValidationError` заменены на `"?"`. Настоящие значения уходят только при `sensitive: "show"` или через вашу функцию `{ mask }`, и даже тогда не для полей, помеченных `sensitive` в схеме. Режимы описаны в [справочнике событий](../reference/observability/events.mdx#subscribersensitive).

Тенант по умолчанию в Sentry не уходит, ведь это данные ваших клиентов. Если он нужен для разбора ошибок, включите `includeTenant: true`. У отправленной ошибки появятся тег `typemo.tenant` и поле `tenant` в контексте `typemo`. Для операций без тенанта ничего не меняется, а в breadcrumbs тенанта не бывает никогда.

```ts
TypemoSentry.instrument(client, { includeTenant: true });
```

## Как выбрать

Спросите себя, **где вы хотите видеть ошибки**. Если в Sentry, берите этот адаптер, а спаны пусть даёт OpenTelemetry — их можно подключить вместе. Если в другом трекере, напишите подписчика, как в [Своей интеграции](./custom-integration.mdx).

## Когда это не нужно

Если вы уже ловите ошибки на границе приложения и сами отправляете их с нужным контекстом, адаптер продублирует контекст. Тогда оставьте только breadcrumbs. Ошибку из хука `pre('save')`, брошенную до начала операции, адаптер не видит, она случилась вне операции.

## Если что-то пошло не так

**В Sentry нет ошибок валидации.** `create`, `$save` и `bulkSave` проверяют значения внутри своей операции, так что `ValidationError` до Sentry доходит. Не доходит только ошибка, брошенная в хуке `pre('save')` до операции.

**Ошибки приходят, но без значений.** Так и задумано, вместо значений стоит `"?"`. Включайте `sensitive: "show"` осознанно, понимая, что данные уйдут в Sentry.
