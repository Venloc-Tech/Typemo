Многое из того, что есть в Mongoose, в Typemo отсутствует не потому, что «не дошли руки», а потому, что это неотделимо от неявного поведения: то самое «молча приведу», «молча отброшу», «молча пропущу». Эта страница перечисляет такие возможности и для каждой называет причину и замену. Если вы ищете один конкретный метод, быстрее взглянуть на таблицы [Соответствия API](../reference/migration/api-mapping.mdx); здесь разобраны те отсутствия, для которых нужно не имя, а другой подход.

## Что предполагается

Примеры используют блог: пользователи и посты. `Posts` — модель поста, полученная у клиента: `client.db().model(Post)`.

## Быстрый путь

Пять отсутствий, с которыми сталкиваются почти все, и их замены:

| В Mongoose | В Typemo |
|---|---|
| поле `Mixed`, `Object`, `{}` | вложенный класс или [`Spec.map`](../reference/schemas/types-and-spec.mdx#specmap) |
| `strict: false`, `strictQuery: false` | нет; неизвестное — ошибка |
| `select("a -b")`, `sort("-age")` | объект: `select({ a: 1 })`, `sort({ age: -1 })` |
| `next()` и колбэки | асинхронные методы и исключения |
| `this` как `Query` в хуках | типизированный контекст с методом `.modify` |

Остальная страница разбирает каждое из них.

## Поле произвольной формы: `Mixed`

Сценарий: в документе лежит объект, форму которого заранее не знает схема, например настройки, которые пользователь задаёт сам. Mongoose принимает любой объект, а изменения внутри него нужно вручную отмечать `markModified`. Typemo отказывает уже при объявлении модели:

```ts twoslash
import { Entity, Prop, Schema } from "@venloc/typemo";
// ---cut---
// @errors: 1240
@Schema({ collection: "settings" })
class Settings extends Entity {
  @Prop(() => Object)
  data!: unknown;
}
// во время работы при создании модели:
// ConfigurationError: Settings.data: Object (Mixed) is not supported: declare a @Schema class or Spec.map(X)
```

Причина в том, что Mixed выключает всё, ради чего Typemo существует: проверку значения, тип поля, обновления по вложенным путям и защиту от неизвестных ключей. Компилятор и база для такого поля ничего не знают, а изменение внутри объекта не видно ни `save`, ни `$getChanges`.

Замен две, в зависимости от того, известны ли ключи. Если ключи известны, опишите вложенный класс с [`nested: true`](../reference/schemas/schema.mdx#nested). Если ключи произвольные, а значения одного типа, используйте [`Spec.map`](../reference/schemas/types-and-spec.mdx#specmap): карта со строковыми ключами и проверяемыми значениями.

```ts twoslash
import { Entity, Prop, Schema, Spec, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
// ---cut---
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Spec.map(String)) preferences?: Map<string, string>;
}
const Users = client.db().model(User);
const user = await Users.create({ name: "Ann", preferences: new Map([["theme", "dark"]]) });
console.log(user.preferences?.get("theme"));
// → dark
```

Если действительно нужен произвольный JSON, храните его строкой и разбирайте сами, либо обратитесь к драйверу через [`client.unsafeDriver()`](../reference/connection/typemo-client.mdx#clientunsafedriver) и помните, что политики и проверки Typemo там не действуют.

## Отключить строгость: `strict: false`

Сценарий: часть кода пишет в документ поля, которых нет в схеме, а часть читает их. Опции `strict`, `strictQuery`, `strictPopulate`, `useNestedStrict` и `sanitizeFilter` у Typemo нет. Компилятор отвергает их в [`@Schema`](../reference/schemas/schema.mdx#schema) как неизвестные. Из JavaScript без типов (или с `as never`) ключ тоже не проходит молча: любой ключ, которого нет в списке опций, при сборке модели даёт [`ConfigurationError`](../reference/errors/configuration-errors.mdx#configurationerror) с перечнем допустимых опций, например `Account: @Schema has no "strict" option (the options are: collection, nested, ext, discriminatorKey, discriminators, timeseries, capped, collation, clustered, changeStreamPreAndPostImages, validator, autoIndex, autoCreate, readConcern, writeConcern, optimisticConcurrency, shardKey, tenant, softDelete, audit)`. Для `toJSON` и `toObject` текст свой: он подсказывает передавать параметры сериализации в каждый вызов.

Причина: строгость, которую можно выключить, перестаёт быть гарантией. Библиотека, которая иногда отбрасывает неизвестное поле, а иногда пишет его, заставляет вас помнить, в каком режиме вы сейчас. Если поля действительно есть в базе, но не нужны вашему коду, опишите их в классе. Если это данные, записанные другим приложением, они остаются в документе нетронутыми: верхнего уровня — при любом сохранении, поддокументов — с явным согласием, как описано в руководстве [Неизвестные поля](../documents/unknown-fields.mdx).

## Строки вместо объектов в `select` и `sort`

Mongoose принимает `select("name -password")`, `select("+passwordHash")` и `sort("-age name")`. Typemo принимает только объекты, потому что строку невозможно проверить типами: опечатка в `"nmae"` увидела бы компилятор в объекте, но не в строке.

<Compare>

```ts
const posts = await MPost.find().select("title -views").sort("-views title");
```

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number) views?: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
// ---cut---
const posts = await Posts.find().select({ title: 1 }).sort({ views: -1, title: 1 });
```

</Compare>

Направления `1` и `-1` можно писать и словами `"asc"` и `"desc"`. Смешивать включение и исключение в одной проекции нельзя: Mongoose тихо выбирал одно из двух, Typemo бросает ошибку. Скрытое поле возвращается только явным `+` в проекции, и только для полей, объявленных как [`Hidden`](../reference/schemas/field-markers.mdx#hidden). Подробнее — в справочниках [`.select`](../reference/query/reading.mdx#select) и [`.sort`](../reference/query/reading.mdx#sort).

## Колбэки и `next()`

Колбэки у методов модели Mongoose убрал ещё в седьмой версии, а в девятой убрал и параметр `next` у `pre`-хуков. Если вы переходите с 9.x, вы, скорее всего, уже пишете `async`-функции и ничего менять не придётся. Если код ещё на старой версии, сначала переведите его на промисы внутри Mongoose: так проще найти регрессии, чем при одновременной смене библиотеки.

В Typemo хук — это метод класса, ошибка — исключение, а «пропустить» — вызов `this.skip` в запросном хуке. Ни колбэков, ни `next`, ни события `error` нет.

## `this` в хуках

В хуке запроса Mongoose `this` — это `Query`: им можно переписать условие (`this.where`), добавить `populate`, поменять опции. Всё это происходит после проверок и в обход политик, поэтому в Typemo такого доступа нет. В хуке запроса `this` — типизированный контекст [`OperationHookContext`](../reference/hooks/operation-context.mdx#operationhookcontext): значения операции только читаются, а менять их можно методом [`.modify`](../reference/hooks/operation-context.mdx#modify), и результат снова проходит политики.

<Compare>

```ts
schema.pre("find", function () {
  this.where({ archived: false });
});
```

```ts twoslash
import { type Defaulted, Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
// ---cut---
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Boolean, { default: false }) archived!: Defaulted<boolean>;

  @Pre("query.find")
  onlyActive(this: OperationHookContext<Post, "query.find">): void {
    this.modify({ where: { archived: false } });
  }
}
```

</Compare>

В хуке документа `this` — сам документ, как и в Mongoose, но с `$`-методами. Подробнее — в руководствах [Выполнить код при сохранении документа](../hooks/document-hooks.mdx) и [Вмешаться в операцию](../hooks/operation-hooks.mdx).

## Регулярные выражения в событиях, `pre("save")` для всего

`schema.pre(/^find/, fn)` ловит все события `find`, `findOne` и `findOneAnd*` сразу. В Typemo список событий явный: [`HOOK_EVENTS`](../reference/hooks/pre-post.mdx#hook_events), а один и тот же метод можно повесить на несколько событий несколькими декораторами. Причина — читаемость: по имени события видно, что произойдёт, и регулярное выражение не подхватит новую операцию, о которой вы не знали.

## Сеттеры и порядок обработки значения

В Mongoose порядок сеттеров обратный порядку регистрации, а `trim` и `lowercase` — те же сеттеры. У Typemo порядок фиксирован: приведение типа, затем [`trim`](../reference/schemas/prop.mdx#trim), затем [`lowercase` или `uppercase`](../reference/schemas/prop.mdx#lowercase), затем ваш [`set`](../reference/schemas/prop.mdx#set). Значение `null` в nullable-поле сеттеры не видят: они работают только с настоящим значением.

## Плагины-функции и глобальное изменение схем

Плагин Mongoose — функция, которая мутирует схему, а глобальные плагины применяются при создании каждой модели, кроме уже скомпилированных. Плагин Typemo — объект с методом `apply`, который работает с черновиком метаданных, и регистрация закрывается первой успешно скомпилированной моделью: поздняя регистрация — ошибка, а не тихий пропуск. Подробности — в руководстве [Плагины](../hooks/plugins.mdx).

Для типичных задач, ради которых писали плагины в Mongoose, есть встроенные механизмы: мягкое удаление, тенанты и аудит подключаются опциями [`@Schema`](../reference/schemas/schema.mdx#softdelete) и действуют на всех операциях, включая агрегацию. Плагины `mongoose-delete`, `mongoose-history` и им подобные при переходе становятся ненужными.

## Отладка запросов и `mongoose.set("debug")`

Глобального `debug` нет. Вместо него подписчик на события: [`Typemo.instrument`](../reference/connection/typemo.mdx#typemoinstrument) получает начало и конец каждой операции, время, ошибку и команду. Подробнее — в руководстве [События операций](../observability/events.mdx).

## Код на JavaScript в запросах: `$where`, `$function`, `$accumulator`

В Mongoose можно передать в запрос или конвейер код на JavaScript: условие `$where`, выражение `$function`, аккумулятор `$accumulator`. Typemo серверный JavaScript не выполняет: такой код работает с правами базы, его нельзя проверить по схеме, а внедрённый ввод становится исполняемым кодом. Вызовы [`fn.function` и `fn.accumulator`](../reference/aggregation/accumulators.mdx#код-на-javascript) — ошибки компиляции, текст которых называет замену, а оператор, переданный в обход типов, отклоняется до отправки с `StrictModeError` (правило `sanitize`). Условие пишется операторами запроса или выражением [`$expr`](../queries/filters.mdx), значение группы — аккумуляторами `fn.sum`, `fn.push`, `fn.top`, вычисление — операторами `fn.cond`, `fn.map`, `fn.reduce`.

## Когда это не нужно

Эта страница не про обязательность переноса всего. Если ваши данные по природе «произвольной формы» (журнал событий с полями, которые определяют клиенты, слепок чужих ответов), Typemo для этих коллекций даст больше трения, чем пользы: там строгая модель невозможна. Оставьте такие коллекции на Mongoose или на драйвере, а на Typemo переносите остальные: обе библиотеки работают с одной базой, см. руководство [Пошаговая миграция](./step-by-step.mdx).

## Частые ошибки

### Модель не создаётся: `Object (Mixed) is not supported`

Поле объявлено как `@Prop(() => Object)` или как массив без типа элемента. Замените его вложенным классом или `Spec.map`, как показано выше.

### Опция схемы отвергается на этапе компиляции

Вы перенесли `@Schema({ strict: false })` или `toJSON`. Такие опции у декоратора не существуют, и это сделано намеренно: компилятор их не принимает, а код без типов получит `ConfigurationError` при сборке модели. Уберите их, а параметры сериализации передавайте при вызове [`$toJSON`](../reference/documents/document-api.mdx#tojson).
