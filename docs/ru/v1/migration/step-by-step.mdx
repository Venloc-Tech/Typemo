---

Переносить всё приложение за один релиз не нужно. Обе библиотеки читают и пишут одни и те же документы MongoDB, так что можно описать класс Typemo для одной коллекции, а остальные пока оставить на Mongoose. Ниже — порядок, в котором это безопасно, и места, где две библиотеки мешают друг другу.

Работать вместе они могут, потому что Typemo хранит данные в обычном формате MongoDB и использует тот же драйвер и те же классы `ObjectId`, что и Mongoose. Скрытой служебной разметки в документы не добавляет ни одна из них. Это проверено в обе стороны. Typemo прочитал, изменил и сохранил документ, созданный Mongoose с метками времени, а Mongoose прочитал результат без потерь. И наоборот.

## Что понадобится [#prerequisites]

Приложение на Mongoose 9 с моделью поста `Post` в коллекции `posts` с метками времени и MongoDB, доступная обеим библиотекам. Примеры построены на блоге. Код Mongoose показан только там, где важна разница.

<Steps>
<Step>

### Подготовьте проект [#prepare-project]

Установите пакеты и включите декораторы в `tsconfig`, как в [Быстром старте](../getting-started/quick-start.mdx). Декораторам ядра нужен только флаг `experimentalDecorators`. Ставить и подключать `reflect-metadata` (`import "reflect-metadata"`) не нужно, ядро хранит метаданные само. `emitDecoratorMetadata` тоже не нужен — Typemo не читает `design:type`, а тип поля всегда называется явно, `@Prop(() => String)`.

Если в вашем проекте на Mongoose эти флаги уже включены ради других библиотек, оставьте их, Typemo они не мешают. А если других декораторов в проекте нет, присмотритесь к [пакету TC39-декораторов](../decorators-tc39/tc39.mdx), которому `experimentalDecorators` не нужен.

Typemo требует последние версии MongoDB, драйвера `mongodb` и `bson`. Если ваш Mongoose сидит на другом драйвере, сначала обновите его, иначе классы `ObjectId` окажутся разными. Затем подключите клиент рядом с существующим подключением Mongoose. Подробнее — в руководстве [Подключиться к базе](../connection/connect.mdx).

</Step>
<Step>

### Опишите класс поверх существующей коллекции [#describe-existing-collection]

Имя коллекции задайте явно. Mongoose выводит его из имени модели во множественном числе, а Typemo берёт ровно то, что написано в [`collection`](../reference/schemas/schema.mdx#collection). Служебные поля добавляйте базовыми классами, которые повторяют опции Mongoose. [`Timestamped`](../reference/schemas/base-classes.mdx#timestamped) заменяет `timestamps: true`, а [`Versioned`](../reference/schemas/base-classes.mdx#versioned) — `__v`.

```ts twoslash title="posts/post.ts"
import { Entity, Prop, Schema, Timestamped, TypemoClient, Versioned } from "@venloc/typemo";

@Schema({ collection: "posts" })
export class Post extends Timestamped(Versioned(Entity)) {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => Number)
  views?: number;

  @Prop(() => [String])
  tags!: string[];
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
```

Класс описывает документ в той форме, в какой его создавал Mongoose. Пустой массив для `tags` объявлять не нужно. Поле-массив без `default` и без `required` в Typemo, как и в Mongoose, начинается с `[]`. Документ, прочитанный из базы без этого ключа, тоже отдаст `[]`. Так что код с `post.tags.length` продолжит работать и на старых документах, и на новых.

Если у документов Mongoose свой тип `_id` (строка-код, число, `UUID`), не объявляйте `_id` в классе вручную. Базовый класс [`EntityWithId`](../reference/schemas/base-classes.mdx#entity-with-id) задаёт его тип одной строкой.

```ts twoslash title="countries/country.ts"
import { EntityWithId, Prop, Schema, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
// ---cut---
@Schema({ collection: "countries" })
export class Country extends EntityWithId(() => String) {
  @Prop(() => String, { required: true })
  name!: string;
}

const Countries = client.db().model(Country);
const france = await Countries.findById("FR").orFail().lean();
console.log(france._id);
// → FR
```

`_id` из `EntityWithId` неизменяем, а при `create` без `default` обязателен, иначе будет `Validation failed: "_id": the field is required [required]`. `findById`, ссылки и `populate` на такой модели работают со строкой. Подробнее, в том числе про `UUID` и числовой счётчик, — в руководстве [Задать свой тип _id](../schemas/custom-ids.mdx).

Поля, которые есть в базе, но не описаны в классе (скажем, старое `legacy`), Typemo при чтении и сохранении документа не трогает, они остаются в базе. Строже он только с поддокументами, об этом — [`UnknownFieldsError`](../reference/errors/data-errors.mdx#unknown-fields-error).

</Step>
<Step>

### Не создавайте индексы вслепую [#no-blind-indexes]

При старте Typemo индексы не создаёт, а [`syncIndexes`](../reference/collections/model-indexes.mdx#model.sync-indexes) удаляет те, которых нет в классе. Если Mongoose или DBA завели в коллекции индексы, о которых класс не знает, синхронизация их снесёт. Поэтому сначала посмотрите план.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
// ---cut---
const plan = await Posts.syncIndexes({ dryRun: true });
console.log(plan.toDrop, plan.dryRun);
// → ["legacy_1"] true
```

В коллекции был индекс `legacy_1`, которого нет в классе. `dryRun` показал, что его удалили бы, и ничего не изменил. Перенесите такие индексы в класс декораторами [`@Index`](../reference/schemas/index-decorators.mdx#index) или опциями [`@Prop`](../reference/schemas/prop.mdx#index), и только потом запускайте синхронизацию по-настоящему.

</Step>
<Step>

### Замените плагины политиками [#replace-plugins-with-policies]

Если в Mongoose вы ограничивали данные организации плагином или хуком, в Typemo для этого есть политика схемы. Её поле помечается декоратором [`@Tenant()`](../reference/schemas/field-markers.mdx#tenant) рядом с `@Prop`. Без пометки схема с опцией `tenant` не соберётся — `ConfigurationError: Order: the tenant field "tenantId" must be marked @Tenant() (declare it @Prop(...) @Tenant() tenantId!: TenantField<T>)`. Мягкое удаление и аудит включаются опциями `softDelete` и `audit`, а не плагинами.

```ts twoslash title="orders/order.ts"
import { Entity, Prop, Schema, Tenant, type TenantField } from "@venloc/typemo";

@Schema({ collection: "orders", tenant: true })
export class Order extends Entity {
  @Prop(() => String)
  @Tenant()
  tenantId!: TenantField<string>;

  @Prop(() => String, { required: true })
  number!: string;
}
```

Пока с коллекцией работают обе библиотеки, помните, что политика тенанта действует только на запросах Typemo. Запросы Mongoose её не видят. Поэтому не переводите на тенанта часть кода одной коллекции, переносите её целиком. Подробнее — в разделе о двух библиотеках ниже. Как открыть область тенанта на время запроса, показано в руководстве [Разделить данные организаций](../policies/tenants.mdx) и в рецепте [Многотенантное приложение](../recipes/multi-tenant.mdx).

</Step>
<Step>

### Переключайте чтение, потом запись [#switch-reads-then-writes]

Начните с чтения. Оно не меняет данные, а различия видны сразу — неизвестное поле в фильтре, `undefined`, строка вместо числа. Затем переведите записи модели — `create`, `updateOne`, `findOneAndUpdate`. Без нужды не меняйте одну коллекцию из обеих библиотек в одном сценарии, потому что хуки и плагины одной не срабатывают на записях другой (об этом ниже).

Замену для каждого метода ищите в [Соответствии API](../reference/migration/api-mapping.mdx), различия в поведении с причинами — в [Отличиях в поведении](./behavior-differences.mdx). То, чего нет совсем, собрано в [Чего нет в Typemo](./missing-features.mdx).

</Step>
<Step>

### Уберите Mongoose из коллекции [#remove-mongoose-from-collection]

Когда все обращения к коллекции идут через Typemo, удалите модель и схему Mongoose. А когда переведена последняя модель, удалите пакет `mongoose` и глобальное подключение.

</Step>
</Steps>

## Как жить с двумя библиотеками одновременно [#side-by-side]

Пока переход не закончен, у коллекции два хозяина, и правила каждого действуют только внутри своей библиотеки.

**Политики не общие.** Тенант, мягкое удаление и аудит работают только на операциях Typemo. Запрос Mongoose к той же коллекции о них не знает и вернёт чужие данные или удалённые документы. Поэтому коллекцию с политиками переносите целиком, а не по методам.

**Хуки и плагины не общие.** `pre("save")` из Mongoose не срабатывает на записи Typemo, и наоборот. Если хук поддерживает инвариант, например нормализует адрес, на время переноса пишите через одну библиотеку. Или продублируйте хук в классе Typemo декоратором [`@Pre`](../reference/hooks/pre-post.mdx#pre).

**Проверки значений тоже разные.** Mongoose при записи приведёт `"42"` к числу, а Typemo откажет. Mongoose пишет данные по своей схеме, Typemo — по классу. Если схемы разошлись, читающая сторона получит то, что лежит в базе. Typemo при чтении значения не проверяет, к типу схемы их приводит только Mongoose.

**Транзакции между библиотеками не переносятся.** Сессия Mongoose и транзакция [`client.transaction`](../reference/connection/typemo-client.mdx#client.transaction) друг о друге не знают. Записи одной транзакции делайте одной библиотекой.

## Как выбрать, с какой коллекции начать [#how-to-choose]

Спросите себя, что будет, если эта коллекция станет вести себя строже. Начните с простой схемы, где мало хуков, нет `Mixed`, а данные под вашим контролем. Первые ошибки строгости покажут, где приложение полагалось на молчаливое приведение. Коллекции с плагинами, дискриминаторами и `Mixed` переносите последними — для них нужны новые решения, а не просто замена метода.

## Когда переносить не нужно [#when-not-to-use]

Если приложение стабильно работает, схема почти не меняется и тип документа вас не беспокоит, перенос не окупится. Вы заплатите временем за строгость, которая вам не нужна. И не трогайте то, что зависит от `Mixed` и `strict: false`, пока не решите, как описывать такие данные. Подробнее о цене — в [Зачем переходить](./why.mdx).

## Если что-то пошло не так [#troubleshooting]

**После синхронизации пропал индекс.** `syncIndexes` привёл индексы точно к классу и удалил лишние. Восстановите индекс, объявите его в классе и повторите `syncIndexes`. В следующий раз запускайте с `dryRun: true`.

**`ConfigurationError` про тенанта при создании модели.** Схема с опцией `tenant` не знает, какое поле заполнять. Добавьте `@Tenant()` рядом с `@Prop` на поле типа `TenantField<T>`, как в шаге про политики.

**`create` отвергает документ без `_id`.** Модель на `EntityWithId` без `default` требует идентификатор — `Validation failed: "_id": the field is required [required]`. В Mongoose такой документ без `_id` тоже не сохранялся (`MongooseError: document must have an _id before saving`). Передайте `_id` или задайте фабрику в `default`, как описано в [Свой тип _id](../schemas/custom-ids.mdx).

**Ошибка при сохранении документа, созданного Mongoose.** В поддокументе есть поле, которого нет в классе. Typemo не стирает его молча и бросает [`UnknownFieldsError`](../reference/errors/data-errors.mdx#unknown-fields-error). Добавьте поле в класс или осознанно согласитесь его потерять, как описано в [Неизвестных полях](../documents/unknown-fields.mdx).
