Там, где Mongoose молча делает что-то своё, Typemo отвечает ошибкой. Mongoose приводит строку к числу, отбрасывает неизвестное поле, превращает `undefined` в `null`, пропускает пустое обновление. Все эти различия растут из одного решения — **строгость по умолчанию**, и без выключателя. У Mongoose выключатель есть почти на каждый случай (`strict`, `strictQuery`, `runValidators`, `sanitizeFilter`), у Typemo его нет.

Эта страница пригодится, если вы перенесли код и что-то стало вести себя иначе. Или если хотите заранее понять, что сломается. Сначала разберём то, что Typemo делает так же, как Mongoose, хотя вы могли ждать иного, — такой код переносится без правок. Потом то, где Typemo строже, по темам и с причиной у каждой. Таблица «метод и его аналог» лежит в [Соответствии API](../reference/migration/api-mapping.mdx), а то, чего в Typemo нет совсем, — в руководстве [Чего нет в Typemo](./missing-features.mdx).

## Что понадобится

Примеры построены на блоге, и модель поста растёт по ходу страницы. `Posts` — модель Typemo, `MPost` — модель Mongoose 9.10.2 над теми же данными. Результаты и тексты ошибок получены на настоящей MongoDB с обеими библиотеками.

## Быстрый путь

Вот три различия, о которые спотыкаются первыми. Числовая строка больше не становится числом, обновление без операторов не работает, а `findOneAndUpdate` возвращает уже изменённый документ.

<Compare>

```ts
await MPost.create({ title: "Hello", views: "42" }); // views: 42
await MPost.updateOne({ title: "Hello" }, { views: 10 }); // обёрнуто в $set
const post = await MPost.findOneAndUpdate({ title: "Hello" }, { $inc: { views: 1 } });
// post.views → значение до изменения
```

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number) views?: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
// ---cut---
await Posts.create({ title: "Hello", views: 42 });
await Posts.updateOne({ title: "Hello" }, { $set: { views: 10 } });
const post = await Posts.findOneAndUpdate({ title: "Hello" }, { $inc: { views: 1 } });
console.log(post?.views);
// → 11
```

</Compare>

Ниже разберём каждое различие отдельно.

## Что теперь совпадает с Mongoose

Есть два поведения, на которых перенесённый код спотыкался бы зря. В Typemo они такие же, как в Mongoose, и в коде ничего править не нужно.

**Массив по умолчанию пустой.** Поле-массив без `default` и без `required` при создании документа получает `[]`. Mongoose поступает так же, поэтому код, который читает `post.tags.length` у нового документа, продолжает работать. Typemo подставляет `[]` и там, где вы этого не видите, — у нового поддокумента и при вставке через `upsert`. Если в базе у документа нет ключа массива, при чтении документа тоже будет `[]`, и следующий `$save` его запишет. А [`lean`](../reference/query/reading.mdx#lean) отдаёт документ как он хранится. У поля с `required: true` умолчания нет.

<Compare>

```ts
const post = await MPost.create({ title: "a" });
console.log(post.tags);
// → []
```

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => [String]) tags!: string[];
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
// ---cut---
const post = await Posts.create({ title: "a" });
console.log(post.tags);
// → []
```

</Compare>

Помечать поле `Defaulted` при этом не нужно, и в `create` массив необязателен, тип поля — просто `string[]`. При чтении документа вы получите не `string[]`, а [`StrictArray`](../reference/documents/typed-collections.mdx#strictarray), который меняется только своими методами. Результаты `.lean()` и `.plain()` отдают обычный массив.

**Имя ключа дискриминатора меняется опцией.** В Mongoose ключ по умолчанию называется `__t`, а `discriminatorKey` в опциях схемы задаёт другое имя. В Typemo так же — опция называется `discriminatorKey`, и значение пишется в документ под этим именем. Разница одна. Класс объявляет ключ типом, чтобы его видел компилятор, — `declare readonly kind?: Discriminators<…>`. Целиком устройство иерархии описано в руководстве [Наследование и дискриминаторы](../schemas/discriminators.mdx#базовая-модель-знает-наследников).

<Compare>

```ts
const Base = mongoose.model("Base", new Schema({ amount: Number }, { discriminatorKey: "kind" }));
const Card = Base.discriminator("Card", new Schema({ last4: String }));
await Card.create({ amount: 1, last4: "1" });
// в базе: { amount: 1, last4: "1", kind: "Card" }
```

```ts twoslash
import { Discriminator, Entity, Prop, Schema, TypemoClient, type Discriminators, type DiscriminatorValue } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
// ---cut---
@Schema({ collection: "payments", discriminatorKey: "kind", discriminators: () => [CardPayment] })
class Payment extends Entity {
  declare readonly kind?: Discriminators<CardPayment>;
  @Prop(() => Number, { required: true }) amount!: number;
}

@Discriminator("card")
class CardPayment extends Payment {
  declare readonly kind: DiscriminatorValue<"card">;
  @Prop(() => String, { required: true }) last4!: string;
}

const card = await client.db().model(CardPayment).create({ amount: 1, last4: "1" });
// в базе: { amount: 1, last4: "1", kind: "card" }
```

</Compare>

Во всём остальном Typemo строже. Об этом дальше.

## Строка больше не превращается в число

Скажем, данные приходят из формы или из параметров адреса, и в них `"42"` вместо `42`. Mongoose приведёт значение к типу поля и промолчит, что оно было другим. Typemo принимает только значение нужного типа.

<Compare>

```ts
const post = await MPost.create({ title: "Hello", views: "42" });
console.log(post.views);
// → 42
```

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number) views?: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
// ---cut---
// @errors: 2769
await Posts.create({ title: "Hello", views: "42" });
// компилятор: No overload matches this call (Type 'string' is not assignable to type 'number')
// во время работы: Cast to number failed at path "views" for "42" (string): expected a number [type]
```

</Compare>

У приведения в Mongoose много неочевидных правил. `" "` становится `0`, `"0x10"` — `16`, `true` — `1`, пустая строка в поле-числе — `null`, а даты зависят от часового пояса сервера. Каждое правило работает, пока данные приходят такими, как вы ждали. Когда приходят другие, ошибка тихо превращается в неверное значение. Typemo принимает `number`, а всё остальное отклоняет с [`CastError`](../reference/errors/data-errors.mdx#casterror) и причиной `type`.

У правила три осознанных исключения, потому что у этих типов есть каноническая строковая форма.

- Строку с идентификатором `ObjectId` или `UUID` Typemo принимает везде — в создании, обновлениях, фильтрах и [`findById`](../reference/query/reading.mdx#modelfindbyid).
- Строку с целым числом он принимает для `int64` (`BigInt`), а строку с десятичным числом — для `Decimal128`.
- Календарную дату `YYYY-MM-DD` и полную дату ISO 8601 с часовым поясом он принимает для `Date`.

Всё остальное, включая `null` в поле без `nullable`, — ошибка.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number) views?: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
// ---cut---
try {
  await Posts.create({ title: "Hello", views: null as unknown as number });
} catch (error) {
  console.log((error as Error).message);
}
// → Cast to number failed at path "views" for null: null is not allowed on a path that is not nullable [null]
```

Mongoose записал бы здесь `null` в любое необязательное поле. Чтобы поле могло быть `null`, объявите его [`nullable`](../reference/schemas/prop.mdx#nullable). Тогда `null` и отсутствие поля станут двумя разными состояниями, и тип их различит.

## Неизвестное не отбрасывается

Возьмём опечатку в имени поля. Mongoose с настройками по умолчанию (`strict: true`, `strictQuery: false`) реагирует на неё по-разному в зависимости от места, но ошибки не бросает нигде.

<Compare>

```ts
await MPost.create({ title: "d", extra: 1 });
// extra молча выброшен

const posts = await MPost.find({ nope: 1 });
// фильтр отправлен как есть: posts.length → 0
```

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
// ---cut---
// @errors: 2769
await Posts.create({ title: "d", extra: 1 });
// компилятор: No overload matches this call (Object literal may only specify known properties, and 'extra' does not exist in type 'CreateInput<Post>')
// во время работы: Cast to Post failed at path "extra" for 1 (number): not a field of Post [unknown-key]
```

</Compare>

Молчание опасно тем, что выглядит как успех. Поле `extra` не сохранилось, и вы узнаете об этом, только когда не найдёте его в базе. Фильтр с опечаткой `nope` ничего не нашёл, и это тоже похоже на обычное «ничего нет».

В Typemo опечатку в поле останавливает компилятор. А если значение пришло из JavaScript без типов, ошибка будет во время работы. Неизвестное поле в фильтре даст [`StrictModeError`](../reference/errors/data-errors.mdx#strictmodeerror) с причиной `unknown-path`, неизвестный ключ в создаваемом документе — `CastError` с причиной `unknown-key`, а неизвестный путь в обновлении — `StrictModeError` ещё до отправки в базу.

С данными, которые уже лежат в базе, правило работает в обратную сторону. Поле, которого нет в классе, при чтении и сохранении верхнего уровня остаётся в документе нетронутым. С поддокументами Typemo строже. Если перезапись поддокумента стёрла бы неизвестное поле, вместо тихой потери будет [`UnknownFieldsError`](../reference/errors/data-errors.mdx#unknownfieldserror). Как это выглядит на практике и как осознанно согласиться на потерю, рассказано в руководстве [Неизвестные поля](../documents/unknown-fields.mdx).

## `undefined` — не значение

В JavaScript `undefined` и «поля нет» — почти одно и то же, а в базе `undefined` записывается как `null`. Mongoose в фильтре превращает `undefined` в `null`, и запрос `find({ views: undefined })` ищет документы, где `views` равно `null` или поля нет. Если значение пришло из необязательного параметра запроса, вы получите не «всё» и не ошибку, а не тот срез, который имели в виду.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number) views?: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
const maybeViews = undefined as number | undefined;
// ---cut---
// @errors: 2379
try {
  await Posts.find({ views: maybeViews });
} catch (error) {
  console.log((error as Error).message);
}
// компилятор: Type 'undefined' is not assignable to type 'number | ScalarOperators<number, never>'
// во время работы (значение пришло из JavaScript без типов): filter: undefined at "views" (use $exists: false / $unset; undefined is never a value)
```

Typemo бросает [`QueryError`](../reference/errors/query-errors.mdx#queryerror) и подсказывает, что писать вместо `undefined`. Для «поля нет» есть [`$exists: false`](../reference/query/filter-operators.mdx#exists), а для удаления поля — [`$unset`](../reference/writes/update-operators.mdx#unset). В обновлениях работает тот же принцип — `undefined` там не пропускается и не пишется как `null`.

## Значение, которое не приводится, — всегда CastError

Допустим, поле получило значение не того типа, например `doc.views = "abc"`. Mongoose запоминает ошибку приведения в документе и сообщает о ней при проверке вместе со всеми остальными, внутри `ValidationError`. Для схемы с обязательным `title` конструктор `new MPost({ views: "abc" })` без `title` дал одну `ValidationError` с двумя записями — `views` (`CastError`) и `title` (`required`).

Typemo строже. Значение, которое не приводится, — это всегда [`CastError`](../reference/errors/data-errors.mdx#casterror), одна на поле, и ограничения этого поля (`min`, `enum`) после неё не проверяются, проверять уже нечего. Когда придёт ошибка, зависит от того, как значение попало в документ. Методы, которые принимают значение (`create`, `Model.new`, `$set`, методы массивов, операторы обновления), приводят его сразу. Простое присваивание `doc.views = …` приводится на ближайшем [`$validate()`](../reference/documents/document-api.mdx#validate) или `$save()`. `CastError` приходит раньше любой проверки значений, и в базу ничего не уходит.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { min: 10 }) views?: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
// ---cut---
const post = Posts.new({ title: "t" });
// @errors: 2322
post.views = "abc";
// компилятор: Type 'string' is not assignable to type 'number'
// во время работы (значение пришло без типов), на $validate() или $save():
//   CastError: Cast to number failed at path "views" for "abc" (string): expected a number [type]
```

Если в документе одновременно неверное значение и нет обязательного поля, `$validate()` назовёт только `CastError`. Проверка значений начинается, когда всё приведено. Это сознательная разница. Приведение отвечает на вопрос «того ли типа значение», а проверка — «подходит ли оно по правилам». Второй вопрос не имеет смысла, пока нет ответа на первый.

Исключение — места, где нужно собрать все проблемы разом. Это `Model.validate(input)` и интеграция Standard Schema для форм. Там приведение — одна из записей общего списка с причиной `cast`, а `CastError` лежит в `cause` этой записи — `Validation failed: "title": the field is required [required]; "views": Cast to number failed at path "views" for "abc" (string): expected a number [type] [cast]`.

## Пустое и «почти пустое» — ошибка

Бывает, что из-за ошибки в коде в обновление или удаление попадает пустое условие или пустое изменение. Mongoose терпит все варианты, в том числе пустой фильтр в формах `One`. `updateOne({}, …)` меняет первый попавшийся документ коллекции, `deleteOne({})` удаляет его, а `replaceOne({}, …)` заменяет.

<Compare>

```ts
await MPost.updateOne({ title: "a" }, {});
// → { acknowledged: false } — ничего не сделано

await MPost.updateOne({ title: "a" }, { views: 10 });
// обёрнуто в $set, документ изменён

await MPost.deleteMany({});
// удалены все документы коллекции

await MPost.deleteOne({});
// удалён первый попавшийся документ
```

```ts twoslash
import { Entity, Filters, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number) views?: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
// ---cut---
// пустое обновление: QueryError "update: an empty update changes nothing"
// обновление без оператора: QueryError
//   "update: \"views\" is not an update operator (write { $set: { … } })"
// пустой фильтр в любой из пяти записей (updateOne, updateMany, deleteOne, deleteMany, replaceOne):
// StrictModeError до отправки в базу, например
//   "deleteOne with an empty filter would change or remove an arbitrary document; pass a filter,
//    or Filters.all() to mean every document on purpose [empty-filter]"

// удалить все документы можно, но только намеренно:
await Posts.deleteMany(Filters.all());
```

</Compare>

Всё дело в цене ошибки. Одна опечатка превращает `deleteMany({ author: id })` в `deleteMany({ author: undefined })` или в `deleteMany({})`, и коллекции больше нет. Поэтому пустой фильтр в записи запрещён во всех пяти методах, включая формы `One`. `updateOne({})` и `deleteOne({})` затронули бы один документ, но какой — решала бы база, а автор кода имел в виду совсем не это.

Литерал `{}` в этих методах не компилируется (`an empty filter would change or remove an arbitrary document; pass a filter, or Filters.all() to mean every document on purpose`). Фильтр, собранный во время работы из переменной или ввода пользователя, отвергается при вызове. В пакете `bulkWrite` та же проверка действует для каждой операции. Если нужны все документы, скажите это отдельным словом — [`Filters.all`](../reference/policies/violations.mdx#filtersall). Подробности — в руководстве [Пустые фильтры](../writes/empty-filters.mdx).

Пустое обновление Typemo тоже считает ошибкой. Разумного результата у него нет, кроме «ничего не произошло», а это не должно выглядеть как успех.

## `findOneAndUpdate` возвращает документ после изменения

В Mongoose этот метод по умолчанию возвращает документ **до** изменения (`new: false`), а за новым надо просить `new: true` или `returnDocument: "after"`. Это одна из главных причин переносить код внимательно. Без правки код продолжит работать, но начнёт читать другое значение.

<Compare>

```ts
const before = await MPost.findOneAndUpdate({ title: "a" }, { $inc: { views: 1 } });
// before.views → 1 (значение до)
const after = await MPost.findOneAndUpdate(
  { title: "a" }, { $inc: { views: 1 } }, { new: true },
);
```

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number) views?: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
// ---cut---
const after = await Posts.findOneAndUpdate({ title: "a" }, { $inc: { views: 1 } });
const before = await Posts.findOneAndUpdate(
  { title: "a" },
  { $inc: { views: 1 } },
  { returnDocument: "before" },
);
```

</Compare>

Обычно вы хотите увидеть результат своей записи, поэтому в Typemo это поведение по умолчанию. Опций `new` и `returnOriginal` нет. `returnDocument` принимает `"before"` и `"after"`, и другого способа сказать то же самое нет. Подробнее — в справочнике [`findOneAndUpdate`](../reference/writes/writes.mdx#findoneandupdate).

## Запрос выполняется один раз

Mongoose разрешает собрать запрос, но повторно выполнить его нельзя. Второй `await` бросает `Query was already executed: Post.find({ title: 'a' })`. Typemo с чтением мягче и предсказуемее — повторный `await` того же строителя вернёт тот же результат без нового похода в базу.

С записью правило другое и жёстче. Строитель записи выполняется один раз, потому что повторная запись — это повторный побочный эффект. Как читать и писать в цепочке, показывают справочник [`.exec`](../reference/query/reading.mdx#exec) и раздел [«Одно выполнение на строитель»](../reference/writes/writes.mdx#одно-выполнение-на-строитель).

## Массивы, документы и связи ведут себя как значения

Представьте код, который работает с массивами внутри документа так, как принято в JavaScript.

Первое различие — в том, как менять массив. В Mongoose `post.tags[0] = "x"` отслеживается, а `post.tags.length = 0` и `delete post.tags[0]` — нет, и изменение пропадает без единого сообщения. В Typemo массив документа — это [`StrictArray`](../reference/documents/typed-collections.mdx#strictarray). Запись по индексу и в `length` не компилируется, а заменяют элементы методы [`set`](../reference/documents/typed-collections.mdx#strictarrayset), [`clear`](../reference/documents/typed-collections.mdx#strictarrayclear), [`splice`](../reference/documents/typed-collections.mdx#strictarraysplice) и [`replace`](../reference/documents/typed-collections.mdx#strictarrayreplace). `set(i, v)` меняет только существующую позицию. Дописать за границей массива, как в Mongoose, нельзя, для этого есть `push`.

Второе — заполненные связи. В Mongoose заполненный массив можно менять на месте, и `push(id)` превращает его обратно в массив идентификаторов. В Typemo заполненный массив и карта доступны только для чтения, а ссылки меняются через сами идентификаторы. После `push` в Mongoose нельзя предсказать, что уйдёт в базу при сохранении, документы или идентификаторы. Подробнее — в руководстве [Заполненные связи в документе](../populate/document-populate.mdx).

## Пакетная запись сообщает о каждой ошибке

Возьмём `insertMany` с тремя документами, один из которых невалиден.

<Compare>

```ts
const saved = await MPost.insertMany(
  [{ title: "e" }, { views: 5 }, { title: "f" }],
  { ordered: false },
);
// saved.length → 2, промис выполнен, ошибок нет
```

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number) views?: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Posts = client.db().model(Post);
// ---cut---
try {
  await Posts.insertMany(
    [{ title: "e" }, { views: 5 } as unknown as { title: string }, { title: "f" }],
    { ordered: false },
  );
} catch (error) {
  console.log((error as Error).message);
}
// → Post.insertMany: 1 write(s) failed (first at index 1: Validation failed: "title": the field is required [required])
```

</Compare>

Mongoose вставит валидные документы, а невалидный молча пропустит. Вы получите массив из двух, и куда делся третий, программа не скажет. Typemo вставит те же валидные документы, но закончит операцию с [`BulkWriteError`](../reference/errors/server-errors.mdx#bulkwriteerror). Для каждого сбоя в ней есть индекс во входном массиве, код и исходная ошибка, так что вы точно знаете, что вставлено, а что нет. Тот же класс ошибки приходит из [`bulkWrite`](../reference/writes/writes.mdx#bulkwrite), а сообщение сервера сохраняется в `cause`.

Отдельно о [`create`](../reference/writes/writes.mdx#create) со списком. В Mongoose он сохранял документы параллельно и внутри транзакции требовал `ordered: true`. Typemo вставляет список одним упорядоченным `insertMany` и никогда не параллельно, поэтому такой опции у него нет.

## Пакет `bulkWrite` проверяет и вызывает хуки каждой операции

Скажем, импорт идёт через `bulkWrite` с `upsert`. В Mongoose этот метод проверял схемой только `insertOne` и `replaceOne`. Значения в `updateOne` уходили в базу без проверки, а хуки отдельных операций не вызывались, работали только `pre("bulkWrite")` и `post("bulkWrite")` самого пакета. Пакет с `updateOne`, `upsert: true` и ценой `-1` при `min: 0` записал документ с отрицательной ценой, а вставку без обязательного поля создал без ошибок. Хук `pre("updateOne")` не вызвался ни разу.

В Typemo каждая операция пакета ведёт себя как её одиночный аналог. Значения `$set` проверяются, а `upsert` проверяет ещё и обязательные поля вставляемого документа. `insertOne` запускает хуки документа, остальные операции — хуки `query.updateOne`, `query.deleteMany` и так далее. Номер операции хук узнаёт из `this.bulkIndex`.

```ts twoslash
import { Entity, Pre, Prop, Schema, TypemoClient, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "products" })
class Product extends Entity {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true, min: 0 }) price!: number;

  @Pre("query.updateOne")
  count(this: OperationHookContext<Product, "query.updateOne">): void {
    console.log("pre updateOne", this.bulkIndex);
  }
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Products = client.db().model(Product);
// ---cut---
await Products.bulkWrite(
  [
    { updateOne: { filter: { sku: "a" }, update: { $set: { price: 1 } }, upsert: true } },
    { updateOne: { filter: { sku: "b" }, update: { $set: { price: -1 } }, upsert: true } },
  ],
  { ordered: false },
).catch((error) => console.log((error as Error).message));
// → pre updateOne 0
// → Product.bulkWrite: 1 write(s) failed (first at index 1: Validation failed: "price": must be at least 0 [min])
```

Первая операция записала документ, вторая отвергнута, и её номер назван в ошибке. Если хук операции бросает исключение, весь пакет в базу не уходит. Подробности и порядок вызова хуков — в руководстве [Пакетная запись](../writes/bulk.mdx#хуки-операций-внутри-bulkwrite).

## У хуков другой порядок и другой `this`

Возьмём логику при сохранении. В Mongoose `save` сначала проверяет значения, а потом вызывает `pre("save")`. Значит, то, что исправил ваш хук, уже не проверяется. В Typemo порядок обратный — сначала [`@Pre("document.save")`](../reference/hooks/pre-post.mdx#pre), затем проверка, затем запись. Всё, что изменил хук, проверяется так же строго, как ввод пользователя.

Второе различие — `this`. В хуках запроса Mongoose `this` — это сам `Query`, и хук может переписать условие, подменить настройки или подмешать стадию. Всё это происходило уже после проверки и в обход политик — тенанта, мягкого удаления, санитизации. В Typemo хук запроса получает контекст операции только для чтения. Менять операцию можно методом [`.modify`](../reference/hooks/operation-context.mdx#modify) и только в той форме, которую проверяют политики. Как это выглядит в коде, показывает руководство [Вмешаться в операцию](../hooks/operation-hooks.mdx).

В хуке документа `this` — это документ или поддокумент, если класс встроен в другую модель. Хук класса срабатывает в обоих случаях. Его тип — [`HookThis<"document.save", Post>`](../reference/hooks/pre-post.mdx#hookthis), то есть `HydratedDoc<Post> | Subdocument<Post>`. Методы `$isNew()` и `$isModified()` есть у обоих, а методы корня вроде `$getChanges()` и `$save()` доступны после проверки [`this.$isRoot()`](../reference/documents/document-api.mdx#isroot). Объявить `this: HydratedDoc<Post>` компилятор не даст, потому что такой тип пообещал бы методы корня и поддокументу, у которого их нет.

Третье — события хуков не задаются строками и регулярными выражениями. В Mongoose `pre("deleteOne")` мог означать и документ, и запрос в зависимости от опции, а `/^find/` ловил всё подряд. В Typemo у события всегда есть область — `document.save`, `query.find`, а их перечень явный, это [`HOOK_EVENTS`](../reference/hooks/pre-post.mdx#hook_events). Хук документа `deleteOne` не сработает на `deleteOne` запроса, и наоборот.

## Ключ дискриминатора нельзя изменить

Допустим, документ-карту хочется «превратить» в перевод, сменив ключ. В Mongoose результат зависит от того, как вы это делаете, и предсказать его трудно. Присваивание `doc.kind = "Transfer"` в сохранённом документе-наследнике даёт `ValidationError` с текстом про приведение ключа к строке, потому что дискриминатор `Card` не принимает чужое значение. Обновление `updateOne({ _id }, { $set: { kind: "Transfer" } })` молча ничего не делает — ответ `acknowledged: false`, документ не изменился. Сменить ключ можно только с опцией `overwriteDiscriminatorKey: true`, тогда обновление проходит.

В Typemo значение ключа неизменяемо без исключений, и выключателя нет. Присваивание не компилируется. Обновление и `$save` после присваивания отвергаются ещё до базы с `StrictModeError` и причиной `immutable`. Вид документа выбирается один раз при создании. Чтобы его сменить, создайте документ нужного вида и удалите прежний. Если у двух наследников совпало значение ключа, будет `ConfigurationError` уже при первом `model()`. Тексты ошибок и примеры — в справочнике [Значение ключа неизменяемо](../reference/schemas/discriminator.mdx#значение-ключа-неизменяемо).

## Тенант — часть схемы

В Mongoose мультитенантность строят сами — плагином, хуками `pre("find")` или условием в каждом запросе. Любой путь мимо хуков (агрегация, `lean`, драйвер) может вернуть чужие данные. В Typemo тенант — это политика схемы. Её включает опция `tenant`, а поле тенанта типа `TenantField<T>` обязательно помечается декоратором [`@Tenant()`](../reference/schemas/field-markers.mdx#tenant) рядом с `@Prop`.

```ts twoslash
import { Entity, PolicyContext, Prop, Schema, Tenant, type TenantField, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders", tenant: true })
class Order extends Entity {
  @Prop(() => String) @Tenant() tenantId!: TenantField<string>;
  @Prop(() => String, { required: true }) number!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "crm" });
const Orders = client.db().model(Order);
// ---cut---
const order = await PolicyContext.run({ tenant: "acme" }, () => Orders.create({ number: "A-1" }));
console.log(order.tenantId);
// → acme

await Orders.find().catch((error) => console.log((error as Error).message));
// → Order.find: Order is scoped by tenant ("tenantId") and the operation has no tenant; run it inside PolicyContext.run({ tenant }, …) or add .policy({ tenant }) to the query (cross-tenant work: .policy({ allTenants: true })) [tenant]
```

Строже здесь сразу в нескольких местах.

- Схема с опцией `tenant` без пометки `@Tenant()` не собирается — `ConfigurationError: Order: the tenant field "tenantId" must be marked @Tenant() (declare it @Prop(...) @Tenant() tenantId!: TenantField<T>)`. То же будет с пометкой без опции или на двух полях.
- Операция без тенанта не возвращает всё подряд, а падает.
- Пустая строка в роли тенанта — тоже ошибка.
- Работа сразу по всем организациям записывается явно, `.policy({ allTenants: true })`.

Подробности — в руководстве [Разделить данные организаций](../policies/tenants.mdx#описать-поле-тенанта) и в рецепте [Многотенантное приложение](../recipes/multi-tenant.mdx).

## Ничего не создаётся неявно

Mongoose при создании модели сам создаёт коллекцию и индексы (`autoCreate`, `autoIndex`) и держит команды в очереди, пока нет подключения (`bufferCommands`). Ещё он добавляет каждому документу `_id`, а модели — виртуальное свойство `id`, метки времени и версию по вашей опции. Typemo ничего из этого сам не делает.

Коллекции и индексы создаёт ваша команда. Это [`connection.init()`](../reference/connection/connection.mdx#connectioninit) один раз при запуске сервиса или [`syncIndexes`](../reference/collections/model-indexes.mdx#modelsyncindexes) в шаге развёртывания. `syncIndexes` удаляет индексы, которых нет в классе. Поэтому перед первым запуском на коллекции, которой раньше занимался Mongoose, посмотрите план — `syncIndexes({ dryRun: true })` ничего не пишет. Операция до подключения в очередь не встаёт. Она ждёт готовности клиента внутри, а по истечении времени бросает ошибку ([`client.ready`](../reference/connection/typemo-client.mdx#clientready)).

Если синхронизация не может привести коллекцию к схеме, Typemo об этом скажет. В такой ситуации `Model.init()` и `createCollection()` в Mongoose молча пропускают коллекцию. Если коллекция уже существует без опции `capped`, схема с `capped` её не меняет, и ошибки нет — `isCapped()` вернул `false`. А при `autoCreate: false` коллекция с `capped` или `collation` просто не создаётся (это ошибки gh-8566 и gh-8814 в тестах Mongoose). Приложение стартует с коллекцией не той формы и узнаёт об этом по последствиям.

В Typemo [`connection.init()`](../reference/connection/connection.mdx#connectioninit) и `syncAll()` выполняют все шаги, а потом бросают одну [`SyncError`](../reference/errors/configuration-errors.mdx#syncerror). В ней все сбои перечислены в `failures`, а исходные ошибки лежат в `cause`. На коллекции `logs`, созданной без `capped`, при схеме с `capped: { size: 100_000 }` получится `SyncError: connection.init() of "app": 1 failure(s) — collection "logs": exists with options MongoDB cannot change (capped): drop the collection and create it again`.

Служебные поля тоже явные. `_id` даёт базовый класс [`Entity`](../reference/schemas/base-classes.mdx#entity), метки времени — [`Timestamped`](../reference/schemas/base-classes.mdx#timestamped), версию `__v` — [`Versioned`](../reference/schemas/base-classes.mdx#versioned). Виртуального `id` нет. Идентификатор — это `_id`, и в результате `.plain()` и в JSON он уже строка.

## Чтение из базы не проверяет данные

Здесь различие в обратную сторону. При записи Typemo строже Mongoose, а при чтении не проверяет, что лежит в базе. Mongoose приводит прочитанное значение к типу схемы, и строка `"5"` в поле `views` превратится в `5`. Typemo отдаёт то, что хранится.

Если в поле `views` лежит строка `"5"`, [`findById`](../reference/query/reading.mdx#modelfindbyid) вернёт `views: "5"`, хотя тип обещает число. Typemo нарочно читает данные как есть, чтобы превращение в документ не становилось ещё одной проверкой. Пока коллекцию писал Mongoose, в поле лежит то, к чему схема привела значение при записи, и расхождений нет. Они появляются, когда в коллекцию пишет кто-то, кто схему не соблюдал. Если такое возможно, проверяйте результат во время работы методом [`.parse`](../reference/query/contracts.mdx#parse), как в руководстве [Проверить данные из базы во время работы](../queries/contracts.mdx#проверить-данные-из-базы-во-время-работы).

## Если что-то пошло не так

**После переезда тесты падают на строках вместо чисел.** Тесты и обработчики передавали `"42"` и получали `42`, а теперь получают `CastError` с причиной `type`. Приводите значение на границе приложения, а не в модели. Разберите параметр запроса при чтении и передавайте число.

**`findOneAndUpdate` вернул уже новое значение.** Код считал разницу между старым и новым значением по результату `findOneAndUpdate`. Теперь там новое значение. Если старое действительно нужно, добавьте `{ returnDocument: "before" }`.

**Фильтр с опечаткой теперь падает.** Раньше он молча находил ноль документов. Это не регресс, а найденная ошибка, так что поправьте имя поля. Если запрос строится из JavaScript без типов, ошибку даст [`StrictModeError`](../reference/errors/data-errors.mdx#strictmodeerror) с причиной `unknown-path`.

**`updateOne({})` и `deleteOne({})` в тестах и скриптах.** Скрипты и тесты на Mongoose часто чистят коллекцию через `deleteOne({})` в цикле или обновляют «любой документ» через `updateOne({}, …)`. Теперь это `StrictModeError`. Назовите документ условием (`{ _id }`, `{ title }`) или, если нужен действительно любой, прочитайте его и обновите по `_id`. Для всех документов есть [`Filters.all()`](../reference/policies/violations.mdx#filtersall).

**`init()` падает на старте с `SyncError`.** Раньше Mongoose молча запускался на коллекции не той формы. `SyncError` называет каждую коллекцию и причину — расхождение опций, которые сервер не меняет (например, `capped`), или конфликт индексов. Исправьте коллекцию, пересоздав её или приведя схему в соответствие, а не ловите ошибку.

**Схема тенанта не собирается.** Вы видите `ConfigurationError: …must be marked @Tenant()`. Пометьте поле типа `TenantField<T>` декоратором, как в разделе о тенантах выше.

**Пустой `updateOne` больше не «ничего не делает».** Код обновлял документ изменением, которое иногда приходило пустым. Теперь это [`QueryError`](../reference/errors/query-errors.mdx#queryerror). Проверяйте изменение до вызова. Пустое обновление значит, что вы сами не знали, что хотели изменить.
