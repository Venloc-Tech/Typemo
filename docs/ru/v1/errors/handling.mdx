Ошибки Typemo нужно ловить по классу, а не по тексту: у каждой ситуации свой класс, а его поля говорят, что именно произошло. Такая ошибка приходит быстро и по делу: библиотека не глотает опечатку в имени поля и не превращает неверное значение в пустое, а останавливает операцию понятным отказом. Задача обработчика на границе приложения — превратить отказ в правильный ответ клиенту: «нет такого счёта» в 404, «имя уже занято» в 409, «форма заполнена неверно» в 422.

Эта страница показывает, как это сделать. Если вы хотите увидеть каждый класс отдельно, с полями и точными текстами, откройте [справочник ошибок](../reference/errors/index.mdx).

## Что предполагается

Примеры используют подключённый клиент из файла `db/client.ts` и модель счёта из `accounts/account.ts`.

```ts twoslash title="db/client.ts"
import { TypemoClient } from "@venloc/typemo";

export const client = await TypemoClient.connect("mongodb://localhost:27017/app");
```

```ts twoslash title="accounts/account.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;
}
```

Класс ответа вашего приложения (404, 409) в примерах помечен `__NotFound__`: это ваш код, а не часть Typemo.

## Быстрый путь

Все ошибки Typemo — потомки [`TypemoError`](../reference/errors/hierarchy.mdx#typemoerror). Поэтому один `instanceof` отделяет отказ библиотеки от чужого сбоя, а проверка по конкретному классу выбирает реакцию:

```ts twoslash
import { DocumentNotFoundError, DuplicateKeyError, Entity, Prop, Schema, TypemoClient, TypemoError } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
await client.connection.init();
// ---cut---
try {
  await Accounts.findOne({ title: "no such account" }).orFail();
} catch (error) {
  if (error instanceof DocumentNotFoundError) console.log("not found");
  // → "not found"
  else if (error instanceof DuplicateKeyError) console.log("already exists");
  else if (error instanceof TypemoError) console.log(error.message);
  else throw error;
}
```

Последняя ветка `throw error` возвращает наверх всё, что не принадлежит библиотеке: чужую ошибку не нужно прятать. Остальная страница разбирает типичные задачи: как отдать ошибку клиенту, как отличить повторяемую ошибку, как не выдать секрет.

## Ловить по классу

Классы образуют дерево, поэтому порядок проверок важен: от частного к общему. [`DuplicateKeyError`](../reference/errors/server-errors.mdx#duplicatekeyerror), [`ServerValidationError`](../reference/errors/server-errors.mdx#servervalidationerror) и [`WriteConflictError`](../reference/errors/server-errors.mdx#writeconflicterror) — потомки [`ServerError`](../reference/errors/server-errors.mdx#servererror), а [`KeysetTokenError`](../reference/errors/query-errors.mdx#keysettokenerror) — потомок [`QueryError`](../reference/errors/query-errors.mdx#queryerror). Проверка по родителю поставленная первой перехватила бы потомка, и ветка потомка никогда не выполнилась бы.

Правильный порядок: сначала конкретный класс, потом его родитель, в конце общий [`TypemoError`](../reference/errors/hierarchy.mdx#typemoerror). Дерево целиком — в разделе [Иерархия ошибок](../reference/errors/hierarchy.mdx).

Сравнивать `error.name` со строкой не нужно: `instanceof` учитывает наследование, а имя нет. Не разбирайте и `error.message`: текст читается человеком и может уточняться, а решения принимаются по классу и полям (`reason`, `code`, `path`).

## Ответить клиенту кодом HTTP

На границе приложения (обработчик запроса, точка входа сервиса) все ошибки превращаются в ответ клиенту. Удобно сделать это один раз в общей функции и вызывать её из всех обработчиков: тогда у ответов один вид, а решения о кодах лежат в одном месте.

Отображение ситуаций в коды не задано библиотекой, его определяет ваше приложение. Вот разумная схема: неверный ввод даёт 400 и 422, отсутствие документа 404, конфликт с существующими данными 409, недоступность базы 503. Остальное — 500 с общим текстом, без подробностей.

```ts twoslash title="errors/to-http.ts"
import {
  CastError,
  ConnectionError,
  DocumentNotFoundError,
  DuplicateKeyError,
  QueryError,
  StrictModeError,
  TimeoutError,
  ValidationError,
  VersionError,
} from "@venloc/typemo";

export interface HttpAnswer {
  readonly status: number;
  readonly body: { readonly error: string; readonly details?: unknown };
}

export const toHttp = (error: unknown): HttpAnswer => {
  if (error instanceof ValidationError) {
    return { status: 422, body: { error: "validation", details: error.toJSON().issues } };
  }
  if (error instanceof DocumentNotFoundError) return { status: 404, body: { error: "not-found" } };
  if (error instanceof DuplicateKeyError) {
    return { status: 409, body: { error: "duplicate", details: Object.keys(error.keyPattern ?? {}) } };
  }
  if (error instanceof VersionError) return { status: 409, body: { error: "changed-meanwhile" } };
  if (error instanceof CastError || error instanceof StrictModeError || error instanceof QueryError) {
    return { status: 400, body: { error: "bad-request" } };
  }
  if (error instanceof TimeoutError || error instanceof ConnectionError) {
    return { status: 503, body: { error: "unavailable" } };
  }
  return { status: 500, body: { error: "internal" } };
};
```

Запуск на настоящих ошибках дал такие ответы: создание счёта без владельца — 422 с перечнем `[{ path: "owner", reason: "required", message: "the field is required" }]`; `findOne(...).orFail()` без результата — 404; создание с занятым названием — 409 с `details: ["title"]`; владелец числом — 400; фильтр с неизвестным полем — 400; испорченный токен страницы — 400; конфликт версий — 409; обычная `Error` из вашего кода — 500.

Тело ответа 422 берётся из [`error.toJSON()`](../reference/errors/data-errors.mdx#ответ-клиенту), а не из самой ошибки: `toJSON` опускает значения нарушений, а они могут оказаться большими или секретными. Для 409 достаточно имён полей из `keyPattern`; значение, которое уже занято, клиенту лучше не пересылать.

Ошибку вашего собственного кода (500) стоит записать в журнал целиком, а клиенту вернуть общий текст: подробности ошибки нужны разработчику, но не пользователю.

## Не показать лишнего

Тексты ошибок делаются подробными, чтобы разработчику хватало их для диагностики: в них есть имя модели, путь и значение. Поэтому сырое `error.message` не отдают клиенту: оно может выдать устройство схемы и данные. Отдавайте либо готовые поля (`toJSON`), либо собственный короткий текст.

Секретные поля защищены отдельно. Если в схеме у поля указано `sensitive`, его значение заменяется на `[hidden]` в ошибках уникальности и приведения, а не только в журнале аудита. В запуске поле `email` с `sensitive: "hide"` дало такой текст:

```text
DuplicateKeyError: duplicate key on email_1: { email: "[hidden]" } (code 11000 DuplicateKey)
```

`keyValue` у этой ошибки был `{ email: "[hidden]" }`, полный текст сервера в `serverMessage` замаскирован так же, а `cause` содержал ту же замаскированную копию: секрет не попадает ни в сообщение, ни в поля, ни в цепочку причин. Оригинал драйвера остаётся доступен только внутри библиотеки.

### Причина сбоя

Поле `cause` хранит ошибку, из-за которой возникла текущая: ошибку драйвера, ошибку вашей функции, ошибку приведения. Полезно записывать её в журнал вместе с ошибкой верхнего уровня: класс Typemo говорит, что произошло, а `cause` — почему.

```ts twoslash
import { TypemoError } from "@venloc/typemo";
declare const error: TypemoError;
declare const __logger__: { warn(message: string, fields: unknown): void };
// ---cut---
__logger__.warn(error.message, { name: error.name, cause: error.cause });
```

## Ошибки сервера

Отказы сервера разделены на классы по коду: нарушение уникальности, отказ валидатора коллекции, конфликт записей и общий [`ServerError`](../reference/errors/server-errors.mdx#servererror). Коды сервера, на которые реагирует библиотека, собраны в [`ServerErrorCodes`](../reference/errors/server-errors.mdx#servererrorcodes), чтобы вместо числа 11000 читалось `ServerErrorCodes.DuplicateKey`. Драйверную ошибку, из которой всё получилось, всегда можно достать из `cause`.

Общий `ServerError` бросается для любого кода без специального класса: например, при подсказке индекса, которого нет, пришёл `code: 2` и `codeName: "BadValue"`, а сообщение было таким: `hint provided does not correspond to an existing index (code 2 BadValue)`. Сообщение нарочно короткое: причина и код. Полный текст сервера (в нём бывают план запроса и значения) лежит в поле `serverMessage` и в `cause`: пишите его в журнал, но не отдавайте клиенту. Чаще всего такая ошибка означает ошибку вашего запроса, а не временный сбой, поэтому повторять его бессмысленно.

## Повторяемые ошибки

Сервер и драйвер прикрепляют к ошибкам **метки**: они подсказывают, что можно сделать. Самая важная для приложения — `TransientTransactionError` («транзакцию можно выполнить заново целиком»). Внутри [`connection.transaction`](../reference/transactions/transactions.mdx#transaction) повтор делает драйвер, вам ничего писать не нужно: в запуске функция транзакции при двух временных сбоях выполнилась трижды, и запись зафиксировалась. Читать метки самим нужно только при ручном управлении транзакцией.

```ts twoslash
import { ErrorLabels, ServerError } from "@venloc/typemo";
declare const error: ServerError;
// ---cut---
if (error.hasErrorLabel(ErrorLabels.TransientTransactionError)) {
  // всю транзакцию можно выполнить заново
}
```

Метки перечислены в справочнике [`ErrorLabels`](../reference/errors/server-errors.mdx#errorlabels). Ошибку без метки повторять вслепую нельзя: нарушение уникальности повторится с тем же результатом, а неидемпотентная запись при повторе выполнится дважды.

Чтобы не разбирать метки и коды самому, спросите [`ErrorClassifier`](../reference/errors/hierarchy.mdx#errorclassifier): `ErrorClassifier.isRetryable(error)` отвечает, поможет ли повтор той же операции, а `ErrorClassifier.isTransient(error)` — можно ли выполнить заново всю транзакцию. Классификатор принимает любое значение, в том числе ошибку драйвера, пришедшую мимо моделей, и для нарушения уникальности или ошибки приведения отвечает «нет»: повтор с теми же данными ничего не изменит.

## Пакетная запись

Пакет (`insertMany`, `bulkWrite`) не атомарен, поэтому при частичной неудаче приходит [`BulkWriteError`](../reference/errors/server-errors.mdx#bulkwriteerror): он говорит, какие записи не прошли (номер в вашем вводе, код, разобранная ошибка) и что записалось. Реакция зависит от задачи: сообщить пользователю, какие строки отвергнуты, и принять остальные, либо откатить всё.

```ts twoslash
import { BulkWriteError, DuplicateKeyError, Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
await client.connection.init();
await Accounts.create({ title: "Main", owner: "alice" });
// ---cut---
const rows = [
  { title: "N1", owner: "a" },
  { title: "Main", owner: "b" },
  { title: "N2", owner: "c" },
];

try {
  await Accounts.insertMany(rows, { ordered: false });
} catch (error) {
  if (error instanceof BulkWriteError) {
    const duplicates = error.writeErrors.filter((failure) => failure.error instanceof DuplicateKeyError);
    console.log(duplicates.map((failure) => failure.index), error.result.insertedCount);
    // → [1] 2
  }
}
```

Индексы в `writeErrors` считаются по вашему вводу, а не по внутреннему разбиению драйвера: строка с индексом 1 — это `rows[1]`. Без `ordered: false` пакет остановился бы на первой ошибке.

## Запись прошла, а хук упал

После успешной записи могут сработать [post-хуки](../hooks/order-and-errors.mdx): письмо, журнал, кеш. Если такой хук бросил ошибку, вызывающий код получает [`PostHookError`](../reference/errors/hierarchy.mdx#posthookerror), а не исходную ошибку хука. Так сделано для одного случая: `applied` у этой ошибки всегда `true`, и это значит «запись уже в базе». Повторить вызов, не заглянув в ошибку, значит записать документ второй раз.

```ts twoslash
import { Entity, Post, PostHookError, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;

  @Post("document.save")
  notify(this: Account): void {
    throw new Error("the hook failed");
  }
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
// ---cut---
try {
  await Accounts.create({ owner: "ann" });
} catch (error) {
  if (error instanceof PostHookError) console.log(error.applied, (error.cause as Error).message);
  // → true "the hook failed"
}
```

Что делать, решает приложение: чаще всего записать сбой хука в журнал и ответить клиенту успехом, потому что запись удалась. Внутри [транзакции](../transactions/transactions.mdx) оболочки нет: сбой post-хука откатывает запись, и вы получаете ошибку хука как она была брошена.

## Запуск приложения

При старте приложение обычно вызывает [`connection.init()`](../reference/connection/connection.mdx#connectioninit), чтобы создать недостающие коллекции и индексы. Если хоть что-то не вышло, приходит [`SyncError`](../reference/errors/configuration-errors.mdx#syncerror). Он собирает **все** сбои сразу: один неудавшийся индекс не мешает проверить остальные, поэтому за один запуск вы видите полный список проблем, а не исправляете их по одной.

```ts twoslash
import { SyncError, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
// ---cut---
try {
  await client.connection.init();
} catch (error) {
  if (error instanceof SyncError) {
    for (const failure of error.failures) console.error(failure.kind, failure.name, failure.errors.map((e) => e.message));
  }
  throw error;
}
```

Продолжать работу с базой, которая не соответствует схеме, не стоит: ошибки появятся позже и в неожиданных местах. Поэтому пример записывает проблемы и пробрасывает ошибку дальше, останавливая запуск.

## Ошибки внутри обхода курсора

При обходе больших выборок функция, которую вы передаёте в `eachAsync`, может бросить ошибку. Без `continueOnError` первая ошибка прерывает обход и приходит как есть. С `continueOnError: true` обход дочитывается до конца, а ошибки собираются в [`EachAsyncError`](../reference/errors/query-errors.mdx#eachasyncerror): все они лежат в `error.errors` в порядке документов, а первая ещё и в `cause`. Подробнее об обходе — в руководстве [Большие выборки](../queries/large-results.mdx).

## Как выбрать, где ловить

Задайте себе один вопрос: **что можно сделать с этой ошибкой на этом уровне кода?** Если ничего осмысленного (нужно только сообщить клиенту), не ловите её в сервисе: пусть она поднимается до общего обработчика, где живёт `toHttp`. Ловите на месте только ту ошибку, для которой у вас есть настоящая реакция: повторить, взять другое значение, начать заново (например, «имя занято, предложить другое» или «токен страницы испорчен, отдать первую страницу»).

Признак правильного места: после `catch` код продолжает работать осмысленно. Если после `catch` он только пробрасывает ошибку дальше, `catch` лишний.

## Когда это не нужно

Ловить ошибки библиотеки не нужно там, где отказ для вас и есть ответ: скрипт миграции должен упасть на первой же ошибке, а не продолжать с неполными данными. Не нужно и проверять входные данные вручную перед вызовом ради красивой ошибки: схема модели проверяет их сама и вернёт [`ValidationError`](../reference/errors/data-errors.mdx#validationerror) со всеми нарушениями сразу.

## Частые ошибки

### Ветка потомка не срабатывает

Обработчик ловит `ServerError` раньше `DuplicateKeyError`, и дубликаты попадают в общую ветку с кодом 500:

```ts twoslash
import { DuplicateKeyError, ServerError } from "@venloc/typemo";
declare const error: unknown;
// ---cut---
// неправильно: ServerError ловит и DuplicateKeyError
if (error instanceof ServerError) console.log("server");
else if (error instanceof DuplicateKeyError) console.log("duplicate");

// правильно: сначала частный класс
if (error instanceof DuplicateKeyError) console.log("duplicate");
else if (error instanceof ServerError) console.log("server");
```

`DuplicateKeyError` — потомок `ServerError`, поэтому первая проверка перехватывает обе ситуации, а вторая никогда не выполняется. Ставьте проверки от частного к общему.

### В ответ попал текст ошибки

Клиент получил в теле ответа `Cast to string failed at path "owner" for 5 (number)…`. Сообщение написано для разработчика: в нём имена полей и значения. Отдавайте клиенту собственный текст или результат `toJSON()`, а сообщение пишите в журнал.

### После PostHookError запись повторили

Симптом: в коллекции два одинаковых документа. Обработчик ловил любую ошибку `create` и повторял вызов, а ошибка была `PostHookError`: запись к этому моменту уже была в базе. Проверяйте `error instanceof PostHookError` (или `ErrorClassifier.classify(error).kind === "post-hook"`) до общего повтора и не повторяйте вызов: `applied` у этой ошибки всегда `true`.

### Ошибка проверена по имени

Проверка `error.name === "DuplicateKeyError"` не срабатывает для наследников и ломается при переименовании. Используйте `instanceof`: он учитывает дерево классов.

### Дубликат ловится проверкой перед записью

Код сначала проверяет `findOne({ title })`, а потом создаёт запись, и два параллельных запроса всё равно создают дубликат: между проверкой и записью успевает вклиниться другой запрос. Уникальность гарантирует только индекс. Пишите сразу и ловите [`DuplicateKeyError`](../reference/errors/server-errors.mdx#duplicatekeyerror):

```ts twoslash
import { DuplicateKeyError, Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
await client.connection.init();
await Accounts.create({ title: "Main", owner: "alice" });
// ---cut---
try {
  await Accounts.create({ title: "Main", owner: "bob" });
} catch (error) {
  if (error instanceof DuplicateKeyError) console.log(Object.keys(error.keyPattern ?? {}));
  // → ["title"]
}
```

Индекс появляется после [`connection.init`](../reference/connection/connection.mdx#connectioninit): без него дубликат запишется без ошибки.

## Полный пример

Один файл собирает всё вместе: сервисная функция бросает ошибки библиотеки как есть, а общий обработчик превращает их в ответ. Код читателя, которого нет в Typemo, помечен `__…__`.

```ts twoslash title="accounts/accounts.service.ts"
import {
  DocumentNotFoundError,
  DuplicateKeyError,
  Entity,
  Prop,
  Schema,
  TypemoClient,
  TypemoError,
  ValidationError,
} from "@venloc/typemo";

@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;
}

declare class __NotFound__ extends Error {}
declare const __respond__: (status: number, body: unknown) => void;
declare const __logError__: (error: unknown) => void;

const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
await client.connection.init();

// сервис: ничего не ловит, ошибки библиотеки поднимаются как есть
export const openAccount = (body: unknown) => Accounts.create(body as { title: string; owner: string });
export const getAccount = (title: string) => Accounts.findOne({ title }).orFail();

// граница приложения: одно место, где ошибки превращаются в ответы
export const handle = async (run: () => Promise<unknown>): Promise<void> => {
  try {
    __respond__(200, await run());
  } catch (error) {
    if (error instanceof ValidationError) __respond__(422, error.toJSON().issues);
    else if (error instanceof DocumentNotFoundError) __respond__(404, { error: "not-found" });
    else if (error instanceof DuplicateKeyError) __respond__(409, { fields: Object.keys(error.keyPattern ?? {}) });
    else if (error instanceof TypemoError) {
      __logError__(error);
      __respond__(500, { error: "internal" });
    } else throw error;
  }
};
```

<Callout type="migration">

В Mongoose ошибка драйвера превращалась в обычный объект со свойствами вроде `code` и `keyValue`, а часть полей терялась при копировании. В Typemo у каждого отказа сервера свой класс: `code`, `codeName` и метки скопированы на ошибку, а сама ошибка драйвера лежит в `cause` неизменной. `ValidationError` и `CastError` не хранят ссылку на модель, поэтому печать ошибки в журнал не выводит всю модель.

</Callout>
