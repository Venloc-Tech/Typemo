Ловите ошибки Typemo по классу, а не по тексту. У каждой ситуации свой класс, а его поля говорят, что именно случилось. Ошибка приходит сразу и по делу. Typemo не проглатывает опечатку в имени поля и не превращает неверное значение в пустое, а останавливает операцию понятным отказом.

Обработчику на границе приложения остаётся превратить этот отказ в правильный ответ. «Нет такого счёта» становится 404, «имя уже занято» — 409, «форма заполнена неверно» — 422. Ниже покажем, как это сделать. А каждый класс по отдельности, с полями и точными текстами, описан в [справочнике ошибок](../reference/errors/index.mdx).

## Что понадобится

Подключённый клиент из файла `db/client.ts` и модель счёта из `accounts/account.ts`.

```ts twoslash title="db/client.ts"
import { TypemoClient } from "@venloc/typemo";

export const client = await TypemoClient.connect("mongodb://localhost:27017/app");
```

```ts twoslash title="accounts/account.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;
}
```

Классы ответов вашего приложения (404, 409) в примерах помечены `__NotFound__`. Это ваш код, а не часть Typemo.

## Быстрый путь

Все ошибки Typemo — потомки [`TypemoError`](../reference/errors/hierarchy.mdx#typemoerror). Один `instanceof` отделяет отказ библиотеки от чужого сбоя, а проверка по конкретному классу выбирает реакцию.

```ts twoslash
import { DocumentNotFoundError, DuplicateKeyError, Entity, Prop, Schema, TypemoClient, TypemoError } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
await client.connection.init();
// ---cut---
try {
  await Accounts.findOne({ title: "no such account" }).orFail();
} catch (error) {
  if (error instanceof DocumentNotFoundError) console.log("not found");
  // → "not found"
  else if (error instanceof DuplicateKeyError) console.log("already exists");
  else if (error instanceof TypemoError) console.log(error.message);
  else throw error;
}
```

Последняя ветка, `throw error`, отправляет наверх всё, что к библиотеке не относится. Прятать чужую ошибку незачем. Ниже разберём типичные задачи — как отдать ошибку клиенту, как отличить повторяемую ошибку и как не выдать секрет.

## Ловить по классу

Классы образуют дерево, поэтому порядок проверок важен — от частного к общему. [`DuplicateKeyError`](../reference/errors/server-errors.mdx#duplicatekeyerror), [`ServerValidationError`](../reference/errors/server-errors.mdx#servervalidationerror) и [`WriteConflictError`](../reference/errors/server-errors.mdx#writeconflicterror) — потомки [`ServerError`](../reference/errors/server-errors.mdx#servererror), а [`KeysetTokenError`](../reference/errors/query-errors.mdx#keysettokenerror) — потомок [`QueryError`](../reference/errors/query-errors.mdx#queryerror). Поставьте проверку по родителю первой, и она перехватит потомка. Ветка потомка тогда не выполнится никогда.

Так что сначала проверяйте конкретный класс, потом его родителя, а в самом конце общий [`TypemoError`](../reference/errors/hierarchy.mdx#typemoerror). Дерево целиком нарисовано в разделе [Иерархия ошибок](../reference/errors/hierarchy.mdx).

Сравнивать `error.name` со строкой не нужно. `instanceof` учитывает наследование, а имя нет. И не разбирайте `error.message`. Этот текст пишется для человека и может уточняться, а решения принимают по классу и полям (`reason`, `code`, `path`).

## Ответить клиенту кодом HTTP

На границе приложения, в обработчике запроса или точке входа сервиса, любая ошибка превращается в ответ клиенту. Сделайте это один раз в общей функции и вызывайте её из всех обработчиков. Тогда ответы выглядят одинаково, а решения о кодах лежат в одном месте.

Какой ситуации какой код, библиотека не решает, это дело вашего приложения. Вот разумная схема.

- Неверный ввод — 400 и 422.
- Документа нет — 404.
- Конфликт с существующими данными — 409.
- База недоступна — 503.
- Всё остальное — 500 с общим текстом, без подробностей.

```ts twoslash title="errors/to-http.ts"
import {
  CastError,
  ConnectionError,
  DocumentNotFoundError,
  DuplicateKeyError,
  QueryError,
  StrictModeError,
  TimeoutError,
  ValidationError,
  VersionError,
} from "@venloc/typemo";

export interface HttpAnswer {
  readonly status: number;
  readonly body: { readonly error: string; readonly details?: unknown };
}

export const toHttp = (error: unknown): HttpAnswer => {
  if (error instanceof ValidationError) {
    return { status: 422, body: { error: "validation", details: error.toJSON().issues } };
  }
  if (error instanceof DocumentNotFoundError) return { status: 404, body: { error: "not-found" } };
  if (error instanceof DuplicateKeyError) {
    return { status: 409, body: { error: "duplicate", details: Object.keys(error.keyPattern ?? {}) } };
  }
  if (error instanceof VersionError) return { status: 409, body: { error: "changed-meanwhile" } };
  if (error instanceof CastError || error instanceof StrictModeError || error instanceof QueryError) {
    return { status: 400, body: { error: "bad-request" } };
  }
  if (error instanceof TimeoutError || error instanceof ConnectionError) {
    return { status: 503, body: { error: "unavailable" } };
  }
  return { status: 500, body: { error: "internal" } };
};
```

На настоящих ошибках получились такие ответы.

- Счёт без владельца — 422 с перечнем `[{ path: "owner", reason: "required", message: "the field is required" }]`.
- `findOne(...).orFail()` без результата — 404.
- Занятое название — 409 с `details: ["title"]`.
- Владелец числом, фильтр с неизвестным полем, испорченный токен страницы — 400.
- Конфликт версий — 409.
- Обычная `Error` из вашего кода — 500.

Тело ответа 422 берётся из [`error.toJSON()`](../reference/errors/data-errors.mdx#ответ-клиенту), а не из самой ошибки. `toJSON` не включает значения нарушений, а они бывают большими или секретными. Для 409 хватит имён полей из `keyPattern`. Само занятое значение клиенту лучше не пересылать.

Ошибку вашего собственного кода (500) запишите в журнал целиком, а клиенту верните общий текст. Подробности нужны разработчику, а не пользователю.

## Не показать лишнего

Тексты ошибок нарочно подробные, чтобы разработчику хватило их для диагностики. В них есть имя модели, путь и значение. Поэтому сырое `error.message` клиенту не отдают, оно может выдать устройство схемы и сами данные. Отдавайте готовые поля (`toJSON`) или свой короткий текст.

Секретные поля защищены отдельно. Если у поля в схеме указано `sensitive`, его значение заменяется на `[hidden]` в ошибках уникальности и приведения, а не только в журнале аудита. Вот какой текст дало поле `email` с `sensitive: "hide"`.

```text
DuplicateKeyError: duplicate key on email_1: { email: "[hidden]" } (code 11000 DuplicateKey)
```

`keyValue` у этой ошибки был `{ email: "[hidden]" }`. Полный текст сервера в `serverMessage` замаскирован так же, и `cause` содержал ту же замаскированную копию. Секрет не попадает ни в сообщение, ни в поля, ни в цепочку причин. Оригинал драйвера доступен только внутри библиотеки.

### Причина сбоя

В `cause` лежит ошибка, из-за которой возникла текущая, — ошибка драйвера, вашей функции или приведения. Пишите её в журнал вместе с ошибкой верхнего уровня. Класс Typemo говорит, что случилось, а `cause` — почему.

```ts twoslash
import { TypemoError } from "@venloc/typemo";
declare const error: TypemoError;
declare const __logger__: { warn(message: string, fields: unknown): void };
// ---cut---
__logger__.warn(error.message, { name: error.name, cause: error.cause });
```

## Ошибки сервера

Отказы сервера разложены по классам в зависимости от кода.

- Нарушение уникальности.
- Отказ валидатора коллекции.
- Конфликт записей.
- Общий [`ServerError`](../reference/errors/server-errors.mdx#servererror) для всего остального.

Коды, на которые реагирует библиотека, собраны в [`ServerErrorCodes`](../reference/errors/server-errors.mdx#servererrorcodes), так что вместо числа 11000 в коде читается `ServerErrorCodes.DuplicateKey`. Исходная ошибка драйвера всегда лежит в `cause`.

Общий `ServerError` приходит на любой код, для которого нет своего класса. Скажем, подсказка несуществующего индекса дала `code: 2` и `codeName: "BadValue"` с сообщением `hint provided does not correspond to an existing index (code 2 BadValue)`. Сообщение нарочно короткое, в нём только причина и код. Полный текст сервера, где бывают план запроса и значения, лежит в `serverMessage` и в `cause`. Пишите его в журнал, но не отдавайте клиенту. Чаще всего такая ошибка значит, что неверен ваш запрос, а не что сервер временно сбоит, и повторять его бессмысленно.

## Повторяемые ошибки

Сервер и драйвер вешают на ошибки **метки**, которые подсказывают, что можно сделать. Главная для приложения — `TransientTransactionError`, «транзакцию можно выполнить заново целиком». Внутри [`connection.transaction`](../reference/transactions/transactions.mdx#transaction) повтор делает драйвер, писать ничего не нужно. При двух временных сбоях функция транзакции выполнилась трижды, и запись зафиксировалась. Самим читать метки приходится только при ручном управлении транзакцией.

```ts twoslash
import { ErrorLabels, ServerError } from "@venloc/typemo";
declare const error: ServerError;
// ---cut---
if (error.hasErrorLabel(ErrorLabels.TransientTransactionError)) {
  // всю транзакцию можно выполнить заново
}
```

Все метки перечислены в справочнике [`ErrorLabels`](../reference/errors/server-errors.mdx#errorlabels). Ошибку без метки вслепую не повторяйте. Нарушение уникальности повторится с тем же результатом, а неидемпотентная запись выполнится дважды.

Разбирать метки и коды самому необязательно, спросите [`ErrorClassifier`](../reference/errors/hierarchy.mdx#errorclassifier). `ErrorClassifier.isRetryable(error)` отвечает, поможет ли повтор той же операции, а `ErrorClassifier.isTransient(error)` — можно ли заново выполнить всю транзакцию. Классификатор принимает любое значение, даже ошибку драйвера, пришедшую мимо моделей. Для нарушения уникальности или ошибки приведения он ответит «нет», ведь повтор с теми же данными ничего не изменит.

## Пакетная запись

Пакет (`insertMany`, `bulkWrite`) не атомарен. При частичной неудаче приходит [`BulkWriteError`](../reference/errors/server-errors.mdx#bulkwriteerror) — он говорит, какие записи не прошли (номер в вашем вводе, код, разобранная ошибка) и что всё-таки записалось. Дальше решает задача. Можно сообщить пользователю, какие строки отвергнуты, и принять остальные, а можно откатить всё.

```ts twoslash
import { BulkWriteError, DuplicateKeyError, Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
await client.connection.init();
await Accounts.create({ title: "Main", owner: "alice" });
// ---cut---
const rows = [
  { title: "N1", owner: "a" },
  { title: "Main", owner: "b" },
  { title: "N2", owner: "c" },
];

try {
  await Accounts.insertMany(rows, { ordered: false });
} catch (error) {
  if (error instanceof BulkWriteError) {
    const duplicates = error.writeErrors.filter((failure) => failure.error instanceof DuplicateKeyError);
    console.log(duplicates.map((failure) => failure.index), error.result.insertedCount);
    // → [1] 2
  }
}
```

Индексы в `writeErrors` считаются по вашему вводу, а не по тому, как драйвер разбил пакет внутри. Строка с индексом 1 — это `rows[1]`. Без `ordered: false` пакет остановился бы на первой ошибке.

## Запись прошла, а хук упал

После успешной записи могут сработать [post-хуки](../hooks/order-and-errors.mdx) — письмо, журнал, кеш. Если такой хук бросил ошибку, вызывающий код получит [`PostHookError`](../reference/errors/hierarchy.mdx#posthookerror), а не исходную ошибку хука. Обёртка нужна ради одного. `applied` у этой ошибки всегда `true`, то есть запись уже в базе. Повторите вызов, не заглянув в ошибку, — и документ запишется второй раз.

```ts twoslash
import { Entity, Post, PostHookError, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) owner!: string;

  @Post("document.save")
  notify(this: Account): void {
    throw new Error("the hook failed");
  }
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
// ---cut---
try {
  await Accounts.create({ owner: "ann" });
} catch (error) {
  if (error instanceof PostHookError) console.log(error.applied, (error.cause as Error).message);
  // → true "the hook failed"
}
```

Что делать дальше, решает приложение. Обычно сбой хука пишут в журнал и отвечают клиенту успехом, ведь запись удалась. Внутри [транзакции](../transactions/transactions.mdx) обёртки нет. Сбой post-хука откатывает запись, и вы получаете ошибку хука в том виде, в каком её бросили.

## Запуск приложения

При старте приложение обычно вызывает [`connection.init()`](../reference/connection/connection.mdx#connectioninit), чтобы создать недостающие коллекции и индексы. Если что-то не вышло, придёт [`SyncError`](../reference/errors/configuration-errors.mdx#syncerror). Он собирает **все** сбои сразу. Один неудачный индекс не мешает проверить остальные, так что за один запуск вы видите весь список проблем и не чините их по одной.

```ts twoslash
import { SyncError, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
// ---cut---
try {
  await client.connection.init();
} catch (error) {
  if (error instanceof SyncError) {
    for (const failure of error.failures) console.error(failure.kind, failure.name, failure.errors.map((e) => e.message));
  }
  throw error;
}
```

Работать дальше с базой, которая не соответствует схеме, не стоит. Ошибки всплывут позже и в неожиданных местах. Поэтому пример записывает проблемы и пробрасывает ошибку, останавливая запуск.

## Ошибки внутри обхода курсора

Когда вы обходите большую выборку, функция, переданная в `eachAsync`, может бросить ошибку. Без `continueOnError` первая же ошибка прерывает обход и приходит как есть. С `continueOnError: true` обход дочитывается до конца, а ошибки собираются в [`EachAsyncError`](../reference/errors/query-errors.mdx#eachasyncerror). Все они лежат в `error.errors` в порядке документов, а первая ещё и в `cause`. Подробнее об обходе — в руководстве [Большие выборки](../queries/large-results.mdx).

## Как выбрать, где ловить

Спросите себя — **что можно сделать с этой ошибкой на этом уровне кода?**

- **Ничего осмысленного, только сообщить клиенту** — не ловите её в сервисе. Пусть поднимется до общего обработчика, где живёт `toHttp`.
- **Есть настоящая реакция** — ловите на месте. Повторить, взять другое значение, начать заново. Например, «имя занято, предложим другое» или «токен страницы испорчен, отдадим первую страницу».

Проверить себя просто. Если после `catch` код продолжает работать осмысленно, место выбрано верно. Если он только пробрасывает ошибку дальше, `catch` лишний.

## Когда это не нужно

Ловить ошибки библиотеки незачем там, где отказ и есть ответ. Скрипт миграции должен упасть на первой ошибке, а не продолжать с неполными данными. Не нужно и проверять ввод вручную перед вызовом ради красивой ошибки. Схема модели проверит его сама и вернёт [`ValidationError`](../reference/errors/data-errors.mdx#validationerror) со всеми нарушениями сразу.

## Если что-то пошло не так

**Ветка потомка не срабатывает.** Обработчик ловит `ServerError` раньше `DuplicateKeyError`, и дубликаты уходят в общую ветку с кодом 500.

```ts twoslash
import { DuplicateKeyError, ServerError } from "@venloc/typemo";
declare const error: unknown;
// ---cut---
// неправильно: ServerError ловит и DuplicateKeyError
if (error instanceof ServerError) console.log("server");
else if (error instanceof DuplicateKeyError) console.log("duplicate");

// правильно: сначала частный класс
if (error instanceof DuplicateKeyError) console.log("duplicate");
else if (error instanceof ServerError) console.log("server");
```

`DuplicateKeyError` — потомок `ServerError`, так что первая проверка перехватывает обе ситуации, а до второй дело не доходит. Ставьте проверки от частного к общему.

**В ответ попал текст ошибки.** Клиент получил в теле ответа `Cast to string failed at path "owner" for 5 (number)…`. Это сообщение для разработчика, в нём имена полей и значения. Отдавайте клиенту свой текст или результат `toJSON()`, а сообщение пишите в журнал.

**В коллекции два одинаковых документа после `PostHookError`.** Обработчик ловил любую ошибку `create` и повторял вызов, а пришла `PostHookError` — запись к этому моменту уже была в базе. Проверяйте `error instanceof PostHookError` (или `ErrorClassifier.classify(error).kind === "post-hook"`) до общего повтора и не повторяйте вызов. `applied` у этой ошибки всегда `true`.

**Проверка по имени не срабатывает.** `error.name === "DuplicateKeyError"` не узнаёт наследников и ломается при переименовании. Используйте `instanceof`, он учитывает дерево классов.

**Дубликат проходит, хотя перед записью есть проверка.** Код сначала вызывает `findOne({ title })`, потом создаёт запись, и два параллельных запроса всё равно создают дубликат. Между проверкой и записью успевает вклиниться другой запрос, и гарантирует уникальность только индекс. Пишите сразу и ловите [`DuplicateKeyError`](../reference/errors/server-errors.mdx#duplicatekeyerror).

```ts twoslash
import { DuplicateKeyError, Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
await client.connection.init();
await Accounts.create({ title: "Main", owner: "alice" });
// ---cut---
try {
  await Accounts.create({ title: "Main", owner: "bob" });
} catch (error) {
  if (error instanceof DuplicateKeyError) console.log(Object.keys(error.keyPattern ?? {}));
  // → ["title"]
}
```

Индекс появляется после [`connection.init`](../reference/connection/connection.mdx#connectioninit). Без него дубликат запишется без всякой ошибки.

## Полный пример

Всё вместе в одном файле. Сервисная функция бросает ошибки библиотеки как есть, а общий обработчик превращает их в ответ. Код, которого нет в Typemo, помечен `__…__`.

```ts twoslash title="accounts/accounts.service.ts"
import {
  DocumentNotFoundError,
  DuplicateKeyError,
  Entity,
  Prop,
  Schema,
  TypemoClient,
  TypemoError,
  ValidationError,
} from "@venloc/typemo";

@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;
}

declare class __NotFound__ extends Error {}
declare const __respond__: (status: number, body: unknown) => void;
declare const __logError__: (error: unknown) => void;

const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
await client.connection.init();

// сервис: ничего не ловит, ошибки библиотеки поднимаются как есть
export const openAccount = (body: unknown) => Accounts.create(body as { title: string; owner: string });
export const getAccount = (title: string) => Accounts.findOne({ title }).orFail();

// граница приложения: одно место, где ошибки превращаются в ответы
export const handle = async (run: () => Promise<unknown>): Promise<void> => {
  try {
    __respond__(200, await run());
  } catch (error) {
    if (error instanceof ValidationError) __respond__(422, error.toJSON().issues);
    else if (error instanceof DocumentNotFoundError) __respond__(404, { error: "not-found" });
    else if (error instanceof DuplicateKeyError) __respond__(409, { fields: Object.keys(error.keyPattern ?? {}) });
    else if (error instanceof TypemoError) {
      __logError__(error);
      __respond__(500, { error: "internal" });
    } else throw error;
  }
};
```

<Callout type="migration">

В Mongoose ошибка драйвера превращалась в обычный объект со свойствами вроде `code` и `keyValue`, и часть полей терялась при копировании. В Typemo у каждого отказа сервера свой класс. `code`, `codeName` и метки скопированы на ошибку, а сама ошибка драйвера лежит в `cause` нетронутой. `ValidationError` и `CastError` не держат ссылку на модель, так что ошибка в журнале не тащит за собой всю модель.

</Callout>
