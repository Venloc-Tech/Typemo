Схемы в Typemo описываются классами и декораторами, а декораторы бывают двух видов. Ядро `@venloc/typemo` работает на **legacy-декораторах**, то есть в режиме TypeScript `experimentalDecorators`. Пакет `@venloc/typemo-decorators` даёт те же декораторы по **стандарту TC39** — без флагов компилятора и без `reflect-metadata`. Имена и опции одни и те же. Меняется только то, откуда вы импортируете декораторы и как объявляете тип поля.

Оба пакета пишут схему в один и тот же построитель ядра. Модели, запросы, типы документов и ошибки получаются одинаковыми. Так что выбор пакета — это выбор режима компилятора, а не возможностей.

## Что понадобится [#prerequisites]

Проект на TypeScript с установленными `@venloc/typemo`, `mongodb` и `bson` ([установка](../getting-started/installation.mdx)). Учтите, что сборка документации эти блоки кода не компилирует, она проверяет примеры на legacy-декораторах. Поведение пакета проверено запуском на настоящей базе.

## Быстрый путь [#quick-start]

```package-install
@venloc/typemo-decorators
```

В `tsconfig.json` не должно быть `experimentalDecorators`, по умолчанию его там и нет. `emitDecoratorMetadata` не нужен ни в одном режиме, `reflect-metadata` подключать тоже не надо. Если у вас задан свой `lib`, добавлять в него `esnext.decorators` не придётся. Проект с `lib: ["ES2022"]` и `lib: ["ES2020"]` компилируется с собранным пакетом и так. Полный `tsconfig` для обоих режимов есть на странице [Установка и настройка](../getting-started/installation.mdx#configure-tsconfig). Декораторы импортируйте из нового пакета, всё остальное — из ядра.

```ts title="accounts/account.ts"
import { Entity } from "@venloc/typemo";
import { Prop, Schema } from "@venloc/typemo-decorators";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true, trim: true })
  title!: string;

  @Prop(() => Number, { min: 0 })
  balance!: number;
}
```

На настоящей базе такая модель сохранила `create({ title: "  Main ", balance: 5 })` с заголовком `"Main"`, а `create({ title: "x", balance: -1 })` бросил `ValidationError: Validation failed: "balance": must be at least 0 [min]`. Ниже разберём отличия и переход.

## Выбрать пакет [#choose-package]

Вопрос всего один — **включён ли в проекте `experimentalDecorators`?**

- **Да, его требуют другие библиотеки на legacy-декораторах** — оставайтесь на `@venloc/typemo`. Флаг действует на весь проект, TypeScript компилирует все декораторы по legacy-правилам, и TC39-декораторы работать не будут.
- **Нет** — берите `@venloc/typemo-decorators`. Это стандарт языка, флаги и `reflect-metadata` ему не нужны.

## Тип поля указывается функцией [#type-as-function]

У стандартных декораторов нет метаданных `design:type`, и во время работы тип поля неизвестен. Поэтому тип называется явно, в каждом поле, функцией.

```ts
@Prop(() => String, { required: true })
title!: string;
```

`@Prop()` без типа и `@Prop(String)` без функции — это ошибка компиляции, а во время работы `ConfigurationError` с текстом `@Prop "name": the type must be a thunk () => T (for example () => String), got String`. Подробнее — в [`@Prop`](../reference/decorators-tc39/decorators.mdx#prop).

## Строже, чем legacy-декораторы [#stricter-than-legacy]

Стандартный декоратор поля получает от компилятора тип поля, его имя и признаки `static` и `#private`. Поэтому лишнее ловится уже при компиляции. Компилятор сообщает `TS1240`, а в тексте названа причина, например `@Prop "#x": #private fields cannot be schema fields` или `@Prop "label": static fields are not schema fields`.

Если кто-то обошёл типы, те же ошибки бросит `ConfigurationError` во время работы.

- `@Prop` на `#private` поле — `@Prop on private field "#x" (#private fields cannot be schema members)`.
- На статическом — `@Prop on static member "label" (static members are not schema members)`.
- На методе — `@Prop on "greet", which is a method (getters are virtuals and need no decorator)`.

Геттеру с вычисляемым значением декоратор не нужен. Связи описываются через [`@Virtual`](../reference/decorators-tc39/decorators.mdx#virtual).

## Пометить поле тенанта [#mark-tenant-field]

В схеме, разделённой по тенантам, поле тенанта нужно пометить декоратором [`@Tenant()`](../reference/decorators-tc39/decorators.mdx#tenant). Он ставится рядом с `@Prop` на поле типа `TenantField<T>`. В пакете TC39 декоратор называется так же, а правила сборки схемы общие с ядром. Зачем пометка обязательна, объясняет руководство [Тенанты](../policies/tenants.mdx#define-tenant-field).

```ts title="notes/note.ts"
import { Entity, type TenantField } from "@venloc/typemo";
import { Prop, Schema, Tenant } from "@venloc/typemo-decorators";

@Schema({ collection: "notes", tenant: true })
export class Note extends Entity {
  @Prop(() => String)
  @Tenant()
  tenantId!: TenantField<string>;

  @Prop(() => String, { required: true })
  text!: string;
}
```

`create({ text: "a" }, { policy: { tenant: "t1" } })` сохранил заметку с `tenantId: "t1"`, а `find()` без тенанта бросил `StrictModeError: Note.find: Note is scoped by tenant ("tenantId") and the operation has no tenant; …`.

Ошибки сборки такие же, как у ядра, и приходят при первом `model()`.

- Схема с `tenant: true` без пометки — `the tenant field "tenantId" must be marked @Tenant() (declare it @Prop(...) @Tenant() tenantId!: TenantField<T>)`.
- `@Tenant()` в схеме без опции `tenant` — `@Tenant() on "tenantId", but the schema has no tenant policy — add tenant: true (or { field }) to @Schema`.
- Две пометки — `@Tenant() marks "tenantId", "other"; only the tenant field "tenantId" may be marked`.

А `@Tenant()` на поле другого типа просто не скомпилируется — `@Tenant "other": declare the field as TenantField<T>`.

## Не смешивать пакеты [#dont-mix-packages]

Декораторы двух пакетов в одном проекте не уживаются, и причина техническая. Режим декораторов задаёт флаг компилятора на весь проект, а не на файл. Смешение проявляется двумя способами, и оба кончаются `ConfigurationError`, а не тихой потерей полей.

Первый — в проект попал декоратор не того пакета. Он сразу, при объявлении класса, видит, в каком режиме его вызвали. Декоратор `@Prop` ядра в проекте без `experimentalDecorators` бросил `ConfigurationError: @Prop from "@venloc/typemo" is a legacy decorator, but it was applied as a TC39 decorator (experimentalDecorators is off). Use "@venloc/typemo-decorators" in a TC39 project; the two packages cannot be mixed`. Обратный случай, TC39-декоратор при включённом `experimentalDecorators`, даёт ту же ошибку с текстом `… is a TC39 decorator, but it was applied as a legacy decorator (experimentalDecorators is on). Use "@venloc/typemo" in a legacy project; …`.

Второй — каждый декоратор отработал в своём режиме, но метаданные обоих видов встретились на одном классе или в одной иерархии. Так бывает, когда базовый класс пришёл из библиотеки, собранной в другом режиме. Тогда ошибку бросит первый `model()` — `Mixed: mixes legacy decorators ("@venloc/typemo", on Mixed) and TC39 decorators ("@venloc/typemo-decorators", on Mixed) in one class hierarchy; use one decorator package per project`. Лучше упасть сразу, чем получить схему, где часть полей потерялась.

Импортируйте декораторы только из одного пакета. `Entity`, `TypemoClient`, [`Mask`](../reference/query/masks.mdx), типы и ошибки по-прежнему берутся из `@venloc/typemo`.

## Перейти с legacy-декораторов [#from-legacy-decorators]

Сначала убедитесь, что `experimentalDecorators` не нужен другим библиотекам. Если нужен, не переходите. Дальше по шагам.

1. Установите `@venloc/typemo-decorators`.
2. Уберите `experimentalDecorators` из `tsconfig.json`. `emitDecoratorMetadata` Typemo не нужен ни в одном режиме, оставьте его, только если он нужен кому-то ещё.
3. Перенесите импорты `Schema`, `Prop`, `Tenant`, `Virtual`, `Index`, `SearchIndex`, `Plugin`, `Discriminator`, `Pre`, `Post`, `PostError` на новый пакет.
4. Запустите `tsc --noEmit` и тесты. Забытый импорт декоратора из ядра выдаст `ConfigurationError` при объявлении класса.

Тип в каждом `@Prop` уже должен быть функцией. Ядро требует этого и в legacy-режиме.

## Полифил `Symbol.metadata` [#symbol-metadata-polyfill]

Стандартные декораторы хранят метаданные в `context.metadata`, а класс получает их по `Symbol.metadata`. В Bun и Node его пока нет. Пакет при загрузке ставит его сам, если он не определён (`Symbol.metadata ??= Symbol.for("Symbol.metadata")`), так что делать ничего не нужно. Важно только, чтобы пакет загрузился раньше первого класса схемы, и обычный `import { Prop } from "@venloc/typemo-decorators"` это гарантирует. И помните, что Bun берёт `tsconfig.json` из папки запуска. В монорепозитории запускайте код и тесты из папки нужного пакета.

## Когда это не нужно [#when-not-to-use]

Не переходите, если в проекте есть код на legacy-декораторах, который нельзя перевести, например сторонняя библиотека. И не пытайтесь развести пакеты «по разным файлам» — флаг компилятора один на весь проект.

## Если что-то пошло не так [#troubleshooting]

**Ошибка `@Prop from "@venloc/typemo" is a legacy decorator`.** Импорт `Prop` остался из ядра. Замените его на `import { Prop } from "@venloc/typemo-decorators"`.

**Опция не подходит типу поля.** Компилятор сверяет опции с типом поля так же, как в legacy-режиме. `@Prop(() => Number, { trim: true })` не скомпилируется с ошибкой `TS2353: Object literal may only specify known properties, and 'trim' does not exist in type …`. Уберите опцию или исправьте тип поля.

**Хук не принимается.** `@Pre("document.save")` на поле, геттере или методе с символьным именем бросает `ConfigurationError: @Pre: a hook must be a string-named instance method, got field`. Вместо `field` там будет вид члена — `getter` или `method`. Хук — это обычный метод экземпляра со строковым именем. На статическом методе или на `#private` члене ошибка называет причину так же, как у `@Prop`.
