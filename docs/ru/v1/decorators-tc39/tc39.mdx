Typemo описывает схемы классами и декораторами, и декораторы бывают двух видов. В ядре `@venloc/typemo` работают **legacy-декораторы** (режим TypeScript `experimentalDecorators`), а пакет `@venloc/typemo-decorators` даёт те же декораторы в форме **стандарта TC39**: без флагов компилятора и без `reflect-metadata`. Имена и опции одинаковы; меняется только откуда вы импортируете декораторы и как объявляете тип поля.

Оба пакета записывают схему в один и тот же построитель ядра, поэтому модели, запросы, типы документов и ошибки получаются одинаковыми. Выбор между пакетами — выбор режима компилятора, а не возможностей.

## Что предполагается

Проект на TypeScript с установленным `@venloc/typemo`, `mongodb` и `bson` ([установка](../getting-started/installation.mdx)). Блоки кода на этой странице не компилируются сборкой документации: она проверяет примеры с legacy-декораторами; поведение пакета проверено запуском на настоящей базе.

## Быстрый путь

```package-install
@venloc/typemo-decorators
```

В `tsconfig.json` не должно быть `experimentalDecorators` (по умолчанию его нет). `emitDecoratorMetadata` не нужен ни в одном режиме, а `reflect-metadata` подключать не надо. Если у вас задан свой `lib`, добавлять в него `esnext.decorators` не требуется: проект с `lib: ["ES2022"]` и `lib: ["ES2020"]` компилируется с собранным пакетом без него. Полный `tsconfig` для обоих режимов — на странице [Установка и настройка](../getting-started/installation.mdx#настроить-tsconfig). Декораторы импортируются из нового пакета, остальное — из ядра:

```ts title="accounts/account.ts"
import { Entity } from "@venloc/typemo";
import { Prop, Schema } from "@venloc/typemo-decorators";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true, trim: true })
  title!: string;

  @Prop(() => Number, { min: 0 })
  balance!: number;
}
```

Запуск такой модели на настоящей базе сохранил `create({ title: "  Main ", balance: 5 })` с заголовком `"Main"`, а `create({ title: "x", balance: -1 })` бросил `ValidationError: Validation failed: "balance": must be at least 0 [min]`. Остальная страница объясняет отличия и переход.

## Выбрать пакет

Задайте себе один вопрос: **включён ли в проекте `experimentalDecorators`?** Если да (его требуют другие библиотеки на legacy-декораторах), оставайтесь на `@venloc/typemo`: флаг действует на весь проект, и TypeScript компилирует все декораторы по legacy-правилам, так что TC39-декораторы работать не будут. Если нет, берите `@venloc/typemo-decorators`: это стандарт языка, для него не нужны флаги и `reflect-metadata`.

## Тип поля указывается функцией

У стандартных декораторов нет метаданных `design:type`, поэтому компилятор не знает тип поля во время работы. Тип называется явно, в каждом поле, функцией:

```ts
@Prop(() => String, { required: true })
title!: string;
```

`@Prop()` без типа и `@Prop(String)` без функции — ошибка компиляции и `ConfigurationError` во время работы: `@Prop "name": the type must be a thunk () => T (for example () => String), got String`. Подробнее — [`@Prop`](../reference/decorators-tc39/decorators.mdx#prop).

## Строже, чем legacy: где ловятся ошибки

Стандартный декоратор поля получает от компилятора тип поля, его имя и признаки `static`/`#private`, поэтому лишнее ловится при компиляции: компилятор сообщает `TS1240`, а в тексте ошибки названа причина, например `@Prop "#x": #private fields cannot be schema fields` или `@Prop "label": static fields are not schema fields`. Во время работы те же ошибки бросают `ConfigurationError`, если кто-то обошёл типы. Запуск дал:

- `@Prop` на `#private` поле: `@Prop on private field "#x" (#private fields cannot be schema members)`;
- на статическом: `@Prop on static member "label" (static members are not schema members)`;
- на методе: `@Prop on "greet", which is a method (getters are virtuals and need no decorator)`.

Вычисляемое значение через геттер декоратора не требует; связи описываются [`@Virtual`](../reference/decorators-tc39/decorators.mdx#virtual).

## Пометить поле тенанта

Схема, разделённая по тенантам, требует, чтобы поле тенанта было помечено декоратором [`@Tenant()`](../reference/decorators-tc39/decorators.mdx#tenant): он ставится рядом с `@Prop` на поле типа `TenantField<T>`. Пакет TC39 даёт тот же декоратор под тем же именем, а правила сборки схемы общие с ядром (почему пометка обязательна, объясняет руководство [Тенанты](../policies/tenants.mdx#описать-поле-тенанта)).

```ts title="notes/note.ts"
import { Entity, type TenantField } from "@venloc/typemo";
import { Prop, Schema, Tenant } from "@venloc/typemo-decorators";

@Schema({ collection: "notes", tenant: true })
export class Note extends Entity {
  @Prop(() => String)
  @Tenant()
  tenantId!: TenantField<string>;

  @Prop(() => String, { required: true })
  text!: string;
}
```

Запуск: `create({ text: "a" }, { policy: { tenant: "t1" } })` сохранил заметку с `tenantId: "t1"`, а `find()` без тенанта бросил `StrictModeError: Note.find: Note is scoped by tenant ("tenantId") and the operation has no tenant; …`. Ошибки сборки такие же, как у ядра, и приходят при первом `model()`: схема с `tenant: true` и без пометки — `the tenant field "tenantId" must be marked @Tenant() (declare it @Prop(...) @Tenant() tenantId!: TenantField<T>)`; `@Tenant()` в схеме без опции `tenant` — `@Tenant() on "tenantId", but the schema has no tenant policy — add tenant: true (or { field }) to @Schema`; две пометки — `@Tenant() marks "tenantId", "other"; only the tenant field "tenantId" may be marked`. `@Tenant()` на поле другого типа не компилируется: `@Tenant "other": declare the field as TenantField<T>`.

## Не смешивать пакеты

Смешивать декораторы двух пакетов в одном проекте нельзя, и причина техническая: режим декораторов задаёт флаг компилятора на весь проект, а не на файл. Поэтому смешение проявляется двумя способами, и оба кончаются `ConfigurationError`, а не тихой потерей полей.

Первый способ: декоратор не того пакета оказался в проекте. Он сразу, при объявлении класса, замечает, в каком режиме его вызвали. Запуск с декоратором `@Prop` ядра в проекте без `experimentalDecorators` дал `ConfigurationError: @Prop from "@venloc/typemo" is a legacy decorator, but it was applied as a TC39 decorator (experimentalDecorators is off). Use "@venloc/typemo-decorators" in a TC39 project; the two packages cannot be mixed`. Обратный случай, TC39-декоратор при включённом `experimentalDecorators`, даёт ту же ошибку с текстом `… is a TC39 decorator, but it was applied as a legacy decorator (experimentalDecorators is on). Use "@venloc/typemo" in a legacy project; …`.

Второй способ: каждый декоратор отработал в своём режиме, но метаданные обоих видов встретились на одном классе или в одной иерархии. Так бывает, когда базовый класс пришёл из библиотеки, собранной в другом режиме. Эту ошибку бросает первый `model()`: `Mixed: mixes legacy decorators ("@venloc/typemo", on Mixed) and TC39 decorators ("@venloc/typemo-decorators", on Mixed) in one class hierarchy; use one decorator package per project`. Лучше упасть сразу, чем получить схему, в которой часть полей потерялась.

Импортируйте декораторы только из одного пакета. `Entity`, `TypemoClient`, [`Mask`](../reference/query/masks.mdx), типы и ошибки по-прежнему приходят из `@venloc/typemo`.

## Перейти с legacy-декораторов

Порядок такой: убедитесь, что другим библиотекам не нужен `experimentalDecorators` (иначе не переходите), установите `@venloc/typemo-decorators`, уберите `experimentalDecorators` из `tsconfig.json` (`emitDecoratorMetadata` Typemo не нужен ни в одном режиме; оставьте его, только если он нужен другим библиотекам), замените импорты `Schema`, `Prop`, `Tenant`, `Virtual`, `Index`, `SearchIndex`, `Plugin`, `Discriminator`, `Pre`, `Post`, `PostError` на импорты из нового пакета. В каждом `@Prop` тип уже должен быть функцией: это требование ядра и в legacy-режиме. Затем запустите `tsc --noEmit` и тесты: оставшийся импорт декоратора из ядра выдаст `ConfigurationError` при объявлении класса.

## Полифил `Symbol.metadata`

Стандартные декораторы хранят метаданные в `context.metadata`, а класс получает их по `Symbol.metadata`, которого в Bun и Node пока нет. Пакет при загрузке ставит его сам, если он не определён (`Symbol.metadata ??= Symbol.for("Symbol.metadata")`), и вам ничего делать не нужно. Импорт пакета должен случиться до первого класса схемы: обычный `import { Prop } from "@venloc/typemo-decorators"` это гарантирует. Bun берёт `tsconfig.json` из папки запуска, поэтому в монорепозитории запускайте код и тесты из папки нужного пакета.

## Когда это не нужно

Не переходите, если в проекте есть код на legacy-декораторах, который нельзя перевести (сторонняя библиотека). Не пытайтесь использовать оба пакета «в разных файлах»: флаг компилятора один на проект.

## Частые ошибки

### `@Prop from "@venloc/typemo" is a legacy decorator`

Импорт `Prop` остался из ядра. Замените на `import { Prop } from "@venloc/typemo-decorators"`.

### Опция не подходит типу поля

Компилятор проверяет опции против типа поля так же, как в legacy-режиме: `@Prop(() => Number, { trim: true })` не компилируется, ошибка `TS2353: Object literal may only specify known properties, and 'trim' does not exist in type …`. Уберите опцию или исправьте тип поля.

### Хук не принимается

`@Pre("document.save")` на поле, геттере или методе с символьным именем бросает `ConfigurationError: @Pre: a hook must be a string-named instance method, got field` (вместо `field` стоит вид члена: `getter`, `method`). Хук — обычный метод экземпляра со строковым именем; на статическом методе или на `#private` члене ошибка называет причину так же, как у `@Prop`.
