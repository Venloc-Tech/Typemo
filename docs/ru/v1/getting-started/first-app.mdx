Соберём небольшой блог, где пользователи пишут посты, а читатели их комментируют. На этом проекте строятся остальные руководства. Вы опишете три модели, подключитесь к MongoDB, напишете функции сервисов и запустите скрипт, который пройдёт весь путь от регистрации до удаления комментария.

Проект самый обычный. Файлы лежат рядом, функции сервисов вызываются из скрипта, веб-фреймворка нет. Тот же код можно вызвать из обработчика любого фреймворка, а границу приложения, например ответы «занято» и «не найдено», обозначают ваши классы `__Conflict__` и `__NotFound__`. Модель растёт по ходу страницы. Сначала пользователь с двумя полями, потом пост, потом скрытое поле и связь поста с комментариями.

## Что понадобится

Установленные пакеты и `tsconfig.json`, настроенный по [Установке и настройке](./installation.mdx), — legacy-декораторы и `target` `ESNext`. Если вы ещё ничего не запускали, начните с [Быстрого старта](./quick-start.mdx). И работающий сервер MongoDB на `localhost:27017`.

## Разложить проект по файлам

Проект плоский. Все файлы лежат в `src`, и по имени файла видно, что в нём. Так в коротких примерах не приходится писать пути.

```tree
src/
  user.model.ts       # модель пользователя
  post.model.ts       # модель поста
  comment.model.ts    # модель комментария
  db.ts               # клиент, подключение, модели
  users.service.ts    # регистрация
  posts.service.ts    # написать, опубликовать, показать
  comments.service.ts # добавить и удалить комментарий
  main.ts             # скрипт, который всё это запускает
```

## Описать пользователя

Начнём с модели пользователя, у которого есть имя и адрес почты. [`trim`](../reference/schemas/prop.mdx#trim) обрезает пробелы по краям имени. [`lowercase`](../reference/schemas/prop.mdx#lowercase) приводит адрес к нижнему регистру, чтобы `Alice@Example.com` и `alice@example.com` считались одним адресом. А [`unique`](../reference/schemas/prop.mdx#unique) не даст завести двух пользователей с одним адресом. Как устроены `@Schema` и `@Prop`, подробно рассказано в руководстве [Описать модель](../schemas/define-model.mdx).

```ts twoslash title="src/user.model.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true, trim: true })
  name!: string;

  @Prop(() => String, { required: true, unique: true, lowercase: true })
  email!: string;
}
```

## Описать пост

Пост принадлежит пользователю, и автор хранится как **ссылка**. В базе лежит только `_id` пользователя, а [`ref`](../reference/schemas/prop.mdx#ref) говорит, в какой модели его искать. Тип [`Ref<User>`](../reference/schemas/field-markers.mdx#ref) подсказывает компилятору, что здесь может оказаться и идентификатор, и сам пользователь. Подробнее — в руководстве [Ссылки на другие модели](../schemas/references.mdx).

Здесь же три новых приёма.

- [`Timestamped(Entity)`](../reference/schemas/base-classes.mdx#timestamped) добавляет посту `createdAt` и `updatedAt`, и Typemo заполняет их сам. Подробнее — в [Метках времени и версиях](../schemas/timestamps-and-versions.mdx).
- `tags` — массив. У массива без `required` и без `default` значение есть всегда, хотя бы пустой `[]`. Поэтому при создании поста его можно не передавать, и `undefined` он не будет никогда.
- У `published` есть [значение по умолчанию](../schemas/defaults.mdx), и его тип объявлен как [`Defaulted<boolean>`](../reference/schemas/field-markers.mdx#defaulted). Так компилятор знает, что при создании поста поле можно пропустить. Забыть `Defaulted` не получится, об этом — в разделе [Если что-то пошло не так](#если-что-то-пошло-не-так).

```ts twoslash title="src/post.model.ts"
// @filename: user.model.ts
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true, trim: true })
  name!: string;

  @Prop(() => String, { required: true, unique: true, lowercase: true })
  email!: string;
}
// @filename: post.model.ts
// ---cut---
import { type Defaulted, Entity, Prop, type Ref, Schema, Timestamped, Types } from "@venloc/typemo";
import { User } from "./user.model.ts";

@Schema({ collection: "posts" })
export class Post extends Timestamped(Entity) {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  body!: string;

  @Prop(() => [String])
  tags!: string[];

  @Prop(() => Boolean, { default: false })
  published!: Defaulted<boolean>;

  @Prop(() => Types.ObjectId, { ref: () => User, required: true })
  author!: Ref<User>;
}
```

## Описать комментарий и связать его с постом

Комментарий хранит ссылки на пост и на автора. А вот пост комментарии у себя не хранит, иначе список внутри поста рос бы без предела. Вместо этого в модель поста добавим **виртуальное поле** `comments`. В базу оно ничего не пишет, а при запросе находит комментарии, у которых `post` равен `_id` поста. Подробнее — в руководстве [Виртуальные поля](../schemas/virtuals.mdx).

```ts twoslash title="src/comment.model.ts"
// @filename: user.model.ts
import { Entity, type Hidden, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true, trim: true })
  name!: string;

  @Prop(() => String, { required: true, unique: true, lowercase: true })
  email!: string;

  @Prop(() => String, { hidden: true })
  passwordHash?: Hidden<string>;
}
// @filename: post.model.ts
import { type Defaulted, Entity, Prop, type Ref, Schema, Timestamped, Types, Virtual, type VirtualRef } from "@venloc/typemo";
import { Comment } from "./comment.model.ts";
import { User } from "./user.model.ts";

@Schema({ collection: "posts" })
export class Post extends Timestamped(Entity) {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  body!: string;

  @Prop(() => [String])
  tags!: string[];

  @Prop(() => Boolean, { default: false })
  published!: Defaulted<boolean>;

  @Prop(() => Types.ObjectId, { ref: () => User, required: true })
  author!: Ref<User>;

  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post" })
  comments?: VirtualRef<Comment>;
}
// @filename: comment.model.ts
// ---cut---
import { Entity, Prop, type Ref, Schema, Types } from "@venloc/typemo";
import { Post } from "./post.model.ts";
import { User } from "./user.model.ts";

@Schema({ collection: "comments" })
export class Comment extends Entity {
  @Prop(() => String, { required: true })
  text!: string;

  @Prop(() => Types.ObjectId, { ref: () => Post, required: true })
  post!: Ref<Post>;

  @Prop(() => Types.ObjectId, { ref: () => User, required: true })
  author!: Ref<User>;
}
```

В пост добавляются импорт комментария и виртуальное поле. [`@Virtual`](../reference/schemas/virtual.mdx#virtual) получает `localField` и `foreignField`. Первое — поле поста, по значению которого ищем, здесь `_id`. Второе — поле комментария, где это значение лежит, здесь `post`. Тип [`VirtualRef<Comment>`](../reference/schemas/field-markers.mdx#virtualref) говорит компилятору, что после заполнения связи здесь окажутся комментарии.


Пост и комментарий импортируют друг друга, и это нормально. `ref: () => Comment` и `ref: () => Post` — функции, которые вызываются позже, когда оба класса уже загружены.

## Подключиться к базе и создать индексы

Клиент и модели создаются один раз, в отдельном файле. [`TypemoClient.connect`](../reference/connection/typemo-client.mdx#typemoclientconnect) открывает соединение, а [`connection.model`](../reference/connection/connection.mdx#connectionmodel) выдаёт модель по классу. [`connection.init`](../reference/connection/connection.mdx#connectioninit) создаёт в базе то, чего там ещё нет, и прежде всего уникальный индекс по `email`. Сам Typemo индексы не создаёт, и без `init` опция `unique` ничего бы не гарантировала. Подробнее о клиенте — в руководстве [Подключиться к базе](../connection/connect.mdx).

## Зарегистрировать пользователя

Пользователь заполнил форму регистрации. Хеш пароля нужно сохранить, но наружу не отдавать никогда. Добавим в модель поле `passwordHash` с опцией [`hidden`](../reference/schemas/prop.mdx#hidden) и типом [`Hidden<string>`](../reference/schemas/field-markers.mdx#hidden). Скрытое поле хранится в базе, но не попадает в данные для ответа клиенту, то есть в результат `.plain()` и `$toPlain()`. Подробнее — в руководстве [Скрытые и чувствительные поля](../schemas/hidden-and-sensitive.mdx).

```ts twoslash title="src/user.model.ts"
import { Entity, type Hidden, Prop, Schema } from "@venloc/typemo"; // [!code ++]

@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true, trim: true })
  name!: string;

  @Prop(() => String, { required: true, unique: true, lowercase: true })
  email!: string;

  @Prop(() => String, { hidden: true }) // [!code ++]
  passwordHash?: Hidden<string>; // [!code ++]
}
```

`registerUser` создаёт пользователя методом [`create`](../reference/writes/writes.mdx#create). Если адрес уже занят, уникальный индекс не пустит запись, и Typemo бросит [`DuplicateKeyError`](../reference/errors/server-errors.mdx#duplicatekeyerror). Сервис превращает её в свою ошибку `__Conflict__`, которую обработчик запроса покажет как ответ 409. `create` возвращает документ, а [`$toPlain`](../reference/documents/document-api.mdx#toplain) превращает его в обычный объект без скрытых полей.

```ts twoslash title="src/users.service.ts"
// @filename: user.model.ts

export class User extends Entity {

  @Prop(() => String, { required: true, unique: true, lowercase: true })
  email!: string;

  @Prop(() => String, { hidden: true })
  passwordHash?: Hidden<string>;
}
// @filename: post.model.ts
import { type Defaulted, Entity, Prop, type Ref, Schema, Timestamped, Types, Virtual, type VirtualRef } from "@venloc/typemo";
import { Comment } from "./comment.model.ts";
import { User } from "./user.model.ts";

@Schema({ collection: "posts" })
export class Post extends Timestamped(Entity) {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  body!: string;

  @Prop(() => [String])
  tags!: string[];

  @Prop(() => Boolean, { default: false })
  published!: Defaulted<boolean>;

  @Prop(() => Types.ObjectId, { ref: () => User, required: true })
  author!: Ref<User>;

  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post" })
  comments?: VirtualRef<Comment>;
}
// @filename: comment.model.ts
import { Entity, Prop, type Ref, Schema, Types } from "@venloc/typemo";
import { Post } from "./post.model.ts";
import { User } from "./user.model.ts";

@Schema({ collection: "comments" })
export class Comment extends Entity {
  @Prop(() => String, { required: true })
  text!: string;

  @Prop(() => Types.ObjectId, { ref: () => Post, required: true })
  post!: Ref<Post>;

  @Prop(() => Types.ObjectId, { ref: () => User, required: true })
  author!: Ref<User>;
}
// @filename: db.ts
import { TypemoClient } from "@venloc/typemo";
import { Comment } from "./comment.model.ts";
import { Post } from "./post.model.ts";
import { User } from "./user.model.ts";

export const client = await TypemoClient.connect("mongodb://localhost:27017/blog");

export const Users = client.connection.model(User);
export const Posts = client.connection.model(Post);
export const Comments = client.connection.model(Comment);

await client.connection.init();
// @filename: users.service.ts
// ---cut---
import { DuplicateKeyError } from "@venloc/typemo";
import { Users } from "./db.ts";

// код читателя: ошибка на границе приложения и хеширование пароля
export class __Conflict__ extends Error {}
const __hashPassword__ = (password: string): string => `hash:${password}`;

export const registerUser = async (name: string, email: string, password: string) => {
  try {
    const user = await Users.create({ name, email, passwordHash: __hashPassword__(password) });
    return user.$toPlain();
  } catch (error) {
    if (error instanceof DuplicateKeyError) throw new __Conflict__(`email ${email} is taken`);
    throw error;
  }
};
```

`__hashPassword__` — ваша функция хеширования, в Typemo её нет. Двойные подчёркивания обозначают код читателя. `registerUser("Alice", "alice@example.com", "s3cret")` вернёт `{ _id: "…", name: "Alice", email: "alice@example.com" }`. Поля `passwordHash` в нём нет, хотя в базе оно лежит.

## Написать и опубликовать пост

Автор пишет черновик, потом публикует его и добавляет тег. `writePost` создаёт пост. Идентификатор автора приходит строкой, например из сессии, и [`create`](../reference/writes/writes.mdx#create) принимает строку там, где ждёт `ObjectId`, так что приводить её самому не нужно. Поле `published` не передаётся, значит, оно `false`.

[`updateOne`](../reference/writes/writes.mdx#updateone) меняет документ, не читая его заранее. `$set` записывает новое значение поля, а `$addToSet` добавляет тег в массив, только если такого там ещё нет. Оба вызова тоже принимают `_id` строкой.

```ts twoslash title="src/posts.service.ts"
// @filename: user.model.ts
import { Entity, type Hidden, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true, trim: true })
  name!: string;

  @Prop(() => String, { required: true, unique: true, lowercase: true })
  email!: string;

  @Prop(() => String, { hidden: true })
  passwordHash?: Hidden<string>;
}
// @filename: post.model.ts
import { type Defaulted, Entity, Prop, type Ref, Schema, Timestamped, Types, Virtual, type VirtualRef } from "@venloc/typemo";
import { Comment } from "./comment.model.ts";
import { User } from "./user.model.ts";

@Schema({ collection: "posts" })
export class Post extends Timestamped(Entity) {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  body!: string;

  @Prop(() => [String])
  tags!: string[];

  @Prop(() => Boolean, { default: false })
  published!: Defaulted<boolean>;

  @Prop(() => Types.ObjectId, { ref: () => User, required: true })
  author!: Ref<User>;

  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post" })
  comments?: VirtualRef<Comment>;
}
// @filename: comment.model.ts
import { Entity, Prop, type Ref, Schema, Types } from "@venloc/typemo";
import { Post } from "./post.model.ts";
import { User } from "./user.model.ts";

@Schema({ collection: "comments" })
export class Comment extends Entity {
  @Prop(() => String, { required: true })
  text!: string;

  @Prop(() => Types.ObjectId, { ref: () => Post, required: true })
  post!: Ref<Post>;

  @Prop(() => Types.ObjectId, { ref: () => User, required: true })
  author!: Ref<User>;
}
// @filename: db.ts
import { TypemoClient } from "@venloc/typemo";
import { Comment } from "./comment.model.ts";
import { Post } from "./post.model.ts";
import { User } from "./user.model.ts";

export const client = await TypemoClient.connect("mongodb://localhost:27017/blog");

export const Users = client.connection.model(User);
export const Posts = client.connection.model(Post);
export const Comments = client.connection.model(Comment);

await client.connection.init();
// @filename: posts.service.ts
// ---cut---
import { Posts } from "./db.ts";

export const writePost = (authorId: string, title: string, body: string, tags: string[] = []) =>
  Posts.create({ author: authorId, title, body, tags });

export const publishPost = (id: string) => Posts.updateOne({ _id: id }, { $set: { published: true } });

export const addTag = (id: string, tag: string) => Posts.updateOne({ _id: id }, { $addToSet: { tags: tag } });
```

`updateOne` возвращает не документ, а счётчики. `matchedCount` — сколько документов подошло, `modifiedCount` — сколько изменилось. Вместе с вашими полями Typemo сам обновляет `updatedAt`. Другие способы изменить данные разобраны в руководстве [Изменить документы](../writes/update.mdx).

## Показать ленту постов

На главной странице нужен список опубликованных постов с именем автора — новые сверху, по десять на страницу. [`find`](../reference/query/reading.mdx#modelfind) принимает фильтр, а дальше запрос строится цепочкой вызовов.

- [`.sort`](../reference/query/reading.mdx#sort) задаёт порядок. Второй ключ `_id` делает его стабильным, когда даты совпадают.
- [`.skip`](../reference/query/reading.mdx#skip) и [`.limit`](../reference/query/reading.mdx#limit) выбирают страницу.
- [`.select`](../reference/query/reading.mdx#select) оставляет только нужные поля.

[`.populate`](../reference/populate/populate.mdx#populate) подставляет вместо идентификатора самого автора, а `select` внутри него берёт только имя. Автор у поста обязателен, но пользователя могли удалить. Без `required: true` заполненное поле имело бы тип `User | null`, и `item.author.name` не скомпилировалось бы. С `required: true` удалённый автор становится ошибкой [`DocumentNotFoundError`](../reference/errors/query-errors.mdx#documentnotfounderror), а `null` пропадает из типа. Завершает цепочку [`.plain()`](../reference/query/reading.mdx#plain), и в результате получаются обычные объекты, готовые для клиента.

## Показать пост с комментариями

На странице поста нужны автор и комментарии, и у каждого комментария тоже показан автор. Комментарии берутся из виртуального поля `comments`, а вложенный `populate` заполняет их авторов. ## Добавить и удалить комментарий

Читатель оставляет комментарий, а автор или модератор может его убрать. `addComment` создаёт комментарий. `removeComment` удаляет его методом [`deleteOne`](../reference/writes/writes.mdx#deleteone) и по счётчику `deletedCount` сообщает, нашёлся ли он. ## Как выбрать

В приложении вы снова и снова будете возвращаться к одному вопросу — **в каком виде вам нужны данные**.

- **Отдаёте клиенту**, как в `listPublished` и `readPost`, — заканчивайте запрос [`.plain()`](../reference/query/reading.mdx#plain).
- **Собираетесь изменить и сохранить** — читайте документ, без `.plain()`.
- **Считаете что-то внутри приложения**, и наружу данные не уходят, — подойдёт [`.lean()`](../reference/query/reading.mdx#lean).

Подробное сравнение — в руководстве [Чтение данных](../queries/reading-data.mdx).

## Когда это не нужно

Пример учебный. В нём нет ни авторизации, ни защиты от чужих комментариев, ни страниц с курсором, ни транзакций. Если нужно выгружать тысячи постов, вместо `skip` и `limit` возьмите [постраничную выдачу по ключу](../queries/keyset-pagination.mdx). А если несколько записей должны меняться вместе, используйте [транзакции](../transactions/transactions.mdx).

## Если что-то пошло не так

**Компилятор требует `Defaulted<T>`.** Поле с `default` объявлено обычным типом. Компилятор остановит вас прямо на декораторе, а не там, где вы забыли передать поле.

```ts twoslash
// @errors: 1240
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "posts" })
export class Post extends Entity {
  @Prop(() => Boolean, { default: false })
  published!: boolean;
}
```

Тип входных данных `create` Typemo выводит из типа поля. С `boolean` поле обязательно, а с `Defaulted<boolean>` — нет. Если объявить `default`, но оставить `boolean`, `create` всё равно требовал бы поле, и значение по умолчанию никогда бы не сработало. Поэтому декоратор такую модель отвергает. Объявите `Defaulted<boolean>`, как в модели поста выше.

**Идентификатор из адреса не подошёл.** Страница поста берёт `id` из адреса, а пользователь может ввести туда что угодно. Строка, которая не похожа на `ObjectId`, даёт [`CastError`](../reference/errors/data-errors.mdx#casterror). Правильный `id` несуществующего поста даёт [`DocumentNotFoundError`](../reference/errors/query-errors.mdx#documentnotfounderror).

```text
CastError: Cast to ObjectId failed at path "_id" for "nope" (string): not a 24-character hex string [format]
DocumentNotFoundError: Post.findById: no document matched the filter (orFail)
```

```ts twoslash title="src/posts.controller.ts"
};
```

**Опечатка в имени поля.** Если ключ с опечаткой приходит во время работы, например из данных, а не из вашего кода, Typemo остановит запись и не станет молча создавать лишнее поле. В примере ключ приведён к `any`.

```text
CastError: Cast to Post failed at path "pubished" for true (boolean): not a field of Post [unknown-key]
```

Так же ведёт себя запись без обязательного поля — `ValidationError: Validation failed: "body": the field is required [required]`. Подробнее — в руководствах [Создать документы](../writes/create.mdx) и [Строгость](../concepts/strictness.mdx).

## Полный пример

Полный код проекта — это файлы выше. Три модели, `db.ts`, три сервиса и скрипт `main.ts`, который запускает их вместе и печатает результаты из комментариев `// →`.

<Callout type="migration">

В Mongoose `mongoose.connect(uri)` создаёт глобальное подключение, и модели привязываются к нему сами. В Typemo глобального подключения нет. Вы держите клиент в `db.ts` и берёте модели из него. Ссылка описывается типом `Ref<T>`, а у результата запроса с `populate` свой тип, и компилятор знает, где `author` заполнен, а где нет.

</Callout>
