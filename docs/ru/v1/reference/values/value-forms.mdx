Одно и то же сохранённое значение Typemo отдаёт в пяти формах. Таблица ниже показывает, как в каждой из них выглядит каждый тип MongoDB. Форм несколько, потому что у типов MongoDB нет пары в JSON. `ObjectId`, 64-битное целое, `Decimal128`, двоичные данные и даты не помещаются в JSON без потерь или превращений. Драйверу, приложению и клиенту API нужны три разные картины одного документа.

Если вы выбираете форму для своей задачи, начните с руководства [Чтение данных](../../queries/reading-data.mdx). Типы TypeScript, которыми формы записаны, описаны на странице [Типы форм](./form-types.mdx).

Все результаты на странице получены запуском на одном документе. В нём по одному полю каждого типа MongoDB, который схема умеет хранить как поле. Исключение — `MinKey` и `MaxKey`, для них в таблице описаны только формы.

```ts twoslash title="sensors/reading.ts"
import { Binary, Decimal128, UUID } from "mongodb";
import { Entity, Prop, Schema, Spec, Types, type Vector } from "@venloc/typemo";

@Schema({ collection: "readings" })
export class Reading extends Entity {
  @Prop(() => String, { required: true })
  label!: string;

  @Prop(() => Types.Double)
  ratio?: number;

  @Prop(() => Types.Int32)
  count?: number;

  @Prop(() => BigInt)
  total?: bigint;

  @Prop(() => Types.Decimal128)
  price?: Decimal128;

  @Prop(() => Boolean)
  ok?: boolean;

  @Prop(() => Date)
  at?: Date;

  @Prop(() => Spec.binary({ subtype: 0 }))
  blob?: Binary;

  @Prop(() => Types.UUID)
  uid?: UUID;

  @Prop(() => Spec.vector({ dtype: "float32", dimensions: 3 }))
  vec?: Vector;

  @Prop(() => RegExp)
  re?: RegExp;

  @Prop(() => Types.Timestamp)
  ts?: InstanceType<typeof Types.Timestamp>;

  @Prop(() => Spec.map(BigInt))
  scores?: Map<string, bigint>;
}
```

## Пять форм

Форму определяет то, как вы читаете данные, схема на неё не влияет.

- **Документ** — результат обычного чтения. Объект модели с методами `$save`, `$set` и типизированными массивами и картами.
- **Результат `.lean()`** — строки драйвера как есть. `ObjectId`, `bigint`, `Binary`, а карта — обычный объект.
- **`$toObject()`** — данные документа с BSON-значениями как есть и картами в виде `Map`.
- **Результат `.plain()`** — то, что отдают `$toPlain()` и `.plain()`. Типы MongoDB превращены в строки, родные типы JavaScript остаются.
- **JSON** — то, что отдаёт `$toJSON()` и `JSON.stringify(doc)`. Всё, чего нет в JSON, превращено в строки.

Для ответа клиенту предназначены две формы из пяти. Результат `.plain()` — данные остаются данными JavaScript, а идентификаторы и большие числа становятся строками. И JSON, готовый к сериализации. Остальные три нужны внутри приложения. Все формы строятся из одной таблицы типов, поэтому тип результата, который выводит компилятор, совпадает с данными. Это проверяют тесты на настоящей базе.

## Таблица по типам

<ValueForms />

Таблица строится из кода при сборке документации и разойтись с поведением не может. В строках контейнеров (`массив`, `поддокумент`, `Map`) вместо `T` и `V` подставляется тип элемента или значения, и форма применяется к ним рекурсивно. Вспомогательные типы форм — `TimestampJson` это `{ t: number; i: number }`, `MinKeyJson` — `{ $minKey: 1 }`, `MaxKeyJson` — `{ $maxKey: 1 }`.

Прочитайте один документ во всех формах, и форма каждого поля станет видна.

```ts twoslash
import { Binary, Decimal128, UUID } from "mongodb";
import { Entity, Prop, Schema, Spec, TypemoClient, Types, type Vector } from "@venloc/typemo";
@Schema({ collection: "readings" })
class Reading extends Entity {
  @Prop(() => String, { required: true }) label!: string;
  @Prop(() => Types.Double) ratio?: number;
  @Prop(() => Types.Int32) count?: number;
  @Prop(() => BigInt) total?: bigint;
  @Prop(() => Types.Decimal128) price?: Decimal128;
  @Prop(() => Boolean) ok?: boolean;
  @Prop(() => Date) at?: Date;
  @Prop(() => Spec.binary({ subtype: 0 })) blob?: Binary;
  @Prop(() => Types.UUID) uid?: UUID;
  @Prop(() => Spec.vector({ dtype: "float32", dimensions: 3 })) vec?: Vector;
  @Prop(() => RegExp) re?: RegExp;
  @Prop(() => Types.Timestamp) ts?: InstanceType<typeof Types.Timestamp>;
  @Prop(() => Spec.map(BigInt)) scores?: Map<string, bigint>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "sensors" });
const Readings = client.db().model(Reading);
// ---cut---
const doc = await Readings.findOne({ label: "r1" }).orFail();
const lean = await Readings.findOne({ label: "r1" }).orFail().lean();
const plain = doc.$toPlain();
const json = doc.$toJSON();
console.log(typeof lean.total, typeof plain.total, typeof json.total);
// → "bigint" "string" "string"
```

Типы в редакторе совпадают с данными.

## Идентификаторы: ObjectId и UUID

В документе, результате `.lean()` и `$toObject()` идентификатор — экземпляр `ObjectId` (или `UUID`). В результате `.plain()` и в JSON это строка из 24 шестнадцатеричных символов, а у `UUID` — запись через дефисы, например `0f8fad5b-d9cb-469f-a165-70867728950e`. Клиент API с классом `ObjectId` работать не умеет. Он показывает строку, кладёт её в адрес и присылает обратно. Обратно её принимают все методы записи, фильтры и `findById`, оборачивать строку в `ObjectId` вручную не нужно.

## Числа: double, int32 и int64

Обычное число JavaScript и `Types.Double` хранятся как double, `Types.Int32` — как 32-битное целое. Во всех формах они остаются `number`.

С 64-битным `int64` (в схеме это `BigInt`) иначе. В документе, результате `.lean()` и `$toObject()` он `bigint`, а в результате `.plain()` и JSON — **десятичная строка** любого размера. Число JavaScript хранит целые точно только до 2⁵³. Значение `9007199254740993` в числе превратилось бы в `9007199254740992`, и никакой ошибки не возникло бы. Строка сохраняет все цифры. А `JSON.stringify` никогда не встретит `bigint`, на котором падает — `TypeError: JSON.stringify cannot serialize BigInt.` Так падает сериализация строки из `.lean()`.

Тип `int64` в формах `.plain()` и JSON — не `string`, а `` `${bigint}` `` (тип [`Int64String`](./form-types.mdx#int64string)). Такая строка принимается обратно во всех методах записи без приведений. Принимается строго десятичное целое. `"-42"` и `"9223372036854775807"` подойдут, а `"1.5"`, `"1e3"`, `" 1"`, `"0x10"` и число вне диапазона int64 — нет. Всё остальное — [`CastError`](../errors/data-errors.mdx#casterror) с причиной `format`, например `Cast to Long failed at path "total" for "1.5" (string): a string must be a decimal integer (no sign +, leading zeros, -0, spaces, exponent or prefix) [format]`.

Обычное число JavaScript в `BigInt`-поле принимается только как безопасное целое, по модулю не больше 2⁵³ − 1. Дробное число и число, которое уже потеряло точность, дают `CastError` с подсказкой, как передать значение правильно.

```text
CastError: Cast to Long failed at path "total" for 1.5 (number): a fractional number is not an int64; pass a bigint (5n) or a decimal integer string ("5") [integer]
CastError: Cast to Long failed at path "total" for 1152921504606847000 (number): beyond Number.MAX_SAFE_INTEGER the number is already imprecise; pass a bigint (5n) or a decimal integer string ("5") [precision]
```

`2 ** 60` в JavaScript уже не то число, которое вы имели в виду. Записать его молча значило бы записать другое значение. Десятичная строка работает и в операторах обновления, `$inc`, `$mul`, `$min` и `$max` принимают `"9007199254740993"` так же, как `bigint`.

`NaN` и `Infinity` — обычные числа JavaScript. В результатах `.lean()` и `.plain()` они остаются числами, а при сборке JSON (`$toJSON()`) это ошибка с причиной `json`, ведь в JSON нет ни того, ни другого. Подробности в разделе [Ошибки](./bson-guards.mdx#ошибки) справочника `BsonTypeTable`.

## Decimal128

`Decimal128` — десятичное число с точностью до 34 цифр, на нём хранят деньги. В документе, результате `.lean()` и `$toObject()` это экземпляр `Decimal128`, в результате `.plain()` и JSON — строка вроде `"19.99"`. Причина та же, что у `int64`. Число JavaScript двоичное и десятичные дроби хранит неточно. По этой же причине поле принимает на входе (`create`, обновления) строку, `price: "19.99"` не нужно оборачивать в `Decimal128` вручную. Строка, которая не число, даёт `CastError` — `Cast to Decimal128 failed at path "price" for "abc" (string): not a decimal number string [format]`.

## Даты и регулярные выражения

`Date` в результате `.plain()` остаётся `Date`, родной тип JavaScript превращать незачем, но это отдельная копия. В JSON это ISO-строка (`"2026-01-02T03:04:05.000Z"`). `RegExp` тоже остаётся `RegExp` в результате `.plain()` и превращается в строку `"/a.b/i"` в JSON. Из флагов регулярного выражения сохраняются только `i` и `m`. Это ограничение формата, а не выбор Typemo.

## Двоичные данные и векторы

`Binary` в результате `.plain()` — отдельная копия `Uint8Array` (не `Buffer` и не вид на память документа). В JSON это строка base64, `"AQID"` для байтов 1, 2, 3. Поэтому `JSON.stringify` результата `.plain()` превращает `Uint8Array` в объект с индексами (`{"0":1,"1":2,"2":3}`). Для JSON вызывайте `$toJSON()`.

Вектор (`Vector`, двоичный подтип 9) в документе — `Binary`, а в результате `.plain()` и JSON — массив чисел. На входе вектор задаётся обычным массивом (`vec: [1, 2, 3]`). Объявляйте поле вектора типом `Vector`, тогда тип в форме `.plain()` будет массивом чисел, а не байтами.

## Timestamp, MinKey и MaxKey

`Timestamp` в результате `.plain()` и в JSON превращается в объект `{ t, i }` (секунды и порядковый номер внутри секунды), например `{"t":1700000000,"i":7}`. Это служебный тип MongoDB для репликации, а не дата. Для моментов времени берите `Date`. `MinKey` и `MaxKey` — служебные крайние значения в сортировке. В результате `.plain()` и JSON они превращаются в `{ $minKey: 1 }` и `{ $maxKey: 1 }`.

## Карты, массивы и вложенные документы

Карта (`Spec.map`) в документе — типизированная `Map`, в результате `.lean()` — обычный объект (так отдаёт драйвер), в `$toObject()` и результате `.plain()` — снова `Map`, а в JSON — объект. Значения карты и элементы массива проходят через ту же таблицу. Карта из `bigint` в результате `.plain()` — это `Map` со значениями-строками, а в JSON — `{ "a": "1" }`. Массивы и вложенные документы в документе — типизированные коллекции с методами `$`, во всех остальных формах — обычные массивы и объекты.

## Как выбрать форму

Спросите себя, что будет с данными после чтения.

- **Данные будете менять и сохранять** — читайте документ.
- **Данные останутся в приложении и нужны исходные типы**, например для расчёта с `bigint` или сравнения `ObjectId` — читайте `.lean()`.
- **Данные уйдут за пределы процесса**, в ответ API, очередь или кэш — читайте `.plain()`. Он безопасен для `JSON.stringify`, пока в данных нет `Uint8Array` и `Map`.
- **Нужен готовый JSON**, где все значения примитивы, — берите `$toJSON()`.

## Когда формы не нужны

Если вы пишете данные, формы не участвуют. Методы записи принимают значения в удобном виде (строку вместо `ObjectId`, строку вместо `bigint`) и приводят их сами. Типы этих входов — [`CreateInput` и `UpdateInput`](./form-types.mdx#createinput-и-updateinput).

## Частые ошибки

### Сериализация падает на больших числах

`JSON.stringify(lean)` падает с `TypeError: JSON.stringify cannot serialize BigInt.` Результат `.lean()` хранит `int64` как `bigint`, а `JSON.stringify` его не принимает. Отдавайте наружу `.plain()` или JSON, где `int64` — строка.

### В JSON вместо байтов объект с индексами

`JSON.stringify(doc.$toPlain())` превращает `Uint8Array` в `{"0":1,"1":2,"2":3}`, а `Map` — в `{}`. Результат `.plain()` остаётся данными JavaScript, а не JSON. Для JSON вызывайте `$toJSON()` или `JSON.stringify(doc)`, он делает то же самое.

### Идентификатор не сравнивается

Два `ObjectId` с одинаковым значением — разные объекты, и `===` вернёт `false`. Сравнивайте через `id.equals(other)` или берите строки из результата `.plain()`.
