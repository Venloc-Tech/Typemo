Одно и то же сохранённое значение Typemo отдаёт в пяти формах, и таблица ниже показывает, как выглядит в каждой из них каждый тип MongoDB. Формы существуют потому, что у типов MongoDB нет пары в JSON: `ObjectId`, 64-битное целое, `Decimal128`, двоичные данные и даты не помещаются в JSON без потерь или превращений, а разным потребителям нужно разное. Драйверу, приложению и клиенту API нужны три разные картины одного и того же документа.

Если вы выбираете, в какой форме читать данные для своей задачи, начните с руководства [Чтение данных](../../queries/reading-data.mdx). Эта страница — справочник: полная таблица и правила для каждого типа. Типы TypeScript, которыми формы записаны, описаны на странице [Типы форм](./form-types.mdx).

Все результаты на странице получены запуском на одном документе. В нём есть по одному полю каждого типа MongoDB, который схема умеет хранить как поле (кроме `MinKey` и `MaxKey`: для них в таблице описаны только формы).

```ts twoslash title="sensors/reading.ts"
import { Binary, Decimal128, UUID } from "mongodb";
import { Entity, Prop, Schema, Spec, Types, type Vector } from "@venloc/typemo";

@Schema({ collection: "readings" })
export class Reading extends Entity {
  @Prop(() => String, { required: true })
  label!: string;

  @Prop(() => Types.Double)
  ratio?: number;

  @Prop(() => Types.Int32)
  count?: number;

  @Prop(() => BigInt)
  total?: bigint;

  @Prop(() => Types.Decimal128)
  price?: Decimal128;

  @Prop(() => Boolean)
  ok?: boolean;

  @Prop(() => Date)
  at?: Date;

  @Prop(() => Spec.binary({ subtype: 0 }))
  blob?: Binary;

  @Prop(() => Types.UUID)
  uid?: UUID;

  @Prop(() => Spec.vector({ dtype: "float32", dimensions: 3 }))
  vec?: Vector;

  @Prop(() => RegExp)
  re?: RegExp;

  @Prop(() => Types.Timestamp)
  ts?: InstanceType<typeof Types.Timestamp>;

  @Prop(() => Spec.map(BigInt))
  scores?: Map<string, bigint>;
}
```

## Пять форм

Форма определяется тем, как вы читаете данные, и не зависит от схемы. **Документ** (hydrated) — результат обычного чтения: объект модели с методами `$save`, `$set` и типизированными массивами и картами. **Lean** — строки драйвера как есть: `ObjectId`, `bigint`, `Binary`, а карта — обычный объект. **`$toObject()`** — данные документа с BSON-значениями как есть и картами в виде `Map`. **Plain** — то, что отдают `$toPlain()` и `.plain()`: типы MongoDB превращены в строки, родные типы JavaScript остаются. **JSON** — то, что отдаёт `$toJSON()` и `JSON.stringify(doc)`: всё, чего нет в JSON, превращено в строки.

Из пяти форм для ответа клиенту предназначены две: plain (данные остаются данными JavaScript, а идентификаторы и большие числа — строками) и JSON (готово к сериализации). Остальные три служат внутри приложения. Все формы строятся из одной таблицы типов, поэтому тип результата, который выводит компилятор, совпадает с данными: это проверяют тесты на настоящей базе.

## Таблица по типам

<ValueForms />

Таблица строится из кода при сборке документации и не может разойтись с поведением. В строках контейнеров (`массив`, `поддокумент`, `Map`) вместо `T` и `V` подставляется тип элемента или значения, и форма применяется к ним рекурсивно. Вспомогательные типы формы: `TimestampJson` — это `{ t: number; i: number }`, `MinKeyJson` — `{ $minKey: 1 }`, `MaxKeyJson` — `{ $maxKey: 1 }`.

Чтобы увидеть форму каждого поля своими глазами, прочитайте один документ во всех формах:

```ts twoslash
import { Binary, Decimal128, UUID } from "mongodb";
import { Entity, Prop, Schema, Spec, TypemoClient, Types, type Vector } from "@venloc/typemo";
@Schema({ collection: "readings" })
class Reading extends Entity {
  @Prop(() => String, { required: true }) label!: string;
  @Prop(() => Types.Double) ratio?: number;
  @Prop(() => Types.Int32) count?: number;
  @Prop(() => BigInt) total?: bigint;
  @Prop(() => Types.Decimal128) price?: Decimal128;
  @Prop(() => Boolean) ok?: boolean;
  @Prop(() => Date) at?: Date;
  @Prop(() => Spec.binary({ subtype: 0 })) blob?: Binary;
  @Prop(() => Types.UUID) uid?: UUID;
  @Prop(() => Spec.vector({ dtype: "float32", dimensions: 3 })) vec?: Vector;
  @Prop(() => RegExp) re?: RegExp;
  @Prop(() => Types.Timestamp) ts?: InstanceType<typeof Types.Timestamp>;
  @Prop(() => Spec.map(BigInt)) scores?: Map<string, bigint>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "sensors" });
const Readings = client.db().model(Reading);
// ---cut---
const doc = await Readings.findOne({ label: "r1" }).orFail();
const lean = await Readings.findOne({ label: "r1" }).orFail().lean();
const plain = doc.$toPlain();
const json = doc.$toJSON();
console.log(typeof lean.total, typeof plain.total, typeof json.total);
// → "bigint" "string" "string"
```

## Идентификаторы: ObjectId и UUID

В документе, в lean и в `$toObject()` идентификатор — экземпляр `ObjectId` (или `UUID`), а в plain и в JSON — строка из 24 шестнадцатеричных символов (у `UUID` — запись через дефисы: `0f8fad5b-d9cb-469f-a165-70867728950e`). Идентификатор превращается в строку, потому что клиент API не умеет работать с классом `ObjectId`: он показывает строку, кладёт её в адрес и присылает обратно. Обратно её принимают все методы записи, фильтры и `findById`, поэтому клиентскую строку не нужно оборачивать в `ObjectId` вручную.

## Числа: double, int32 и int64

Обычное число JavaScript и `Types.Double` хранятся как double, `Types.Int32` — как 32-битное целое; во всех формах они остаются `number`. Иначе устроен 64-битный `int64` (в схеме это `BigInt`): в документе, lean и `$toObject()` он `bigint`, а в plain и JSON — **десятичная строка** любого размера. Строкой, потому что число JavaScript хранит целые точно только до 2⁵³, а значение `9007199254740993` в числе превратилось бы в `9007199254740992`, и никакой ошибки не возникло бы. Строка сохраняет все цифры, а `JSON.stringify` никогда не встречает `bigint`, на котором падает: `TypeError: JSON.stringify cannot serialize BigInt.` — так падает сериализация lean-строки.

Тип plain- и JSON-формы `int64` — не `string`, а `` `${bigint}` `` (тип [`Int64String`](./form-types.mdx#int64string)): такая строка принимается обратно во всех методах записи без приведений. Принимается строго десятичное целое: `"-42"` и `"9223372036854775807"`, но не `"1.5"`, `"1e3"`, `" 1"`, `"0x10"` и не число вне диапазона int64. Всё остальное — [`CastError`](../errors/data-errors.mdx#casterror) с причиной `format`: `Cast to Long failed at path "total" for "1.5" (string): a string must be a decimal integer (no sign +, leading zeros, -0, spaces, exponent or prefix) [format]`.

Обычное число JavaScript в `BigInt`-поле принимается только как безопасное целое (по модулю не больше 2⁵³ − 1). Дробное число и число, которое уже потеряло точность, — `CastError` с подсказкой, как передать значение правильно:

```text
CastError: Cast to Long failed at path "total" for 1.5 (number): a fractional number is not an int64; pass a bigint (5n) or a decimal integer string ("5") [integer]
CastError: Cast to Long failed at path "total" for 1152921504606847000 (number): beyond Number.MAX_SAFE_INTEGER the number is already imprecise; pass a bigint (5n) or a decimal integer string ("5") [precision]
```

Так сделано потому, что `2 ** 60` в JavaScript уже не то число, которое вы имели в виду, и записать его молча значило бы записать другое значение. Десятичная строка работает и в операторах обновления: `$inc`, `$mul`, `$min` и `$max` принимают `"9007199254740993"` так же, как `bigint`.

`NaN` и `Infinity` — обычные числа JavaScript. В lean и plain они остаются числами, а при сборке JSON (`$toJSON()`) это ошибка с причиной `json`: в JSON нет ни того, ни другого. Подробности — в разделе [Ошибки](./bson-guards.mdx#ошибки) справочника `BsonTypeTable`.

## Decimal128

`Decimal128` — десятичное число с точностью до 34 цифр; на нём хранят деньги. В документе, lean и `$toObject()` это экземпляр `Decimal128`, в plain и JSON — строка вида `"19.99"`. Строка нужна по той же причине, что и у `int64`: число JavaScript двоичное и неточно хранит десятичные дроби. Из-за этого и на входе (`create`, обновления) поле принимает строку: `price: "19.99"` не нужно оборачивать в `Decimal128` вручную. Строка, которая не число, — `CastError`: `Cast to Decimal128 failed at path "price" for "abc" (string): not a decimal number string [format]`.

## Даты и регулярные выражения

`Date` в plain-форме остаётся `Date` (родной тип JavaScript, превращать его незачем), но это отдельная копия, а в JSON — ISO-строка (`"2026-01-02T03:04:05.000Z"`). `RegExp` тоже остаётся `RegExp` в plain и превращается в строку `"/a.b/i"` в JSON. Из флагов регулярного выражения сохраняются только `i` и `m`: это ограничение формата, а не выбор Typemo.

## Двоичные данные и векторы

`Binary` в plain-форме — отдельная копия `Uint8Array` (не `Buffer` и не вид на память документа), а в JSON — строка base64 (`"AQID"` для байтов 1, 2, 3). Поэтому `JSON.stringify` plain-формы превращает `Uint8Array` в объект с индексами (`{"0":1,"1":2,"2":3}`): для JSON вызывайте `$toJSON()`. Вектор (`Vector`, двоичный подтип 9) в документе — `Binary`, а в plain и JSON — массив чисел. На входе вектор задаётся обычным массивом чисел (`vec: [1, 2, 3]`). Поле вектора объявляется типом `Vector`: этот тип нужен, чтобы тип plain-формы был массивом чисел, а не байтами.

## Timestamp, MinKey и MaxKey

`Timestamp` в plain и JSON превращается в объект `{ t, i }` (секунды и порядковый номер внутри секунды): `{"t":1700000000,"i":7}`. Это служебный тип MongoDB для репликации, а не дата: для моментов времени используйте `Date`. `MinKey` и `MaxKey` — служебные крайние значения в сортировке; в plain и JSON они превращаются в `{ $minKey: 1 }` и `{ $maxKey: 1 }`.

## Карты, массивы и вложенные документы

Карта (`Spec.map`) в документе — типизированная `Map`, в lean — обычный объект (так отдаёт драйвер), в `$toObject()` и plain — снова `Map`, а в JSON — объект. Значения карты и элементы массива проходят через ту же таблицу: карта из `bigint` в plain — `Map` со значениями-строками, а в JSON — `{ "a": "1" }`. Массивы и вложенные документы в документе — типизированные коллекции с методами `$`, во всех остальных формах — обычные массивы и объекты.

## Как выбрать форму

Задайте себе один вопрос: **что будет с данными после чтения?** Если вы будете их менять и сохранять, читайте документ. Если данные пойдут внутри приложения и вам нужны исходные типы (для расчёта с `bigint`, для сравнения `ObjectId`), читайте lean. Если данные уйдут за пределы процесса (ответ API, очередь, кэш), читайте plain: он безопасен для `JSON.stringify` там, где нет `Uint8Array` и `Map`. А если вам нужен именно готовый JSON (все значения примитивами), используйте `$toJSON()`.

## Когда формы не нужны

Если вы пишете данные, формы не участвуют: методы записи принимают значения в удобном виде (строку вместо `ObjectId`, строку вместо `bigint`) и приводят их сами. Типы этих входов — [`CreateInput` и `UpdateInput`](./form-types.mdx#createinput-и-updateinput).

## Частые ошибки

### Сериализация падает на больших числах

`JSON.stringify(lean)` падает: `TypeError: JSON.stringify cannot serialize BigInt.` Lean хранит `int64` как `bigint`, а `JSON.stringify` его не принимает. Отдавайте наружу plain или JSON, где `int64` — строка.

### В JSON вместо байтов объект с индексами

`JSON.stringify(doc.$toPlain())` превращает `Uint8Array` в `{"0":1,"1":2,"2":3}`, а `Map` — в `{}`. Plain остаётся данными JavaScript, а не JSON. Для JSON вызывайте `$toJSON()` или `JSON.stringify(doc)`, который делает то же самое.

### Идентификатор не сравнивается

Два `ObjectId` с одинаковым значением — разные объекты, и `===` вернёт `false`. Сравнивайте `id.equals(other)` или строки из plain-формы.
