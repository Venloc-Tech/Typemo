**Контекст операции** — это объект, который получает в `this` хук на событие запроса, модели или агрегации: представление операции, которую Typemo сейчас выполняет. Из него хук читает, что операция отправит в базу (фильтр, обновление, документы), и решает, что с ней делать: ничего, изменить или совсем пропустить. Страница описывает этот объект целиком и три типа рядом с ним: имя операции, описание операции для наблюдателей и описание изменений документа.

Если вы впервые пишете хук операции, сначала прочитайте руководство [Хуки операций](../../hooks/operation-hooks.mdx). Здесь только справочник. Декораторы, которыми хуки объявляются, и список событий описаны на странице [`@Pre`, `@Post` и `@PostError`](./pre-post.mdx).

Все примеры используют одну модель счёта.

```ts twoslash title="accounts/account.ts"
import { type Defaulted, Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => Number, { default: 0 })
  balance!: Defaulted<number>;
}
```

В коллекции три счёта: `a` и `b` у `alice` и `c` у `bob`.

## OperationHookContext

`OperationHookContext<T, E>` — тип `this` для всех событий, кроме `document.*`. `T` — ваша модель, `E` — событие. Хук `@Pre("query.find")` объявляет `this: OperationHookContext<Account, "query.find">`, и компилятор тогда знает, какие изменения и какой результат допустимы именно для `find`. Если хук обслуживает список событий, второй параметр можно не указывать: тогда допустимо любое из событий.

Значения в контексте — в **базовой форме**, то есть такими, какими операция уйдёт в драйвер: приведённые схемой, с добавленными политиками (условие удалённых документов, арендатор). Поэтому в `this.filter` вы увидите то, что действительно отправится, а не то, что написал вызывающий код. Значения только для чтения: менять операцию нужно через [`.modify`](#modify).

```ts twoslash
import { type Defaulted, Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { default: 0 }) balance!: Defaulted<number>;
// ---cut---
  @Pre("query.updateOne")
  describe(this: OperationHookContext<Account, "query.updateOne">): void {
    console.log(this.event, this.operation, this.model, this.filter, this.update);
    // → query.updateOne updateOne Account { title: "a" } { $inc: { balance: 5 } }
  }
}
```

Запуск: `updateOne({ title: "a" }, { $inc: { balance: 5 } })` вывел `query.updateOne updateOne Account` и оба объекта, как в комментарии.

### locals: значения между хуками одной операции

`locals` — обычный `Map`, который живёт ровно одну операцию. Хук `pre` кладёт в него значение, а `post` и `postError` той же операции его читают. Так замеряют время или передают решение, принятое до операции. Запуск: `locals.set("startedAt", 1)` в `pre` был прочитан в `post` той же операции. У следующей операции `Map` новый и пустой.

### bulkIndex: хук одной операции пакета

Когда вы вызываете [`bulkWrite`](../writes/writes.mdx#bulkwrite), каждая операция пакета запускает те же хуки `query.*`, что и её отдельный аналог: `updateOne` пакета — хуки `query.updateOne`, `deleteMany` пакета — хуки `query.deleteMany`. Чтобы хук понимал, для какой операции он выполняется, у контекста есть `bulkIndex` — позиция операции во входном списке. У хука обычного вызова `bulkIndex` равен `undefined`, поэтому одним методом можно обслужить оба случая.

```ts twoslash
import { Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
// ---cut---
  @Pre("query.updateOne")
  describe(this: OperationHookContext<Account, "query.updateOne">): void {
    console.log(this.bulkIndex, JSON.stringify(this.filter));
    // → 1 {"title":"Ups"}
  }
}
```

Запуск: в `bulkWrite` из шести операций хук `query.updateOne` вызвался для операций 0 и 1 и вывел их номера и фильтры в базовой форме. Значения `event`, `operation` и `filter` у такого хука те же, что у отдельного вызова: `query.updateOne`, `updateOne` и фильтр операции. Полей `documents`, `operations` и `pipeline` у него нет (`undefined`): операция пакета не владеет документами, список операций виден только хукам `model.bulkWrite`. `session`, `inTransaction` и `policy` — общие для всего пакета.

[`.modify`](#modify) у такого хука меняет **эту одну операцию** так же, как у отдельного вызова: запуск `modify({ update: { $set: { note: "hook@0" } } })` в хуке `query.updateOne` дописал `note` в обновление нулевой операции пакета. После изменения пакет собирается заново и проходит все политики: условие с несуществующим полем бросает тот же `StrictModeError`. [`.skip`](#skip) для одной операции пакета запрещён: подробнее в разделе про `.skip`.

Исключение из `@Pre` хука одной операции пакета зависит от режима пакета. В неупорядоченном (`ordered: false`) оно не останавливает пакет: операция не отправляется и попадает в `BulkWriteError.writeErrors` под своим `bulkIndex` (в `error` — `TypemoError` с исходным исключением в `cause`, `code` — `undefined`), остальные операции записываются, а для самой операции выполняются `@PostError` хуки. В упорядоченном пакет останавливается до отправки, и приходит исключение хука как оно есть. Запуск с хуком, отказавшим операции 1 из трёх upsert: в неупорядоченном режиме записаны операции 0 и 2, в `writeErrors` один элемент с индексом 1; в упорядоченном ничего не записано.

### Поля не меняются на месте

Значения в контексте нельзя менять напрямую: массивы стадий и обновлений отдаются замороженными копиями, и повторное чтение `this.pipeline` возвращает один и тот же объект, пока стадии не заменены. Чтобы изменить операцию, вызовите [`.modify`](#modify). Внутри самого хука, который вызвал `modify`, поля ещё показывают старую операцию: Typemo пересобирает операцию после того, как хук вернул управление. Запуск: хук добавил `$inc` через `modify` и сразу же прочитал `this.update`, а там был только `{ $set: { archived: true } }`.

### Когда контекст не подходит

Если вам нужно только наблюдать за операциями, не вмешиваясь в них, используйте [события операций](../observability/events.mdx): подписчик получает такие же поля и не может ничего сломать. Если вам нужен документ, а не операция, используйте хуки `document.*`: их `this` — сам документ.

## .skip <Badge>только pre</Badge>

`.skip(result)` отменяет операцию: в базу запрос не уходит, а вызывающий код получает `result`, как будто его вернул сервер. Он нужен для кеша, для «сухого прогона», когда операции записи нужно проверить без последствий, и для тестов, которые подменяют ответ базы.

```ts twoslash
import { type Defaulted, Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
declare const dryRun: boolean;
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { default: 0 }) balance!: Defaulted<number>;
// ---cut---
  @Pre("query.deleteMany")
  dryRunOnly(this: OperationHookContext<Account, "query.deleteMany">): void {
    if (dryRun) this.skip({ acknowledged: true, deletedCount: 0 });
  }
}
```

Запуск с `dryRun = true`: `deleteMany({ owner: "bob" })` вернул `{ acknowledged: true, deletedCount: 0 }`, а `countDocuments()` после него показал прежние три счёта.

<Params>
<Param name="result" type="SkipResult<E, T>" required>

Результат операции в кодовых именах: массив lean-документов для `find`, число для подсчёта, `UpdateResult` или `DeleteResult` для записи, `Lean<T> | null` для `findOne`. Точная форма по событиям описана в [`SkipResult`](./pre-post.mdx#skipresult). `undefined` не принимается.

</Param>
</Params>

Возвращает `void`. После `skip` остальные хуки `pre` этой операции не запускаются, а хуки `post` запускаются, получая тот результат, который вернул `skip`.

Пропущенный результат проходит дальше по всем шагам, как настоящий: документы для `find` становятся гидратированными или остаются lean, как просил вызывающий код, `.orFail()` срабатывает на `null`, подгрузка связей работает. Поэтому подложить нельзя то, чего сервер не вернул бы. Документ приводится схемой, и неверный даёт ту же ошибку, что и чтение из базы:

```text
CastError: Cast to string failed at path "title" for 5 (number): expected a string [type]
```

Запись, которую пропустили, ничего не записывает и не попадает в журнал изменений.

### Ошибки

`.skip` можно вызвать только в `pre`. Из `post` он бросает `QueryError`:

```text
QueryError: Account.find: skip() is only for pre hooks (the operation already ran)
```

Вызов без результата (или с `undefined`) бросает `QueryError: Account.find: skip(result) needs a result`. Результат неверной формы, например строка вместо числа для подсчёта, бросает `QueryError` с текстом вида `Account.countDocuments: skip(result): the count must be a non-negative integer`. Событие без результата, `document.*`, пропустить нельзя: у него нет метода `skip`. Если до `skip` в том же хуке вызвать `modify`, операция всё равно пропускается: результат возвращается, а изменение отбрасывается. Обратный порядок, `modify` после `skip`, — ошибка `QueryError: Account.find: modify() after skip() — the operation is not sent`.

В хуке одной операции [`bulkWrite`](../writes/writes.mdx#bulkwrite) `.skip` тоже запрещён, потому что результат одной операции из пакета подменить нельзя:

```text
QueryError: Account.deleteOne (bulkWrite[0]): skip() cannot replace one operation of a bulkWrite with a result; skip the whole bulkWrite from a model.bulkWrite pre hook
```

Пакет целиком пропускается из хука `@Pre("model.bulkWrite")`: он получает `skip(result)` с [`BulkWriteResult`](../writes/writes.mdx#bulkwriteresult). Запуск: `skip` с результатом из нулей в таком хуке вернул этот результат вызывающему, а вставка из пакета в базу не попала.

### Когда `.skip` не подходит

Чтобы запретить операцию, бросьте ошибку из хука: `skip` вернёт вызывающему успешный результат, и он не узнает, что операции не было. Чтобы изменить операцию, а не отменить, используйте [`.modify`](#modify).

## .modify <Badge>только pre</Badge>

`.modify(change)` меняет операцию, которую собирается выполнить Typemo: добавляет условие к фильтру, дописывает операторы в обновление, заменяет выбор полей или сортировку, добавляет стадии в агрегацию. Он нужен, чтобы правило применялось ко всем чтениям и записям модели, даже если вызывающий код о нём не знает: исключить архивные записи, увеличить счётчик ревизии при каждом обновлении.

```ts twoslash
import { type Defaulted, Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
// ---cut---
@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => Number, { default: 0 })
  balance!: Defaulted<number>;

  @Pre("query.updateMany")
  bumpRevision(this: OperationHookContext<Account, "query.updateMany">): void {
    this.modify({ update: { $inc: { balance: 1 } } });
  }
}
```

Запуск: `updateMany({ owner: "alice" }, { $set: { title: "x" } })` затронул два счёта, и у обоих `balance` стал равен 1.

<Params>
<Param name="change" type="OperationChange<T, E>" required>

Объект изменений. Допустимые ключи зависят от события: остальные компилятор не принимает, а во время работы они дают `QueryError`. Ключи и их смысл описаны в [`OperationChanges`](#operationchanges).

</Param>
</Params>

Возвращает `void`. Изменения складываются: несколько вызовов `modify` в одном хуке и в разных хуках применяются по очереди, и следующий хук видит результат предыдущих.

**Изменённая операция проходит все политики заново.** После хука Typemo пересобирает операцию так, будто её собрал сам вызывающий код: нормализует, разрешает пути, приводит типы, применяет политики (строгий режим, санитайзер, арендатор, мягкое удаление, скрытые поля), подставляет значения по умолчанию и проверяет. Поэтому хук не может обойти политику: условие с несуществующим полем даёт тот же `StrictModeError`, что и в обычном запросе. Запуск: `modify({ where: { nope: 1 } })` в `find` привёл к

```text
StrictModeError: filter: "nope" is not a field of Account [unknown-path]
```

Хук, который ничего не менял (включая `modify({})`), ничего не стоит: копия не делается и шаги заново не выполняются.

### Как изменения объединяются с запросом

`where` объединяется с фильтром вызывающего кода через AND: условия вызывающего остаются, и хук может только сузить выборку. `update` добавляет операторы к обновлению вызывающего: если оператор у обновления уже есть, в него дописываются пути хука. `select` и `sort` заменяют проекцию и сортировку целиком. `stages` дописываются в конец конвейера.

Хук не может молча переписать значение, которое обновление уже записывает: путь, записываемый тем же оператором, — ошибка. Запуск: `updateOne({ owner: "bob" }, { $set: { title: "user" } })` при хуке `modify({ update: { $set: { title: "hook" } } })` бросил

```text
QueryError: Account.updateOne: modify(): "$set.title" is already written by the update
```

`update` не работает для обновления конвейером (массивом стадий): `QueryError`, «`update` merges operators into an update of operators, not an update pipeline».

### Ошибки

`.modify` можно вызвать только в `pre`. Из `post` он бросает `QueryError`:

```text
QueryError: Account.find: modify() is only for pre hooks (the operation already ran)
```

Ключ, которого нет в списке, бросает `QueryError: Account.find: modify(): unknown change "nope" (where, update, select, sort, stages)`. Ключ, который к операции не относится, бросает `QueryError: Account.find: modify(): "update" does not apply to find`. Компилятор ловит обе ошибки заранее:

```ts twoslash
import { Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
// ---cut---
  @Pre("query.find")
  wrong(this: OperationHookContext<Account, "query.find">): void {
    // @errors: 2353
    this.modify({ update: { $set: { title: "x" } } });
  }
}
```

### Когда `.modify` не подходит

Чтобы отменить операцию целиком, используйте [`.skip`](#skip). Чтобы запретить, бросьте ошибку. Если нужно применять условие к каждому чтению модели по её смыслу (мягкое удаление, арендатор), для этого есть [политики](../policies/schema-options.mdx): они встроены в ядро и не зависят от хуков.

## OperationChanges

`OperationChanges<T>` описывает все изменения, которые хук может внести в операцию. Ключи названы по-кодовому, как методы модели. `OperationChange<T, E>` оставляет только те ключи, которые подходят событию `E`, а `ChangeKeys<E>` — список этих ключей.

<TypeTable
  type={{

Какие ключи допустимы для каких событий:

```ts twoslash
import type { ChangeKeys } from "@venloc/typemo";
// ---cut---
type Find = ChangeKeys<"query.find">;
//   ^?
type Update = ChangeKeys<"query.updateOne">;
//   ^?
type Insert = ChangeKeys<"model.insertMany">;
//   ^?
```

Для `query.find`, `query.findOne`, `query.findOneAndReplace` и `query.findOneAndDelete` это `where`, `select`, `sort`. Для `query.findOneAndUpdate` к ним добавляется `update`. Для `query.updateOne` и `query.updateMany` это `where` и `update`. Для `query.countDocuments`, `query.distinct`, `query.replaceOne`, `query.deleteOne` и `query.deleteMany` только `where`. Для `aggregate` только `stages`. Для `query.estimatedDocumentCount`, `model.insertMany` и `model.bulkWrite` изменять нечего: `ChangeKeys` даёт `never`.

<FullType>

```ts
interface OperationChanges<T> {
  readonly where?: Filter<T>;
  readonly update?: Update<T>;
  readonly select?: Projection<T>;
  readonly sort?: Sort<T>;
  readonly stages?: readonly PipelineStage[];
}

type ChangeKeys<E> = E extends "query.find" | "query.findOne" | "query.findOneAndReplace" | "query.findOneAndDelete"
  ? "where" | "select" | "sort"
  : E extends "query.findOneAndUpdate"
    ? "where" | "update" | "select" | "sort"
    : E extends "query.updateOne" | "query.updateMany"
      ? "where" | "update"
      : E extends "query.countDocuments" | "query.distinct" | "query.replaceOne" | "query.deleteOne" | "query.deleteMany"
        ? "where"
        : E extends "aggregate"
          ? "stages"
          : never;

type OperationChange<T, E> = Pick<OperationChanges<T>, ChangeKeys<E>>;
```

</FullType>

## BulkOperationResult

`BulkOperationResult` — результат, который получает `@Post` хука `query.updateOne`, `query.updateMany`, `query.replaceOne`, `query.deleteOne` или `query.deleteMany`, когда хук запущен для одной операции внутри [`bulkWrite`](../writes/writes.mdx#bulkwrite). Он нужен, чтобы хук мог сказать, что произошло с его операцией, не выдумывая числа, которых сервер не сообщал.

Дело в том, что `bulkWrite` отправляется одним запросом, а ответ сервера — это итоги всего пакета. По отдельной операции сервер называет только идентификатор документа, который она вставила через `upsert`. Сколько документов нашла, изменила или удалила каждая операция, неизвестно. Поэтому такие счётчики в `BulkOperationResult` равны `null`, а не нулю: ноль означал бы «ничего не найдено», а это неправда. Итоги пакета приходят в хук `model.bulkWrite` как [`BulkWriteResult`](../writes/writes.mdx#bulkwriteresult).

```ts twoslash
import { Entity, Post, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
// ---cut---
  @Post("query.updateOne")
  report(this: OperationHookContext<Account, "query.updateOne">, result: { readonly upsertedId: unknown }): void {
    console.log(this.bulkIndex, JSON.stringify(result));
    // → 1 {"acknowledged":true,"matchedCount":null,"modifiedCount":null,"upsertedCount":1,"upsertedId":"…"}
  }
}
```

Запуск: в пакете из двух `updateOne`, где вторая операция с `upsert: true` вставила документ, первый вызов хука вывел `upsertedCount: 0` и `upsertedId: null`, а второй — `upsertedCount: 1` и настоящий идентификатор. Для `deleteOne` и `deleteMany` внутри пакета результат короче: `{ acknowledged: true, deletedCount: null }`. Объект заморожен.

<TypeTable
  type={{
    "acknowledged": { description: "Подтвердил ли сервер запись пакета.", type: "boolean" },
    "matchedCount": { description: "Только у обновлений и замен. Для одной операции пакета неизвестно: всегда `null`.", type: "null" },
    "modifiedCount": { description: "Только у обновлений и замен. Неизвестно: всегда `null`.", type: "null" },
    "upsertedCount": { description: "Только у обновлений и замен. `1`, если эта операция вставила документ через `upsert`, иначе `0`. Это единственный счётчик, который сервер сообщает по одной операции.", type: "number" },
    "upsertedId": { description: "Только у обновлений и замен. `_id` вставленного документа, иначе `null`.", type: "Id | null" },
    "deletedCount": { description: "Только у удалений. Неизвестно: всегда `null`.", type: "null" },
  }}
/>

Тип — объединение двух форм: у обновлений и замен есть `matchedCount`, `modifiedCount`, `upsertedCount` и `upsertedId`, у удалений — только `deletedCount`. Тип `@Post` подбирается по событию: для `query.updateOne` это `UpdateResult | BulkOperationResult` (первая форма приходит от обычного вызова, вторая — от пакета), для `query.deleteMany` — `DeleteResult | BulkOperationResult` с удалением. Если хуку нужны только поля, общие для обеих форм (`upsertedId`, `acknowledged`), объявите аргумент узким типом, как в примере.

<FullType>

```ts
type BulkOperationResult<Id = unknown> =
  | {
      readonly acknowledged: boolean;
      readonly matchedCount: null;
      readonly modifiedCount: null;
      readonly upsertedCount: number;
      readonly upsertedId: Id | null;
    }
  | {
      readonly acknowledged: boolean;
      readonly deletedCount: null;
    };
```

</FullType>

### Какие хуки получают эту форму

Только хуки `@Post` пяти событий `query.*` у операций внутри `bulkWrite`. Для обычного вызова `Accounts.updateOne(...)` тот же хук получает [`UpdateResult`](../writes/writes.mdx#updateresult) с настоящими счётчиками. У хуков `@PostError` нет результата: они получают ошибку. Порядок вызова, ordered и unordered пакеты описаны в руководстве [Хуки операций внутри `bulkWrite`](../../writes/bulk.mdx#хуки-операций-внутри-bulkwrite).

### Когда не подходит

Чтобы узнать итоги пакета (сколько всего вставлено, найдено, удалено), читайте [`BulkWriteResult`](../writes/writes.mdx#bulkwriteresult) в хуке `model.bulkWrite` или в результате самого вызова. Чтобы узнать число документов, которые затронула конкретная операция, выполните её отдельным вызовом [`updateMany`](../writes/writes.mdx#updatemany) или [`deleteMany`](../writes/writes.mdx#deletemany).

## DocumentChanges

`DocumentChanges` — то, что `$save` отправил бы в базу для этого документа: операторы, пути и значения в кодовых именах. Его возвращает метод документа `$getChanges()`, а в хуке `document.save` он показывает, что уйдёт в базу.

```ts twoslash
import { type Defaulted, Entity, type HookThis, Pre, Prop, Schema } from "@venloc/typemo";
// ---cut---
@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => Number, { default: 0 })
  balance!: Defaulted<number>;

  @Pre("document.save")
  logChanges(this: HookThis<"document.save", Account>): void {
    if (!this.$isRoot()) return;
    console.log(this.$isNew(), this.$getChanges());
    // → false { $set: { balance: 5 } }
  }
}
```

В хуке `this` имеет тип `HydratedDoc<Account>`, поэтому методы документа с `$` доступны без приведения типа. Запуск: `balance = 5` у загруженного документа и `$save()` вывели `false { $set: { balance: 5 } }`. У нового документа в `$set` попадают все поля, включая `_id` и значения по умолчанию: `true { $set: { _id: "…", title: "  Main  ", balance: 0 } }`. Подробнее об отслеживании изменений — в руководстве [Изменить и сохранить](../../documents/change-and-save.mdx), а метод описан в [API документа](../documents/document-api.mdx#getchanges).

<FullType>

```ts
type DocumentChanges = Readonly<Record<string, Readonly<Record<string, unknown>>>>;
```

</FullType>

## OperationName

`OperationName` — имя операции: то, что стоит в поле `operation` контекста хука и события наблюдаемости. Это объединение строк, которые называют действие, без области: `find`, `findOne`, `findOneAndUpdate`, `findOneAndReplace`, `findOneAndDelete`, `updateOne`, `updateMany`, `replaceOne`, `deleteOne`, `deleteMany`, `countDocuments`, `estimatedDocumentCount`, `distinct`, `insertOne`, `insertMany`, `bulkWrite`, `aggregate` и `watch`.

Имя операции не совпадает с событием хука: у события есть область (`query.find`), а имя нужно наблюдателю. В `operation` контекста хука тип строго `string`, а в событиях наблюдаемости — `OperationName`. У операций `insertOne` и `watch` события хука нет: хуки для них не запускаются.

<FullType>

```ts
type OperationName = ExecutionPlan["op"];
```

</FullType>

## OperationInfo

`OperationInfo` — общая часть всех событий операции в наблюдаемости: те же данные об операции, которые хук видит в контексте, плюс описание окружения (база, клиент, сервер). От него наследуют `OperationStartEvent`, `OperationEndEvent` и `OperationErrorEvent`, поэтому подписчик на события и хук читают операцию одинаково.
