**Контекст операции** — объект, который приходит в `this` хука на событие запроса, модели или агрегации. Это представление операции, которую Typemo выполняет прямо сейчас. Хук читает из него, что уйдёт в базу (фильтр, обновление, документы), и решает, что делать дальше — ничего, изменить или пропустить совсем. Здесь описан этот объект и три соседних типа, имя операции, описание операции для наблюдателей и описание изменений документа.

Если вы пишете хук операции впервые, начните с руководства [Хуки операций](../../hooks/operation-hooks.mdx). Эта страница — справочник. Декораторы хуков и список событий описаны на странице [`@Pre`, `@Post` и `@PostError`](./pre-post.mdx).

Во всех примерах одна модель счёта.

```ts twoslash title="accounts/account.ts"
import { type Defaulted, Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => Number, { default: 0 })
  balance!: Defaulted<number>;
}
```

В коллекции три счёта. У `alice` это `a` и `b`, у `bob` — `c`.

## OperationHookContext [#operation-hook-context]

`OperationHookContext<T, E>` — тип `this` для всех событий, кроме `document.*`. `T` — ваша модель, `E` — событие. Хук `@Pre("query.find")` объявляет `this: OperationHookContext<Account, "query.find">`, и компилятор знает, какие изменения и какой результат допустимы именно для `find`. Если хук обслуживает список событий, второй параметр можно опустить, тогда допустимо любое из них.

Значения в контексте лежат в **базовой форме**, такими, какими операция уйдёт в драйвер. Они приведены схемой и дополнены политиками (условие удалённых документов, тенант). Поэтому в `this.filter` вы увидите то, что действительно отправится в базу, а не то, что написал вызывающий код. Значения доступны только для чтения. Менять операцию нужно через [`.modify`](#modify).

```ts twoslash
import { type Defaulted, Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { default: 0 }) balance!: Defaulted<number>;
// ---cut---
  @Pre("query.updateOne")
  describe(this: OperationHookContext<Account, "query.updateOne">): void {
    console.log(this.event, this.operation, this.model, this.filter, this.update);
    // → query.updateOne updateOne Account { title: "a" } { $inc: { balance: 5 } }
  }
}
```

`updateOne({ title: "a" }, { $inc: { balance: 5 } })` вывел `query.updateOne updateOne Account` и оба объекта, как в комментарии.


### locals: значения между хуками одной операции [#locals]

`locals` — обычный `Map`, который живёт ровно одну операцию. Хук `pre` кладёт в него значение, а `post` и `postError` той же операции его читают. Так замеряют время или передают решение, принятое до операции. `locals.set("startedAt", 1)` в `pre` прочитался в `post` той же операции. У следующей операции `Map` новый и пустой.

### bulkIndex: хук одной операции пакета [#bulk-index]

Каждая операция [`bulkWrite`](../writes/writes.mdx#bulk-write) запускает те же хуки `query.*`, что и её отдельный аналог. `updateOne` пакета запускает хуки `query.updateOne`, `deleteMany` пакета — хуки `query.deleteMany`. Чтобы хук понимал, для какой операции он выполняется, у контекста есть `bulkIndex`, позиция операции во входном списке. У хука обычного вызова `bulkIndex` равен `undefined`, так что один метод обслужит оба случая.

```ts twoslash
import { Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
// ---cut---
  @Pre("query.updateOne")
  describe(this: OperationHookContext<Account, "query.updateOne">): void {
    console.log(this.bulkIndex, JSON.stringify(this.filter));
    // → 1 {"title":"Ups"}
  }
}
```

В `bulkWrite` из шести операций хук `query.updateOne` вызвался для операций 0 и 1 и вывел их номера и фильтры в базовой форме. `event`, `operation` и `filter` у такого хука те же, что у отдельного вызова, то есть `query.updateOne`, `updateOne` и фильтр операции. Полей `documents`, `operations` и `pipeline` у него нет, они `undefined`. Операция пакета документами не владеет, а список операций видят только хуки `model.bulkWrite`. `session`, `inTransaction` и `policy` общие для всего пакета.

[`.modify`](#modify) у такого хука меняет **эту одну операцию** так же, как у отдельного вызова. `modify({ update: { $set: { note: "hook@0" } } })` в хуке `query.updateOne` дописал `note` в обновление нулевой операции пакета. После изменения пакет собирается заново и проходит все политики, так что условие с несуществующим полем бросит тот же `StrictModeError`. [`.skip`](#skip) для одной операции пакета запрещён, подробности в разделе про `.skip`.

Что будет с исключением из `@Pre` хука одной операции пакета, зависит от режима пакета. В неупорядоченном (`ordered: false`) оно пакет не останавливает. Операция не отправляется и попадает в `BulkWriteError.writeErrors` под своим `bulkIndex`, в `error` лежит `TypemoError` с исходным исключением в `cause`, а `code` равен `undefined`. Остальные операции записываются, а для самой операции выполняются `@PostError` хуки. В упорядоченном пакет останавливается до отправки, и приходит исключение хука как есть.

Мы отказали операции 1 из трёх upsert. В неупорядоченном режиме записались операции 0 и 2, а в `writeErrors` остался один элемент с индексом 1. В упорядоченном не записалось ничего.

### Поля не меняются на месте [#no-in-place-change]

Значения в контексте напрямую менять нельзя. Массивы стадий и обновлений отдаются замороженными копиями, а повторное чтение `this.pipeline` возвращает один и тот же объект, пока стадии не заменены. Чтобы изменить операцию, вызовите [`.modify`](#modify).

Внутри самого хука, вызвавшего `modify`, поля ещё показывают старую операцию, потому что Typemo пересобирает её после возврата из хука. Хук добавил `$inc` через `modify` и тут же прочитал `this.update`, а там был только `{ $set: { archived: true } }`.

### Когда контекст не подходит [#operation-hook-context.when-not-to-use]

Если за операциями нужно только наблюдать, берите [события операций](../observability/events.mdx). Подписчик получает те же поля и ничего сломать не может. Если нужен документ, а не операция, берите хуки `document.*`, их `this` — сам документ.

## .skip <Badge>только pre</Badge> [#skip]

`.skip(result)` отменяет операцию. Запрос в базу не уходит, а вызывающий код получает `result`, будто его вернул сервер. Это пригодится для кеша, для «сухого прогона», когда запись нужно проверить без последствий, и для тестов, которые подменяют ответ базы.

```ts twoslash
import { type Defaulted, Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
declare const dryRun: boolean;
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => Number, { default: 0 }) balance!: Defaulted<number>;
// ---cut---
  @Pre("query.deleteMany")
  dryRunOnly(this: OperationHookContext<Account, "query.deleteMany">): void {
    if (dryRun) this.skip({ acknowledged: true, deletedCount: 0 });
  }
}
```

С `dryRun = true` `deleteMany({ owner: "bob" })` вернул `{ acknowledged: true, deletedCount: 0 }`, а `countDocuments()` после него показал прежние три счёта.

<Params>
<Param name="result" type="SkipResult<E, T>" required>

Результат операции в именах кода. Для `find` это массив данных `.lean()`, для подсчёта число, для записи `UpdateResult` или `DeleteResult`, для `findOne` `Lean<T> | null`. Точная форма по событиям описана в [`SkipResult`](./pre-post.mdx#skip-result). `undefined` не принимается.

</Param>
</Params>

Возвращает `void`. После `skip` остальные хуки `pre` этой операции не запускаются, а хуки `post` запускаются и получают то, что вернул `skip`.

Пропущенный результат идёт дальше по всем шагам, как настоящий. Документы `find` становятся документами модели или остаются данными `.lean()`, как просил вызывающий код, `.orFail()` срабатывает на `null`, подгрузка связей работает. Поэтому подложить то, чего сервер не вернул бы, не получится. Схема приводит документ, и неверный даёт ту же ошибку, что чтение из базы.

```text
CastError: Cast to string failed at path "title" for 5 (number): expected a string [type]
```

Пропущенная запись ничего не записывает и в журнал изменений не попадает.

### Ошибки [#skip.errors]

`.skip` работает только в `pre`. Из `post` он бросает `QueryError`.

```text
QueryError: Account.find: skip() is only for pre hooks (the operation already ran)
```

Вызов без результата или с `undefined` бросает `QueryError: Account.find: skip(result) needs a result`. Результат неверной формы, например строка вместо числа для подсчёта, даёт `QueryError` с текстом вроде `Account.countDocuments: skip(result): the count must be a non-negative integer`. Событие без результата, то есть `document.*`, пропустить нельзя, метода `skip` у него нет.

Если вызвать `modify` до `skip` в том же хуке, операция всё равно пропускается. Результат возвращается, а изменение отбрасывается. Обратный порядок, `modify` после `skip`, — ошибка `QueryError: Account.find: modify() after skip() — the operation is not sent`.

В хуке одной операции [`bulkWrite`](../writes/writes.mdx#bulk-write) `.skip` тоже запрещён, потому что результат одной операции пакета подменить нельзя.

```text
QueryError: Account.deleteOne (bulkWrite[0]): skip() cannot replace one operation of a bulkWrite with a result; skip the whole bulkWrite from a model.bulkWrite pre hook
```

Пакет целиком можно пропустить из хука `@Pre("model.bulkWrite")`. Он получает `skip(result)` с [`BulkWriteResult`](../writes/writes.mdx#bulk-write-result). `skip` с результатом из нулей в таком хуке вернул его вызывающему, а вставка из пакета в базу не попала.

### Когда `.skip` не подходит [#skip.when-not-to-use]

Чтобы запретить операцию, бросьте ошибку из хука. `skip` вернёт вызывающему успешный результат, и тот не узнает, что операции не было. Чтобы изменить операцию, а не отменить, берите [`.modify`](#modify).

## .modify <Badge>только pre</Badge> [#modify]

`.modify(change)` меняет операцию, которую собирается выполнить Typemo. Он добавляет условие к фильтру, дописывает операторы в обновление, заменяет выбор полей или сортировку, добавляет стадии в агрегацию. С ним правило действует на все чтения и записи модели, даже если вызывающий код о нём не знает. Например, исключить архивные записи или увеличить счётчик ревизии при каждом обновлении.

```ts twoslash
import { type Defaulted, Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
// ---cut---
@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => Number, { default: 0 })
  balance!: Defaulted<number>;

  @Pre("query.updateMany")
  bumpRevision(this: OperationHookContext<Account, "query.updateMany">): void {
    this.modify({ update: { $inc: { balance: 1 } } });
  }
}
```

`updateMany({ owner: "alice" }, { $set: { title: "x" } })` затронул два счёта, и у обоих `balance` стал равен 1.

<Params>
<Param name="change" type="OperationChange<T, E>" required>

Объект изменений. Допустимые ключи зависят от события. Остальные компилятор не примет, а во время работы они дают `QueryError`. Ключи и их смысл описаны в [`OperationChanges`](#operation-changes).

</Param>
</Params>

Возвращает `void`. Изменения складываются. Несколько вызовов `modify` в одном хуке и в разных применяются по очереди, и следующий хук видит результат предыдущих.

**Изменённая операция заново проходит все политики.** После хука Typemo пересобирает операцию так, будто её собрал сам вызывающий код. Он нормализует, разрешает пути, приводит типы, применяет политики (строгий режим, санитайзер, тенант, мягкое удаление, скрытые поля), подставляет значения по умолчанию и проверяет. Хук не может обойти политику. Условие с несуществующим полем даёт тот же `StrictModeError`, что и в обычном запросе. `modify({ where: { nope: 1 } })` в `find` привёл к такой ошибке.

```text
StrictModeError: filter: "nope" is not a field of Account [unknown-path]
```

Хук, который ничего не менял, включая `modify({})`, ничего не стоит. Копия не делается, шаги заново не выполняются.

### Как изменения объединяются с запросом [#merge-with-query]

`where` объединяется с фильтром вызывающего кода через AND. Условия вызывающего остаются, хук может только сузить выборку. `update` добавляет операторы к обновлению вызывающего, и если такой оператор уже есть, в него дописываются пути хука. `select` и `sort` заменяют проекцию и сортировку целиком. `stages` дописываются в конец конвейера.

Хук не может молча переписать значение, которое обновление уже записывает. Путь, который пишет тот же оператор, — ошибка. `updateOne({ owner: "bob" }, { $set: { title: "user" } })` при хуке `modify({ update: { $set: { title: "hook" } } })` бросил такую ошибку.

```text
QueryError: Account.updateOne: modify(): "$set.title" is already written by the update
```

`update` не работает с обновлением конвейером (массивом стадий). Будет `QueryError` с текстом «`update` merges operators into an update of operators, not an update pipeline».

### Ошибки [#modify.errors]

`.modify` работает только в `pre`. Из `post` он бросает `QueryError`.

```text
QueryError: Account.find: modify() is only for pre hooks (the operation already ran)
```

Ключ вне списка бросает `QueryError: Account.find: modify(): unknown change "nope" (where, update, select, sort, stages)`. Ключ, который к операции не относится, бросает `QueryError: Account.find: modify(): "update" does not apply to find`. Компилятор ловит обе ошибки заранее.

```ts twoslash
import { Entity, Pre, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
// ---cut---
// @errors: 2353
  @Pre("query.find")
  wrong(this: OperationHookContext<Account, "query.find">): void {
    this.modify({ update: { $set: { title: "x" } } });
  }
}
```

### Когда `.modify` не подходит [#modify.when-not-to-use]

Чтобы отменить операцию целиком, берите [`.skip`](#skip). Чтобы запретить, бросьте ошибку. Если условие должно действовать на каждое чтение модели по её смыслу, как мягкое удаление или тенант, для этого есть [политики](../policies/schema-options.mdx). Они встроены в ядро и от хуков не зависят.

## OperationChanges [#operation-changes]

`OperationChanges<T>` описывает все изменения, которые хук может внести в операцию. Ключи названы по-кодовому, как методы модели. `OperationChange<T, E>` оставляет только ключи, подходящие событию `E`, а `ChangeKeys<E>` даёт список этих ключей.

<TypeTable
  type={{

Какие ключи допустимы для каких событий, показывает этот тип.

```ts twoslash
import type { ChangeKeys } from "@venloc/typemo";
// ---cut---
type Find = ChangeKeys<"query.find">;
//   ^?
type Update = ChangeKeys<"query.updateOne">;
//   ^?
type Insert = ChangeKeys<"model.insertMany">;
//   ^?
```

Для `query.find`, `query.findOne`, `query.findOneAndReplace` и `query.findOneAndDelete` это `where`, `select`, `sort`. Для `query.findOneAndUpdate` к ним добавляется `update`. Для `query.updateOne` и `query.updateMany` это `where` и `update`. Для `query.countDocuments`, `query.distinct`, `query.replaceOne`, `query.deleteOne` и `query.deleteMany` только `where`. Для `aggregate` только `stages`. Для `query.estimatedDocumentCount`, `model.insertMany` и `model.bulkWrite` менять нечего, `ChangeKeys` даёт `never`.

<FullType>

```ts
interface OperationChanges<T> {
  readonly where?: Filter<T>;
  readonly update?: Update<T>;
  readonly select?: Projection<T>;
  readonly sort?: Sort<T>;
  readonly stages?: readonly PipelineStage[];
}

type ChangeKeys<E> = E extends "query.find" | "query.findOne" | "query.findOneAndReplace" | "query.findOneAndDelete"
  ? "where" | "select" | "sort"
  : E extends "query.findOneAndUpdate"
    ? "where" | "update" | "select" | "sort"
    : E extends "query.updateOne" | "query.updateMany"
      ? "where" | "update"
      : E extends "query.countDocuments" | "query.distinct" | "query.replaceOne" | "query.deleteOne" | "query.deleteMany"
        ? "where"
        : E extends "aggregate"
          ? "stages"
          : never;

type OperationChange<T, E> = Pick<OperationChanges<T>, ChangeKeys<E>>;
```

</FullType>

## BulkOperationResult [#bulk-operation-result]

`BulkOperationResult` — результат, который получает `@Post` хука `query.updateOne`, `query.updateMany`, `query.replaceOne`, `query.deleteOne` или `query.deleteMany`, когда хук запущен для одной операции внутри [`bulkWrite`](../writes/writes.mdx#bulk-write). С ним хук может сказать, что случилось с его операцией, не выдумывая чисел, которых сервер не сообщал.

`bulkWrite` уходит на сервер одним запросом, и ответ — это итоги всего пакета. По отдельной операции сервер называет только идентификатор документа, вставленного через `upsert`. Сколько документов операция нашла, изменила или удалила, неизвестно. Поэтому такие счётчики в `BulkOperationResult` равны `null`, а не нулю. Ноль значил бы «ничего не найдено», а это неправда. Итоги пакета приходят в хук `model.bulkWrite` как [`BulkWriteResult`](../writes/writes.mdx#bulk-write-result).

```ts twoslash
import { Entity, Post, Prop, Schema, type OperationHookContext } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
// ---cut---
  @Post("query.updateOne")
  report(this: OperationHookContext<Account, "query.updateOne">, result: { readonly upsertedId: unknown }): void {
    console.log(this.bulkIndex, JSON.stringify(result));
    // → 1 {"acknowledged":true,"matchedCount":null,"modifiedCount":null,"upsertedCount":1,"upsertedId":"…"}
  }
}
```

В пакете из двух `updateOne` вторая операция с `upsert: true` вставила документ. Первый вызов хука вывел `upsertedCount: 0` и `upsertedId: null`, второй — `upsertedCount: 1` и настоящий идентификатор. Для `deleteOne` и `deleteMany` внутри пакета результат короче, `{ acknowledged: true, deletedCount: null }`. Объект заморожен.

<TypeTable
  type={{
    "acknowledged": { description: "Подтвердил ли сервер запись пакета.", type: "boolean" },
    "matchedCount": { description: "Только у обновлений и замен. Для одной операции пакета неизвестно, всегда `null`.", type: "null" },
    "modifiedCount": { description: "Только у обновлений и замен. Неизвестно, всегда `null`.", type: "null" },
    "upsertedCount": { description: "Только у обновлений и замен. `1`, если эта операция вставила документ через `upsert`, иначе `0`. Это единственный счётчик, который сервер сообщает по одной операции.", type: "number" },
    "upsertedId": { description: "Только у обновлений и замен. `_id` вставленного документа, иначе `null`.", type: "Id | null" },
    "deletedCount": { description: "Только у удалений. Неизвестно, всегда `null`.", type: "null" },
  }}
/>

Тип — объединение двух форм. У обновлений и замен есть `matchedCount`, `modifiedCount`, `upsertedCount` и `upsertedId`, у удалений только `deletedCount`. Тип `@Post` подбирается по событию. Для `query.updateOne` это `UpdateResult | BulkOperationResult`, где первая форма приходит от обычного вызова, а вторая от пакета. Для `query.deleteMany` это `DeleteResult | BulkOperationResult` с удалением. Если хуку нужны только поля, общие для обеих форм (`upsertedId`, `acknowledged`), объявите аргумент узким типом, как в примере.

<FullType>

```ts
type BulkOperationResult<Id = unknown> =
  | {
      readonly acknowledged: boolean;
      readonly matchedCount: null;
      readonly modifiedCount: null;
      readonly upsertedCount: number;
      readonly upsertedId: Id | null;
    }
  | {
      readonly acknowledged: boolean;
      readonly deletedCount: null;
    };
```

</FullType>

### Какие хуки получают эту форму [#hooks-with-this-shape]

Только хуки `@Post` пяти событий `query.*` у операций внутри `bulkWrite`. Для обычного вызова `Accounts.updateOne(...)` тот же хук получает [`UpdateResult`](../writes/writes.mdx#update-result) с настоящими счётчиками. У хуков `@PostError` результата нет, они получают ошибку. Порядок вызова и разницу между упорядоченным и неупорядоченным пакетом описывает руководство [Хуки операций внутри `bulkWrite`](../../writes/bulk.mdx#bulk-write-hooks).

### Когда не подходит [#bulk-operation-result.when-not-to-use]

Итоги пакета (сколько всего вставлено, найдено, удалено) читайте из [`BulkWriteResult`](../writes/writes.mdx#bulk-write-result) в хуке `model.bulkWrite` или в результате самого вызова. Сколько документов затронула конкретная операция, узнаете, выполнив её отдельным вызовом [`updateMany`](../writes/writes.mdx#update-many) или [`deleteMany`](../writes/writes.mdx#delete-many).

## DocumentChanges [#document-changes]

`DocumentChanges` — то, что `$save` отправил бы в базу для этого документа. Это операторы, пути и значения в именах кода. Его возвращает метод документа `$getChanges()`, а в хуке `document.save` он показывает, что уйдёт в базу.

```ts twoslash
import { type Defaulted, Entity, type HookThis, Pre, Prop, Schema } from "@venloc/typemo";
// ---cut---
@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => Number, { default: 0 })
  balance!: Defaulted<number>;

  @Pre("document.save")
  logChanges(this: HookThis<"document.save", Account>): void {
    if (!this.$isRoot()) return;
    console.log(this.$isNew(), this.$getChanges());
    // → false { $set: { balance: 5 } }
  }
}
```

В хуке `this` имеет тип `HydratedDoc<Account>`, поэтому методы документа с `$` доступны без приведения типа. `balance = 5` у загруженного документа и `$save()` вывели `false { $set: { balance: 5 } }`. У нового документа в `$set` попадают все поля, включая `_id` и значения по умолчанию, `true { $set: { _id: "…", title: "  Main  ", balance: 0 } }`. Об отслеживании изменений читайте в руководстве [Изменить и сохранить](../../documents/change-and-save.mdx), а сам метод описан в [API документа](../documents/document-api.mdx#get-changes).

<FullType>

```ts
type DocumentChanges = Readonly<Record<string, Readonly<Record<string, unknown>>>>;
```

</FullType>

## OperationName [#operation-name]

`OperationName` — имя операции, то, что стоит в поле `operation` контекста хука и события наблюдаемости. Это объединение строк, которые называют действие без области — `find`, `findOne`, `findOneAndUpdate`, `findOneAndReplace`, `findOneAndDelete`, `updateOne`, `updateMany`, `replaceOne`, `deleteOne`, `deleteMany`, `countDocuments`, `estimatedDocumentCount`, `distinct`, `insertOne`, `insertMany`, `bulkWrite`, `aggregate` и `watch`.

Имя операции не совпадает с событием хука. У события есть область (`query.find`), а имя нужно наблюдателю. В `operation` контекста хука тип строго `string`, а в событиях наблюдаемости — `OperationName`. У операций `insertOne` и `watch` события хука нет, хуки для них не запускаются.

<FullType>

```ts
type OperationName = ExecutionPlan["op"];
```

</FullType>

От него наследуют `OperationStartEvent`, `OperationEndEvent` и `OperationErrorEvent`, поэтому подписчик и хук читают операцию одинаково.
