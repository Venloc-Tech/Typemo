**Плагин схемы** — объект с именем и функцией `apply`. При компиляции схемы `apply` получает построитель и добавляет в схему поля, индексы, хуки, виртуальные поля, статические методы модели и политики. Плагин нужен, когда одно и то же требуется многим моделям — метка времени последнего просмотра, мягкое удаление, набор индексов, общий хук журнала. Здесь описано всё, из чего плагины состоят и как их подключают.

Если вы пишете плагин впервые, начните с руководства [Плагины](../../hooks/plugins.mdx). Эта страница — справочник. Хуки, которые плагин может добавить, описаны на странице [`@Pre`, `@Post` и `@PostError`](./pre-post.mdx), а глобальная регистрация — в справочнике [`Typemo`](../connection/typemo.mdx#typemoplugin).

В примерах одна модель товара и плагин с методом, который считает товары.

```ts twoslash title="products/product.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "products" })
export class Product extends Entity {
  @Prop(() => String, { required: true })
  title!: string;
}
```

---

## SchemaPlugin

`SchemaPlugin<O, S>` — форма плагина. Обязательны два свойства, непустое `name` и метод `apply(builder, options)`. Необязательное `statics` — объект со статическими методами, которые плагин добавляет моделям. `O` — тип настроек плагина, `S` — тип объекта `statics`.

Имя нужно не только для сообщений об ошибках. По нему Typemo различает регистрации. Один плагин, подключённый на двух уровнях, применяется один раз, а два разных плагина с одним именем дают ошибку.

```ts twoslash
import { type SchemaPlugin } from "@venloc/typemo";
// ---cut---
export const seenAt: SchemaPlugin<{ readonly field: string }> = {
  name: "seen-at",
  apply: (builder, options) => {
    builder.addField(options.field, () => Date);
  },
};
```

Подключение и применение.

```ts twoslash
import { Entity, Plugin, Prop, Schema, type SchemaPlugin } from "@venloc/typemo";
const seenAt: SchemaPlugin<{ readonly field: string }> = {
  name: "seen-at",
  apply: (builder, options) => {
    builder.addField(options.field, () => Date);
  },
};
// ---cut---
@Plugin(seenAt, { field: "seenAt" })
@Schema({ collection: "products" })
export class Product extends Entity {
  @Prop(() => String, { required: true })
  title!: string;
}
```

После `insertOne({ title: "w", seenAt: new Date() })` поле `seenAt` оказалось в документе. Тип модели о нём не знает. Плагин добавляет поле при компиляции, а компилятор видит только объявленный класс. Поэтому такие поля пишут и читают через приведение типа, а лучше объявите их в самом классе.

<Params>
<Param name="name" type="string" required>

Уникальное имя плагина, непустая строка.

</Param>
<Param name="apply" type="(builder: PluginBuilder, options: O) => void" required>

Применяет плагин к компилируемой схеме, по одному разу на схему. Получает [`PluginBuilder`](#pluginbuilder) и настройки, с которыми плагин подключён. Это именно метод, а не свойство-функция, чтобы плагины с разными типами настроек помещались в один список.

</Param>
<Param name="statics" type="S">

Статические методы моделей тех схем, к которым применён плагин. `this` внутри метода — модель, объявите его явно (`this: Model<Product>`). Типизированный доступ к ним даёт [`Model.statics`](#modelstatics).

</Param>
</Params>

<FullType>

```ts
interface SchemaPlugin<O = undefined, S extends object = Record<never, never>> {
  readonly name: string;
  apply(builder: PluginBuilder, options: O): void;
  readonly statics?: S;
}
```

</FullType>

### Настройки плагина

Если тип настроек `O` не допускает `undefined`, при подключении настройки обязательны. Компилятор потребует второй аргумент у [`@Plugin`](#plugin), [`Typemo.plugin`](../connection/typemo.mdx#typemoplugin) или `use`. Если допускает, настройки можно не передавать. При повторной регистрации настройки сравниваются сначала по identity, затем по сериализации в JSON.

### Ошибки

Плагин без имени или без `apply` при регистрации даёт `ConfigurationError`.

```text
ConfigurationError: a plugin is an object { name, apply(builder, options) }
```

### Когда плагин не подходит

Если нужен один хук на одной модели, объявите его методом класса с [`@Pre`](./pre-post.mdx#pre). Если надо хранить свои настройки в описании поля, а не менять схему, возьмите [расширение](../extensions/extensions.mdx#typemoextension). Сам в операции плагин не вмешивается, как и любой код при компиляции. Для этого у него есть только хуки.

## @Plugin

`@Plugin(plugin, options?)` подключает плагин к одной модели. Это декоратор класса, ставьте его рядом с `@Schema`. Настройки идут вторым аргументом, и его тип задаёт сам плагин.

```ts twoslash
import { Entity, Plugin, Prop, Schema, type SchemaPlugin } from "@venloc/typemo";
const audit: SchemaPlugin = {
  name: "audit-log",
  apply: (builder) => {
    builder.addHook("pre", "query.find", function () {
      console.log("чтение товаров");
    });
  },
};
// ---cut---
@Plugin(audit)
@Schema({ collection: "products" })
export class Product extends Entity {
  @Prop(() => String, { required: true })
  title!: string;
}
```

Несколько `@Plugin` на одном классе применяются сверху вниз. Класс с `@Plugin(tools)`, `@Plugin(both)`, `@Plugin(stamp)` и `@Plugin(softly)` в таком порядке скомпилировался со списком плагинов `["conn", "both", "tools", "stamp", "softly"]`. Плагины `conn` и `both` пришли с уровня подключения (см. [порядок применения](#порядок-применения)).

<Params>
<Param name="plugin" type="SchemaPlugin<O>" required>

Плагин.

</Param>
<Param name="options" type="O">

Настройки плагина. Обязательны, если тип `O` не допускает `undefined`.

</Param>
</Params>

<FullType>

```ts
const Plugin: <O>(
  plugin: SchemaPlugin<O>,
  ...options: undefined extends O ? [options?: O] : [options: O]
) => <C extends EntityClass>(target: C) => void;
```

</FullType>

На уровне подключения плагин регистрируют через `connection.plugins.use(plugin, options)` (см. [`connection.plugins`](../connection/connection.mdx#connectionplugins)), на уровне процесса — через [`Typemo.plugin`](../connection/typemo.mdx#typemoplugin). Как выбрать уровень, читайте в руководстве [Несколько клиентов и расширения](../../connection/clients-and-extensions.mdx#как-выбрать-уровень).

### Порядок применения

Сначала идут глобальные плагины, затем плагины подключения, затем плагины модели (`@Plugin`). Внутри уровня порядок такой, в каком их регистрировали. Плагин, подключённый на нескольких уровнях с одинаковыми настройками, применяется один раз, на месте первого появления. Хуки плагинов выполняются **после** хуков самого класса. Мы подключили `conn` на уровне подключения, а `both` и на уровне подключения, и на уровне модели. Получился порядок `conn`, `both`, а не `both` дважды.

### Ошибки

Один плагин с разными настройками на двух уровнях или два разных плагина с одним именем дают `ConfigurationError`. Текст называет обе стороны.

```text
ConfigurationError: Widget: plugin "stamp" is registered twice (connection and model) with different options
ConfigurationError: Widget: two different plugins are named "both"
```

### Когда `@Plugin` не подходит

Чтобы плагин действовал на все модели приложения, возьмите [`Typemo.plugin`](../connection/typemo.mdx#typemoplugin), а на все модели одной базы — `connection.plugins.use`. Вешать его на каждый класс тогда не придётся.

## PluginBuilder

`PluginBuilder` — то, что плагин получает в `apply`. Это узкий интерфейс для изменения компилируемой схемы. Внутреннее устройство схемы плагину недоступно.

```ts twoslash
import { type SchemaPlugin } from "@venloc/typemo";
// ---cut---
export const slugged: SchemaPlugin = {
  name: "slugged",
  apply: (builder) => {
    console.log(builder.target.name, builder.fieldKeys);
    // → Product [ "_id", "title" ]
    builder.addField("slug", () => String);
    builder.addIndex({ slug: 1 });
  },
};
```

Плагин, подключённый к модели с полями `_id` и `title`, вывел `Product [ "_id", "title" ]`.

`addStatic` и `enablePolicy` есть только у плагинов, у обычных декораторов классов их нет. Вызов этих методов у построителя обычного класса даёт ошибки `statics are added by plugins` и `enablePolicy is for plugins`.

<FullType>

```ts
interface PluginBuilder {
  readonly target: ClassRef;
  readonly fieldKeys: readonly string[];
  addField(key: string, type: () => unknown, options?: Readonly<Record<string, unknown>>): void;
  addIndex(fields: IndexFields, options?: IndexOptions): void;
  addHook(phase: HookPhase, events: HookEvent | readonly HookEvent[], fn: HookFunction): void;
  addVirtual(key: string, options: VirtualOptions): void;
  addStatic(name: string, fn: StaticFunction): void;
  enablePolicy<K extends keyof PluginPolicies>(policy: K, options: NonNullable<PluginPolicies[K]>): void;
}
```

</FullType>

### Хуки плагина

Функцию хука объявляйте с `this: unknown` и приводите `this` сами, потому что построитель не знает, какой `this` у какого события. Для события запроса это контекст операции, для события документа — документ. Хук `pre` на `query.find`, добавленный плагином, сработал после хуков класса.

### Политики плагина

`enablePolicy` включает политику так же, как `@Schema`. Плагин с `enablePolicy("softDelete", true)` сделал `deleteOne` мягким. После него `countDocuments()` вернул 0, а в коллекции документ остался (1). Если политику уже задал `@Schema` с другими опциями, а плагин включает её иначе, будет `ConfigurationError` с текстом `declared by @Schema and enabled by plugin "other"`.

### Когда построитель не подходит

Сами операции построитель менять не умеет. Для этого в хуке есть [`.modify`](./operation-context.mdx#modify). Читать схему целиком плагину тоже незачем, для чтения есть [`SchemaInfo`](../schemas/schema-info.mdx).

## PluginPolicies

`PluginPolicies` — политики, которые плагин может включить через [`enablePolicy`](#pluginbuilder). Это `tenant`, `softDelete` и `audit`. Значение каждой — `true` или объект опций, такой же, как в `@Schema`. Об опциях читайте в справочнике [Опции политик в схеме](../policies/schema-options.mdx).

<FullType>

```ts
interface PluginPolicies {
  readonly tenant?: true | TenantSchemaOptions;
  readonly softDelete?: true | SoftDeleteSchemaOptions;
  readonly audit?: true | AuditSchemaOptions;
}
```

</FullType>

## StaticFunction

`StaticFunction` — тип функции для [`addStatic`](#pluginbuilder). Это любая функция, у которой `this` на этом уровне не проверяется. Точные типы статических методов задаёт объект [`statics`](#schemaplugin) плагина.

<FullType>

```ts
type StaticFunction = (this: never, ...args: never[]) => unknown;
```

</FullType>

## PluginStatics

`PluginStatics<P>` — тип статических методов плагина `P` в том виде, в каком их видит модель. Методы привязываются к модели во время работы, поэтому параметр `this` из типа убран. Иначе метод с `this: Model<Product>` нельзя было бы вызвать на модели с другими параметрами типа.

```ts twoslash
import { Entity, Prop, Schema, type PluginStatics, type Model, type SchemaPlugin } from "@venloc/typemo";
@Schema({ collection: "products" })
class Product extends Entity {
  @Prop(() => String, { required: true }) title!: string;
}
// ---cut---
const statics = {
  async byTitle(this: Model<Product>, title: string): Promise<number> {
    return this.countDocuments({ title });
  },
};
const tools: SchemaPlugin<undefined, typeof statics> = { name: "tools", apply: () => {}, statics };

type Bound = PluginStatics<typeof tools>;
//   ^?
```

<FullType>

```ts
type PluginStatics<P> = P extends { readonly statics?: infer S }
  ? { readonly [K in keyof Exclude<S, undefined>]: OmitThisParameter<Exclude<S, undefined>[K]> }
  : never;
```

</FullType>

## Model.statics

`model.statics(plugin)` возвращает ту же модель, но типизированную статическими методами плагина, например `Products.statics(tools).byTitle("w")`. Typemo проверяет, что плагин применён к схеме этой модели, чтобы тип не обещал метод, которого нет во время работы.

```ts twoslash
import { Entity, Plugin, Prop, Schema, TypemoClient, type Model, type SchemaPlugin } from "@venloc/typemo";
const statics = {
  async byTitle(this: Model<Product>, title: string): Promise<number> {
    return this.countDocuments({ title });
  },
};
const tools: SchemaPlugin<undefined, typeof statics> = { name: "tools", apply: () => {}, statics };

@Plugin(tools)
@Schema({ collection: "products" })
class Product extends Entity {
  @Prop(() => String, { required: true })
  title!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Products = client.db().model(Product);
// ---cut---
const count = await Products.statics(tools).byTitle("w");
//    ^?
```

После вставки товара `w` вызов вернул `1`. Методы, добавленные через `addStatic`, во время работы есть, но в типе не видны. Вызывайте их с приведением типа.

<Params>
<Param name="plugin" type="SchemaPlugin<never, object>" required>

Плагин, чьи статические методы нужны.

</Param>
</Params>

<Returns type="this & PluginStatics<P>">

Та же модель, тип которой дополнен статическими методами плагина.

</Returns>

Если плагин к модели не применён, будет ошибка.

```text
ConfigurationError: Account: plugin "tools" is not applied to this model's schema
```

Статический метод с именем члена модели при создании модели даёт `ConfigurationError`. Typemo не затеняет метод молча.

```text
ConfigurationError: Clash: the plugin static "find" would shadow a member of the model
```

## PluginRegistry

`PluginRegistry` — упорядоченный список регистраций плагинов одного уровня. Он живёт на объекте подключения как `connection.plugins`, и есть ещё глобальный. Глобальный реестр вы не видите, пользуйтесь [`Typemo.plugin`](../connection/typemo.mdx#typemoplugin). Тип экспортируется без конструктора, только для типизации.

```ts twoslash
import { TypemoClient, type SchemaPlugin } from "@venloc/typemo";
const audit: SchemaPlugin = { name: "audit-log", apply: () => {} };
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
client.db().plugins.use(audit);
console.log(client.db().plugins.list.map((entry) => `${entry.level}:${entry.plugin.name}`));
// → ["connection:audit-log"]
```

    "list": { description: "Регистрации по порядку, это копия.", type: "readonly PluginUse[]" },

Запись реестра — `PluginUse`, в ней `plugin`, `options` и `level`.

### Реестр закрывается первой моделью

Реестр закрывает первая **успешно** скомпилированная схема. Реестр базы закрывает первая модель этой базы, глобальный реестр — первая модель на любом клиенте. Схема, которая не скомпилировалась, реестр не закрывает. Плагин, зарегистрированный позже, не применился бы к готовым схемам, и приложение получило бы модели, часть из которых плагин не видит. Поэтому Typemo бросает ошибку.

```text
ConfigurationError: plugin "late": the connection plugins are fixed once a schema is compiled (Widget was); register plugins before the first model
```

Для глобального реестра текст такой — `the global plugins are fixed once a schema is compiled`. Расширения закрываются по тому же правилу, подробности в руководстве [Несколько клиентов и расширения](../../connection/clients-and-extensions.mdx#регистрировать-до-первой-модели).

<FullType>

```ts
class PluginRegistry {
  readonly level: Exclude<PluginLevel, "model">;
  use<O>(plugin: SchemaPlugin<O>, ...options: OptionsArgs<O>): this;
  get list(): readonly PluginUse[];
}

interface PluginUse {
  readonly plugin: SchemaPlugin<unknown>;
  readonly options: unknown;
  readonly level: PluginLevel;
}
```

</FullType>

## PluginLevel

`PluginLevel` — уровень, на котором зарегистрирован плагин. Это `"global"` (`Typemo.plugin`), `"connection"` (`connection.plugins.use`) или `"model"` (`@Plugin`). Значение лежит в поле `level` записей `PluginUse`.

<FullType>

```ts
type PluginLevel = "global" | "connection" | "model";
```

</FullType>
