**Плагин схемы** — это объект с именем и функцией `apply`, которая при компиляции схемы получает построитель и добавляет в схему поля, индексы, хуки, виртуальные поля, статические методы модели и политики. Плагины нужны, когда одно и то же нужно многим моделям: метка времени последнего просмотра, мягкое удаление, набор индексов, общий хук журнала. Эта страница описывает всё, из чего плагины состоят и как их подключают.

Если вы впервые пишете плагин, сначала прочитайте руководство [Плагины](../../hooks/plugins.mdx). Эта страница — справочник. Хуки, которые плагин может добавить, описаны на странице [`@Pre`, `@Post` и `@PostError`](./pre-post.mdx), а глобальная регистрация — в справочнике [`Typemo`](../connection/typemo.mdx#typemoplugin).

Примеры используют одну модель товара и плагин с методами, который считает товары.

```ts twoslash title="products/product.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "products" })
export class Product extends Entity {
  @Prop(() => String, { required: true })
  title!: string;
}
```

---

## SchemaPlugin

`SchemaPlugin<O, S>` — форма плагина. Обязательны два свойства: непустое `name` и метод `apply(builder, options)`. Необязательное `statics` — объект со статическими методами, которые плагин добавляет моделям. `O` — тип настроек плагина, `S` — тип объекта `statics`.

Имя нужно не только для сообщений об ошибках: по нему Typemo различает регистрации. Один и тот же плагин, подключённый на двух уровнях, применяется один раз, а два разных плагина с одним именем — ошибка.

```ts twoslash
import { type SchemaPlugin } from "@venloc/typemo";
// ---cut---
export const seenAt: SchemaPlugin<{ readonly field: string }> = {
  name: "seen-at",
  apply: (builder, options) => {
    builder.addField(options.field, () => Date);
  },
};
```

Подключение и применение:

```ts twoslash
import { Entity, Plugin, Prop, Schema, type SchemaPlugin } from "@venloc/typemo";
const seenAt: SchemaPlugin<{ readonly field: string }> = {
  name: "seen-at",
  apply: (builder, options) => {
    builder.addField(options.field, () => Date);
  },
};
// ---cut---
@Plugin(seenAt, { field: "seenAt" })
@Schema({ collection: "products" })
export class Product extends Entity {
  @Prop(() => String, { required: true })
  title!: string;
}
```

Запуск: `insertOne({ title: "w", seenAt: new Date() })` сохранил поле `seenAt` в документе. Тип модели поля `seenAt` не знает: плагин добавляет его при компиляции, а компилятор видит только объявленный класс. Поэтому такие поля записываются и читаются через приведение типа, или их лучше объявить в самом классе.

<Params>
<Param name="name" type="string" required>

Уникальное имя плагина. Не пустая строка.

</Param>
<Param name="apply" type="(builder: PluginBuilder, options: O) => void" required>

Применяет плагин к схеме, которую компилируют. Вызывается один раз на схему. Получает [`PluginBuilder`](#pluginbuilder) и настройки, с которыми плагин подключён. Метод объявлен методом, а не свойством-функцией, чтобы плагины с разными типами настроек помещались в один список.

</Param>
<Param name="statics" type="S">

Статические методы моделей схем, к которым применён плагин. Внутри метода `this` — модель: объявите его явно (`this: Model<Product>`). Типизированный доступ к ним даёт [`Model.statics`](#modelstatics).

</Param>
</Params>

<FullType>

```ts
interface SchemaPlugin<O = undefined, S extends object = Record<never, never>> {
  readonly name: string;
  apply(builder: PluginBuilder, options: O): void;
  readonly statics?: S;
}
```

</FullType>

### Настройки плагина

Если тип настроек `O` не допускает `undefined`, при подключении настройки обязательны, и компилятор потребует второй аргумент [`@Plugin`](#plugin), [`Typemo.plugin`](../connection/typemo.mdx#typemoplugin) или `use`. Если допускает, их можно не передавать. Настройки сравниваются при повторной регистрации: identity, затем сериализация в JSON.

### Ошибки

Плагин без имени или без `apply` при регистрации даёт `ConfigurationError`:

```text
ConfigurationError: a plugin is an object { name, apply(builder, options) }
```

### Когда плагин не подходит

Если нужен только один хук на одной модели, объявите его методом класса с [`@Pre`](./pre-post.mdx#pre). Если нужно хранить свои настройки в описании поля, а не менять схему, используйте [расширение](../extensions/extensions.mdx#typemoextension). Плагин, как и любой код при компиляции, не вмешивается в операции сам: для этого у него есть только хуки.

## @Plugin

`@Plugin(plugin, options?)` подключает плагин к одной модели. Это декоратор класса, и его ставят рядом с `@Schema`. Настройки передаются вторым аргументом; тип второго аргумента определяется плагином.

```ts twoslash
import { Entity, Plugin, Prop, Schema, type SchemaPlugin } from "@venloc/typemo";
const audit: SchemaPlugin = {
  name: "audit-log",
  apply: (builder) => {
    builder.addHook("pre", "query.find", function () {
      console.log("чтение товаров");
    });
  },
};
// ---cut---
@Plugin(audit)
@Schema({ collection: "products" })
export class Product extends Entity {
  @Prop(() => String, { required: true })
  title!: string;
}
```

Несколько `@Plugin` на одном классе применяются в порядке сверху вниз. Запуск: класс с `@Plugin(tools)`, `@Plugin(both)`, `@Plugin(stamp)` и `@Plugin(softly)` в таком порядке скомпилировался со списком плагинов `["conn", "both", "tools", "stamp", "softly"]`, где `conn` и `both` пришли с уровня подключения (см. [порядок применения](#порядок-применения)).

<Params>
<Param name="plugin" type="SchemaPlugin<O>" required>

Плагин.

</Param>
<Param name="options" type="O">

Настройки плагина. Обязательны, если тип `O` не допускает `undefined`.

</Param>
</Params>

<FullType>

```ts
const Plugin: <O>(
  plugin: SchemaPlugin<O>,
  ...options: undefined extends O ? [options?: O] : [options: O]
) => <C extends EntityClass>(target: C) => void;
```

</FullType>

Плагин на уровне подключения регистрируют через `connection.plugins.use(plugin, options)` (см. [`connection.plugins`](../connection/connection.mdx#connectionplugins)), на уровне процесса через [`Typemo.plugin`](../connection/typemo.mdx#typemoplugin). Как выбирать уровень, описано в руководстве [Несколько клиентов и расширения](../../connection/clients-and-extensions.mdx#как-выбрать-уровень).

### Порядок применения

Плагины применяются в определённом порядке: глобальные, затем плагины подключения, затем плагины модели (`@Plugin`), внутри уровня в порядке регистрации. Один и тот же плагин, подключённый на нескольких уровнях с одинаковыми настройками, применяется один раз, на месте первого появления. Хуки плагинов выполняются **после** хуков самого класса. Запуск: плагин подключения `conn`, тот же `both` на уровне подключения и модели дали порядок `conn`, `both`, а не `both` дважды.

### Ошибки

Один плагин с разными настройками на двух уровнях или два разных плагина с одним именем — `ConfigurationError`, причём текст называет обе стороны (получен запуском):

```text
ConfigurationError: Widget: plugin "stamp" is registered twice (connection and model) with different options
ConfigurationError: Widget: two different plugins are named "both"
```

### Когда `@Plugin` не подходит

Чтобы плагин применялся ко всем моделям приложения, используйте [`Typemo.plugin`](../connection/typemo.mdx#typemoplugin), а ко всем моделям одной базы — `connection.plugins.use`: тогда его не нужно вешать на каждый класс.

## PluginBuilder

`PluginBuilder` — то, что плагин получает в `apply`: узкий интерфейс изменения схемы, которую компилируют. Всё остальное во внутреннем устройстве схемы плагину недоступно.

```ts twoslash
import { type SchemaPlugin } from "@venloc/typemo";
// ---cut---
export const slugged: SchemaPlugin = {
  name: "slugged",
  apply: (builder) => {
    console.log(builder.target.name, builder.fieldKeys);
    // → Product [ "_id", "title" ]
    builder.addField("slug", () => String);
    builder.addIndex({ slug: 1 });
  },
};
```

Запуск: плагин, подключённый к модели с полями `_id`, `title`, вывел `Product [ "_id", "title" ]`.

`addStatic` и `enablePolicy` доступны только плагинам: обычные декораторы классов их не имеют. Запуск: вызов этих методов у построителя, созданного для обычного класса, даёт ошибку `statics are added by plugins` и `enablePolicy is for plugins`.

<FullType>

```ts
interface PluginBuilder {
  readonly target: ClassRef;
  readonly fieldKeys: readonly string[];
  addField(key: string, type: () => unknown, options?: Readonly<Record<string, unknown>>): void;
  addIndex(fields: IndexFields, options?: IndexOptions): void;
  addHook(phase: HookPhase, events: HookEvent | readonly HookEvent[], fn: HookFunction): void;
  addVirtual(key: string, options: VirtualOptions): void;
  addStatic(name: string, fn: StaticFunction): void;
  enablePolicy<K extends keyof PluginPolicies>(policy: K, options: NonNullable<PluginPolicies[K]>): void;
}
```

</FullType>

### Хуки плагина

Функция хука объявляется с `this: unknown` и приводит `this` сама, потому что построитель не знает, для какого события какой `this`. Для события запроса это контекст операции, для события документа — документ. Запуск: хук `pre` на `query.find`, добавленный плагином, сработал после хуков класса.

### Политики плагина

`enablePolicy` включает политику так же, как `@Schema`. Запуск: плагин с `enablePolicy("softDelete", true)` сделал `deleteOne` мягким: `countDocuments()` после него дало 0, а в коллекции документ остался (1). Если политику уже задал `@Schema` с другими опциями, а плагин включает её иначе, это `ConfigurationError` с текстом `declared by @Schema and enabled by plugin "other"`.

### Когда построитель не подходит

Изменять сами операции построитель не может: для этого есть [`.modify`](./operation-context.mdx#modify) в хуке. Читать схему целиком плагину тоже не нужно: для чтения есть [`SchemaInfo`](../schemas/schema-info.mdx).

## PluginPolicies

`PluginPolicies` — политики, которые плагин может включить через [`enablePolicy`](#pluginbuilder): `tenant`, `softDelete` и `audit`. Значение каждого — `true` или объект опций, такой же, как в `@Schema`. Подробнее об опциях — в справочнике [Опции политик в схеме](../policies/schema-options.mdx).

<FullType>

```ts
interface PluginPolicies {
  readonly tenant?: true | TenantSchemaOptions;
  readonly softDelete?: true | SoftDeleteSchemaOptions;
  readonly audit?: true | AuditSchemaOptions;
}
```

</FullType>

## StaticFunction

`StaticFunction` — тип функции для [`addStatic`](#pluginbuilder): любая функция, у которой `this` не проверяется на этом уровне. Точный тип статических методов задаёт объект [`statics`](#schemaplugin) плагина.

<FullType>

```ts
type StaticFunction = (this: never, ...args: never[]) => unknown;
```

</FullType>

## PluginStatics

`PluginStatics<P>` — тип статических методов плагина `P` так, как их видит модель. Методы привязаны к модели во время работы, поэтому параметр `this` из типа убирается: иначе метод с `this: Model<Product>` нельзя было бы вызвать на модели с другими параметрами типа.

```ts twoslash
import { Entity, Prop, Schema, type PluginStatics, type Model, type SchemaPlugin } from "@venloc/typemo";
@Schema({ collection: "products" })
class Product extends Entity {
  @Prop(() => String, { required: true }) title!: string;
}
// ---cut---
const statics = {
  async byTitle(this: Model<Product>, title: string): Promise<number> {
    return this.countDocuments({ title });
  },
};
const tools: SchemaPlugin<undefined, typeof statics> = { name: "tools", apply: () => {}, statics };

type Bound = PluginStatics<typeof tools>;
//   ^?
```

<FullType>

```ts
type PluginStatics<P> = P extends { readonly statics?: infer S }
  ? { readonly [K in keyof Exclude<S, undefined>]: OmitThisParameter<Exclude<S, undefined>[K]> }
  : never;
```

</FullType>

## Model.statics

`model.statics(plugin)` возвращает ту же модель, типизированную статическими методами плагина: `Products.statics(tools).byTitle("w")`. Чтобы тип не обещал метод, которого нет во время работы, Typemo проверяет, что плагин применён к схеме этой модели.

```ts twoslash
import { Entity, Plugin, Prop, Schema, TypemoClient, type Model, type SchemaPlugin } from "@venloc/typemo";
const statics = {
  async byTitle(this: Model<Product>, title: string): Promise<number> {
    return this.countDocuments({ title });
  },
};
const tools: SchemaPlugin<undefined, typeof statics> = { name: "tools", apply: () => {}, statics };

@Plugin(tools)
@Schema({ collection: "products" })
class Product extends Entity {
  @Prop(() => String, { required: true })
  title!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Products = client.db().model(Product);
// ---cut---
const count = await Products.statics(tools).byTitle("w");
//    ^?
```

Запуск: после вставки товара `w` вызов вернул `1`. Методы, добавленные через `addStatic`, существуют во время работы, но в типе не видны: они вызываются с приведением типа.

<Params>
<Param name="plugin" type="SchemaPlugin<never, object>" required>

Плагин, статические методы которого нужны.

</Param>
</Params>

<Returns type="this & PluginStatics<P>">

Та же модель с типом, дополненным статическими методами плагина.

</Returns>

Ошибка при плагине, который к модели не применён (текст получен запуском):

```text
ConfigurationError: Account: plugin "tools" is not applied to this model's schema
```

Статический метод, чьё имя совпадает с членом модели, при создании модели даёт `ConfigurationError`, а не тихо затеняет метод (получен запуском):

```text
ConfigurationError: Clash: the plugin static "find" would shadow a member of the model
```

## PluginRegistry

`PluginRegistry` — упорядоченный список регистраций плагинов одного уровня. Он живёт на объекте подключения: `connection.plugins`, — и глобально; глобальный реестр вы не видите, вы пользуетесь [`Typemo.plugin`](../connection/typemo.mdx#typemoplugin). Тип экспортируется без конструктора для типизации.

```ts twoslash
import { TypemoClient, type SchemaPlugin } from "@venloc/typemo";
const audit: SchemaPlugin = { name: "audit-log", apply: () => {} };
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
client.db().plugins.use(audit);
console.log(client.db().plugins.list.map((entry) => `${entry.level}:${entry.plugin.name}`));
// → ["connection:audit-log"]
```

Запись реестра — `PluginUse`: `plugin`, `options` и `level`.

### Реестр закрывается первой моделью

Реестр закрывается первой **успешно** скомпилированной схемой: реестр базы — первой моделью этой базы, глобальный реестр — первой моделью на любом клиенте. Схема, которая не скомпилировалась, реестр не закрывает. Плагин, зарегистрированный позже, не применился бы к уже готовым схемам, и приложение получило бы модели, часть из которых плагин не видит. Поэтому Typemo бросает ошибку (получен запуском):

```text
ConfigurationError: plugin "late": the connection plugins are fixed once a schema is compiled (Widget was); register plugins before the first model
```

Для глобального реестра то же самое с текстом `the global plugins are fixed once a schema is compiled`. Расширения закрываются по тому же правилу: об этом — в руководстве [Несколько клиентов и расширения](../../connection/clients-and-extensions.mdx#регистрировать-до-первой-модели).

<FullType>

```ts
class PluginRegistry {
  readonly level: Exclude<PluginLevel, "model">;
  use<O>(plugin: SchemaPlugin<O>, ...options: OptionsArgs<O>): this;
  get list(): readonly PluginUse[];
}

interface PluginUse {
  readonly plugin: SchemaPlugin<unknown>;
  readonly options: unknown;
  readonly level: PluginLevel;
}
```

</FullType>

## PluginLevel

`PluginLevel` — уровень, на котором зарегистрирован плагин: `"global"` (`Typemo.plugin`), `"connection"` (`connection.plugins.use`) или `"model"` (`@Plugin`). Значение стоит в поле `level` записей `PluginUse`.

<FullType>

```ts
type PluginLevel = "global" | "connection" | "model";
```

</FullType>
