Здесь собраны все способы начать **конвейер** (pipeline) — цепочку **стадий**, через которую MongoDB пропускает документы. Здесь же методы запроса агрегации, то есть то, что вы получаете из [`Model.aggregate`](#model.aggregate) и что можно к нему добавить. Агрегации всей базы (`Pipeline.database`, `Pipeline.admin`, `Pipeline.sessions`) выполняют [`connection.aggregate`](../connection/connection.mdx#connection.aggregate) и [`client.aggregate`](../connection/typemo-client.mdx#client.aggregate). Их запрос такой же, как у `Model.aggregate`. Сами стадии описаны в справочнике [Стадии](./stages.mdx), выражения внутри стадий — на страницах `expr-*`.

Если вы только начинаете, прочитайте сначала руководство [Первая агрегация](../../aggregation/first-aggregation.mdx). Эта страница — справочник, сюда возвращаются за деталью.

Во всех примерах одна модель — заказ магазина. В ней есть обязательные поля, поле `BigInt` (после агрегации оно покажет разницу между видами результата), индекс по `status` (для подсказки `hint`) и скрытое поле `internalNote`.

```ts twoslash title="models/order.ts"
import { Entity, type Hidden, Index, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "orders" })
@Index({ status: 1 })
export class Order extends Entity {
  @Prop(() => String, { required: true })
  customer!: string;

  @Prop(() => String, { required: true })
  status!: string;

  @Prop(() => Number, { required: true })
  total!: number;

  @Prop(() => BigInt)
  points?: bigint;

  @Prop(() => String, { hidden: true })
  internalNote?: Hidden<string>;
}
```

В коллекции три заказа. Alice, `paid`, 120, 10 баллов, заметка `vip`. Bob, `open`, 40, 5 баллов. Alice, `paid`, 60, 7 баллов. Результаты в комментариях `// →` получены на этих данных. Идентификаторы в них сокращены до `"…"`, потому что база выдаёт их заново при каждой загрузке данных.

Строитель конвейера неизменяемый. Каждая стадия возвращает новый строитель, а прежний остаётся как был. Ошибки в форме полей ловит компилятор, а типы строк вычисляются по стадиям — после `group` строка уже не заказ, а группа. О строителе и его стадиях читайте в [Стадиях](./stages.mdx).

## Pipeline.from [#pipeline.from]

`Pipeline.from` начинает конвейер над коллекцией модели. Так агрегацию строят заранее, отдельно от запроса. Вы получаете строитель, добавляете стадии и в конце вызываете [`.plan()`](#pipeline-builder.plan) — выходит готовый план для [`Model.aggregate`](#model.aggregate). Обычно `Pipeline.from` вызывают не сами. `Model.aggregate((p) => …)` делает это за вас и передаёт колбэку такой строитель.

Строки конвейера начинаются как сохранённые документы модели, но **без скрытых полей** ([`Hidden`](../../schemas/hidden-and-sensitive.mdx)). Конвейер, молча читающий скрытое поле, выдал бы пароль или заметку в отчёт, поэтому Typemo убирает такие поля первой стадией. Нужное скрытое поле оставьте, назвав его в `options.include`.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const paid = Pipeline.from(Order).match({ status: "paid" }).sort({ total: -1 }).plan();
console.log(paid.pipeline);
// → [{ $match: { status: "paid" } }, { $sort: { total: -1 } }]
const rows = await Orders.aggregate(paid);
console.log(rows.map((row) => row.total));
// → [120, 60]
```

<Returns type="PipelineBuilder<…, &quot;collection&quot;, &quot;empty&quot;>">

Пустой строитель над сохранёнными документами источника. Пока в нём нет ни одной стадии, у него нет [`.plan()`](#pipeline-builder.plan). Пустой конвейер компилятор не пропустит.

</Returns>

<Params>
<Param name="source" type="EntityClass | Model" required>

Класс сущности или модель. Источник задаёт типы полей и коллекцию, из которой читает конвейер.

</Param>
<Param name="options.hint" type="string | { [path]: 1 | -1 | &quot;text&quot; | … }">

Индекс, который должен использовать сервер. Укажите имя (`"status_1"`) или спецификацию ключей (`{ status: 1 }`). Пути проверяет компилятор, а `Pipeline.from` ещё и во время работы сверяет, что такой индекс объявлен в схеме.

</Param>
<Param name="options.collation" type="CollationOptions">

Правило сортировки строк для всей агрегации.

</Param>
<Param name="options.allowDiskUse" type="boolean">

Позволяет стадиям писать временные файлы на диск, когда не хватает памяти.

</Param>
<Param name="options.comment" type="string">

Комментарий к команде. Он виден в журнале сервера и в профилировщике. То же делает [`.comment`](#comment) запроса.

</Param>
<Param name="options.batchSize" type="number">

Сколько документов курсор получает за один обмен с сервером. То же делает [`.batchSize`](#batch-size) запроса.

</Param>
<Param name="options.bypassDocumentValidation" type="boolean">

Не проверять документы правилами валидации коллекции, когда стадии `$out` и `$merge` пишут в неё.

</Param>
<Param name="options.include" type="readonly HiddenPath[]">

Пути скрытых полей, которые нужно оставить в строках. Компилятор принимает только пути с пометкой `Hidden` и добавляет их в тип строки.

</Param>
</Params>

```ts

```

</FullType>

### Скрытые поля [#hidden-fields]

Без `include` скрытого поля в строках нет ни в типе, ни в данных. С `include` оно появляется и там, и там.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const plan = Pipeline.from(Order, { include: ["internalNote"] })
  .match({ customer: "Alice" })
  .sort({ total: -1 })
  .limit(1)
  .plan();
const [row] = await Orders.aggregate(plan);
//     ^?
console.log(row?.internalNote);
// → "vip"
```

Тот же запрос без `include` вернул бы эту строку без ключа `internalNote`. Через `Orders.aggregate((p) => …)` скрытое поле не включить, у колбэка нет `options`. Если оно нужно, соберите план через `Pipeline.from(…, { include })` и передайте его в `aggregate`.

### Подсказка индекса [#index-hint]

`hint` сверяется со схемой в момент вызова `Pipeline.from`, а не когда запрос дойдёт до базы. Если схема такого индекса не объявляет, ошибка приходит сразу.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
// @errors: 2353
Pipeline.from(Order, { hint: { nope: 1 } });
```

Путь, которого нет в модели, останавливает компилятор. Если путь есть, а индекса под него нет (`total` не индексирован), останавливает Typemo.

```text
ConfigurationError: Order: hint {"total":1} matches no declared index (declared: _id_, status_1)
```

Без этой проверки `hint` отверг бы сервер, и только при выполнении. Ошибка пришла бы из базы, а не из места, где вы её написали.

## Pipeline.database [#pipeline.database]

`Pipeline.database` начинает конвейер, который читает не коллекцию, а всю базу. Он нужен агрегациям без собственных документов. Стадия [`documents`](./stages.mdx#documents) выдаёт литеральные документы, а [`listLocalSessions`](./stages.mdx#list-local-sessions) и [`listClusterCatalog`](./stages.mdx#list-cluster-catalog) читают служебные данные сервера.

У такого плана нет модели, и [`Model.aggregate`](#model.aggregate) его не принимает. Его выполняют [`connection.aggregate`](../connection/connection.mdx#connection.aggregate) (база этого подключения) и [`client.aggregate`](../connection/typemo-client.mdx#client.aggregate) (база клиента по умолчанию). Это обычная операция Typemo — с транзакциями, `timeoutMS`, ошибками Typemo, курсором и `explain`, но без хуков. Примеры ищите в руководстве [Запросы уровня базы](../../aggregation/database-level.mdx).

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const plan = Pipeline.database()
  .documents([{ n: 1 }, { n: 2 }])
  .plan();
console.log(plan.target, plan.pipeline);
// → { kind: "database", admin: false } [{ $documents: [{ n: 1 }, { n: 2 }] }]
const rows = await client.aggregate(plan);
//    ^?
console.log(rows);
// → [{ n: 1 }, { n: 2 }]
```

<Returns type="PipelineBuilder<never, &quot;database&quot;, &quot;empty&quot;>">

Пустой строитель, не привязанный к коллекции. Строка начинается как `never`, а типы строк задают стадии.

</Returns>

<Params>
<Param name="options" type="AggregateOptions<never>">

Те же настройки, что у [`Pipeline.from`](#pipeline.from) — `collation`, `allowDiskUse`, `comment`, `batchSize`, `bypassDocumentValidation`. Они уходят в команду как есть. `hint` и `include` здесь не имеют смысла, потому что у плана нет схемы, по которой их можно проверить.

</Param>
</Params>

<FullType>

```ts
static database(options?: AggregateOptions<never>): PipelineBuilder<never, "database", "empty">
```

</FullType>

База, в которой выполнится план, зависит от того, чем его запустили. `connection.aggregate` берёт базу своего подключения, `client.aggregate` — базу клиента по умолчанию. Отдайте такой план в `Model.aggregate`, и вы получите ошибку вместо чтения чужой базы. Текст ошибки получен запуском.

```text
ConfigurationError: Order.aggregate: the plan reads a database, not this model's collection "orders"; run it with connection.aggregate(plan) or client.aggregate(plan)
```

Служебные стадии привязаны к месту запуска, и компилятор это проверяет. [`documents`](./stages.mdx#documents) и [`listClusterCatalog`](./stages.mdx#list-cluster-catalog) доступны и в `Pipeline.database()`, и в `Pipeline.admin()`. [`currentOp`](./stages.mdx#current-op) есть только в `Pipeline.admin()`, а [`listSessions`](./stages.mdx#list-sessions) — только в `Pipeline.sessions()`.

## Pipeline.admin [#pipeline.admin]

`Pipeline.admin` — то же, что [`Pipeline.database`](#pipeline.database), но для базы `admin`. Здесь живут служебные стадии, которые сервер разрешает только там. Это [`currentOp`](./stages.mdx#current-op) (что выполняется прямо сейчас), [`queryStats`](./stages.mdx#query-stats), [`querySettings`](./stages.mdx#query-settings), [`listSampledQueries`](./stages.mdx#list-sampled-queries) и [`shardedDataDistribution`](./stages.mdx#sharded-data-distribution).

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const plan = Pipeline.admin().currentOp({ idleConnections: false }).limit(1).plan();
console.log(plan.target, plan.pipeline);
// → { kind: "database", admin: true } [{ $currentOp: { idleConnections: false } }, { $limit: 1 }]
const operations = await client.aggregate(plan);
console.log(operations.length);
// → 1
```

<Returns type="PipelineBuilder<never, &quot;admin&quot;, &quot;empty&quot;>">

Пустой строитель базы `admin`. В плане `target.admin` равен `true`, поэтому `connection.aggregate` и `client.aggregate` знают, куда отправить конвейер. План `admin` выполняется в `admin`, с какого бы подключения вы его ни запустили.

</Returns>

<Params>
<Param name="options" type="AggregateOptions<never>">

Те же настройки, что у [`Pipeline.database`](#pipeline.database).

</Param>
</Params>

<FullType>

```ts
static admin(options?: AggregateOptions<never>): PipelineBuilder<never, "admin", "empty">
```

</FullType>

Подробнее о служебных агрегациях — в руководстве [Служебные агрегации](../../aggregation/system.mdx).

## Pipeline.sessions [#pipeline.sessions]

`Pipeline.sessions` начинает конвейер над коллекцией `config.system.sessions`. Только там сервер принимает стадию [`listSessions`](./stages.mdx#list-sessions). Над любой другой коллекцией он отвечает `$listSessions may only be run against config.system.sessions`.

Поэтому `listSessions` есть только у `Pipeline.sessions()`, а у `Pipeline.from`, `Model.aggregate`, `Pipeline.database()` и `Pipeline.admin()` её нет. Компилятор не даёт поставить стадию туда, где сервер всё равно её отвергнет. После неё доступны обычные стадии (`match`, `project`, `sort`, `group`).

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const plan = Pipeline.sessions().listSessions({ allUsers: true }).plan();
console.log(plan.target, plan.pipeline);
// → { kind: "sessions" } [{ $listSessions: { allUsers: true } }]
const sessions = await client.aggregate(plan);
//    ^?
```

План выполняют `client.aggregate` и `connection.aggregate`. Он всегда идёт в `config.system.sessions`, с какого бы подключения вы его ни запустили. В событиях операции `collection` равен `"system.sessions"`, а `database` — `"config"`.

<Returns type="PipelineBuilder<never, &quot;sessions&quot;, &quot;empty&quot;>">

Пустой строитель, привязанный к `config.system.sessions`. План только для чтения, у него нет [`out`](./stages.mdx#out) и [`merge`](./stages.mdx#merge).

</Returns>

<Params>
<Param name="options" type="AggregateOptions<never>">

Те же настройки, что у [`Pipeline.database`](#pipeline.database).

</Param>
</Params>

<FullType>

```ts
static sessions(options?: AggregateOptions<never>): PipelineBuilder<never, "sessions", "empty">
```

</FullType>

Поставьте `listSessions` не туда или добавьте запись, и компилятор остановит вас сразу. Сообщения получены компилятором.

```ts twoslash
// @errors: 2684 2769
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
Orders.aggregate((p) => p.listSessions());
Pipeline.sessions().listSessions().out("copy");
```

Сервер записывает свежие сессии в `config.system.sessions` не сразу, поэтому на только что запущенном сервере результат пуст. Сессии, которые известны одному узлу и ещё не записаны, показывает стадия [`listLocalSessions`](./stages.mdx#list-local-sessions) в `Pipeline.database()`.

## Pipeline.update [#pipeline.update]

`Pipeline.update` собирает **конвейер обновления**. Это стадии, которые `updateOne` и `updateMany` принимают вместо обычного документа с операторами. С ним поле вычисляется из других полей самого документа — удвоить сумму, склеить имя из двух частей. Обычный оператор вроде `$set` так не умеет.

В этом режиме у строителя всего шесть стадий — [`addFields`](./stages.mdx#add-fields), [`set`](./stages.mdx#set), [`project`](./stages.mdx#project), [`unset`](./stages.mdx#unset), [`replaceRoot`](./stages.mdx#replace-root) и [`replaceWith`](./stages.mdx#replace-with). Других методов у него нет, поэтому компилятор не даст добавить `group` туда, где сервер его всё равно отвергнет.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const stages = Pipeline.update(Order)
  .set((f) => ({ total: fn.multiply(f.total, 2) }))
  .unset("points")
  .build();
console.log(stages);
// → [{ $set: { total: { $multiply: ["$total", 2] } } }, { $unset: "points" }]
```

<Returns type="PipelineBuilder<StoredDocOf<Src>, &quot;update&quot;, &quot;empty&quot;>">

Пустой строитель в режиме обновления. Результат берите через [`.build()`](#pipeline-builder.build), а не `.plan()`. Это не агрегация, а список стадий для команды обновления.

</Returns>

<Params>
<Param name="source" type="EntityClass | Model" required>

Сущность, документ которой обновляет конвейер. Нужна только ради типа, строки — это её сохранённые документы.

</Param>
</Params>

<FullType>

```ts
static update<const Src extends SourceInput>(_source: Src): PipelineBuilder<StoredDocOf<Src>, "update", "empty">
```

</FullType>

Такой конвейер принимают [`updateOne`](../writes/writes.mdx#update-one) и [`updateMany`](../writes/writes.mdx#update-many) модели.

Перед отправкой Typemo проверяет конвейер по схеме модели. Обновление остановится с ошибкой Typemo, если конвейер делает `unset` обязательного поля, ставит константу не того типа, теряет неизменяемое поле или пуст. Например, `unset("title")` у модели с обязательным `title` даёт `ValidationError: Validation failed: "title": update.0.$unset: the field is required; the pipeline would remove it [required]`, а пустой конвейер — `QueryError: an update pipeline needs at least one stage`. Все проверки описаны в справочнике [Конвейеры обновления](../writes/pipeline-updates.mdx#update-pipelines).

## Pipeline.view [#pipeline.view]

`Pipeline.view` собирает **определение представления** (view) — конвейер, сохранённый на сервере над другой коллекцией и читаемый как обычная коллекция. Представление хранит не данные, а способ их получить.

Обычно `Pipeline.view` напрямую не вызывают, это делает [`TypedView.define`](../collections/typed-view.mdx#typed-view.define). Метод пригодится, когда вы создаёте представление сами и хотите получить проверенное определение.

Конвейер проверяется по классу представления. Строки должны содержать все поля класса с совместимыми типами, а если поле пропало или у него не тот тип, компилятор назовёт его. В режиме представления у строителя нет [`out`](./stages.mdx#out) и [`merge`](./stages.mdx#merge), потому что представление писать не может.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
@Schema({ collection: "paid_orders" })
class PaidOrder extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => Number, { required: true }) total!: number;
}

const definition = Pipeline.view(PaidOrder, {
  on: Order,
  pipeline: (p) => p.match({ status: "paid" }).project({ customer: 1, total: 1 }),
});
console.log(definition);
// → { viewOn: "orders", pipeline: [{ $match: { status: "paid" } }, { $project: { customer: 1, total: 1 } }] }
```

<Returns type="ViewDefinition">

Замороженный объект с двумя полями. `viewOn` — имя коллекции-источника, `pipeline` — массив сериализованных стадий. Объект можно передать в команду `create` драйвера. Саму коллекцию-представление этот метод не создаёт.

</Returns>

<Params>
<Param name="view" type="EntityClass" required>

Класс строки представления. Нужен для проверки типов, во время работы не используется.

</Param>
<Param name="definition.on" type="EntityClass | Model" required>

Источник — коллекция или другое представление, которое читает конвейер.

</Param>
<Param name="definition.pipeline" type="(p) => ViewPipelineCheck<R, View>" required>

Колбэк получает пустой строитель в режиме представления и возвращает конвейер хотя бы с одной стадией. Если строки конвейера не подходят классу, колбэк вернёт не конвейер, а описание проблемы. Это делает [`ViewPipelineCheck`](#view-pipeline-check), и компилятор останавливает вызов.

</Param>
</Params>

<FullType>

```ts
static view<View extends abstract new () => object, const Src extends SourceInput, R extends StagedPipeline>(
  _view: View,
  definition: {
    readonly on: Src;
    readonly pipeline: (p: PipelineBuilder<DocOf<Src>, "view", "empty">) => ViewPipelineCheck<R, InstanceType<View>>;
  },
): ViewDefinition
```

</FullType>

`ViewDefinition` — публичный тип с полями `viewOn: string` и `pipeline: readonly PipelineStage[]`.

### Конвейер не подходит классу представления [#pipeline-class-mismatch]

Класс представления описывает строки, которые вы будете читать, поэтому конвейер обязан отдавать все его поля с совместимыми типами. Ошибаются обычно тремя способами. В строках теряется поле класса, поле становится другого типа или пропадает `_id`. Текст каждой ошибки получен компилятором.

```ts twoslash
// @errors: 2741 2741 2741
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
@Schema({ collection: "paid_orders" })
class PaidOrder extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => Number, { required: true }) total!: number;
}
// ---cut---
Pipeline.view(PaidOrder, { on: Order, pipeline: (p) => p.project({ customer: 1, total: 1, _id: 0 }) });
Pipeline.view(PaidOrder, { on: Order, pipeline: (p) => p.project({ customer: 1 }) });
Pipeline.view(PaidOrder, { on: Order, pipeline: (p) => p.project((f) => ({ customer: 1, total: fn.toString_(f.total) })) });
```

Первая строка потеряла `_id` (класс получил его от `Entity`), вторая — `total`, третья сделала `total` строкой. Компилятор на каждую отвечает одинаково — `Property 'error' is missing in type 'PipelineBuilder<…>' but required in type 'PathError<…>'`. Причина записана в самом `PathError` — `the pipeline result does not match the fields of the view class: check the field "_id"` (во второй и третьей строках поле называется `"total"`).

Записать результат в представлении нельзя вообще. У строителя в режиме представления нет `out` и `merge`, поэтому `p.out("copy")` не скомпилируется, а колбэк, вернувший запись, получит причину `a view pipeline cannot end with $out or $merge (MongoDB does not allow them in a view)`.

## ViewPipelineCheck [#view-pipeline-check]

`ViewPipelineCheck<R, V>` — тип, по которому [`Pipeline.view`](#pipeline.view) решает, что вернуть из колбэка конвейера. Если строки конвейера `R` подходят классу `V`, тип равен самому `R` и ничего не меняется. Иначе он равен `PathError` с текстом причины, и компилятор печатает этот текст вместо длинного пересечения типа конвейера с типом ошибки. Читать сам тип не нужно. Он нужен, чтобы в ошибке вы видели «check the field "_id"», а не простыню вывода типов.

Тип проверяет два условия. Конвейер не должен заканчиваться записью, потому что `$out` и `$merge` в представлении сервер запрещает. И каждое поле класса должно быть в строках конвейера с совместимым типом. `_id` обязателен, если класс его объявляет (его даёт `Entity`), и необязателен, если не объявляет.

<FullType>

```ts
type ViewPipelineCheck<R, V> = [ViewRowProblems<ViewRowsOf<R>, V>] extends [never]
  ? R
  : PathError<"…">
```

</FullType>

Цель записи тоже сверяется с полями строки. Для [`out`](./stages.mdx#out) и [`merge`](./stages.mdx#merge) в модель-цель действует такая же проверка полей.

## Pipeline.watch [#pipeline.watch]

`Pipeline.watch` собирает конвейер для **подписки на изменения** (change stream). Строки такого конвейера — события драйвера (`ChangeStreamDocument`), а не документы модели. Поэтому события можно фильтровать и переписывать, а группировать нельзя.

Доступны только [`match`](./stages.mdx#match), [`project`](./stages.mdx#project), [`addFields`](./stages.mdx#add-fields), [`set`](./stages.mdx#set), [`unset`](./stages.mdx#unset), [`replaceRoot`](./stages.mdx#replace-root), [`replaceWith`](./stages.mdx#replace-with) и [`redact`](./stages.mdx#redact). Самой последней можно поставить [`changeStreamSplitLargeEvent`](./stages.mdx#change-stream-split-large-event).

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const stages = Pipeline.watch(Order).match({ operationType: "insert" }).build();
console.log(stages);
// → [{ $match: { operationType: "insert" } }]
```

<Returns type="PipelineBuilder<ChangeStreamDocument<…>, &quot;watch&quot;, &quot;empty&quot;>">

Пустой строитель в режиме подписки. Строки — события изменений документов источника.

</Returns>

<Params>
<Param name="source" type="EntityClass | Model" required>

Сущность, коллекцию которой слушает подписка.

</Param>
</Params>

<FullType>

```ts
static watch<const Src extends SourceInput>(
  source: Src,
): PipelineBuilder<ChangeStreamDocument<…>, "watch", "empty">
```

</FullType>

Подписку открывает [`Model.watch`](../change-streams/watch.mdx), а не этот метод. Он только готовит стадии. Для стадии `$changeStream` внутри обычной агрегации есть [`changeStream`](./stages.mdx#change-stream).

## PipelineBuilder.plan [#pipeline-builder.plan]

`.plan()` завершает конвейер верхнего уровня и возвращает **план агрегации** (`AggregatePlan`) — замороженный объект с источником, стадиями и опциями. Его принимают [`Model.aggregate`](#model.aggregate), [`connection.aggregate`](../connection/connection.mdx#connection.aggregate) и [`client.aggregate`](../connection/typemo-client.mdx#client.aggregate).

Метод есть только у строителя, в котором уже есть стадия, и только у тех, что запускаются отдельной агрегацией, — `Pipeline.from`, `Pipeline.database`, `Pipeline.admin` и `Pipeline.sessions`. План не знает ни модели, ни параметров запуска (`session`, `timeoutMS`), поэтому запускается на любой модели своей коллекции. Чем он отличается от плана, который отдаёт сам запрос, объясняет раздел [Две формы плана](#plan-forms).

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const plan = Pipeline.from(Order).match({ status: "paid" }).plan();
console.log(plan.op, plan.target.kind, plan.pipeline, plan.options);
// → aggregate collection [{ $match: { status: "paid" } }] {}
```

<Returns type="AggregatePlan<Row>">

Замороженный план с полями `op` (всегда `"aggregate"`), `target` (откуда читает конвейер), `pipeline` (стадии) и `options` (`hint`, `collation`, `allowDiskUse`, `comment`, `batchSize`, `bypassDocumentValidation`, `include` из `Pipeline.from(…, options)`). `target` бывает трёх видов — `{ kind: "collection", collection, entity, discriminator }`, `{ kind: "database", admin }` и `{ kind: "sessions" }`. Тип строки (`Row`) живёт только в типе, во время работы его нет.

</Returns>

<FullType>

```ts
interface AggregatePlan<Row> {
  readonly op: "aggregate";
  readonly target: PipelineTarget;
  readonly pipeline: readonly PipelineStage[];
  readonly options: AggregateOptions<unknown>;
}
```

</FullType>

Пустой конвейер компилятор не пропустит. Если строитель пришёл из нетипизированного кода, ошибку бросит сам Typemo.

```text
ConfigurationError: an empty pipeline does not run: add a stage
```

Сервер тоже отверг бы пустую агрегацию, но текст Typemo называет причину и лечение.

## Model.aggregate [#model.aggregate]

`Model.aggregate` запускает агрегацию над коллекцией модели. Он пропускает документы через конвейер и возвращает строки результата. Это самый частый путь. Для отчётов по заказам, сумм, группировок и соединений коллекций вы пишете колбэк, а Typemo передаёт ему строитель над сохранёнными документами.

Как и [`find`](../query/reading.mdx#model.find), метод сразу в базу не ходит. Он возвращает **запрос агрегации** (`AggregateQuery`), который уходит на сервер при `await`. К запросу можно добавить опции, а результат получить массивом, курсором, планом сервера или проверенным по схеме.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const byStatus = await Orders.aggregate((p) =>
  p.group((f) => ({ _id: f.status, revenue: fn.sum(f.total), orders: fn.count() })).sort({ _id: 1 }),
);
console.log(byStatus);
// → [{ _id: "open", revenue: 40, orders: 1 }, { _id: "paid", revenue: 180, orders: 2 }]
```

<Returns type="AggregateQuery<Row>">

Запрос агрегации. После `await` вы получаете массив строк, а тип строки компилятор вычисляет по стадиям. Запрос неизменяемый — каждый метод (`.plain()`, `.session()`, …) возвращает новый запрос, а старый не меняется.

</Returns>

<Params>
<Param name="build" type="(p) => StagedPipeline | TerminalPipeline | AggregatePlan" required>

Колбэк, который получает пустой строитель над сохранёнными документами модели, или готовый план из [`Pipeline.from`](#pipeline.from). В конвейере должна быть хотя бы одна стадия. Стадии [`out`](./stages.mdx#out) и [`merge`](./stages.mdx#merge) завершают конвейер и превращают запрос в запись, строк у такого запроса нет.

</Param>
<Param name="options.session" type="ClientSession | null">

Явная сессия. `null` выполняет запрос вне текущей транзакции. То же делает [`.session`](#session).

</Param>
<Param name="options.timeoutMS" type="number">

Ограничение времени на стороне клиента в миллисекундах. То же делает [`.timeoutMS`](#timeout-ms).

</Param>
<Param name="options.policy" type="PolicyValues">

Значения политик для этой агрегации — тенант, актор, режим мягкого удаления. То же делает [`.policy`](#policy).

</Param>
</Params>

<FullType>

```ts
aggregate<B extends AggregateResult>(
  build: AggregateBuild<T, B>,
  options?: ModelAggregateOptions,
): AggregateQuery<AggregateRows<B>>;
aggregate<R>(plan: AggregatePlan<R>, options?: ModelAggregateOptions): AggregateQuery<R>;
```

</FullType>

### Строки без схемы [#rows-without-schema]

Сохранённые документы модели проходят через схему, а строки агрегации нет. У результата `group` или `project` нет класса, по которому его можно собрать. Поэтому значения остаются такими, как их вернул драйвер — идентификатор это `ObjectId`, а поле `points` — `bigint`. Как отдать их клиенту, показывает [`.plain()`](#plain).

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const [row] = await Orders.aggregate((p) => p.match({ customer: "Bob" }));
console.log(row?._id.constructor.name, typeof row?.points);
// → ObjectId bigint
```

### Один запрос — одно выполнение [#one-query-one-run]

Запрос на чтение выполняется один раз на объект. Повторный `await` того же запроса отдаёт те же строки и в базу не ходит. Чтобы выполнить его ещё раз, вызовите [`.exec({ force: true })`](#exec).

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const query = Orders.aggregate((p) => p.limit(1));
const first = await query;
const second = await query;
console.log(first === second);
// → true
```

### Чужая коллекция [#foreign-collection]

План собирается над одной коллекцией. Отдайте модели план другой коллекции, и ошибка придёт сразу при вызове, ещё до обращения к базе. Политики модели относятся к её коллекции и чужие данные не прикроют. Для плана другой коллекции, плана базы и плана сессий тексты разные, они получены запуском.

```text
ConfigurationError: Order.aggregate: the plan reads "other", not this model's collection "orders"
ConfigurationError: Order.aggregate: the plan reads a database, not this model's collection "orders"; run it with connection.aggregate(plan) or client.aggregate(plan)
ConfigurationError: Order.aggregate: the plan reads config.system.sessions, not this model's collection "orders"; run it with connection.aggregate(plan) or client.aggregate(plan)
```

Планы базы и сессий выполняют [`connection.aggregate`](../connection/connection.mdx#connection.aggregate) и [`client.aggregate`](../connection/typemo-client.mdx#client.aggregate). Если первый аргумент не колбэк и не план, метод бросает `QueryError`.

```text
QueryError: aggregate: a pipeline callback or an aggregation plan
```

### Транзакции и политики [#transactions-and-policies]

Внутри [`transaction`](../transactions/transactions.mdx#transaction) запрос автоматически выполняется в сессии транзакции.

<Callout type="migration">

В Mongoose у `Model.aggregate` нет типов строк, результат всегда `any[]`, а скрытые (`select: false`) поля попадают в конвейер как есть. В Typemo тип строки вычисляется по стадиям, а скрытые поля убирает первая стадия.

</Callout>

## .plain [#plain]

`.plain()` превращает строки в обычные объекты, которые безопасно сериализовать в JSON и отдать клиенту. Идентификаторы, `bigint`, `Decimal128` и `UUID` становятся строками, `Date` и `RegExp` остаются, двоичные данные становятся `Uint8Array`, вектор — массивом чисел.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const [row] = await Orders.aggregate((p) => p.match({ customer: "Bob" })).plain();
//     ^?
console.log(typeof row?._id, typeof row?.points);
// → string string
```

У запроса агрегации нет `.lean()`, и он не нужен. Строки агрегации никогда не бывают документами модели, это всегда данные как их отдал драйвер. Второй вид результата один — `.plain()`.

<Returns type="AggregateQuery<PlainValue<Row>>">

Новый запрос с тем же конвейером. Строки — результат `.plain()`, а тип строки — `PlainValue` от прежнего. Повторный `.plain()` возвращает тот же запрос, дважды строки не преобразуются. После него доступны [`.parse`](#parse), [`.expect`](#expect) и [`.cursor`](#cursor).

</Returns>

<FullType>

```ts
plain(): AggregateQuery<PlainValue<Row>>
```

</FullType>

У строки нет схемы, поэтому сохранённое поле `Map` в ней — обычный объект, и `.plain()` оставляет его объектом. Превратить его в `Map` может только схема. О видах результата читайте в концепции [Чтение и типы результата](../../concepts/reading-types.mdx).

## .cursor [#cursor]

`.cursor()` отдаёт строки по одной, по мере чтения из базы, а не собирает весь результат в массив. Он нужен для больших отчётов и выгрузок — в памяти одна строка, а не весь результат.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const seen: number[] = [];
for await (const row of Orders.aggregate((p) => p.sort({ total: 1 })).batchSize(1).cursor()) {
  seen.push(row.total);
}
console.log(seen);
// → [40, 60, 120]
```

<Returns type="QueryCursor<Row>">

Курсор строк. Его методы описаны в справочнике [Курсор](../query/cursor.mdx). Если на запросе были [`.plain()`](#plain), [`.parse`](#parse) или [`.mask`](#mask), курсор применяет их к каждой строке в момент чтения.

</Returns>

<FullType>

```ts
cursor(): QueryCursor<Row>
```

</FullType>

## .exec [#exec]

`.exec()` выполняет запрос и возвращает промис строк. Это то же, что `await query`, только с настройкой — запрос можно выполнить ещё раз принудительно.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const query = Orders.aggregate((p) => p.limit(1));
const first = await query;
const again = await query.exec({ force: true });
console.log(first === again, again.length);
// → false 1
```

<Returns type="Promise<Row[]>">

Строки результата. Обычное чтение выполняется один раз на объект, потом отдаёт кешированный результат.

</Returns>

<Params>
<Param name="options.force" type="boolean">

`true` выполняет запрос заново, даже если он уже выполнялся.

</Param>
</Params>

<FullType>

```ts
exec(options?: ExecOptions): Promise<Row[]>
```

</FullType>

### Запись через агрегацию [#write-via-aggregation]

Агрегация, которая кончается на [`out`](./stages.mdx#out) или [`merge`](./stages.mdx#merge), — это запись, и Typemo обращается с ней иначе. Второй `await` того же запроса запись не повторяет, а бросает ошибку. Молчаливая повторная запись стёрла бы или задвоила результат.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const write = Orders.aggregate((p) => p.match({ status: "paid" }).out("paid_orders"));
await write;
await write.exec();
```

```text
QueryError: aggregate: this operation was already executed; build a new one, or run it again deliberately with exec({ force: true }) (a write runs once per builder)
```

Если вы действительно хотите записать ещё раз, скажите это явно — `write.exec({ force: true })`. Ошибка называет `aggregate`, то есть метод, который вы вызвали.

## .explain [#explain]

`.explain()` спрашивает у сервера **план запроса** — какие индексы он выберет и сколько документов просмотрит. Строк вы при этом не получаете. Метод нужен, когда агрегация медленная и надо понять почему.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const plan = await Orders.aggregate((p) => p.match({ status: "paid" })).explain("executionStats");
console.log(Object.keys(plan));
// → ["explainVersion", "queryPlanner", "executionStats", "queryShapeHash", "command", …]
```

<Returns type="Promise<ExplainResult>">

Ответ сервера. Ключи `queryPlanner`, `executionStats` и `serverInfo` в нём всегда, а `executionStats` — при уровне подробности не ниже `"executionStats"`.

</Returns>

<Params>
<Param name="verbosity" type="&quot;queryPlanner&quot; | &quot;executionStats&quot; | &quot;allPlansExecution&quot;" default="&quot;queryPlanner&quot;">

Насколько подробен ответ. `queryPlanner` показывает выбранный план, `executionStats` выполняет запрос и добавляет счётчики, `allPlansExecution` показывает и отвергнутые планы. Другое значение (его можно передать только в обход типов) даёт `QueryError` до обращения к базе.

</Param>
</Params>

<FullType>

```ts
explain(verbosity?: ExplainVerbosity): Promise<ExplainResult>
```

</FullType>

Такой же метод есть у запросов чтения — [`.explain`](../query/search-and-explain.mdx#explain).

## .parse [#parse]

`.parse(schema)` проверяет каждую строку результата по **Standard Schema**. Это общий интерфейс проверки, его реализуют zod, valibot, arktype и схемы моделей Typemo (`~standard`). Строками результата становится то, что вернула схема. Метод нужен на границе с внешним миром. Сервер может вернуть неожиданное, и `parse` остановит это раньше, чем строки уйдут дальше.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
import type { StandardSchemaV1 } from "@venloc/typemo";
// ---cut---
const rowSchema: StandardSchemaV1<unknown, { status: string; orders: number }> = {
  "~standard": {
    version: 1,
    vendor: "example",
    validate: (row) => {
      const value = row as { _id: string; orders: number };
      return typeof value.orders === "number"
        ? { value: { status: value._id, orders: value.orders } }
        : { issues: [{ message: "orders must be a number", path: ["orders"] }] };
    },
  },
};
const rows = await Orders.aggregate((p) =>
  p.group((f) => ({ _id: f.status, orders: fn.count() })).sort({ _id: 1 }),
).parse(rowSchema);
console.log(rows);
// → [{ status: "open", orders: 1 }, { status: "paid", orders: 2 }]
```

<Returns type="ParsedQuery<Output[]>">

Запрос, который отдаёт проверенные строки, то есть выход схемы. Асинхронные схемы он дожидается. Набор методов у `.parse` тот же, что описан в [`.parse`](../query/contracts.mdx#parse) запроса чтения. `.cursor()` проверяет строки по мере чтения.

</Returns>

<Params>
<Param name="schema" type="StandardSchema" required>

Любой объект со свойством `~standard`.

</Param>
</Params>

<FullType>

```ts
parse<Sch extends AnyStandardSchema>(
  schema: Sch,
): ParsedQuery<StandardSchemaOutput<Sch>[], StandardSchemaOutput<Sch>, true>
```

</FullType>

Если строка не подходит, вы получаете `ValidationError`, а путь в нём начинается с номера строки.

```text
ValidationError: Validation failed: "0.orders": row 0: nope [schema]; "1.orders": row 1: nope [schema]
```

Обе строки названы в одном сообщении, потому что проверяются все строки, а не только первая.

## .expect [#expect]

`.expect<Shape>()` проверяет **контракт** результата при компиляции. Строка должна быть в точности той формы, которую вы ждёте. Во время работы метод ничего не делает и ничего не стоит. Он нужен, когда результат уходит потребителю с фиксированной формой, например в ответ API или отчёт. Конвейер изменится, и компилятор скажет, что форма разошлась.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const report = Orders.aggregate((p) =>
  p.group((f) => ({ _id: f.status, revenue: fn.sum(f.total) })),
).expect<{ _id: string; revenue: number }>();
```

<Returns type="AggregateQuery<Row>">

Тот же запрос. Если форма строки совпала не точно, компилятор сообщит, чего не хватает (`missing`), что лишнее (`extra`) и что другого типа (`mismatch`). О контрактах читайте в справочнике [`.expect`](../query/contracts.mdx#expect).

</Returns>

<FullType>

```ts
expect<Shape>(this: AggregateQuery<Row> & ExpectRows<Row, Shape>): AggregateQuery<Row>
```

</FullType>

## .mask [#mask]

`.mask(spec)` скрывает значения в строках результата, прежде чем их увидит вызывающий код — e-mail, номер карты, любые пути строки. Ключи — пути **итоговой** строки конвейера. Значение — `"mask"` (заменить на `"?"`) или функция маски из [`Mask`](../query/masks.mdx#mask-presets).

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p.group((f) => ({ _id: f.customer, revenue: fn.sum(f.total) })).sort({ revenue: 1 }),
).mask({ _id: "mask" });
console.log(rows);
// → [{ _id: "?", revenue: 40 }, { _id: "?", revenue: 180 }]
```

<Returns type="MaskedQuery<…>">

Запрос, который отдаёт замаскированные строки. Хуки, события и аудит видят настоящие строки. `.cursor()` маскирует каждую строку при чтении.

</Returns>

<Params>
<Param name="spec" type="{ [path]: &quot;mask&quot; | MaskFunction }" required>

Пути итоговой строки. Предустановки `"sensitive"` для агрегации нет, маскируются только перечисленные пути. Скрыть поле совсем — задача [`project`](./stages.mdx#project) или [`unset`](./stages.mdx#unset).

</Param>
</Params>

<FullType>

```ts
mask<const Sp extends object>(
  spec: Sp & MaskSpecCheck<Row, Sp>,
): MaskedQuery<ApplyMask<Row, Sp>[], ApplyMask<Row, Sp>, true>
```

</FullType>

Путь, которого нет в итоговой строке, останавливает агрегацию. Маска, которая ничего не скрыла бы, была бы тихой дырой в защите. Текст ошибки получен запуском.

```text
StrictModeError: mask: "nope" matched nothing in the rows of Order's aggregation, so nothing would be masked there; name a field of the final rows [unknown-path]
```

Все маски и их пресеты описаны в справочнике [Маски ответа](../query/masks.mdx#mask).

</Param>
</Params>

## .batchSize [#batch-size]

`.batchSize(n)` задаёт, сколько строк курсор получает от сервера за один обмен. Чем меньше размер, тем меньше памяти уходит на пачку и тем больше обменов. Метод нужен вместе с [`.cursor()`](#cursor) на больших выгрузках.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const query = Orders.aggregate((p) => p.sort({ total: 1 })).batchSize(100);
```

<Returns type="AggregateQuery<Row>">

Новый запрос. Значение должно быть положительным целым, а ноль, отрицательное и нецелое число дают `QueryError`. Ноль отвергается намеренно. Драйвер читает `0` как «по умолчанию сервера», и случайный ноль молча отменил бы ваш размер пачки.

</Returns>

<Params>
<Param name="n" type="number" required>

Размер пачки, положительное целое число.

</Param>
</Params>

```text
QueryError: batchSize must be a positive integer, got -1 (number)
QueryError: batchSize must be a positive integer, got 0 (number) (the driver reads 0 as "the server default"; leave batchSize out for the default)
```

У запросов чтения `.batchSize` есть только у `find` — [`.batchSize`](../query/options.mdx#batch-size).

## .readPreference [#read-preference]

## .readConcern [#read-concern]

`.readConcern(level)` задаёт уровень изоляции чтения, то есть что сервер вправе показать. Например, только данные, подтверждённые большинством (`"majority"`). Метод нужен, когда отчёт не должен видеть данные, которые потом откатятся.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const query = Orders.aggregate((p) => p.limit(1)).readConcern("majority");
```

<Returns type="AggregateQuery<Row>">

Новый запрос с выбранным уровнем.

</Returns>

<Params>
<Param name="level" type="ReadConcernLevel" required>

Уровень драйвера — `"local"`, `"available"`, `"majority"`, `"linearizable"`, `"snapshot"`.

</Param>
</Params>

Внутри транзакции действуют настройки самой транзакции, поэтому уровень чтения там даёт ошибку.

```text

```

Подробности — в [`.readConcern` запроса чтения](../query/options.mdx#read-concern).

## .build [#build]

`.build()` у запроса агрегации отдаёт **план выполнения** (`AggregateExecutionPlan`) — конвейер, опции и сущность, которые уйдут в операцию. Он нужен для отладки. Вы смотрите, во что превратился ваш колбэк и какие параметры запуска добавили к нему вызовы запроса. Подробнее — в разделе [Две формы плана](#plan-forms).

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const plan = Orders.aggregate((p) => p.match({ status: "paid" })).timeoutMS(500).build();
console.log(plan.entity.name, plan.pipeline, plan.options.timeoutMS);
// → Order [{ $match: { status: "paid" } }] 500
```

<Returns type="AggregateExecutionPlan">

Замороженный план выполнения. Это не то же, что [`PipelineBuilder.plan`](#pipeline-builder.plan). У плана выполнения есть сущность и параметры запуска, а у плана строителя только источник и стадии.

</Returns>

## Две формы плана [#plan-forms]

В агрегации «планом» называют два разных объекта. Они похожи, но получаются по-разному и нужны для разного, так что их легко перепутать.

**`AggregatePlan`** — план конвейера. Его возвращает [`.plan()`](#pipeline-builder.plan) строителя. В нём источник (`target`), стадии и опции конвейера, а модели и параметров запуска нет. Поэтому план можно собрать в одном модуле и запустить где угодно. План коллекции идёт на модель той же коллекции через [`Model.aggregate`](#model.aggregate), план базы или сессий — через [`connection.aggregate`](../connection/connection.mdx#connection.aggregate) и [`client.aggregate`](../connection/typemo-client.mdx#client.aggregate).

**`AggregateExecutionPlan`** — план выполнения. Его возвращает [`.build()`](#build) запроса, когда конвейер уже привязан к модели. В нём сущность модели (`entity`), стадии (`pipeline`), опции конвейера (`aggregateOptions`) и параметры этого запуска (`options` — `session`, `timeoutMS`, `policy`, `comment`, `batchSize`…). Именно его выполняет конвейер операций. Тип экспортирован, чтобы функция могла принять и вернуть такой план, но руками его собирают редко.

```ts twoslash
import { Entity, type Hidden, fn, Index, Pipeline, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "orders" })
@Index({ status: 1 })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => String, { hidden: true }) internalNote?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Orders = client.db().model(Order);
// ---cut---
const plan = Pipeline.from(Order).match({ status: "paid" }).plan();
console.log(Object.keys(plan));
// → ["op", "target", "pipeline", "options"]

const execution = Orders.aggregate(plan).timeoutMS(500).build();
//    ^?
console.log(Object.keys(execution));
// → ["op", "entity", "pipeline", "aggregateOptions", "options"]
```

Стадии в обоих планах одни и те же, различаются обёртка и добавленное к ним. У `AggregatePlan` есть `target`, у `AggregateExecutionPlan` вместо него `entity`. Опции конвейера (`hint`, `collation`, `allowDiskUse`…) в первом лежат в `options`, а во втором в `aggregateOptions`, потому что `options` занято параметрами запуска. Обратной дороги нет. `AggregateExecutionPlan` в `aggregate` не передать, он принимает только `AggregatePlan`.

<FullType>

```ts
interface AggregatePlan<Row> {
  readonly op: "aggregate";
  readonly target: PipelineTarget;
  readonly pipeline: readonly PipelineStage[];
  readonly options: AggregateOptions<unknown>;
}

interface AggregateExecutionPlan {
  readonly op: "aggregate";
  readonly entity: EntityClass;
  readonly pipeline: readonly PipelineStage[];
  readonly aggregateOptions: AggregateOptions<unknown>;
  readonly options: PlanOptions;
}
```

</FullType>

Какой план нужен, подскажет вопрос — вы описываете конвейер или смотрите, что будет выполнено? Описываете — берите `AggregatePlan` из `.plan()`. Отлаживаете или пишете тест на параметры, ушедшие в операцию, — смотрите `AggregateExecutionPlan` из `.build()`. Для плана базы (`connection.aggregate`) `entity` — служебный класс с именем вызванного метода (`connection` или `client`), потому что у такой агрегации нет модели.

## Когда не подходит [#when-not-to-use]

Нужны документы модели с методами и виртуальными полями, а не строки-отчёты? Берите [`find`](../query/reading.mdx#model.find), агрегация документов не возвращает. Для простого подсчёта или списка уникальных значений есть [`countDocuments`](../query/reading.mdx#model.count-documents) и [`distinct`](../query/reading.mdx#model.distinct), они проще и конвейера не требуют.

Для результата, который хранится постоянно, смотрите [`TypedView.define`](../collections/typed-view.mdx#typed-view.define) (представление, которое считается при каждом чтении) и [материализованные представления](../collections/materialized.mdx) (результат записан в коллекцию).
