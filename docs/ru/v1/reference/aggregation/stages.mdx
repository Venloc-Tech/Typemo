Здесь описаны все стадии строителя конвейера — методы объекта, который вы получаете в [`Model.aggregate((p) => …)`](./pipeline.mdx#modelaggregate) или из [`Pipeline.from`](./pipeline.mdx#pipelinefrom). **Стадия** (stage) — один шаг **конвейера**: она берёт строки предыдущего шага и отдаёт новые. Имя метода совпадает с именем стадии MongoDB без `$`: `match` — это `$match`.

Если вы только начинаете, сначала прочитайте руководство [Первая агрегация](../../aggregation/first-aggregation.mdx). Эта страница — справочник.

Главное отличие Typemo от голого драйвера: после каждой стадии компилятор пересчитывает **тип строки**. После `group` строка — уже не заказ, а группа с полями, которые вы назвали. Поэтому следующая стадия видит только настоящие поля, а опечатка в имени поля остановит компилятор. Значения внутри стадий (`fn.sum(f.total)`) пишутся колбэком `(f) => …`, где `f` — прокси полей, а `fn` — каталог операторов; про них — руководство [Выражения](../../aggregation/expressions.mdx).

Все примеры используют модель магазина: покупатели и заказы со строками-товарами.

```ts twoslash title="models/order.ts"
import { ObjectId } from "mongodb";
import { Entity, Prop, type Ref, Schema } from "@venloc/typemo";

@Schema({ collection: "customers" })
export class Customer extends Entity {
  @Prop(() => String, { required: true })
  name!: string;

  @Prop(() => String, { required: true })
  city!: string;

  @Prop(() => ObjectId, { ref: () => Customer })
  referrer?: Ref<Customer>;
}

@Schema()
export class Item {
  @Prop(() => String, { required: true })
  sku!: string;

  @Prop(() => Number, { required: true })
  qty!: number;

  @Prop(() => Number, { required: true })
  price!: number;
}

@Schema({ collection: "orders" })
export class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true })
  customer!: Ref<Customer>;

  @Prop(() => String, { required: true })
  status!: string;

  @Prop(() => Number, { required: true })
  total!: number;

  @Prop(() => Date, { required: true })
  placedAt!: Date;

  @Prop(() => [Item])
  items!: Item[];

  @Prop(() => String)
  note?: string;
}
```

Покупатели: Alice (Oslo), Bob (Paris), Carol (Oslo, её пригласила Alice). Заказов четыре: Alice, `paid`, 120, 5 января, товары `pen`×2 и `book`; Bob, `open`, 40, 20 января, `pen`×4; Alice, `paid`, 60, 3 февраля, `ink`×3, заметка `gift`; Bob, `paid`, 30, 14 февраля, без товаров. Результаты в комментариях `// →` получены на этих данных. В результатах опущены поля `_id`, если они не важны.

Стадии, которые читают служебные данные сервера (`collStats`, `currentOp` и другие), и стадии Atlas (`search`, `vectorSearch`) описаны в конце: они работают только на первом месте конвейера и не во всех режимах. Если у модели есть [скрытые поля](../../schemas/hidden-and-sensitive.mdx#скрытое-поле-в-агрегации), [`Model.aggregate`](./pipeline.mdx#modelaggregate) убирает их стадией `$unset` в начале конвейера, а после такой первой стадии (`search`, `searchMeta`, `vectorSearch`, `geoNear`, `collStats`, `indexStats` и других) — сразу за ней: стадия остаётся первой, как требует сервер. Служебные стадии базы и сервера (`documents`, `currentOp`, `listLocalSessions`, `listSessions` и другие) строятся в [`Pipeline.database`](./pipeline.mdx#pipelinedatabase), [`Pipeline.admin`](./pipeline.mdx#pipelineadmin) и [`Pipeline.sessions`](./pipeline.mdx#pipelinesessions) и выполняются через [`client.aggregate`](../connection/typemo-client.mdx#clientaggregate).

## match

`match` оставляет только строки, которые подходят под условие. Это самая частая стадия: чем раньше она стоит, тем меньше строк сервер тащит через остальной конвейер и тем лучше он использует индексы.

Условие пишется как фильтр [`find`](../query/reading.mdx#modelfind) или колбэком с булевым выражением: во втором случае Typemo отправляет его как `$expr`.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p.match({ status: "paid", total: { $gte: 50 } }).project({ total: 1, _id: 0 }),
);
console.log(rows);
// → [{ total: 120 }, { total: 60 }]
```

Сырой объект с `$expr` запрещён. Условие, которое сравнивает два поля строки, пишется колбэком:


Возвращает строитель с теми же строками. Работает в любом режиме, кроме конвейера обновления. Третья форма принимает готовый фильтр сущности (`const filter: Filter<Order>`), пока строки ещё имеют сохранённый вид.

## sort

`sort` упорядочивает строки. Ключи — пути текущей строки, направления — `1`/`-1` или слова `"ascending"`/`"descending"`; ключ можно заменить оценкой текстового поиска `{ $meta: "textScore" }`.

## limit

`limit` пропускает первые `n` строк и отбрасывает остальные. `n` — целое не меньше 1: в MongoDB ноль означает «без ограничения», и опечатка превратила бы «ничего» в «всё», поэтому Typemo отказывается.

```ts twoslash
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
```

## skip

`skip` пропускает первые `n` строк. `n` — целое не меньше 0. Вместе с `limit` даёт страницы, но на больших смещениях сервер всё равно читает пропущенное, поэтому для длинных списков лучше [пагинация по ключу](../query/keyset.mdx).

## count

`count` заменяет все строки одной: `{ [поле]: число }`. Если строк на входе не было, на выходе тоже нет ни одной, а не `0`. Для подсчёта по группам используйте [`group`](#group) с `fn.count()`.


## redact

`redact` решает по условию, оставить документ целиком, отбросить его или пойти глубже во вложенные документы. Условие — колбэк, который возвращает `Vars.KEEP`, `Vars.PRUNE` или `Vars.DESCEND`, обычно через `fn.cond`. Нужен для построчной безопасности внутри документа: убрать вложенные блоки, которые пользователю видеть нельзя.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p.redact((f) => fn.cond(fn.gte(f.total, 50), Vars.KEEP, Vars.PRUNE)).project({ total: 1, _id: 0 }),
);
console.log(rows);
// → [{ total: 120 }, { total: 60 }]
```

## addFields

`addFields` добавляет поля или заменяет существующие, остальные оставляет. Значения — выражения над полями строки. Ключ с точкой пишет внутрь вложенного документа, а `fn.remove()` удаляет поле.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p
    .match({ status: "paid" })
    .addFields((f) => ({ withTax: fn.multiply(f.total, 1.2) }))
    .project({ total: 1, withTax: 1, _id: 0 }),
);
console.log(rows);
// → [{ total: 120, withTax: 144 }, { total: 60, withTax: 72 }, { total: 30, withTax: 36 }]
```

Тип строки после стадии — прежний плюс новые поля. Опечатка в имени поля внутри выражения остановит компилятор.

## set

`set` — второе имя [`addFields`](#addfields): принимает и делает то же самое. В конвейере обновления ([`Pipeline.update`](./pipeline.mdx#pipelineupdate)) обычно пишут `set`, в отчётах — `addFields`.


## project

`project` оставляет только названные поля или вычисляет новые. Значение `1` или `true` оставляет поле, `0` или `false` — убирает, выражение — вычисляет. Смешивать «оставить» и «убрать» нельзя, кроме `_id`: компилятор остановит, а сервер такую проекцию отверг бы.

```ts twoslash

  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
```

Вторая форма принимает объект с путями без колбэка: `p.project({ status: 1, total: 1 })`. Пустая проекция — `ConfigurationError: $project needs at least one field`.

В [конвейере обновления](./pipeline.mdx#pipelineupdate) `project` переписывает документ целиком, и на модели с неизменяемыми полями (`immutable`, а также `createdAt` у `Timestamped`) Typemo пропускает его только тогда, когда включающая проекция называет каждое неизменяемое поле (а исключающая их не трогает). Иначе обновление останавливается до отправки, а в тексте названы потерянные поля. Подробно — в руководстве [Обновление через конвейер](../../writes/pipeline-updates.mdx#заменить-документ-целиком-стадией).

## replaceWith

`replaceWith` — короткая запись [`replaceRoot`](#replaceroot): принимает сам новый корень, без обёртки `newRoot`. В [конвейере обновления](./pipeline.mdx#pipelineupdate) эта стадия, как и `replaceRoot` и `project`, заменяет документ целиком: на модели с неизменяемыми полями новый корень обязан перенести каждое такое поле как есть (`createdAt: f.createdAt`, весь корень через `fn.mergeObjects(f, …)`), иначе Typemo бросит `StrictModeError` с причиной `immutable` до отправки. ## group

`group` собирает строки в группы по ключу `_id` и считает по каждой группе **аккумуляторы** — операторы вроде `fn.sum`, `fn.avg`, `fn.count`. Это главная стадия отчётов: выручка по статусам, число заказов на клиента.

`_id` — выражение, `null` (одна группа на все строки) или составной объект. Любое другое поле обязано быть аккумулятором: обычное выражение в этом месте компилятор не пропустит, потому что сервер тоже его отверг бы. Все аккумуляторы перечислены в справочнике [Аккумуляторы](./accumulators.mdx). Обратное тоже верно: операторы, которые работают только как аккумуляторы (`fn.push`, `fn.addToSet`, `fn.count`, `fn.top` и другие), разрешены только в `group`, `bucket`, `bucketAuto` (в их `output`) и `setWindowFields`, а в `project` или `addFields` не скомпилируются. Операторы с двойной ролью (`fn.sum`, `fn.avg`, `fn.min`, `fn.max`) там остаются обычными выражениями над массивом внутри документа: [как это работает](./accumulators.mdx#как-работают-аккумуляторы).

## bucket

`bucket` раскладывает строки по интервалам заданных границ. `_id` группы — нижняя граница интервала, а строки вне границ уходят в группу `default`. Нужен для гистограмм: заказы до 50, от 50 до 100.

## setWindowFields

`setWindowFields` считает новое поле по **окну** соседних строк, не схлопывая строки в группы: бегущая сумма, место в рейтинге, разница с предыдущей. `partitionBy` делит строки на независимые части, `sortBy` задаёт порядок, `output` описывает поля через `withWindow`.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p
    .setWindowFields({
      partitionBy: (f) => f.status,
      sortBy: { placedAt: 1 },
      output: (f) => ({
        running: withWindow(fn.sum(f.total), { documents: ["unbounded", "current"] }),
      }),
    })
    .project({ status: 1, total: 1, running: 1, _id: 0 })
    .sort({ status: 1, running: 1 }),
);
console.log(rows.slice(1));
// → [{ status: "paid", total: 120, running: 120 }, { status: "paid", total: 60, running: 180 }, { status: "paid", total: 30, running: 210 }]
```

Функции, которым нужен порядок (`fn.rank()`, `fn.shift`, ограниченные окна), требуют `sortBy`: без него они не компилируются. Ранги и `fn.linearFill` (`fn.rank`, `fn.denseRank`, `fn.documentNumber`, `fn.linearFill`) требуют `sortBy` ровно из одного поля: с двумя компилятор остановит вызов, назвав поле результата и правило. Оконные операторы — справочник [Оконные операторы](./window-operators.mdx). Руководство — [Оконные функции](../../aggregation/windows.mdx).

## densify

`densify` заполняет пропуски в ряду чисел или дат: добавляет строки с недостающими значениями поля. Нужен для графиков, где месяц без заказов должен быть виден как ноль, а не пропасть.

```ts twoslash
  @Prop(() => String) note?: string;
```

## lookup

`lookup` присоединяет к каждой строке документы другой коллекции. Результат — массив в поле `as`, даже если найден один документ или ни одного. Это аналог соединения из реляционных баз.

Первая форма — по равенству полей: `localField` этой строки и `foreignField` присоединяемой. Тип присоединённых документов берётся из `from`.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p
    .match({ status: "open" })
    .lookup({ from: Customer, localField: "customer", foreignField: "_id", as: "buyer" })
    .project({ total: 1, "buyer.name": 1, _id: 0 }),
);
console.log(rows);
// → [{ total: 40, buyer: [{ name: "Bob" }] }]
```

Присоединённые документы проходят политики класса из `from`, как при обычном чтении через его модель. Мягко удалённые документы не присоединяются, поля `Hidden` убираются, а из тенантской коллекции присоединяются только документы тенанта операции; без тенанта Typemo бросает `StrictModeError` с правилом `tenant` до обращения к серверу. Создавать модель этого класса на подключении не нужно: схему Typemo компилирует сам.

Вторая форма — с **вложенным конвейером**: присоединяемые документы проходят свои стадии. Переменные (`let`) передают значения строки внутрь: колбэк конвейера получает их вторым аргументом.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Customers.aggregate((p) =>
  p
    .lookup({
      from: Order,
      as: "paid",
      let: (f) => ({ id: f._id }),
      pipeline: (q, v) =>
        q.match((o) => fn.and(fn.eq(o.customer, v.id), fn.eq(o.status, "paid"))).count("n"),
    })
    .project({ name: 1, paid: 1, _id: 0 })
    .sort({ name: 1 }),
);
console.log(rows);
// → [{ name: "Alice", paid: [{ n: 2 }] }, { name: "Bob", paid: [{ n: 1 }] }, { name: "Carol", paid: [] }]
```

Третья форма — без `from`: вложенный конвейер сам создаёт документы стадией [`documents`](#documents). Вложенный конвейер должен иметь хотя бы одну стадию, иначе `ConfigurationError`. Имя переменной должно быть допустимым, иначе тоже ошибка. Ключ `as` с точкой пишет в поле вложенного документа. Подробнее — руководство [Соединения](../../aggregation/joins.mdx).

## graphLookup

`graphLookup` рекурсивно идёт по связям внутри одной коллекции: цепочка приглашений, дерево комментариев, подчинённые сотрудника. `startWith` — откуда начать, `connectFromField` и `connectToField` — как перейти к следующему документу.

```ts twoslash
import { ObjectId } from "mongodb";

  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;

const Orders = client.db().model(Order);

  p
    .match({ name: "Carol" })
    .graphLookup({
      from: Customer,

      connectFromField: "referrer",
      connectToField: "_id",
```

Найденные документы проходят политики класса из `from` так же, как у [`lookup`](#lookup): мягкое удаление, тенант и поля `Hidden`. С `depthField` каждый найденный документ получает глубину (int64). `maxDepth` ограничивает глубину: целое не меньше 0. `restrictSearchWithMatch` — фильтр по найденным документам.

## unionWith

`unionWith` дописывает к строкам строки другой коллекции. Тип строки после неё — объединение: `T | Joined`, потому что строки бывают двух видов. Нужна для общего списка из двух источников.

```ts twoslash

@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;

  @Prop(() => String) note?: string;
```

Три формы: только коллекция (`unionWith(Customer)`), коллекция с вложенным конвейером (`{ coll, pipeline }`) и конвейер без коллекции, который создаёт документы сам (как выше). Дописанные строки проходят политики класса, названного коллекцией, так же, как у [`lookup`](#lookup): мягкое удаление, тенант и поля `Hidden`, и модель этого класса создавать не нужно.

## facet

`facet` запускает несколько конвейеров над одними и теми же строками и возвращает **одну** строку, в которой у каждой ветки свой массив. Нужна, чтобы получить сразу несколько отчётов за один проход по данным: список и итоги по статусам.

```ts twoslash
import { ObjectId } from "mongodb";

@Schema({ collection: "customers" })

}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
```

## geoNear

`geoNear` ищет документы рядом с точкой и добавляет расстояние. Это всегда первая стадия конвейера (или вложенного конвейера `lookup`); в `facet` её нельзя. Ей нужен геопространственный индекс `2dsphere` на поле.

## search

`search` — полнотекстовый поиск Atlas Search. Стадия работает только в Atlas (или в локальной установке Atlas CLI) и только первой в конвейере. Спецификация проверяется по типам: `index`, оператор (`text`, `phrase`, `compound`, …), `highlight`, `count`, `sort`.

## rankFusion

```ts twoslash
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
```

## out

`out` записывает результат конвейера в коллекцию, полностью заменяя её содержимое. Это последняя стадия: после неё стадий добавить нельзя, а результат `await` — пустой массив, потому что строк нет. Агрегация с `out` считается записью: второй `await` того же запроса — ошибка, см. [`.exec`](./pipeline.mdx#exec).

Если целью служит сущность, компилятор сверяет строки с её полями: не хватает поля или тип не тот — ошибка на месте вызова, а не порченые данные в коллекции. Сообщение называет цель и поле: `PathError<"the pipeline rows do not match the target model: check the field \"revenue\"">`. Когда ключ группы становится `_id` результата, у цели должен быть `_id` того же типа. Для этого её описывают через [`EntityWithId`](../schemas/base-classes.mdx#entitywithid): обычный класс с `_id!: string` тоже принимается, но тип `_id` у него не проверяется ни в `findById`, ни в ссылках, и `_id` остаётся изменяемым.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, EntityWithId, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
@Schema({ collection: "status_totals" })
class StatusTotal extends EntityWithId(() => String) { // [!code highlight]
  @Prop(() => Number, { required: true }) revenue!: number;
  @Prop(() => Number, { required: true }) orders!: number;
}

await Orders.aggregate((p) =>
  p.group((f) => ({ _id: f.status, revenue: fn.sum(f.total), orders: fn.count() })).out(StatusTotal),
);
const StatusTotals = client.db().model(StatusTotal);
console.log(await StatusTotals.find().sort({ _id: 1 }).lean());
// → [{ _id: "open", revenue: 40, orders: 1 }, { _id: "paid", revenue: 210, orders: 3 }]
```

Цель можно назвать строкой (`out("paid_orders")` — коллекция этой же базы) или объектом `{ db, coll }`: оба поля обязательны, и объект без `db` или без `coll` Typemo отвергает сразу, при построении, ошибкой `ConfigurationError` `$out: a target object needs both "db" and "coll" as non-empty strings (got coll); to write into an entity, pass the class` (в скобках — ключи объекта), а не текстом сервера. В объекте можно задать `timeseries` (`timeField`, `metaField`, `granularity`). Строки для имени не проверяются. Запись в тенантскую коллекцию, названную сущностью или моделью на подключении, Typemo отвергает с `StrictModeError` (правило `tenant`), если у операции нет `allTenants: true`: такая запись смешала бы тенантов. Руководство — [Сохранить результат](../../aggregation/output.mdx).

## merge

`merge` записывает результат в коллекцию, не стирая её: совпавшие документы обновляются, новые добавляются. Последняя стадия. Нужна для постепенного накопления отчётов.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, EntityWithId, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
@Schema({ collection: "status_totals" })
class StatusTotal extends EntityWithId(() => String) {
  @Prop(() => Number, { required: true }) revenue!: number;
  @Prop(() => Number, { required: true }) orders!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const StatusTotals = client.db().model(StatusTotal);
const accumulate = () =>
  Orders.aggregate((p) =>
    p
      .group((f) => ({ _id: f.status, revenue: fn.sum(f.total), orders: fn.count() }))
      .merge({
        into: StatusTotal,
        on: "_id",
        whenMatched: (q, v) => q.set((f) => ({ revenue: fn.add(f.revenue, v.new.revenue), orders: fn.add(f.orders, v.new.orders) })),
        whenNotMatched: "insert",
      }),
  );
await accumulate();
await accumulate();
console.log(await StatusTotals.find().sort({ _id: 1 }).lean());
// → [{ _id: "open", revenue: 80, orders: 2 }, { _id: "paid", revenue: 420, orders: 6 }]
```

`into` — сущность или `{ db, coll }` (`db` можно опустить: тогда база самой агрегации; объект без `coll` — `ConfigurationError` `$merge: a target object needs "coll" (and "db" when given) as non-empty strings (got db); to write into an entity, pass the class`); `on` — поле или поля совпадения (на них нужен уникальный индекс); `whenMatched` — `"replace"`, `"keepExisting"`, `"merge"`, `"fail"` или конвейер обновления, где новая строка доступна как `v.new`; `whenNotMatched` — `"insert"`, `"discard"`, `"fail"`. Переменные `let` доступны в конвейере `whenMatched`. Строки, не подходящие классу `into`, компилятор отвергает так же, как у `out`: `PathError<"the pipeline rows do not match the target model: check the field …">`. Запись в тенантскую коллекцию отвергается так же, как у [`out`](#out).

<Callout type="warning" title="Полный пересчёт со сложением удваивает итоги">

Пример выше запускает конвейер дважды на тех же данных, и итоги **удвоились**: `paid` — 420 вместо 210, `open` — 80 вместо 40. `whenMatched` с `fn.add` прибавляет новую строку к уже записанной, а конвейер каждый раз пересчитывает все заказы. Ошибки нет: так устроен сервер, `merge` не знает, что строка уже учтена, и Typemo этого тоже не видит. Сложение подходит только тогда, когда `match` отбирает лишь новые документы. Для полного пересчёта берите `whenMatched: "replace"`: повторный запуск даёт тот же итог.

</Callout>
