На этой странице все стадии строителя конвейера. Это методы объекта, который вы получаете в [`Model.aggregate((p) => …)`](./pipeline.mdx#model.aggregate) или из [`Pipeline.from`](./pipeline.mdx#pipeline.from). **Стадия** (stage) — один шаг **конвейера**. Она берёт строки предыдущего шага и отдаёт новые. Имя метода совпадает с именем стадии MongoDB без `$`, то есть `match` — это `$match`.

Если вы только начинаете, сначала прочитайте руководство [Первая агрегация](../../aggregation/first-aggregation.mdx). Здесь — справочник.

Главное отличие Typemo от голого драйвера в том, что после каждой стадии компилятор пересчитывает **тип строки**. После `group` строка уже не заказ, а группа с полями, которые вы назвали. Следующая стадия видит только настоящие поля, а опечатка в имени поля останавливает компилятор. Значения внутри стадий (`fn.sum(f.total)`) пишутся колбэком `(f) => …`. В нём `f` — прокси полей, а `fn` — каталог операторов. Подробнее о них в руководстве [Выражения](../../aggregation/expressions.mdx).

Все примеры используют модель магазина — покупатели и заказы со строками-товарами.

```ts twoslash title="models/order.ts"
import { ObjectId } from "mongodb";
import { Entity, Prop, type Ref, Schema } from "@venloc/typemo";

@Schema({ collection: "customers" })
export class Customer extends Entity {
  @Prop(() => String, { required: true })
  name!: string;

  @Prop(() => String, { required: true })
  city!: string;

  @Prop(() => ObjectId, { ref: () => Customer })
  referrer?: Ref<Customer>;
}

@Schema()
export class Item {
  @Prop(() => String, { required: true })
  sku!: string;

  @Prop(() => Number, { required: true })
  qty!: number;

  @Prop(() => Number, { required: true })
  price!: number;
}

@Schema({ collection: "orders" })
export class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true })
  customer!: Ref<Customer>;

  @Prop(() => String, { required: true })
  status!: string;

  @Prop(() => Number, { required: true })
  total!: number;

  @Prop(() => Date, { required: true })
  placedAt!: Date;

  @Prop(() => [Item])
  items!: Item[];

  @Prop(() => String)
  note?: string;
}
```

Покупатели — Alice (Oslo), Bob (Paris) и Carol (Oslo, её пригласила Alice). Заказов четыре.

- Alice, `paid`, 120, 5 января, товары `pen`×2 и `book`.
- Bob, `open`, 40, 20 января, `pen`×4.
- Alice, `paid`, 60, 3 февраля, `ink`×3, заметка `gift`.
- Bob, `paid`, 30, 14 февраля, без товаров.

Результаты в комментариях `// →` получены на этих данных. Поля `_id` в них опущены, если не важны.

Стадии, которые читают служебные данные сервера (`collStats`, `currentOp` и другие), и стадии Atlas (`search`, `vectorSearch`) описаны в конце. Они работают только на первом месте конвейера и не во всех режимах.

Если у модели есть [скрытые поля](../../schemas/hidden-and-sensitive.mdx#hidden-in-aggregation), [`Model.aggregate`](./pipeline.mdx#model.aggregate) убирает их стадией `$unset` в начале конвейера. Если же первая стадия обязана остаться первой (`search`, `searchMeta`, `vectorSearch`, `geoNear`, `collStats`, `indexStats` и другие), `$unset` встаёт сразу за ней, как требует сервер.

Служебные стадии базы и сервера (`documents`, `currentOp`, `listLocalSessions`, `listSessions` и другие) строятся в [`Pipeline.database`](./pipeline.mdx#pipeline.database), [`Pipeline.admin`](./pipeline.mdx#pipeline.admin) и [`Pipeline.sessions`](./pipeline.mdx#pipeline.sessions). Выполняет их [`client.aggregate`](../connection/typemo-client.mdx#client.aggregate).

## match [#match]

`match` оставляет только строки, которые подходят под условие. Это самая частая стадия. Чем раньше она стоит, тем меньше строк сервер тащит через конвейер и тем лучше использует индексы.

Условие пишется как фильтр [`find`](../query/reading.mdx#model.find) или колбэком с булевым выражением. Во втором случае Typemo отправляет его как `$expr`.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p.match({ status: "paid", total: { $gte: 50 } }).project({ total: 1, _id: 0 }),
);
console.log(rows);
// → [{ total: 120 }, { total: 60 }]
```

Сырой объект с `$expr` запрещён. Условие, которое сравнивает два поля строки, пишите колбэком.


Стадия возвращает строитель с теми же строками. Она работает в любом режиме, кроме конвейера обновления. Третья форма принимает готовый фильтр сущности (`const filter: Filter<Order>`), пока строки ещё имеют сохранённый вид.

## sort [#sort]

`sort` упорядочивает строки. Ключи — пути текущей строки, направления — `1`/`-1` или слова `"ascending"`/`"descending"`. Ключ можно заменить оценкой текстового поиска `{ $meta: "textScore" }`.

```ts twoslash
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
```

## limit [#limit]

`limit` пропускает первые `n` строк и отбрасывает остальные. `n` — целое не меньше 1. В MongoDB ноль означает «без ограничения», и опечатка превратила бы «ничего» в «всё», поэтому Typemo отказывается.

```ts twoslash
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
```

## skip [#skip]

`skip` пропускает первые `n` строк. `n` — целое не меньше 0. Вместе с `limit` он даёт страницы, но на больших смещениях сервер всё равно читает пропущенное. Для длинных списков лучше [пагинация по ключу](../query/keyset.mdx).

## count [#count]

`count` заменяет все строки одной вида `{ [поле]: число }`. Если строк на входе не было, на выходе тоже нет ни одной, а не `0`. Для подсчёта по группам берите [`group`](#group) с `fn.count()`.

## redact [#redact]

`redact` решает по условию, что делать с документом. Оставить целиком, отбросить или пойти глубже во вложенные документы. Условие — колбэк, который возвращает `Vars.KEEP`, `Vars.PRUNE` или `Vars.DESCEND`, обычно через `fn.cond`. Стадия нужна для безопасности внутри документа, когда пользователю нельзя видеть часть вложенных блоков.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p.redact((f) => fn.cond(fn.gte(f.total, 50), Vars.KEEP, Vars.PRUNE)).project({ total: 1, _id: 0 }),
);
console.log(rows);
// → [{ total: 120 }, { total: 60 }]
```

## addFields [#add-fields]

`addFields` добавляет поля или заменяет существующие, остальные оставляет. Значения — выражения над полями строки. Ключ с точкой пишет внутрь вложенного документа, а `fn.remove()` удаляет поле.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p
    .match({ status: "paid" })
    .addFields((f) => ({ withTax: fn.multiply(f.total, 1.2) }))
    .project({ total: 1, withTax: 1, _id: 0 }),
);
console.log(rows);
// → [{ total: 120, withTax: 144 }, { total: 60, withTax: 72 }, { total: 30, withTax: 36 }]
```

Тип строки после стадии — прежний плюс новые поля. Опечатка в имени поля внутри выражения останавливает компилятор.

## set [#set]

`set` — второе имя [`addFields`](#add-fields), и делает он то же самое. В конвейере обновления ([`Pipeline.update`](./pipeline.mdx#pipeline.update)) обычно пишут `set`, в отчётах — `addFields`.

```ts twoslash
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;

```

## project [#project]

`project` оставляет только названные поля или вычисляет новые. Значение `1` или `true` оставляет поле, `0` или `false` убирает, выражение вычисляет. «Оставить» и «убрать» смешивать нельзя, кроме `_id`. Компилятор остановит такую проекцию, а сервер отверг бы её.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
```

Вторая форма принимает объект с путями без колбэка — `p.project({ status: 1, total: 1 })`. Пустая проекция даёт `ConfigurationError: $project needs at least one field`.

В [конвейере обновления](./pipeline.mdx#pipeline.update) `project` переписывает документ целиком. Иначе обновление останавливается до отправки, а в тексте ошибки названы потерянные поля. Подробнее в руководстве [Обновление через конвейер](../../writes/pipeline-updates.mdx#replace-with-stage).

## replaceWith [#replace-with]

`replaceWith` — короткая запись [`replaceRoot`](#replace-root). Она принимает сам новый корень, без обёртки `newRoot`.

В [конвейере обновления](./pipeline.mdx#pipeline.update) эта стадия, как `replaceRoot` и `project`, заменяет документ целиком. Иначе Typemo бросит `StrictModeError` с причиной `immutable` до отправки. Ключи нового корня вы пишете именами полей модели, а если у поля задан `dbName`, Typemo переведёт их в имена в базе. `unwind` разворачивает массив. На каждый элемент приходится своя строка, остальные поля копируются. Так считают что-то по товарам, а не по заказам. Путь пишется строкой с `$`, и компилятор принимает только пути массивов.

## group [#group]

`group` собирает строки в группы по ключу `_id` и считает по каждой группе **аккумуляторы** — операторы вроде `fn.sum`, `fn.avg`, `fn.count`. Это главная стадия отчётов, например выручка по статусам или число заказов на клиента.

`_id` — выражение, `null` (одна группа на все строки) или составной объект. Любое другое поле обязано быть аккумулятором. Обычное выражение компилятор не пропустит, потому что сервер тоже его отверг бы. Все аккумуляторы перечислены в справочнике [Аккумуляторы](./accumulators.mdx).

Верно и обратное. Операторы, которые работают только как аккумуляторы (`fn.push`, `fn.addToSet`, `fn.count`, `fn.top` и другие), разрешены лишь в `group`, `bucket`, `bucketAuto` (в их `output`) и `setWindowFields`. В `project` или `addFields` они не скомпилируются. Операторы с двойной ролью (`fn.sum`, `fn.avg`, `fn.min`, `fn.max`) там остаются обычными выражениями над массивом внутри документа. Как это работает, объясняет раздел [про аккумуляторы](./accumulators.mdx#how-accumulators-work).

Если в `group` попало обычное выражение, компилятор называет поле и причину прямо в тексте ошибки.

## bucket [#bucket]

`bucket` раскладывает строки по интервалам с заданными границами. `_id` группы — нижняя граница интервала, а строки вне границ попадают в группу `default`. Стадия нужна для гистограмм, например заказы до 50 и от 50 до 100.

```ts twoslash

  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
```

Границы — массив не короче двух значений по возрастанию, того же типа, что `groupBy`. Строка со значением вне границ без `default` даёт ошибку сервера.

## setWindowFields [#set-window-fields]

`setWindowFields` считает новое поле по **окну** соседних строк и не схлопывает строки в группы. Так получают бегущую сумму, место в рейтинге или разницу с предыдущей строкой. `partitionBy` делит строки на независимые части, `sortBy` задаёт порядок, `output` описывает поля через `withWindow`.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p
    .setWindowFields({
      partitionBy: (f) => f.status,
      sortBy: { placedAt: 1 },
      output: (f) => ({
        running: withWindow(fn.sum(f.total), { documents: ["unbounded", "current"] }),
      }),
    })
    .project({ status: 1, total: 1, running: 1, _id: 0 })
    .sort({ status: 1, running: 1 }),
);
console.log(rows.slice(1));
// → [{ status: "paid", total: 120, running: 120 }, { status: "paid", total: 60, running: 180 }, { status: "paid", total: 30, running: 210 }]
```

Функциям, которым нужен порядок (`fn.rank()`, `fn.shift`, ограниченные окна), требуется `sortBy`, без него они не компилируются. Ранги и `fn.linearFill` (`fn.rank`, `fn.denseRank`, `fn.documentNumber`, `fn.linearFill`) требуют `sortBy` ровно из одного поля. С двумя компилятор остановит вызов и назовёт поле результата и правило. Оконные операторы описаны в справочнике [Оконные операторы](./window-operators.mdx). Руководство — [Оконные функции](../../aggregation/windows.mdx).

## densify [#densify]

`densify` заполняет пропуски в ряду чисел или дат и добавляет строки с недостающими значениями поля. Она нужна для графиков, где месяц без заказов должен быть виден как ноль, а не пропасть.

```ts twoslash
import { ObjectId } from "mongodb";

  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---

  p
    .match({ status: "paid" })
    .project({ placedAt: 1, _id: 0 })
    .densify({ field: "placedAt", range: { step: 1, unit: "month", bounds: "full" } }),

// → ["2026-01-05", "2026-02-03", "2026-02-05", "2026-02-14"]
```

Добавленные строки содержат только это поле и поля `partitionByFields`, поэтому остальные поля в типе становятся необязательными. Для дат `range` задаёт `step` и `unit`, для чисел — только `step`.

## lookup [#lookup]

`lookup` подтягивает к каждой строке документы другой коллекции. Результат — массив в поле `as`, даже если найден один документ или ни одного. Это аналог соединения из реляционных баз.

Первая форма работает по равенству полей. Сравниваются `localField` этой строки и `foreignField` подтягиваемой. Тип подтянутых документов берётся из `from`.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p
    .match({ status: "open" })
    .lookup({ from: Customer, localField: "customer", foreignField: "_id", as: "buyer" })
    .project({ total: 1, "buyer.name": 1, _id: 0 }),
);
console.log(rows);
// → [{ total: 40, buyer: [{ name: "Bob" }] }]
```

Подтянутые документы проходят политики класса из `from`, как при обычном чтении через его модель. Мягко удалённые документы не подтягиваются, поля `Hidden` убираются, а из тенантской коллекции подтягиваются только документы тенанта операции. Без тенанта Typemo бросает `StrictModeError` с правилом `tenant` до обращения к серверу. Создавать модель этого класса на подключении не нужно, схему Typemo компилирует сам.

Вторая форма использует **вложенный конвейер**. Подтягиваемые документы проходят свои стадии. Переменные (`let`) передают значения строки внутрь, а колбэк конвейера получает их вторым аргументом.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Customers.aggregate((p) =>
  p
    .lookup({
      from: Order,
      as: "paid",
      let: (f) => ({ id: f._id }),
      pipeline: (q, v) =>
        q.match((o) => fn.and(fn.eq(o.customer, v.id), fn.eq(o.status, "paid"))).count("n"),
    })
    .project({ name: 1, paid: 1, _id: 0 })
    .sort({ name: 1 }),
);
console.log(rows);
// → [{ name: "Alice", paid: [{ n: 2 }] }, { name: "Bob", paid: [{ n: 1 }] }, { name: "Carol", paid: [] }]
```

Третья форма обходится без `from`. Вложенный конвейер сам создаёт документы стадией [`documents`](#documents). У него должна быть хотя бы одна стадия, иначе `ConfigurationError`. Имя переменной должно быть допустимым, иначе тоже ошибка. Ключ `as` с точкой пишет в поле вложенного документа. Подробнее в руководстве [Соединения](../../aggregation/joins.mdx).

## graphLookup [#graph-lookup]

`graphLookup` рекурсивно идёт по связям внутри одной коллекции. Так обходят цепочку приглашений, дерево комментариев или подчинённых сотрудника. `startWith` — откуда начать, `connectFromField` и `connectToField` — как перейти к следующему документу.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Customers.aggregate((p) =>
  p
    .match({ name: "Carol" })
    .graphLookup({
      from: Customer,
      startWith: (f) => f.referrer,
      connectFromField: "referrer",
      connectToField: "_id",
      as: "chain",
      depthField: "depth",
    })
    .project({ name: 1, "chain.name": 1, "chain.depth": 1, _id: 0 }),
);
console.log(rows);
// → [{ name: "Carol", chain: [{ name: "Alice", depth: 0n }] }]
```

Найденные документы проходят политики класса из `from` так же, как у [`lookup`](#lookup) — мягкое удаление, тенант и поля `Hidden`. С `depthField` каждый найденный документ получает глубину (int64). `maxDepth` ограничивает глубину и принимает целое не меньше 0. `restrictSearchWithMatch` — фильтр по найденным документам.

## unionWith [#union-with]

`unionWith` дописывает к строкам строки другой коллекции. Тип строки после неё — объединение `T | Joined`, потому что строки бывают двух видов. Стадия нужна для общего списка из двух источников.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p
    .match({ status: "open" })
    .project({ total: 1, _id: 0 })
    .unionWith({ pipeline: (q) => q.documents([{ total: 0 }]) }),
);
console.log(rows);
// → [{ total: 40 }, { total: 0 }]
```

Форм три. Первая принимает только коллекцию (`unionWith(Customer)`). Вторая — коллекцию с вложенным конвейером (`{ coll, pipeline }`). Третья — конвейер без коллекции, который сам создаёт документы, как в примере выше. Дописанные строки проходят политики класса, названного коллекцией, так же, как у [`lookup`](#lookup) — мягкое удаление, тенант и поля `Hidden`. Модель этого класса создавать не нужно.

## facet [#facet]

`facet` запускает несколько конвейеров над одними и теми же строками и возвращает **одну** строку, где у каждой ветки свой массив. Стадия даёт сразу несколько отчётов за один проход по данным, например список и итоги по статусам.

```ts twoslash
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });

  p.facet({
```

## geoNear [#geo-near]

`geoNear` ищет документы рядом с точкой и добавляет расстояние. Это всегда первая стадия конвейера или вложенного конвейера `lookup`, а в `facet` её нельзя. Нужен геопространственный индекс `2dsphere` на поле.

## documents [#documents]

## search [#search]

`search` — полнотекстовый поиск Atlas Search. Стадия работает только в Atlas (или в локальной установке Atlas CLI) и только первой в конвейере. Типы проверяют спецификацию — `index`, оператор (`text`, `phrase`, `compound`, …), `highlight`, `count`, `sort`.

```ts twoslash

@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
```

На обычном MongoDB сервер отвечает ошибкой `ServerError: Using $search and $vectorSearch aggregation stages requires additional configuration. (code 31082 SearchNotEnabled)`. Полный текст сервера с советом подключиться к Atlas или к локальному развёртыванию Atlas CLI лежит в поле `serverMessage`. Стадия проверена только на уровне сборки конвейера. Руководство — [Поиск в агрегациях](../../aggregation/search.mdx).

## rankFusion [#rank-fusion]

`rankFusion` сводит результаты нескольких конвейеров в один рейтинг по методу взаимных рангов. Она выручает, когда вы ищете двумя способами (текст и вектор), а список нужен один. Требует MongoDB 8.1+ и стоит первой в конвейере коллекции.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const rows = await Orders.aggregate((p) =>
  p
    .rankFusion({
      input: {
        pipelines: {
          byTotal: (q) => q.sort({ total: -1 }),
          byDate: (q) => q.sort({ placedAt: 1 }),
        },
      },
    })
    .project({ total: 1, _id: 0 }),

console.log(rows);
// → [{ total: 120 }, { total: 40 }, { total: 60 }, { total: 30 }]
```

Кроме `input.pipelines` стадия принимает `combination.weights` (веса по именам ветвей) и `scoreDetails`. Ветка без стадий даёт `ConfigurationError`.

## out [#out]

`out` записывает результат конвейера в коллекцию и полностью заменяет её содержимое. Это последняя стадия. После неё стадий добавить нельзя, а результат `await` — пустой массив, потому что строк нет. Агрегация с `out` считается записью, и второй `await` того же запроса даёт ошибку, см. [`.exec`](./pipeline.mdx#exec).

Если целью служит сущность, компилятор сверяет строки с её полями. Не хватает поля или тип не тот — ошибка на месте вызова, а не порченые данные в коллекции. Сообщение называет цель и поле, например `PathError<"the pipeline rows do not match the target model: check the field \"revenue\"">`. Когда ключ группы становится `_id` результата, у цели должен быть `_id` того же типа. Опишите её через [`EntityWithId`](../schemas/base-classes.mdx#entity-with-id). Обычный класс с `_id!: string` тоже принимается, но тип `_id` у него не проверяется ни в `findById`, ни в ссылках, и `_id` остаётся изменяемым.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, EntityWithId, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
@Schema({ collection: "status_totals" })
class StatusTotal extends EntityWithId(() => String) { // [!code highlight]
  @Prop(() => Number, { required: true }) revenue!: number;
  @Prop(() => Number, { required: true }) orders!: number;
}

await Orders.aggregate((p) =>
  p.group((f) => ({ _id: f.status, revenue: fn.sum(f.total), orders: fn.count() })).out(StatusTotal),
);
const StatusTotals = client.db().model(StatusTotal);
console.log(await StatusTotals.find().sort({ _id: 1 }).lean());
// → [{ _id: "open", revenue: 40, orders: 1 }, { _id: "paid", revenue: 210, orders: 3 }]
```

Цель можно назвать строкой (`out("paid_orders")` — коллекция этой же базы) или объектом `{ db, coll }`. Оба поля обязательны. Объект без `db` или без `coll` Typemo отвергает сразу, при построении, ошибкой `ConfigurationError` `$out: a target object needs both "db" and "coll" as non-empty strings (got coll); to write into an entity, pass the class` (в скобках ключи объекта), а не текстом сервера. В объекте можно задать `timeseries` (`timeField`, `metaField`, `granularity`). Строки для имени не проверяются.

Запись в тенантскую коллекцию, названную сущностью или моделью на подключении, Typemo отвергает с `StrictModeError` (правило `tenant`), если у операции нет `allTenants: true`. Такая запись смешала бы тенантов. Руководство — [Сохранить результат](../../aggregation/output.mdx).

## merge [#merge]

`merge` записывает результат в коллекцию и не стирает её. Совпавшие документы обновляются, новые добавляются. Это последняя стадия, она нужна для постепенного накопления отчётов.

```ts twoslash
import { ObjectId } from "mongodb";
import { Entity, EntityWithId, fn, Pipeline, Prop, type Ref, Schema, TypemoClient, Vars, withWindow } from "@venloc/typemo";
@Schema({ collection: "customers" })
class Customer extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => ObjectId, { ref: () => Customer }) referrer?: Ref<Customer>;
}
@Schema()
class Item {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true }) qty!: number;
  @Prop(() => Number, { required: true }) price!: number;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => ObjectId, { ref: () => Customer, required: true }) customer!: Ref<Customer>;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Number, { required: true }) total!: number;
  @Prop(() => Date, { required: true }) placedAt!: Date;
  @Prop(() => [Item]) items!: Item[];
  @Prop(() => String) note?: string;
}
@Schema({ collection: "status_totals" })
class StatusTotal extends EntityWithId(() => String) {
  @Prop(() => Number, { required: true }) revenue!: number;
  @Prop(() => Number, { required: true }) orders!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
const Customers = client.db().model(Customer);
const Orders = client.db().model(Order);
// ---cut---
const StatusTotals = client.db().model(StatusTotal);
const accumulate = () =>
  Orders.aggregate((p) =>
    p
      .group((f) => ({ _id: f.status, revenue: fn.sum(f.total), orders: fn.count() }))
      .merge({
        into: StatusTotal,
        on: "_id",
        whenMatched: (q, v) => q.set((f) => ({ revenue: fn.add(f.revenue, v.new.revenue), orders: fn.add(f.orders, v.new.orders) })),
        whenNotMatched: "insert",
      }),
  );
await accumulate();
await accumulate();
console.log(await StatusTotals.find().sort({ _id: 1 }).lean());
// → [{ _id: "open", revenue: 80, orders: 2 }, { _id: "paid", revenue: 420, orders: 6 }]
```

`into` — сущность или `{ db, coll }`. `db` можно опустить, тогда берётся база самой агрегации. Объект без `coll` даёт `ConfigurationError` `$merge: a target object needs "coll" (and "db" when given) as non-empty strings (got db); to write into an entity, pass the class`.

`on` — поле или поля совпадения, на них нужен уникальный индекс. `whenMatched` — `"replace"`, `"keepExisting"`, `"merge"`, `"fail"` или конвейер обновления, где новая строка доступна как `v.new`. `whenNotMatched` — `"insert"`, `"discard"` или `"fail"`. Переменные `let` доступны в конвейере `whenMatched`.

Строки, не подходящие классу `into`, компилятор отвергает так же, как у `out`, ошибкой `PathError<"the pipeline rows do not match the target model: check the field …">`. Запись в тенантскую коллекцию отвергается так же, как у [`out`](#out).

<Callout type="warning" title="Полный пересчёт со сложением удваивает итоги">

Пример выше запускает конвейер дважды на тех же данных, и итоги **удвоились**. `paid` стал 420 вместо 210, `open` — 80 вместо 40. `whenMatched` с `fn.add` прибавляет новую строку к уже записанной, а конвейер каждый раз пересчитывает все заказы. Ошибки нет, так работает сервер. `merge` не знает, что строка уже учтена, и Typemo этого не видит. Сложение подходит, только когда `match` отбирает лишь новые документы. Для полного пересчёта берите `whenMatched: "replace"`, и повторный запуск даст тот же итог.

</Callout>
