**Пагинация по ключу** отдаёт страницу как «строки после последней увиденной», а не как «пропусти N строк». Страница стоит одинаково на любой глубине, а записи, которые добавили или удалили между запросами страниц, не повторяются и не теряются. Эта страница описывает метод [`Model.keysetPage`](#modelkeysetpage), его опции и результат, подпись токена следующей страницы и ошибку [`KeysetTokenError`](#keysettokenerror).

Если вы только начинаете, сначала прочитайте руководство [Пагинация по ключу](../../queries/keyset-pagination.mdx): оно объясняет, почему [`.skip`](./reading.mdx#skip) плохо работает на длинных списках. Эта страница — справочник.

Все примеры используют одну модель поста. Постов на странице показывается много, поэтому её поля выбраны так, чтобы были видны все особые случаи: обязательные поля годятся для сортировки, необязательное и допускающее `null` нет.

```ts twoslash title="models/post.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "posts" })
export class Post extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => Number, { required: true })
  views!: number;

  @Prop(() => Number)
  rating?: number;

  @Prop(() => String, { nullable: true })
  topic!: string | null;
}
```

В коллекции семь постов с названиями от `A` до `G`. Просмотры: `A` — 50, `B` и `C` — по 40, `D` — 30, `E` — 20, `F` и `G` — по 10. Посты созданы в алфавитном порядке. Результаты в комментариях `// →` — названия постов в порядке страницы.

## Model.keysetPage

`keysetPage` возвращает одну страницу постов и токен, по которому запрашивается следующая. Используйте его для бесконечной прокрутки и длинных списков, в которых пользователь листает вперёд: лента новостей, журнал событий, список заказов.

Порядок страницы **полный**: к вашим ключам сортировки Typemo добавляет `_id` последним ключом. Поэтому строки с одинаковыми просмотрами всё равно идут в определённом порядке, и граница страницы всегда однозначна. Токен запоминает значения ключей последней строки страницы, а следующий запрос начинается сразу за ними.

```ts twoslash
import { Entity, Keyset, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
  @Prop(() => Number) rating?: number;
  @Prop(() => String, { nullable: true }) topic!: string | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Posts = client.db().model(Post);
// ---cut---
const first = await Posts.keysetPage({ sort: [["views", "desc"]], limit: 3 });
console.log(first.items.map((post) => post.title), first.hasMore);
// → ["A", "C", "B"] true

const second = await Posts.keysetPage({ sort: [["views", "desc"]], limit: 3, after: first.nextCursor });
console.log(second.items.map((post) => post.title), second.hasMore);
// → ["D", "E", "G"] true
```

Между `B` и `C` при одинаковых просмотрах решает `_id`: `desc` в сортировке относится и к нему, поэтому более новый пост `C` идёт раньше `B`.

<Returns type="Promise<KeysetPage<Row>>">

Страница: `items` — строки в запрошенном порядке (документы, а с `lean: true` — lean-строки), `nextCursor` — токен для следующей страницы или `null` на последней, `hasMore` — есть ли следующая страница. Пустая выборка даёт `{ items: [], nextCursor: null, hasMore: false }`, а не ошибку.

</Returns>

<Params>
<Param name="options.sort" type="KeysetSort<T>" required>

Порядок: непустой список пар `[поле, направление]`. Направление — `1`, `-1`, `"asc"`, `"desc"`, `"ascending"` или `"descending"`. Ключами могут быть только обязательные необнуляемые поля верхнего уровня с порядком (числа, строки, даты, идентификаторы) и `_id`, а также `createdAt` и `updatedAt` моделей с [`Timestamped`](../schemas/base-classes.mdx#timestamped): ядро само заполняет их при каждой вставке, поэтому отсутствующих значений там не бывает. Ключ должен быть позицией, а позиции у отсутствующего значения нет. `_id` в конец добавится сам, с направлением последнего ключа; если вы указали его сами, он остаётся там, где вы его поставили.

Список пар, а не объект, потому что порядок ключей объекта не всегда совпадает с порядком записи: числоподобные ключи JavaScript сортирует по-своему.

</Param>
<Param name="options.limit" type="number" required>

Сколько строк на странице: целое положительное число. Иначе `QueryError` с текстом `keysetPage: limit must be a positive integer, got 0 (number)`; значение печатается с типом, так что строка `"3"` даёт `got "3" (string)`.

</Param>
<Param name="options.after" type="string | null">

Токен `nextCursor` предыдущей страницы. Для первой страницы не передавайте (или передайте `null`). Токен приходит от клиента, поэтому Typemo не доверяет ему и проверяет полностью: см. [Токен и его проверка](#токен-и-его-проверка).

</Param>
<Param name="options.filter" type="Filter<T>">

Какие документы листать. Проверяется как фильтр в [`find`](./reading.mdx#modelfind). Он действует на каждую страницу, поэтому токен не даёт доступа к документам вне фильтра.

</Param>
<Param name="options.lean" type="boolean" default="false">

Вернуть [lean-строки](./reading.mdx#lean) вместо документов.

</Param>
<Param name="options.session" type="ClientSession | null">

Выполнить в этой сессии; `null` — вне транзакции, как у [`.session`](./options.mdx#session).

</Param>
</Params>

<FullType>

```ts
keysetPage<F extends Filter<T, true> = Record<never, never>, const L extends boolean = false>(
  options: KeysetPageOptions<T, F, L>,
): Promise<KeysetPage<ResultDoc<T, undefined, never, L, NoNarrowing, never>>>

interface KeysetPageOptions<T, F, L extends boolean> {
  readonly filter?: F & NoInfer<FilterCheck<T, F>>;
```

### Последняя страница

Когда строк осталось не больше `limit`, `hasMore` равен `false`, а `nextCursor` равен `null`. Typemo определяет это, запрашивая на одну строку больше, чем `limit`. Поэтому последняя страница с ровно `limit` строками тоже сообщает, что продолжения нет, а вы не делаете лишний пустой запрос:

```ts twoslash
import { Entity, Keyset, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
  @Prop(() => Number) rating?: number;
  @Prop(() => String, { nullable: true }) topic!: string | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Posts = client.db().model(Post);
// ---cut---
const last = await Posts.keysetPage({ sort: [["views", "desc"]], limit: 7 });
console.log(last.items.length, last.hasMore, last.nextCursor);
// → 7 false null
```

### Записи, добавленные между страницами

Главное отличие от `.skip`: если между запросами страниц в начало списка добавили запись, следующая страница не сдвигается. Токен помнит позицию, а не номер.

```ts twoslash
import { Entity, Keyset, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
  @Prop(() => Number) rating?: number;
  @Prop(() => String, { nullable: true }) topic!: string | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Posts = client.db().model(Post);
// ---cut---
const first = await Posts.keysetPage({ sort: [["views", "desc"]], limit: 2 });
console.log(first.items.map((post) => post.title));
// → ["A", "C"]

await Posts.create({ title: "Z", views: 100, topic: null }); // новый самый популярный пост

const second = await Posts.keysetPage({ sort: [["views", "desc"]], limit: 2, after: first.nextCursor });
console.log(second.items.map((post) => post.title));
// → ["B", "D"]
```

С `.skip(2)` вторая страница началась бы с `C`, который читатель уже видел: новая запись сдвинула бы все остальные.

### Сортировка по времени

Лента «сначала новые» сортируется по времени создания, а список «недавно менявшиеся» — по времени изменения. Для моделей с [`Timestamped`](../schemas/base-classes.mdx#timestamped) оба поля, `createdAt` и `updatedAt`, годятся в ключ, хотя в схеме они не объявлены как `required`: ядро заполняет их при каждой вставке, и отсутствующего значения там нет. Примеры ниже — на модели заметки с полем `title`; в коллекции пять заметок `s1`…`s5`, созданных по очереди.

```ts twoslash
import { Entity, Prop, Schema, Timestamped, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "notes" })
class Note extends Timestamped(Entity) {
  @Prop(() => String, { required: true }) title!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Notes = client.db().model(Note);
// ---cut---
const page1 = await Notes.keysetPage({ sort: [["createdAt", "asc"]], limit: 2 });
console.log(page1.items.map((note) => note.title));
// → ["s1", "s2"]

const page2 = await Notes.keysetPage({ sort: [["createdAt", "asc"]], limit: 2, after: page1.nextCursor });
console.log(page2.items.map((note) => note.title));
// → ["s3", "s4"]
```

`updatedAt` меняется при любой записи, поэтому порядок по нему живой: заметка, которую только что изменили, оказывается на первой странице списка «сначала изменённые». Если список должен быть устойчивым, а не подвижным, листайте по `createdAt`, а не по `updatedAt`.

```ts twoslash
import { Entity, Prop, Schema, Timestamped, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "notes" })
class Note extends Timestamped(Entity) {
  @Prop(() => String, { required: true }) title!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Notes = client.db().model(Note);
// ---cut---
const note = await Notes.findOne({ title: "s1" }).orFail();
note.title = "s1x";
await note.$save();

const recent = await Notes.keysetPage({ sort: [["updatedAt", "desc"]], limit: 2 });
console.log(recent.items.map((item) => item.title));
// → ["s1x", "s5"]
```

В токене значение даты хранится без потерь, так что совпадающие до миллисекунды метки различает `_id`, который Typemo добавляет последним ключом.

### Ключ, который нельзя использовать

Поле, которого в документе может не быть или которое может быть `null`, не подходит в ключ: у отсутствующего значения нет места в порядке. Компилятор не даст указать такое поле, а во время работы Typemo бросает [`ConfigurationError`](../errors/configuration-errors.mdx#configurationerror):

```ts twoslash
import { Entity, Keyset, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
  @Prop(() => Number) rating?: number;
  @Prop(() => String, { nullable: true }) topic!: string | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Posts = client.db().model(Post);
// ---cut---
// @errors: 2322
await Posts.keysetPage({ sort: [["rating", "asc"]], limit: 3 });
```

```text
ConfigurationError: keysetPage: sort "rating" of Post must be required and not nullable (a missing value cannot be a position)
```

Так же отвергаются логические поля, регулярные выражения и вектора (`is not an orderable scalar field`). Неизвестное поле и одно поле дважды — [`QueryError`](../errors/query-errors.mdx#queryerror) с текстами `keysetPage: sort "nope" is not a top-level field of Post` и `keysetPage: sort names "views" twice`. Пустой список ключей — `keysetPage: sort is a non-empty list of [field, direction] pairs`.

### Токен и его проверка

Токен — это строка, которую вы отдаёте клиенту, а тот присылает её обратно. Значит, клиент может прислать что угодно: обрезанный, подделанный или собранный для другой сортировки токен. Typemo проверяет токен до того, как строит по нему запрос: длину и алфавит, структуру, совпадение ключей и направлений с вашей сортировкой и тип каждого значения. Токен, который не прошёл проверку, — [`KeysetTokenError`](#keysettokenerror), и в запрос он не попадает.

```ts twoslash
import { Entity, Keyset, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
  @Prop(() => Number) rating?: number;
  @Prop(() => String, { nullable: true }) topic!: string | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Posts = client.db().model(Post);
// ---cut---
try {
  await Posts.keysetPage({ sort: [["views", "desc"]], limit: 3, after: "garbage" });
} catch (error) {
  console.log(String(error));
  // → "KeysetTokenError: keysetPage: invalid cursor — it cannot be read"
}
```

Токен, выданный для одной сортировки, нельзя использовать с другой: `keysetPage: invalid cursor — it was made for another sort`.

### Подпись токена

По умолчанию токен не подписан. Он говорит, где остановилась страница, но не даёт доступа: фильтр запроса по-прежнему действует на каждую страницу, поэтому подделанным токеном чужих данных не получить, максимум сместить позицию. Если позицию менять клиенту нельзя, включите подпись: опция клиента `keysetSecret` (ключ не короче 32 байт) превращает токен в `payload.подпись`, где подпись — HMAC-SHA256 от payload.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";

@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
}

// ---cut---
const client = await TypemoClient.connect("mongodb://localhost:27017", {
  dbName: "app",
  keysetSecret: "__a-secret-of-at-least-32-bytes-long__",
});
const Posts = client.db().model(Post);

const first = await Posts.keysetPage({ sort: [["views", "desc"]], limit: 3 });
console.log(first.nextCursor?.includes("."));
// → true
```

Подпись проверяется прежде, чем токен разбирается, и сравнение занимает одно и то же время независимо от того, сколько символов совпало. С включённой подписью:

- неподписанный токен отвергается: `keysetPage: invalid cursor — it is not signed (the client signs its tokens: keysetSecret)`;
- изменённый токен отвергается: `keysetPage: invalid cursor — the signature is not valid`;
- клиент без ключа отвергает подписанный токен: `keysetPage: invalid cursor — it is signed, but this client has no keysetSecret`.

Список ключей позволяет менять ключ без разрыва: первый ключ подписывает, любой из списка проверяет. Опция клиента описана в справочнике [`TypemoClient`](../connection/typemo-client.mdx#опции-клиента).

### Когда `keysetPage` не подходит

Метод листает только вперёд и не знает общего числа страниц: перейти на страницу 17 или показать «страница 3 из 40» он не может. Для такого списка используйте [`.skip`](./reading.mdx#skip) с [`.limit`](./reading.mdx#limit) и [`countDocuments`](./reading.mdx#modelcountdocuments) для общего числа: цена в том, что глубокие страницы медленнее, а записи, добавленные между запросами, сдвигают границы.

## Keyset

`Keyset` — класс со статическими помощниками, из которых `keysetPage` собирает страницу. Вам они нужны, только если вы строите собственную выборку по ключу, например для агрегации.

<TypeTable
  type={{
    "Keyset.keys": { description: "Разрешает сортировку: добавляет `_id` последним ключом и проверяет каждый ключ по схеме. Берёт внутренний тип схемы модели.", type: "(schema, sort) => readonly [string, 1 | -1][]" },
    "Keyset.plan": { description: "Планирует страницу: ключи, размер и проверенное условие «после токена». Берёт внутренний тип схемы модели.", type: "(schema, options, secrets?) => KeysetPlan" },
    "Keyset.decode": { description: "Разбирает и проверяет токен клиента, возвращает позицию: по значению на каждый ключ. Бросает `KeysetTokenError`.", type: "(schema, keys, token, secrets?) => unknown[]" },
    "Keyset.encode": { description: "Делает токен позиции после строки; подписывает первым ключом из `secrets`, если он задан.", type: "(keys, row, secrets?) => string" },
    "Keyset.afterFilter": { description: "Строит условие «строки после этой позиции»: цепочку `$or` по ключам.", type: "(keys, values) => Record<string, unknown>" },
  }}
/>

`Keyset.afterFilter` и `Keyset.encode` работают без схемы. `afterFilter` строит лексикографическое условие: строки после позиции `views = 40`, `_id = …` в порядке «просмотры по убыванию, затем `_id` по убыванию».

```ts twoslash
import { Keyset } from "@venloc/typemo";
// ---cut---
const condition = Keyset.afterFilter([["views", -1], ["_id", -1]], [40, "ID"]);
console.log(condition);
// → { $or: [{ views: { $lt: 40 } }, { views: 40, _id: { $lt: "ID" } }] }
```

`Keyset.keys`, `Keyset.plan` и `Keyset.decode` принимают внутренний тип схемы, которого у публичного API нет: `Model.schema` отдаёт его усечённое представление. Поэтому вне `keysetPage` их не вызывают.

## KeysetTokenError

`KeysetTokenError` — ошибка, которую бросает [`keysetPage`](#modelkeysetpage), когда токен `after` не подходит: он обрезан, изменён, собран для другой сортировки, не подписан или подписан неверно. Это ошибка данных клиента, а не сбой сервера, и ваш код может ответить на неё как на неверный ввод. Класс описан также в справочнике ошибок: [`KeysetTokenError`](../errors/query-errors.mdx#keysettokenerror). Он наследует [`QueryError`](../errors/query-errors.mdx#queryerror), поле `path` равно `"after"`, а причина стоит в тексте после `invalid cursor — `.

```ts twoslash
import { KeysetTokenError } from "@venloc/typemo";
import { Entity, Keyset, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
  @Prop(() => Number) rating?: number;
  @Prop(() => String, { nullable: true }) topic!: string | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Posts = client.db().model(Post);
declare class __BadRequest__ extends Error {}
// ---cut---
export const listPosts = async (afterFromUrl: string | null) => {
  try {
    return await Posts.keysetPage({ sort: [["views", "desc"]], limit: 20, after: afterFromUrl, lean: true });
  } catch (error) {
    if (error instanceof KeysetTokenError) throw new __BadRequest__("the page token is invalid");
    throw error;
  }
};
```

Причина стоит в тексте ошибки после `invalid cursor — `. Например, `it cannot be read` (токен не разбирается), `not a string` (токен пустой или не строка), `it was made for another sort` (токен от другой сортировки), а также три текста про подпись, приведённые в разделе [Подпись токена](#подпись-токена).
