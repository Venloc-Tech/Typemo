На этой странице собраны все методы модели, которые читают данные, и главные методы **строителя запроса** — объекта, в котором запрос собирается по частям и уходит в базу только на `await`. Здесь описано, как ведёт себя каждый метод, что он принимает, что возвращает и где он может вас удивить.

Если вы только начинаете работать с Typemo, сначала прочитайте руководство [Чтение данных](../../queries/reading-data.mdx). Оно объясняет, зачем нужны документ, lean и plain и как между ними выбирать. Эта страница — справочник: к ней возвращаются, когда нужно уточнить конкретную деталь.

Все примеры используют одну модель пользователя. В ней есть обязательное поле, необязательное поле, массив и скрытое поле: так на каждом методе видно, как он обращается с каждым видом полей.

```ts twoslash title="models/user.ts"
import { Entity, type Hidden, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true })
  name!: string;

  @Prop(() => Number)
  age?: number;

  @Prop(() => [String])
  tags!: string[];

  @Prop(() => String, { hidden: true })
  passwordHash?: Hidden<string>;
}
```

В коллекции три пользователя: Alice (30 лет, теги `admin` и `dev`, хеш пароля `$argon2id$…`), Bob (17 лет, тег `dev`) и Carol (30 лет, без тегов). Результаты в комментариях `// →` получены на этих данных. Идентификаторы в результатах сокращены до `"…"`, потому что база выдаёт их заново при каждой загрузке данных.

Методы строителя, которых нет на этой странице, перечислены в конце, в разделе [Остальные методы строителя](#остальные-методы-строителя).

## Model.find

`find` находит все документы, которые подходят под фильтр, и возвращает их массивом. Это основной метод чтения: с него начинается почти любой список в приложении — пользователи на странице администратора, заказы клиента, записи для отчёта.

Сам по себе `find` ещё не обращается к базе. Он возвращает [строитель запроса](#как-работает-строитель), к которому вы цепочкой добавляете сортировку, ограничения и выбор полей. Запрос уходит в MongoDB, когда вы пишете `await`.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const adults = await Users.find({ age: { $gte: 18 } }).sort({ name: 1 });
console.log(adults.map((user) => user.name));
// → ["Alice", "Carol"]
```

<Returns type="QueryBuilder">

[Строитель запроса](#как-работает-строитель). После `await` вы получаете массив документов. Если под фильтр ничего не подошло, массив пустой: `find` никогда не возвращает `null`. Если пустой список для вас ошибка, добавьте [`.orFail()`](#orfail).

</Returns>

<Params>
<Param name="filter" type="Filter<T>">

Условия поиска. Ключи — это поля модели, значения — либо само значение поля, либо [операторы фильтра](./filter-operators.mdx): `$gte`, `$in`, `$regex` и другие. Компилятор знает поля и их типы, поэтому подскажет доступные ключи и не даст сравнить число со строкой. Если фильтр не передать, найдутся все документы.

</Param>
</Params>

<FullType>

```ts
find<F extends Filter<T, true>>(
  filter?: F & NoInfer<FilterCheck<T, F>>,
): QueryBuilder<T, "find", undefined, never, false, false, NoNarrowing, never>
```

</FullType>

### Все документы коллекции

Чтобы прочитать всю коллекцию, вызовите `find` без аргумента или с пустым объектом. Для чтения эти варианты равнозначны:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const everyone = await Users.find();
const everyoneToo = await Users.find({});
console.log(everyone.length, everyoneToo.length);
// → 3 3
```

Пустой фильтр разрешён только в чтении, потому что чтение ничего не портит.

<Callout type="warning">

В [`updateMany`](../writes/writes.mdx#updatemany), [`deleteMany`](../writes/writes.mdx#deletemany) и других методах записи Typemo запрещает пустой фильтр: одна опечатка в коде, который собирает фильтр, и вы изменили бы или удалили всю коллекцию. Подробнее — в статье [Пустые фильтры в записи](../../writes/empty-filters.mdx).

</Callout>

### Как Typemo проверяет фильтр

Фильтр проверяется дважды. Первый раз его проверяет компилятор, пока вы пишете код. Второй раз — сам Typemo, перед тем как отправить запрос в базу. Вторая проверка нужна потому, что фильтр часто собирается из данных, которых компилятор не видит: из тела HTTP-запроса, из параметров URL, из конфигурации.

Допустим, вы опечатались в имени поля. Компилятор остановит вас сразу:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2345
Users.find({ nope: 1 });
```

Если же такой фильтр пришёл во время работы программы, Typemo откажется его выполнять, а до базы запрос не дойдёт:

```text
StrictModeError: filter: "nope" is not a field of User [unknown-path]
```

Путь в тексте называется один раз: слово `filter` говорит, где искать ошибку, а `"nope"` — какое имя не подошло. MongoDB в такой ситуации просто вернула бы пустой массив: поля `nope` нет ни у одного документа, значит, ни один не подошёл. Ошибку в имени поля пришлось бы искать по странному поведению приложения. Typemo сообщает о ней сразу, через [`StrictModeError`](../errors/data-errors.mdx#strictmodeerror).

Фильтр, собранный во время работы, например типа `Record<string, unknown>` (или `{ [key: string]: unknown }`), компилятор принимает: он не видит ключей такого объекта. То же верно для `findOne`, `countDocuments` и записей с фильтром. Поэтому опечатка в ключе такого фильтра всплывёт только при запуске запроса, теми же `StrictModeError` и `CastError`, а до базы запрос всё равно не дойдёт.

С типами значений то же самое. Возраст в модели — число, поэтому строка `"30"` не пройдёт ни компилятор, ни проверку во время работы:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2322
Users.find({ age: "30" });
```

```text
CastError: Cast to number failed at path "age" for "30" (string): expected a number [type]
```

Особый случай — `undefined`. В JavaScript его легко получить случайно, например из необязательного параметра запроса. Если бы Typemo тихо превращал `{ age: undefined }` в «поле не задано», вы получили бы совсем не тех пользователей, которых искали. Компилятор такой фильтр не пропустит, а если он собран в коде без типов, `find` бросит [`QueryError`](../errors/query-errors.mdx#queryerror) сразу при вызове:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2379
Users.find({ age: undefined });
```

```text
QueryError: filter: undefined at "age" (use $exists: false / $unset; undefined is never a value)
```

Если вы действительно хотите найти документы, у которых нет поля, скажите об этом явно: `{ age: { $exists: false } }`.

### Когда `find` не подходит

Если вам нужен один документ, используйте [`findOne`](#modelfindone) или [`findById`](#modelfindbyid). Они возвращают сам документ или `null`, и вам не придётся доставать его из массива.

Если нужно только узнать, есть ли подходящий документ, используйте [`exists`](#modelexists). Он читает из базы один `_id`, а не документы целиком.

Если нужно число документов, используйте [`countDocuments`](#modelcountdocuments). `find` загрузил бы в память все документы только для того, чтобы вы посчитали длину массива.

Если документов очень много — десятки тысяч и больше, — добавьте в конце [`.cursor()`](#cursor). Тогда документы будут приходить по одному, и вам не придётся держать их все в памяти одновременно.

## Model.findOne

`findOne` находит первый документ, который подходит под фильтр. Если такого документа нет, он возвращает `null`. Используйте его, когда по смыслу задачи результат один: пользователь по email, настройки по ключу, последний заказ клиента.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const alice = await Users.findOne({ name: "Alice" }).plain();
//    ^?
console.log(alice?.name);
// → "Alice"
```

<Returns type="QueryBuilder">

[Строитель запроса](#как-работает-строитель). После `await` вы получаете документ или `null`. TypeScript не даст обратиться к полям результата, пока вы не проверите его на `null`. Если отсутствие документа для вас ошибка, добавьте [`.orFail()`](#orfail): тогда вместо `null` будет брошена [`DocumentNotFoundError`](../errors/query-errors.mdx#documentnotfounderror), а `null` пропадёт из типа.

</Returns>

<Params>
<Param name="filter" type="Filter<T>">

Условия поиска, такие же, как у [`find`](#modelfind), и проверяются они так же. Без фильтра `findOne` вернёт любой документ коллекции.

</Param>
</Params>

<FullType>

```ts
findOne<F extends Filter<T, true>>(
  filter?: F & NoInfer<FilterCheck<T, F>>,
): QueryBuilder<T, "findOne", undefined, never, false, false, NoNarrowing, never>
```

</FullType>

### Какой документ считается первым

MongoDB не хранит документы в каком-то определённом порядке и не обещает, в каком порядке их вернёт. Поэтому без сортировки «первый» документ — это просто один из подходящих, и при следующем запросе он может оказаться другим.

Если вам важно, какой именно документ вернётся, задайте порядок через [`.sort`](#sort). Например, так можно найти самого младшего пользователя:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const youngest = await Users.findOne().sort({ age: 1 }).plain();
// → { _id: "…", name: "Bob", age: 17, tags: ["dev"] }
```

### Когда `findOne` не подходит

Если вы знаете `_id` документа, используйте [`findById`](#modelfindbyid). Он делает то же самое, но короче записывается и сразу проверяет id.

Если вам нужно несколько первых документов, например пять последних заказов, используйте [`find`](#modelfind) вместе с [`.sort`](#sort) и [`.limit`](#limit).

## Model.findById

`findById` находит документ по его `_id`. Это самый частый способ прочитать одну конкретную запись: страница профиля, карточка товара, заказ по ссылке из письма. По смыслу он ничем не отличается от [`findOne`](#modelfindone) с фильтром `{ _id: id }`, но принимает id в двух видах и защищает от пустого id.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
import { ObjectId } from "mongodb";
const id = new ObjectId();
// ---cut---
const user = await Users.findById(id);
// → null (документа с таким id нет)
```

<Returns type="QueryBuilder">

[Строитель запроса](#как-работает-строитель). После `await` вы получаете документ или `null`, как у [`findOne`](#modelfindone).

</Returns>

<Params>
<Param name="id" type="тип поля _id, либо его строка" required>

Идентификатор документа. У моделей, унаследованных от [`Entity`](../schemas/base-classes.mdx#entity), это `ObjectId` или его строка из 24 шестнадцатеричных символов. Если в вашей модели `_id` другого типа, например число, `findById` ожидает именно его. Для `UUID` подходит его каноническая строка.

</Param>
</Params>

<FullType>

```ts
findById(id: IdInputOf<T>): QueryBuilder<T, "findOne", undefined, never, false, false, NoNarrowing, never>
```

</FullType>

### id из URL или тела запроса

Чаще всего id приходит от клиента: из адреса вроде `/users/6abcddec50864200b93c7fea` (24 шестнадцатеричных символа) или из JSON в теле запроса. В обоих случаях это строка, и `findById` принимает её как есть: приводить строку к `ObjectId` самому не нужно.

```ts twoslash title="users/users.service.ts"
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
export const getUserName = async (idFromUrl: string): Promise<string | undefined> => {
  const user = await Users.findById(idFromUrl).plain();
  return user?.name;
};

const alice = await Users.findOne({ name: "Alice" }).plain().orFail();
console.log(await getUserName(alice._id)); // _id в plain-виде уже строка
// → "Alice"
```

Формат строки Typemo проверяет сам. Если строка не похожа на идентификатор, запрос не уходит в базу, а `await` завершается ошибкой [`CastError`](../errors/data-errors.mdx#casterror):

```text
CastError: Cast to ObjectId failed at path "_id" for "abc" (string): not a 24-character hex string [format]
```

Это ошибка данных клиента, а не сбой сервера: ваш код может поймать `CastError` и ответить клиенту, что id неверный. Свой разбор строки перед вызовом для этого не нужен.

```ts twoslash title="users/users.service.ts"
import { CastError } from "@venloc/typemo";
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
declare class __BadRequest__ extends Error {}
// ---cut---
export const getUserByUrlId = async (idFromUrl: string) => {
  try {
    return await Users.findById(idFromUrl).orFail().plain();
  } catch (error) {
    if (error instanceof CastError) throw new __BadRequest__("the id is malformed");
    throw error;
  }
};
```

### Пустой id

Если передать `null` или `undefined`, компилятор это не пропустит. А если пустой id пришёл из кода без типов, `findById` бросит ошибку сразу при вызове и не пойдёт в базу:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2345
Users.findById(undefined);
```

```text
QueryError: findById: an id is required
```

Это защита от тихой ошибки. Запрос по `{ _id: undefined }` мог бы превратиться в поиск по `null`, вернуть `null`, и приложение ответило бы «не найдено». Настоящая проблема — id потерялся где-то в вашем коде — осталась бы незамеченной.

### Когда `findById` не подходит

Если ищете не по `_id`, а по другому полю, используйте [`findOne`](#modelfindone). Если нужно найти сразу несколько документов по списку id, используйте [`find`](#modelfind) с оператором [`$in`](./filter-operators.mdx#in).

## Model.exists

`exists` отвечает на вопрос «есть ли хотя бы один подходящий документ?». Используйте его для проверок перед действием: занят ли email при регистрации, есть ли у клиента активный заказ, существует ли запись, на которую ссылаются.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const taken = await Users.exists({ name: "Alice" });
//    ^?
// → { _id: ObjectId("…") }

const free = await Users.exists({ name: "Zed" });
// → null
```

<Returns type="OptionQuery<{ _id } | null>">

Запрос, который после `await` даёт объект с `_id` найденного документа или `null`. В условии его удобно использовать как логическое значение: `if (await Users.exists(…))`. Запрос принимает те же [опции](./options.mdx), что и другие запросы значений: `.session`, `.policy`, `.hint`, `.collation`, `.comment`, `.timeoutMS`.

</Returns>

<Params>
<Param name="filter" type="Filter<T>" required>

Условия поиска, как у [`find`](#modelfind). В отличие от `find`, здесь фильтр обязателен: вопрос «есть ли в коллекции хоть что-нибудь» почти всегда означает ошибку в коде.

</Param>
</Params>

<FullType>

```ts
exists<F extends Filter<T, true>>(
  filter: F & NoInfer<FilterCheck<T, F>>,
): OptionQuery<{ _id: IdOf<T> } | null>
```

</FullType>

### Почему не `findOne`

Результат был бы тем же, но [`findOne`](#modelfindone) прочитал бы из базы документ целиком и построил бы из него объект. `exists` просит базу вернуть только `_id`. Для проверки «есть или нет» остальные поля не нужны, и на больших документах разница заметна.

## Model.countDocuments

`countDocuments` считает документы, которые подходят под фильтр. Используйте его, когда нужно само число: общее количество записей для постраничного вывода, счётчик непрочитанных сообщений, число заказов за день.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {

// ---cut---
const thirty = await Users.countDocuments({ age: 30 });
// → 2

const total = await Users.countDocuments();
// → 3
```

Остальные [опции](./options.mdx) — `.session`, `.policy`, `.hint`, `.collation`, `.comment`, `.timeoutMS` — тоже доступны.

</Returns>

<Params>
<Param name="filter" type="Filter<T>">

Условия поиска, как у [`find`](#modelfind). Без фильтра считаются все документы коллекции.

</Param>
</Params>

<FullType>

```ts

```

</FullType>

### Посчитать «не больше чем»

Иногда точное число не нужно, достаточно знать, превышает ли оно порог. Например, показать «99+» вместо точного числа уведомлений. `.limit` останавливает подсчёт, как только набралось нужное количество, и базе не приходится проходить все документы:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const count = await Users.countDocuments().limit(2);
// → 2, хотя пользователей три
```

`.limit` у `countDocuments` принимает только положительное целое, а `.skip` — целое не меньше нуля. Иначе запрос бросает `QueryError` с текстом `limit must be a positive integer, got 0 (number)`.

### Когда `countDocuments` не подходит

Если нужен размер всей коллекции без фильтра и точность не важна, например для панели мониторинга, используйте [`estimatedDocumentCount`](#modelestimateddocumentcount). Он не проходит по документам и отвечает мгновенно даже на миллионах записей.

## Model.estimatedDocumentCount

`estimatedDocumentCount` возвращает число документов в коллекции, не читая сами документы: MongoDB берёт его из служебных данных коллекции. Поэтому ответ приходит мгновенно на коллекции любого размера.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const approx = await Users.estimatedDocumentCount();
// → 3
```

<Returns type="OptionQuery<number>">

Запрос, который после `await` даёт число. Опции запроса такие же, как у [`exists`](#modelexists).

</Returns>

Принимает ничего: фильтра здесь быть не может, потому что служебные данные хранят только общее количество.

<FullType>

```ts
estimatedDocumentCount(): OptionQuery<number>
```

</FullType>

### Насколько число точное

Обычно число совпадает с настоящим. Но после аварийной остановки сервера, в шардированном кластере или во время активной записи оно может ненадолго отличаться. Для статистики и мониторинга это не важно. Если от числа зависит логика приложения, например постраничный вывод, используйте [`countDocuments`](#modelcountdocuments).

### Мягкое удаление, тенанты и дискриминаторы

Служебные данные коллекции знают только общее число документов. Они не знают, какие документы помечены удалёнными, какому тенанту принадлежит каждый документ и к какой модели-наследнику он относится. Поэтому в трёх случаях `estimatedDocumentCount` дал бы число, которое выглядит правильным, но считает не то, что вы ожидаете. Typemo в этих случаях не отвечает неверным числом, а бросает ошибку и подсказывает, что использовать вместо него.

Если у модели включено [мягкое удаление](../../policies/soft-delete.mdx), в число попали бы и удалённые документы:

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
// ---cut---
@Schema({ collection: "accounts", softDelete: true })
class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => Date, { nullable: true })
  deletedAt?: Date | null;
}

const Accounts = client.db().model(Account);

await Accounts.estimatedDocumentCount(); // [!code error]
```

```text
StrictModeError: Account.estimatedDocumentCount: the collection's metadata counts soft-deleted documents too; use countDocuments() (or includeDeleted: true to count them all) [soft-delete]
```

Если вам действительно нужно число всех документов вместе с удалёнными, скажите об этом явно через [`.policy()`](./options.mdx#policy):

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
@Schema({ collection: "accounts", softDelete: true })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const Accounts = client.db().model(Account);
// ---cut---
const withDeleted = await Accounts.estimatedDocumentCount().policy({ includeDeleted: true });
// → 3 (две живые записи и одна удалённая)
```

Если у модели есть [поле тенанта](../../policies/tenants.mdx), в число попали бы документы всех тенантов, а не только текущего. Тогда `estimatedDocumentCount` тоже бросает ошибку и советует `countDocuments`, который учитывает тенанта (здесь модель называется `Order`):

```text
StrictModeError: Order.estimatedDocumentCount: estimatedDocumentCount reads the collection's metadata and would count every tenant; use countDocuments() (scoped by the tenant) [tenant]
```

Если число по всем тенантам нужно осознанно, передайте `.policy({ allTenants: true })`.

Если модель — [дискриминатор](../../schemas/discriminators.mdx), то есть наследник, который хранится в общей коллекции с базовой моделью, в число попали бы документы всех наследников. Typemo бросает [`ConfigurationError`](../errors/configuration-errors.mdx#configurationerror) и предлагает `countDocuments` (здесь наследник называется `CardPayment`):

```text
ConfigurationError: estimatedDocumentCount of the discriminator CardPayment would count every document of the collection; use countDocuments
```

## Как работает строитель

[`find`](#modelfind), [`findOne`](#modelfindone) и [`findById`](#modelfindbyid) не обращаются к базе сразу. Они возвращают **строитель запроса** — объект, в котором запрос собирается по частям. Цепочкой вызовов вы добавляете сортировку, ограничения, выбор полей и указываете, в каком виде хотите получить результат. Запрос уходит в MongoDB только тогда, когда вы пишете `await`, вызываете [`.exec()`](#exec) или [`.cursor()`](#cursor).

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const query = Users.find({ age: { $gte: 18 } })
  .sort({ name: 1 })
  .limit(10)
  .select({ name: 1 })
  .plain();
// в базу ещё ничего не ушло

const rows = await query;
//    ^?
// → [{ _id: "…", name: "Alice" }, { _id: "…", name: "Carol" }]
```

Такой подход позволяет собирать запрос в нескольких местах кода. Например, одна функция добавляет фильтр по правам пользователя, другая — сортировку из параметров URL, и только в конце запрос выполняется один раз.

Строитель неизменяемый: каждый метод возвращает **новый** строитель и не трогает предыдущий. Поэтому общий запрос можно безопасно расширять в разных местах, не боясь испортить чужую цепочку:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const base = Users.find({ age: 30 }).sort({ name: 1 });
const first = base.limit(1);

console.log((await base).length, (await first).length);
// → 2 1
```

Каждый метод цепочки меняет не только сам запрос, но и тип результата. После [`.select({ name: 1 })`](#select) в типе остаются только `_id` и `name`, и обратиться к `age` уже не получится. После [`.plain()`](#plain) все значения в типе переходят в plain-вид. После [`.orFail()`](#orfail) из типа пропадает `null`. Порядок вызовов при этом не важен: `.plain().select(…)` и `.select(…).plain()` дают один и тот же результат и один и тот же тип.

Методы, которые не имеют смысла для операции, не компилируются. Например, [`.skip`](#skip) и [`.cursor`](#cursor) есть только у `find`: пропускать документы или отдавать их по одному, когда результат заведомо один, бессмысленно.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2345
Users.findOne().skip(1);
```

Текст компилятора сразу говорит, в чём дело: `skip() applies to find()`. Если то же самое собрано в коде без типов, проверка во время работы бросает `QueryError` с текстом `skip applies to find() only, not findOne()`.

### Строитель как `Promise`

Строитель запроса ведёт себя как `Promise` результата: у него есть `then`, `catch` и `finally`, а `Object.prototype.toString.call(query)` печатает `[object TypemoQuery]`. Поэтому функцию можно объявить возвращающей `Promise` и вернуть из неё запрос прямо, без `async` и без `await`:

```ts twoslash
import { Entity, type HydratedDoc, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
export const getUser = (id: string): Promise<HydratedDoc<User>> => Users.findById(id).orFail();

const alice = await Users.findOne({ name: "Alice" }).orFail();
const loaded = await getUser(String(alice._id));
console.log(loaded.name);
// → "Alice"
```

Запрос при этом не выполняется, пока кто-нибудь не вызовет `then` (это делает `await`), `catch`, `finally`, [`.exec()`](#exec) или [`.cursor()`](#cursor): создание строителя ничего не отправляет в базу.

Есть одно место, где строитель не заменяет `Promise`: по нему нельзя итерировать. `for await` по самому запросу бросает `QueryError`, который подсказывает, что нужен курсор:

```text
QueryError: find(): a query is not iterable with "for await"; iterate its cursor instead: for await (const doc of Model.find(filter).cursor())
```

Запрос — это обещание результата, а не поток, и цикл по нему не имеет смысла. Без этой проверки вы получили бы общий `TypeError` среды выполнения («не итерируемый объект»), как у запросов значений вроде `countDocuments`. У `findOne` текст тот же, но начинается с `findOne():`.

## .select

`.select` выбирает, какие поля документа вернуть из базы. Это полезно по двум причинам. Во-первых, меньше данных идёт по сети: список пользователей для выпадающего меню не должен тащить за собой теги и настройки. Во-вторых, тип результата сужается вместе с выбором, и компилятор не даст случайно обратиться к полю, которое вы не загрузили.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const rows = await Users.find({ name: "Alice" }).select({ name: 1, age: 1 }).plain();
//    ^?
// → [{ _id: "…", name: "Alice", age: 30 }]
```

<Returns type="QueryBuilder">

Тот же строитель, но в типе результата остаются только выбранные поля.

</Returns>

<Params>
<Param name="projection" type="Projection<T>" required>

Объект, в котором ключи — поля модели, а значения говорят, что с ними делать. Есть три формы, и смешивать первые две в одном вызове нельзя.

- **Включение** — `{ name: 1, age: 1 }`. Вернуть только эти поля и `_id`.
- **Исключение** — `{ tags: 0 }`. Вернуть все поля, кроме этих.
- **Скрытое поле** — `{ "+passwordHash": true }`. Добавить скрытое поле к обычному набору полей.

Для массивов проекция принимает ещё `$slice` и `$elemMatch`.

Принимаются и проекции, формы которых компилятор не видит: значение объявленного типа [`Projection<T>`](../values/query-types.mdx#projection), словарь `Record<string, 0 | 1>` и данные извне, обёрнутые в [`untrusted(fields, "projection")`](../policies/soft-delete-and-untrusted.mdx#untrusted). Для них результат — все поля модели, каждое необязательное, а пути и смешение включения с исключением проверяются при запуске.

</Param>
</Params>

<FullType>

```ts
select<const P extends Projection<T> & { readonly [key: string]: unknown }>(
  projection: P & ProjectionCheck<T, P>,
): QueryBuilder<T, Op, MergeProjection<S, AnyProjection<P>>, E, Form, Found, N, X>
```

</FullType>

### Без `_id`

MongoDB возвращает `_id`, даже если вы его не выбирали. Обычно это удобно: по `_id` клиент потом запросит конкретную запись. Если `_id` не нужен, например для экспорта в таблицу, исключите его явно. Это единственное поле, которое можно исключить внутри включения:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const names = await Users.find({ age: 30 }).select({ name: 1, _id: 0 }).plain().sort({ name: 1 });
//    ^?
// → [{ name: "Alice" }, { name: "Carol" }]
```

### Скрытое поле

Поля с опцией [`hidden`](../schemas/prop.mdx#hidden) Typemo не читает из базы, пока вы о них не попросите. Так хеш пароля не окажется в памяти приложения, когда он не нужен. Чтобы прочитать скрытое поле, добавьте `+` перед его именем:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const user = await Users.findOne({ name: "Alice" })
  .select({ "+passwordHash": true })
  .orFail();

console.log(user.passwordHash);
// → "$argon2id$…"
```

Обратите внимание: `+` не превращает выбор во включение. Вы получите все обычные поля и в дополнение к ним скрытое. Ключ `+` у поля, которое не скрыто, — ошибка (текст и причина — в описании [`.select`](#select), в конце раздела про проверку имён).

Прочитать поле ещё не значит отдать его клиенту. В [`.plain()`](#plain) и [`$toPlain()`](../documents/document-api.mdx#toplain) загруженное скрытое поле всё равно не попадёт без опции `{ hidden: true }`. Подробнее — в разделе [`.plain`](#plain).

### Несколько вызовов

Если вызвать `.select` несколько раз, выборы складываются. Это удобно, когда запрос собирается в разных местах кода:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const rows = await Users.find({ name: "Alice" }).select({ name: 1 }).select({ age: 1 }).plain();
//    ^?
// → [{ _id: "…", name: "Alice", age: 30 }]
```

Один и тот же ключ дважды не выбирается, как и в `.sort`: второй вызов с тем же ключом бросает `QueryError` с текстом `projection: "name" is selected twice`. Так повторный вызов не может незаметно оказаться бесполезным или противоречить первому.

### Проекция, собранная во время работы

Обычно проекция записана литералом, и компилятор видит все её ключи. Но бывает, что набор полей приходит извне: функция принимает проекцию параметром, а клиент API сам выбирает поля строкой `?fields=name,age`. Для таких случаев `.select` принимает значение объявленного типа [`Projection<T>`](../values/query-types.mdx#projection) и словарь `Record<string, 0 | 1>`. Обходить проверку типов приведением не нужно.

```ts twoslash
import { Entity, type Hidden, Prop, type Projection, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const fields: Projection<User> = { name: 1, age: 1 };
const rows = await Users.find({ name: "Alice" }).select(fields).plain();
//    ^?
// → [{ _id: "…", name: "Alice", age: 30 }]
```

Компилятор не знает, какие именно ключи окажутся в `fields`, поэтому результат описан самым широким образом: все поля модели, каждое необязательное (необязательность касается только верхнего уровня, вложенные документы остаются такими, какие они в модели). Зато пути и смешение включения с исключением проверяются при запуске запроса, до обращения к базе.

Словарь, который строится из данных клиента, нужно обернуть в [`untrusted(fields, "projection")`](../policies/soft-delete-and-untrusted.mdx#untrusted). Функция возвращает ту же проекцию, но отказывается принимать ключи, которые начинаются с `$` или `+`: через `$` клиент превратил бы проекцию в вычисляемое выражение, а через `+` — прочитал бы скрытое поле, например хеш пароля.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient, untrusted } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
export const listUsers = (fieldsFromRequest: Record<string, 0 | 1>) =>
  Users.find().select(untrusted(fieldsFromRequest, "projection")).plain();

const rows = await listUsers({ name: 1 });
//    ^?
// → [{ _id: "…", name: "Alice" }, { _id: "…", name: "Bob" }, { _id: "…", name: "Carol" }]
```

Если в словаре оказался запрещённый ключ, запрос не строится:

```text
StrictModeError: untrusted value: "+passwordHash" at "+passwordHash" — a "+path" key inside data from outside would select a Hidden field; validate the input and build the projection yourself [sanitize]
```

`untrusted` — лишь дополнительная страховка, а не проверка входных данных: он не знает, какие поля вы готовы отдать. Сверяйте поля клиента со списком разрешённых и собирайте проекцию сами.

Если в словаре есть неизвестное поле или включение смешано с исключением, при запуске бросается та же ошибка, что и для литерала:

```text
StrictModeError: projection: "nope" is not a field of User [unknown-path]
QueryError: projection: cannot mix inclusion (name) and exclusion (tags); the server refuses it
```

### Ошибки

MongoDB не принимает включение и исключение в одной проекции: непонятно, что делать с полями, которые не упомянуты. Typemo ловит это раньше, чем запрос дойдёт до базы. Компилятор покажет ошибку прямо в редакторе:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2345
Users.find().select({ name: 1, tags: 0 });
```

В тексте компилятора есть свойство `"projection error"` с пояснением: `cannot mix inclusion ("name") and exclusion ("tags") in one projection`. А если проекция собралась во время работы программы, `.select` бросит [`QueryError`](../errors/query-errors.mdx#queryerror) сразу при вызове:

```text
QueryError: projection: cannot mix inclusion (name) and exclusion (tags); the server refuses it
```

Поле, которого нет в модели, не скомпилируется. Ошибка компилятора одна и та же на любой модели, с пояснением `unknown field "nope"` в том же свойстве `"projection error"`:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2345
Users.find().select({ nope: 1 });
```

Так же компилятор отвергает имя несуществующего скрытого поля: `select({ "+nope": true })` не компилируется, а в коде без типов даёт ошибку при запуске:

```text
StrictModeError: projection: "nope" is not a field of User [unknown-path]
```

Ключ `+имя` предназначен только для скрытых полей. Для обычного поля он ничего бы не менял (вернулись бы все поля), поэтому Typemo не молчит: компилятор такой ключ не принимает, а в коде без типов или в словаре `Record<string, 0 | 1>` запрос останавливается до обращения к базе со `StrictModeError` и отдельной причиной [`not-hidden`](../policies/violations.mdx#not-hidden): поле существует, но не скрыто.

```text
StrictModeError: projection: "+name" adds a Hidden field back, and "name" is not Hidden; select it without the "+" [not-hidden]
```

### Когда `.select` не подходит

Если поля нужно спрятать не только при чтении, а вообще скрыть от клиента или замаскировать значение, используйте [`hidden`](../schemas/prop.mdx#hidden) в модели и [`.mask`](./masks.mdx#mask). Если нужно проверить, что ответ имеет ровно заданную форму, добавьте [`.expect`](./contracts.mdx#expect).

## .sort

`.sort` задаёт порядок, в котором вернутся документы. Без него MongoDB возвращает документы в любом порядке, и этот порядок может меняться от запроса к запросу. Поэтому если порядок виден пользователю, например в списке или таблице, сортировку нужно задавать всегда.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const sorted = await Users.find().sort({ age: -1, name: 1 }).plain();
console.log(sorted.map((user) => user.name));
// → ["Alice", "Carol", "Bob"]
```

Здесь пользователи отсортированы по убыванию возраста. Alice и Carol одного возраста, поэтому между ними работает второй ключ — имя по алфавиту.

<Returns type="QueryBuilder">

Тот же строитель с сортировкой.

</Returns>

<Params>
<Param name="sort" type="Sort<T>" required>

Объект «поле → направление» или список пар `[поле, направление]`. `1` означает по возрастанию, `-1` — по убыванию; принимаются и слова `"asc"`, `"desc"`, `"ascending"`, `"descending"`. Компилятор подскажет доступные поля. После [`.textScore(name)`](./search-and-explain.mdx#textscore) поле оценки — тоже ключ сортировки, только с направлением `-1`: `.sort({ score: -1 })` сортирует по оценке, лучшие первыми.

</Param>
</Params>

<FullType>

```ts
sort(sort: Sort<T, ScoreKeys<T, N>>): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Список пар

Когда ключей сортировки несколько, их порядок важен: второй ключ работает только внутри одинаковых значений первого. В объекте этот порядок задаётся порядком записи ключей. Если вы хотите, чтобы он был очевиден при чтении кода, используйте список пар:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const sorted = await Users.find().sort([["age", -1], ["name", 1]]).plain();
console.log(sorted.map((user) => user.name));
// → ["Alice", "Carol", "Bob"]
```

### Несколько вызовов

Каждый следующий вызов `.sort` добавляет ключи в конец, а не заменяет предыдущие:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const sorted = await Users.find().sort({ age: -1 }).sort({ name: -1 }).plain();
// то же, что .sort({ age: -1, name: -1 })
console.log(sorted.map((user) => user.name));
// → ["Carol", "Alice", "Bob"]
```

Один и тот же путь дважды не сортируется: и в одном вызове, и в разных Typemo бросает `QueryError` с текстом `sort: "age" is sorted twice`. Так второй вызов не может незаметно оказаться бесполезным: ключ, который уже стоит в сортировке, нельзя переопределить.

## .limit <Badge>только find</Badge>

`.limit` ограничивает, сколько документов вернёт запрос. Используйте его всегда, когда список показывается пользователю: коллекция, в которой сегодня десять записей, через год может вырасти до миллиона, и запрос без ограничения положит приложение. Метод есть только у [`find`](#modelfind).

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const page = await Users.find().sort({ name: 1 }).limit(2).plain();
console.log(page.map((user) => user.name));
// → ["Alice", "Bob"]
```

<Returns type="QueryBuilder">

Тот же строитель с ограничением.

</Returns>

<Params>
<Param name="n" type="number" required>

Максимальное число документов. Должно быть целым и больше нуля.

</Param>
</Params>

<FullType>

```ts
limit(n: FindOnly<Op, number, "limit">): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Ноль и отрицательные числа

В MongoDB `limit(0)` означает «без ограничения», а отрицательное число включает особый режим, в котором сервер возвращает одну порцию и закрывает курсор. Оба правила неочевидны: `limit(0)` легко получить из пустого параметра запроса и неожиданно выгрузить всю коллекцию. Поэтому Typemo принимает только положительные целые числа. Компилятор само число не проверяет, ошибка приходит во время работы, сразу при вызове `.limit`:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
Users.find().limit(0); // [!code error]
// QueryError: limit must be a positive integer, got 0 (number)
```

Значение в тексте ошибки печатается вместе с типом, поэтому строку, которая выглядит как число, легко отличить от числа. Так бывает, когда предел пришёл из параметра URL: `limit("3")` бросает `limit must be a positive integer, got "3" (string)`. Преобразуйте такое значение сами, прежде чем передать его в `.limit`.

Если ограничение не нужно, не вызывайте `.limit`.

## .skip <Badge>только find</Badge>

`.skip` пропускает первые `n` документов. Вместе с [`.limit`](#limit) он даёт простой постраничный вывод: пропустить предыдущие страницы и взять одну. Метод есть только у [`find`](#modelfind).

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const pageNumber = 2;
const perPage = 2;

const page = await Users.find()
  .sort({ name: 1 })
  .skip((pageNumber - 1) * perPage)
  .limit(perPage)
  .plain();
console.log(page.map((user) => user.name));
// → ["Carol"]
```

Обязательно задавайте сортировку вместе с `.skip`. Без неё порядок документов не определён, и одни и те же записи могут оказаться на разных страницах.

<Returns type="QueryBuilder">

Тот же строитель с пропуском.

</Returns>

<Params>
<Param name="n" type="number" required>

Сколько документов пропустить. Должно быть целым и не меньше нуля.

</Param>
</Params>

<FullType>

```ts
skip(n: FindOnly<Op, number, "skip">): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Когда `.skip` не подходит

Чтобы пропустить `n` документов, MongoDB всё равно их прочитывает, а потом отбрасывает. На первых страницах это незаметно, но на тысячной странице с двадцатью записями база прочитает двадцать тысяч документов ради двадцати. Кроме того, если между запросами страниц кто-то добавил запись, документы сдвинутся, и пользователь увидит одну запись дважды или пропустит другую.

Для длинных списков и бесконечной прокрутки используйте [пагинацию по ключу](../../queries/keyset-pagination.mdx) и метод [`Model.keysetPage`](./keyset.mdx#modelkeysetpage). Там следующая страница начинается сразу после последнего показанного документа, и база не читает лишнего.

### Ошибки

Отрицательное или дробное число — ошибка во время работы, сразу при вызове `.skip`:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
Users.find().skip(-1); // [!code error]
// QueryError: skip must be a non-negative integer, got -1 (number)
```

## .orFail

`.orFail` превращает «ничего не найдено» в ошибку. Без него [`findOne`](#modelfindone) и [`findById`](#modelfindbyid) возвращают `null`, а `find` возвращает пустой массив, и вам приходится проверять результат перед каждым использованием. С ним вы получаете либо результат, либо исключение, а `null` пропадает из типа.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const user = await Users.findOne({ name: "Alice" }).plain().orFail();
//    ^?
console.log(user.name); // проверка на null не нужна
// → "Alice"
```

Используйте `.orFail`, когда отсутствие документа — ошибка с точки зрения вашей задачи. Например, пользователь открыл страницу заказа по ссылке, а заказа нет: это не обычная ситуация, а повод ответить 404.

<Returns type="QueryBuilder">

Тот же строитель. Если документ не найден, `await` бросает [`DocumentNotFoundError`](../errors/query-errors.mdx#documentnotfounderror) с полями `operation` и `model`. Фильтр в ошибку намеренно не попадает: он может содержать персональные данные.

</Returns>

Принимает ничего.

<FullType>

```ts
orFail(): QueryBuilder<T, Op, S, E, Form, true, N, X>
```

</FullType>

### Обработать «не найдено»

В тексте ошибки указаны модель и операция, поэтому в логах сразу видно, что именно не нашлось:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
await Users.findOne({ name: "Zed" }).orFail(); // [!code error]
// DocumentNotFoundError: User.findOne: no document matched the filter (orFail)
```

В тексте стоит имя метода, который вы вызвали: у `Users.findById(id).orFail()` это `User.findById`, у `Users.find(...).orFail()` — `User.find`.

Границу вашего приложения, например ответ 404, лучше строить в одном месте: перехватите `DocumentNotFoundError` там, где вы превращаете ошибки в ответы, а не в каждом обработчике.

```ts twoslash title="users/users.service.ts"
import { DocumentNotFoundError } from "@venloc/typemo";
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
declare class __NotFound__ extends Error {}
// ---cut---
export const getUser = async (name: string) => {
  try {
    return await Users.findOne({ name }).orFail().plain();
  } catch (error) {
    if (error instanceof DocumentNotFoundError) throw new __NotFound__(`${error.model} not found`);
    throw error;
  }
};
```

### С `find`

У `find` результат — массив, и «ничего не найдено» здесь значит «список пуст». `.orFail()` на `find` тоже считает пустой список ошибкой и бросает `DocumentNotFoundError`, а непустой список возвращает как обычно:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
await Users.find({ name: "Zed" }).orFail(); // [!code error]
// DocumentNotFoundError: User.find: no document matched the filter (orFail)

const found = await Users.find({ name: "Alice" }).orFail();
console.log(found.length);
// → 1
```

Пустой список бывает совершенно нормальным ответом: например, у пользователя пока нет заказов. Поэтому добавляйте `.orFail()` к `find` только там, где пустой результат означает сбой, а не «пока ничего нет».

С [`.cursor()`](#cursor) `.orFail()` ошибку не бросает: курсор отдаёт документы порциями и не знает заранее, что их не будет, поэтому на пустой выборке он просто завершается без единого документа.

## .lean

`.lean` возвращает данные ровно в том виде, в каком их отдал драйвер MongoDB, без создания документа. Такой результат читается быстрее всего: Typemo не строит объект с методами и не запоминает исходные значения для отслеживания изменений.

Чтобы показать значения разных типов, добавим ещё одну модель, кошелёк. В нём 64-битное число, точное десятичное число, дата и поле-словарь:

```ts twoslash title="models/wallet.ts"
import { Entity, Prop, Schema, Spec, Types } from "@venloc/typemo";
import type { Decimal128 } from "mongodb";

@Schema({ collection: "wallets" })
export class Wallet extends Entity {
  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => BigInt)
  points?: bigint;

  @Prop(() => Types.Decimal128)
  balance?: Decimal128;

  @Prop(() => Date)
  opened?: Date;

  @Prop(() => Spec.map(Number))
  limits?: Map<string, number>;
}
```

```ts twoslash
import { Entity, Prop, Schema, Spec, Types, TypemoClient } from "@venloc/typemo";
import type { Decimal128 } from "mongodb";
@Schema({ collection: "wallets" })
class Wallet extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => Types.Decimal128) balance?: Decimal128;
  @Prop(() => Date) opened?: Date;
  @Prop(() => Spec.map(Number)) limits?: Map<string, number>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Wallets = client.db().model(Wallet);
// ---cut---
const wallet = await Wallets.findOne({ owner: "w1" }).lean().orFail();
//    ^?
// → { _id: ObjectId("…"), owner: "w1", points: 9007199254740993n,
//     balance: Decimal128("10.50"), opened: 2026-01-02T00:00:00.000Z, limits: { daily: 100 } }
```

Значения остаются типами MongoDB: `_id` — объект `ObjectId`, 64-битные числа — `bigint`, точные десятичные — `Decimal128`. Поля-`Map` приходят обычными объектами, потому что именно так MongoDB их хранит. Как выглядит каждый тип, показано в справочнике [Формы значений](../values/value-forms.mdx).

<Returns type="QueryBuilder">

Тот же строитель. После `await` вы получаете lean-строки. Их тип учитывает [`.select`](#select) и [`populate`](../populate/populate.mdx): невыбранных полей в типе нет.

</Returns>

Принимает ничего.

<FullType>

```ts
lean(): QueryBuilder<T, Op, S, E, true, Found, N, X>
```

</FullType>

### Когда использовать

`.lean` подходит для работы внутри приложения, где нужны точные значения MongoDB: сложить очки в `bigint`, сравнить идентификаторы через `ObjectId.equals`, передать `_id` в следующий запрос.

Для ответа клиенту `.lean` не подходит. `JSON.stringify` не умеет сериализовать `bigint` и бросает `TypeError: JSON.stringify cannot serialize BigInt.`, а `ObjectId` и `Decimal128` клиенту ни о чём не говорят. Для ответов используйте [`.plain`](#plain). Как выбирать между документом, lean и plain, подробно разобрано в руководстве [Чтение данных](../../queries/reading-data.mdx#как-выбрать).

### Скрытые поля

`.lean` отдаёт всё, что было прочитано из базы, включая скрытые поля, которые вы запросили через `+`. Он предназначен для кода внутри приложения, а не для ответа клиенту, поэтому ничего не прячет:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const rows = await Users.find({ name: "Alice" }).select({ "+passwordHash": true }).lean();
// → [{ _id: ObjectId("…"), name: "Alice", age: 30, tags: ["admin", "dev"], passwordHash: "$argon2id$…" }]
```

## .plain

`.plain` возвращает данные, переведённые в обычные значения JavaScript. Это вид для всего, что уходит за пределы приложения: ответов API, сообщений в очередь, записей в кеш. Документ при этом не создаётся, поэтому `.plain` почти так же быстр, как [`.lean`](#lean).

```ts twoslash
import { Entity, Prop, Schema, Spec, Types, TypemoClient } from "@venloc/typemo";
import type { Decimal128 } from "mongodb";
@Schema({ collection: "wallets" })
class Wallet extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => Types.Decimal128) balance?: Decimal128;
  @Prop(() => Date) opened?: Date;
  @Prop(() => Spec.map(Number)) limits?: Map<string, number>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Wallets = client.db().model(Wallet);
// ---cut---
const wallet = await Wallets.findOne({ owner: "w1" }).plain().orFail();
//    ^?
// → { _id: "6abcde37…", owner: "w1", points: "9007199254740993", balance: "10.50",
//     opened: 2026-01-02T00:00:00.000Z, limits: Map(1) { "daily" => 100 } }
```

Вот как переводятся значения:
- `ObjectId`, `Decimal128` и UUID становятся строками.
- 64-битные целые становятся строками с типом `` `${bigint}` ``, чтобы не потерять точность при передаче в JSON.
- `Date` и `RegExp` остаются как есть.
- Поля-`Map` остаются `Map`.
- Связанные документы после [`populate`](../populate/populate.mdx) тоже переводятся, каждый по своей модели.
- Скрытые поля убираются.

<ValueForms types={["objectId", "long", "decimal", "date", "map"]} forms={["lean", "plain"]} />

Полная таблица по всем типам MongoDB — в справочнике [Формы значений](../values/value-forms.mdx).

<Returns type="QueryBuilder">

Тот же строитель. После `await` вы получаете plain-строки. Их тип учитывает [`.select`](#select), [`populate`](../populate/populate.mdx) и скрытые поля.

</Returns>

<Params>
<Param name="options.hidden" type="boolean" default="false">

Оставить скрытые поля, которые запрос прочитал через `+`. Тип результата тоже будет их включать. Любой другой ключ в `options` приводит к `QueryError` с текстом `plain: "x" is not an option (only "hidden")`.

</Param>
</Params>

<FullType>

```ts
plain(): QueryBuilder<T, Op, S, E, "plain", Found, N, X>
plain<const O extends PlainReadOptions>(
  options: O,
): QueryBuilder<T, Op, S, E, O extends { readonly hidden: true } ? "plain+hidden" : "plain", Found, N, X>
```

</FullType>

### Скрытые поля

Скрытое поле в plain-виде защищено дважды. Сначала его нужно прочитать через `+`, а потом ещё и разрешить отдать через `{ hidden: true }`. Без второго шага поле не попадёт в результат, даже если его прочитали:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const safe = await Users.findOne({ name: "Alice" })
  .select({ "+passwordHash": true })
  .plain()
  .orFail();
// → { _id: "…", name: "Alice", age: 30, tags: ["admin", "dev"] }

const full = await Users.findOne({ name: "Alice" })
  .select({ "+passwordHash": true })
  .plain({ hidden: true })
  .orFail();
// → { _id: "…", name: "Alice", age: 30, tags: ["admin", "dev"], passwordHash: "$argon2id$…" }
```

Так хеш пароля не утечёт в ответ API из-за того, что кто-то добавил `+passwordHash` в общий запрос для проверки пароля.

### `Map` в JSON

В plain-виде поля-`Map` остаются настоящими `Map`. Это удобно в коде, но `JSON.stringify` превращает `Map` в пустой объект без ошибки: на выходе `{"limits":{}}`, значения словаря молча пропали. Если вы отдаёте поле-`Map` клиенту, превратите его в объект сами, например через `Object.fromEntries(wallet.limits)`, или прочитайте документ без `.plain()` и вызовите его [`$toJSON()`](../documents/document-api.mdx#tojson): там `Map` уже превращён в объект.

### Что нельзя после `.plain()`

Результат `.plain()` — это данные, а не документ. У него нет [`$save()`](../documents/document-api.mdx#save) и других методов документа, и компилятор не даст их вызвать:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2339
const user = await Users.findOne({ name: "Alice" }).plain().orFail();
user.$save();
```

Если запись нужно изменить, прочитайте её без `.plain()` или используйте методы обновления: [`updateOne`](../writes/writes.mdx#updateone), [`findByIdAndUpdate`](../writes/writes.mdx#findbyidandupdate).

## .cursor <Badge>только find</Badge>

`.cursor` выполняет запрос и отдаёт документы по одному, по мере того как они приходят из базы. Обычный `await` сначала собирает все документы в массив и только потом отдаёт его вам. Курсор отдаёт первый документ сразу, а следующие подгружает порциями, пока вы их обрабатываете. Метод есть только у [`find`](#modelfind).

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
declare const __sendToWarehouse__: (user: { name: string }) => Promise<void>;
// ---cut---
for await (const user of Users.find().sort({ _id: 1 }).plain().cursor()) {
  await __sendToWarehouse__(user);
}
```

<Returns type="QueryCursor">

Курсор типа [`QueryCursor`](./cursor.mdx#querycursor): асинхронный итератор с методами `next`, `toArray`, `map`, `eachAsync` и `close`. Каждый элемент в том виде, который задала цепочка: документ, lean или plain. Все методы курсора — в справочнике [Курсор](./cursor.mdx). У `findOne` метод не компилируется, а в коде без типов бросает `QueryError` с текстом `cursor applies to find() only, not findOne()`.

</Returns>

Принимает ничего.

<FullType>

```ts
cursor(this: OnlyFor<Op, "find", "cursor() applies to find()">): QueryCursor<ResultDoc<T, S, E, Form, N, X>>
```

</FullType>

### Когда использовать

Курсор нужен, когда документов так много, что массив целиком не поместится в память или будет собираться слишком долго. Типичные случаи — выгрузка в другую систему, миграция данных, ночная пересборка отчётов.

Для списков на странице курсор не нужен: там всё равно показывается ограниченное число записей, и обычного `await` с [`.limit`](#limit) достаточно.

## .exec

`.exec` выполняет запрос и возвращает `Promise` с результатом. `await query` делает то же самое, поэтому в обычном коде `.exec()` писать не нужно. Он пригодится в двух случаях: когда вы хотите явно показать, что здесь запрос уходит в базу, и когда нужно выполнить уже выполненный запрос ещё раз.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const rows = await Users.find().plain().exec();
```

<Returns type="Promise">

`Promise` с результатом запроса.

</Returns>

<Params>
<Param name="options.force" type="boolean" default="false">

Выполнить запрос заново, даже если он уже выполнялся. Значение не boolean приводит к `QueryError` с текстом `find: exec({ force }) takes a boolean`: Typemo не приводит значения тихо.

</Param>
</Params>

<FullType>

```ts
exec(options?: ExecOptions): Promise<QueryOutput<T, Op, S, E, Form, Found, N, X>>
```

</FullType>

### Повторный `await`

Один строитель выполняет чтение только один раз. Если написать `await` для того же запроса повторно, вы получите тот же самый результат без нового обращения к базе:

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const query = Users.find().plain();

const first = await query; // → 3 пользователя
await Users.create({ name: "Dave", tags: [] });
const second = await query; // → те же 3 пользователя, тот же массив
console.log(first === second);
// → true

const fresh = await query.exec({ force: true });
// → 4 пользователя
```

Так случайный повторный `await`, например в двух ветках кода, не делает лишних запросов к базе. Если вам нужны свежие данные, вызовите `exec({ force: true })` или создайте новый запрос.
