Здесь собраны все методы модели, которые читают данные, и главные методы **строителя запроса**. Это объект, в котором запрос собирается по частям и уходит в базу только на `await`. Для каждого метода описано, что он принимает, что возвращает и где может вас удивить.

Если вы только начинаете работать с Typemo, сначала прочитайте руководство [Чтение данных](../../queries/reading-data.mdx). Оно объясняет, зачем нужны документ, `.lean()` и `.plain()` и как между ними выбирать. Эта страница — справочник, к ней возвращаются за конкретной деталью.

Во всех примерах одна модель пользователя. В ней есть обязательное поле, необязательное поле, массив и скрытое поле, так что на каждом методе видно, как он обращается с каждым видом полей.

```ts twoslash title="models/user.ts"
import { Entity, type Hidden, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true })
  name!: string;

  @Prop(() => Number)
  age?: number;

  @Prop(() => [String])
  tags!: string[];

  @Prop(() => String, { hidden: true })
  passwordHash?: Hidden<string>;
}
```

В коллекции три пользователя. Alice — 30 лет, теги `admin` и `dev`, хеш пароля `$argon2id$…`. Bob — 17 лет, тег `dev`. Carol — 30 лет, без тегов. Результаты в комментариях `// →` получены на этих данных. Идентификаторы в результатах сокращены до `"…"`, потому что база выдаёт их заново при каждой загрузке данных.

Методы строителя, которых нет на этой странице, перечислены в конце, в разделе [Остальные методы строителя](#other-builder-methods).

## Model.find [#model.find]

`find` находит все документы, которые подходят под фильтр, и возвращает их массивом. Это основной метод чтения. С него начинается почти любой список в приложении — пользователи на странице администратора, заказы клиента, записи для отчёта.

Сам по себе `find` к базе не обращается. Он возвращает [строитель запроса](#how-builder-works), и к нему цепочкой добавляют сортировку, ограничения и выбор полей. Запрос уходит в MongoDB, когда вы пишете `await`.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const adults = await Users.find({ age: { $gte: 18 } }).sort({ name: 1 });
console.log(adults.map((user) => user.name));
// → ["Alice", "Carol"]
```

<Returns type="QueryBuilder">

[Строитель запроса](#how-builder-works). После `await` вы получаете массив документов. Если под фильтр ничего не подошло, массив пустой, `find` никогда не возвращает `null`. Если пустой список для вас ошибка, добавьте [`.orFail()`](#or-fail).

</Returns>

<Params>
<Param name="filter" type="Filter<T>">

Условия поиска. Ключи — поля модели, значения — само значение поля или [операторы фильтра](./filter-operators.mdx), такие как `$gte`, `$in`, `$regex`. Компилятор знает поля и их типы, поэтому подскажет доступные ключи и не даст сравнить число со строкой. Если фильтр не передать, найдутся все документы.

</Param>
</Params>

<FullType>

```ts
find<F extends Filter<T, true>>(
  filter?: F & NoInfer<FilterCheck<T, F>>,
): QueryBuilder<T, "find", undefined, never, false, false, NoNarrowing, never>
```

</FullType>

### Все документы коллекции [#all-documents]

Чтобы прочитать всю коллекцию, вызовите `find` без аргумента или с пустым объектом. Для чтения эти варианты равнозначны.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const everyone = await Users.find();
const everyoneToo = await Users.find({});
console.log(everyone.length, everyoneToo.length);
// → 3 3
```

Пустой фильтр разрешён только в чтении, потому что чтение ничего не портит.

<Callout type="warning">

В [`updateMany`](../writes/writes.mdx#update-many), [`deleteMany`](../writes/writes.mdx#delete-many) и других методах записи Typemo пустой фильтр запрещает. Одна опечатка в коде, который собирает фильтр, и вы изменили бы или удалили всю коллекцию. Подробнее в статье [Пустые фильтры в записи](../../writes/empty-filters.mdx).

</Callout>

### Как Typemo проверяет фильтр [#how-filter-is-checked]

Фильтр проверяется дважды. Первый раз его проверяет компилятор, пока вы пишете код. Второй раз — сам Typemo, перед отправкой запроса в базу. Вторая проверка нужна, потому что фильтр часто собирается из данных, которых компилятор не видит. Это тело HTTP-запроса, параметры URL, конфигурация.

Допустим, вы опечатались в имени поля. Компилятор остановит вас сразу.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2345
Users.find({ nope: 1 });
```

Если же такой фильтр пришёл во время работы программы, Typemo откажется его выполнять, и до базы запрос не дойдёт.

```text
StrictModeError: filter: "nope" is not a field of User [unknown-path]
```

Путь в тексте называется один раз. Слово `filter` говорит, где искать ошибку, а `"nope"` — какое имя не подошло. MongoDB просто вернула бы пустой массив, потому что поля `nope` нет ни у одного документа. Ошибку в имени пришлось бы искать по странному поведению приложения. Typemo сообщает о ней сразу, через [`StrictModeError`](../errors/data-errors.mdx#strict-mode-error).

Фильтр, собранный во время работы, например типа `Record<string, unknown>` (или `{ [key: string]: unknown }`), компилятор принимает. Ключей такого объекта он не видит. То же верно для `findOne`, `countDocuments` и записей с фильтром. Поэтому опечатка в ключе такого фильтра всплывёт только при запуске запроса, теми же `StrictModeError` и `CastError`, а до базы запрос всё равно не дойдёт.

С типами значений то же самое. Возраст в модели — число, поэтому строка `"30"` не пройдёт ни компилятор, ни проверку во время работы.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2322
Users.find({ age: "30" });
```

```text
CastError: Cast to number failed at path "age" for "30" (string): expected a number [type]
```

Особый случай — `undefined`. В JavaScript его легко получить случайно, например из необязательного параметра запроса. Если бы Typemo молча превращал `{ age: undefined }` в «поле не задано», вы получили бы совсем не тех пользователей, которых искали. Компилятор такой фильтр не пропустит, а если он собран в коде без типов, `find` сразу при вызове бросит [`QueryError`](../errors/query-errors.mdx#query-error).

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2379
Users.find({ age: undefined });
```

```text
QueryError: filter: undefined at "age" (use $exists: false / $unset; undefined is never a value)
```

Если вы правда хотите найти документы без поля, скажите об этом явно — `{ age: { $exists: false } }`.

### Когда `find` не подходит [#model.find.when-not-to-use]

Если нужен один документ, берите [`findOne`](#model.find-one) или [`findById`](#model.find-by-id). Они возвращают сам документ или `null`, и доставать его из массива не придётся.

Если надо лишь узнать, есть ли подходящий документ, берите [`exists`](#model.exists). Он читает из базы один `_id`, а не документы целиком.

Если нужно число документов, берите [`countDocuments`](#model.count-documents). `find` загрузил бы в память все документы только ради длины массива.

Если документов очень много, десятки тысяч и больше, добавьте в конце [`.cursor()`](#cursor). Документы будут приходить по одному, и держать их все в памяти сразу не придётся.

## Model.findOne [#model.find-one]

`findOne` находит первый документ, который подходит под фильтр. Если такого документа нет, он возвращает `null`. Берите его, когда по смыслу задачи результат один — пользователь по email, настройки по ключу, последний заказ клиента.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const alice = await Users.findOne({ name: "Alice" }).plain();
//    ^?
console.log(alice?.name);
// → "Alice"
```

<Returns type="QueryBuilder">

[Строитель запроса](#how-builder-works). После `await` вы получаете документ или `null`. TypeScript не даст обратиться к полям результата, пока вы не проверите его на `null`. Если отсутствие документа для вас ошибка, добавьте [`.orFail()`](#or-fail). Вместо `null` будет брошена [`DocumentNotFoundError`](../errors/query-errors.mdx#document-not-found-error), а `null` исчезнет из типа.

</Returns>

<Params>
<Param name="filter" type="Filter<T>">

Условия поиска, такие же, как у [`find`](#model.find), и проверяются так же. Без фильтра `findOne` вернёт любой документ коллекции.

</Param>
</Params>

<FullType>

```ts
findOne<F extends Filter<T, true>>(
  filter?: F & NoInfer<FilterCheck<T, F>>,
): QueryBuilder<T, "findOne", undefined, never, false, false, NoNarrowing, never>
```

</FullType>

### Какой документ считается первым [#first-document]

MongoDB не хранит документы в определённом порядке и не обещает, в каком порядке их вернёт. Поэтому без сортировки «первый» документ — просто один из подходящих, и при следующем запросе он может оказаться другим.

Если важно, какой именно документ вернётся, задайте порядок через [`.sort`](#sort). Так, например, находят самого младшего пользователя.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const youngest = await Users.findOne().sort({ age: 1 }).plain();
// → { _id: "…", name: "Bob", age: 17, tags: ["dev"] }
```

### Когда `findOne` не подходит [#model.find-one.when-not-to-use]

Если вы знаете `_id` документа, берите [`findById`](#model.find-by-id). Он делает то же самое, но записывается короче и сразу проверяет id.

Если нужно несколько первых документов, например пять последних заказов, берите [`find`](#model.find) вместе с [`.sort`](#sort) и [`.limit`](#limit).

## Model.findById [#model.find-by-id]

`findById` находит документ по `_id`. Это самый частый способ прочитать одну конкретную запись — страница профиля, карточка товара, заказ по ссылке из письма. По смыслу он такой же, как [`findOne`](#model.find-one) с фильтром `{ _id: id }`. Отличие в том, что он принимает id в двух видах и защищает от пустого id.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
import { ObjectId } from "mongodb";
const id = new ObjectId();
// ---cut---
const user = await Users.findById(id);
// → null (документа с таким id нет)
```

<Returns type="QueryBuilder">

[Строитель запроса](#how-builder-works). После `await` вы получаете документ или `null`, как у [`findOne`](#model.find-one).

</Returns>

<Params>
<Param name="id" type="тип поля _id, либо его строка" required>

Идентификатор документа. У моделей, унаследованных от [`Entity`](../schemas/base-classes.mdx#entity), это `ObjectId` или его строка из 24 шестнадцатеричных символов. Если `_id` в вашей модели другого типа, например число, `findById` ожидает именно его. Для `UUID` подходит его каноническая строка.

</Param>
</Params>

<FullType>

```ts
findById(id: IdInputOf<T>): QueryBuilder<T, "findOne", undefined, never, false, false, NoNarrowing, never>
```

</FullType>

### id из URL или тела запроса [#id-from-request]

Чаще всего id приходит от клиента — из адреса вроде `/users/6abcddec50864200b93c7fea` (24 шестнадцатеричных символа) или из JSON в теле запроса. В обоих случаях это строка, и `findById` принимает её как есть. Приводить строку к `ObjectId` самому не нужно.

```ts twoslash title="users/users.service.ts"
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
export const getUserName = async (idFromUrl: string): Promise<string | undefined> => {
  const user = await Users.findById(idFromUrl).plain();
  return user?.name;
};

const alice = await Users.findOne({ name: "Alice" }).plain().orFail();
console.log(await getUserName(alice._id)); // _id в plain-виде уже строка
// → "Alice"
```

Формат строки Typemo проверяет сам. Если строка не похожа на идентификатор, запрос в базу не уходит, а `await` завершается ошибкой [`CastError`](../errors/data-errors.mdx#cast-error).

```text
CastError: Cast to ObjectId failed at path "_id" for "abc" (string): not a 24-character hex string [format]
```

Это ошибка данных клиента, а не сбой сервера. Ваш код может поймать `CastError` и ответить клиенту, что id неверный. Разбирать строку перед вызовом самому для этого не нужно.

```ts twoslash title="users/users.service.ts"
import { CastError } from "@venloc/typemo";
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
declare class __BadRequest__ extends Error {}
// ---cut---
export const getUserByUrlId = async (idFromUrl: string) => {
  try {
    return await Users.findById(idFromUrl).orFail().plain();
  } catch (error) {
    if (error instanceof CastError) throw new __BadRequest__("the id is malformed");
    throw error;
  }
};
```

### Пустой id [#empty-id]

Если передать `null` или `undefined`, компилятор это не пропустит. А если пустой id пришёл из кода без типов, `findById` бросит ошибку сразу при вызове и в базу не пойдёт.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2345
Users.findById(undefined);
```

```text
QueryError: findById: an id is required
```

Это защита от тихой ошибки. Запрос по `{ _id: undefined }` мог бы превратиться в поиск по `null`, вернуть `null`, и приложение ответило бы «не найдено». Настоящая проблема, то есть потерянный где-то в вашем коде id, осталась бы незамеченной.

### Когда `findById` не подходит [#model.find-by-id.when-not-to-use]

Если вы ищете не по `_id`, а по другому полю, берите [`findOne`](#model.find-one). Если нужно найти сразу несколько документов по списку id, берите [`find`](#model.find) с оператором [`$in`](./filter-operators.mdx#in).

## Model.exists [#model.exists]

`exists` отвечает на вопрос «есть ли хотя бы один подходящий документ». Он нужен для проверок перед действием — занят ли email при регистрации, есть ли у клиента активный заказ, существует ли запись, на которую ссылаются.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const taken = await Users.exists({ name: "Alice" });
//    ^?
// → { _id: ObjectId("…") }

const free = await Users.exists({ name: "Zed" });
// → null
```

<Returns type="OptionQuery<{ _id } | null>">

Запрос, который после `await` даёт объект с `_id` найденного документа или `null`. В условии его удобно использовать как логическое значение — `if (await Users.exists(…))`. Запрос принимает те же [опции](./options.mdx), что и другие запросы значений, то есть `.session`, `.policy`, `.hint`, `.collation`, `.comment`, `.timeoutMS`.

</Returns>

<Params>
<Param name="filter" type="Filter<T>" required>

Условия поиска, как у [`find`](#model.find). В отличие от `find`, здесь фильтр обязателен. Вопрос «есть ли в коллекции хоть что-нибудь» почти всегда означает ошибку в коде.

</Param>
</Params>

<FullType>

```ts
exists<F extends Filter<T, true>>(
  filter: F & NoInfer<FilterCheck<T, F>>,
): OptionQuery<{ _id: IdOf<T> } | null>
```

</FullType>

### Почему не `findOne` [#why-not-find-one]

Результат был бы тем же, но [`findOne`](#model.find-one) прочитал бы документ целиком и построил бы из него объект. `exists` просит у базы только `_id`. Для проверки «есть или нет» остальные поля не нужны, а на больших документах разница заметна.

## Model.countDocuments [#model.count-documents]

`countDocuments` считает документы, которые подходят под фильтр. Он нужен, когда требуется само число — общее количество записей для постраничного вывода, счётчик непрочитанных сообщений, число заказов за день.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";

const thirty = await Users.countDocuments({ age: 30 });
// → 2

const total = await Users.countDocuments();
// → 3
```

Остальные [опции](./options.mdx) — `.session`, `.policy`, `.hint`, `.collation`, `.comment`, `.timeoutMS` — тоже доступны.

</Returns>

### Посчитать «не больше чем» [#count-up-to]

Иногда точное число не нужно, достаточно знать, превышает ли оно порог. Например, показать «99+» вместо точного числа уведомлений. `.limit` останавливает подсчёт, как только набралось нужное количество, и базе не приходится проходить все документы.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const count = await Users.countDocuments().limit(2);
// → 2, хотя пользователей три
```

`.limit` у `countDocuments` принимает только положительное целое, а `.skip` — целое не меньше нуля. Иначе запрос бросает `QueryError` с текстом `limit must be a positive integer, got 0 (number)`.

### Когда `countDocuments` не подходит [#model.count-documents.when-not-to-use]

Если нужен размер всей коллекции без фильтра, а точность не важна, например для панели мониторинга, берите [`estimatedDocumentCount`](#model.estimated-document-count). Он не проходит по документам и отвечает мгновенно даже на миллионах записей.

## Model.estimatedDocumentCount [#model.estimated-document-count]

`estimatedDocumentCount` возвращает число документов в коллекции, не читая сами документы. MongoDB берёт его из служебных данных коллекции, поэтому ответ приходит мгновенно на коллекции любого размера.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const approx = await Users.estimatedDocumentCount();
// → 3
```

<Returns type="OptionQuery<number>">

Запрос, который после `await` даёт число. Опции запроса такие же, как у [`exists`](#model.exists).

</Returns>

Принимает ничего. Фильтра здесь быть не может, потому что служебные данные хранят только общее количество.

<FullType>

```ts

```

</FullType>

### Насколько число точное [#precision]

Обычно число совпадает с настоящим. Но после аварийной остановки сервера, в шардированном кластере или во время активной записи оно может ненадолго отличаться. Для статистики и мониторинга это неважно. Если от числа зависит логика приложения, например постраничный вывод, берите [`countDocuments`](#model.count-documents).

### Мягкое удаление, тенанты и дискриминаторы [#soft-delete-tenants-discriminators]

Служебные данные коллекции знают только общее число документов. Они не знают, какие документы помечены удалёнными, какому тенанту принадлежит каждый документ и к какой модели-наследнику он относится. Поэтому в трёх случаях `estimatedDocumentCount` дал бы число, которое выглядит правильным, но считает не то, что вы ждёте. Typemo в этих случаях неверным числом не отвечает. Он бросает ошибку и подсказывает, что использовать вместо него.

Если у модели включено [мягкое удаление](../../policies/soft-delete.mdx), в число попали бы и удалённые документы.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
// ---cut---
@Schema({ collection: "accounts", softDelete: true })
class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => Date, { nullable: true })
  deletedAt?: Date | null;
}

const Accounts = client.db().model(Account);

await Accounts.estimatedDocumentCount(); // [!code error]
```

```text
StrictModeError: Account.estimatedDocumentCount: the collection's metadata counts soft-deleted documents too; use countDocuments() (or includeDeleted: true to count them all) [soft-delete]
```

Если вам правда нужно число всех документов вместе с удалёнными, скажите об этом явно через [`.policy()`](./options.mdx#policy).

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
@Schema({ collection: "accounts", softDelete: true })
class Account extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const Accounts = client.db().model(Account);
// ---cut---
const withDeleted = await Accounts.estimatedDocumentCount().policy({ includeDeleted: true });
// → 3 (две живые записи и одна удалённая)
```

Если у модели есть [поле тенанта](../../policies/tenants.mdx), в число попали бы документы всех тенантов, а не только текущего. Тогда `estimatedDocumentCount` тоже бросает ошибку и советует `countDocuments`, который учитывает тенанта. Здесь модель называется `Order`.

```text
StrictModeError: Order.estimatedDocumentCount: estimatedDocumentCount reads the collection's metadata and would count every tenant; use countDocuments() (scoped by the tenant) [tenant]
```

Если число по всем тенантам нужно осознанно, передайте `.policy({ allTenants: true })`.

Если модель — [дискриминатор](../../schemas/discriminators.mdx), то есть наследник, который хранится в общей коллекции с базовой моделью, в число попали бы документы всех наследников. Typemo бросает [`ConfigurationError`](../errors/configuration-errors.mdx#configuration-error) и предлагает `countDocuments`. Здесь наследник называется `CardPayment`.

```text
ConfigurationError: estimatedDocumentCount of the discriminator CardPayment would count every document of the collection; use countDocuments
```

## Как работает строитель [#how-builder-works]

[`find`](#model.find), [`findOne`](#model.find-one) и [`findById`](#model.find-by-id) к базе сразу не обращаются. Они возвращают **строитель запроса** — объект, в котором запрос собирается по частям. Цепочкой вызовов вы добавляете сортировку, ограничения, выбор полей и указываете, в каком виде нужен результат. Запрос уходит в MongoDB, только когда вы пишете `await`, вызываете [`.exec()`](#exec) или [`.cursor()`](#cursor).

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const query = Users.find({ age: { $gte: 18 } })
  .sort({ name: 1 })
  .limit(10)
  .select({ name: 1 })
  .plain();
// в базу ещё ничего не ушло

const rows = await query;
//    ^?
// → [{ _id: "…", name: "Alice" }, { _id: "…", name: "Carol" }]
```

Благодаря этому запрос можно собирать в нескольких местах кода. Одна функция добавляет фильтр по правам пользователя, другая — сортировку из параметров URL, а выполняется запрос один раз, в конце.

Строитель неизменяемый. Каждый метод возвращает **новый** строитель и предыдущий не трогает. Поэтому общий запрос можно спокойно расширять в разных местах, не боясь испортить чужую цепочку.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const base = Users.find({ age: 30 }).sort({ name: 1 });
const first = base.limit(1);

console.log((await base).length, (await first).length);
// → 2 1
```

Каждый метод цепочки меняет не только сам запрос, но и тип результата. После [`.select({ name: 1 })`](#select) в типе остаются только `_id` и `name`, и обратиться к `age` уже не получится. После [`.plain()`](#plain) все значения в типе принимают форму результата `.plain()`. После [`.orFail()`](#or-fail) из типа пропадает `null`. Порядок вызовов не важен. `.plain().select(…)` и `.select(…).plain()` дают один и тот же результат и один и тот же тип.

Методы, которые не имеют смысла для операции, не компилируются. Например, [`.skip`](#skip) и [`.cursor`](#cursor) есть только у `find`. Пропускать документы или отдавать их по одному, когда результат заведомо один, бессмысленно.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2345
Users.findOne().skip(1);
```

Текст компилятора сразу называет причину — `skip() applies to find()`. Если то же самое собрано в коде без типов, проверка во время работы бросает `QueryError` с текстом `skip applies to find() only, not findOne()`.

### Строитель как `Promise` [#builder-as-promise]

Строитель запроса ведёт себя как `Promise` результата. У него есть `then`, `catch` и `finally`, а `Object.prototype.toString.call(query)` печатает `[object TypemoQuery]`. Поэтому функцию можно объявить возвращающей `Promise` и вернуть из неё запрос прямо, без `async` и без `await`.

```ts twoslash
import { Entity, type HydratedDoc, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
export const getUser = (id: string): Promise<HydratedDoc<User>> => Users.findById(id).orFail();

const alice = await Users.findOne({ name: "Alice" }).orFail();
const loaded = await getUser(String(alice._id));
console.log(loaded.name);
// → "Alice"
```

Запрос при этом не выполняется, пока кто-нибудь не вызовет `then` (это делает `await`), `catch`, `finally`, [`.exec()`](#exec) или [`.cursor()`](#cursor). Создание строителя в базу ничего не отправляет.

В одном месте строитель `Promise` не заменяет. По нему нельзя итерировать. `for await` по самому запросу бросает `QueryError` с подсказкой, что нужен курсор.

```text
QueryError: find(): a query is not iterable with "for await"; iterate its cursor instead: for await (const doc of Model.find(filter).cursor())
```

Запрос — это обещание результата, а не поток, и цикл по нему смысла не имеет. Без этой проверки вы получили бы общий `TypeError` среды выполнения («не итерируемый объект»), как у запросов значений вроде `countDocuments`. У `findOne` текст тот же, но начинается с `findOne():`.

## .select [#select]

`.select` выбирает, какие поля документа вернуть из базы. Это полезно по двум причинам. Во-первых, по сети идёт меньше данных, и список пользователей для выпадающего меню не тащит за собой теги и настройки. Во-вторых, тип результата сужается вместе с выбором, и компилятор не даст случайно обратиться к полю, которое вы не загрузили.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const rows = await Users.find({ name: "Alice" }).select({ name: 1, age: 1 }).plain();
//    ^?
// → [{ _id: "…", name: "Alice", age: 30 }]
```

<Returns type="QueryBuilder">

Тот же строитель, но в типе результата остаются только выбранные поля.

</Returns>

<Params>
<Param name="projection" type="Projection<T>" required>

Объект, где ключи — поля модели, а значения говорят, что с ними делать. Форм три, и первые две в одном вызове смешивать нельзя.

- **Включение** — `{ name: 1, age: 1 }`. Вернуть только эти поля и `_id`.
- **Исключение** — `{ tags: 0 }`. Вернуть все поля, кроме этих.
- **Скрытое поле** — `{ "+passwordHash": true }`. Добавить скрытое поле к обычному набору полей.

Для массивов проекция принимает ещё `$slice` и `$elemMatch`.

Принимаются и проекции, формы которых компилятор не видит. Это значение объявленного типа [`Projection<T>`](../values/query-types.mdx#projection), словарь `Record<string, 0 | 1>` и данные извне, обёрнутые в [`untrusted(fields, "projection")`](../policies/soft-delete-and-untrusted.mdx#untrusted). Для них результат — все поля модели, каждое необязательное, а пути и смешение включения с исключением проверяются при запуске.

</Param>
</Params>

<FullType>

```ts
select<const P extends Projection<T> & { readonly [key: string]: unknown }>(
  projection: P & ProjectionCheck<T, P>,
): QueryBuilder<T, Op, MergeProjection<S, AnyProjection<P>>, E, Form, Found, N, X>
```

</FullType>

### Без `_id` [#without-id]

MongoDB возвращает `_id`, даже если вы его не выбирали. Обычно это удобно, по `_id` клиент потом запросит конкретную запись. Если `_id` не нужен, например для экспорта в таблицу, исключите его явно. Это единственное поле, которое можно исключить внутри включения.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const names = await Users.find({ age: 30 }).select({ name: 1, _id: 0 }).plain().sort({ name: 1 });
//    ^?
// → [{ name: "Alice" }, { name: "Carol" }]
```

### Скрытое поле [#hidden-field]

Поля с опцией [`hidden`](../schemas/prop.mdx#hidden) Typemo из базы не читает, пока вы о них не попросите. Так хеш пароля не окажется в памяти приложения, когда он не нужен. Чтобы прочитать скрытое поле, поставьте `+` перед его именем.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const user = await Users.findOne({ name: "Alice" })
  .select({ "+passwordHash": true })
  .orFail();

console.log(user.passwordHash);
// → "$argon2id$…"
```

Обратите внимание, что `+` выбор во включение не превращает. Вы получаете все обычные поля и вдобавок скрытое. `+` у поля, которое не скрыто, — ошибка (текст и причина в описании [`.select`](#select), в конце раздела про проверку имён).

Прочитать поле — не значит отдать его клиенту. В [`.plain()`](#plain) и [`$toPlain()`](../documents/document-api.mdx#to-plain) загруженное скрытое поле без опции `{ hidden: true }` не попадёт. Подробнее в разделе [`.plain`](#plain).

### Несколько вызовов [#select.multiple-calls]

Если вызвать `.select` несколько раз, выборы складываются. Это удобно, когда запрос собирается в разных местах кода.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const rows = await Users.find({ name: "Alice" }).select({ name: 1 }).select({ age: 1 }).plain();
//    ^?
// → [{ _id: "…", name: "Alice", age: 30 }]
```

Один и тот же ключ дважды не выбирается, как и в `.sort`. Второй вызов с тем же ключом бросает `QueryError` с текстом `projection: "name" is selected twice`. Повторный вызов не может ни остаться незамеченным, ни противоречить первому.

### Проекция, собранная во время работы [#runtime-projection]

Обычно проекцию записывают литералом, и компилятор видит все её ключи. Но набор полей бывает и внешним. Функция принимает проекцию параметром, а клиент API сам выбирает поля строкой `?fields=name,age`. Для таких случаев `.select` принимает значение объявленного типа [`Projection<T>`](../values/query-types.mdx#projection) и словарь `Record<string, 0 | 1>`. Обходить проверку типов приведением не нужно.

```ts twoslash
import { Entity, type Hidden, Prop, type Projection, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const fields: Projection<User> = { name: 1, age: 1 };
const rows = await Users.find({ name: "Alice" }).select(fields).plain();
//    ^?
// → [{ _id: "…", name: "Alice", age: 30 }]
```

Компилятор не знает, какие ключи окажутся в `fields`, поэтому результат описан самым широким образом. Это все поля модели, каждое необязательное (необязательность касается только верхнего уровня, вложенные документы остаются такими, как в модели). Зато пути и смешение включения с исключением проверяются при запуске запроса, до обращения к базе.

Словарь, который строится из данных клиента, оберните в [`untrusted(fields, "projection")`](../policies/soft-delete-and-untrusted.mdx#untrusted). Функция возвращает ту же проекцию, но отказывается принимать ключи, которые начинаются с `$` или `+`. Через `$` клиент превратил бы проекцию в вычисляемое выражение, а через `+` прочитал бы скрытое поле, например хеш пароля.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient, untrusted } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
export const listUsers = (fieldsFromRequest: Record<string, 0 | 1>) =>
  Users.find().select(untrusted(fieldsFromRequest, "projection")).plain();

const rows = await listUsers({ name: 1 });
//    ^?
// → [{ _id: "…", name: "Alice" }, { _id: "…", name: "Bob" }, { _id: "…", name: "Carol" }]
```

Если в словаре оказался запрещённый ключ, запрос не строится.

```text
StrictModeError: untrusted value: "+passwordHash" at "+passwordHash" — a "+path" key inside data from outside would select a Hidden field; validate the input and build the projection yourself [sanitize]
```

`untrusted` — лишь дополнительная страховка, а не проверка входных данных. Он не знает, какие поля вы готовы отдать. Сверяйте поля клиента со списком разрешённых и собирайте проекцию сами.

Если в словаре есть неизвестное поле или включение смешано с исключением, при запуске бросается та же ошибка, что и для литерала.

```text
StrictModeError: projection: "nope" is not a field of User [unknown-path]
QueryError: projection: cannot mix inclusion (name) and exclusion (tags); the server refuses it
```

### Ошибки [#select.errors]

MongoDB не принимает включение и исключение в одной проекции, потому что непонятно, что делать с неупомянутыми полями. Typemo ловит это раньше, чем запрос дойдёт до базы. Компилятор покажет ошибку прямо в редакторе.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2345
Users.find().select({ name: 1, tags: 0 });
```

В тексте компилятора есть свойство `"projection error"` с пояснением `cannot mix inclusion ("name") and exclusion ("tags") in one projection`. Если проекция собралась во время работы программы, `.select` сразу при вызове бросит [`QueryError`](../errors/query-errors.mdx#query-error).

```text
QueryError: projection: cannot mix inclusion (name) and exclusion (tags); the server refuses it
```

Поле, которого нет в модели, не скомпилируется. Ошибка компилятора одна и та же на любой модели, с пояснением `unknown field "nope"` в том же свойстве `"projection error"`.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2345
Users.find().select({ nope: 1 });
```

Так же компилятор отвергает имя несуществующего скрытого поля. `select({ "+nope": true })` не компилируется, а в коде без типов даёт ошибку при запуске.

```text
StrictModeError: projection: "nope" is not a field of User [unknown-path]
```

Ключ `+имя` предназначен только для скрытых полей. Для обычного поля он ничего бы не менял, вернулись бы все поля, поэтому Typemo не молчит. Компилятор такой ключ не принимает, а в коде без типов или в словаре `Record<string, 0 | 1>` запрос останавливается до обращения к базе. Typemo бросает `StrictModeError` с отдельной причиной [`not-hidden`](../policies/violations.mdx#not-hidden) — поле существует, но не скрыто.

```text
StrictModeError: projection: "+name" adds a Hidden field back, and "name" is not Hidden; select it without the "+" [not-hidden]
```

### Когда `.select` не подходит [#select.when-not-to-use]

Если поля надо спрятать не только при чтении, а вообще скрыть от клиента или замаскировать значение, берите [`hidden`](../schemas/prop.mdx#hidden) в модели и [`.mask`](./masks.mdx#mask). Если нужно проверить, что ответ имеет ровно заданную форму, добавьте [`.expect`](./contracts.mdx#expect).

## .sort [#sort]

`.sort` задаёт порядок, в котором вернутся документы. Без него MongoDB отдаёт документы в любом порядке, и этот порядок может меняться от запроса к запросу. Поэтому если порядок виден пользователю, например в списке или таблице, сортировку надо задавать всегда.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const sorted = await Users.find().sort({ age: -1, name: 1 }).plain();
console.log(sorted.map((user) => user.name));
// → ["Alice", "Carol", "Bob"]
```

Здесь пользователи отсортированы по убыванию возраста. Alice и Carol одного возраста, и между ними работает второй ключ — имя по алфавиту.

<Returns type="QueryBuilder">

Тот же строитель с сортировкой.

</Returns>

<Params>
<Param name="sort" type="Sort<T>" required>

Объект «поле → направление» или список пар `[поле, направление]`. `1` значит по возрастанию, `-1` — по убыванию. Принимаются и слова `"asc"`, `"desc"`, `"ascending"`, `"descending"`. Компилятор подскажет доступные поля. После [`.textScore(name)`](./search-and-explain.mdx#text-score) поле оценки тоже становится ключом сортировки, только с направлением `-1`. `.sort({ score: -1 })` сортирует по оценке, лучшие первыми.

</Param>
</Params>

<FullType>

```ts
sort(sort: Sort<T, ScoreKeys<T, N>>): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Список пар [#pairs]

Когда ключей сортировки несколько, их порядок важен. Второй ключ работает только внутри одинаковых значений первого. В объекте этот порядок задаётся порядком записи ключей. Если хотите, чтобы он был очевиден при чтении кода, используйте список пар.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const sorted = await Users.find().sort([["age", -1], ["name", 1]]).plain();
console.log(sorted.map((user) => user.name));
// → ["Alice", "Carol", "Bob"]
```

### Несколько вызовов [#sort.multiple-calls]

Каждый следующий вызов `.sort` добавляет ключи в конец, а не заменяет предыдущие.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const sorted = await Users.find().sort({ age: -1 }).sort({ name: -1 }).plain();
// то же, что .sort({ age: -1, name: -1 })
console.log(sorted.map((user) => user.name));
// → ["Carol", "Alice", "Bob"]
```

Один и тот же путь дважды не сортируется, ни в одном вызове, ни в разных. Typemo бросает `QueryError` с текстом `sort: "age" is sorted twice`. Второй вызов не может незаметно оказаться бесполезным, ведь ключ, который уже стоит в сортировке, переопределить нельзя.

## .limit <Badge>только find</Badge> [#limit]

`.limit` ограничивает, сколько документов вернёт запрос. Ставьте его всегда, когда список показывается пользователю. Коллекция, где сегодня десять записей, через год может вырасти до миллиона, и запрос без ограничения положит приложение. Метод есть только у [`find`](#model.find).

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const page = await Users.find().sort({ name: 1 }).limit(2).plain();
console.log(page.map((user) => user.name));
// → ["Alice", "Bob"]
```

<Returns type="QueryBuilder">

Тот же строитель с ограничением.

</Returns>

<Params>
<Param name="n" type="number" required>

Максимальное число документов. Целое число больше нуля.

</Param>
</Params>

<FullType>

```ts
limit(n: FindOnly<Op, number, "limit">): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Ноль и отрицательные числа [#zero-and-negative]

В MongoDB `limit(0)` значит «без ограничения», а отрицательное число включает особый режим, где сервер возвращает одну порцию и закрывает курсор. Оба правила неочевидны. `limit(0)` легко получить из пустого параметра запроса и неожиданно выгрузить всю коллекцию. Поэтому Typemo принимает только положительные целые числа. Компилятор само число не проверяет, ошибка приходит во время работы, сразу при вызове `.limit`.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
Users.find().limit(0); // [!code error]
// QueryError: limit must be a positive integer, got 0 (number)
```

Значение в тексте ошибки печатается вместе с типом, так что строку, которая выглядит как число, легко отличить от числа. Так бывает, когда предел пришёл из параметра URL. `limit("3")` бросает `limit must be a positive integer, got "3" (string)`. Преобразуйте такое значение сами, прежде чем передать в `.limit`.

Если ограничение не нужно, не вызывайте `.limit`.

## .skip <Badge>только find</Badge> [#skip]

`.skip` пропускает первые `n` документов. Вместе с [`.limit`](#limit) он даёт простой постраничный вывод — пропустить предыдущие страницы и взять одну. Метод есть только у [`find`](#model.find).

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const pageNumber = 2;
const perPage = 2;

const page = await Users.find()
  .sort({ name: 1 })
  .skip((pageNumber - 1) * perPage)
  .limit(perPage)
  .plain();
console.log(page.map((user) => user.name));
// → ["Carol"]
```

Всегда задавайте сортировку вместе с `.skip`. Без неё порядок документов не определён, и одни и те же записи могут оказаться на разных страницах.

<Returns type="QueryBuilder">

Тот же строитель с пропуском.

</Returns>

<Params>
<Param name="n" type="number" required>

Сколько документов пропустить. Целое число не меньше нуля.

</Param>
</Params>

<FullType>

```ts
skip(n: FindOnly<Op, number, "skip">): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Когда `.skip` не подходит [#skip.when-not-to-use]

Чтобы пропустить `n` документов, MongoDB всё равно их читает, а потом отбрасывает. На первых страницах это незаметно, но на тысячной странице с двадцатью записями база прочитает двадцать тысяч документов ради двадцати. К тому же, если между запросами страниц кто-то добавил запись, документы сдвинутся. Пользователь увидит одну запись дважды или пропустит другую.

Для длинных списков и бесконечной прокрутки берите [пагинацию по ключу](../../queries/keyset-pagination.mdx) и метод [`Model.keysetPage`](./keyset.mdx#model.keyset-page). Там следующая страница начинается сразу после последнего показанного документа, и база лишнего не читает.

### Ошибки [#skip.errors]

Отрицательное или дробное число — ошибка во время работы, сразу при вызове `.skip`.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
Users.find().skip(-1); // [!code error]
// QueryError: skip must be a non-negative integer, got -1 (number)
```

## .orFail [#or-fail]

`.orFail` превращает «ничего не найдено» в ошибку. Без него [`findOne`](#model.find-one) и [`findById`](#model.find-by-id) возвращают `null`, а `find` — пустой массив, и результат приходится проверять перед каждым использованием. С ним вы получаете либо результат, либо исключение, а `null` пропадает из типа.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const user = await Users.findOne({ name: "Alice" }).plain().orFail();
//    ^?
console.log(user.name); // проверка на null не нужна
// → "Alice"
```

Берите `.orFail`, когда отсутствие документа — ошибка с точки зрения вашей задачи. Скажем, пользователь открыл страницу заказа по ссылке, а заказа нет. Это не обычная ситуация, а повод ответить 404.

<Returns type="QueryBuilder">

Тот же строитель. Если документ не найден, `await` бросает [`DocumentNotFoundError`](../errors/query-errors.mdx#document-not-found-error) с полями `operation` и `model`. Фильтр в ошибку намеренно не попадает, ведь он может содержать персональные данные.

</Returns>

Принимает ничего.

<FullType>

```ts
orFail(): QueryBuilder<T, Op, S, E, Form, true, N, X>
```

</FullType>

### Обработать «не найдено» [#handle-not-found]

В тексте ошибки указаны модель и операция, так что в логах сразу видно, что именно не нашлось.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
await Users.findOne({ name: "Zed" }).orFail(); // [!code error]
// DocumentNotFoundError: User.findOne: no document matched the filter (orFail)
```

В тексте стоит имя метода, который вы вызвали. У `Users.findById(id).orFail()` это `User.findById`, у `Users.find(...).orFail()` — `User.find`.

Границу приложения, например ответ 404, лучше строить в одном месте. Перехватывайте `DocumentNotFoundError` там, где вы превращаете ошибки в ответы, а не в каждом обработчике.

```ts twoslash title="users/users.service.ts"
import { DocumentNotFoundError } from "@venloc/typemo";
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
declare class __NotFound__ extends Error {}
// ---cut---
export const getUser = async (name: string) => {
  try {
    return await Users.findOne({ name }).orFail().plain();
  } catch (error) {
    if (error instanceof DocumentNotFoundError) throw new __NotFound__(`${error.model} not found`);
    throw error;
  }
};
```

### С `find` [#with-find]

У `find` результат — массив, и «ничего не найдено» значит «список пуст». `.orFail()` на `find` тоже считает пустой список ошибкой и бросает `DocumentNotFoundError`, а непустой список возвращает как обычно.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
await Users.find({ name: "Zed" }).orFail(); // [!code error]
// DocumentNotFoundError: User.find: no document matched the filter (orFail)

const found = await Users.find({ name: "Alice" }).orFail();
console.log(found.length);
// → 1
```

Пустой список бывает совершенно нормальным ответом, скажем, у пользователя пока нет заказов. Поэтому добавляйте `.orFail()` к `find` только там, где пустой результат означает сбой, а не «пока ничего нет».

С [`.cursor()`](#cursor) `.orFail()` ошибку не бросает. Курсор отдаёт документы порциями и заранее не знает, что их не будет, поэтому на пустой выборке он просто завершается без единого документа.

## .lean [#lean]

`.lean` возвращает данные ровно в том виде, в каком их отдал драйвер MongoDB, без создания документа. Такой результат читается быстрее всего. Typemo не строит объект с методами и не запоминает исходные значения для отслеживания изменений.

Чтобы показать значения разных типов, добавим ещё одну модель — кошелёк. В нём 64-битное число, точное десятичное число, дата и поле-словарь.

```ts twoslash title="models/wallet.ts"
import { Entity, Prop, Schema, Spec, Types } from "@venloc/typemo";
import type { Decimal128 } from "mongodb";

@Schema({ collection: "wallets" })
export class Wallet extends Entity {
  @Prop(() => String, { required: true })
  owner!: string;

  @Prop(() => BigInt)
  points?: bigint;

  @Prop(() => Types.Decimal128)
  balance?: Decimal128;

  @Prop(() => Date)
  opened?: Date;

  @Prop(() => Spec.map(Number))
  limits?: Map<string, number>;
}
```

```ts twoslash
import { Entity, Prop, Schema, Spec, Types, TypemoClient } from "@venloc/typemo";
import type { Decimal128 } from "mongodb";
@Schema({ collection: "wallets" })
class Wallet extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => Types.Decimal128) balance?: Decimal128;
  @Prop(() => Date) opened?: Date;
  @Prop(() => Spec.map(Number)) limits?: Map<string, number>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Wallets = client.db().model(Wallet);
// ---cut---
const wallet = await Wallets.findOne({ owner: "w1" }).lean().orFail();
//    ^?
// → { _id: ObjectId("…"), owner: "w1", points: 9007199254740993n,
//     balance: Decimal128("10.50"), opened: 2026-01-02T00:00:00.000Z, limits: { daily: 100 } }
```

Значения остаются типами MongoDB. `_id` — объект `ObjectId`, 64-битные числа — `bigint`, точные десятичные — `Decimal128`. Поля-`Map` приходят обычными объектами, потому что именно так MongoDB их хранит. Как выглядит каждый тип, показано в справочнике [Формы значений](../values/value-forms.mdx).

<Returns type="QueryBuilder">

Тот же строитель. После `await` вы получаете данные как их отдал драйвер. Их тип учитывает [`.select`](#select) и [`populate`](../populate/populate.mdx), невыбранных полей в типе нет.

</Returns>

Принимает ничего.

<FullType>

```ts
lean(): QueryBuilder<T, Op, S, E, true, Found, N, X>
```

</FullType>

### Когда использовать [#lean.when-to-use]

`.lean` подходит для работы внутри приложения, где нужны точные значения MongoDB. Например, сложить очки в `bigint`, сравнить идентификаторы через `ObjectId.equals` или передать `_id` в следующий запрос.

Для ответа клиенту `.lean` не годится. `JSON.stringify` не умеет сериализовать `bigint` и бросает `TypeError: JSON.stringify cannot serialize BigInt.`, а `ObjectId` и `Decimal128` клиенту ни о чём не говорят. Для ответов берите [`.plain`](#plain). Как выбирать между документом, `.lean()` и `.plain()`, подробно разобрано в руководстве [Чтение данных](../../queries/reading-data.mdx#how-to-choose).

### Скрытые поля [#lean.hidden-fields]

`.lean` отдаёт всё, что было прочитано из базы, в том числе скрытые поля, которые вы запросили через `+`. Он рассчитан на код внутри приложения, а не на ответ клиенту, поэтому ничего не прячет.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const rows = await Users.find({ name: "Alice" }).select({ "+passwordHash": true }).lean();
// → [{ _id: ObjectId("…"), name: "Alice", age: 30, tags: ["admin", "dev"], passwordHash: "$argon2id$…" }]
```

## .plain [#plain]

`.plain` возвращает данные, переведённые в обычные значения JavaScript. Эти значения предназначены для всего, что уходит за пределы приложения, — ответов API, сообщений в очередь, записей в кеш. Документ при этом не создаётся, поэтому `.plain` почти так же быстр, как [`.lean`](#lean).

```ts twoslash
import { Entity, Prop, Schema, Spec, Types, TypemoClient } from "@venloc/typemo";
import type { Decimal128 } from "mongodb";
@Schema({ collection: "wallets" })
class Wallet extends Entity {
  @Prop(() => String, { required: true }) owner!: string;
  @Prop(() => BigInt) points?: bigint;
  @Prop(() => Types.Decimal128) balance?: Decimal128;
  @Prop(() => Date) opened?: Date;
  @Prop(() => Spec.map(Number)) limits?: Map<string, number>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Wallets = client.db().model(Wallet);
// ---cut---
const wallet = await Wallets.findOne({ owner: "w1" }).plain().orFail();
//    ^?
// → { _id: "6abcde37…", owner: "w1", points: "9007199254740993", balance: "10.50",
//     opened: 2026-01-02T00:00:00.000Z, limits: Map(1) { "daily" => 100 } }
```

Значения переводятся так.
- `ObjectId`, `Decimal128` и UUID становятся строками.
- 64-битные целые становятся строками с типом `` `${bigint}` ``, чтобы не потерять точность при передаче в JSON.
- `Date` и `RegExp` остаются как есть.
- Поля-`Map` остаются `Map`.
- Связанные документы после [`populate`](../populate/populate.mdx) тоже переводятся, каждый по своей модели.
- Скрытые поля убираются.

<ValueForms types={["objectId", "long", "decimal", "date", "map"]} forms={["lean", "plain"]} />

Полная таблица по всем типам MongoDB в справочнике [Формы значений](../values/value-forms.mdx).

<Returns type="QueryBuilder">

Тот же строитель. После `await` вы получаете обычные данные, готовые для клиента. Их тип учитывает [`.select`](#select), [`populate`](../populate/populate.mdx) и скрытые поля.

</Returns>

<Params>
<Param name="options.hidden" type="boolean" default="false">

Оставить скрытые поля, которые запрос прочитал через `+`. Тип результата тоже будет их включать. Любой другой ключ в `options` даёт `QueryError` с текстом `plain: "x" is not an option (only "hidden")`.

</Param>
</Params>

<FullType>

```ts
plain(): QueryBuilder<T, Op, S, E, "plain", Found, N, X>
plain<const O extends PlainReadOptions>(
  options: O,
): QueryBuilder<T, Op, S, E, O extends { readonly hidden: true } ? "plain+hidden" : "plain", Found, N, X>
```

</FullType>

### Скрытые поля [#plain.hidden-fields]

Скрытое поле в результате `.plain()` защищено дважды. Сначала его надо прочитать через `+`, а потом ещё и разрешить отдать через `{ hidden: true }`. Без второго шага поле в результат не попадёт, даже если его прочитали.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const safe = await Users.findOne({ name: "Alice" })
  .select({ "+passwordHash": true })
  .plain()
  .orFail();
// → { _id: "…", name: "Alice", age: 30, tags: ["admin", "dev"] }

const full = await Users.findOne({ name: "Alice" })
  .select({ "+passwordHash": true })
  .plain({ hidden: true })
  .orFail();
// → { _id: "…", name: "Alice", age: 30, tags: ["admin", "dev"], passwordHash: "$argon2id$…" }
```

Так хеш пароля не утечёт в ответ API из-за того, что кто-то добавил `+passwordHash` в общий запрос для проверки пароля.

### `Map` в JSON [#map-in-json]

В результате `.plain()` поля-`Map` остаются настоящими `Map`. В коде это удобно, но `JSON.stringify` превращает `Map` в пустой объект без ошибки. На выходе `{"limits":{}}`, значения словаря молча пропали. Если вы отдаёте поле-`Map` клиенту, превратите его в объект сами, например через `Object.fromEntries(wallet.limits)`. Можно и прочитать документ без `.plain()` и вызвать его [`$toJSON()`](../documents/document-api.mdx#to-json), там `Map` уже превращён в объект.

### Что нельзя после `.plain()` [#after-plain-limits]

Результат `.plain()` — это данные, а не документ. У него нет [`$save()`](../documents/document-api.mdx#save) и других методов документа, и компилятор не даст их вызвать.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
// @errors: 2339
const user = await Users.findOne({ name: "Alice" }).plain().orFail();
user.$save();
```

Если запись нужно изменить, прочитайте её без `.plain()` или используйте методы обновления — [`updateOne`](../writes/writes.mdx#update-one), [`findByIdAndUpdate`](../writes/writes.mdx#find-by-id-and-update).

## .cursor <Badge>только find</Badge> [#cursor]

`.cursor` выполняет запрос и отдаёт документы по одному, по мере того как они приходят из базы. Обычный `await` сначала собирает все документы в массив и только потом отдаёт его вам. Курсор отдаёт первый документ сразу, а следующие подгружает порциями, пока вы обрабатываете предыдущие. Метод есть только у [`find`](#model.find).

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
declare const __sendToWarehouse__: (user: { name: string }) => Promise<void>;
// ---cut---
for await (const user of Users.find().sort({ _id: 1 }).plain().cursor()) {
  await __sendToWarehouse__(user);
}
```

<Returns type="QueryCursor">

Курсор типа [`QueryCursor`](./cursor.mdx#query-cursor) — асинхронный итератор с методами `next`, `toArray`, `map`, `eachAsync` и `close`. Каждый элемент имеет вид, который задала цепочка, то есть документ, результат `.lean()` или `.plain()`. Все методы курсора описаны в справочнике [Курсор](./cursor.mdx). У `findOne` метод не компилируется, а в коде без типов бросает `QueryError` с текстом `cursor applies to find() only, not findOne()`.

</Returns>

Принимает ничего.

<FullType>

```ts
cursor(this: OnlyFor<Op, "find", "cursor() applies to find()">): QueryCursor<ResultDoc<T, S, E, Form, N, X>>
```

</FullType>

### Когда использовать [#cursor.when-to-use]

Курсор нужен, когда документов так много, что массив целиком не поместится в память или будет собираться слишком долго. Типичные случаи — выгрузка в другую систему, миграция данных, ночная пересборка отчётов.

Для списков на странице курсор не нужен. Там всё равно показывается ограниченное число записей, и обычного `await` с [`.limit`](#limit) достаточно.

## .exec [#exec]

`.exec` выполняет запрос и возвращает `Promise` с результатом. `await query` делает то же самое, поэтому в обычном коде `.exec()` писать не нужно. Он пригодится в двух случаях. Первый — вы хотите явно показать, что здесь запрос уходит в базу. Второй — нужно выполнить уже выполненный запрос ещё раз.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const rows = await Users.find().plain().exec();
```

<Returns type="Promise">

`Promise` с результатом запроса.

</Returns>

<Params>
<Param name="options.force" type="boolean" default="false">

Выполнить запрос заново, даже если он уже выполнялся. Значение не boolean даёт `QueryError` с текстом `find: exec({ force }) takes a boolean`, потому что Typemo значения молча не приводит.

</Param>
</Params>

<FullType>

```ts
exec(options?: ExecOptions): Promise<QueryOutput<T, Op, S, E, Form, Found, N, X>>
```

</FullType>

### Повторный `await` [#second-await]

Один строитель читает базу только один раз. Если написать `await` для того же запроса повторно, вы получите тот же результат без нового обращения к базе.

```ts twoslash
import { Entity, type Hidden, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => Number) age?: number;
  @Prop(() => [String]) tags!: string[];
  @Prop(() => String, { hidden: true }) passwordHash?: Hidden<string>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Users = client.db().model(User);
// ---cut---
const query = Users.find().plain();

const first = await query; // → 3 пользователя
await Users.create({ name: "Dave", tags: [] });
const second = await query; // → те же 3 пользователя, тот же массив
console.log(first === second);
// → true

const fresh = await query.exec({ force: true });
// → 4 пользователя
```

Так случайный повторный `await`, например в двух ветках кода, лишних запросов не делает. Если нужны свежие данные, вызовите `exec({ force: true })` или создайте новый запрос.
