Опции запроса не меняют, **какие** документы вы ищете, а меняют, **как** база их ищет и в каком окружении: в какой транзакции, с каким индексом, с каким таймаутом, с каким представлением политик модели. Все они записываются в цепочку запроса так же, как [`.sort`](./reading.mdx#sort) или [`.limit`](./reading.mdx#limit), и, как остальные методы строителя, возвращают новый запрос, не меняя старый.

Если вы только начинаете, сначала прочитайте руководство [Производительность запросов](../../queries/performance.mdx): там объяснено, когда вам понадобятся `hint`, `comment` и `timeoutMS`. Эта страница — справочник.

Не все опции есть у всех запросов. Шесть первых (`session`, `policy`, `hint`, `collation`, `comment`, `timeoutMS`) доступны у всех запросов на чтение: [`find`](./reading.mdx#modelfind), [`findOne`](./reading.mdx#modelfindone), [`findById`](./reading.mdx#modelfindbyid), а также у запросов значений [`countDocuments`](./reading.mdx#modelcountdocuments), [`exists`](./reading.mdx#modelexists), [`distinct`](./reading.mdx#modeldistinct) и [`estimatedDocumentCount`](./reading.mdx#modelestimateddocumentcount), и у методов записи. `batchSize` и `allowDiskUse` есть только у `find`, потому что они относятся к чтению порциями. `readPreference`, `readConcern` и `validateReads` есть у строителя (`find`, `findOne`, `findById` и операций «найти и изменить»), но не у запросов значений.

Все примеры используют одну модель заказа. У неё есть индекс по `number`, а мягкое удаление включено: удалённые заказы остаются в базе, но обычные запросы их не видят.

```ts twoslash title="models/order.ts"
import { Entity, Index, Prop, Schema } from "@venloc/typemo";

@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
export class Order extends Entity {
  @Prop(() => Number, { required: true })
  number!: number;

  @Prop(() => String, { required: true })
  status!: string;

  @Prop(() => Date, { nullable: true })
  deletedAt?: Date | null;
}
```

В коллекции три заказа: № 1 со статусом `Paid`, № 2 со статусом `paid` (обратите внимание на регистр) и № 3 со статусом `new`, который удалён. Индекс `number_1` создан. Результаты в комментариях `// →` — номера заказов по возрастанию.

## .session

`.session` привязывает запрос к сессии драйвера, то есть к транзакции: запрос увидит изменения, которые эта транзакция уже сделала, и сам станет частью её атомарного результата. Внутри [`client.transaction`](../connection/typemo-client.mdx#clienttransaction) сессия подставляется сама, поэтому явный `.session` нужен для ручных сессий, полученных через [`client.startSession`](../connection/typemo-client.mdx#clientstartsession).

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
const session = await client.startSession();
try {
  const orders = await Orders.find().session(session).sort({ number: 1 }).plain();
  console.log(orders.map((order) => order.number));
  // → [1, 2]
} finally {
  await session.endSession();
}
```

<Returns type="этот же запрос, с сессией">

Новый запрос, привязанный к сессии.

</Returns>

<Params>
<Param name="session" type="ClientSession | null" required>

Сессия драйвера или `null`. `null` означает «выполнить вне транзакции, даже если вызов сделан внутри неё».

</Param>
</Params>

<FullType>

```ts
session(session: ClientSession | null): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Выйти из транзакции

Внутри `client.transaction` все запросы идут в транзакции. Чтобы одно чтение осознанно выполнить вне её, передайте `null`. Оно не увидит ещё не подтверждённых изменений:

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
const counts = await client.transaction(async () => {
  await Orders.create({ number: 10, status: "tx" });
  const inside = await Orders.countDocuments({ number: 10 });
  const outside = await Orders.countDocuments({ number: 10 }).session(null);
  return [inside, outside];
});
// → [1, 0]
```

Внутри транзакции заказ № 10 уже виден, снаружи ещё нет. Подробнее о транзакциях — в руководстве [Транзакции](../../transactions/transactions.mdx) и справочнике [Транзакции](../transactions/transactions.mdx).

## .policy

`.policy` задаёт **контекст политик** одной операции: какому арендатору принадлежат данные, от чьего имени идёт действие и видны ли удалённые документы. Он дополняет контекст, в котором запрос построен, а не заменяет его целиком. Политики — тенант, мягкое удаление, аудит — работают в модели независимо от запроса, а `.policy` нужен там, где одной операции надо увидеть данные иначе, чем остальным.

Самый частый случай — мягкое удаление. Обычный запрос не видит удалённых документов, а `includeDeleted` или `onlyDeleted` меняют это для одной операции:

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
const live = await Orders.find().sort({ number: 1 }).plain();
console.log(live.map((order) => order.number));
// → [1, 2]

const all = await Orders.find().policy({ includeDeleted: true }).sort({ number: 1 }).plain();
console.log(all.map((order) => order.number));
// → [1, 2, 3]

const deleted = await Orders.find().policy({ onlyDeleted: true }).plain();
console.log(deleted.map((order) => order.number));
// → [3]
```

<Returns type="этот же запрос, с политиками">

Новый запрос. Значения `.policy` объединяются с контекстом, в котором запрос был построен: явное значение перекрывает то, что пришло из окружения. Если значения противоречат контексту, бросается ошибка политик.

</Returns>

<Params>
<Param name="values" type="PolicyValues" required>

Объект со значениями политик. Допустимые ключи: `tenant` (арендатор), `allTenants: true` (работа сразу по всем арендаторам), `actor` (кто действует, попадает в аудит), `includeDeleted: true`, `onlyDeleted: true` и `hardDelete: true` (для записи). Флаги принимают только `true` или отсутствие. Неизвестный ключ приводит к `QueryError`: `find.policy: unknown policy value "foo" (known: tenant, allTenants, actor, includeDeleted, onlyDeleted, hardDelete)`.

</Param>
</Params>

<FullType>

```ts
policy(values: PolicyValues): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Модель без политики

`.policy` не требует, чтобы у модели была включена соответствующая политика. Значение `tenant` для модели без поля арендатора принимается и ничего не меняет. Так один и тот же код работает с разными моделями.

### Когда `.policy` не подходит

Если контекст нужен всем операциям блока кода, а не одной, задайте его один раз для всего блока, а не на каждом запросе: [контекст политик](../policies/policy-context.mdx) действует на все запросы, построенные внутри. Подробнее о политиках — в руководстве [Политики данных](../../policies/policy-context.mdx).

## .hint

`.hint` заставляет базу использовать указанный индекс. Обычно база выбирает индекс сама и делает это хорошо, поэтому `.hint` нужен редко: когда план запроса ([`.explain`](./search-and-explain.mdx#explain)) показал неудачный выбор, а перестраивать индексы нельзя.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
const byName = await Orders.find().hint("number_1").sort({ number: 1 }).plain();
const byPattern = await Orders.find().hint({ number: 1 }).sort({ number: 1 }).plain();
console.log(byName.length, byPattern.length);
// → 2 2
```

<Returns type="этот же запрос, с подсказкой">

Новый запрос, который принудит базу использовать индекс.

</Returns>

<Params>
<Param name="hint" type="string | { [path]: 1 | -1 | &quot;text&quot; | &quot;2dsphere&quot; | &quot;2d&quot; | &quot;hashed&quot; }" required>

Имя индекса (`"number_1"`) или его ключи (`{ number: 1 }`). В ключах компилятор подсказывает только пути модели. Индексы схемы компилятору не видны, поэтому правильность имени проверяет база. Пустая строка и пустой объект приводят к `QueryError` с текстом `hint: an index name or a non-empty key pattern`.

</Param>
</Params>

<FullType>

```ts
hint(hint: Hint<T>): QueryBuilder<T, Op, S, E, Form, Found, N, X>

type Hint<T> = string | { readonly [P in FilterPaths<T>]?: 1 | -1 | "text" | "2dsphere" | "2d" | "hashed" }
```

</FullType>

### Индекса с таким именем нет

Если такого индекса нет, база отказывается выполнять запрос, и Typemo бросает [`ServerError`](../errors/server-errors.mdx#servererror). Его сообщение — причина и код сервера: `hint provided does not correspond to an existing index (code 2 BadValue)`; полный текст сервера лежит в поле `serverMessage`. Обычно это опечатка в имени или индекс, который ещё не создан: индексы создаются [синхронизацией](../../collections/index-sync.mdx), а не самим запросом.

### Когда `.hint` не подходит

Если запрос медленный, сначала посмотрите его план через [`.explain`](./search-and-explain.mdx#explain). Чаще всего лечение — добавить или поменять индекс в модели, а не закреплять индекс подсказкой: подсказка остаётся в коде и после того, как данные изменились и другой индекс стал лучше.

## .collation

`.collation` задаёт правила сравнения строк для одного запроса: учитывать ли регистр, диакритику, как сортировать в конкретном языке. Без него база сравнивает строки побайтово: `"paid"` и `"Paid"` — разные значения.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
const exact = await Orders.find({ status: "paid" }).plain();
console.log(exact.map((order) => order.number));
// → [2]

const anyCase = await Orders.find({ status: "paid" })
  .collation({ locale: "en", strength: 2 })
  .sort({ number: 1 })
  .plain();
console.log(anyCase.map((order) => order.number));
// → [1, 2]
```

`strength: 2` означает «различать буквы, но не регистр»: поэтому `Paid` и `paid` считаются одним значением.

<Returns type="этот же запрос, с правилами сравнения">

Новый запрос. Typemo копирует объект `collation`, так что последующее изменение вашего объекта на запрос не влияет.

</Returns>

<Params>
<Param name="collation" type="CollationOptions" required>

Объект правил драйвера `mongodb`: `locale` обязателен, остальные (`strength`, `caseLevel`, `numericOrdering` и другие) необязательны. Полный список — в документации драйвера.

</Param>
</Params>

<FullType>

```ts
collation(collation: CollationOptions): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Когда `.collation` не подходит

Если регистронезависимый поиск нужен постоянно, заведите индекс с той же collation и указывайте её в каждом запросе: без индекса с тем же `collation` база просматривает всю коллекцию. Для разового поиска по части строки подходит [`$regex`](./filter-operators.mdx#regex) с флагом `i`.

## .comment

`.comment` прикрепляет к запросу текстовую метку. Она не меняет результат, но видна в профилировщике сервера и в логах, поэтому по ней можно понять, какой код породил медленный запрос.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
const orders = await Orders.find().comment("dashboard: recent orders").sort({ number: 1 }).plain();
console.log(orders.length);
// → 2
```

Метка попала в профилировщик: при включённом профилировании запрос виден в `system.profile` как команда с полем `comment`, равным `"dashboard: recent orders"`.

<Returns type="этот же запрос, с меткой">

Новый запрос с меткой.

</Returns>

<Params>
<Param name="comment" type="string" required>

Текст метки. Пишите в нём место в коде, а не данные: метка попадает в логи сервера.

</Param>
</Params>

<FullType>

```ts
comment(comment: string): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

Для метки на уровне всего фильтра, а не запроса, есть оператор [`$comment`](./filter-operators.mdx#comment).

## .timeoutMS

`.timeoutMS` ограничивает время всей операции на стороне клиента: если запрос не уложился, драйвер прерывает его и бросает ошибку. Так один тяжёлый запрос не задерживает приложение надолго. Значение `0` означает «без ограничения».

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
const orders = await Orders.find().timeoutMS(2_000).sort({ number: 1 }).plain();
console.log(orders.length);
// → 2
```

<Returns type="этот же запрос, с таймаутом">

Новый запрос с таймаутом.

</Returns>

<Params>
<Param name="ms" type="number" required>

Время в миллисекундах: целое число не меньше нуля. Другое значение приводит к `QueryError` с текстом `timeoutMS must be a non-negative integer, got -1 (number)`. Значение заменяет `maxTimeMS`: ограничение действует на стороне клиента на всю операцию целиком.

</Param>
</Params>

<FullType>

```ts
timeoutMS(ms: number): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

Внутри транзакции у запроса не может быть своего `timeoutMS`, если он задан у самой транзакции: настройки транзакции приоритетнее, и Typemo сообщает об этом [`StrictModeError`](../errors/data-errors.mdx#strictmodeerror), как и для [`.readConcern`](#readconcern):

```text
StrictModeError: Order.find: timeoutMS 100 (the transaction has timeoutMS 5000) inside a transaction — the transaction's own settings apply (set them on transaction()) [transaction-option]
```

Если у транзакции своего `timeoutMS` нет, запрос внутри неё получает собственный без ошибки.

## .batchSize <Badge>только find</Badge>

`.batchSize` задаёт, сколько документов сервер отдаёт клиенту за одну порцию при чтении курсором. Меньшая порция уменьшает пиковое потребление памяти, большая уменьшает число обращений к сети. Результат запроса от него не зависит. Метод есть только у [`find`](./reading.mdx#modelfind).

Ноль здесь не допускается. Драйвер читает `batchSize(0)` как «размер порции по умолчанию», а человек, который пишет ноль, скорее ждёт нуль документов. Чтобы такое значение, например из пустого параметра, не меняло смысл молча, Typemo отвечает ошибкой. Порция по умолчанию получается, если метод не вызывать.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
const orders = await Orders.find().sort({ number: 1 }).batchSize(1).plain().cursor().toArray();
console.log(orders.map((order) => order.number));
// → [1, 2]
```

<Returns type="этот же запрос, с размером порции">

Новый запрос.

</Returns>

<Params>
<Param name="n" type="number" required>

Число документов в порции: положительное целое. Другое значение, в том числе `0`, — `QueryError`: `batchSize must be a positive integer, got -1 (number)`; для нуля к тексту добавлено пояснение: `batchSize must be a positive integer, got 0 (number) (the driver reads 0 as "the server default"; leave batchSize out for the default)`. У `findOne` метод не компилируется, а во время работы бросает `QueryError` с текстом `batchSize applies to find() only, not findOne()`.

</Param>
</Params>

<FullType>

```ts
batchSize(n: FindOnly<Op, number, "batchSize">): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

Не путайте с опцией `batchSize` метода [`.eachAsync`](./cursor.mdx#eachasync): та задаёт размер порции, которую получает ваша функция, а не размер порции сети.

## .readPreference

`.readPreference` говорит, с каких узлов набора реплик читать: с основного, с вторичного, с ближайшего. Чтение с вторичных узлов разгружает основной, но может вернуть данные, которые ещё не догнали основной узел.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
const orders = await Orders.find().readPreference("secondaryPreferred").sort({ number: 1 }).plain();
console.log(orders.length);
// → 2
```

<Returns type="этот же запрос, с настройкой чтения">

Новый запрос.

</Returns>

<Params>
<Param name="mode" type="ReadPreferenceMode" required>

Один из режимов драйвера: `"primary"`, `"primaryPreferred"`, `"secondary"`, `"secondaryPreferred"`, `"nearest"`.

</Param>
</Params>

<FullType>

```ts
readPreference(mode: ReadPreferenceMode): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Внутри транзакции

Транзакция всегда читает с основного узла. Поэтому внутри `client.transaction` любой режим, кроме `"primary"`, приводит к [`StrictModeError`](../errors/data-errors.mdx#strictmodeerror):

```text
StrictModeError: Order.find: readPreference "secondary" (a transaction reads from the primary) inside a transaction — the transaction's own settings apply (set them on transaction()) [transaction-option]
```

Ошибка нужна потому, что иначе настройка молча не подействовала бы, и приложение читало бы не то, что вы просили.

## .readConcern

`.readConcern` задаёт уровень согласованности чтения: насколько подтверждёнными должны быть прочитанные данные (`"local"`, `"majority"`, `"snapshot"` и другие). `"majority"` вернёт только данные, которые подтвердило большинство узлов и которые не откатятся.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
const orders = await Orders.find().readConcern("majority").sort({ number: 1 }).plain();
console.log(orders.length);
// → 2
```

<Returns type="этот же запрос, с уровнем чтения">

Новый запрос.

</Returns>

<Params>
<Param name="level" type="ReadConcernLevel" required>

Уровень драйвера: `"local"`, `"available"`, `"majority"`, `"linearizable"`, `"snapshot"`.

</Param>
</Params>

<FullType>

```ts
readConcern(level: ReadConcernLevel): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Внутри транзакции

Уровень чтения у транзакции свой, и он задаётся при её запуске. Запрос внутри транзакции со своим `readConcern` приводит к [`StrictModeError`](../errors/data-errors.mdx#strictmodeerror):

```text
StrictModeError: Order.find: readConcern "majority" inside a transaction — the transaction's own settings apply (set them on transaction()) [transaction-option]
```

Чтобы задать уровень для транзакции, передайте его в опциях [`client.transaction`](../connection/typemo-client.mdx#clienttransaction).

## .allowDiskUse <Badge>только find</Badge>

`.allowDiskUse` разрешает серверу использовать диск, когда сортировке не хватает выделенной памяти. Без него большая сортировка без индекса завершается ошибкой сервера. Метод есть только у [`find`](./reading.mdx#modelfind).

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
const orders = await Orders.find().sort({ status: 1, number: 1 }).allowDiskUse(true).plain();
console.log(orders.length);
// → 2
```

<Returns type="этот же запрос, с разрешением диска">

Новый запрос.

</Returns>

<Params>
<Param name="allow" type="boolean" required>

`true` разрешает диск, `false` запрещает. У `findOne` метод не компилируется, а во время работы бросает `QueryError` с текстом `allowDiskUse applies to find() only, not findOne()`.

</Param>
</Params>

<FullType>

```ts
allowDiskUse(allow: FindOnly<Op, boolean, "allowDiskUse">): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Когда `.allowDiskUse` не подходит

Сортировка на диске в разы медленнее сортировки в памяти. Если запрос упирается в память, лучше добавить индекс, по которому он уже отсортирован, чем разрешать диск.

## .validateReads

`.validateReads` включает для одного запроса **строгое чтение**: каждый документ, который вернула база, сверяется со схемой до того, как станет результатом, и значение другого типа — [`CastError`](../errors/data-errors.mdx#casterror) с путём поля. По умолчанию чтение документы не сверяет: данные, записанные через модель, проверены при записи, а сверка стоила бы времени на каждом чтении. Метод нужен, когда в коллекцию пишут мимо модели: импорт, другой сервис, скрипт на драйвере.

Допустим, другой сервис записал в коллекцию заказ с номером-строкой, `{ number: "4", status: "paid" }`. Обычный запрос вернёт его как есть, а с `.validateReads()` запрос остановится на этом документе:

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ number: 1 })
@Schema({ collection: "orders", softDelete: true })
class Order extends Entity {
  @Prop(() => Number, { required: true }) number!: number;
  @Prop(() => String, { required: true }) status!: string;
  @Prop(() => Date, { nullable: true }) deletedAt?: Date | null;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Orders = client.db().model(Order);
// ---cut---
try {
  await Orders.find().sort({ number: 1 }).validateReads().plain();
} catch (error) {
  console.log((error as Error).message);
}
// → Cast to number failed at path "number" for "4" (string): the stored value does not match the schema of Order (a document read from the database, checked by validateReads) [type]
```

Что именно проверяется (поля, массивы, `Map`, поддокументы, `null`, маскировка значений) и почему по умолчанию проверки нет, описано в опции клиента [`validateReads`](../connection/typemo-client.mdx#validatereads). Документы, которые запрос подставляет через `populate`, проверяются по тому же решению, что и сам запрос.

<Returns type="этот же запрос, со своим решением о проверке">

Новый запрос. Решение запроса сильнее опции клиента: `.validateReads()` проверяет даже на клиенте без `validateReads`, а `.validateReads(false)` не проверяет на клиенте с `validateReads: true`.

</Returns>

<Params>
<Param name="enabled" type="boolean" default="true">

`true` — сверять документы со схемой, `false` — не сверять. Любое другое значение в коде без типов — `QueryError` с текстом `validateReads: true or false`.

</Param>
</Params>

<FullType>

```ts
validateReads(enabled?: boolean): QueryBuilder<T, Op, S, E, Form, Found, N, X>
```

</FullType>

### Выключить проверку для одного запроса

Клиент со строгим чтением (`validateReads: true` или `"development"` в разработке) проверяет каждый документ. Для тяжёлого отчёта по миллионам строк, которые вы уже проверили, проверку можно выключить точечно: `Orders.find(filter).validateReads(false)`. На клиенте `validateReads: true` такой запрос вернул заказ с номером `"4"` без ошибки.

### Когда `.validateReads` не подходит

Строгое чтение находит испорченные данные, но не исправляет их. Если документы другого вида пишет известный источник, исправьте его и приведите старые документы миграцией. Если включать проверку в каждом запросе неудобно, задайте её клиенту, опцией [`validateReads`](../connection/typemo-client.mdx#validatereads). Строки агрегаций не проверяются: сверьте их со схемой через [`.parse`](./contracts.mdx#parse).
