Отдельный вход пакета `@venloc/typemo/testing` собирает инструменты для тестов вашего приложения. Там есть **фабрики** тестовых данных, которые проверяет компилятор, и проверки плана запроса. Они роняют тест, когда запрос перестал использовать индекс. Вход зависит только от ядра, сервер для тестов и другие пакеты он не тянет. Тестовую базу вы поднимаете сами.

Как всё это применять, рассказывает руководство [Тестировать приложение](../../testing/testing-apps.mdx).

Примеры построены на модели счёта. Значения получены запуском на настоящей базе. В коллекции три счёта — `Account 1`, `Account 2`, `Account 3`, у `title` уникальный индекс.

## defineFactory [#define-factory]

`defineFactory` создаёт фабрику. Вы один раз описываете обычный документ, а в тесте задаёте только то, что для теста важно. Фабрика типизирована по модели. Переименовали поле модели — сломается фабрика, а не тихо тест. Данные строит функция от номера (1, 2, …), так что уникальные поля не конфликтуют.

<Snippet id="reference/testing/testing/define-factory" twoslash />

<Params>
<Param name="model" type="FactoryModel<T>" required>

Модель, которая сохраняет документы. Подойдёт любая модель Typemo, нужны только `entity` и `create`.

</Param>
<Param name="defaults" type="(n: number) => CreateInput<T>" required>

Значения по умолчанию по номеру. Тип `CreateInput<T>` — то, что принимает `create`, так что обязательные поля обязательны и здесь.

</Param>
</Params>

<Returns type="Factory<T>">

Замороженный объект фабрики, см. [`Factory`](#factory). Умолчания и переопределения не меняются, каждый вызов строит новый объект.

</Returns>

## Factory [#factory]

`Factory` — то, что вернул `defineFactory`. Счётчик номера общий для всех методов, каждый `build` увеличивает его на единицу.

  type={{
    "build(overrides?)": { description: "Данные одного документа (умолчания, затем переопределения) без сохранения. Вторым по счёту вызовом `build({ balance: 5 })` дал `{ title: \"Account 2\", balance: 5 }`.", type: "(overrides?: FactoryOverrides<T>) => CreateInput<T>" },
    "buildMany(count, overrides?)": { description: "Данные `count` документов. Если `count` не целое неотрицательное число, будет `TypemoError: defineFactory: count must be a non-negative integer, got -1`.", type: "(count: number, overrides?: FactoryOverrides<T>) => CreateInput<T>[]" },
    "create(overrides?)": { description: "Строит и сохраняет один документ через `model.create` и возвращает его.", type: "(overrides?: FactoryOverrides<T>) => Promise<HydratedDoc<T>>" },
    "createMany(count, overrides?)": { description: "Строит и сохраняет `count` документов по одному, в порядке номеров. К `count` то же условие, что у `buildMany`.", type: "(count: number, overrides?: FactoryOverrides<T>) => Promise<HydratedDoc<T>[]>" },
    "reset()": { description: "Возвращает счётчик к началу, следующий номер снова 1. Вызывайте между тестами, если уникальные поля не должны зависеть от порядка запуска.", type: "() => void" },
  }}
/>

Переопределение — объект с частью полей или функция от номера. Третьим вызовом `accounts.build((n) => ({ title: "VIP " + n }))` дал `{ title: "VIP 3", balance: 100 }`. Переопределение заменяет поле целиком, вложенные объекты не сливаются.

## explainIndexUsage [#explain-index-usage]

`explainIndexUsage` спрашивает у базы план запроса (`explain("executionStats")`) и превращает ответ сервера в короткий отчёт. В нём видно стадии, индексы и сколько документов прочитано. Берите его там, где хотите смотреть на план сами, например в отладке или в собственной проверке.

<Snippet id="reference/testing/testing/explain-index-usage" twoslash />

Запрос по уникальному индексу сервер выполняет стадией `EXPRESS_IXSCAN`. Индекс находит документ, сервер читает его целиком, поэтому `docsExamined: 1` и `covered: false`. Если запросу нужны только поля индекса, документ читать не надо. Тогда `docsExamined` равен нулю, а `covered` — `true`.

<Snippet id="reference/testing/testing/explain-index-usage-2" twoslash />

<Params>
<Param name="query" type="Explainable" required>

Запрос `find`/`findOne` или агрегация модели, то есть всё, у чего есть метод `explain`.

</Param>
</Params>

<Returns type="Promise<IndexUsage>">

Замороженный отчёт [`IndexUsage`](#index-usage).

</Returns>

Если сервер не вернул план, функция бросает `TypemoError: explainIndexUsage: the server returned no plan`.

<Callout type="warning">

`covered` равен `true` только тогда, когда запрос идёт через индекс, не читает всю коллекцию, не содержит стадии `FETCH` и сервер не прочитал ни одного документа (`docsExamined` равен нулю). У `EXPRESS_IXSCAN` стадии `FETCH` нет, но документ он читает. Поэтому одного отсутствия `FETCH` мало, и `findById` с `find` по уникальному полю дают `covered: false`. Чтобы запрос стал покрытым, ограничьте его полями индекса через [`select`](../query/reading.mdx#select) и уберите `_id`, если его нет в индексе.

</Callout>

`IndexUsage` — отчёт о том, как запрос читает коллекцию. Его возвращают `explainIndexUsage`, `expectIndexScan` и `expectCollScan`, а `IndexUsageError` хранит его в `usage`.

## expectIndexScan [#expect-index-scan]

`expectIndexScan` роняет тест, если запрос читает всю коллекцию или не использует индекс. Индекс легко потерять. Переименовали поле или поменяли порядок ключей, и запрос тихо стал медленным. Проверка превращает потерю в красный тест.

<Snippet id="reference/testing/testing/expect-index-scan" twoslash />

<Params>
<Param name="query" type="Explainable" required>

Запрос `find`/`findOne` или агрегация.

</Param>
<Param name="options" type="ExpectIndexOptions" default="{}">

Дополнительные ожидания. `index` — имя индекса, который должен использоваться. `maxDocsExamined` — потолок прочитанных документов. `covered: true` — результат только из индекса, без чтения документов (`docsExamined` равен нулю).

</Param>
</Params>

<Returns type="Promise<IndexUsage>">

Отчёт, если план соответствует ожиданиям.

</Returns>

**Ошибки.** [`IndexUsageError`](#index-usage-error) с перечнем проблем и планом. Тексты взяты из реального запуска.

- Без индекса — `the query is not served by an index: it scans the whole collection (COLLSCAN). plan: COLLSCAN; examined 3 documents, returned 3`.
- Не тот индекс — `the query is not served by an index: it does not use the index "nope_1" (it uses: title_1). plan: EXPRESS_IXSCAN; examined 1 documents, returned 1`.

Если нет ни `COLLSCAN`, ни индекса, текст такой — `it uses no index`. Превышение `maxDocsExamined` даёт `it examined N documents, more than M`. Невыполненное требование `covered` — `it is not covered by the index (it fetches documents)`. Несколько проблем склеиваются через `; `.

Обратная проверка — [`expectCollScan`](#expect-coll-scan).

## expectCollScan [#expect-coll-scan]

`expectCollScan` роняет тест, если запрос **не** читает всю коллекцию. Он нужен, когда отсутствие индекса задумано. Скажем, редкий отчёт по полю, индекс на которое держать не стоит, а вы хотите заметить, если кто-то его добавит или запрос изменится.

<Snippet id="reference/testing/testing/expect-coll-scan" twoslash />

<Params>
<Param name="query" type="Explainable" required>

Запрос или агрегация.

</Param>
</Params>

<Returns type="Promise<IndexUsage>">

Отчёт, если запрос читает всю коллекцию.

</Returns>

Ошибка выглядит так — `IndexUsageError: the query does not scan the collection. plan: EXPRESS_IXSCAN; examined 1 documents, returned 1`.

## Explainable [#explainable]

`Explainable` — то, что принимают проверки, то есть любой объект с методом `explain(verbosity?)`. Запрос `find`/`findOne` и агрегация модели такие. Описывать больше нечего, тип объявлен в блоке «Полный тип» у [`explainIndexUsage`](#explain-index-usage).

## IndexUsageError [#index-usage-error]

`IndexUsageError` — ошибка проверок `expectIndexScan` и `expectCollScan`. Она наследует `TypemoError`, а в поле `usage` хранит [`IndexUsage`](#index-usage) плана, который проверку не прошёл. Тест может вывести детали.

## Когда это не подходит [#when-not-to-use]

Проверки плана нужны в тестах и отладке. Они выполняют `explain`, то есть лишний запрос. В рабочем коде берите [`.explain`](../query/search-and-explain.mdx#explain) напрямую.

Тестовую базу поднимайте средствами приложения, `@venloc/typemo/testing` её не создаёт.
