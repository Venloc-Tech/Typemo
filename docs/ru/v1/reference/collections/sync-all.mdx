`SyncAll` приводит всю базу подключения в соответствие со схемами моделей за один вызов. Для каждой коллекции он сверяет параметры и индексы, для каждого представления — его определение. Обычно вы вызываете его не напрямую, а через [`connection.syncAll`](../connection/connection.mdx#connectionsyncall) — код тот же. Здесь описан отчёт, потому что при деплое читать приходится именно его.

Если вы впервые настраиваете базу при запуске, начните с руководства [Синхронизация индексов](../../collections/index-sync.mdx). Эта страница — справочник.

`SyncAll` **не останавливается на первой ошибке**. Сбой одной модели не мешает остальным, например когда индекс не построился на грязных данных или коллекция в базе объявлена иначе. Каждый шаг каждой модели выполняется, а в конце метод бросает одну ошибку [`SyncError`](../errors/configuration-errors.mdx#syncerror) со списком всех сбоев и полным отчётом. Для деплоя это удобнее всего. За один запуск вы видите всё, что не сошлось, и деплой не пройдёт «успешно» с непостроенным индексом.

Примеры используют две модели — счёт с уникальным названием и журнал проводок ограниченного размера.

```ts twoslash title="accounts/models.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => String, { required: true, index: true })
  owner!: string;
}

@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
export class LedgerEntry extends Entity {
  @Prop(() => String, { required: true })
  note!: string;
}
```

Результаты в комментариях получены на пустой базе, если рядом не сказано иное.

## SyncAll.run

`SyncAll.run` синхронизирует все модели и представления подключения и возвращает отчёт. Берите его, когда нужны сразу все итоги — в скрипте деплоя, в проверке окружения на CI, в служебной команде.

Для каждой коллекции метод делает три шага по очереди. Он приводит параметры коллекции ([`ensureCollection`](./collection-manager.mdx#modelensurecollection)), обычные индексы ([`syncIndexes`](./model-indexes.mdx#modelsyncindexes)) и, если схема объявляет поисковые индексы, их тоже ([`syncSearchIndexes`](./model-indexes.mdx#modelsyncsearchindexes)). Потом для каждого представления вызывается [`TypedView.ensure`](./typed-view.mdx#typedviewensure). Сбой любого шага запоминается, остальные шаги идут дальше.

```ts twoslash
import { Entity, Prop, Schema, SyncAll, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
}
@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
connection.model(Account);
connection.model(LedgerEntry);
// ---cut---
const report = await SyncAll.run(connection);
console.log(report.inSync, report.failed);
// → false false
console.log(report.collections.map((c) => [c.collection, c.options?.result, c.indexes?.toCreate]));
// → [["accounts", "created", ["title_1", "owner_1"]], ["ledger", "created", []]]
console.log(report.created);
// → ["collection accounts", "index accounts.title_1", "index accounts.owner_1", "collection ledger"]
```

`inSync` здесь `false`, хотя ничего не сломалось. В базе было что создавать, и список `created` говорит, что именно создано. Когда всё создано, повторный вызов вернёт `inSync: true` и пустой `created`.

<Returns type="Promise<SyncReport>">

Отчёт [`SyncReport`](#syncreport), если ни один шаг не упал. Если упал хотя бы один, метод бросает [`SyncError`](../errors/configuration-errors.mdx#syncerror), а тот же отчёт с `failed: true` лежит в его поле `report`.

</Returns>

<Params>
<Param name="connection" type="Connection" required>

Подключение, чьи модели и представления синхронизируются. Учитываются только классы, зарегистрированные через [`connection.model`](../connection/connection.mdx#connectionmodel), и представления из [`TypedView.define`](./typed-view.mdx#typedviewdefine). Незарегистрированный класс метод не увидит.

</Param>
<Param name="options" type="SyncAllOptions">

Опции синхронизации — [`SyncAllOptions`](#syncalloptions).

</Param>
</Params>

<FullType>

```ts
static run(connection: Connection, options?: SyncAllOptions): Promise<SyncReport>
```

</FullType>

Для запуска приложения есть другой метод, [`connection.init`](../connection/connection.mdx#connectioninit). Шаги у него те же, но он только **создаёт** недостающее, ничего не удаляя и не меняя, а расхождение считает сбоем. Отчёт и ошибка у него такие же.

### Проверить, не записывая

С `dryRun: true` метод сообщает, что изменилось бы, и ничего не записывает — ни коллекций, ни индексов, ни представлений. Так удобно проверять базу перед деплоем, например в CI. После такого вызова на пустой базе в ней по-прежнему нет ни одной коллекции.

```ts twoslash
import { Entity, Prop, Schema, SyncAll, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
connection.model(Account);
// ---cut---
const plan = await SyncAll.run(connection, { dryRun: true });
console.log(plan.inSync, plan.collections[0]?.indexes?.dryRun);
// → false true
console.log(plan.created);
// → ["collection accounts", "index accounts.title_1", "index accounts.owner_1"]
```

При `dryRun` список `created` показывает то, что было бы создано. Если проверка находит сбой, например коллекцию, устроенную иначе, чем в схеме, метод и с `dryRun` бросает `SyncError`. Деплой с таким расхождением всё равно не прошёл бы.

### Сбой одной модели

Скажем, в `accounts` два счёта с одним названием, а `ledger` уже есть как обычная коллекция без ограничения размера. Оба сбоя попадут в одну ошибку.

```ts twoslash
import { Entity, Prop, Schema, SyncAll, SyncError, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
}
@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
connection.model(Account);
connection.model(LedgerEntry);
const db = client.unsafeDriver().db("app");
await db.createCollection("ledger");
await db.collection("accounts").insertMany([
  { title: "Main", owner: "alice" },
  { title: "Main", owner: "bob" },
]);
// ---cut---
try {
  await SyncAll.run(connection);
} catch (error) {
  if (error instanceof SyncError) {
    console.log(error.failures.map((f) => [f.kind, f.name, f.model, f.errors.map((e) => e.name)]));
    // → [["collection", "accounts", "Account", ["IndexSyncError"]],
    //    ["collection", "ledger", "LedgerEntry", ["CollectionOptionsError"]]]
  }
}
```

Сбой индекса `accounts` не помешал остальным шагам. Параметры коллекции `accounts` сверены (`error.report.collections[0].options.result` равен `"unchanged"`), индекс `owner_1` построен, и не создался только `title_1`. У записи `ledger`, где не сошлись параметры коллекции, поле `options` пустое. Сообщение подсказывает, что делать.

```text
collection "ledger": exists with options MongoDB cannot change (capped): drop the collection and create it again
```

### Какие модели пропускаются

Схема с `autoCreate: false` не проходит шаг параметров коллекции. Схема с `autoIndex: false` не проходит шаги индексов, и соответствующие поля отчёта остаются пустыми. Обе опции действуют только здесь и в [`connection.init`](../connection/connection.mdx#connectioninit). Прямые вызовы `syncIndexes`, `createIndexes` и `ensureCollection` у модели их не смотрят.

Схема с `autoCreate: false` и без индексов пропускается целиком, даже если коллекции ещё нет. Если у неё есть индексы и параметры «только при создании», отсутствующая коллекция — ошибка. Подробности на странице [`CollectionManager`](./collection-manager.mdx#схема-с-autocreate-false).

Модели-наследники ([дискриминаторы](../schemas/discriminator.mdx)) делят коллекцию с базовой моделью. Коллекция синхронизируется один раз по схеме базовой модели, а индексы наследников в неё уже включены. Классы представлений (`TypedView`) в коллекции не попадают, их обрабатывают как представления.

## SyncAll.collections

`SyncAll.collections` возвращает схемы корневых моделей подключения, по одной на коллекцию. По этому списку `run` проходит шаги коллекций. Представлений в нём нет, а наследники с общей коллекцией не перечисляются повторно. Метод пригодится для проверок вроде «какие коллекции затронет деплой».

```ts twoslash
import { Entity, Prop, Schema, SyncAll, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
}
@Schema({ collection: "ledger", capped: { size: 65_536, max: 100 } })
class LedgerEntry extends Entity {
  @Prop(() => String, { required: true }) note!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
// ---cut---
console.log(SyncAll.collections(connection).map((schema) => schema.collection));
// → []

connection.model(Account);
connection.model(LedgerEntry);
console.log(SyncAll.collections(connection).map((schema) => schema.collection));
// → ["accounts", "ledger"]
```

<Returns type="readonly SchemaInfo[]">

Описания схем корневых моделей — [`SchemaInfo`](../schemas/schema-info.mdx) с полями `collection` (имя коллекции) и `name` (имя класса). Пока ни одна модель не зарегистрирована, список пустой.

</Returns>

<Params>
<Param name="connection" type="Connection" required>

Подключение, чьи модели перечисляются.

</Param>
</Params>

<FullType>

```ts
static collections(connection: Connection): readonly SchemaInfo[]
```

</FullType>

## SyncAllOptions

Опции [`SyncAll.run`](#syncallrun) и [`connection.syncAll`](../connection/connection.mdx#connectionsyncall).

<TypeTable
  type={{
    dryRun: { type: "boolean", default: "false", description: "Только сообщить, что изменилось бы, и ничего не записывать. Действует на коллекции, индексы, поисковые индексы и представления." },
    update: { type: "boolean", default: "false", description: "Применяет командой `collMod` то, что сервер умеет менять на месте — параметры коллекции и определение представления. Без неё такое различие становится сбоем (ошибка [`CollectionOptionsError`](../errors/configuration-errors.mdx#collectionoptionserror) в отчёте и в `SyncError`). На индексы не влияет, их `syncAll` приводит в соответствие всегда." },
  }}
/>

`update` защищает работающую коллекцию от случайных изменений параметров. Скажем, в схеме появился валидатор, а коллекция создана без него. Без `update: true` метод бросит `SyncError` с `CollectionOptionsError`, а с ним валидатор применится.

## SyncReport

Итог [`SyncAll.run`](#syncallrun) и [`connection.syncAll`](../connection/connection.mdx#connectionsyncall). Объект и все его списки заморожены, менять их нельзя.

<TypeTable
  type={{
    collections: { type: "readonly SyncCollectionReport[]", required: true, description: "По одной записи на каждую синхронизированную коллекцию, в порядке регистрации моделей." },
    views: { type: "readonly SyncViewReport[]", required: true, description: "По одной записи на каждое представление подключения, в порядке определения." },
    inSync: { type: "boolean", required: true, description: "`true`, если ничего не упало и база совпадает со схемами. Для `syncAll` это значит, что различий не было. Если метод что-то создал или изменил, `inSync` равен `false`, даже когда различие удалось устранить, а повторный вызов покажет `true`. У [`connection.init`](../connection/connection.mdx#connectioninit) `inSync` равен `true` и после создания недостающего. `init` только создаёт, и после успеха база совпадает со схемами. `dryRun`, который находит что делать, не бывает `inSync`." },
    created: { type: "readonly string[]", required: true, description: "Что создано или, при `dryRun`, было бы создано, по порядку. Например `\"collection users\"`, `\"index users.email_1\"`, `\"search index users.default\"`, `\"view active_users\"`. Пусто, если недостающего не было." },
    failed: { type: "boolean", required: true, description: "`true`, если хотя бы один шаг не удался. У возвращённого отчёта всегда `false`. При сбое метод бросает [`SyncError`](../errors/configuration-errors.mdx#syncerror), а `true` бывает только в его поле `report`." },
  }}
/>

`inSync` и `failed` — разные вещи. `failed: false, inSync: false` значит, что изменения были и все применены (или, при `dryRun`, что изменения нужны). `failed: true` значит, что часть работы не сделана. Такой отчёт приходит только из `SyncError.report`, а причины лежат в `errors` его записей.

### Как читать сбой

Перехватите `SyncError` — тогда вы выведете все сбои одним списком и остановите деплой. Исходные ошибки лежат в его `errors`, полный отчёт в `report`.

```ts twoslash
import { Entity, Prop, Schema, SyncError, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
connection.model(Account);
// ---cut---
try {
  await connection.syncAll();
} catch (error) {
  if (error instanceof SyncError) {
    for (const failure of error.failures) console.error(failure.name, failure.errors.map((e) => e.message));
    throw new Error(`database sync failed: ${error.errors.length} problem(s)`, { cause: error });
  }
  throw error;
}
```

## Когда не подходит

Если нужно только создать недостающее, ничего не удаляя и не меняя, вызовите [`connection.init`](../connection/connection.mdx#connectioninit). Расхождение он тоже считает сбоем и бросает [`SyncError`](../errors/configuration-errors.mdx#syncerror), как и `syncAll`. Для одной модели вызывайте [`syncIndexes`](./model-indexes.mdx#modelsyncindexes) и [`ensureCollection`](./collection-manager.mdx#modelensurecollection) у неё самой. Состояние можно проверить и без записи и без `SyncAll` — [`diffIndexes`](./model-indexes.mdx#modeldiffindexes) показывает расхождение индексов одной модели.

Руководство с реальными задачами — [Синхронизация индексов](../../collections/index-sync.mdx).
