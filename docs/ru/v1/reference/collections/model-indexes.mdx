Здесь собраны методы модели для работы с **индексами** коллекции. Индекс — служебная структура MongoDB. Благодаря ему запросы не перебирают всю коллекцию, а уникальные поля остаются уникальными. Схема описывает нужные индексы (`unique`, `index`, [`@Index`](../schemas/index-decorators.mdx#index)), а методы отсюда сравнивают описание с тем, что лежит на сервере, и при необходимости подтягивают сервер к схеме. Отдельная группа методов работает с **поисковыми индексами** ([`@SearchIndex`](../schemas/index-decorators.mdx#searchindex)), для которых нужен Atlas Search.

Если вы впервые настраиваете индексы, начните с руководства [Синхронизация индексов](../../collections/index-sync.mdx). Эта страница — справочник, сюда возвращаются за деталями.

Все примеры используют модель счёта. В ней уникальное поле, обычный индекс через `index: true` и TTL-индекс через [`@Index`](../schemas/index-decorators.mdx#index). По TTL-индексу сервер сам удаляет старые документы.

```ts twoslash title="accounts/account.ts"
import { Entity, Index, Prop, Schema } from "@venloc/typemo";

@Index({ opened: 1 }, { name: "opened_ttl", expireAfterSeconds: 3600 })
@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => String, { required: true, index: true })
  owner!: string;

  @Prop(() => Date)
  opened?: Date;
}
```

Схема объявляет три индекса — `title_1`, `owner_1` и `opened_ttl`. Если `name` не задан, имя строится из ключей по образцу `поле_направление`. Индекс `_id_` сервер создаёт сам, Typemo его не трогает. Результаты в комментариях `// →` получены на пустой базе, где коллекции `accounts` ещё нет. Если нужны данные, они описаны рядом с примером.

Методы работают только с коллекцией модели. Все они сначала ждут подключения клиента (см. [`client.ready`](../connection/typemo-client.mdx#clientready)). Все модели подключения за раз синхронизирует [`connection.syncAll`](../connection/connection.mdx#connectionsyncall), он описан на странице [`SyncAll`](./sync-all.mdx).

Опция схемы `autoIndex` на эти методы не влияет. Она нужна только [`connection.init`](../connection/connection.mdx#connectioninit) и `connection.syncAll`, чтобы решить, строить ли индексы модели. Если вы сами вызвали `syncIndexes` или `createIndexes` у модели с `autoIndex: false`, индексы построятся (на MongoDB 9.0 у такой модели получилось `["code_1"]`).

## Model.listIndexes

`listIndexes` возвращает индексы, которые сейчас лежат на сервере, в том виде, в каком их отдаёт драйвер. Он пригодится в проверках и служебных скриптах. Посмотрите, какие индексы уже есть, прежде чем что-то менять, или убедитесь после деплоя, что нужный индекс создан.

Со схемой метод ничего не сравнивает и показывает сервер как есть. Если коллекции ещё нет, вы получите пустой массив, а не ошибку.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ opened: 1 }, { name: "opened_ttl", expireAfterSeconds: 3600 })
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
  @Prop(() => Date) opened?: Date;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
// ---cut---
console.log(await Accounts.listIndexes());
// → []

await Accounts.syncIndexes();
const indexes = await Accounts.listIndexes();
console.log(indexes.map((index) => [index.name, index.unique, index.expireAfterSeconds]));
// → [["_id_", undefined, undefined], ["title_1", true, undefined],
//    ["owner_1", undefined, undefined], ["opened_ttl", undefined, 3600]]
```

<Returns type="Promise<IndexDescriptionInfo[]>">

Массив описаний индексов из драйвера `mongodb`. У каждого есть `name`, `key` (ключи с направлениями) и версия `v`, а ещё заданные у индекса опции — `unique`, `expireAfterSeconds`, `hidden`, `partialFilterExpression`, `collation`. Индекс `_id_` есть в списке всегда, если коллекция существует. Для несуществующей коллекции массив пустой.

</Returns>

Принимает ничего.

<FullType>

```ts
listIndexes(): Promise<IndexDescriptionInfo[]>
```

</FullType>

### Что показывает сервер, а не схема

`listIndexes` отдаёт то, что записал сервер, поэтому в описаниях бывают поля, которых вы не задавали. Например, MongoDB 9 добавляет к каждому индексу `collation: { locale: "simple" }`. Сравнивать описание индекса со схемой вручную не нужно, этим занимается [`diffIndexes`](#modeldiffindexes).

## Model.diffIndexes

`diffIndexes` сравнивает индексы схемы с индексами сервера и говорит, что создать, что удалить и что изменить на месте. Ничего он не записывает. Берите его, чтобы увидеть расхождение до того, как его исправит [`syncIndexes`](#modelsyncindexes), например в проверке перед деплоем.

Сравнение строгое и симметричное. Индекс считается тем же самым, если совпали ключи и их порядок, `unique`, `sparse`, `partialFilterExpression`, настройки текстового индекса и правило сортировки строк (collation). Опция со значением по умолчанию равна отсутствующей, так что `unique: false` и `sparse: false` на сервере отличием не считаются. Без пересоздания сервер умеет менять только видимость индекса (`hidden`) и срок жизни TTL-индекса. Эти два различия попадают в отдельный список.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ opened: 1 }, { name: "opened_ttl", expireAfterSeconds: 3600 })
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
  @Prop(() => Date) opened?: Date;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
// ---cut---
const diff = await Accounts.diffIndexes();
console.log(diff);
// → { toCreate: ["title_1", "owner_1", "opened_ttl"], toDrop: [], toModify: [] }
```

<Returns type="Promise<IndexDiff>">

Объект [`IndexDiff`](#indexdiff) с тремя списками. В `toCreate` лежат индексы схемы, которых нет на сервере или которые отличаются. В `toDrop` — индексы сервера, которых нет в схеме или которые отличаются. В `toModify` — изменения на месте. Если всё сходится, все три списка пустые.

</Returns>

Принимает ничего.

<FullType>

```ts
diffIndexes(): Promise<IndexDiff>
```

</FullType>

### Текстовый индекс

Текстовый индекс (`@Index({ title: "text", body: "text" })`) сервер хранит вместе с весами полей. Если вы их не задали, каждое поле получает вес 1. Typemo знает это правило, поэтому сразу после создания такой индекс совпадает со схемой, и повторный вызов различий не находит. Явный вес, отличный от единицы, сравнивается как любая другая опция индекса.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "posts" })
@Index({ title: "text", body: "text" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Posts = client.connection.model(Post);
// ---cut---
console.log((await Posts.diffIndexes()).toCreate);
// → ["title_text_body_text"]

await Posts.syncIndexes();
console.log(await Posts.diffIndexes());
// → { toCreate: [], toDrop: [], toModify: [] }
```

### Лишний индекс

Индекса, которого нет в схеме, быть не должно, и он попадает в `toDrop`. Схема — полное описание, поэтому индекс, созданный вручную, Typemo считает лишним. Скажем, в коллекции есть индекс `closed_1`, которого схема не объявляет.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ opened: 1 }, { name: "opened_ttl", expireAfterSeconds: 3600 })
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
  @Prop(() => Date) opened?: Date;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
await Accounts.syncIndexes();
await client.unsafeDriver().db("app").collection("accounts").createIndex({ closed: 1 }, { name: "closed_1" });
// ---cut---
console.log(await Accounts.diffIndexes());
// → { toCreate: [], toDrop: ["closed_1"], toModify: [] }
```

`_id_` в `toDrop` не попадает никогда, ведь это индекс сервера, а не схемы. Лишними не считаются и индекс кластерной коллекции, и служебный индекс коллекции временных рядов, который сервер создаёт сам.

### Индекс объявлен иначе

Бывает, что индекс с тем же именем есть и в схеме, и на сервере, а ключи или опции у них разные. Изменить такой индекс на месте нельзя, поэтому его имя стоит **и в `toDrop`, и в `toCreate`**. Индекс нужно удалить и создать заново. В примере на сервере `owner_1` сделан уникальным, а схема этого не требует.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ opened: 1 }, { name: "opened_ttl", expireAfterSeconds: 3600 })
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
  @Prop(() => Date) opened?: Date;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
const raw = client.unsafeDriver().db("app").collection("accounts");
await Accounts.syncIndexes();
await raw.dropIndex("owner_1");
await raw.createIndex({ owner: 1 }, { name: "owner_1", unique: true });
// ---cut---
console.log(await Accounts.diffIndexes());
// → { toCreate: ["owner_1"], toDrop: ["owner_1"], toModify: [] }
```

### Изменение на месте

Срок жизни TTL-индекса и видимость индекса сервер меняет командой, без пересоздания. Поэтому такие различия лежат в `toModify` вместе с новым значением. В примере кто-то вручную сократил срок жизни `opened_ttl` до минуты.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ opened: 1 }, { name: "opened_ttl", expireAfterSeconds: 3600 })
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
  @Prop(() => Date) opened?: Date;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
await Accounts.syncIndexes();
await client.unsafeDriver().db("app").command({
  collMod: "accounts",
  index: { name: "opened_ttl", expireAfterSeconds: 60 },
});
// ---cut---
console.log(await Accounts.diffIndexes());
// → { toCreate: [], toDrop: [], toModify: [{ name: "opened_ttl", expireAfterSeconds: 3600 }] }
```

Добавление или снятие TTL у существующего индекса код считает перестройкой, а не изменением на месте. Так у индекса не меняется смысл без пересоздания. Этот случай описан по коду и запуском не проверялся.

## Model.syncIndexes

`syncIndexes` приводит индексы сервера в точное соответствие со схемой. Он удаляет лишние, меняет на месте то, что можно, и создаёт недостающие. Это метод для шага деплоя и для скрипта миграции. Сами по себе индексы Typemo не создаёт. Пока вы не вызвали `syncIndexes` (или [`createIndexes`](#modelcreateindexes), или [`connection.init`](../connection/connection.mdx#connectioninit)), уникальность из схемы на сервере не гарантирована.

У модели могут быть параметры, которые задаются только при создании коллекции (`capped`, `timeseries`, `clustered`, `collation`). Если при этом коллекции ещё нет, `syncIndexes` ничего не создаёт и бросает [`ConfigurationError`](../errors/configuration-errors.mdx#configurationerror). Иначе индекс создал бы обычную коллекцию, и параметры потерялись бы. Сначала создайте коллекцию через [`ensureCollection`](./collection-manager.mdx#modelensurecollection) или [`connection.init`](../connection/connection.mdx#connectioninit). С `dryRun: true` такой проверки нет, потому что он ничего не пишет.

Шаги идут в таком порядке. Сначала удаляются индексы из `toDrop`, потом применяются изменения из `toModify`, потом создаются индексы из `toCreate`. Пересоздаваемый индекс сначала удаляется, потом создаётся. Если шаг не удался, метод не останавливается. Он пробует всё остальное и в конце бросает одну ошибку [`IndexSyncError`](../errors/configuration-errors.mdx#indexsyncerror) со всеми неудачами. Индексы, которые получилось применить, остаются.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ opened: 1 }, { name: "opened_ttl", expireAfterSeconds: 3600 })
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
  @Prop(() => Date) opened?: Date;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
// ---cut---
const result = await Accounts.syncIndexes();
console.log(result.toCreate, result.dryRun);
// → ["title_1", "owner_1", "opened_ttl"] false
```

<Returns type="Promise<IndexSyncResult>">

Объект [`IndexSyncResult`](#indexsyncresult) — те же три списка, что у [`IndexDiff`](#indexdiff), и поле `dryRun`. Списки описывают то, что применено (при `dryRun` — что было бы применено). Повторный вызов на синхронизированной коллекции вернёт пустые списки.

</Returns>

<Params>
<Param name="options.dryRun" type="boolean" default="false">

Только сообщить, что изменилось бы, и ничего не записывать. Результат тот же, что у [`diffIndexes`](#modeldiffindexes), но с `dryRun: true`. Так деплой можно проверить заранее.

</Param>
</Params>

<FullType>

```ts
syncIndexes(options?: { readonly dryRun?: boolean }): Promise<IndexSyncResult>
```

</FullType>

### Проверить, не записывая

С `dryRun: true` метод возвращает план и не трогает сервер.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ opened: 1 }, { name: "opened_ttl", expireAfterSeconds: 3600 })
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
  @Prop(() => Date) opened?: Date;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
// ---cut---
const plan = await Accounts.syncIndexes({ dryRun: true });
console.log(plan.dryRun, plan.toCreate);
// → true ["title_1", "owner_1", "opened_ttl"]
console.log((await Accounts.listIndexes()).length);
// → 0
```

### Данные нарушают уникальность

Чаще всего метод падает потому, что в коллекции уже лежат документы, нарушающие новый уникальный индекс. Пусть в `accounts` два счёта с названием `Main`, а схема требует уникальный `title`. Метод создаст остальные индексы и бросит ошибку про `title_1`.

```ts twoslash
import { Entity, Index, IndexSyncError, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ opened: 1 }, { name: "opened_ttl", expireAfterSeconds: 3600 })
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
  @Prop(() => Date) opened?: Date;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
await client.unsafeDriver().db("app").collection("accounts").insertMany([
  { title: "Main", owner: "alice" },
  { title: "Main", owner: "bob" },
]);
// ---cut---
try {
  await Accounts.syncIndexes();
} catch (error) {
  if (error instanceof IndexSyncError) {
    console.log(error.model, error.failures.map((f) => [f.name, f.action, f.error.name]));
    // → "Account" [["title_1", "create", "DuplicateKeyError"]]
    console.log((await Accounts.listIndexes()).map((index) => index.name));
    // → ["_id_", "owner_1", "opened_ttl"]
  }
}
```

Текст ошибки короткий. В нём индекс, значение и код `DuplicateKeyError`. Длинный текст сервера лежит в `serverMessage` вложенной ошибки. В нём есть идентификаторы сборки индекса, и они зависят от версии MongoDB.

```text
IndexSyncError: Account: 1 index operation(s) failed: create title_1: duplicate key on title_1: { title: "Main" } (code 11000 DuplicateKey)
```

`owner_1` и `opened_ttl` созданы и остались, неудача одного индекса остальные не откатывает. Исправьте данные и вызовите `syncIndexes` ещё раз. Создастся только недостающий `title_1`.

## Model.createIndexes

`createIndexes` создаёт индексы схемы, ничего не удаляя и не сравнивая. Берите его, когда лишних индексов точно нет и нужно просто доложить недостающие. В остальных случаях выбирайте [`syncIndexes`](#modelsyncindexes), он и удаляет, и меняет.

Как и `syncIndexes`, метод собирает все неудачи и бросает одну [`IndexSyncError`](../errors/configuration-errors.mdx#indexsyncerror). У модели с параметрами «только при создании» и без коллекции он бросает ту же [`ConfigurationError`](../errors/configuration-errors.mdx#configurationerror). Повторный вызов безопасен, ведь индекс, который уже есть в точности таким же, сервер не пересоздаёт.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ opened: 1 }, { name: "opened_ttl", expireAfterSeconds: 3600 })
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true, index: true }) owner!: string;
  @Prop(() => Date) opened?: Date;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Accounts = client.connection.model(Account);
// ---cut---
console.log(await Accounts.createIndexes());
// → ["title_1", "owner_1", "opened_ttl"]
console.log(await Accounts.createIndexes());
// → ["title_1", "owner_1", "opened_ttl"]
```

<Returns type="Promise<readonly string[]>">

Имена **всех** индексов схемы, которые после вызова есть на сервере. Имена приходят и у индексов, которые уже были в точности такими же (второй вызов выше вернул тот же список). Поэтому по списку не понять, что создано именно сейчас. Для этого вызовите [`diffIndexes`](#modeldiffindexes) до `createIndexes`, его `toCreate` покажет то, что будет создано.

</Returns>

Принимает ничего.

<FullType>

```ts
createIndexes(): Promise<readonly string[]>
```

</FullType>

### Индекс с тем же именем, но другими опциями

`createIndexes` существующий индекс не заменяет. Допустим, на сервере есть `title_1` без `unique`, а схема требует уникальный. Сервер не станет создавать второй индекс с тем же именем, и вы получите `IndexSyncError`.

```text
IndexSyncError: Account: 1 index operation(s) failed: create title_1: An existing index has the same name as the requested index. (code 86 IndexKeySpecsConflict)
```

В таком случае берите [`syncIndexes`](#modelsyncindexes). Он видит различие, удаляет старый индекс и создаёт новый.

## Model.diffSearchIndexes <Badge variant="requires">Atlas Search</Badge>

`diffSearchIndexes` сравнивает **поисковые индексы** схемы с теми, что есть на сервере. Это индексы Atlas Search и Atlas Vector Search, их описывает декоратор [`@SearchIndex`](../schemas/index-decorators.mdx#searchindex). Сервер строит их отдельным процессом и хранит отдельно от обычных. Работают они только там, где есть Atlas Search, то есть в Atlas или в локальном развёртывании Atlas CLI. Сравнение идёт по имени, а тип и определение индекса должны совпасть.

Обычный `mongod` без Atlas Search отвечает на такой запрос ошибкой. Typemo не превращает её в «индексов нет», и ошибка доходит до вас. Так вы не примете отсутствие поиска на сервере за «всё синхронизировано».

<Returns type="Promise<SearchIndexDiff>">

Объект [`SearchIndexDiff`](#searchindexdiff). В `toCreate` лежат индексы схемы, которых нет на сервере. В `toUpdate` — индексы, которые есть, но тип или определение отличаются. В `toDrop` — индексы сервера, которых нет в схеме.

</Returns>

Принимает ничего.

<FullType>

```ts
diffSearchIndexes(): Promise<SearchIndexDiff>
```

</FullType>

```ts twoslash
import { Entity, Prop, Schema, SearchIndex, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "articles" })
@SearchIndex({ name: "articles_text", definition: { mappings: { dynamic: true } } })
class Article extends Entity {
  @Prop(() => String, { required: true }) body!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Articles = client.connection.model(Article);
// ---cut---
const diff = await Articles.diffSearchIndexes();
console.log(diff.toCreate, diff.toUpdate, diff.toDrop);
// на сервере с Atlas Search: ["articles_text"] [] []
```

Результат этого примера **не проверялся запуском**, потому что тестовый сервер Atlas Search не поддерживает. А вот что метод делает на сервере без поиска, проверено. Он бросает [`ServerError`](../errors/server-errors.mdx#servererror) с кодом `31082` (`SearchNotEnabled`). В `message` лежат причина и код, а полный текст сервера с подсказкой, куда подключиться, лежит в [`serverMessage`](../errors/server-errors.mdx#servererror).

```text
ServerError: Using Atlas Search Database Commands and the $listSearchIndexes aggregation stage requires additional configuration. (code 31082 SearchNotEnabled)
```

## Model.syncSearchIndexes <Badge variant="requires">Atlas Search</Badge>

`syncSearchIndexes` приводит поисковые индексы сервера в соответствие со схемой. Он создаёт недостающие, обновляет отличающиеся и удаляет лишние. Работает он как [`syncIndexes`](#modelsyncindexes) для обычных индексов. Метод пробует все шаги, собирает неудачи и в конце бросает [`IndexSyncError`](../errors/configuration-errors.mdx#indexsyncerror). Шаги идут по порядку — удаление, обновление, создание.

<Returns type="Promise<SearchIndexSyncResult>">

Объект [`SearchIndexSyncResult`](#searchindexsyncresult) — три списка, как у [`SearchIndexDiff`](#searchindexdiff), и `dryRun`.

</Returns>

<Params>
<Param name="options.dryRun" type="boolean" default="false">

Только сообщить, что изменилось бы. Но за списком поисковых индексов проверка всё равно обращается к серверу, поэтому на сервере без поиска `dryRun` тоже бросает `ServerError` с кодом `31082`.

</Param>
</Params>

<FullType>

```ts
syncSearchIndexes(options?: { readonly dryRun?: boolean }): Promise<SearchIndexSyncResult>
```

</FullType>

Поведение на сервере с Atlas Search **запуском не проверялось** (нет окружения), оно описано по коду. Проверено другое. На обычном `mongod` вызов, в том числе с `dryRun: true`, бросает `ServerError` с кодом `31082`.

## Когда методы не подходят

Чтобы привести в порядок всю базу за один вызов — коллекции, индексы, поисковые индексы и представления сразу, — берите [`connection.syncAll`](../connection/connection.mdx#connectionsyncall). Он проходит по всем моделям, не останавливается на первом сбое и в конце бросает одну [`SyncError`](../errors/configuration-errors.mdx#syncerror) со всеми сбоями и полным отчётом. Если нужно только создать недостающее, ничего не меняя, а при расхождении получить ошибку, берите [`connection.init`](../connection/connection.mdx#connectioninit). Для коллекции и её параметров (`capped`, валидатор, временные ряды) индексные методы не годятся. Они описаны в [`CollectionManager`](./collection-manager.mdx) и в методах модели [`ensureCollection`](./collection-manager.mdx#modelensurecollection) и [`createCollection`](./collection-manager.mdx#modelcreatecollection).

Руководства с реальными задачами — [Синхронизация индексов](../../collections/index-sync.mdx) и [Поисковые индексы](../../collections/search-indexes.mdx).
