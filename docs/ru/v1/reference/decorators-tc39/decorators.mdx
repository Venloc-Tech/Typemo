Пакет `@venloc/typemo-decorators` даёт те же декораторы, что и ядро `@venloc/typemo`, но в форме **стандартных декораторов TC39**. Им не нужны ни флаг `experimentalDecorators`, ни `reflect-metadata` (`emitDecoratorMetadata` не нужен ни в одном режиме). Если у вас свой `lib`, добавлять в него `esnext.decorators` не требуется. Имена, аргументы и опции те же.

Пакет ничего не описывает заново. Он записывает то, что вы объявили, в тот же построитель метаданных ядра, поэтому схема, модель, запросы и типы получаются такими же, как с декораторами ядра.

Как перейти на этот пакет и что поставить в `tsconfig`, рассказывает руководство [Использовать TC39-декораторы](../../decorators-tc39/tc39.mdx). Здесь только отличия каждого декоратора от одноимённого декоратора ядра. Полные списки опций ищите в справочнике схем, ссылки есть в каждом разделе.

Блоки кода этой страницы сборка документации не компилирует. Она проверяет код с legacy-декораторами, а этому пакету нужен режим без `experimentalDecorators`. Поведение проверено запуском на настоящей базе, в пакете с выключенными legacy-флагами.

В примерах — модель счёта.

```ts title="accounts/account.ts"
import { Entity } from "@venloc/typemo";
import { Index, Pre, Prop, Schema } from "@venloc/typemo-decorators";

@Schema({ collection: "accounts" })
@Index({ title: 1, balance: -1 }, { unique: true })
export class Account extends Entity {
  @Prop(() => String, { required: true, trim: true })
  title!: string;

  @Prop(() => Number, { min: 0 })
  balance!: number;

  @Pre("document.save")
  touch(this: Account): void {
    this.title = `${this.title}!`;
  }
}
```

`create({ title: "  Main ", balance: 5 })` сохранил счёт с заголовком `"Main!"`. `trim` убрал пробелы, хук добавил знак. А `create({ title: "x", balance: -1 })` бросил `ValidationError: Validation failed: "balance": must be at least 0 [min]`.

Общее для всех декораторов пакета — **импортируйте пакет до первого класса схемы**. При загрузке пакет ставит `Symbol.metadata`, если его ещё нет в окружении (`Symbol.metadata ??= Symbol.for("Symbol.metadata")`). Bun и Node пока его не определяют. Это единственная глобальная запись пакета, и она стандартная. Обычный `import { Prop } from "@venloc/typemo-decorators"` выполняет её сам.

**Пакеты смешивать нельзя.** Декоратор не того пакета бросает `ConfigurationError` сразу при объявлении класса. В проекте без `experimentalDecorators` декоратор `@Prop` из ядра дал `ConfigurationError: @Prop from "@venloc/typemo" is a legacy decorator, but it was applied as a TC39 decorator (experimentalDecorators is off). Use "@venloc/typemo-decorators" in a TC39 project; the two packages cannot be mixed`.

Метаданные обоих видов могут всё же встретиться на одном классе или в одной иерархии, например в базовом классе из библиотеки, собранной в другом режиме. Тогда первый `model()` бросит `ConfigurationError: Mixed: mixes legacy decorators ("@venloc/typemo", on Mixed) and TC39 decorators ("@venloc/typemo-decorators", on Mixed) in one class hierarchy; use one decorator package per project`. Тихого слияния нет.

## @Schema

`@Schema` объявляет класс схемой и принимает те же опции, что [`@Schema` ядра](../schemas/schema.mdx#schema) — `collection`, `nested`, `timeseries`, `tenant`, `softDelete` и остальные. Компилятор проверяет их так же, с сохранением литеральных типов.

```ts
@Schema({ collection: "accounts" })
class Account extends Entity {}
```

<Params>
<Param name="options" type="SchemaOptions" default="{}">

Опции схемы. Описаны в справочнике [`@Schema`](../schemas/schema.mdx#schema).

</Param>
</Params>

Если применить декоратор не к классу, будет `ConfigurationError: @Schema is a class decorator, got <вид>`. О смешивании с legacy читайте выше. Руководство — [Описать модель](../../schemas/define-model.mdx).

<FullType>

```ts
const Schema: <const O extends SchemaOptions = Record<never, never>>(
  options?: O,
) => <C extends EntityClass>(target: C & SchemaCheck<C, O>, context: ClassDecoratorContext<C>) => void;
```

</FullType>

## @Prop

`@Prop` объявляет поле схемы. Опции те же, что у [`@Prop` ядра](../schemas/prop.mdx#prop) — `required`, `nullable`, `default`, `trim`, `min`, `sensitive` и остальные. Компилятор так же сверяет их с типом поля.

Отличие одно, зато обязательное. **Тип передаётся функцией**, `@Prop(() => String)`. У стандартных декораторов нет `design:type`, и компилятор не знает тип поля во время работы. Назовите его явно в каждом поле.

```ts
@Prop(() => String, { required: true, trim: true })
title!: string;
```

<Params>
<Param name="type" type="() => TypeSpec" required>

Функция, которая возвращает тип, например `() => String`, `() => [Address]` или `() => Types.ObjectId`.

</Param>
<Param name="options" type="PropOptions<S>">

Опции поля. Описаны в справочнике [`@Prop`](../schemas/prop.mdx#prop).

</Param>
</Params>

Декоратор знает тип поля из контекста, поэтому ошибки видны в момент применения. Во время работы он бросает `ConfigurationError`, если его применили не к обычному полю. Тексты взяты из реального запуска.

- Поле `#private` — `@Prop on private field "#x" (#private fields cannot be schema members)`.
- Статическое поле — `@Prop on static member "label" (static members are not schema members)`.
- Метод — `@Prop on "greet", which is a method (getters are virtuals and need no decorator)`.
- Поле с символьным именем — `@Prop on a symbol-keyed field (schema fields have string names)`.
- Нет функции типа — `@Prop "name": the type must be a thunk () => T (for example () => String), got undefined`, а с `@Prop(String)` — `…got String`.

Во время компиляции те же случаи отвергают типы. У статических и `#private` полей и у `private`/`protected` членов декоратор проверку не проходит, и компилятор сообщает `TS1240`. В тексте названа причина, например `@Prop "#x": #private fields cannot be schema fields`, `@Prop "label": static fields are not schema fields` или `@Prop "secret": not a public field (private and protected fields cannot be schema fields)`.

<FullType>

```ts
const Prop: <const S extends TypeSpec, const O extends PropOptions<S>>(
  type: () => S,
  options?: O & NoExtraOptions<O, PropOptions<S>>,
) => Tc39PropDecorator<S, O>;
```

</FullType>

## @Tenant

`@Tenant()` помечает поле тенанта. Ставьте его рядом с `@Prop` на поле типа `TenantField<T>`, как [`@Tenant` ядра](../schemas/field-markers.mdx#tenant). Схема с опцией `tenant` без такой пометки не соберётся, так что декоратор нужен в каждой схеме, разделённой по тенантам. Зачем, рассказывает руководство [Тенанты](../../policies/tenants.mdx#описать-поле-тенанта).

```ts
@Schema({ collection: "notes", tenant: true })
class Note extends Entity {
  @Prop(() => String)
  @Tenant()
  tenantId!: TenantField<string>;
}
```

Аргументов нет. Возвращает декоратор поля.

Правила сборки схемы общие с ядром, ошибки те же. При первом `model()` запуск дал `ConfigurationError` трёх видов.

- Опция `tenant` есть, пометки нет — `Note: the tenant field "tenantId" must be marked @Tenant() (declare it @Prop(...) @Tenant() tenantId!: TenantField<T>)`.
- Пометка есть, опции нет — `Note: @Tenant() on "tenantId", but the schema has no tenant policy — add tenant: true (or { field }) to @Schema`.
- Пометок две — `Note: @Tenant() marks "tenantId", "other"; only the tenant field "tenantId" may be marked`.

Поле другого типа компилятор отвергает сообщением `@Tenant "other": declare the field as TenantField<T>` (`TS1240`). На `#private` и статическом члене декоратор бросает `ConfigurationError` с тем же текстом, что у `@Prop`, например `@Tenant on private field "#x" (#private fields cannot be schema members)`.

<FullType>

```ts
const Tenant: () => Tc39TenantDecorator;
```

</FullType>

## @Virtual

`@Virtual` объявляет виртуальное поле подгрузки связей на поле типа `VirtualRef`. Опции те же, что у [`@Virtual` ядра](../schemas/virtual.mdx#virtual) — `ref`, `localField`, `foreignField`, `justOne`, `count`, `match`, `options`, `perDocumentLimit`.

```ts
@Virtual({ ref: () => Post, localField: "_id", foreignField: "author" })
posts!: VirtualRef<Post>;
```

<Params>
<Param name="options" type="VirtualOptions" required>

Опции связи. Описаны в справочнике [`@Virtual`](../schemas/virtual.mdx#virtual).

</Param>
</Params>

К не-полю, статическому члену, `#private` и полю с символьным именем декоратор применить нельзя, будет `ConfigurationError`.

## @Discriminator

`@Discriminator` делает класс наследником базового класса по ключу дискриминатора. Значение по умолчанию — имя класса. Контракт тот же, что у [`@Discriminator` ядра](../schemas/discriminator.mdx#discriminator).

```ts
@Discriminator("savings")
class SavingsAccount extends Account {}
```

<Params>
<Param name="value" type="string">

Значение ключа дискриминатора. По умолчанию имя класса.

</Param>
</Params>

## @Index

`@Index` объявляет на классе составной или любой другой индекс. Поля и опции проверяются по классу, как у [`@Index` ядра](../schemas/index-decorators.mdx#index).

```ts
@Index({ title: 1, balance: -1 }, { unique: true })
class Account extends Entity {}
```

<Params>
<Param name="fields" type="IndexFields" required>

Поля индекса с направлениями.

</Param>
<Param name="options" type="IndexOptions" default="{}">

Опции индекса — `unique`, `sparse`, `expireAfterSeconds` и другие. См. [`@Index`](../schemas/index-decorators.mdx#index).

</Param>
</Params>

## @SearchIndex

`@SearchIndex` описывает индекс Atlas Search или Vector Search. Опции те же, что у [`@SearchIndex` ядра](../schemas/index-decorators.mdx#searchindex). Индексы поиска работают только с Atlas или с конфигурацией, которая их поддерживает. Этот декоратор лишь записывает описание.

<Params>
<Param name="options" type="SearchIndexOptions" required>

Определение индекса поиска.

</Param>
</Params>

## @Plugin

`@Plugin` подключает плагин схемы к классу при компиляции схемы. Это то же, что [`Typemo.plugin`](../connection/typemo.mdx#typemoplugin), но для одной модели. Если тип настроек плагина не допускает `undefined`, настройки обязательны.

<Param name="plugin" type="SchemaPlugin<O>" required>

Плагин схемы.

</Param>
<Param name="options" type="O">

Настройки плагина.

</Param>
</Params>

Руководство — [Плагины](../../hooks/plugins.mdx).

## @Pre

`@Pre` помечает метод класса хуком «до события». События и `this` те же, что у [`@Pre` ядра](../hooks/pre-post.mdx#pre). В хуках документа `this` — документ, пишите `touch(this: Account)`. В хуках операций это контекст операции.

```ts
@Pre("document.save")
touch(this: Account): void {}
```

<Params>
<Param name="events" type="HookEvent | [HookEvent, ...HookEvent[]]" required>

Событие или несколько событий.

</Param>
</Params>

Хуком может быть только метод экземпляра со строковым именем. На поле, геттере или методе с символьным именем декоратор бросает `ConfigurationError: @Pre: a hook must be a string-named instance method, got field`, где вместо `field` стоит вид члена, например `getter`. Статический хук компилятор не принимает. Во время работы `@Pre` называет причину так же, как `@Prop` — `@Pre on static member "m" (static members are not schema members)`.

В хуках документа `this` объявляется так же, как у декораторов ядра. Для работы с полями пишите `touch(this: Account)`, для методов документа — `touch(this: HookThis<"document.save", Account>)`. Хук класса запускается и на поддокументе, если класс встроен в другую модель. Поэтому методы корня (`$getChanges()`, `$save()`) доступны после проверки [`this.$isRoot()`](../documents/document-api.mdx#isroot), а `touch(this: HydratedDoc<Account>)` не компилируется. Подробности в справочнике [`@Pre`](../hooks/pre-post.mdx#this-зависит-от-области-события).

## @Post

`@Post` помечает метод хуком «после успешного события» и получает результат. Остальное как у [`@Post` ядра](../hooks/pre-post.mdx#post).

## @PostError

`@PostError` помечает метод хуком «после ошибки события». Он вызывается вместо `@Post` и получает ошибку. Остальное как у [`@PostError` ядра](../hooks/pre-post.mdx#posterror).

## Типы пакета

Пакет экспортирует и типы возвращаемых декораторов — `Tc39PropDecorator`, `Tc39TenantDecorator`, `Tc39VirtualDecorator`, `Tc39HookDecorator` и `Tc39PropCheck` (проверка опций против типа поля). Они нужны, только если вы пишете обёртку над декоратором и вам надо назвать его тип.

## Когда пакет не подходит

Если в проекте включён `experimentalDecorators`, например этого требует другая библиотека, берите декораторы ядра `@venloc/typemo`. Флаг действует на весь проект, и TC39-декораторы в нём работать не будут. Как выбрать, читайте в руководстве [Использовать TC39-декораторы](../../decorators-tc39/tc39.mdx#выбрать-пакет).
