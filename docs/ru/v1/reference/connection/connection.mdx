`Connection` — это одна база клиента вместе с её моделями. Через него вы берёте модель по классу-сущности, переходите к другой базе того же клиента, создаёте в базе всё, что нужно моделям, и запускаете транзакции. Соединений `Connection` сам не открывает. Сеть, пул и закрытие остаются за [`TypemoClient`](./typemo-client.mdx), а `Connection` лишь выбирает базу.

Создавать `Connection` вам не нужно, его выдаёт [`client.db`](./typemo-client.mdx#clientdb) или [`client.connection`](./typemo-client.mdx#clientconnection). Если вы только начинаете, сначала прочитайте руководство [Подключиться к базе](../../connection/connect.mdx). Эта страница — справочник.

В примерах модель счёта с уникальным полем, чтобы `init` и `syncAll` было что создавать.

```ts twoslash title="accounts/account.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;
}
```

Поля `connection.client` (клиент-владелец) и `connection.name` (имя базы) только читаются.

```ts twoslash
import { TypemoClient } from "@venloc/typemo";
const client = new TypemoClient("mongodb://localhost:27017", { dbName: "app" });
// ---cut---
const connection = client.connection;
console.log(connection.name, connection.client === client);
// → "app" true
```

## connection.model

`connection.model` возвращает модель для класса с `@Schema`. Через модель вы читаете и пишете документы. Первый вызов компилирует схему класса — проверяет описание полей, применяет плагины и расширения. Поэтому ошибки в схеме вы увидите на этом вызове, а не на первой операции.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = new TypemoClient("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
// ---cut---
const Accounts = connection.model(Account);
console.log(Accounts === connection.model(Account));
// → true
```

<Returns type="Model<T>">

Модель класса на этом подключении. Для одного класса вы всегда получаете один и тот же объект. На другом подключении, то есть в другой базе, модель того же класса будет другой — у неё своя база, и данные не пересекаются.

</Returns>

<Params>
<Param name="entity" type="EntityClass<T>" required>

Класс с `@Schema`. Если передать не класс, вызов сразу бросит `ConfigurationError` с текстом `connection.model: an entity class (@Schema)`.

</Param>
</Params>

<FullType>

```ts
model<T extends object>(entity: EntityClass<T>): Model<T>
```

</FullType>

Что делать с моделью дальше, описано в руководстве [Чтение](../../queries/reading-data.mdx) и в [справочнике чтения](../query/reading.mdx).

## connection.models

Все модели, которые уже зарегистрированы на этом подключении, в порядке регистрации. Список удобен для проверок и служебных скриптов, например чтобы пройти по моделям и вывести имена коллекций.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = new TypemoClient("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
connection.model(Account);
// ---cut---
console.log(connection.models.map((model) => model.modelName));
// → ["Account"]
```

Тип — `readonly Model<object>[]`. В списке только те модели, для которых вы вызывали [`connection.model`](#connectionmodel). Класс, который вы не регистрировали, там не появится.

## connection.useDb

`connection.useDb` возвращает подключение к другой базе **того же клиента**. С ним можно работать с несколькими базами, скажем по одной на тенанта или на отчёты, и не открывать новых соединений. Пул общий, а модели у каждой базы свои.

```ts twoslash
import { TypemoClient } from "@venloc/typemo";
const client = new TypemoClient("mongodb://localhost:27017", { dbName: "app" });
// ---cut---
const reports = client.connection.useDb("reports");
console.log(reports.name, reports === client.db("reports"));
// → "reports" true
```

Метод делает то же, что [`client.db(name)`](./typemo-client.mdx#clientdb), только вызывается от подключения. Закрывать `reports` отдельно не нужно, да и нельзя — закрывается весь клиент через [`client.close`](./typemo-client.mdx#clientclose). Пустое имя даёт `ConfigurationError`.

<Params>
<Param name="name" type="string" required>

Имя базы.

</Param>
</Params>

Возвращает `Connection`.

## connection.init

`connection.init` создаёт в базе всё, что нужно моделям подключения и чего там ещё нет. Это коллекции (с параметрами схемы), индексы, поисковые индексы и представления. Typemo ничего не создаёт сам, `init` вы вызываете явно — при старте приложения или на шаге деплоя, когда модели уже зарегистрированы через [`connection.model`](#connectionmodel).

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
connection.model(Account);
// ---cut---
const report = await connection.init();
console.log(report.inSync, report.created);
// → true ["collection accounts", "index accounts.title_1"]
console.log(report.collections[0]?.indexes?.toCreate);
// → ["title_1"]
```

`init` ничего не удаляет и не меняет. Лишний индекс остаётся, а индекс или коллекция, объявленные иначе, чем в базе, дают сбой (см. «Ошибки» ниже). Заменять существующее умеет [`connection.syncAll`](#connectionsyncall).

Если `init` вернул отчёт, база соответствует моделям, и `inSync` равен `true`. Так и в первый вызов, когда метод что-то создал, и в повторные. Созданное перечислено в `created` строками вида `"collection accounts"`, `"index accounts.title_1"`, `"search index accounts.default"`, `"view active_accounts"`. Если создавать было нечего, список пуст, и второй вызов подряд вернул `created: []`.

<Returns type="Promise<SyncReport>">

Отчёт о том, что есть и что создано. В нём `collections` и `views` (по записи на каждую), `created`, `inSync` и `failed`. У возвращённого отчёта всегда `failed: false`, потому что любой сбой шага становится исключением (см. ниже). Поля отчёта описаны в справочнике [`SyncReport`](../collections/sync-all.mdx#syncreport).

</Returns>

Принимает ничего.

<FullType>

```ts
init(): Promise<SyncReport>
```

</FullType>

### Ошибки

`init` выполняет все шаги всех моделей до конца, и сбой одной модели остальные не останавливает. Если хоть один шаг не удался, вместо отчёта вы получите [`SyncError`](../errors/configuration-errors.mdx#syncerror). В нём `operation` (`"connection.init"`), `failures` (сбои по коллекциям и представлениям), `errors` (все исходные ошибки подряд) и `report` (полный отчёт с `failed: true`). В `cause` лежит `AggregateError` с теми же исходными ошибками. Типичный сбой — индекс, который в базе объявлен иначе, чем в схеме.

```ts twoslash
import { Entity, Prop, Schema, SyncError, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
connection.model(Account);
// ---cut---
try {
  await connection.init();
} catch (error) {
  if (error instanceof SyncError) {
    console.log(error.operation, error.failures.map((failure) => failure.name));
    // → "connection.init" ["accounts"]
  }
}
```

Сообщение называет подключение, число сбоев и причину каждого. Мы получили этот текст на базе, где индекс `title_1` уже создан без `unique`.

```text
SyncError: connection.init() of "app": 1 failure(s) — collection "accounts": Account: 1 index operation(s) failed: create title_1: index "title_1" exists on the server with other keys or options; init() never drops or changes an index — run syncIndexes()/syncAll() to replace it
```

Каждое имя в сообщении встречается один раз. Модель называет вложенная [`IndexSyncError`](../errors/configuration-errors.mdx#indexsyncerror) (`Account: 1 index operation(s) failed: …`), а её собственные сбои начинаются с действия и индекса. Если вложенная ошибка сама называет коллекцию, как `CollectionOptionsError` (`collection "logs": exists with options MongoDB cannot change (capped): drop the collection and create it again`), `SyncError` имя коллекции не повторяет.

Тихого пропуска тут нет, потому что `init` обещает «после меня база соответствует моделям». Индекс, который остался другим, нарушает это обещание, и приложение должно узнать об этом при старте, а не на первой дублирующей записи.

Как создаются коллекции и индексы, подробно описано в руководствах [Создание коллекций](../../collections/create.mdx) и [Синхронизация индексов](../../collections/index-sync.mdx).

## connection.syncAll

`connection.syncAll` приводит коллекции, индексы, поисковые индексы и представления базы в соответствие со схемами моделей. В отличие от [`connection.init`](#connectioninit) он умеет заменять существующее. Он меняет индексы, которые отличаются от схемы, а с `update` — ещё и параметры коллекций и представлений. Как и `init`, он проходит все шаги всех моделей и в конце сообщает о сбоях одним [`SyncError`](../errors/configuration-errors.mdx#syncerror). Поэтому его удобно ставить на шаг деплоя, который должен показать всё, что не сошлось.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
connection.model(Account);
// ---cut---
const plan = await connection.syncAll({ dryRun: true });
console.log(plan.inSync, plan.created, plan.collections[0]?.indexes?.toCreate);
// → false ["collection accounts", "index accounts.title_1"] ["title_1"]
```

С `dryRun: true` метод только показывает, что изменилось бы. Ни коллекции, ни индексы, ни представления он не записывает, так что базу можно проверить до деплоя. Пока есть что создавать или менять, `inSync` у пробного запуска равен `false`.

<Params>
<Param name="options.dryRun" type="boolean" default="false">

Только сообщить о различиях, ничего не записывая. В отчёте `created` перечисляет то, что было бы создано.

</Param>
<Param name="options.update" type="boolean" default="false">

Применить то, что умеет изменить `collMod` — параметры коллекции и конвейер представления. Без этой опции такое различие попадает в сбои шага.

</Param>
</Params>

<Returns type="Promise<SyncReport>">

Отчёт с полями `collections` и `views` (по записи на каждую), `created`, `inSync` (`true`, если ничего не отличалось и ничего не упало) и `failed` (у возвращённого отчёта всегда `false`). Если шаг не удался, вы получите `SyncError` с `operation: "syncAll"`, а отчёт со сбоями ищите в его поле `report`. Так же и с `dryRun`, если пробный запуск нашёл невозможное изменение.

</Returns>

<FullType>

```ts
syncAll(options?: SyncAllOptions): Promise<SyncReport>
```

</FullType>

Подробности отчёта — в справочнике [`SyncAll`](../collections/sync-all.mdx).

## connection.aggregate

`connection.aggregate` выполняет агрегацию уровня базы. Такой план не читает коллекцию модели, он работает со всей базой подключения, с базой `admin` или с сессиями сервера. С ним вы получаете выполняющиеся операции (`$currentOp`), литеральные документы (`$documents`) или локальные сессии (`$listLocalSessions`). План строят [`Pipeline.database`](../aggregation/pipeline.mdx#pipelinedatabase), [`Pipeline.admin`](../aggregation/pipeline.mdx#pipelineadmin) и [`Pipeline.sessions`](../aggregation/pipeline.mdx#pipelinesessions), а метод его выполняет.

```ts twoslash
import { Pipeline, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
// ---cut---
const rows = await connection.aggregate(
  Pipeline.database()
    .documents([{ n: 1 }, { n: 2 }, { n: 3 }])
    .match({ n: { $gt: 1 } })
    .plan(),
);
console.log(rows);
// → [{ n: 2 }, { n: 3 }]
```

Операция идёт тем же путём, что и запросы моделей. В транзакции `connection.transaction` она участвует сама, `timeoutMS` действует, ошибки сервера приходят как ошибки Typemo, а подписчики [`client.instrument`](./typemo-client.mdx#clientinstrument) получают события.

От [`Model.aggregate`](../aggregation/pipeline.mdx#modelaggregate) метод отличается двумя вещами. У операции нет модели, поэтому в её событиях `model` и `collection` равны `null` (у плана `Pipeline.sessions` коллекция `"system.sessions"`), а `database` называет базу, где она выполнена. И хуки не вызываются, ведь они регистрируются на моделях. Политики моделей, к которым план обращается через `$lookup` или `$unionWith`, по-прежнему действуют.

Базу выбирает план. `Pipeline.database()` работает в базе подключения, `Pipeline.admin()` всегда в `admin`, `Pipeline.sessions()` всегда в `config.system.sessions`, с какого бы подключения вы ни вызвали метод. Такой же метод есть у клиента — [`client.aggregate`](./typemo-client.mdx#clientaggregate) работает с базой клиента по умолчанию.

<Returns type="AggregateQuery<R>">

Запрос агрегации, типизированный строками плана. После `await` вы получите массив строк. `.cursor()` отдаёт их по одной, `.explain()` показывает план сервера, `.plain()` превращает значения BSON в данные для клиента, а `.timeoutMS()`, `.session()`, `.policy()` и остальные методы настраивают запуск так же, как у `Model.aggregate`.

</Returns>

<Params>
<Param name="plan" type="AggregatePlan<R>" required>

План агрегации — результат `.plan()` у строителя `Pipeline.database()`, `Pipeline.admin()` или `Pipeline.sessions()`.

</Param>
<Param name="options" type="ModelAggregateOptions">

Необязательные параметры запуска. `session` — своя сессия (`null` выполняет вне текущей транзакции), `timeoutMS` — клиентский срок операции, `policy` — значения политик поверх окружающего контекста.

</Param>
</Params>

<FullType>

```ts
aggregate<R>(plan: AggregatePlan<R>, options?: ModelAggregateOptions): AggregateQuery<R>
```

</FullType>

### Ошибки

Метод бросает ошибку сразу при вызове, до обращения к базе, в двух случаях. Если аргумент не план агрегации, это `QueryError` с именем вызванного метода. Если план читает коллекцию (`Pipeline.from(Account)`), это `ConfigurationError`, потому что такие планы выполняет `Model.aggregate`. А `Model.aggregate` в ответ бросит ошибку, если отдать ему план уровня базы.

```text
QueryError: connection.aggregate: an aggregation plan of Pipeline.database(), Pipeline.admin() or Pipeline.sessions()
ConfigurationError: connection.aggregate: the plan reads the collection "accounts"; run it with the model's aggregate()
ConfigurationError: Account.aggregate: the plan reads a database, not this model's collection "accounts"; run it with connection.aggregate(plan) or client.aggregate(plan)
```

Ошибки самого сервера во время выполнения приходят как [`ServerError`](../errors/server-errors.mdx#servererror), а исходная ошибка драйвера лежит в `cause`.

### Когда не подходит

Данные моделей читайте и пишите через саму модель, она применяет политики, маски и хуки. `aggregate` подключения берите только там, где у агрегации нет коллекции. Примеры с `$currentOp`, `$documents` и `$listSessions` — в руководстве [Запросы уровня базы](../../aggregation/database-level.mdx).

## connection.ready

`connection.ready` ждёт, пока подключится клиент, которому принадлежит база. Он делает то же, что [`client.ready`](./typemo-client.mdx#clientready), и нужен коду, который получил только `Connection` и хочет дождаться готовности.

```ts twoslash
import { TypemoClient } from "@venloc/typemo";
const client = new TypemoClient("mongodb://localhost:27017", { dbName: "app" });
// ---cut---
await client.connection.ready(2_000);
```

<Params>
<Param name="timeoutMS" type="number" default="client.options.readyTimeoutMS">

Сколько ждать, в миллисекундах. Ноль — без ограничения.

</Param>
</Params>

Возвращает `Promise<void>`. Когда время вышло, бросает `TimeoutError` с `kind: "connection"`.

## connection.transaction

`connection.transaction` запускает транзакцию на клиенте этого подключения. Это тот же [`client.transaction`](./typemo-client.mdx#clienttransaction), только вызванный от `Connection`. Транзакция к базе не привязана, так что в ней участвуют операции моделей разных баз одного клиента.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const connection = client.connection;
const Accounts = connection.model(Account);
// ---cut---
await connection.transaction(async () => {
  await Accounts.create({ title: "Checking", owner: "alice" });
});
```

Параметры, ошибки и поведение при повторах описаны у [`client.transaction`](./typemo-client.mdx#clienttransaction) и в руководстве [Транзакции](../../transactions/transactions.mdx).

<FullType>

```ts
transaction<R>(fn: TransactionCallback<R>, options?: TransactionOptions): Promise<R>
```

</FullType>

## connection.plugins

`connection.plugins` — реестр плагинов схем уровня подключения. `connection.plugins.use(plugin)` подключает плагин ко всем моделям этой базы, после глобальных плагинов (см. [`Typemo.plugin`](./typemo.mdx#typemoplugin)).

Регистрируйте плагин до первой модели подключения. Реестр закрывает первая **успешная** компиляция схемы на этом подключении, упавшая компиляция его не закрывает. Позже схемы уже скомпилированы, и плагин на них не повлияет, поэтому вы получите `ConfigurationError`.

```text
ConfigurationError: plugin "late": the connection plugins are fixed once a schema is compiled (Note was); register plugins before the first model
```

Как устроены плагины и что они добавляют в схему, написано в руководстве [Плагины](../../hooks/plugins.mdx) и в справочнике [Плагины](../hooks/plugins.mdx).

## Когда `Connection` не подходит

Сессию или подключение к другому серверу `Connection` не даст. Для этого есть [`client.startSession`](./typemo-client.mdx#clientstartsession) и отдельный [`TypemoClient`](./typemo-client.mdx). Если нужна операция, которой у модели нет, обратитесь к [`client.unsafeDriver`](./typemo-client.mdx#clientunsafedriver) и помните, что политики на неё не действуют.
