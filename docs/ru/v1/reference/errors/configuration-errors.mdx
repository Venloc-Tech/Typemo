Ошибки этой группы говорят не о данных, а о состоянии окружения: неверна настройка, нет связи с сервером, драйвер отказал на своей стороне, индексы и коллекции в базе разошлись со схемой, запись аудита не удалась. Они обычно возникают при запуске приложения или при первом обращении к базе и чаще всего требуют вмешательства человека, а не повтора запроса.

Если вы только начинаете, сначала прочитайте руководство [Обработка ошибок](../../errors/handling.mdx). Эта страница — справочник. Дерево классов — в разделе [Иерархия ошибок](./hierarchy.mdx).

Примеры используют модель счёта с уникальным названием: на ней видны и ошибки индексов, и ошибки настройки.

```ts twoslash title="accounts/account.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => String, { required: true })
  owner!: string;
}
```

Ошибки из групп соседних страниц: [ошибки данных](./data-errors.mdx), [ошибки запросов](./query-errors.mdx), [ошибки сервера](./server-errors.mdx).

## ConfigurationError

`ConfigurationError` бросается, когда найдена ошибка настройки, причём **до** того, как затронуты какие-либо данные: несовместимые опции клиента, невозможное описание поля (вектор нулевой размерности, объединение без вариантов), схема, которую нельзя построить, вызов, который не имеет смысла в текущем состоянии (транзакция внутри транзакции). Для плохих данных ошибка не бросается: их ловит [`CastError`](./data-errors.mdx#casterror) или [`ValidationError`](./data-errors.mdx#validationerror).

Почти всегда это ошибка программиста, и исправляется она в коде или конфигурации, а не повтором. Поэтому библиотека бросает её как можно раньше, а текст называет и проблему, и лекарство. Здесь схема просит оптимистичную блокировку, но не подключает поле версии:

```ts twoslash
import { ConfigurationError, Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
// ---cut---
@Schema({ collection: "orders", optimisticConcurrency: true })
class Order extends Entity {
  @Prop(() => String, { required: true })
  customer!: string;
}

try {
  client.connection.model(Order);
} catch (error) {
  if (error instanceof ConfigurationError) {
    console.log(error.message);
    // → Order: optimisticConcurrency needs the version field — extend Versioned(...)
  }
}
```

Модель компилируется при первом вызове [`connection.model`](../connection/connection.mdx#connectionmodel), поэтому ошибка схемы проявляется там, а не при объявлении класса.

### Где встречается

Тексты, полученные запуском, по ситуациям:

```text
ConfigurationError: transaction(): transactions do not nest (already inside a transaction of this client)
ConfigurationError: Account.countDocuments: called inside a transaction of another client; its model cannot join that transaction — pass session(null) (or { session: null }) to run it outside explicitly
ConfigurationError: TypemoClient: dbName must be a non-empty string
ConfigurationError: TypemoClient "default": transaction(): transactions need a replica set or a sharded cluster; this server is a standalone mongod. Run MongoDB as a replica set (a single-member one is enough).
ConfigurationError: Order: @Schema has no "strict" option (the options are: collection, nested, ext, discriminatorKey, discriminators, timeseries, capped, collation, clustered, changeStreamPreAndPostImages, validator, autoIndex, autoCreate, readConcern, writeConcern, optimisticConcurrency, shardKey, tenant, softDelete, audit)
```

Первая появляется при вложенной транзакции. Вторая — когда внутри транзакции одного клиента вызвана модель другого: она не может присоединиться к транзакции, и библиотека не молчит, а просит указать явно, что операция идёт вне транзакции. Третья — одна из проверок опций клиента; все они описаны в справочнике [`TypemoClient`](../connection/typemo-client.mdx#new-typemoclient). Четвёртая — `client.transaction` на одиночном `mongod`: транзакциям нужен реплика-сет или шардированный кластер, и вызов отказывает до того, как выполнится функция (см. [транзакции](../../transactions/transactions.mdx#транзакция-не-запускается-на-одиночном-сервере)). Пятая — неизвестный ключ в `@Schema`: опция, которой нет в списке, не молчит, а останавливает сборку схемы (подробности — на странице [`@Schema`](../schemas/schema.mdx)).

Схему с полем тенанта, которое не помечено `@Tenant()`, модель тоже отвергает при сборке: `Order: the tenant field "tenantId" must be marked @Tenant() (declare it @Prop(...) @Tenant() tenantId!: TenantField<T>)`. Остальные ошибки сборки схемы тенанта собраны в руководстве [Разделить данные организаций](../../policies/tenants.mdx#ошибки-сборки-схемы).

Сбои [`connection.init`](../connection/connection.mdx#connectioninit) и `syncAll` сюда не относятся: они приходят как [`SyncError`](#syncerror).

<Params title="Поля ошибки">
<Param name="message" type="string">

Что не так с настройкой. Собственных полей у класса нет: причина целиком в тексте, а первопричина, если она есть, в `cause`.

</Param>
</Params>

### Когда не подходит

Не ловите `ConfigurationError` вокруг каждой операции: он не про ввод пользователя. Ловите его при старте приложения, чтобы остановить запуск с внятным сообщением.

## ConnectionError

`ConnectionError` бросается, когда клиент не смог связаться с сервером или уже закрыт. Поле `failure` называет причину, а в `cause` лежит ошибка драйвера. Библиотека различает четыре причины, потому что действовать при каждой нужно по-разному: закрытый клиент создают заново, недоступный сервер и сеть ждут и повторяют, отказ в учётных данных повтором не исправить.

```ts twoslash
import { ConnectionError, TypemoClient } from "@venloc/typemo";
// ---cut---
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
await client.close();

try {
  await client.startSession();
} catch (error) {
  if (error instanceof ConnectionError) {
    console.log(error.failure);
    // → "closed"
    console.log(error.message);
    // → TypemoClient "default" is closed; create a new client
  }
}
```

<TypeTable
  type={{
    closed: { description: "Клиент закрыт (после `close()`). Создайте новый клиент." },
    "server-selection": { description: "Не найден сервер, подходящий для операции (`MongoServerSelectionError`)." },
    network: { description: "Сбой сети (`MongoNetworkError`)." },
    authentication: { description: "Сервер отверг учётные данные (код 18)." },
  }}
/>

Текст при недоступном сервере — `no server available: connect ECONNREFUSED 127.0.0.1:1` (запуск на закрытом порту), подробности и способ показать его — в разделе [`TypemoClient.connect`](../connection/typemo-client.mdx#typemoclientconnect). Классификация по коду драйвера: `MongoServerSelectionError` даёт `server-selection`, `MongoNetworkError` и `MongoNetworkTimeoutError` — `network`, остановленный клиент — `closed`. Причины `network` и `authentication` в запуске не воспроизводились.

### Поля

<Params title="Поля ошибки">
<Param name="failure" type="ConnectionFailure">

Причина: `closed`, `server-selection`, `network` или `authentication`.

</Param>
<Param name="errorLabels" type="readonly string[]">

Метки, которые прислал драйвер. Массив заморожен.

</Param>
</Params>

Ответ клиенту: база недоступна у вас, а не у пользователя, это 503 вашего приложения. Если клиент не успел подключиться к моменту операции, вы получите не эту ошибку, а [`TimeoutError`](./server-errors.mdx#timeouterror) с видом `connection`.

### Когда не подходит

Не создавайте клиент заново на каждую ошибку `server-selection`: драйвер сам переподключается, а операции ждут сервер до `serverSelectionTimeoutMS`. Пересоздание клиента нужно только после `closed`.

## DriverError

`DriverError` бросается, когда драйвер отказал **на стороне клиента**, не дойдя до сервера: вы неправильно использовали его API, и он это заметил. Типичные случаи: использована уже закрытая сессия, транзакция в неподходящем состоянии, неверный аргумент дошёл до драйвера. Ошибка драйвера сохраняется в `cause`, а её класс называет поле `driverError`.

Здесь запрос выполняется в сессии, которую уже закрыли:

```ts twoslash
import { DriverError, Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
// ---cut---
const session = await client.startSession();
await session.endSession();

try {
  await Accounts.countDocuments().session(session);
} catch (error) {
  if (error instanceof DriverError) {
    console.log(error.driverError, error.message);
    // → "MongoExpiredSessionError" "Use of expired sessions is not permitted"
  }
}
```

<Params title="Поля ошибки">
<Param name="driverError" type="string">

Имя класса ошибки драйвера (`MongoExpiredSessionError`, `MongoTransactionError`).

</Param>
<Param name="errorLabels" type="readonly string[]">

Метки ошибки драйвера. Массив заморожен.

</Param>
</Params>

Любая ошибка драйвера без кода сервера, которая не подходит под `ConnectionError` и `TimeoutError`, приходит как `DriverError`. Это баг вызывающего кода, поэтому повторять операцию не нужно.

### Когда не подходит

Если вам нужна ошибка сервера с кодом, смотрите [`ServerError`](./server-errors.mdx#servererror): она возникает, когда отказал сервер, а `DriverError` — когда отказал сам драйвер до отправки.

## IndexSyncError

`IndexSyncError` бросается, когда `syncIndexes` или `createIndexes` не смогли применить все индексы. Библиотека собирает **все** неудачи, а не останавливается на первой (Mongoose останавливался на первой неудаче): вы видите полный список проблем за один запуск. Индексы, которые получилось применить, остаются применёнными.

Чаще всего причина — данные, которые уже нарушают уникальность нового индекса. Здесь в коллекции два счёта с одним названием, а схема требует уникальное название:

```ts twoslash
import { Entity, IndexSyncError, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "accounts" })
class Account extends Entity {
  @Prop(() => String, { required: true, unique: true }) title!: string;
  @Prop(() => String, { required: true }) owner!: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Accounts = client.connection.model(Account);
// ---cut---
try {
  await Accounts.syncIndexes();
} catch (error) {
  if (error instanceof IndexSyncError) {
    console.log(error.model);
    // → "Account"
    console.log(error.failures.map((f) => [f.name, f.action, f.error.name]));
    // → [["title_1", "create", "DuplicateKeyError"]]
  }
}
```

Сообщение начинается с `Account: 1 index operation(s) failed: create title_1: duplicate key on title_1: { title: "Main" } (code 11000 DuplicateKey)` и перечисляет все неудачи через `;`. Модель названа один раз, в начале: если текст вложенной ошибки сам начинается с имени модели (`Account: index "title_1" exists on the server with other keys or options; …` у `init`), в общем сообщении это начало опущено, а в `failures[i].error.message` текст остаётся полным. Тексты вложенных ошибок короткие: полный текст сервера, с идентификаторами сборки индекса, лежит в `serverMessage` вложенной ошибки.

### Поля

<Params title="Поля ошибки">
<Param name="model" type="string">

Модель, индексы которой синхронизировались.

</Param>
<Param name="failures" type="readonly IndexFailure[]">

Каждая неудавшаяся операция с индексом. У элемента: `name` (имя индекса), `action` (`create`, `drop`, `modify`, а для поисковых индексов `createSearch`, `updateSearch`, `dropSearch`) и `error` (ошибка операции; в запуске это был `DuplicateKeyError`). Массив заморожен.

</Param>
</Params>

`IndexSyncError` бросают методы модели `syncIndexes` и `createIndexes`. [`connection.init`](../connection/connection.mdx#connectioninit) и `syncAll` не пробрасывают его как есть: они собирают неудачи всех моделей в [`SyncError`](#syncerror), где `IndexSyncError` лежит в `errors` сбоя своей коллекции.

### Когда не подходит

Если нужно только посмотреть, что разошлось, не применяя изменений, используйте `diffIndexes`: он сравнивает индексы и ничего не создаёт.

## SyncError

`SyncError` бросают [`connection.init`](../connection/connection.mdx#connectioninit) и `syncAll`, когда не удалось привести базу в соответствие с моделями: не создалась коллекция, не применился индекс, коллекция или представление уже существуют с другими опциями. Один сбой не останавливает остальные: прежде чем бросить ошибку, библиотека выполняет каждый шаг для каждой модели. Поэтому ошибка несёт полный итог: что не удалось по каждой коллекции и представлению, все исходные ошибки подряд и отчёт целиком. Запуск на старте приложения превращается в один `catch` со всем списком проблем, а не в цепочку «исправил одно, упало следующее».

Ошибка бросается и при `dryRun: true`, если сбой найден уже при проверке: пробный прогон не скрывает проблему, которую боевой запуск всё равно обнаружил бы. Пример: в базе `logs` уже есть обычная коллекция, а схема объявляет ограниченную (`capped`). Эту опцию MongoDB на месте не меняет.

```ts twoslash
import { Entity, Prop, Schema, SyncError, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
await client.unsafeDriver().db("app").createCollection("logs");
// ---cut---
@Schema({ collection: "logs", capped: { size: 100_000 } })
class Log extends Entity {
  @Prop(() => String, { required: true })
  text!: string;
}
client.connection.model(Log);

try {
  await client.connection.init();
} catch (error) {
  if (error instanceof SyncError) {
    console.log(error.message);
    // → connection.init() of "app": 1 failure(s) — collection "logs": exists with options MongoDB cannot change (capped): drop the collection and create it again
    console.log(error.operation, error.report.failed);
    // → "connection.init" true
    console.log(error.failures.map((failure) => [failure.kind, failure.name, failure.model, failure.errors.map((e) => e.name)]));
    // → [["collection", "logs", "Log", ["CollectionOptionsError"]]]
    console.log(error.cause instanceof AggregateError);
    // → true
  }
}
```

Сообщение начинается с метода и имени базы, затем идёт число сбоев и по каждой коллекции (`collection "…"`) или представлению (`view "…"`) их тексты. Имя коллекции в нём названо один раз: если вложенная ошибка сама начинается с него (`CollectionOptionsError`), повтор убран. Тексты ошибок индексов вложены целиком, поэтому сообщение может быть длинным: для сравнения по смыслу пользуйтесь полями.

### Поля

<Params title="Поля ошибки">
<Param name="operation" type='"connection.init" | "syncAll"'>

Метод, который не справился.

</Param>
<Param name="failures" type="readonly SyncFailure[]">

Сбои по коллекциям и представлениям (только те, где сбой был). Массив заморожен. У элемента `SyncFailure`: `kind` (`"collection"` для коллекции модели, `"view"` для представления), `name` (имя коллекции или представления), `model` (имя корневого класса коллекции, у представления `undefined`) и `errors` (все сбои этой коллекции по порядку шагов: [`IndexSyncError`](#indexsyncerror), [`CollectionOptionsError`](#collectionoptionserror), [`ServerError`](./server-errors.mdx#servererror) и другие).

</Param>
<Param name="errors" type="readonly TypemoError[]">

Все исходные ошибки подряд, в порядке отчёта. Тот же список лежит в `AggregateError` в поле `cause`. Массив заморожен.

</Param>
<Param name="report" type="SyncReport">

Отчёт вызова целиком, с `failed: true`: что нашли и что успели сделать, в том числе для пробного прогона.

</Param>
</Params>

<FullType>

```ts
class SyncError extends TypemoError {
  readonly operation: "connection.init" | "syncAll";
  readonly failures: readonly SyncFailure[];
  readonly errors: readonly TypemoError[];
  readonly report: SyncReport;
}

interface SyncFailure {
  readonly kind: "collection" | "view";
  readonly name: string;
  readonly model: string | undefined;
  readonly errors: readonly TypemoError[];
}
```

</FullType>

[`ErrorClassifier`](./hierarchy.mdx#errorclassifier) относит `SyncError` к роду `index-sync`, как и [`IndexSyncError`](#indexsyncerror). Ошибки уровня модели (`syncIndexes`, `createIndexes`) по-прежнему бросают `IndexSyncError` без оболочки. Руководство, где синхронизация показана на задаче запуска приложения: [Синхронизация индексов](../../collections/index-sync.mdx).

### Когда не подходит

Не глотайте `SyncError` при старте: приложение, которое продолжает работу с базой, не соответствующей схеме, получит ошибки позже и в неожиданных местах. Если нужно только посмотреть, что разошлось, не применяя изменений, используйте `syncAll({ dryRun: true })`: он ничего не меняет, но при найденном сбое тоже бросает `SyncError`, а отчёт лежит в `error.report`.

## CollectionOptionsError

`CollectionOptionsError` бросается, когда коллекция (или представление) уже существует, но с другими опциями, чем в схеме, или другого вида: представление там, где нужна обычная коллекция, обычная коллекция там, где объявлена временная серия. Mongoose в такой ситуации ничего не сообщал: `createCollection` молча пропускал существующую коллекцию, и изменённая опция никогда не доходила до базы. Typemo сообщает о расхождении.

В примере схема объявляет ограниченную коллекцию (`capped`), а в базе `logs` уже есть обычная:

```ts twoslash
import { CollectionOptionsError, Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
// ---cut---
@Schema({ collection: "logs", capped: { size: 100_000 } })
class Log extends Entity {
  @Prop(() => String, { required: true })
  text!: string;
}
const Logs = client.connection.model(Log);

try {
  await Logs.createCollection();
} catch (error) {
  if (error instanceof CollectionOptionsError) {
    console.log(error.message);
    // → collection "logs": exists with options MongoDB cannot change (capped): drop the collection and create it again
    console.log(error.collection, error.differences);
    // → "logs" [{ option: "capped", mutable: false, wanted: true }]
  }
}
```

<Params title="Поля ошибки">
<Param name="collection" type="string">

Имя коллекции или представления.

</Param>
<Param name="differences" type="readonly CollectionDifference[]">

Опции, которые различаются. У элемента: `option` (имя опции: `validator`, `capped`, `timeseries.granularity`, `pipeline`), `mutable` (`true`, если `collMod` умеет её менять, то есть подойдёт `ensureCollection({ update: true })`), `wanted` (что объявляет схема) и `actual` (что есть на сервере; `undefined`, если не задано). Массив заморожен.

</Param>
</Params>

Опция `capped` изменить на месте нельзя (`mutable: false`): коллекцию придётся пересоздать. Опции, которые `collMod` менять умеет, применяются через `ensureCollection({ update: true })`. Текст один для `createCollection`, `ensureCollection`, `connection.init` и `syncAll`: если среди различий есть то, что MongoDB изменить не умеет, это сказано первым (`exists with options MongoDB cannot change (capped): drop the collection and create it again`); если изменить можно всё, текст отсылает к `ensureCollection({ update: true })` (`exists with other options (validator); run ensureCollection({ update: true }) to change them with collMod`).

### Когда не подходит

Для существующей коллекции, опции которой вы хотите привести к схеме, используйте `ensureCollection`: он сравнивает и применяет то, что можно изменить. `createCollection` нужен только для создания и сообщает, если коллекция уже есть с другими опциями.

## AuditError

`AuditError` бросается, когда запись аудита не удалась, и **это проваливает саму операцию**: запись в модель с политикой `audit` без следа в аудите не остаётся. Запись и след пишутся в одной транзакции, поэтому при сбое откатываются вместе. Если запись вызвана вне транзакции, библиотека запускает для неё собственную транзакцию: для модели с аудитом нужен реплика-сет (или шардированный кластер), а на одиночном `mongod` такая запись бросает [`ConfigurationError`](#configurationerror).

Здесь коллекция аудита создана заранее с валидатором, который отвергает любую запись (он требует поле, которого в строках журнала нет):

```ts twoslash
import { AuditError, Entity, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Schema({ collection: "payments", audit: true })
class Payment extends Entity {
  @Prop(() => Number, { required: true })
  amount!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Payments = client.connection.model(Payment);
// ---cut---
await client.unsafeDriver().db("app").createCollection("payments_audit", {
  validator: { $jsonSchema: { bsonType: "object", required: ["nope"] } },
});

try {
  await Payments.create({ amount: 2 });
} catch (error) {
  if (error instanceof AuditError) {
    console.log(error.message);
    // → Payment.create: the audit entry could not be written; the transaction is aborted with this error, the write is rolled back
    console.log(error.model, error.operation, error.applied);
    // → "Payment" "create" false
    console.log((error.cause as { code?: number }).code);
    // → 121
  }
}
```

После ошибки счётчик платежей в коллекции не вырос: запись откатилась вместе с аудитом.

<Params title="Поля ошибки">
<Param name="model" type="string">

Модель с аудитом.

</Param>
<Param name="operation" type="string">

Метод, который вызвали вы и который аудировался: `create`, `updateMany`, `save`. Как и у [`PostHookError`](./hierarchy.mdx#posthookerror), это имя вашего вызова, а не внутренней операции.

</Param>
<Param name="applied" type="false">

Всегда `false`: запись откатывается вместе со строкой журнала, в базе её нет. У конструктора ошибки нет аргумента, который мог бы это изменить.

</Param>
<Param name="operationError" type="unknown">

Собственная ошибка операции, если она тоже не удалась и журнал писался уже после её сбоя. Если сама запись прошла успешно, поле `undefined` (так было в запуске примера выше).

</Param>
</Params>

Причина сбоя записи аудита лежит в `cause`. Подробнее об аудите — в руководстве [Аудит](../../policies/audit.mdx).

### Когда не подходит

Не ловите `AuditError`, чтобы «пропустить аудит и записать всё равно»: библиотека не даёт этого делать намеренно. Если след нужен не для всех записей, не включайте `audit` на модели целиком.

## InternalError

`InternalError` бросается, когда нарушен внутренний инвариант самой библиотеки: например, объект, который должен быть гидратированным документом, им не является, или запрос одной строки запросил курсор. Причиной не бывают ваши данные, поэтому такая ошибка — повод сообщить об ошибке в Typemo, а не исправлять свой код. Сообщение всегда начинается с `Internal error: `.

Класс входит в иерархию, поэтому `instanceof TypemoError` по-прежнему отделяет отказы библиотеки от чужих. Воспроизвести ошибку намеренно нельзя: это не сценарий использования, а сбой, и в запуске она не получалась.

<Params title="Поля ошибки">
<Param name="message" type="string">

Какой инвариант нарушен. Собственных полей у класса нет; первопричина, если она есть, лежит в `cause`.

</Param>
</Params>

### Когда не подходит

Не обрабатывайте эту ошибку особым образом в приложении. Пусть она попадёт в общий обработчик неожиданных ошибок как 500, а текст и трассировку отправьте разработчикам библиотеки.
