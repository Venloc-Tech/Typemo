Каждая ошибка Typemo — экземпляр [`TypemoError`](#typemo-error). Один `instanceof` отделяет отказы библиотеки и базы от чужих ошибок в вашем коде, будь то `TypeError` в вашей функции или сбой сети в соседней библиотеке. Классы-потомки добавляют структурированные поля, и по ним можно принять решение, не разбирая текст сообщения.

Если вы только начинаете, сначала прочитайте руководство [Обработка ошибок](../../errors/handling.mdx). Эта страница описывает общий корень, а каждый конкретный класс — страница его группы. Здесь же два элемента, которые не входят ни в одну группу. Это [`PostHookError`](#post-hook-error) (запись прошла, а хук после неё упал) и [`ErrorClassifier`](#error-classifier) (разбор любой ошибки для повторов, журналов и метрик).

## Дерево классов [#class-tree]

Классы разложены по группам по тому, где вы встретите ошибку, а не по файлам исходного кода. Ошибки данных приходят, когда значение не подходит схеме. Ошибки запросов — когда запрос нельзя построить или он ничего не нашёл. Ошибки сервера — когда отказала сама база. Ошибки конфигурации и подключения — когда неверна настройка или нет связи.

```tree
TypemoError
  ValidationError            # the data failed the schema
  CastError                  # a value can't be cast to the field type
  StrictModeError            # an operation broke a strictness rule
  UnknownFieldsError         # a save would erase unknown fields
  DirectWriteError           # a collection was changed around its methods
  PartialArrayError          # the array is loaded partially
  QueryError                 # the query can't be built
    KeysetTokenError         # the page token was rejected
  DocumentNotFoundError      # orFail found nothing
  VersionError               # the document changed after it was read
  EachAsyncError             # callback failures in eachAsync
  ServerError                # the database refused
    DuplicateKeyError        # a unique index was violated
    ServerValidationError    # the collection validator refused
    WriteConflictError       # two writes touched one document
  BulkWriteError             # part of a bulk write failed
  TimeoutError               # time ran out
  ConnectionError            # no connection to the server
  DriverError                # the driver refused on its own side
  ConfigurationError         # a wrong setting
  IndexSyncError             # indexes weren't applied
  SyncError                  # init() or syncAll() didn't bring the database to the schema
  CollectionOptionsError     # collection options differ from the schema
  AuditError                 # the audit write failed
  PostHookError              # a post hook failed after a successful write
  InternalError              # an internal invariant was broken
```

Страницы групп — [ошибки данных](./data-errors.mdx), [ошибки запросов](./query-errors.mdx), [ошибки сервера](./server-errors.mdx), [ошибки конфигурации и подключения](./configuration-errors.mdx). Там же [`SyncError`](./configuration-errors.mdx#sync-error).

В дереве есть два неочевидных места. `KeysetTokenError` — потомок `QueryError`, так что `catch` по `QueryError` поймает и его. `DuplicateKeyError`, `ServerValidationError` и `WriteConflictError` — потомки `ServerError`, и проверка по `ServerError` ловит все три вместе с остальными отказами сервера. Поэтому в обработчике идите от частного к общему. Сначала `DuplicateKeyError`, потом `ServerError`.

## TypemoError [#typemo-error]

`TypemoError` — корень иерархии. Сам он почти не встречается, Typemo бросает его потомков. Он нужен как общий знаменатель в `catch` и как база для ваших ошибок, если они должны проходить те же проверки.

<Snippet id="reference/errors/hierarchy/typemo-error" twoslash />

### Поля [#typemo-error.fields]

**`message`** — текст для человека. Он читается без других полей, в нём есть имя модели, операции, путь и причина. Решения по тексту не принимайте, он может уточняться между версиями. Для решений есть структурированные поля конкретных классов (`reason`, `code`, `path`).

**`cause`** — оригинальная ошибка, из-за которой возникла эта. Например, ошибка драйвера, ошибка вашей функции в хуке или ошибка приведения внутри валидации. Поле стандартное для `Error`, Typemo его только заполняет. Ошибка драйвера лежит в нём без изменений, так что любые её поля доступны.

Если в оригинале были значения полей с пометкой `sensitive`, в `cause` лежит копия, где они заменены на `[hidden]`. Секрет не попадёт в журнал вместе с ошибкой. У `DuplicateKeyError` по полю с `sensitive: "hide"` и сообщение, и `keyValue`, и текст `cause` содержат `[hidden]`.

**`name`** — имя класса, например `"ConfigurationError"` или `"CastError"`. Оно лежит на прототипе, а не на экземпляре, поэтому не попадает в `Object.keys(error)` и не дублируется в каждой строке структурного журнала. Тип проверяйте через `instanceof`, а не сравнением `name`, потому что `instanceof` учитывает наследование.

Классы ошибок Typemo вы не создаёте, библиотека сама выбирает нужный по ситуации. Конструктор пригодится в тестах, когда обработчику нужно подать готовую ошибку.

### Когда не подходит [#typemo-error.when-not-to-use]

Чтобы разобрать причину отказа, `instanceof TypemoError` слишком грубая проверка. Ловите конкретный класс, например [`DuplicateKeyError`](./server-errors.mdx#duplicate-key-error) или [`CastError`](./data-errors.mdx#cast-error). Общий `TypemoError` годится для последнего звена обработчика — «это отказ библиотеки, а не мой баг».

## PostHookError [#post-hook-error]

`PostHookError` бросается, когда [post-хук](../hooks/pre-post.mdx) упал **после** успешной записи. Запись в базе уже есть, а вызывающий код получил ошибку. Если принять её за обычный отказ и повторить вызов, документ запишется второй раз. Поэтому Typemo оборачивает ошибку хука в класс с полем `applied`. Оно всегда `true` и значит «запись применена, не повторяйте».

Ошибка нужна в сервисах, где после записи что-то делают хуки — отправляют письмо, пишут в журнал, обновляют кеш. Сбой такого хука не должен выглядеть как провал самой записи. В примере хук документа падает после `create`.

<Snippet id="reference/errors/hierarchy/post-hook-error" twoslash />

`operation` называет метод, который вызвали вы (`create`), а не внутреннюю операцию, в которую он превращается. Документ из примера записан в коллекцию. `error.result` хранит то, что вернула запись. Для `create` это сохранённый документ, для `updateOne` результат обновления, для `insertMany` массив документов, для `$deleteOne` результат удаления. Поле `result` неперечисляемое. Оно не попадает в `Object.keys(error)` и не уходит в журнал вместе с ошибкой, потому что документы могут содержать секреты.

### Внутри транзакции [#in-transaction]

В транзакции всё иначе. Сбой post-хука прерывает транзакцию, запись откатывается, а вызывающий код получает ошибку хука **как она была брошена**, без оболочки. `PostHookError` нужен только там, где откатывать нечего, то есть вне транзакции. Хук `document.save`, брошенный внутри `transaction`, дал ту же ошибку снаружи, а коллекция осталась пустой.

### Хук чтения и хук ошибки [#read-and-error-hooks]

Post-хук **чтения** (`query.find`) ничего не записывал, поэтому его ошибка приходит как есть. Если сам хук `@PostError` бросает ошибку, исходная ошибка операции не теряется. Она лежит в `cause` ошибки хука.

### Когда не подходит [#post-hook-error.when-not-to-use]

Не повторяйте вызов при `PostHookError`, запись уже есть. Если хук должен откатываться вместе с записью, выполняйте запись внутри [транзакции](../../transactions/transactions.mdx). Тогда ошибка хука отменит и запись. Порядок хуков и их ошибок описан в руководстве [Порядок и ошибки хуков](../../hooks/order-and-errors.mdx).

## ErrorClassifier [#error-classifier]

`ErrorClassifier` отвечает на вопросы, которые задают журналы, метрики и повторы. Какого рода ошибка, есть ли у неё код сервера, поможет ли повтор. Он принимает **любое** брошенное значение. Это может быть ошибка Typemo, необработанная ошибка драйвера `mongodb` (он классифицирует её как тот класс Typemo, в который её превратила бы библиотека) или что угодно ещё. Поэтому классификатор годится и там, где ошибка пришла не через модель, а из [`client.unsafeDriver()`](../connection/typemo-client.mdx#client.unsafe-driver).

<Snippet id="reference/errors/hierarchy/error-classifier" twoslash />

На нарушении уникальности он вернул `{ kind: "duplicate-key", name: "DuplicateKeyError", code: 11000, errorLabels: [], retryable: false, transient: false }`. Тот же результат получился для необработанной ошибки драйвера из `insertOne`, выполненного мимо Typemo. Для конфликта записей с меткой `TransientTransactionError` результат такой — `{ kind: "write-conflict", name: "WriteConflictError", code: 112, errorLabels: ["TransientTransactionError"], retryable: true, transient: true }`.

### classify [#classify]

`classify` возвращает `ErrorClassification`. В нём `kind` (род, таблица ниже), `name` (имя класса ошибки, а для не-ошибки — `typeof` значения), `code` (код сервера, если он есть), `errorLabels`, `retryable` и `transient`.

`retryable` равен `true` в трёх случаях. У ошибки есть метка `TransientTransactionError` или `RetryableWriteError`. Это `ConnectionError`, причём не вида `closed` и не `authentication`. Или код сервера относится к временным состояниям — остановка узла, смена первичного, сетевой таймаут, конфликт записей и подобные. Нарушение уникальности, ошибка приведения и отказ валидатора коллекции дают `false`, потому что повтор с теми же данными даст тот же результат.

У `PostHookError`, `AuditError` и `EachAsyncError` свои роды, их не спутать с чужой ошибкой. `PostHookError` (post-хук `document.save` бросил после `create`) дал `{ kind: "post-hook", name: "PostHookError", errorLabels: [], retryable: false, transient: false }`. Род `post-hook` важнее остальных. Запись уже есть, `retryable` равен `false`, и повтор создал бы дубликат. Если ваш общий обработчик повторяет вызовы, проверяйте род до повтора.

### Сценарии [#scenarios]

Первый сценарий — решение «создан, занят или попробуйте позже» в одном месте.

<Snippet id="reference/errors/hierarchy/scenarios" twoslash />

Второй сценарий — пакетная запись. `isDuplicateKey` для `BulkWriteError` вернёт `false`, потому что пакетная ошибка — другой класс. Был ли среди отказов дубликат, спросите у `hasDuplicateKey`. `insertMany` с одним повтором и `ordered: false` дал `isDuplicateKey: false`, `hasDuplicateKey: true` и род `bulk-write`.

### Когда не подходит [#error-classifier.when-not-to-use]

Классификатор не заменяет `instanceof`, когда нужны поля конкретного класса — `keyValue`, `failures`, `errors`. Сначала сузьте тип проверкой класса, потом читайте поля. Что ответить клиенту, классификатор тоже не решает. Соответствие родов кодам HTTP определяет ваше приложение, пример есть в руководстве [Обработка ошибок](../../errors/handling.mdx#http-status).
