Ошибки сервера приходят, когда отказала сама база. Нарушен уникальный индекс, валидатор коллекции отверг документ, две записи задели один документ, закончилось время, часть пакетной записи не прошла. Typemo превращает ошибку драйвера в свой класс по коду сервера, чтобы вы решали по классу и полям, а не по тексту. Оригинал при этом остаётся в `cause` без изменений.

Если вы только начинаете, сначала прочитайте руководство [Обработка ошибок](../../errors/handling.mdx). Дерево классов описано в разделе [Иерархия ошибок](./hierarchy.mdx).

Примеры используют модель счёта с уникальным названием. На ней проявляются и нарушение уникальности, и пакетная запись.

<Snippet id="errors/handling/prerequisites" title="accounts/account.ts" twoslash />

Ошибки из соседних групп описаны на других страницах — [ошибки данных](./data-errors.mdx), [ошибки запросов](./query-errors.mdx), [ошибки конфигурации и подключения](./configuration-errors.mdx).

## ServerError [#server-error]

`ServerError` — общий класс отказа сервера. Typemo бросает его, когда для кода ошибки нет более точного класса. Три других класса на этой странице, [`DuplicateKeyError`](#duplicate-key-error), [`ServerValidationError`](#server-validation-error) и [`WriteConflictError`](#write-conflict-error), его потомки, поэтому проверка по `ServerError` ловит все четыре.

Из ошибки драйвера класс копирует код, имя кода и метки. Сама ошибка драйвера остаётся в `cause` целиком. Копировать пришлось, потому что Mongoose разворачивал ошибку драйвера в свой объект и терял код.

Сообщение у общего `ServerError` короткое. В нём причина, которую назвал сервер, и код в скобках. Полный текст сервера часто содержит план запроса и значения из него, и в журнал или в ответ клиенту такое попадать не должно. Поэтому полный текст лежит отдельно, в поле `serverMessage` и в `cause`, а в `message` остаётся только то, что нужно для понимания.

В примере подсказка индекса (`hint`) называет индекс, которого нет. Сервер отвечает ошибкой с кодом 2.

<Snippet id="reference/errors/server-errors/server-error" twoslash />

### Поля [#server-error.fields]

<Params title="Поля ошибки">
<Param name="code" type="number | undefined">

Код ошибки сервера, если драйвер его сообщил. Названия известных кодов собраны в [`ServerErrorCodes`](#server-error-codes).

</Param>
<Param name="codeName" type="string | undefined">

Имя кода (`BadValue`, `WriteConflict`, `DuplicateKey`). Сервер присылает его не во всех ответах, например не в ошибках записи. Недостающее имя Typemo берёт из таблицы [`ServerErrorCodes`](#server-error-codes). Так у нарушения уникальности появился `DuplicateKey`, у отказа валидатора `DocumentValidationFailure`, и так же у пакетных ошибок. Если кода нет в таблице и сервер прислал его без имени, поле равно `undefined`. Для решений надёжнее `code`.

</Param>
<Param name="errorLabels" type="readonly string[]">

Метки ошибки (`TransientTransactionError`, `RetryableWriteError`). Массив заморожен. Смысл меток описан в разделе [`ErrorLabels`](#error-labels).

</Param>
<Param name="serverMessage" type="string">

Полный текст, который прислал сервер, без сокращений. В нём может быть план запроса и значения документов, так что клиенту его не отдавайте. У классов-потомков (`DuplicateKeyError`, `ServerValidationError`, `WriteConflictError`) это текст сервера без приставки, которую Typemo добавляет к `message`.

</Param>
</Params>

## DuplicateKeyError [#duplicate-key-error]

`DuplicateKeyError` бросается, когда запись нарушила уникальный индекс (код сервера 11000). Это самая частая ошибка сервера в веб-приложении. Два пользователя регистрируются с одной почтой, два запроса создают один и тот же счёт. Уникальность гарантирует индекс, а не проверка «есть ли уже такое» перед записью. Проверка и запись не атомарны, между ними успеет вклиниться другой запрос. Поэтому пытайтесь записать и ловите эту ошибку.

<Snippet id="reference/errors/server-errors/duplicate-key-error" twoslash />

Уникальный индекс существует только после [`connection.init`](../connection/connection.mdx#connection.init). Без него дубликат запишется без ошибки. Сообщение короткое — индекс, значение ключа и код, `duplicate key on title_1: { title: "Main" } (code 11000 DuplicateKey)`. Служебные подробности сервера в него не попадают. Это имена базы и коллекции, идентификаторы сборки индекса и цепочка `:: caused by ::`. Они лежат в `serverMessage`.

### Поля [#duplicate-key-error.fields]

<Params title="Дополнительные поля">
<Param name="keyPattern" type="Record<string, unknown> | undefined">

Ключи нарушенного индекса (`{ title: 1 }`), если сервер их сообщил. По ним видно, какое поле вызвало конфликт, и текст разбирать не нужно.

</Param>
<Param name="keyValue" type="Record<string, unknown> | undefined">

Повторившиеся значения (`{ title: "Main" }`). Если поле помечено `sensitive`, значение заменено на `[hidden]` (или `?`, смотря какой режим выбран). Замена видна в этом поле, в тексте сообщения, в `serverMessage` и в `cause`. В пакетной записи сервер значения не сообщает, поэтому `keyValue` там `undefined`, а в сообщении значения нет.

</Param>
<Param name="index" type="string | undefined">

Имя индекса, отказавшего в записи. Typemo берёт его из текста сервера (`index: title_1`). Если разобрать не удалось, поле равно `undefined`, а в сообщении нет слов «on …».

</Param>
</Params>

Остальные поля — `code`, `codeName`, `errorLabels` и `serverMessage` — те же, что у [`ServerError`](#server-error). У нарушения уникальности `codeName` равен `DuplicateKey`. Клиенту стоит ответить конфликтом с существующими данными, то есть 409 вашего приложения. Какое поле повторилось, видно в `keyPattern`.

### В пакетной записи [#in-bulk-write]

При `insertMany` и `bulkWrite` дубликат приходит не отдельной ошибкой, а элементом [`BulkWriteError`](#bulk-write-error). В `writeErrors[i].error` лежит `DuplicateKeyError` с теми же полями.

### Когда не подходит [#duplicate-key-error.when-not-to-use]

Если нужно «создать или обновить», эту ошибку не ловите, используйте `upsert` в [`updateOne`](../writes/writes.mdx#update-one). Если хотите заранее проверить, свободно ли имя, помните, что проверка не заменяет индекс. Она только улучшает сообщение пользователю.

## ServerValidationError [#server-validation-error]

`ServerValidationError` бросается, когда валидатор коллекции (`$jsonSchema`) на стороне сервера отверг документ (код 121). Валидатор коллекции — это правила, которые хранит сама база. Они действуют для всех, кто пишет в коллекцию, и для записей в обход Typemo тоже. Ошибка приходит, когда документ прошёл схему в вашем коде, но не прошёл правила базы. Например, схема допускает 500, а валидатор коллекции требует не больше 100.

В примере валидатор коллекции `posts` ограничивает `score` сотней.

<Snippet id="reference/errors/server-errors/server-validation-error" twoslash />

### Поля [#server-validation-error.fields]

<Params title="Дополнительные поля">
<Param name="errInfo" type="Record<string, unknown> | undefined">

Объяснение сервера, какое правило не выполнено и на каком поле (`errInfo.details`). В нём были `operatorName: "$jsonSchema"`, список нарушенных правил, имя поля (`propertyName`), правило (`maximum`), рассмотренное значение (`consideredValue`) и идентификатор отвергнутого документа (`failingDocumentId`).

</Param>
</Params>

Если у поля в схеме есть `sensitive`, значения в `errInfo` маскируются так же, как в других ошибках. Остальные поля такие же, как у [`ServerError`](#server-error). `codeName` здесь `DocumentValidationFailure`, а `serverMessage` — `Document failed validation`.

### Когда не подходит [#server-validation-error.when-not-to-use]

Валидатор коллекции нужен как последний рубеж для записей мимо Typemo. Ввод клиента проверяйте схемой модели. Её [`ValidationError`](./data-errors.mdx#validation-error) перечисляет все проблемы сразу, а ошибка сервера называет их по одной.

## WriteConflictError [#write-conflict-error]

`WriteConflictError` бросается, когда две записи задели один документ и сервер отказал одной из них (код 112). Записи могут быть двумя транзакциями или транзакцией и одиночной записью. Это не поломка, а обычный способ сервера сохранить порядок. Проигравшую запись можно выполнить заново.

Внутри [`connection.transaction`](../transactions/transactions.mdx#transaction) вы почти не встретите эту ошибку. Сервер помечает такой отказ меткой `TransientTransactionError`, и драйвер повторяет функцию транзакции целиком. До вас ошибка доходит, только если запись вне транзакции или повторы закончились. Число попыток и судьбу данных внутри транзакции описывает руководство [Транзакции](../../transactions/transactions.mdx).

Вне транзакции одиночные записи конфликтуют редко, сервер сам повторяет их внутри. Ошибку удалось получить только искусственно, включив на сервере отказ команды `update` с кодом 112. Класс и поля были такими.

<Snippet id="reference/errors/server-errors/write-conflict-error" />

Сообщение всегда начинается с `write conflict: `, дальше идёт текст сервера. Собственных полей у класса нет. `code`, `codeName` и `errorLabels` те же, что у [`ServerError`](#server-error), а `serverMessage` — текст сервера без приставки `write conflict: `.

### Когда не подходит [#write-conflict-error.when-not-to-use]

Внутри транзакции не повторяйте запись вручную, повтор уже делает драйвер. Вне транзакции одиночную запись безопасно повторять, только если она идемпотентна, как установка значения. Накапливающую запись вроде `$inc` повторять нельзя.

## TimeoutError [#timeout-error]

`TimeoutError` бросается, когда закончилось время. Поле `kind` говорит, где именно. `operation` — сработал `timeoutMS` операции или сервер сообщил `MaxTimeMSExpired`. `connection` — клиент не успел подключиться за `readyTimeoutMS`. `transaction` — истёк `timeoutMS` транзакции с учётом повторов. Во всех трёх случаях `timeoutMS` заполнен превышенным пределом.

Сначала срок операции. На сервере искусственно задержан ответ `find`, а операции отпущено 100 мс.

<Snippet id="reference/errors/server-errors/timeout-error" twoslash />

Теперь клиент, который не подключился. У клиента, созданного через `new TypemoClient` без `connect`, операции ждут подключения не дольше `readyTimeoutMS`. После этого приходит ошибка вида `connection` с заполненным `timeoutMS`.

<Snippet id="reference/errors/server-errors/timeout-error-2" />

И срок транзакции. Транзакция с `timeoutMS: 200`, внутри которой ответ `find` задержан на 400 мс, закончилась ошибкой другого вида.

<Snippet id="reference/errors/server-errors/timeout-error-3" />

Оригинал (`MongoOperationTimeoutError` драйвера) лежит в `cause`. Если ошибку с кодом 50 (`MaxTimeMSExpired`) прислал сам сервер, вид будет `operation`, а текст начнётся с `the server stopped the operation (MaxTimeMSExpired):`. Это проверено искусственным отказом сервера.

### Поля [#timeout-error.fields]

<Params title="Поля ошибки">
<Param name="kind" type="TimeoutKind">

Где закончилось время — `operation`, `connection` или `transaction`.

</Param>
<Param name="timeoutMS" type="number | undefined">

Превышенный предел в миллисекундах. У всех трёх видов он был заполнен — 100 у `operation`, 100 у `connection`, 200 у `transaction`. `undefined` оказался у ошибки, которую сервер сообщил сам (код 50), когда у вызова не было своего `timeoutMS`.

</Param>
</Params>

Оригинал, если он есть, лежит в `cause`. Для срока операции это ошибка драйвера `MongoOperationTimeoutError`. Время вышло у вас, а не у пользователя, поэтому клиенту стоит ответить 503 или 504 вашего приложения, а не 500.

### Когда не подходит [#timeout-error.when-not-to-use]

Не увеличивайте `timeoutMS` в ответ на эту ошибку, пока не поняли причину. Чаще операция медленная из-за отсутствия индекса. Как это выяснить, описано в руководстве [Производительность запросов](../../queries/performance.mdx).

## BulkWriteError [#bulk-write-error]

`BulkWriteError` бросается, когда часть пакетной записи (`insertMany`, `bulkWrite`) не прошла. Пакет не атомарен. Одни записи прошли, другие могли отказать, и разобраться поможет только полный отчёт. Ошибка его даёт. В ней список каждой неудавшейся записи с номером **в вашем вводе** (а не внутри пакета драйвера) и итог того, что записалось.

Порядок влияет на результат. В пакете из четырёх документов второй и четвёртый нарушают уникальность. Упорядоченная запись остановилась на втором, а неупорядоченная (`ordered: false`) записала первый и третий.

<Snippet id="reference/errors/server-errors/bulk-write-error" twoslash />

Без `ordered: false` тот же вызов останавливается на первой ошибке. `writeErrors` содержит только индекс 1, `result.insertedCount` равен 1, а `ordered` равен `true`.

### Поля [#bulk-write-error.fields]

<Params title="Поля ошибки">
<Param name="writeErrors" type="readonly BulkWriteFailure[]">

Каждая неудачная запись, отсортированная по индексу во вводе. У элемента есть `index` (номер во вводе), `code` (код сервера, например 11000 или 121, а для записи, отвергнутой до сервера из-за приведения или проверки схемы, `undefined`), `message` (текст сервера для отказа сервера, у остальных тот же, что у `error`) и `error` (разобранная ошибка — `DuplicateKeyError`, `ServerValidationError`, `CastError` или `ValidationError`).

</Param>
<Param name="result" type="BulkWriteSummary">

Что изменили успешные записи. Это `insertedCount`, `matchedCount`, `modifiedCount`, `deletedCount`, `upsertedCount`, а также `insertedIds` и `upsertedIds` по номеру во вводе. В `insertedIds` попадают только записанные вставки. В примере выше это номера 0 и 2, а номеров неудавшихся вставок (1 и 3) там нет.

</Param>
<Param name="ordered" type="boolean">

Была ли запись упорядоченной. При `true` записи после первой неудачной не выполнялись.

</Param>
</Params>

Текст самой ошибки называет неудачу с наименьшим индексом во вводе, а не ту, которую нашли первой. Если проверку Typemo не прошёл документ 2, а сервер отказал документу 1, в тексте будет «first at index 1». Чтобы найти среди неудач повторы, проверьте класс элемента — `failure.error instanceof DuplicateKeyError`.

Ошибка приведения в упорядоченном `insertMany` бросается сразу как [`CastError`](./data-errors.mdx#cast-error), до отправки пакета, и в `BulkWriteError` не собирается. Ошибка проверки схемы в неупорядоченной записи в пакет попадает (в примере это индекс 1).

### Когда не подходит [#bulk-write-error.when-not-to-use]

Если записи должны пройти вместе или не пройти вовсе, пакетная запись не подходит, она частична по природе. Берите [транзакцию](../transactions/transactions.mdx#transaction).

## ServerErrorCodes [#server-error-codes]

`ServerErrorCodes` — замороженный объект с названиями кодов ошибок сервера, на которые реагирует Typemo. Драйвер почти для всех этих кодов не экспортирует констант, даже для 11000, поэтому они собраны здесь. `error.code === ServerErrorCodes.DuplicateKey` читается лучше, чем `error.code === 11000`.

<Snippet id="reference/errors/server-errors/server-error-codes" twoslash />

Тип `ServerErrorCode` — объединение всех значений этой таблицы. Классы по кодам такие. 11000 и 11001 дают `DuplicateKeyError`, 121 — `ServerValidationError`, 112 — `WriteConflictError`, 50 — `TimeoutError`, 18 — `ConnectionError` с видом `authentication`. Остальные коды дают общий `ServerError`.

### Поиск без Atlas [#search-without-atlas]

Стадия `vectorSearch` на обычном сервере MongoDB завершается `ServerError` с кодом `SearchNotEnabled`. Приложение, которое в разработке работает без Atlas, ловит именно этот код и отвечает запасным поиском по словам. Остальные ошибки оно пробрасывает, чтобы сбой сети не выглядел как «поиска нет».

<Snippet id="reference/errors/server-errors/search-without-atlas" title="articles/search.service.ts" twoslash />

Сообщение такой ошибки на тестовом сервере — `Using $search and $vectorSearch aggregation stages requires additional configuration. (code 31082 SearchNotEnabled)`. Целиком пример разобран в рецепте [Поиск по тексту и смыслу](../../recipes/search.mdx#fallback-to-text).

## ErrorLabels [#error-labels]

`ErrorLabels` — замороженный объект с именами меток, которые сервер и драйвер прикрепляют к ошибкам. Метка не говорит, что случилось, а подсказывает, что можно сделать. Повторить запись, повторить транзакцию или выяснить исход фиксации. Читать метки можно у [`ServerError`](#server-error), [`ConnectionError`](./configuration-errors.mdx#connection-error) и [`DriverError`](./configuration-errors.mdx#driver-error) через `errorLabels` и `hasErrorLabel`.

    UnknownTransactionCommitResult: { description: "Исход фиксации неизвестен — она могла пройти или нет. Повторять фиксацию можно, повторять всю транзакцию без проверки нельзя.", type: '"UnknownTransactionCommitResult"' },
    ResumableChangeStreamError: { description: "Поток изменений можно возобновить с последней позиции.", type: '"ResumableChangeStreamError"' },

Метку `TransientTransactionError` видно на отказе, после которого функция транзакции выполнилась повторно. При двух искусственных отказах `update` функция получила `scope.attempt` равный 1, 2 и 3, и транзакция зафиксировалась.

Описания меток, кроме `TransientTransactionError`, взяты из документации драйвера и на сервере не воспроизводились.
