`@venloc/typemo-sentry` передаёт в Sentry то, чего нет в трассировке. Это **ошибки** операций с понятным контекстом и **breadcrumbs**, то есть хлебные крошки Sentry, короткие записи о том, что происходило перед ошибкой. Пакет отдельный. Ядро `@venloc/typemo` про Sentry ничего не знает, а адаптер подписывается на [события операций](./events.mdx) и вызывает `addBreadcrumb` и `captureException` из `@sentry/core`. Поэтому он одинаково работает с `@sentry/node` и `@sentry/bun`, какой SDK вы инициализировали, ему безразлично.

Трассировку пакет не делает. Спаны в Sentry приходят из OpenTelemetry, и за них отвечает [`@venloc/typemo-opentelemetry`](./opentelemetry.mdx). Как подключить адаптер и что вы увидите в Sentry, рассказывает руководство [Sentry](../../observability/sentry.mdx). Эта страница — справочник.

Пакету нужен `@sentry/core` версии не ниже 11.1.0 как peer-зависимость. SDK, DSN и остальные настройки выбирает приложение.

```package-install
@venloc/typemo-sentry @sentry/node
```

В примерах модель счёта.

```ts title="accounts/account.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => Number, { required: true })
  balance!: number;
}
```

Сборка документации блоки кода этой страницы не компилирует, потому что не подключает сторонние пакеты. Результаты мы получили, запустив адаптер на настоящей базе с тестовым клиентом Sentry из `@sentry/core`. Он записывает события и breadcrumbs, а не отправляет их.

## TypemoSentry.instrument

`TypemoSentry.instrument` подписывает адаптер на операции клиента или всех клиентов процесса. С этого момента каждая завершённая операция оставляет breadcrumb, а упавшая ещё и отправляет ошибку в Sentry с контекстом. По событию в Sentry сразу видно, какая модель, коллекция и операция упали, на каком шаге и можно ли повторить.

```ts title="monitoring.ts"
import * as Sentry from "@sentry/node";
import { TypemoClient } from "@venloc/typemo";
import { TypemoSentry } from "@venloc/typemo-sentry";

Sentry.init({ dsn: "https://public@example.test/1" });

const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "bank" });
const subscription = TypemoSentry.instrument(client);
// операции клиента попадают в Sentry

subscription.unsubscribe();
```

Сама регистрация ничего не отправляет, она только подписывает адаптер. На пути операции адаптер исключений не бросает. Если обработка события сбилась, он пишет `console.error("[typemo-sentry] an instrumentation subscriber failed:", error)`, а операция идёт дальше. Две подписки на одну ошибку дают в Sentry одно событие. То же верно, если приложение отправит эту ошибку само после адаптера, ведь `@sentry/core` помечает уже отправленные исключения, и адаптер на это опирается.

<Params>
<Param name="target" type="InstrumentationTarget" required>

Клиент (`TypemoClient`) или класс `Typemo`. Подойдёт любой объект с методом `instrument(subscriber)`, который возвращает подписку. `Typemo` даёт все клиенты процесса.

</Param>
<Param name="options" type="SentryInstrumentationOptions" default="{}">

Настройки в [`SentryInstrumentationOptions`](#sentryinstrumentationoptions).

</Param>
</Params>

<Returns type="Subscription">

Подписка ядра с методом `unsubscribe()`. После него адаптер ничего нового не отправляет.

</Returns>

<FullType>

```ts
class TypemoSentry {
  static instrument(target: InstrumentationTarget, options?: SentryInstrumentationOptions): Subscription;
}

interface InstrumentationTarget {
  readonly instrument: (subscriber: InstrumentationSubscriber) => Subscription;
}
```

</FullType>

## SentryInstrumentationOptions

Все поля необязательны. Без настроек адаптер и оставляет breadcrumbs, и отправляет все ошибки, а значения в них маскирует.

### captureErrors

`boolean`, по умолчанию `true`. Отправляет в Sentry через `captureException` **каждую** ошибку операции, без фильтра по виду. Фильтра нет намеренно. Решать, какие ошибки шумят, удобнее в Sentry (`beforeSend`, правила группировки), где видна вся картина, а адаптер не должен молча пропускать чужие ошибки. При `false` остаются только breadcrumbs.

### breadcrumbs

`boolean`, по умолчанию `true`. Добавляет breadcrumb на завершение каждой операции, на повтор и на откат транзакции. С `captureErrors: false` и `breadcrumbs: false` не осталось ни breadcrumb, ни события, даже когда вышла `DuplicateKeyError`.

### sensitive

`SubscriberSensitive`, по умолчанию `"mask"`. Работает как у [подписчика ядра](./events.mdx#subscribersensitive). Настоящие значения непомеченных полей покидают процесс только при `"show"` или через вашу `{ mask }`. Это касается сводки в breadcrumb и значений в ошибках `CastError`, `ValidationError`, `DuplicateKeyError` и `ServerValidationError`. Пометки `sensitive` в схеме и скрытые поля действуют всегда. Сообщение об ошибке в Sentry выглядит так — `duplicate key on title_1: { title: "?" } (code 11000 DuplicateKey)`, а вызвавший код получил ошибку с настоящим значением.

### includeTenant

`boolean`, по умолчанию `false`. Кладёт тенанта операции в **отправленную ошибку** — тег `typemo.tenant` и поле `tenant` в `contexts.typemo`, значение приводится к строке. По умолчанию тенанта нет, потому что это данные ваших клиентов, а Sentry — внешний сервис. Опцию получает ядро (оно включает `OperationInfo.tenant`), и [`ErrorContextBuilder`](#errorcontextbuilder) проверяет её ещё раз. Breadcrumbs тенанта не несут никогда. У операции вне тенантной политики нет ни тега, ни поля. `Note.find().policy({ tenant: "t-1" })` с ошибкой приведения дал тег `typemo.tenant: "t-1"` и `tenant: "t-1"` в контексте.

<FullType>

```ts
interface SentryInstrumentationOptions {
  readonly captureErrors?: boolean;
  readonly breadcrumbs?: boolean;
  readonly sensitive?: SubscriberSensitive;
  readonly includeTenant?: boolean;
}
```

</FullType>

## Что отправляется

### Breadcrumbs

Breadcrumb создаётся, когда операция закончилась, а не когда началась. Адаптер запоминает сводку запроса из события `operation.start` и кладёт её в запись, когда приходит `operation.end` или `operation.error`. Сообщение имеет вид `Typemo.<операция> (<Модель>)`, как имя спана в OpenTelemetry. Категория всегда `typemo`.

У успешной операции тип `query`, уровень `info`. У операции уровня базы ([`connection.aggregate`](../connection/connection.mdx#connectionaggregate)) нет модели и коллекции. Сообщение будет `Typemo.aggregate (database bank)`, а в `data` не окажется `model` и `collection`. Вот что дал `find`.

```ts
{
  type: "query",
  category: "typemo",
  level: "info",
  message: "Typemo.find (Account)",
  data: {
    model: "Account",
    collection: "accounts",
    database: "bank",
    durationMS: 3.14,
    documentCount: 1,
    summary: { filter: { balance: { $gt: "?" } } },
  },
}
```

У упавшей операции тип `error`, уровень `error`. В `data` добавляются `failedStep` (`"cast"`, `"execute"`) и `errorKind` (`"duplicate-key"`, `"cast"`), а `documentCount` пропадает.

Повтор и откат транзакции тоже оставляют breadcrumb типа `transaction`. Сообщение — `Typemo.transaction retry` (уровень `warning`) или `Typemo.transaction abort` (уровень `error`). В `data` лежат `transactionId`, `attempt`, `connection`, `durationMS` и `errorClass`. В `errorClass` только имя класса ошибки без сообщения, потому что сообщение драйвера или сервера может цитировать значения.

Остальные события — шаги, пачки курсора, команды драйвера, пул, фиксацию транзакции — адаптер не отправляет. Для них есть [OpenTelemetry](./opentelemetry.mdx).

### Ошибки

Каждая ошибка операции уходит через `captureException(error, { contexts: { typemo }, tags })`. Это ошибка из события `operation.error`, то есть копия, замаскированная по `sensitive`. Ушли две ошибки, `DuplicateKeyError` и `CastError`.

В `contexts.typemo` только метаданные, без данных документов.

Теги нужны для фильтра в интерфейсе Sentry, событие открывать не придётся. Это `typemo.error_class` (класс ошибки, например `DuplicateKeyError`), `typemo.classification`, `typemo.operation`, `typemo.model` (нет у операции уровня базы) и `typemo.tenant` (только с `includeTenant: true`). Повторная вставка дала теги `{ "typemo.error_class": "DuplicateKeyError", "typemo.classification": "duplicate-key", "typemo.operation": "insertOne", "typemo.model": "Account" }`.

Есть ещё один вид события. Если ваша функция `mask` из настройки `sensitive` бросила исключение, адаптер отправляет её ошибку, а в ней путь, не значение. Теги — `typemo.instrumentation.source` и `typemo.model`, контекст `typemo` из `source`, `model` и `path`. Значение при этом стало `"?"`. Отправка идёт при `captureErrors: true`.

### Что адаптер не видит

Адаптер видит ровно то, что ядро сообщает в событиях операций. `create`, `$save` и `bulkSave` приводят типы и проверяют внутри своей операции, поэтому их `ValidationError` тоже попадает в Sentry. Ошибка в хуке `pre('save')` случается до операции, вне её, и адаптер о ней не узнает.

## SentrySubscriber

`SentrySubscriber` — сам подписчик, который создаёт `TypemoSentry.instrument`. Класс экспортируется для ручной регистрации, например в клиенте, который не подходит под `InstrumentationTarget`, или в тесте. Он реализует [`InstrumentationSubscriber`](./events.mdx#instrumentationsubscriber), и `handle`, `sensitive` и `includeTenant` доступны как поля.

```ts
import { SentrySubscriber } from "@venloc/typemo-sentry";

const subscriber = new SentrySubscriber({ breadcrumbs: false });
const subscription = client.instrument(subscriber);
```

<Params>
<Param name="options" type="SentryInstrumentationOptions" default="{}">

Те же настройки, что у [`TypemoSentry.instrument`](#typemosentryinstrument).

</Param>
</Params>

Поля экземпляра — `sensitive` и `includeTenant` с применёнными умолчаниями и `handle`, функция обработки событий.

## TypemoErrorContext

`TypemoErrorContext` — тип контекста `contexts.typemo`, его поля перечислены в таблице раздела [Ошибки](#ошибки). `model` и `collection` необязательны, у операции уровня базы их нет, и пустых значений адаптер не пишет. Есть индексная сигнатура `[key: string]: unknown`, потому что Sentry требует от контекста открытый словарь. Все перечисленные поля при этом типизированы точно.

<FullType>

```ts
interface TypemoErrorContext {
  readonly [key: string]: unknown;
  readonly model?: string;
  readonly collection?: string;
  readonly database: string;
  readonly connection: string;
  readonly operation: string;
  readonly path: string | undefined;
  readonly failedStep: string | undefined;
  readonly classification: string;
  readonly serverCode: number | undefined;
  readonly errorLabels: readonly string[];
  readonly retryable: boolean;
  readonly transient: boolean;
  readonly tenant?: string;
}
```

</FullType>

## Когда адаптер не подходит

Если вам нужен не Sentry, а другой трекер ошибок, напишите свой подписчик по образцу этого. Как, объясняет руководство [Своя интеграция](../../observability/custom-integration.mdx). Если нужны спаны и метрики, подключите [`@venloc/typemo-opentelemetry`](./opentelemetry.mdx). Sentry v8 и новее читает трассы из OpenTelemetry сам.
