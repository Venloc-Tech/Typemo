`@venloc/typemo-sentry` передаёт в Sentry то, чего нет в трассировке: **ошибки** операций с понятным контекстом и **breadcrumbs** (хлебные крошки Sentry — короткие записи о том, что происходило перед ошибкой). Пакет отдельный: ядро `@venloc/typemo` не знает про Sentry, а адаптер подписывается на [события операций](./events.mdx) и вызывает `addBreadcrumb` и `captureException` из `@sentry/core`. Поэтому он одинаково работает с `@sentry/node` и `@sentry/bun`: какой SDK вы инициализировали, ему безразлично.

Трассировку этот пакет не делает: спаны в Sentry приходят из OpenTelemetry, поэтому за них отвечает [`@venloc/typemo-opentelemetry`](./opentelemetry.mdx). Как подключить адаптер и что вы увидите в Sentry, рассказывает руководство [Sentry](../../observability/sentry.mdx). Эта страница — справочник.

Пакет требует `@sentry/core` версии не ниже 11.1.0 как peer-зависимость. SDK, DSN и остальные настройки выбирает приложение.

```package-install
@venloc/typemo-sentry @sentry/node
```

Примеры используют модель счёта:

```ts title="accounts/account.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts" })
export class Account extends Entity {
  @Prop(() => String, { required: true, unique: true })
  title!: string;

  @Prop(() => Number, { required: true })
  balance!: number;
}
```

Блоки кода на этой странице не компилируются сборкой документации: она не подключает сторонние пакеты. Результаты получены запуском адаптера на настоящей базе с тестовым клиентом Sentry из `@sentry/core`, который записывает события и breadcrumbs вместо отправки.

## TypemoSentry.instrument

`TypemoSentry.instrument` подписывает адаптер на операции клиента или всех клиентов процесса. С этого момента каждая завершённая операция оставляет breadcrumb, а каждая упавшая ещё и отправляет ошибку в Sentry с контекстом. Он нужен, чтобы по событию в Sentry сразу видеть, какая модель, коллекция и операция упали, на каком шаге и можно ли повторить.

```ts title="monitoring.ts"
import * as Sentry from "@sentry/node";
import { TypemoClient } from "@venloc/typemo";
import { TypemoSentry } from "@venloc/typemo-sentry";

Sentry.init({ dsn: "https://public@example.test/1" });

const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "bank" });
const subscription = TypemoSentry.instrument(client);
// операции клиента попадают в Sentry

subscription.unsubscribe();
```

Регистрация ничего не отправляет сама: она только подписывает адаптер. Адаптер не бросает исключений на пути операции: сбой обработки события он пишет `console.error("[typemo-sentry] an instrumentation subscriber failed:", error)`, а операция идёт дальше. Две подписки на одну ошибку дают в Sentry одно событие, и то же верно, если приложение само отправит эту ошибку после адаптера: `@sentry/core` помечает уже отправленные исключения, и адаптер на это опирается.

<Params>
<Param name="target" type="InstrumentationTarget" required>

Клиент (`TypemoClient`) или класс `Typemo`. Подойдёт любой объект с методом `instrument(subscriber)`, возвращающим подписку. `Typemo` даёт все клиенты процесса.

</Param>
<Param name="options" type="SentryInstrumentationOptions" default="{}">

Настройки: [`SentryInstrumentationOptions`](#sentryinstrumentationoptions).

</Param>
</Params>

<Returns type="Subscription">

Подписка ядра с методом `unsubscribe()`. После него адаптер не отправляет ничего нового.

</Returns>

<FullType>

```ts
class TypemoSentry {
  static instrument(target: InstrumentationTarget, options?: SentryInstrumentationOptions): Subscription;
}

interface InstrumentationTarget {
  readonly instrument: (subscriber: InstrumentationSubscriber) => Subscription;
}
```

</FullType>

## SentryInstrumentationOptions

Все поля необязательны: без настроек адаптер и оставляет breadcrumbs, и отправляет все ошибки, а значения в них маскирует.

### captureErrors

`boolean`, по умолчанию `true`. Отправлять в Sentry через `captureException` **каждую** ошибку операции, без фильтра по виду. Фильтра нет намеренно: решать, какие ошибки шумят, удобнее в Sentry (`beforeSend`, правила группировки), где видно всю картину, а адаптер не должен молча пропускать чужие ошибки. При `false` остаются только breadcrumbs.

### breadcrumbs

`boolean`, по умолчанию `true`. Добавлять breadcrumb на завершение каждой операции, на повтор и на откат транзакции. Запуск с `captureErrors: false` и `breadcrumbs: false` не оставил ни breadcrumb, ни события даже при ошибке `DuplicateKeyError`.

### sensitive

`SubscriberSensitive`, по умолчанию `"mask"`. Так же, как у [подписчика ядра](./events.mdx#subscribersensitive): реальные значения непомеченных полей покидают процесс только при `"show"` или через вашу `{ mask }`. Это относится к сводке в breadcrumb и к значениям в ошибках `CastError`, `ValidationError`, `DuplicateKeyError` и `ServerValidationError`. Пометки `sensitive` в схеме и скрытые поля действуют всегда. Запуск показал: сообщение об ошибке в Sentry — `duplicate key on title_1: { title: "?" } (code 11000 DuplicateKey)`, а вызвавший код получил ошибку с настоящим значением.

### includeTenant

`boolean`, по умолчанию `false`. Класть тенанта операции в **отправленную ошибку**: тег `typemo.tenant` и поле `tenant` в `contexts.typemo` (значение приводится к строке). По умолчанию тенанта нет, потому что тенант — данные ваших клиентов, а Sentry — внешний сервис. Опция передаётся ядру (оно включает `OperationInfo.tenant`) и проверяется ещё раз в [`ErrorContextBuilder`](#errorcontextbuilder). Breadcrumbs тенанта не несут никогда. Для операции вне тенантной политики ни тега, ни поля нет. Запуск с `Note.find().policy({ tenant: "t-1" })` и ошибкой приведения дал тег `typemo.tenant: "t-1"` и `tenant: "t-1"` в контексте.

<FullType>

```ts
interface SentryInstrumentationOptions {
  readonly captureErrors?: boolean;
  readonly breadcrumbs?: boolean;
  readonly sensitive?: SubscriberSensitive;
  readonly includeTenant?: boolean;
}
```

</FullType>

## Что отправляется

### Breadcrumbs

Breadcrumb создаётся, когда операция закончилась, а не когда началась: адаптер запоминает сводку запроса из события `operation.start` и кладёт её в запись, когда приходит `operation.end` или `operation.error`. Сообщение — `Typemo.<операция> (<Модель>)`, как имя спана в OpenTelemetry. Категория всегда `typemo`.

Успешная операция: тип `query`, уровень `info`. У операции уровня базы ([`connection.aggregate`](../connection/connection.mdx#connectionaggregate)) нет модели и коллекции: сообщение `Typemo.aggregate (database bank)`, а в `data` нет `model` и `collection`. Запуск для `find` дал:

```ts
{
  type: "query",
  category: "typemo",
  level: "info",
  message: "Typemo.find (Account)",
  data: {
    model: "Account",
    collection: "accounts",
    database: "bank",
    durationMS: 3.14,
    documentCount: 1,
    summary: { filter: { balance: { $gt: "?" } } },
  },
}
```

Упавшая операция: тип `error`, уровень `error`, в `data` добавляются `failedStep` (`"cast"`, `"execute"`) и `errorKind` (`"duplicate-key"`, `"cast"`), а `documentCount` нет. Транзакция: при повторе и откате тоже breadcrumb, тип `transaction`, сообщение `Typemo.transaction retry` (уровень `warning`) или `Typemo.transaction abort` (уровень `error`), в `data` — `transactionId`, `attempt`, `connection`, `durationMS` и `errorClass`. В `errorClass` только имя класса ошибки без сообщения: сообщение драйвера или сервера может цитировать значения.

Остальные события (шаги, пачки курсора, команды драйвера, пул, фиксация транзакции) адаптер не отправляет: для них есть [OpenTelemetry](./opentelemetry.mdx).

### Ошибки

Каждая ошибка операции уходит через `captureException(error, { contexts: { typemo }, tags })`. Ошибка — та, что приходит в событии `operation.error`, то есть копия, замаскированная по `sensitive`. Запуск дал две ошибки: `DuplicateKeyError` и `CastError`.

Контекст `contexts.typemo` содержит только метаданные, без данных документов:

    "collection": { description: "Имя коллекции. Нет, если операция не читает коллекцию (вся база, `admin`).", type: "string" },
    "database": { description: "Имя базы.", type: "string" },
    "connection": { description: "Имя клиента.", type: "string" },
    "operation": { description: "Имя операции: `insertOne`, `updateOne`.", type: "string" },
    "path": { description: "Путь подгрузки связи, если ошибка во вложенном запросе.", type: "string | undefined" },
    "failedStep": { description: "Шаг, на котором упала операция: `cast`, `execute`.", type: "string | undefined" },
    "classification": { description: "Вид ошибки: `duplicate-key`, `cast`, `not-found`…", type: "string" },

    "errorLabels": { description: "Метки ошибки сервера.", type: "readonly string[]" },
    "retryable": { description: "Может ли помочь повтор.", type: "boolean" },

Теги удобны для фильтра в интерфейсе Sentry, без открытия события: `typemo.error_class` (класс ошибки, например `DuplicateKeyError`), `typemo.classification`, `typemo.operation`, `typemo.model` (нет у операции уровня базы) и `typemo.tenant` (только с `includeTenant: true`). Запуск с повторной вставкой дал теги `{ "typemo.error_class": "DuplicateKeyError", "typemo.classification": "duplicate-key", "typemo.operation": "insertOne", "typemo.model": "Account" }`.

Ещё один вид события: если ваша функция `mask` из настройки `sensitive` бросила исключение, адаптер отправляет её ошибку (в ней путь, а не значение) с тегами `typemo.instrumentation.source` и `typemo.model` и контекстом `typemo` из `source`, `model` и `path`. Значение при этом стало `"?"`. Отправка идёт при `captureErrors: true`.

### Что адаптер не видит

Адаптер видит ровно то, что сообщает ядро в событиях операций: `create`, `$save` и `bulkSave` приводят типы и проверяют внутри своей операции, поэтому их `ValidationError` тоже попадает в Sentry. Ошибка в хуке `pre('save')` до операции остаётся вне её, и адаптер о ней не узнает.

## SentrySubscriber

`SentrySubscriber` — сам подписчик, который создаёт `TypemoSentry.instrument`. Класс экспортируется, если вам нужно зарегистрировать его вручную, например в клиенте, который не подходит под `InstrumentationTarget`, или в тесте. Он реализует [`InstrumentationSubscriber`](./events.mdx#instrumentationsubscriber): `handle`, `sensitive` и `includeTenant` доступны как поля.

```ts
import { SentrySubscriber } from "@venloc/typemo-sentry";

const subscriber = new SentrySubscriber({ breadcrumbs: false });
const subscription = client.instrument(subscriber);
```

<Params>
<Param name="options" type="SentryInstrumentationOptions" default="{}">

Те же настройки, что у [`TypemoSentry.instrument`](#typemosentryinstrument).

</Param>
</Params>

Поля экземпляра: `sensitive` и `includeTenant` (с применёнными умолчаниями), `handle` — функция обработки событий.

`ErrorContextBuilder` — статический класс, который собирает контекст и теги ошибки. Он нужен по той же причине, что и `BreadcrumbBuilder`: свой подписчик получит те же имена полей.

## TypemoErrorContext

`TypemoErrorContext` — тип контекста `contexts.typemo`: поля из таблицы в разделе [Ошибки](#ошибки). `model` и `collection` необязательны: у операции уровня базы их нет, и адаптер не пишет пустых значений. У него есть индексная сигнатура `[key: string]: unknown`, потому что Sentry требует от контекста открытый словарь; все перечисленные поля при этом типизированы точно.

<FullType>

```ts
interface TypemoErrorContext {
  readonly [key: string]: unknown;
  readonly model?: string;
  readonly collection?: string;
  readonly database: string;
  readonly connection: string;
  readonly operation: string;
  readonly path: string | undefined;
  readonly failedStep: string | undefined;
  readonly classification: string;
  readonly serverCode: number | undefined;
  readonly errorLabels: readonly string[];
  readonly retryable: boolean;
  readonly transient: boolean;
  readonly tenant?: string;
}
```

</FullType>

## Когда адаптер не подходит

Если нужен не Sentry, а другой трекер ошибок, напишите свой подписчик по образцу этого: руководство [Своя интеграция](../../observability/custom-integration.mdx). Если нужны спаны и метрики, подключите [`@venloc/typemo-opentelemetry`](./opentelemetry.mdx): Sentry v8 и новее читает трассы из OpenTelemetry сам.
