Три политики данных включаются опциями [`@Schema`](../schemas/schema.mdx) с теми же именами — `tenant`, `softDelete` и `audit`. По умолчанию все три выключены. Опция принимает `true` (настройки по умолчанию) или объект с настройками. После включения политика действует на **все** операции модели, и отключить её в отдельном запросе нельзя. Значения из окружения, например какой тенант и кто действует, передаёт [контекст политик](./policy-context.mdx). Впервые встречаетесь с политиками — начните с [обзора](../../policies/overview.mdx).

Примеры построены на банке. У счёта есть владелец-организация, счёт нельзя стереть без следа, а каждая запись оставляет пометку в журнале.

  type={{

    audit: { description: "Аудит. Каждая запись оставляет строку в журнале, нужен реплика-сет.", type: "true | AuditSchemaOptions" },
  }}

## Опция tenant [#tenant]

Опция `tenant` говорит, что документы модели принадлежат разным **тенантам**. Тенант — независимый владелец данных, например организация или клиент сервиса. Данные тенантов лежат в одной коллекции и не должны видеть друг друга. Политика добавляет условие по полю тенанта в фильтр каждой операции, проставляет тенанта новым документам и не даёт перенести документ к другому. Одна забытая проверка `where orgId = …` в обычном коде выдала бы данные чужой организации. Здесь забыть нельзя, условие ставит не автор запроса.

Поле тенанта описывают три вещи — обычный [`@Prop`](../schemas/prop.mdx), декоратор [`@Tenant()`](../schemas/field-markers.mdx#tenant) и тип [`TenantField`](../schemas/field-markers.mdx#tenant-field). Ядро заполняет поле само, поэтому `create` его не требует, а результаты чтения всегда его содержат. Тип говорит об этом компилятору, декоратор — библиотеке во время работы. Типы TypeScript при запуске исчезают, и без метки Typemo не знал бы, какое поле считать тенантом.

```ts twoslash title="accounts/account.ts"
import { Entity, Prop, Schema, Tenant, type TenantField } from "@venloc/typemo";

@Schema({ collection: "accounts", tenant: true })
export class Account extends Entity {
  @Prop(() => String)
  @Tenant()
  tenantId!: TenantField<string>;

  @Prop(() => String, { required: true })
  title!: string;
}
```

Второй пример показывает объект настроек. Поле называется `orgId`, а тип тенанта — `ObjectId`. Значение из контекста приводится по типу поля, так что строка из адреса запроса подойдёт.

```ts twoslash title="accounts/org-account.ts"
import { Entity, Prop, Schema, Types, Tenant, type TenantField } from "@venloc/typemo";

@Schema({ collection: "org_accounts", tenant: { field: "orgId" } })
export class OrgAccount extends Entity {
  @Prop(() => Types.ObjectId)
  @Tenant()
  orgId!: TenantField<Types.ObjectId>;

  @Prop(() => String, { required: true })
  title!: string;
}
```

Политика охватывает каждый путь.

- Фильтры чтения, записи и «найти и изменить» получают условие тенанта. Если вы сами фильтруете по этому полю, ваше условие остаётся, и должны выполниться оба, так что чужого тенанта не получить.
- Вставки и замены записывают тенанта, если поля нет. Чужое значение — ошибка.
- Обновление не может менять поле тенанта. Запись собственного значения допустима.
- В агрегации условие ставится в начало. [`$lookup`](../aggregation/stages.mdx#lookup), [`$unionWith`](../aggregation/stages.mdx#union-with) и [`$graphLookup`](../aggregation/stages.mdx#graph-lookup) подтягивают только документы того же тенанта, если класс из стадии тоже с политикой. Модель этого класса на подключении не нужна.
- [`$out`](../aggregation/stages.mdx#out) и [`$merge`](../aggregation/stages.mdx#merge) в коллекцию с тенантом запрещены, они записали бы данные мимо политики.
- Запросы [`populate`](../populate/populate.mdx) — это операции целевой модели, и ограничиваются они так же.

Без тенанта операция не уходит на сервер. Typemo бросает [`StrictModeError`](./violations.mdx#tenant) с причиной `tenant`.

<Params title="Настройки">
<Param name="field" type="string" default='"tenantId"'>

Имя поля тенанта в классе. Поле должно быть объявлено, иначе `client.connection.model(Class)` бросит `ConfigurationError: NoField: tenant field "tenantId" is not a field of the class`. Тип `TenantField` и декоратор `@Tenant()` ставятся ровно на это поле. На другом поле или сразу на двух они дают ошибку сборки схемы, а `@Tenant()` на поле не типа `TenantField<T>` не скомпилируется. Подробности в [`TenantField`](../schemas/field-markers.mdx#tenant-field) и [`@Tenant`](../schemas/field-markers.mdx#tenant).

</Param>
</Params>

Согласованность опции и метки проверяется при сборке модели. Любое нарушение — [`ConfigurationError`](../errors/configuration-errors.mdx#configuration-error). Тексты ниже взяты из реального запуска.

```text
ConfigurationError: NoMark: the tenant field "tenantId" must be marked @Tenant() (declare it @Prop(...) @Tenant() tenantId!: TenantField<T>)
ConfigurationError: NoOpt: @Tenant() on "tenantId", but the schema has no tenant policy — add tenant: true (or { field }) to @Schema
ConfigurationError: Two: @Tenant() marks "tenantId", "other"; only the tenant field "tenantId" may be marked
```

Первая ошибка — опция есть, метки нет. Вторая — метка есть, опции нет. Третья — меток две. Все варианты разобраны в руководстве [Разделить данные организаций](../../policies/tenants.mdx#schema-errors). В пакете `@venloc/typemo-decorators` тот же декоратор работает так же.

Три операции ведут себя особо.

- `estimatedDocumentCount` читает метаданные коллекции и не может ограничить подсчёт тенантом. Вместо тихого подсчёта по всем тенантам Typemo бросает ошибку со ссылкой на `countDocuments()`.
- Подписка на изменения ([`watch`](../change-streams/watch.mdx)) модели с тенантом запрещена без `allTenants: true`. В событии удаления нет документа, по которому его можно отфильтровать. Подписаться на всех тенантов можно, но события придётся фильтровать самому.
- `.policy({ tenant })` для модели без политики принимается и ничего не меняет. Так один и тот же код работает с разными моделями.

```ts

  readonly field?: string;

```

## Опция softDelete [#soft-delete]

Опция `softDelete` включает **мягкое удаление**. Удаление не стирает документ, а записывает в поле метку времени, и остальные операции модели перестают видеть помеченные документы. Удалённый счёт можно восстановить, история остаётся. Поле в классе — `Date` с `null`, где `null` значит «жив».

```ts twoslash title="accounts/account.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "accounts", softDelete: true })
export class Account extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => Date, { nullable: true })
  deletedAt?: Date | null;
}
```

Операции `deleteOne`, `deleteMany`, `findOneAndDelete`, удаления в `bulkWrite` и `$deleteOne` документа превращаются в обновление метки. Результат остаётся результатом удаления. `deletedCount` равен числу помеченных документов, а `findOneAndDelete` возвращает документ таким, каким он был. Уже удалённый документ повторно не удаляется, его метка не меняется.

Все остальные операции получают условие `deletedAt: null` (метка `null` или её нет). Ваше условие по полю метки сохраняется, и выполниться должны оба, поэтому `find({ deletedAt: { $ne: null } })` без контекста ничего не найдёт. Чтобы увидеть удалённые, добавьте `includeDeleted` или `onlyDeleted` в [контекст политик](./policy-context.mdx#policy-values). Вставка записывает `deletedAt: null`, если поля нет.

Подтянутые документы ([`$lookup`](../aggregation/stages.mdx#lookup), [`$unionWith`](../aggregation/stages.mdx#union-with), [`$graphLookup`](../aggregation/stages.mdx#graph-lookup), `populate`) удалёнными не бывают. Политику стадия берёт из класса, который в ней назван, даже если его модель на подключении не создана.

<Params title="Настройки">
<Param name="field" type="string" default='"deletedAt"'>

Имя поля метки. Поле обязано быть `Date` с `null`, иначе модель не создаётся — `ConfigurationError: S1: softDelete field "deletedAt" must be a nullable Date field (Date | null)`. Та же ошибка бывает, если поля нет в классе.

</Param>
</Params>

`estimatedDocumentCount` считает и удалённые документы, ведь это метаданные коллекции. Без `includeDeleted: true` Typemo бросает [`StrictModeError`](./violations.mdx#soft-delete) с причиной `soft-delete`.

Мягкое удаление плохо ладит с уникальными индексами, потому что удалённый документ продолжает занимать значение. При создании модели Typemo подсказывает про каждый уникальный индекс без частичного условия по метке, как сделать его частичным по живым документам. Условие такое — `partialFilterExpression: { deletedAt: { $type: "null" } }`. Нужен именно `$type: "null"`. Частичный индекс не умеет выражать «поля нет», а вставка всегда пишет `null`.

Стереть документы навсегда или вернуть их позволяют [`SoftDelete.purge`](./soft-delete-and-untrusted.mdx#soft-delete.purge) и [`SoftDelete.restore`](./soft-delete-and-untrusted.mdx#soft-delete.restore).

## Опция audit [#audit]

Опция `audit` включает **аудит**. Каждая запись в модель оставляет строку в отдельной коллекции журнала. Из строки видно, что и когда записано, чей это тенант и кто действовал (`actor` из [контекста политик](./policy-context.mdx#policy-values)). Журнал читают для расследований вроде «кто изменил лимит счёта», для отчётности и чтобы восстановить цепочку изменений.

```ts twoslash title="transfers/transfer.ts"
import { Entity, Prop, Schema } from "@venloc/typemo";

@Schema({ collection: "transfers", audit: true })
export class Transfer extends Entity {
  @Prop(() => String, { required: true })
  from!: string;

  @Prop(() => Number, { required: true })
  amount!: number;

  @Prop(() => String, { sensitive: "mask" })
  card?: string;
}
```

Журнал пишется в той же транзакции, что и запись, сразу после неё. Строка называет то, что назвала операция. Запись по фильтру без `_id` оставит фильтр, а не идентификаторы затронутых документов. Чтобы получить историю документа, прочитайте идентификаторы в транзакции и пишите по `_id: { $in }`. Рецепт разобран в руководстве [Вести журнал изменений](../../policies/audit.mdx#document-history).

Запись и её строка фиксируются вместе или не фиксируются вовсе. Если строка не записалась, операция падает с [`AuditError`](../errors/configuration-errors.mdx#audit-error), а запись откатывается. Поэтому запись в модель с аудитом вне транзакции сама открывает свою. Для этого нужен **реплика-сет** или шардированный кластер. На одиночном `mongod` запись бросает `ConfigurationError` с просьбой запустить реплика-сет, хватит и одного узла. Чтения в журнал не попадают.

Секреты в журнале маскируются по опции поля [`sensitive`](../schemas/prop.mdx#sensitive), у самой `audit` настроек для этого нет. Значение заменяется на `?` (`"mask"`) или `[hidden]` (`"hide"`) в фильтре, обновлении и документах. Собственная функция `{ mask: (value) => … }` оставляет то, что вернёт, например последние четыре цифры. Её вызывают только со значением объявленного типа поля. Операнд другого типа, скажем `{ $exists: true }` в фильтре по этому полю, попадёт в журнал как `?` без вызова. Скрытое поле (`Hidden`) без пометки тоже маскируется.

<Params title="Настройки">
<Param name="collection" type="string" default="<collection>_audit">

Имя коллекции журнала. По умолчанию к имени коллекции модели добавляется `_audit`, для `transfers` это `transfers_audit`.

</Param>
</Params>

Модели у журнала нет, Typemo только пишет в него. Строки читайте через драйвер — [`client.unsafeDriver()`](../connection/typemo-client.mdx#client.unsafe-driver). Ниже запись в модели `Transfer` от имени `user-7` и строка, которая осталась в журнале.

```ts twoslash
import { Entity, Prop, Schema, TypemoClient, PolicyContext } from "@venloc/typemo";
@Schema({ collection: "transfers", audit: true })
class Transfer extends Entity {
  @Prop(() => String, { required: true }) from!: string;
  @Prop(() => Number, { required: true }) amount!: number;
  @Prop(() => String, { sensitive: "mask" }) card?: string;
}
const client = await TypemoClient.connect("mongodb://localhost:27017/app");
const Transfers = client.connection.model(Transfer);
// ---cut---
await PolicyContext.run({ actor: "user-7" }, () =>
  Transfers.updateOne({ from: "A" }, { $set: { amount: 90, card: "5500000000000004" } }),
);

const trail = client.unsafeDriver().db("app").collection("transfers_audit");
const entry = await trail.findOne({ operation: "updateOne" });
console.log(entry);
// → { model: "Transfer", collection: "transfers", operation: "updateOne", document: false,
//     actor: "user-7", outcome: "ok", filter: { from: "A" },
//     update: { $set: { amount: 90, card: "?" } },
//     result: { matchedCount: 1, modifiedCount: 1, upsertedCount: 0, upsertedId: null }, … }
```

## AuditEntry [#audit-entry]

`AuditEntry` описывает строку журнала. Поля `filter`, `update`, `replacement`, `documents` и `operations` хранят значения после приведения типов, под именами полей класса и с замаскированными секретами. Мягкое удаление записывается как удаление с признаком `softDelete: true`.

<TypeTable
  type={{
    at: { description: "Когда сделана запись.", type: "Date" },
    model: { description: "Имя модели (класса).", type: "string" },
    collection: { description: "Коллекция модели.", type: "string" },
    operation: { description: "Название операции — `insertOne`, `updateMany`, `deleteMany`, `bulkWrite` и так далее. Запись документа через `$save` — это `insertOne` или `updateOne`.", type: "string" },
    document: { description: "`true`, если запись сделана через документ (`$save`, `$deleteOne`, `create`, `bulkSave`).", type: "boolean" },
    actor: { description: "`actor` из контекста политик, если он был.", type: "unknown", required: false },
    tenant: { description: "`tenant` из контекста политик, если он был.", type: "unknown", required: false },
    filter: { description: "Фильтр записи (с маскировкой).", type: "PlanDocument", required: false },
    update: { description: "Обновление (с маскировкой).", type: "PlanDocument | readonly PlanDocument[]", required: false },
    replacement: { description: "Документ замены (с маскировкой).", type: "PlanDocument", required: false },
    documents: { description: "Вставленные документы (только записанные).", type: "readonly PlanDocument[]", required: false },
    operations: { description: "Для `bulkWrite` — отправленные операции (с маскировкой).", type: "readonly PlanDocument[]", required: false },
    result: { description: "Счётчики сервера — `insertedCount`, `matchedCount`, `modifiedCount`, `deletedCount`. Для «найти и изменить» ещё `found` и `_id`.", type: "Readonly<Record<string, unknown>>" },
    outcome: { description: "`\"ok\"` или `\"partial\"`. Второе значение — неупорядоченная пакетная вставка или `bulkWrite` упали, записав часть.", type: '"ok" | "partial"' },
    softDelete: { description: "`true`, если это мягкое удаление.", type: "true", required: false },
  }}
/>

Тип описывает результат чтения журнала. Строка, прочитанная драйвером, дополнительно имеет `_id`.

```ts
interface AuditEntry {
  readonly at: Date;
  readonly model: string;
  readonly collection: string;
  readonly operation: string;
  readonly document: boolean;
  readonly actor?: unknown;
  readonly tenant?: unknown;
  readonly filter?: PlanDocument;
  readonly update?: PlanDocument | readonly PlanDocument[];
  readonly replacement?: PlanDocument;
  readonly documents?: readonly PlanDocument[];
  readonly operations?: readonly PlanDocument[];

  readonly outcome: "ok" | "partial";
  readonly softDelete?: true;
}
```

### Что не попадает в журнал [#not-logged]

В журнал не попадают чтения, агрегации со стадиями `$out` и `$merge` (о них сообщается отдельно) и записи, которые хук отменил до отправки. Записывать там было нечего.

Неупорядоченная пакетная запись, упавшая внутри транзакции, не оставляет ни записи, ни строки, сервер откатывает всю транзакцию. Строка `partial` появляется, только если часть документов отвергнута до отправки на сервер (приведением типов или проверкой), а остальные записаны.

## Когда не подходит [#when-not-to-use]

Политики не заменяют права доступа. Они делят данные и оставляют следы, но не решают, кому разрешена операция. Если нужны роли, проверяйте права до вызова модели.

Для аудита каждого чтения журнал не годится, чтения в него не пишутся. Берите журнал доступа сервера. Если реплика-сета нет, аудит включить нельзя, но историю изменений можно вести собственным [хуком](../../hooks/operation-hooks.mdx) записи. Руководства — [Мультитенантность](../../policies/tenants.mdx), [Мягкое удаление](../../policies/soft-delete.mdx), [Аудит](../../policies/audit.mdx).
