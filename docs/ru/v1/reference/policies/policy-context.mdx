**Контекст политик** — значения, которые политики модели читают при каждой операции. Какому тенанту принадлежат данные, кто действует (для аудита), нужно ли показывать удалённые документы. Модель и клиент их не хранят. Значения приходят из области, которую открывает [`PolicyContext.run`](#policy-context.run), или из [`.policy()`](../query/options.mdx#policy) у одной операции. Если вы только начинаете, прочитайте сначала руководство [Контекст политик](../../policies/policy-context.mdx).

Контекст читается **в момент построения операции**, а не в момент `await`. Запрос, созданный внутри `run`, помнит значения, даже если вы дождётесь его снаружи. Строитель, созданный вне `run`, тенанта не получит, сколько его ни жди внутри. Поэтому запрос, сохранённый в переменной модуля, не сменит тенанта вслед за HTTP-запросом, который случайно его дождался.

В примерах — модель заказа организации. Поле `tenantId` помечено [`@Tenant()`](../schemas/field-markers.mdx#tenant) и типом [`TenantField`](../schemas/field-markers.mdx#tenant-field), а политика тенанта включена ([`tenant`](./schema-options.mdx#tenant)).

## PolicyContext.run [#policy-context.run]

`run` открывает область со значениями контекста и выполняет в ней функцию. Область живёт во всей цепочке асинхронных вызовов внутри функции — после `await`, в колбэках, в таймерах. Так же Node и Bun хранят данные текущего HTTP-запроса. Тенанта не нужно передавать параметром в каждую функцию сервиса.

<Snippet id="reference/policies/policy-context/policy-context-run" twoslash />

Вложенный `run` не заменяет область целиком, а накладывает значения на внешнюю. Внутренний `tenant` перекрывает внешний, остальные значения остаются. Если внутренний `run` задаёт `tenant`, унаследованный `allTenants` отменяется. И наоборот — `allTenants: true` отменяет унаследованный `tenant`. Так же ведут себя `includeDeleted` и `onlyDeleted`, иначе внутри оказался бы противоречивый контекст.

<Snippet id="reference/policies/policy-context/policy-context-run-2" twoslash />

<Returns type="R">

То, что вернула `work`, без изменений — и значение, и `Promise`. Сам `run` ничего не ждёт. Если область нужна и после `await`, объявите функцию `async` и ждите внутри неё, а не снаружи.

</Returns>

</Param>

Функция, в которой действует область.

</Param>

### Ошибки [#errors]

Неверные значения [`run`](#policy-context.run) отвергает до вызова функции. Форму значений проверяет [`QueryError`](../errors/query-errors.mdx#query-error), пустой тенант ловит [`StrictModeError`](./violations.mdx#tenant). Все тексты ниже взяты из реального запуска.

<Snippet id="reference/policies/policy-context/errors" />

Опечатка в имени ключа не превращается в тихое отсутствие тенанта. Ошибка называет `tenat` и список допустимых ключей. По той же причине `null`, пустая строка и строка из пробелов в `tenant` запрещены. Они выглядели бы как «тенант не нужен», а «не нужен» пишется явно — `allTenants: true`. Без проверки ошибка в коде, который достаёт организацию из токена, молча превратилась бы в работу с документами без организации.

## PolicyContext.current [#policy-context.current]

`current` возвращает значения области, в которой вы находитесь. Он нужен там, где значения надо прочитать, а не применить. Например, записать в журнал запроса, передать в задачу очереди или показать в ответе отладки. Вне любого `run` приходит `undefined`, а не пустой объект, так что отсутствие области видно сразу.

<Snippet id="reference/policies/policy-context/policy-context-current" twoslash />

Значения `.policy()` у отдельной операции в `current` не видны. `.policy()` действует на одну операцию и области не создаёт.

<Returns type="Readonly<PolicyValues> | undefined">

Замороженный объект со значениями области (изменить его нельзя) или `undefined` вне `run`.

</Returns>

Аргументов нет.

## PolicyContext.captured [#policy-context.captured]

`captured` отдаёт значения области в форме, которую принимают параметры операций, — `{ policy }`. Метод открыт для обёрток и плагинов, которые сами собирают операцию, например для своего слоя запросов. Операции моделей делают то же самое при построении. Прикладному коду он ни к чему, область открывается через [`run`](#policy-context.run). Вне области `policy` — пустой объект.

<Snippet id="reference/policies/policy-context/policy-context-captured" twoslash />

<Returns type="{ readonly policy: Readonly<PolicyValues> }">

Объект с одним ключом `policy`. Его можно распаковать в параметры операции.

</Returns>

Аргументов нет.

## PolicyContext.merge [#policy-context.merge]

`merge` проверяет значения и накладывает их на другие, не меняя ни то, ни другое. Метод открыт для обёрток и плагинов, которые сочетают свои значения политик со значениями области. Прикладной код передаёт значения операции напрямую (`.policy()`, параметр `policy` записи). Тем же способом [`run`](#policy-context.run) строит вложенную область, а [`.policy()`](../query/options.mdx#policy) накладывает значения операции на область.

Правила те же, что у `run`. Неизвестный ключ, флаг не `true` и противоречия дают [`QueryError`](../errors/query-errors.mdx#query-error), пустой тенант (`null`, пустая строка) — [`StrictModeError`](./violations.mdx#tenant). В тексте обеих ошибок стоит имя вызова из `where`. Значение `undefined` в `extra` пропускается и не стирает значение из `base`.

<Snippet id="reference/policies/policy-context/policy-context-merge" twoslash />

Явный `allTenants` убрал унаследованный `tenant`, и результат не противоречит сам себе.

<Returns type="Readonly<PolicyValues>">

Новый замороженный объект. Аргументы не меняются.

</Returns>

<Params>
<Param name="base" type="Readonly<PolicyValues> | undefined" required>

Значения, на которые накладываются новые. `undefined` значит «ничего».

</Param>
<Param name="extra" type="PolicyValues" required>

Новые значения. Их `merge` проверяет.

</Param>
<Param name="where" type="string" required>

Название вызова. Оно попадает в начало текста ошибки.

</Param>
</Params>

## PolicyValues [#policy-values]

`PolicyValues` — тип объекта, который принимают [`run`](#policy-context.run), [`merge`](#policy-context.merge) и [`.policy()`](../query/options.mdx#policy). Все ключи необязательны, неизвестный ключ — ошибка. Четыре ключа — флаги, они принимают только `true` или отсутствие. `false` в контексте политик ничего не значит, кроме путаницы, ведь «выключить политику» и «не включать» — разные вещи.

<TypeTable
  type={{
    tenant: { description: "Тенант операции. Значение приводится по типу поля тенанта модели (строка, число, `ObjectId`, …). Нужен каждой операции модели с политикой [`tenant`](./schema-options.mdx#tenant). Значение непустое — `null`, пустая строка и строка из пробелов отвергаются.", type: "unknown" },
    allTenants: { description: "Работа сразу по всем тенантам, например фоновая задача администратора. Политика тенанта операцию не ограничивает. Несовместим с `tenant`.", type: "true" },
    actor: { description: "Кто действует. Записывается в каждую запись [аудита](./schema-options.mdx#audit).", type: "unknown" },
    includeDeleted: { description: "Операция видит и удалённые документы (политика [`softDelete`](./schema-options.mdx#soft-delete)). Несовместим с `onlyDeleted`.", type: "true" },
    onlyDeleted: { description: "Операция видит только удалённые документы. Так работает [`SoftDelete.restore`](./soft-delete-and-untrusted.mdx#soft-delete.restore).", type: "true" },
    hardDelete: { description: "Удаление стирает документы навсегда, а не помечает. Так работает [`SoftDelete.purge`](./soft-delete-and-untrusted.mdx#soft-delete.purge).", type: "true" },
  }}
/>

`tenant` и `actor` имеют тип `unknown`, потому что тип тенанта задаёт поле модели. Для `TenantField<string>` годится строка, для `TenantField<ObjectId>` — `ObjectId` или его строка. Значение приводится так же, как значение поля, а неподходящее вызывает [`CastError`](../errors/data-errors.mdx#cast-error). Число для строкового поля даст `Cast to string failed at path "tenantId" for 5 (number): expected a string [type]`.

## Когда не подходит [#when-not-to-use]

Контекст политик не заменяет фильтр. Ограничить выборку по обычному полю, например по владельцу счёта, нужно условием в фильтре. Политики отвечают за то, что нельзя ослабить ни в одном запросе модели. Если одной операции нужен другой тенант или другой режим удалённых, возьмите [`.policy()`](../query/options.mdx#policy), область открывать не придётся. Как контекст работает в задачах, смотрите в руководствах [Контекст политик](../../policies/policy-context.mdx) и [Мультитенантность](../../policies/tenants.mdx).
