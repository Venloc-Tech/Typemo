Чтобы показать пост вместе с именем автора, а не с непонятным идентификатором, используйте [`.populate`](../reference/populate/populate.mdx#populate): он читает связанные документы и подставляет их на место идентификаторов. В MongoDB документы хранятся отдельно и ссылаются друг на друга по `_id`, а сервер не присоединяет их сам при чтении. Без populate вы бы вручную собирали идентификаторы, делали второй запрос и раскладывали результат по местам, а Typemo делает это за один вызов и, что важнее, меняет тип результата: компилятор знает, что в `author` теперь пользователь (или `null`, если пользователя удалили), а не идентификатор.

Если вы впервые работаете со ссылками между документами, вам достаточно одной идеи: поле, объявленное как `Ref<User>`, хранит `_id` документа пользователя, а `.populate("author")` заменяет его самим пользователем в результате запроса. Ссылки описываются в схеме, об этом рассказывает руководство [Ссылки на другие модели](../schemas/references.mdx).

## Что предполагается

Примеры используют клиент из руководства [Подключиться к базе](../connection/connect.mdx) и модели блога: пользователь, тег, пост и комментарий. Модель растёт по ходу страницы, а полностью показана на странице справочника [`.populate`](../reference/populate/populate.mdx). В базе два пользователя (Alice и Bob), два тега (`db` и `ts`) и три поста: «Hello» и «Second» написала Alice, «Bob's» написал Bob. У «Hello» теги `db` и `ts`, у «Second» тег `ts`, у «Bob's» тегов нет. Идентификаторы в результатах сокращены до `"…"`.

Начнём с двух моделей: пост хранит идентификатор автора.

```ts twoslash title="blog/models.ts"
import { Entity, Prop, Schema, Types, type Ref } from "@venloc/typemo";

@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true })
  name!: string;

  @Prop(() => String)
  email?: string;
}

@Schema({ collection: "posts" })
export class Post extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => Types.ObjectId, { ref: () => User, required: true })
  author!: Ref<User>;
}
```

## Быстрый путь

Три самых частых вызова. Каждый принимает путь поля со ссылкой; результат — тот же пост, но вместо идентификатора в `author` лежит пользователь. Знак `?.` в примерах нужен из-за `null`: если автора удалили, поле станет `null`, об этом ниже.

```ts twoslash
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Ref, type VirtualRef } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String) email?: string;
  @Virtual({ ref: () => Post, localField: "_id", foreignField: "author" }) posts?: VirtualRef<Post>;
}
@Schema({ collection: "tags" })
class Tag extends Entity {
  @Prop(() => String, { required: true }) label!: string;
}
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
  @Prop(() => Types.ObjectId, { ref: () => User, required: true }) author!: Ref<User>;
  @Prop(() => Types.ObjectId, { ref: () => User }) editor?: Ref<User>;
  @Prop(() => [Types.ObjectId], { ref: () => Tag }) tags!: Ref<Tag>[];
  @Prop(() => Spec.map(Types.ObjectId), { ref: () => User }) reviewers?: Map<string, Ref<User>>;
  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post" }) comments?: VirtualRef<Comment>;
  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post", count: true }) commentCount?: VirtualRef<Comment, false, true>;
}
@Schema({ collection: "comments" })
class Comment extends Entity {
  @Prop(() => String, { required: true }) text!: string;
  @Prop(() => Types.ObjectId, { ref: () => Post, required: true }) post!: Ref<Post>;
  @Prop(() => Types.ObjectId, { ref: () => User, required: true }) author!: Ref<User>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Users = client.db().model(User);
const Tags = client.db().model(Tag);
const Posts = client.db().model(Post);
const Comments = client.db().model(Comment);
// ---cut---
// одна ссылка
const post = await Posts.findOne({ title: "Hello" }).populate("author").orFail().plain();
console.log(post.author?.name);
// → "Alice"

// только нужные поля связанного документа
const slim = await Posts.findOne({ title: "Hello" })
  .populate({ path: "author", select: { name: 1, _id: 0 } })
  .orFail()
  .plain();
console.log(slim.author);
// → { name: "Alice" }

// несколько связей за раз
const full = await Posts.findOne({ title: "Hello" }).populate(["author", "tags"]).orFail().plain();
console.log(full.author?.name, full.tags.map((tag) => tag.label));
// → "Alice" ["db", "ts"]
```

Остальная страница разбирает каждый случай на реальных задачах: список постов с авторами, выбор полей, связи «один ко многим», тип результата и число запросов.

## Показать автора в списке постов

Ситуация: на главной странице блога нужен список постов с именем автора. Пост хранит только `author` — идентификатор, поэтому без populate имя взять негде.

```ts twoslash title="blog/posts.service.ts"

}
@Schema({ collection: "posts" })

  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
  @Prop(() => Types.ObjectId, { ref: () => User, required: true }) author!: Ref<User>;
  @Prop(() => Types.ObjectId, { ref: () => User }) editor?: Ref<User>;
  @Prop(() => [Types.ObjectId], { ref: () => Tag }) tags!: Ref<Tag>[];
  @Prop(() => Spec.map(Types.ObjectId), { ref: () => User }) reviewers?: Map<string, Ref<User>>;
  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post" }) comments?: VirtualRef<Comment>;
  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post", count: true }) commentCount?: VirtualRef<Comment, false, true>;
}
@Schema({ collection: "comments" })
class Comment extends Entity {
  @Prop(() => String, { required: true }) text!: string;
  @Prop(() => Types.ObjectId, { ref: () => Post, required: true }) post!: Ref<Post>;
  @Prop(() => Types.ObjectId, { ref: () => User, required: true }) author!: Ref<User>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Users = client.db().model(User);
const Tags = client.db().model(Tag);
const Posts = client.db().model(Post);
const Comments = client.db().model(Comment);
// ---cut---
export const listPosts = async () => {
  const posts = await Posts.find().sort({ title: 1 }).populate("author").plain();
  return posts.map((post) => ({ title: post.title, author: post.author?.name }));
};

console.log(await listPosts());
// → [{ title: "Bob's", author: "Bob" }, { title: "Hello", author: "Alice" }, { title: "Second", author: "Alice" }]
```

Что произошло. Typemo прочитал три поста, собрал из них идентификаторы авторов (Bob и Alice, каждый один раз), одним запросом прочитал этих пользователей и разложил их по постам. Число запросов не зависит от числа постов: их два при трёх постах и два при тысяче. Обратите внимание на тип: для `.populate("author")` поле `author` уже не `Ref<User>`, а объект пользователя или `null`, поэтому к имени обращаются через `?.`: автора могли удалить уже после записи поста (подробнее в разделе [Что вернётся и какой тип](#что-вернётся-и-какой-тип)).

Если вызвать `.populate` в другом порядке или не вызвать вообще, тип подскажет разницу: без populate `post.author` — идентификатор, и `post.author.name` не скомпилируется.

## Выбрать только нужные поля связанного документа

Ситуация: из автора нужно только имя, а почту показывать не стоит, да и тянуть её незачем. Опция [`select`](../reference/populate/populate.mdx#select) работает как обычная проекция, но действует на связанные документы.

  @Prop(() => Types.ObjectId, { ref: () => User }) editor?: Ref<User>;

`_id` остаётся, если вы не исключили его явно: проекция работает как везде в Typemo. Тип поля сужается вместе с выбором, поэтому обратиться к `post.author?.email` компилятор не даст: этого поля в результате нет. Выбор полей уменьшает и объём данных, которые база отдаёт приложению, что заметно при больших связанных документах; подробности — в руководстве [Производительность populate](./performance.mdx).

Ситуация: странице поста нужны автор и теги. Передайте список: в нём можно смешивать пути и объекты с опциями.

Каждый путь — отдельный запрос к своей модели, поэтому три пути дают три дополнительных запроса. Пути можно и цеплять вызовами `.populate("author").populate("tags")`: результат тот же. Но повторный вызов для того же пути заменяет прежний, а не складывается с ним: последний вызов выигрывает.

## Связь без хранения: комментарии поста

Ситуация: нужны комментарии поста, но пост не хранит их идентификаторы, а сам комментарий хранит ссылку на пост. Такую обратную связь описывает **виртуальное поле**: оно ничего не записывает в базу, а при populate находит комментарии по полю `post`. Опишем его в модели поста.

```ts twoslash title="blog/models.ts"
import { Entity, Prop, Schema, Types, Virtual, type Ref, type VirtualRef } from "@venloc/typemo";

@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true })
  name!: string;

  @Prop(() => String)
  email?: string;
}

@Schema({ collection: "posts" })
export class Post extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => Types.ObjectId, { ref: () => User, required: true })
  author!: Ref<User>;

  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post" }) // [!code ++]
  comments?: VirtualRef<Comment>; // [!code ++]
}

@Schema({ collection: "comments" })
export class Comment extends Entity {
  @Prop(() => String, { required: true })
  text!: string;

  @Prop(() => Types.ObjectId, { ref: () => Post, required: true })
  post!: Ref<Post>;
}
```

`localField` — поле поста, значение которого ищем (`_id`), `foreignField` — поле комментария, в котором оно должно лежать (`post`). Подробнее о виртуальных полях — в руководстве [Виртуальные поля](../schemas/virtuals.mdx). Дальше виртуальное поле загружается так же, как ссылка:

```ts twoslash

  @Prop(() => Types.ObjectId, { ref: () => User }) editor?: Ref<User>;
  @Prop(() => [Types.ObjectId], { ref: () => Tag }) tags!: Ref<Tag>[];
  @Prop(() => Spec.map(Types.ObjectId), { ref: () => User }) reviewers?: Map<string, Ref<User>>;
  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post" }) comments?: VirtualRef<Comment>;

  @Prop(() => String, { required: true }) text!: string;

```

У поста без комментариев виртуальное поле — пустой массив, а не отсутствие значения: после populate виртуальное поле всегда есть. Если нужно лишь число комментариев, а не сами комментарии, объявите виртуальное поле со счётчиком (`count: true`): [`populate`](../reference/populate/populate.mdx#populate) тогда попросит базу посчитать документы, а не загрузит их. Остальные виды связей — вложенные, через карты и полиморфные — разобраны в руководстве [Сложные связи](./complex-relations.mdx).

## Что вернётся и какой тип

Ссылка, которая не нашла документ, ведёт себя по форме поля: единичная ссылка становится `null`, а из массива элемент исчезает, остальные сохраняют порядок. Так случается, если документ удалён или скрыт мягким удалением. Поэтому тип единичной ссылки после populate всегда допускает `null`: `HydratedDoc<User> | null` у документа, `{ … } | null` у lean и plain. Схема не может это исключить: `required: true` у `@Prop` требует, чтобы идентификатор лежал в посте, а не чтобы пользователь с таким идентификатором существовал.

```ts twoslash
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Ref, type VirtualRef } from "@venloc/typemo";
@Schema({ collection: "users" })

  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String) email?: string;
  @Virtual({ ref: () => Post, localField: "_id", foreignField: "author" }) posts?: VirtualRef<Post>;
}
@Schema({ collection: "tags" })

  @Prop(() => String, { required: true }) label!: string;
}
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
  @Prop(() => Types.ObjectId, { ref: () => User, required: true }) author!: Ref<User>;
  @Prop(() => Types.ObjectId, { ref: () => User }) editor?: Ref<User>;
  @Prop(() => [Types.ObjectId], { ref: () => Tag }) tags!: Ref<Tag>[];
  @Prop(() => Spec.map(Types.ObjectId), { ref: () => User }) reviewers?: Map<string, Ref<User>>;
  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post" }) comments?: VirtualRef<Comment>;
  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post", count: true }) commentCount?: VirtualRef<Comment, false, true>;
}
@Schema({ collection: "comments" })
class Comment extends Entity {
  @Prop(() => String, { required: true }) text!: string;
  @Prop(() => Types.ObjectId, { ref: () => Post, required: true }) post!: Ref<Post>;
  @Prop(() => Types.ObjectId, { ref: () => User, required: true }) author!: Ref<User>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Users = client.db().model(User);
const Tags = client.db().model(Tag);
const Posts = client.db().model(Post);
const Comments = client.db().model(Comment);
// ---cut---
const [bobPost, hello] = await Posts.find({ title: { $in: ["Bob's", "Hello"] } })
  .sort({ title: 1 })
  .populate({ path: "tags", match: { label: "ts" } })
  .plain();
console.log(bobPost?.tags.length, hello?.tags.map((tag) => tag.label));
// → 0 ["ts"]
```

Опция [`match`](../reference/populate/populate.mdx#match) оставила из тегов только `ts`, поэтому у «Hello» пропала ссылка на `db`. Вид результата определяет, что лежит в поле: у документа — документ модели-цели со всеми методами (массив такой — только для чтения), у [`.lean()`](../reference/query/reading.mdx#lean) и [`.plain()`](../reference/query/reading.mdx#plain) — простые объекты. Различие видно по `_id`: в lean это `ObjectId`, в plain — строка.

Что сделать со сменой типа, если он нужен в своей функции, рассказано в руководстве [Проверка типа](./type-checks.mdx), а изменять и сохранять загруженные документы вам придётся осторожно: об этом — в [Populate у документа](./document-populate.mdx).

## Сколько запросов уходит в базу

Один путь — один дополнительный запрос к модели-цели, сколько бы документов вы ни прочитали. Подзапросы видны в [событиях операций](../observability/events.mdx): у каждого заполнен `populatePath`, а родителем указан основной запрос. Вот события для `Posts.find().populate(["author", "tags", "comments"])`:

```text
find:Post
find:User@author
find:Tag@tags
find:Comment@comments
```

Запросы к разным моделям идут параллельно, а внутри транзакции — по очереди. Основной запрос читает посты, и только когда он закончится, известно, какие идентификаторы искать, поэтому запросы populate не могут начаться раньше. Если основной запрос ничего не нашёл, дополнительных запросов нет совсем.

## Как выбрать

Задайте себе один вопрос: **что вам нужно сделать со связанными данными?** Если показать их вместе с основными и они лежат в других коллекциях, используйте populate. Если вам нужен один связанный документ и основной у вас уже есть, обычный [`findById`](../reference/query/reading.mdx#modelfindbyid) короче и понятнее. Если по связанным данным надо считать (сумма, среднее, группировка) или фильтровать основные документы по связанным полям, нужна агрегация со стадией [`$lookup`](../reference/aggregation/stages.mdx#lookup): populate сначала загрузит документы, а фильтровать по ним основной запрос не может.

## Когда populate не нужен

Если связанные данные не показываются пользователю, а нужны только для проверки («существует ли автор»), загружать их незачем: достаточно [`exists`](../reference/query/reading.mdx#modelexists). Если ссылка нужна только как идентификатор, например, для адреса `/users/<id>`, populate тоже лишний. И если вам нужно сравнить или найти пост по полю автора (все посты авторов из Москвы), populate не поможет: он работает после чтения основных документов.

## Частые ошибки

### Вместо автора идентификатор

Вы вызвали `.populate` не на том поле или забыли вызвать. В plain это строка, в lean — `ObjectId`, а в документе — `ObjectId` тоже. Тип подскажет: `post.author.name` не скомпилируется (`Property 'name' does not exist on type 'string'`). Вызовите `.populate("author")`.

### Ошибка: путь не ссылка

```ts twoslash
// @errors: 2345
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Ref, type VirtualRef } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {

  @Prop(() => String) email?: string;
  @Virtual({ ref: () => Post, localField: "_id", foreignField: "author" }) posts?: VirtualRef<Post>;
}
@Schema({ collection: "tags" })
class Tag extends Entity {
  @Prop(() => String, { required: true }) label!: string;
}
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
  @Prop(() => Types.ObjectId, { ref: () => User, required: true }) author!: Ref<User>;
  @Prop(() => Types.ObjectId, { ref: () => User }) editor?: Ref<User>;
  @Prop(() => [Types.ObjectId], { ref: () => Tag }) tags!: Ref<Tag>[];
  @Prop(() => Spec.map(Types.ObjectId), { ref: () => User }) reviewers?: Map<string, Ref<User>>;
  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post" }) comments?: VirtualRef<Comment>;
  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post", count: true }) commentCount?: VirtualRef<Comment, false, true>;
}
@Schema({ collection: "comments" })
class Comment extends Entity {
  @Prop(() => String, { required: true }) text!: string;
  @Prop(() => Types.ObjectId, { ref: () => Post, required: true }) post!: Ref<Post>;
  @Prop(() => Types.ObjectId, { ref: () => User, required: true }) author!: Ref<User>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Users = client.db().model(User);
const Tags = client.db().model(Tag);
const Posts = client.db().model(Post);

```

Компилятор: `TS2345: Argument of type '"title"' is not assignable to parameter of type 'PopulateObject | "Invalid populate path \"title\": \"title\" is not a reference"'`. Во время работы (путь из данных): `QueryError: populate "title": "title" is neither a reference nor an embedded document`. Populate работает только с полями, помеченными `ref`, и с виртуальными полями. Укажите поле со ссылкой: `author`, `tags`.

### Автор оказался null

Ссылка указывает на документ, которого нет, или его скрыло мягкое удаление. Populate не бросает ошибку, а ставит `null`, и тип поля это допускает, поэтому `post.author.name` не скомпилируется (`TS18047: 'post.author' is possibly 'null'`). Если такая ссылка допустима, проверяйте её через `?.` или [`isPresent`](../reference/populate/populate-types.mdx#ispresent). Если она означает ошибку данных, попросите [`required: true`](../reference/populate/populate.mdx#required): тогда висячая ссылка бросает `DocumentNotFoundError`, а из типа результата `null` уходит.

## Полный пример

```ts twoslash title="blog/posts.service.ts"
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Ref, type VirtualRef } from "@venloc/typemo";
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) name!: string;
  @Prop(() => String) email?: string;
  @Virtual({ ref: () => Post, localField: "_id", foreignField: "author" }) posts?: VirtualRef<Post>;
}
@Schema({ collection: "tags" })
class Tag extends Entity {
  @Prop(() => String, { required: true }) label!: string;
}
@Schema({ collection: "posts" })
class Post extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => Number, { required: true }) views!: number;
  @Prop(() => Types.ObjectId, { ref: () => User, required: true }) author!: Ref<User>;
  @Prop(() => Types.ObjectId, { ref: () => User }) editor?: Ref<User>;
  @Prop(() => [Types.ObjectId], { ref: () => Tag }) tags!: Ref<Tag>[];
  @Prop(() => Spec.map(Types.ObjectId), { ref: () => User }) reviewers?: Map<string, Ref<User>>;
  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post" }) comments?: VirtualRef<Comment>;
  @Virtual({ ref: () => Comment, localField: "_id", foreignField: "post", count: true }) commentCount?: VirtualRef<Comment, false, true>;
}
@Schema({ collection: "comments" })
class Comment extends Entity {
  @Prop(() => String, { required: true }) text!: string;
  @Prop(() => Types.ObjectId, { ref: () => Post, required: true }) post!: Ref<Post>;
  @Prop(() => Types.ObjectId, { ref: () => User, required: true }) author!: Ref<User>;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "blog" });
const Users = client.db().model(User);
const Tags = client.db().model(Tag);
const Posts = client.db().model(Post);
const Comments = client.db().model(Comment);
// ---cut---
// список для главной: автор и теги, без лишних полей
export const listPosts = async () => {
  const posts = await Posts.find()
    .sort({ title: 1 })
    .populate([
      { path: "author", select: { name: 1 } },
      { path: "tags", select: { label: 1 } },
    ])
    .plain();
  return posts.map((post) => ({
    title: post.title,
    author: post.author?.name,
    tags: post.tags.map((tag) => tag.label),
  }));
};

// страница поста: автор и комментарии с их авторами
export const readPost = async (title: string) => {
  const post = await Posts.findOne({ title })
    .populate(["author", { path: "comments", populate: { path: "author", select: { name: 1 } } }])
    .orFail()
    .plain();
  return {
    title: post.title,
    author: post.author?.name,
    comments: post.comments.map((comment) => `${comment.author?.name}: ${comment.text}`),
  };
};

console.log(await listPosts());
// → [{ title: "Bob's", author: "Bob", tags: [] }, { title: "Hello", author: "Alice", tags: ["db", "ts"] }, { title: "Second", author: "Alice", tags: ["ts"] }]
console.log(await readPost("Hello"));
// → { title: "Hello", author: "Alice", comments: ["Bob: c1", "Alice: c2"] }
```

<Callout type="migration">

В Typemo `limit` и `skip` в `populate` действуют на каждый исходный документ отдельно и точно: `limit: 2` значит «не больше двух документов на пост». Повторный вызов `.populate` для того же пути заменяет прежний, а неизвестный путь и неизвестная опция — ошибки, а не молчаливое пропускание.
