Чтобы понять, почему запрос медленный, спросите саму базу, как она его выполняет. [`.explain`](../reference/query/search-and-explain.mdx#explain) возвращает **план запроса** — какой индекс база выбрала и сколько документов ей пришлось прочитать. Чаще всего ответ один и тот же. Запрос читает всю коллекцию, потому что подходящего индекса нет.

Вокруг `explain` есть ещё три инструмента.

- [`.hint`](../reference/query/options.mdx#hint) закрепляет индекс.
- [`.comment`](../reference/query/options.mdx#comment) помечает запрос для журнала сервера.
- [`.timeoutMS`](../reference/query/options.mdx#timeoutms) ограничивает время.

Если вы впервые работаете с индексами MongoDB, запомните одно. Индекс — это отсортированная копия части полей, по которой база находит документы, не просматривая всю коллекцию. Без индекса по полю фильтра база проверяет каждый документ по очереди, и запрос замедляется вместе с ростом коллекции.

## Что понадобится

Клиент из руководства [Подключиться к базе](../connection/connect.mdx) и модель статьи из файла `articles/article.ts` с индексом по числу просмотров. Индекс создан [синхронизацией индексов](../collections/index-sync.mdx). Пока вы её не вызвали, индекса в базе нет, сколько бы раз он ни был описан в модели. В коллекции три статьи.

- «Typed queries» — 5 просмотров.
- «Mongo tips» — 50.
- «Cooking» — 500, текст «pasta».

```ts twoslash title="articles/article.ts"
import { Entity, Index, Prop, Schema } from "@venloc/typemo";

@Index({ views: 1 })
@Schema({ collection: "articles" })
export class Article extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  body!: string;

  @Prop(() => Number, { required: true })
  views!: number;
}
```

## Быстрый путь

Попросите план запроса и посмотрите на стадии. `IXSCAN` значит «по индексу», `COLLSCAN` — «вся коллекция». Функция [`explainIndexUsage`](../reference/testing/testing.mdx#explainindexusage) из пакета `@venloc/typemo/testing` сводит ответ базы в короткий отчёт.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
import { explainIndexUsage } from "@venloc/typemo/testing";
@Index({ views: 1 })
@Schema({ collection: "articles" })
class Article extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
  @Prop(() => Number, { required: true }) views!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Articles = client.db().model(Article);
// ---cut---
const byViews = await explainIndexUsage(Articles.find({ views: { $gt: 10 } }));
const byBody = await explainIndexUsage(Articles.find({ body: "pasta" }));
console.log(byViews.stages, byBody.stages);
// → ["FETCH", "IXSCAN"] ["COLLSCAN"]
```

Запрос по `views` идёт по индексу, а запрос по `body` читает все три статьи ради одной. Ниже разберём каждый шаг подробнее.

## Посмотреть план запроса

Допустим, список популярных статей открывается медленно. Вызовите [`.explain`](../reference/query/search-and-explain.mdx#explain) у того же запроса. Документов он не вернёт, зато покажет, как база собирается его выполнять. Ответ — это документ сервера, и его форма зависит от версии. Поэтому Typemo его не разбирает, и поля читаются без подсказок типов.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ views: 1 })
@Schema({ collection: "articles" })
class Article extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
  @Prop(() => Number, { required: true }) views!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Articles = client.db().model(Article);
// ---cut---
const plan = await Articles.find({ views: { $gt: 10 } }).explain();
console.log(plan.queryPlanner);
// → { …, winningPlan: { stage: "FETCH", inputStage: { stage: "IXSCAN", indexName: "views_1", … } } }
```

План читается изнутри наружу. Внутренняя стадия `IXSCAN` находит по индексу `views_1` подходящие ключи, а внешняя `FETCH` читает по этим ключам сами документы. `winningPlan` — это победивший план, база выбрала его из нескольких вариантов.

## Понять, сколько работы сделала база

Без выполнения запроса план говорит только о намерениях. Чтобы увидеть, сколько работы база сделала на самом деле, передайте `"executionStats"`. Запрос выполнится, и вы получите счётчики. Главное — сравнить `nReturned`, сколько документов вернулось, и `totalDocsExamined`, сколько база прочитала. У хорошего запроса они близки.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ views: 1 })
@Schema({ collection: "articles" })
class Article extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
  @Prop(() => Number, { required: true }) views!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Articles = client.db().model(Article);
// ---cut---
const good = await Articles.find({ views: 500 }).explain("executionStats");
console.log(good.executionStats);
// → { nReturned: 1, totalKeysExamined: 1, totalDocsExamined: 1, … }

const bad = await Articles.find({ body: "pasta" }).explain("executionStats");
console.log(bad.executionStats);
// → { nReturned: 1, totalKeysExamined: 0, totalDocsExamined: 3, … }
```

Во втором запросе база просмотрела все три статьи и вернула одну. На трёх документах этого не заметить, а на миллионе то же условие прочитает миллион документов ради одного. Признак беды — `totalDocsExamined` намного больше `nReturned`, а в плане стоит `COLLSCAN`. Лечится это индексом на поле фильтра, через [`@Index`](../reference/schemas/index-decorators.mdx) или опцию `index` у поля, и потом синхронизацией.

Третий уровень, `"allPlansExecution"`, добавляет статистику планов, которые база попробовала и отвергла. Он пригодится, когда база выбирает не тот индекс, которого вы ждали.

### Короткий отчёт вместо документа сервера

[`explainIndexUsage`](../reference/testing/testing.mdx#explainindexusage) запускает `explain("executionStats")` и возвращает разобранный отчёт. В нём стадии плана, использованные индексы, признак просмотра всей коллекции и счётчики. Функция живёт в отдельном входе пакета `@venloc/typemo/testing` и рассчитана на тесты, но в консоли или отладочном скрипте она так же удобна.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
import { explainIndexUsage } from "@venloc/typemo/testing";
@Index({ views: 1 })
@Schema({ collection: "articles" })
class Article extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
  @Prop(() => Number, { required: true }) views!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Articles = client.db().model(Article);
// ---cut---
const usage = await explainIndexUsage(Articles.find({ body: "pasta" }));
console.log(usage.collectionScan, usage.docsExamined, usage.docsReturned);
// → true 3 1
```

### Запрос, который читает только индекс

Самый дешёвый запрос вообще не читает документы, ведь всё нужное уже лежит в индексе. Так бывает, когда в ответе только индексированные поля. Выберите именно их и исключите `_id`, которого в индексе `views_1` нет.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
import { explainIndexUsage } from "@venloc/typemo/testing";
@Index({ views: 1 })
@Schema({ collection: "articles" })
class Article extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
  @Prop(() => Number, { required: true }) views!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Articles = client.db().model(Article);
// ---cut---
const covered = await explainIndexUsage(Articles.find({ views: { $gt: 10 } }).select({ views: 1, _id: 0 }));
console.log(covered.stages, covered.docsExamined, covered.covered);
// → ["PROJECTION_COVERED", "IXSCAN"] 0 true

const fetched = await explainIndexUsage(Articles.find({ views: { $gt: 10 } }));
console.log(fetched.stages, fetched.docsExamined, fetched.covered);
// → ["FETCH", "IXSCAN"] 2 false
```

`covered` равен `true`, только когда в плане нет `FETCH` и база не прочитала ни одного документа, то есть `docsExamined` равен нулю. Одного отсутствия `FETCH` мало. Запрос по `_id` идёт через `EXPRESS_IXSCAN` без стадии `FETCH`, но документ всё равно читает, поэтому `covered` у него `false`.

## Сортировка не по индексу

Индекс по `views` помогает и сортировке по `views`, ключи в нём уже лежат по порядку. А если сортировать по другому полю, базе придётся собрать подходящие документы в памяти и отсортировать их самой. В плане это видно как стадия `SORT` поверх остальных.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
import { explainIndexUsage } from "@venloc/typemo/testing";
@Index({ views: 1 })
@Schema({ collection: "articles" })
class Article extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
  @Prop(() => Number, { required: true }) views!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Articles = client.db().model(Article);
// ---cut---
const sameIndex = await explainIndexUsage(Articles.find({ views: { $gt: 10 } }).sort({ views: 1 }));
const otherField = await explainIndexUsage(Articles.find({ views: { $gt: 10 } }).sort({ title: 1 }));
console.log(sameIndex.stages, otherField.stages);
// → ["FETCH", "IXSCAN"] ["SORT", "FETCH", "IXSCAN"]
```

На больших выборках сортировка в памяти упирается в лимит памяти базы. Поэтому индекс лучше строить сразу под пару «фильтр и сортировка». Как задавать сортировку, рассказано в руководстве [Сортировка и страницы](./sorting-and-pages.mdx).

## Заставить базу использовать индекс

Обычно база выбирает индекс сама и делает это хорошо. Но бывает, что план показывает неудачный выбор, а перестроить индексы нельзя. Тогда назовите индекс явно через [`.hint`](../reference/query/options.mdx#hint) — по имени (`"views_1"`) или по ключам (`{ views: 1 }`).

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ views: 1 })
@Schema({ collection: "articles" })
class Article extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
  @Prop(() => Number, { required: true }) views!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Articles = client.db().model(Article);
// ---cut---
const byName = await Articles.find({ views: { $gt: 10 } }).hint("views_1").sort({ views: 1 }).plain();
const byKeys = await Articles.find({ views: { $gt: 10 } }).hint({ views: 1 }).sort({ views: 1 }).plain();
console.log(byName.length, byKeys.length);
// → 2 2
```

Подсказка останется в коде, даже когда данные изменятся и другой индекс станет лучше. Так что держите её на крайний случай. Если индекса с таким именем нет, база откажется выполнять запрос, и вы получите [`ServerError`](../reference/errors/server-errors.mdx#servererror) с текстом `hint provided does not correspond to an existing index (code 2 BadValue)`.

## Найти запрос в журнале сервера

Медленный запрос виден в журнале базы или в профилировщике, но непонятно, какой код его породил. [`.comment`](../reference/query/options.mdx#comment) прикрепляет к запросу текстовую метку. Результат не меняется, а метка видна в журнале и в `system.profile`. Пишите в ней место в коде, а не данные, ведь метка попадает в логи сервера.

```ts twoslash title="articles/articles.service.ts"
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ views: 1 })
@Schema({ collection: "articles" })
class Article extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
  @Prop(() => Number, { required: true }) views!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Articles = client.db().model(Article);
// ---cut---
export const listPopular = () =>
  Articles.find({ views: { $gt: 10 } }).comment("articles: popular list").sort({ views: -1 }).plain();

console.log((await listPopular()).length);
// → 2
```

## Ограничить время запроса

Один тяжёлый запрос не должен держать всё приложение. [`.timeoutMS`](../reference/query/options.mdx#timeoutms) ограничивает время всей операции на стороне клиента. Не уложились — драйвер прервёт запрос и бросит [`TimeoutError`](../reference/errors/server-errors.mdx#timeouterror). `0` значит «без ограничения», а отрицательное число даёт `QueryError`.

```ts twoslash
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
@Index({ views: 1 })
@Schema({ collection: "articles" })
class Article extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
  @Prop(() => Number, { required: true }) views!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Articles = client.db().model(Article);
// ---cut---
try {
  await Articles.find().timeoutMS(1).plain();
} catch (error) {
  console.log(String(error));
  // → "TimeoutError: operation timed out (timeoutMS): Server reported a timeout error"
}
```

Одна миллисекунда взята нарочно, чтобы запрос не успел. Текст после двоеточия зависит от того, где истёк срок. Если при выборе сервера, там будет `Timed out during server selection`, а класс ошибки и начало текста те же. В приложении ставьте срок, за который нормальный запрос успевает с запасом.

## Проверить индекс в тесте

Индекс легко потерять. Переименовали поле, поменяли порядок ключей в фильтре — и запрос молча стал читать всю коллекцию. [`expectIndexScan`](../reference/testing/testing.mdx#expectindexscan) из `@venloc/typemo/testing` превращает это в упавший тест. Он выполняет `explain` и бросает `IndexUsageError`, если запрос читает всю коллекцию или не использует ожидаемый индекс.

Можно задать имя индекса, предел числа просмотренных документов и `covered: true`, если запрос обязан читаться из индекса целиком. Обратная проверка, [`expectCollScan`](../reference/testing/testing.mdx#expectcollscan), нужна, когда индекса нет намеренно.

```ts twoslash title="articles/articles.index.test.ts"
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
import { expectIndexScan } from "@venloc/typemo/testing";
@Index({ views: 1 })
@Schema({ collection: "articles" })
class Article extends Entity {
  @Prop(() => String, { required: true }) title!: string;
  @Prop(() => String, { required: true }) body!: string;
  @Prop(() => Number, { required: true }) views!: number;
}
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "app" });
const Articles = client.db().model(Article);
// ---cut---
const usage = await expectIndexScan(Articles.find({ views: 500 }), { index: "views_1", maxDocsExamined: 1 });
console.log(usage.stages);
// → ["FETCH", "IXSCAN"]

try {
  await expectIndexScan(Articles.find({ body: "pasta" }));
} catch (error) {
  console.log(String(error));
  // → "IndexUsageError: the query is not served by an index: it scans the whole collection (COLLSCAN). plan: COLLSCAN; examined 3 documents, returned 1"
}
```

О тестировании приложения подробнее в руководстве [Тестировать приложение](../testing/testing-apps.mdx).

## Как выбрать

Спросите себя, **чего именно вы не знаете**.

- **Почему запрос медленный** — смотрите план, [`.explain`](../reference/query/search-and-explain.mdx#explain) с `"executionStats"`.
- **Какой код породил медленный запрос в журнале** — добавьте [`.comment`](../reference/query/options.mdx#comment).
- **План плохой, а индекс менять нельзя** — закрепите нужный индекс через [`.hint`](../reference/query/options.mdx#hint).
- **Запрос может зависнуть** — ограничьте его [`.timeoutMS`](../reference/query/options.mdx#timeoutms).

А чтобы индекс не потерялся при будущих правках, добавьте проверку в тест.

## Когда это не нужно

Если коллекция маленькая, на сотни документов, `COLLSCAN` не беда. База прочитает её быстрее, чем вы заметите, а индекс только замедлит запись. Оценивайте план на данных, похожих на настоящие, на пустой тестовой коллекции планы бывают другими.

И помните, что `.explain` говорит, как база выполняет запрос, но не почему он медленный **в приложении**. Там ещё есть сеть и построение результата. Для этого берите [события наблюдаемости](../observability/events.mdx).

## Если что-то пошло не так

**План показывает `COLLSCAN`, хотя индекс объявлен в модели.** Индекс описан в `@Index` или у поля, а план читает всю коллекцию. Обычно причина одна — Typemo сам индексы в базе не создаёт, это делает [синхронизация индексов](../collections/index-sync.mdx). На только что созданной коллекции запрос по `views` читает всю коллекцию, а после [`Model.syncIndexes`](../reference/collections/model-indexes.mdx#modelsyncindexes) идёт по `views_1`. Вызывайте синхронизацию при развёртывании.

**`.hint` с опечаткой в имени индекса.** Имя индекса компилятор не проверяет, индексы схемы ему не видны. Опечатка приводит к `ServerError` с текстом `hint provided does not correspond to an existing index (code 2 BadValue)`. Имя по умолчанию строится из ключей, индекс `{ views: 1 }` называется `views_1`. Сверьте имя с планом запроса или с `listIndexes`.

**`.explain` у запроса, который не `find`.** `.explain` есть у [`find`](../reference/query/reading.mdx#modelfind), [`findOne`](../reference/query/reading.mdx#modelfindone) и [`findById`](../reference/query/reading.mdx#modelfindbyid). У запросов «найти и изменить» метод не компилируется. Для агрегаций есть свой `explain` у самой агрегации, [`Pipeline`](../reference/aggregation/pipeline.mdx).

**`timeoutMS` поставили на весь обработчик, а не на запрос.** Опция ограничивает **одну операцию**, а не обработчик целиком. Если в обработчике несколько запросов, каждому нужен свой `timeoutMS`, а общий срок задаёт код обработчика.

## Полный пример

Здесь всё вместе — запрос с меткой и сроком, разбор плана и проверка индекса. Код, которого нет в Typemo и который пишете вы, помечен `__…__`.

```ts twoslash title="articles/articles.service.ts"
import { Entity, Index, Prop, Schema, TypemoClient } from "@venloc/typemo";
import { expectIndexScan, explainIndexUsage } from "@venloc/typemo/testing";

@Index({ views: 1 })
@Schema({ collection: "articles" })
class Article extends Entity {
  @Prop(() => String, { required: true })
  title!: string;

  @Prop(() => String, { required: true })
  body!: string;

  @Prop(() => Number, { required: true })
  views!: number;
}

// код читателя: журнал приложения
declare const __log__: (message: string) => void;

export const createArticles = (client: TypemoClient) => {
  const Articles = client.db().model(Article);

  // рабочий запрос: метка для журнала сервера и предел времени
  const popular = () =>
    Articles.find({ views: { $gt: 10 } })
      .comment("articles: popular list")
      .timeoutMS(2_000)
      .sort({ views: -1 })
      .plain();

  // диагностика: читает ли запрос всю коллекцию
  const diagnose = async () => {
    const usage = await explainIndexUsage(Articles.find({ views: { $gt: 10 } }));
    __log__(`stages: ${usage.stages.join(" > ")}; examined ${usage.docsExamined}, returned ${usage.docsReturned}`);
  };

  // проверка для теста: запрос обязан идти по индексу
  const assertIndexed = () => expectIndexScan(Articles.find({ views: { $gt: 10 } }), { index: "views_1" });

  return { popular, diagnose, assertIndexed };
};
```

В Mongoose у запроса тоже есть `explain`, `hint`, `comment` и `maxTimeMS`. Но срок там задавался серверным `maxTimeMS`, а результат `explain` никто не разбирал. В Typemo срок — клиентский [`.timeoutMS`](../reference/query/options.mdx#timeoutms) на всю операцию, а разбор плана и проверка индекса в тесте вынесены в `@venloc/typemo/testing`.

</Callout>
