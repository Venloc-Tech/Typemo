Чтобы найти документы по словам, а не по точному значению, нужен **полнотекстовый поиск**. Условие [`$text`](../reference/query/filter-operators.mdx#text) ищет слова в полях с текстовым индексом, учитывает формы слов («query» найдёт «queries») и умеет считать оценку релевантности.

Для поиска по смыслу, когда документы похожи по значению, даже если слова разные, есть **векторный поиск**. Он сравнивает числовые векторы текстов (эмбеддинги) и работает только в MongoDB Atlas и в локальной среде Atlas.

Если вы впервые работаете с индексами MongoDB, вот что важно. Индекс — это структура, которую база строит заранее, чтобы искать быстро. Для `$text` нужен особый вид, **текстовый индекс**. Без него запрос не станет медленным, он просто упадёт с ошибкой.

## Что понадобится [#prerequisites]

Клиент из руководства [Подключиться к базе](../connection/connect.mdx) и модель статьи из файла `articles/article.ts`. Индексы созданы через [`init()`](../reference/connection/connection.mdx#connection.init). Сама модель индексы в базе не создаёт, это делает [синхронизация](../collections/index-sync.mdx). - «Typed queries» — в тексте «queries in mongodb», 5 просмотров.

- «Cooking» — текст «pasta», 500 просмотров.

## Быстрый путь [#quick-start]

Найдите статьи со словами и получите оценку релевантности каждой. Текстовый индекс по `title` и `body` описан декоратором [`@Index`](../reference/schemas/index-decorators.mdx), а [`.textScore`](../reference/query/search-and-explain.mdx#text-score) добавляет к строкам поле `score`.

<Snippet id="queries/text-and-vector-search/quick-start" twoslash />

Оценка зависит от данных и версии сервера. Сравнивайте значения между собой, а не с числами из документации. Ниже разберём поиск по шагам.

## Найти документы по словам [#text-search]

Допустим, на странице поиска пользователь вводит слова, а вам нужны статьи, где они встречаются. [`$text`](../reference/query/filter-operators.mdx#text) принимает строку `$search` и ищет **любое** из слов. Строка `"typed pasta"` найдёт и статьи про типы, и статью про пасту. Слова сравниваются по основе, поэтому «query» находит «queries».

<Snippet id="queries/text-and-vector-search/text-search" title="articles/search.service.ts" twoslash />

Поиск можно сочетать с обычными условиями, они действуют вместе. Например, так ищут только среди статей, у которых не меньше десяти просмотров.

<Snippet id="queries/text-and-vector-search/text-search-2" twoslash />

### Исключить слово и найти фразу [#exclude-word-and-phrase]

Строка поиска понимает две особые записи. Слово с минусом исключает документы, где оно есть, а фраза в двойных кавычках ищется целиком.

<Snippet id="queries/text-and-vector-search/exclude-word-and-phrase" twoslash />

Чтобы учитывать регистр, добавьте `$caseSensitive: true`, и тогда `"TYPED"` не найдёт слово «typed». Язык для основ слов задаёт `$language`. Неизвестный язык сервер отклонит с `ServerError: unsupported language: "xx" for text index version 3 (code 2 BadValue)`.

## Отсортировать по релевантности [#sort-by-relevance]

Сам `$text` не говорит, какая статья подошла лучше. [`.textScore`](../reference/query/search-and-explain.mdx#text-score) добавляет к каждой строке число — оценку, и по ней база упорядочивает строки. Поле называется `score`, другое имя можно передать первым аргументом. Оно есть и в строке, и в её типе, а без вызова `.textScore` его нет. Даже если вы выбираете поля через `.select`, поле оценки добавится само.

<Snippet id="queries/text-and-vector-search/sort-by-relevance" twoslash />

Чтобы лучшие статьи шли первыми, передайте опцию `{ sort: true }`. Typemo отправит сортировку `{ score: { $meta: "textScore" } }`, и база сама упорядочит строки по убыванию оценки.

<Snippet id="queries/text-and-vector-search/sort-by-relevance-2" twoslash />

Сортировка идёт на сервере, поэтому [`.limit`](../reference/query/reading.mdx#limit) после неё отсекает худшие строки, а не случайные. `.textScore("score", { sort: true }).limit(1)` вернёт одну статью «Typed queries», у неё оценка выше. Без сортировки по оценке порядок строк не определён, и лимит взял бы любую из двух.

Имя поля оценки знает и [`.sort`](../reference/query/reading.mdx#sort). `.sort({ score: -1 })` делает то же, что `{ sort: true }`, но ставит оценку на нужное место среди ключей сортировки. Так статьи с равной оценкой можно дополнительно упорядочить по другому полю.

<Snippet id="queries/text-and-vector-search/sort-by-relevance-3" twoslash />

Оценку можно сортировать только по убыванию. База ранжирует совпадения от лучшего, и обратного порядка у неё нет. Поэтому `.sort({ score: 1 })` не компилируется, а в коде без типов даёт `QueryError`, подробнее в разделе [Если что-то пошло не так](#troubleshooting). Опция `{ sort: true }` ставит оценку после ключей, которые вы уже передали в `.sort`. `.sort({ views: -1 }).textScore("score", { sort: true })` сначала упорядочит по просмотрам.

## Настроить текстовый индекс [#configure-text-index]

Текстовый индекс описывается в модели. В коллекции он может быть **только один**, зато может охватывать несколько полей. Описать его можно двумя способами — декоратором [`@Index`](../reference/schemas/index-decorators.mdx) с видом `"text"` для каждого поля, как выше, или опцией `text: true` у самого поля. Поля с этой опцией объединяются в один индекс.

<Snippet id="queries/text-and-vector-search/configure-text-index" title="articles/article.ts" twoslash />

Оба поля попадут в индекс `title_text_body_text`. Повторный [`init()`](../reference/connection/connection.mdx#connection.init) на такой модели проходит спокойно, индекс уже есть, `inSync` равен `true`, а список `created` пуст. Два разных `@Index` с текстовыми ключами — ошибка `ConfigurationError: Two: a collection has at most one text index; "text: true" fields are merged into one, so remove the extra @Index text (found title_text, body_text)`.

Если одно поле важнее другого, задайте **веса** (`weights`) в опциях `@Index`. Слова из поля с большим весом сильнее влияют на оценку. Ниже заголовок весит в десять раз больше текста. В коллекции две статьи, одна с заголовком «typed» и текстом «other words», другая с заголовком «other» и текстом «typed typed typed». Слово «typed» в заголовке даёт оценку 10, а три вхождения в тексте — 1,75.

<Snippet id="queries/text-and-vector-search/configure-text-index-2" twoslash />

## Поиск по смыслу и Atlas Search [#vector-and-atlas-search]

Текстовый индекс ищет по словам и их формам. «Автомобиль» по запросу «машина» он не найдёт. Для этого в MongoDB Atlas есть две возможности.

- **Atlas Search**, стадия `$search` — нечёткий поиск, подсветка, фасеты.
- **Векторный поиск**, стадия `$vectorSearch` — ближайшие по смыслу документы среди векторов.

Обе работают только в Atlas или в локальной среде Atlas, а не на обычном сервере MongoDB. И строятся они не в запросе `find`, а в [агрегации](../aggregation/search.mdx).

Индексы для них называются **поисковыми** и описываются декоратором [`@SearchIndex`](../reference/schemas/index-decorators.mdx). Декоратор только записывает описание в модель, а создаёт индекс синхронизация, [`Model.syncSearchIndexes`](../reference/collections/model-indexes.mdx#model.sync-search-indexes). Вектор хранится в поле типа `Vector`, описанном через `Spec.vector` с типом чисел и размерностью.

<Snippet id="queries/text-and-vector-search/vector-and-atlas-search" title="articles/document.ts" twoslash />

Сам запрос — это стадия `vectorSearch` в конвейере агрегации. Вы называете индекс, поле с векторами, вектор запроса и число результатов. Вектор запроса строит модель эмбеддингов, то есть ваш код.

<Snippet id="queries/text-and-vector-search/vector-and-atlas-search-2" title="articles/similar.service.ts" twoslash />

<Callout type="warning">

Векторный поиск и `$search` в этой документации **не запускались**, тестовый сервер — не Atlas. На обычном сервере они падают с `ServerError` и текстом `Using $search and $vectorSearch aggregation stages requires additional configuration. (code 31082 SearchNotEnabled)`. Полный текст сервера с советом подключиться к Atlas лежит в поле `serverMessage`.

С [`Model.syncSearchIndexes`](../reference/collections/model-indexes.mdx#model.sync-search-indexes) то же самое — `Using Atlas Search Database Commands and the $listSearchIndexes aggregation stage requires additional configuration. (code 31082 SearchNotEnabled)`. Код выше проверен компилятором, а его поведение на Atlas описано по коду продукта. Все параметры стадий есть в справочнике [Стадии](../reference/aggregation/stages.mdx).

</Callout>

## Как выбрать [#how-to-choose]

Спросите себя, **совпадают ли слова**.

- **Пользователь ищет те же слова, что в тексте**, и хватает основ слов и оценки релевантности — берите `$text`. Он работает на любом сервере MongoDB, и ему нужен только текстовый индекс.
- **Нужен нечёткий поиск, подсветка совпадений или фасеты** — Atlas Search (`$search`).
- **Нужно искать по смыслу, а не по словам** — векторный поиск.

Последние два доступны только в Atlas.

## Когда это не нужно [#when-not-to-use]

Для поиска точного значения вроде артикула или почты не нужен ни один из видов. Обычный фильтр по полю с обычным индексом быстрее и надёжнее. Префиксы и подстроки текстовый индекс тоже не ищет. Он работает с целыми словами, и «pas» не найдёт «pasta». Для фильтров вроде «начинается с» берите `$regex` и индекс, об этом руководство [Фильтры](./filters.mdx).

## Если что-то пошло не так [#troubleshooting]

**`text index required for $text query`.** Вы искали через `$text` по коллекции без текстового индекса. Запрос падает с `ServerError` и текстом `text index required for $text query (code 27 IndexNotFound)` — без индекса поиск не выполняется вовсе. Обычно индекс либо не описан в модели, либо описан, но не создан. Индексы нужно создать при развёртывании. [`init()`](../reference/connection/connection.mdx#connection.init) создаёт недостающие, а [`Model.syncIndexes`](../reference/collections/model-indexes.mdx#model.sync-indexes) приводит индексы модели к описанию.

**`query requires text score metadata`.** Вы вызвали `.textScore()`, а в фильтре нет `$text`. Оценку считает текстовый поиск, и без него считать нечего — `ServerError: query requires text score metadata, but it is not available (code 40218 Location40218)`. Компилятор этого не проверяет. Уберите `.textScore()` или добавьте `$text`.

<Snippet id="queries/text-and-vector-search/troubleshooting" twoslash />

**Оценка по возрастанию.** Вы хотели показать сначала худшие совпадения и написали `.sort({ score: 1 })`. Компилятор такую сортировку не пропустит, у поля оценки направление только `-1`. Если сортировка собрана без типов, запрос не построится и бросит `QueryError: sort: "score" is the text score, which sorts from the best match only: use -1 (or textScore("score", { sort: true }))`.

Дело в самой базе. Она ранжирует совпадения от лучшего к худшему, и порядка «по возрастанию оценки» у `$meta: "textScore"` нет. Сортируйте по убыванию, а обратный порядок получите, перевернув массив в коде.

<Snippet id="queries/text-and-vector-search/troubleshooting-2" twoslash />
