Иногда несколько полей естественно живут вместе: адрес доставки состоит из города и улицы, а строка заказа — из товара и количества. В MongoDB такую группу хранят **внутри** документа-владельца, а не в отдельной коллекции. Typemo описывает её отдельным классом и даёт два вида: **вложенный объект** (`@Schema({ nested: true })`), у которого нет собственной идентичности, и **поддокумент** (обычный `@Schema()`, наследующий [`Entity`](../reference/schemas/base-classes.mdx#entity)), у которого есть свой `_id`.

Выбор влияет на то, как вы будете находить и менять такую группу. Адрес меняют целиком или по полям, и искать «адрес номер пять» не нужно. А строку заказа нужно найти и убрать по идентификатору, для этого у неё должен быть `_id`. Как изменять такие объекты в загруженном документе, описано в руководстве [Работать с вложенными объектами](../documents/subdocuments.mdx); здесь мы объявляем схему.

## Что предполагается

Модель описана по руководству [Описать модель](./define-model.mdx). Примеры строят заказ интернет-магазина и добавляют в него адрес и строки.

## Быстрый путь

Вложенный объект — класс с [`@Schema({ nested: true })`](../reference/schemas/schema.mdx#nested), а поле в документе-владельце объявляется этим классом:

```ts twoslash title="orders/order.ts"
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
@Schema({ nested: true })
class Address {
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => String) street?: string;
}

@Schema({ collection: "orders" })
export class Order extends Entity {
  @Prop(() => String, { required: true })
  customer!: string;

  @Prop(() => Address)
  shipTo?: Address;
}

const Orders = client.connection.model(Order);
const order = await Orders.create({ customer: "ann", shipTo: { city: "Oslo" } });
console.log(order.$toPlain().shipTo);
// → { city: "Oslo" }
```

В базе адрес лежит внутри заказа как обычный вложенный документ. Значения поля передаются обычным объектом, экземпляр класса создавать не нужно. Остальная страница разбирает проверки, поддокументы с `_id` и запросы по вложенным путям.

## Проверить вложенные поля

Вложенный класс — полноценная схема: его поля имеют типы, `required` и остальные опции, как и у документа. Путь к полю в ошибке включает имя поля-владельца, поэтому видно, где именно проблема. Поле с неизвестным именем и `null` на поле без `nullable` тоже отвергаются.

```ts twoslash
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
@Schema({ nested: true })
class Address {
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => String) street?: string;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => Address) shipTo?: Address;
}
const Orders = client.connection.model(Order);
// ---cut---
try {
  await Orders.create({ customer: "ann", shipTo: {} as never });
} catch (error) {
  console.log((error as Error).message);
}
// → Validation failed: "shipTo.city": the field is required [required]
try {
  await Orders.create({ customer: "ann", shipTo: { city: "x", zip: "1" } as never });
} catch (error) {
  console.log((error as Error).message);
}
// → Cast to document failed at path "shipTo.zip" for "1" (string): not a field of Address [unknown-key]
try {
  await Orders.create({ customer: "ann", shipTo: null as never });
} catch (error) {
  console.log((error as Error).message);
}
// → Cast to Address failed at path "shipTo" for null: null is not allowed on a path that is not nullable [null]
```

Сам объект необязателен, пока вы не поставите `required: true` на поле-владельце. Если объект задан, его обязательные поля обязаны быть на месте: адрес без города не сохранится, а заказ без адреса сохранится.

## Дать вложенной группе собственный `_id`

Строка заказа отличается от адреса тем, что её нужно находить и менять по идентификатору: убрать одну строку, изменить количество в ней. Для этого класс не помечают `nested: true` и наследуют `Entity`: тогда Typemo сам создаёт `_id` каждого поддокумента.

```ts twoslash
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
@Schema({ nested: true })
class Address {
  @Prop(() => String, { required: true }) city!: string;
}
// ---cut---
@Schema()
class Line extends Entity { // [!code highlight]
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true, min: 1 }) qty!: number;
}

@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => Address) shipTo?: Address;
  @Prop(() => Line) gift?: Line; // [!code ++]
}

const Orders = client.connection.model(Order);
const order = await Orders.create({ customer: "ann", gift: { sku: "G1", qty: 1 } });
console.log(order.gift?._id.constructor.name);
// → ObjectId
```

Вы можете передать `_id` поддокумента сами: тогда он сохранится как есть. `_id` у поддокумента есть только тогда, когда класс наследует `Entity` или сам объявляет это поле: обычный `@Schema()` без `Entity` `_id` не получает, а `@Schema({ nested: true })` не может его иметь вовсе. Отличие такого класса от вложенного объекта в другом: у него могут быть собственные хуки, а вложенный объект хуков, дискриминаторов и опций коллекции не имеет. Как самостоятельная модель класс без `_id` не собирается (`a model needs an _id field`). У класса с `nested: true` объявлять `_id` запрещено, в том числе унаследовав `Entity`: это `ConfigurationError` (`NestedId: a nested object (no _id, no own hooks) — it declares _id`), а также нельзя использовать его как модель и задавать опции коллекции, такие как `collection`.

## Искать и обновлять по вложенному пути

Путь к вложенному полю пишется через точку. Он работает в фильтрах и в операторах обновления, и Typemo проверяет и сам путь, и тип значения по нему: опечатка в имени или значение не того типа не дойдут до базы.

```ts twoslash
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
@Schema({ nested: true })
class Address {
  @Prop(() => String, { required: true }) city!: string;
}
@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => Address) shipTo?: Address;
}
const Orders = client.connection.model(Order);
await Orders.create({ customer: "ann", shipTo: { city: "Oslo" } });
// ---cut---
await Orders.updateOne({ customer: "ann" }, { $set: { "shipTo.city": "Rome" } });
const rows = await Orders.find({ "shipTo.city": "Rome" }).plain();
console.log(rows.length);
// → 1
try {
  await Orders.updateOne({ customer: "ann" }, { $set: { "shipTo.city": 5 } } as never);
} catch (error) {
  console.log((error as Error).message);
}
// → Cast to string failed at path "$set.shipTo.city" for 5 (number): expected a string [type]
```

Замена вложенного объекта целиком тоже проверяется полностью: `$set: { shipTo: { street: "S" } }` не пройдёт, потому что в новом объекте нет обязательного `city`. Изменение одного поля по пути `shipTo.city` не затрагивает соседние поля, поэтому оно безопаснее замены объекта, когда с документом работают несколько клиентов.

## Как выбрать

Задайте себе один вопрос: **понадобится ли обратиться к этой группе полей отдельно, по идентификатору?** Если нет (адрес, имя и фамилия, координаты), берите вложенный объект с `nested: true`: он проще и не хранит лишнего `_id`. Если да (строка заказа, комментарий, вложение), наследуйте `Entity`: идентификатор нужен, чтобы найти строку и убрать именно её. Если группа полей встроена в много разных документов и нужна отдельная коллекция или запросы по ней как по самостоятельной сущности, это не вложенный объект, а отдельная модель со ссылкой: [Ссылки на другие модели](./references.mdx).

## Когда это не нужно

Если ключи внутри объекта заранее неизвестны (оценки по предметам, настройки по названиям), вложенный класс не подходит: используйте [`Spec.map`](./maps.mdx). Список однотипных групп — это массив поддокументов: [Массивы](./arrays.mdx). Данные, которые растут без границ (комментарии к популярному посту), не стоит встраивать: документ MongoDB ограничен 16 МБ, и лучше вынести их в отдельную коллекцию.

## Частые ошибки

### Нельзя объявить `_id` во вложенном объекте

Класс с `nested: true` не может содержать `_id`. Модель не собирается: `NestedId: a nested object (no _id, no own hooks) — it declares _id`. Причина в определении: вложенный объект — часть документа без собственной идентичности. Уберите `nested: true`, если идентификатор нужен.

### Класс без `@Schema` вместо поддокумента

Поле объявлено классом, но сам класс не помечен: сборка модели бросает `ConfigurationError` с советом `decorate the class with @Schema()`. Каждый класс, который используется как тип поля, должен быть схемой.

### Заменили объект целиком и потеряли соседние поля

`$set: { shipTo: { city: "Rome" } }` заменяет весь адрес, и улица исчезнет. Если нужно поменять одно поле, пишите путь: `"shipTo.city"`.

## Полный пример

Один файл собирает заказ с вложенным адресом и поддокументом с `_id`. Код читателя, которого нет в Typemo, помечен `__…__`.

```ts twoslash title="orders/orders.service.ts"
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
// вложенный объект: адрес без собственного _id
@Schema({ nested: true })
class Address {
  @Prop(() => String, { required: true }) city!: string;
  @Prop(() => String) street?: string;
}

// поддокумент: у строки заказа есть свой _id
@Schema()
class Line extends Entity {
  @Prop(() => String, { required: true }) sku!: string;
  @Prop(() => Number, { required: true, min: 1 }) qty!: number;
}

@Schema({ collection: "orders" })
class Order extends Entity {
  @Prop(() => String, { required: true }) customer!: string;
  @Prop(() => Address, { required: true }) shipTo!: Address;
  @Prop(() => Line) gift?: Line;
}

// код читателя: ошибка на границе приложения
class __BadRequest__ extends Error {}

// создание заказа: ошибки вложенных полей приходят с путём
export const placeOrder = async (customer: string, city: string) => {
  const Orders = client.connection.model(Order);
  try {
    return await Orders.create({ customer, shipTo: { city }, gift: { sku: "G1", qty: 1 } });
  } catch (error) {
    throw new __BadRequest__((error as Error).message);
  }
};

// смена города: путь к вложенному полю, соседние поля не трогаем
export const moveOrder = async (customer: string, city: string) => {
  const Orders = client.connection.model(Order);
  await Orders.updateOne({ customer }, { $set: { "shipTo.city": city } });
};

await placeOrder("zoe", "Oslo");
await moveOrder("zoe", "Rome");
const saved = await client.connection.model(Order).findOne({ customer: "zoe" }).plain();
console.log(saved?.shipTo.city, typeof saved?.gift?._id);
// → Rome string
```

<Callout type="migration">

В Mongoose вложенный объект описывают вложенным `{}` в схеме или отдельной схемой, а `_id` у поддокумента появляется по умолчанию и отключается опцией `_id: false`. В Typemo наоборот: `_id` есть только у класса, который наследует `Entity`, а вложенный объект без идентичности объявляется явно через `@Schema({ nested: true })`. Неизвестные поля вложенного объекта не отбрасываются молча, а вызывают `CastError`.

</Callout>
