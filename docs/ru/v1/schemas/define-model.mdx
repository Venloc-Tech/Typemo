Модель в Typemo начинается с обычного класса. [`@Schema`](../reference/schemas/schema.mdx#schema) превращает его в описание документа, [`@Prop`](../reference/schemas/prop.mdx#prop) объявляет поля, а [`connection.model`](../reference/connection/connection.mdx#connectionmodel) выдаёт по классу **модель** — объект, через который вы читаете и пишете коллекцию.

**Схема** — это описание документа. Какие у него поля, какого они типа и какие правила проверяют значения. Отдельного объекта вроде `new Schema({...})` здесь нет. Typemo собирает схему из самого класса, а TypeScript берёт оттуда же тип документа, так что одно и то же дважды описывать не придётся.

Если MongoDB для вас в новинку, хватит одного факта. Сервер хранит **документы** (объекты с полями) в **коллекциях** и по умолчанию не требует, чтобы у документов одной коллекции были одинаковые поля. Схема Typemo добавляет эту строгость на стороне приложения.

## Что понадобится

Подключённый клиент из руководства [Подключиться к базе](../connection/connect.mdx) и `tsconfig`, настроенный по [Установке и настройке](../getting-started/installation.mdx). В примерах — регистрация пользователей на сайте.

## Быстрый путь

Один класс, два декоратора и одна строка, чтобы получить модель.

```ts twoslash title="users/user.ts"
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true })
  login!: string;
}

const Users = client.connection.model(User);
const user = await Users.create({ login: "ann" });
console.log(user.login, user._id.constructor.name);
// → ann ObjectId
```

`User` наследует [`Entity`](../reference/schemas/base-classes.mdx#entity), и от него получает поле `_id`, которое MongoDB требует у каждого документа. Ниже разберём каждую часть — поля, тип поля, идентификатор, имя коллекции и получение модели.

## Объявить поле

Поле — это пара. Свойство класса с типом TypeScript и декоратор `@Prop` над ним. Первый аргумент `@Prop` — **функция, которая возвращает тип поля во время работы**, например `() => String`, `() => Number`, `() => Date`. Второй — необязательные опции вроде [`required`](../reference/schemas/prop.mdx#required), [`default`](../reference/schemas/prop.mdx#default) и [`min`](../reference/schemas/prop.mdx#min).

```ts twoslash title="users/user.ts"
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
@Schema({ collection: "users" })
export class User extends Entity {
  @Prop(() => String, { required: true })
  login!: string;

  @Prop(() => String) // [!code ++]
  bio?: string; // [!code ++]

  @Prop(() => Date) // [!code ++]
  birthday?: Date; // [!code ++]
}
```

Зачем ещё и `() => String`, если у свойства уже есть тип `string`? Типы TypeScript исчезают при компиляции, а Typemo во время работы должен знать, как приводить и проверять значение. Можно было бы взять метаданные компилятора `design:type`, но они не отличают `int32` от `double`, не знают тип элемента массива и путают `null` с отсутствием значения. Поэтому Typemo их не читает, и ни `emitDecoratorMetadata`, ни `reflect-metadata` вам не нужны.

Тип задаётся явно на каждом поле. Стрелка нужна, чтобы класс, объявленный ниже по файлу или в другом модуле, успел появиться к моменту сборки схемы. Все типы и их отличия собраны в руководстве [Типы полей](./field-types.mdx).

Тип во время работы и тип свойства обязаны совпадать, и компилятор это проверяет. Напишете `() => Number` над строковым свойством — код не скомпилируется.

```ts twoslash title="users/user.ts"
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
// @errors: 1240
@Schema()
class Wrong extends Entity {
  @Prop(() => Number)
  login!: string;
}
```

В сообщении компилятора будет текст `@Prop "login": the runtime type () => X does not match the field type`. В коде без типов сработает та же проверка, только при получении модели, и бросит [`ConfigurationError`](../reference/errors/configuration-errors.mdx#configurationerror).

## Получить модель

[`connection.model`](../reference/connection/connection.mdx#connectionmodel) принимает класс и возвращает модель. Для одного класса на одном подключении это всегда один и тот же объект. Так что вызывайте `model` где удобно, хранить результат в глобальной переменной не нужно. При первом вызове Typemo собирает и проверяет схему, и ошибка в описании полей всплывёт здесь, а не при первой записи.

```ts twoslash title="users/users.service.ts"
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) login!: string;
}
// ---cut---
export const registerUser = async (login: string) => {
  const Users = client.connection.model(User);
  return Users.create({ login });
};

console.log(client.connection.model(User) === client.connection.model(User));
// → true
```

Без `@Schema` класс модель не получит. Typemo не угадывает, что вы имели в виду, и говорит об этом сразу.

```ts twoslash
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
class Plain {
  login?: string;
}
try {
  client.connection.model(Plain);
} catch (error) {
  console.log((error as Error).message);
}
// → Plain: not a schema; decorate the class with @Schema()
```

## Идентификатор документа

Каждому документу MongoDB нужен уникальный `_id`. Проще всего наследовать [`Entity`](../reference/schemas/base-classes.mdx#entity). Он объявляет `_id` типа `ObjectId`, и если вы не передали значение, библиотека создаст его сама. Тип `_id` в `Entity` устроен так, что при создании его можно не передавать, а после создания менять нельзя.

Если идентификатором должно быть ваше значение, например строка-слаг, наследуйте вместо `Entity` класс [`EntityWithId`](../reference/schemas/base-classes.mdx#entitywithid) и передайте ему тип `_id`.

```ts twoslash title="pages/page.ts"
import { EntityWithId, Prop, Schema, TypemoClient } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
@Schema({ collection: "pages" })
class Page extends EntityWithId(() => String) { // [!code highlight]
  @Prop(() => String, { required: true })
  title!: string;
}

const Pages = client.connection.model(Page);
const page = await Pages.create({ _id: "home", title: "Home" });
console.log(page._id);
// → home
```

Без `default` такой идентификатор обязателен при создании. С `default` (`EntityWithId(() => Types.UUID, { default: () => new UUID() })`) он создаётся сам. Строковые, числовые и `UUID`-идентификаторы, ссылки на такие модели и `$out` в них разобраны в руководстве [Задать свой тип _id](./custom-ids.mdx).

Модель без `_id` не соберётся — `NoId: a model needs an _id field (extend Entity or declare @Prop _id)`. Метки времени и версию документа добавляют другие базовые классы, [`Timestamped`](../reference/schemas/base-classes.mdx#timestamped) и [`Versioned`](../reference/schemas/base-classes.mdx#versioned). О них — в руководстве [Метки времени и версии](./timestamps-and-versions.mdx).

## Задать имя коллекции

Опция [`collection`](../reference/schemas/schema.mdx#collection) называет коллекцию в базе. Без неё Typemo берёт имя класса в нижнем регистре и ставит во множественное число по английским правилам, так что `UserProfile` окажется в коллекции `userprofiles`. Для новой коллекции этого хватит. А вот существующую коллекцию называйте явно, иначе модель молча начнёт работать с другой.

```ts twoslash
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
@Schema()
class UserProfile extends Entity {}

@Schema({ collection: "profiles" })
class Profile extends Entity {}

console.log(client.connection.model(UserProfile).collectionName);
// → userprofiles
console.log(client.connection.model(Profile).collectionName);
// → profiles
```

Правила именования и то, как поменять их для всего проекта, описаны в руководстве [Имена коллекций](./collection-names.mdx).

## Что делает схема при записи

Схема строгая всегда. Поле, которого нет в классе, не записывается и не теряется молча, а вызывает [`CastError`](../reference/errors/data-errors.mdx#casterror) с причиной `unknown-key`. Значение не того типа — тоже ошибка, а не тихое преобразование. `"5"` числом не станет.

```ts twoslash
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true }) login!: string;
}
const Users = client.connection.model(User);
// ---cut---
try {
  await Users.create({ login: "bob", nick: "b" } as never);
} catch (error) {
  console.log((error as Error).message);
}
// → Cast to User failed at path "nick" for "b" (string): not a field of User [unknown-key]
```

Опечатка в имени поля или лишнее поле из внешнего запроса до базы не доберутся. `as never` здесь лишь заставляет компилятор пропустить заведомо неверный вызов. В обычном коде [`create`](../reference/writes/writes.mdx#create) остановит такое ещё при компиляции. Опции вроде `strict` из Mongoose не нужны, ослабить строгость нельзя.

## Как выбрать

Спросите себя — **есть ли у документа естественный уникальный ключ, который вы всё равно хотите хранить как `_id`?**

- **Нет**, как у пользователя, заказа или поста — наследуйте `Entity`. `ObjectId` создаётся сам и хорошо подходит для индекса.
- **Есть**, как слаг страницы, код валюты или внешний идентификатор — наследуйте `EntityWithId` с нужным типом. Отдельный ключ с уникальным индексом занимал бы место и требовал второго поиска.

## Когда это не нужно

Класс с `@Schema` нужен только для данных, которые лежат в базе. Значение, которое вычисляется из других полей, через `@Prop` не объявляют, для него есть геттер (см. [Виртуальные поля](./virtuals.mdx)). Настройки подключения и клиента живут в [`TypemoClient`](../reference/connection/typemo-client.mdx), а не в схеме. А если надо просто проверить произвольные данные без коллекции, возьмите [`Model.validate`](../reference/documents/model-document-methods.mdx#modelvalidate).

## Если что-то пошло не так

**Класс без `@Schema` не становится моделью.** Поле объявлено, `@Prop` стоит, а `connection.model(Plain)` бросает `ConfigurationError: Plain: not a schema; decorate the class with @Schema()`. `@Prop` только записывает поле в описание класса, а собирает схему и помечает класс именно `@Schema`. Добавьте декоратор — `@Schema() class Plain extends Entity {}`.

**Поле без `@Prop` не входит в схему.** Для Typemo такого свойства не существует. Его нет ни в проверках, ни в фильтрах, ни в записи. TypeScript о нём знает, ведь оно есть в классе, поэтому код **компилируется**.

Но молча Typemo это не оставит. Если свойство действительно появляется у экземпляра, сборка модели бросит [`ConfigurationError`](../reference/errors/configuration-errors.mdx#configurationerror) и назовёт его. Поле без инициализатора появляется при `useDefineForClassFields: true`, а при `target: "ESNext"` этот флаг включён по умолчанию. Свойство с инициализатором (`cache = new Map()`) или присвоенное в конструкторе ловится при любом значении флага.

```ts twoslash
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true })
  login!: string;

  nick?: string; // забыли @Prop
}
try {
  client.connection.model(User);
} catch (error) {
  console.log((error as Error).message);
}
// → User: property "nick" has no @Prop, so it is not a field of the schema (never stored, cast or loaded); decorate it with @Prop, declare it with "declare", or make it a getter or a method
```

Добавьте над свойством `@Prop(() => String)`, и оно станет полем схемы. Методы, геттеры, свойства через `declare` и неперечисляемые свойства проверка не трогает. Если же поле без инициализатора у экземпляра не появилось (`useDefineForClassFields: false`), сборка пройдёт, а первая запись с таким ключом даст `CastError` — `Cast to User failed at path "nick" for "a" (string): not a field of User [unknown-key]`.

**Значение по умолчанию прямо в объявлении поля.** `login: string = "guest"` в теле класса значением по умолчанию не станет. Typemo отклонит его при сборке модели, потому что для этого есть опция [`default`](../reference/schemas/prop.mdx#default). Ошибка будет такой — `User: field(s) "login" get a value from an initializer or the constructor; use the "default" option — service fields are filled by Typemo`. Как пользоваться опцией, рассказывает руководство [Значения по умолчанию](./defaults.mdx).

## Полный пример

Всё вместе в одном файле — модель, её получение и создание документа с обработкой ошибки на границе. Код, которого нет в Typemo, помечен `__…__`.

```ts twoslash title="users/users.service.ts"
import { Entity, Prop, Schema, Spec, TypemoClient, Types, Virtual, type Computed, type Defaulted, type Hidden, type Immutable, type Ref, type VirtualRef } from "@venloc/typemo";
const client = await TypemoClient.connect("mongodb://localhost:27017", { dbName: "shop" });
// ---cut---
// модель: класс с @Schema, идентификатор от Entity
@Schema({ collection: "users" })
class User extends Entity {
  @Prop(() => String, { required: true })
  login!: string;

  @Prop(() => String)
  bio?: string;

  @Prop(() => Date)
  birthday?: Date;
}

// код читателя: ошибка на границе приложения
class __BadRequest__ extends Error {}

// регистрация: модель берётся там, где нужна
export const registerUser = async (login: string, bio?: string) => {
  const Users = client.connection.model(User);
  try {
    return await Users.create({ login, ...(bio === undefined ? {} : { bio }) });
  } catch (error) {
    throw new __BadRequest__((error as Error).message);
  }
};

const user = await registerUser("ann", "hello");
console.log(user.$toPlain().login);
// → ann
```

<Callout type="migration">

В Mongoose схему создают отдельным объектом `new Schema({...})`, модель — вызовом `mongoose.model("User", schema)`, а тип документа приходится описывать отдельным интерфейсом. В Typemo класс сразу и схема, и тип, а модель выдаёт подключение — `connection.model(User)`. Настроек `strict`, `timestamps`, `versionKey`, `toJSON` и `toObject` у `@Schema` нет. Строгость абсолютная, а метки времени и версия приходят из базовых классов.

</Callout>
