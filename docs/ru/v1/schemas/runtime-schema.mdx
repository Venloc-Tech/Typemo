Схема описана классом, но иногда она нужна как данные. Сгенерировать документацию по полям, собрать снимок для теста, написать запрос к драйверу с настоящими именами полей, узнать, какие поля скрыты. Для этого у каждой модели есть свойство `schema` — описание схемы [`SchemaInfo`](../reference/schemas/schema-info.mdx), **только для чтения**. Изменить схему нельзя. После сборки модели она заморожена, и все, кто её читает, видят одно и то же.

## Что понадобится [#prerequisites]

Клиент из руководства [Подключиться к базе](../connection/connect.mdx) и модель пользователя из файла `users/user.ts`. Почта хранится в базе под именем `e`, есть скрытое поле, вложенный адрес и массив тегов.

## Прочитать пути и их свойства [#read-paths]

`describe()` возвращает обычный объект. Его можно печатать, сравнивать со снимком и обходить. В `paths` каждый путь записан так, как в коде (`address.city`, `tags.$` для элемента массива). У него есть вид узла, тип, имя в базе (если оно другое) и флаги.

<Snippet id="schemas/runtime-schema/read-paths" title="users/inspect.ts" twoslash />

Флаги идут строкой через запятую — `required`, `nullable`, `default`, `immutable`, `hidden` и служебные вроде `service:id`. По ним легко собрать список, например, каких скрытых полей не должно быть в документации API.

<Snippet id="schemas/runtime-schema/read-paths-2" title="users/inspect.ts" twoslash />

Кроме путей, в описании есть `indexes` (ключи и опции), `searchIndexes` (индексы Atlas Search из `@SearchIndex`), `virtuals`, `hooks`, `discriminator` и `discriminators` для иерархий и `ext`.

## Перевести путь в имя из базы [#to-db-path]

В запросе к драйверу полям нужны имена из базы, а не из кода. У нас `email` хранится как `e`, а `address.city` как `address.c`. [`toDbPath`](../reference/schemas/schema-info.mdx#to-db-path) переводит путь на всех уровнях и сохраняет позиции в массиве. Для пути, которого нет в схеме, он вернёт `undefined`, а не бросит ошибку. Так что опечатку ловите проверкой результата.

<Snippet id="schemas/runtime-schema/to-db-path" title="users/raw-query.ts" twoslash />

## Прочитать опции расширений [#read-extension-options]

Расширения хранят свои настройки прямо в схеме, в `@Schema({ ext })` и `@Prop({ ext })`. [`schema.ext`](../reference/schemas/schema-info.mdx#ext) отдаёт настройки схемы, а [`schema.extOf(путь)`](../reference/schemas/schema-info.mdx#ext-of) — настройки поля. Для поля без `ext` это пустой объект, для несуществующего пути — `undefined`. Так интеграции узнают, что для поля включён их режим. Как расширения объявляют опции, рассказывает руководство [Свои опции полей и схем](../extensions/custom-options.mdx).

## Как выбрать [#how-to-choose]

Спросите себя — **нужна схема как данные или как типы?**

- **Как типы** — их даёт сам компилятор, `Lean<User>` и `Plain<User>`.
- **Как данные во время работы** — имя в базе, флаг, индекс. Читайте `schema`.
- **Чтобы проверить значения по схеме** — берите [`StandardSchema`](./json-and-standard-schema.mdx), а не разбор `describe()`.

## Когда это не нужно [#when-not-to-use]

`schema` только читает. Менять поля, индексы или опции во время работы нельзя. Не разбирайте `describe()` ради проверки данных, для этого есть готовые средства. Формат описания рассчитан на снимки и диагностику, а не на надёжный разбор в бизнес-логике.

## Если что-то пошло не так [#troubleshooting]

**`toDbPath` вернул `undefined`.** Такого пути в схеме нет, скорее всего, опечатка. Сверьте имя с `Object.keys(Users.schema.describe().paths)`.

**Поисковых индексов нет в `indexes`.** `describe().indexes` перечисляет только обычные индексы. Индексы [`@SearchIndex`](../reference/schemas/index-decorators.mdx#search-index) лежат в отдельном поле `searchIndexes`, там их объявления из схемы, имя и определение. Их состояние на сервере смотрите методами модели из руководства [Поисковые индексы](../collections/search-indexes.mdx).
