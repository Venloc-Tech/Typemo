This page collects the terms from the guides and the reference, each with a definition in a sentence or two. The full explanation lives on the page the link leads to. The glossary is for quickly recalling a word, not for learning the product from it.

Every term has a stable **key**, a short Latin-letter name. The `Term` component uses it to show the definition on hover. For example, `<Term id="plain">the plain() result</Term>` takes the definition of the term with the key `plain`. The key is given after the definition and doesn't change, even if the term's name changes.

The terms are grouped by topic. If you're looking for a word alphabetically, use the site search. The heading of each entry is the word itself.

## Data and result forms [#data-and-result-forms]

### Document [#document]

A record in a MongoDB collection. When the docs say "document" with no qualifier, they mean a model object that remembers its changes and can save itself with `$save`. Mongoose and English-language sources call it a hydrated document. Key: `document`. More: [Document lifecycle](../documents/lifecycle.mdx).

### Hydration [#hydration]

Turning a raw record from the database into a model document. Values are cast to the schema types, and arrays, subdocuments, and `Map` become strictly typed collections. Key: `hydration`. More: [Document lifecycle](../documents/lifecycle.mdx).

### The `.lean()` result [#lean]

A read result that isn't turned into a document. These are ordinary objects where BSON values keep their own types: `ObjectId`, `bigint`, `Date`. In effect, it's the data as the driver returned it. Key: `lean`. More: [Reading data](../queries/reading-data.mdx).

### The `.plain()` result [#plain]

Ordinary objects ready for the client. `ObjectId` and int64 values in them are replaced with strings, and hidden fields are removed. Key: `plain`. More: [Reading data](../queries/reading-data.mdx).

### Projection [#projection]

The list of fields a query returns, either by including the ones you need or by excluding the ones you don't. In Typemo the `select` method sets the projection, and it changes the result type. Key: `projection`. More: [Projections and the result type](../queries/projections.mdx).

### Selected [#selected]

A type that describes the shape of a response after a projection. You need it when you have to name that shape, for example to return it from a function. Key: `selected`. More: [Contracts](../reference/query/contracts.mdx#selected).

### Contract [#contract]

A fixed response shape. At build time the compiler checks it (`.expect`), and at runtime you can check data from the database against a schema (`.parse`). Key: `contract`. More: [Checking the response shape](../queries/contracts.mdx).

### Mask [#mask]

A rule that hides part of a value in a response to the client. For example, an email keeps only its first letter and the domain. Masks work only with the `.lean()` and `.plain()` results. Key: `mask`. More: [Response masks](../queries/response-masks.mdx).

### Hidden field [#hidden]

A field with the `hidden` option. It doesn't go into responses or serialization until you ask for it explicitly. In types such a field is marked with the `Hidden<T>` marker. Key: `hidden`. More: [Hidden and sensitive fields](../schemas/hidden-and-sensitive.mdx).

### Sensitive field [#sensitive]

A field with the `sensitive` option. Its value is masked or hidden everywhere it could leak: in responses, events, audit, and errors. Key: `sensitive`. More: [Hidden and sensitive fields](../schemas/hidden-and-sensitive.mdx).

### Unknown fields [#unknown-fields]

Fields a document has in the database that aren't described in the schema. Typemo doesn't lose them silently but reports them with an `UnknownFieldsError` when you work with such a document. Key: `unknown-fields`. More: [Handle fields that aren't in the schema](../documents/unknown-fields.mdx).

### Typed collections [#typed-collections]

A document's own strictly typed arrays, `Map`, and subdocument arrays. You can write to them only with methods, because each method corresponds to a MongoDB operator. Key: `typed-collections`. More: [Arrays and Maps in a document](../documents/typed-collections.mdx).

### StrictArray [#strict-array]

The type of an array in a document. You can only read it by index and change it with its own methods like `push`, `pull`, and `splice`. Each such call goes into the change log and becomes a MongoDB operator. Writing by index (`tags[0] = "x"`) doesn't compile, and if you get around that with a type cast, `$save()` throws `DirectWriteError` with a hint about which methods change the array. In the `.lean()` and `.plain()` results and in `$toObject()`, the same fields are ordinary arrays. Key: `strict-array`. More: [Arrays and Maps in a document](../documents/typed-collections.mdx).

### Document in any population state [#any-population-doc]

A document whose reference field can hold either an identifier or an already populated document. Its type is `AnyPopulationDoc<T>`. A function needs it to accept a document both before and after `populate`, and an `isPopulated` check narrows it. Key: `any-population-doc`. More: [Make sure a reference is populated](../populate/type-checks.mdx).

### Subdocument [#subdocument]

A nested object inside a document, described by its own schema class. A subdocument has a parent and a path inside it. Key: `subdocument`. More: [Work with nested objects](../documents/subdocuments.mdx).

### BSON [#bson]

The binary format MongoDB stores data in. It has more types than JSON: `ObjectId`, int64, `Decimal128`, `Binary`, `Timestamp`. So some values can't be sent to a client without conversion. Key: `bson`. More: [MongoDB data types](../concepts/bson-types.mdx).

### ObjectId [#object-id]

A 12-byte identifier that MongoDB puts in the `_id` field by default. Wherever Typemo expects an `ObjectId`, you can pass its string form too. Key: `object-id`. More: [MongoDB data types](../concepts/bson-types.mdx).

### int64 [#int64]

A 64-bit integer. In TypeScript it corresponds to `bigint`, because an ordinary number holds integers exactly only up to 2⁵³. Key: `int64`. More: [Choose a field type](../schemas/field-types.mdx).

### Decimal128 [#decimal128]

MongoDB's exact decimal number, suitable for money. Unlike `number`, it doesn't round fractions. Key: `decimal128`. More: [Choose a field type](../schemas/field-types.mdx).

## Schemas and models [#schemas-and-models]

### Schema [#schema]

The description of a model's data: fields, constraints, indexes, and collection options. In Typemo a schema is a class with the `@Schema` decorator. Key: `schema`. More: [Define a model](../schemas/define-model.mdx).

### Model [#model]

The object you read and write one collection through, with `find`, `create`, `updateOne`, and the other methods. You get a model from a connection, for example `connection.model(Account)`. Key: `model`. More: [Define a model](../schemas/define-model.mdx).

### Field [#field]

A property of a schema class with the `@Prop` decorator. The field's type comes from the class, and options like `required`, `unique`, and `hidden` set constraints. Key: `field`. More: [Define a model](../schemas/define-model.mdx).

### Base class [#base-class]

A class a model extends to get bookkeeping fields. `Entity` gives `_id`, `Timestamped` adds `createdAt` and `updatedAt`, `Versioned` adds the `__v` version, and `EntityWithId` gives an `_id` of your own type instead of `ObjectId`, such as a string, a number, or a UUID. Typemo doesn't add these fields behind your back. Key: `base-class`. More: [Base classes](../reference/schemas/base-classes.mdx).

### Marker types [#marker-types]

Wrapper types like `Hidden<T>`, `Immutable<T>`, and `Ref<M>` that a field uses to tell the type system about one of its properties. They don't change the value at runtime. They change what the compiler allows. Key: `marker-types`. More: [Field marker types](../reference/schemas/field-markers.mdx).

### Required, `null`, and missing [#nullable]

Three different states of a field: it has a value, its value is `null`, or it has no value. Typemo tells them apart and doesn't treat `undefined` as a value. Key: `nullable`. More: [Required fields, null, and missing values](../schemas/required-and-null.mdx).

### Nested object [#nested-object]

An object inside a document, described by a class with `@Schema({ nested })`. It has no `_id` and no collection of its own. Key: `nested-object`. More: [Define nested objects and subdocuments](../schemas/nested-and-subdocuments.mdx).

### Immutable field [#immutable]

A field with the `immutable` option, which can't be changed after the document is created. Key: `immutable`. More: [Immutable fields](../schemas/immutable.mdx).

### Virtual field [#virtual]

A field that isn't in the database. It's either computed on read (a getter) or loads related documents (`@Virtual`). Key: `virtual`. More: [Add computed fields and reverse references](../schemas/virtuals.mdx).

### Reference [#reference]

A field that stores the identifier of a document of another model. You can populate the relation through a reference. Key: `reference`. More: [Reference other models](../schemas/references.mdx).

### Discriminator [#discriminator]

A way to store several child models in one collection. A separate field (`discriminatorKey`) says which model a document belongs to. Key: `discriminator`. More: [Inheritance and discriminators](../schemas/discriminators.mdx).

### Validation [#validation]

Checking values against the schema's rules: `min`, `max`, `enum`, or your own `validate`. It runs on create, save, and update, and its errors are collected into a `ValidationError` with field paths. Key: `validation`. More: [Validate field values](../schemas/validation.mdx).

### Optimistic concurrency [#optimistic-concurrency]

Protection against losing concurrent edits. A document stores a `__v` version, and a save with an outdated version is rejected with a `VersionError`. Key: `optimistic-concurrency`. More: [Don't lose concurrent changes](../documents/versions.mdx).

## Connecting [#connection-basics]

### Peer dependency [#peer-dependency]

A package Typemo doesn't bring along but expects from you through `peerDependencies`. These are `mongodb` and `bson`. That way BSON values in your code and in the library are the same classes. Key: `peer-dependency`. More: [Installation and setup](../getting-started/installation.mdx).

### Client [#client]

The `TypemoClient` object, which owns the connection to MongoDB and the connection pool. You create it once per process. Key: `client`. More: [Connect to the database](../connection/connect.mdx).

### Connection [#connection]

The `Connection` object, the client's link to one database. You get models from it (`model`) and run index sync on it (`init`, `syncAll`). Key: `connection`. More: [Connect to the database](../connection/connect.mdx).

### Driver [#driver]

The official `mongodb` package Typemo talks to the server through. You can reach it around Typemo with `client.unsafeDriver()`, but then policies, masks, and hooks don't apply. Key: `driver`. More: [Driver access](../connection/driver-access.mdx).

### Replica set [#replica-set]

Several MongoDB servers holding copies of the same data. A replica set can also have a single node. It's needed for transactions, change streams, and models with audit. Key: `replica-set`. More: [Connect to the database](../connection/connect.mdx).

### Collection [#collection]

A set of documents in a MongoDB database, roughly the same as a table in a relational database. Key: `collection`. More: [Connect to the database](../connection/connect.mdx).

## Reading and writing [#reads-and-writes]

### Query builder [#query-builder]

The object that `find`, `findOne`, and other methods return. It assembles a query with a chain (`select`, `sort`, `limit`) and goes to the database only on `await`. Key: `query-builder`. More: [Reading](../reference/query/reading.mdx).

### Filter [#filter]

A search condition. It's an object whose keys are model fields and whose values are a field value or an operator like `$in` or `$gt`. Typemo checks a filter both with the compiler and at runtime. Key: `filter`. More: [Filters](../queries/filters.mdx).

### Cursor [#cursor]

An object that hands out documents one at a time, as they're read from the database. You need it when a result doesn't fit in memory. Key: `cursor`. More: [Large results](../queries/large-results.mdx).

### Keyset pagination [#keyset-pagination]

A way to page through long lists without `skip`. The next page is found by the sort field values of the last record, and those values are encoded in a signed token. Key: `keyset-pagination`. More: [Keyset pagination](../queries/keyset-pagination.mdx).

### Query plan [#query-plan]

A description of how the server will run a query: which index it takes and how many documents it examines. `explain` shows it. Key: `query-plan`. More: [Query performance](../queries/performance.mdx).

### Update operator [#update-operator]

A key like `$set`, `$inc`, or `$push` in an update object. It tells the server what to do with a field and doesn't replace the whole document. Key: `update-operator`. More: [Update operators](../writes/update-operators.mdx).

### Pipeline update [#pipeline-update]

An update that passes a pipeline of stages instead of operators. That way a field's new value can be computed from other fields of the document. Key: `pipeline-update`. More: [Pipeline updates](../writes/pipeline-updates.mdx).

### Empty filter [#empty-filter]

The `{}` filter, which matches every document. It's allowed in reads and forbidden in writes (`updateOne`, `updateMany`, `deleteOne`, `deleteMany`, `replaceOne`, `findOneAnd*`). To touch everything on purpose, you write `Filters.all()`. Key: `empty-filter`. More: [Empty filters in writes](../writes/empty-filters.mdx).

### Database-level operation [#database-level-operation]

An aggregation that reads not a model's collection but the whole database, the `admin` database, or the server's sessions, for example `$currentOp`, `$documents`, and `$listSessions`. `Pipeline.database()`, `Pipeline.admin()`, and `Pipeline.sessions()` build the plan for it, and `connection.aggregate` and `client.aggregate` run it. Such an operation has no model, so `model` is `null` in events and hooks aren't called. Key: `database-level-operation`. More: [Database-level queries](../aggregation/database-level.mdx).

### Bulk write [#bulk-write]

Several different write operations that the `bulkWrite` method sends to the server in one request. Key: `bulk-write`. More: [Bulk writes](../writes/bulk.mdx).

## Related data and aggregation [#populate-and-aggregation]

### Populate [#populate]

Filling in a relation. Instead of an identifier, the reference field gets the related document itself, and the field's type changes along with it. The docs call this "populate" or "fill in related documents", and the whole topic "related data". Key: `populate`. More: [Show related data](../populate/basics.mdx).

### Pipeline [#pipeline]

A sequence of aggregation **stages**. Each stage takes documents from the previous one and passes them to the next. Typemo knows the result type after every stage. Key: `pipeline`. More: [Your first aggregation](../aggregation/first-aggregation.mdx).

### Stage [#stage]

One step of a pipeline. For example, `$match` selects documents, `$group` groups them, and `$lookup` pulls in documents from another collection. Key: `stage`. More: [Stages](../reference/aggregation/stages.mdx).

### Expression [#expression]

A formula inside a stage that computes a value from document fields: arithmetic, strings, dates, arrays. In Typemo you build expressions with typed functions, and a raw `$expr` is forbidden. Key: `expression`. More: [Calculations in aggregation](../aggregation/expressions.mdx).

### Accumulator [#accumulator]

An operator that folds a group's documents into one value: a sum, an average, a count, or the first value. Key: `accumulator`. More: [Grouping and reports](../aggregation/grouping.mdx).

### Window function [#window-function]

A calculation over a "window" of neighboring documents, for example a moving average or a running total. Unlike grouping, it doesn't fold the documents into one row. Key: `window-function`. More: [Window functions](../aggregation/windows.mdx).

## Transactions, hooks, and extensions [#transactions-hooks-extensions]

### Transaction [#transaction]

A group of operations that either all run or none do. Typemo starts a transaction with the `transaction` method and retries it on transient errors by itself. Key: `transaction`. More: [Transactions](../transactions/transactions.mdx).

### Session [#session]

A context in which the server ties several operations together, for example into a transaction. You usually don't need a session by hand, because `transaction` manages it. Key: `session`. More: [Manual sessions](../transactions/sessions.mdx).

### Hook [#hook]

Your function that Typemo calls before (`@Pre`) or after (`@Post`) an operation or a document event. A hook sees the operation context and can change the filter or the update, or skip the operation. Key: `hook`. More: [Hook into an operation](../hooks/operation-hooks.mdx).

### Plugin [#plugin]

A set of hooks and static methods that attaches to a schema or to all models at once, so you don't repeat the same logic. Key: `plugin`. More: [Reuse behavior across models](../hooks/plugins.mdx).

### Extension [#ext]

A way to give a field or a schema options of your own through the `ext` key. An extension declares the option's type and is registered on the client before the first model. Key: `ext`. More: [Add your own field and schema options](../extensions/custom-options.mdx).

## Policies and strictness [#policies-and-strictness]

### Policy [#policy]

A rule that applies to every operation of a model and can't be turned off for a single query. For example, tenant, soft delete, strict paths, or audit. Key: `policy`. More: [What data policies are](../policies/overview.mdx).

### Tenant [#tenant]

The owner of data in an app where one database serves many customers. The `tenant` policy adds the tenant to every query, and one customer won't see another's documents. Key: `tenant`. More: [Split data by organization](../policies/tenants.mdx).

### Soft delete [#soft-delete]

A delete where the document stays in the database with a mark, but reads no longer return it. It's turned on with the `softDelete` schema option. Key: `soft-delete`. More: [Delete with a way to restore](../policies/soft-delete.mdx).

### Policy context [#policy-context]

The policy values for the current request: the tenant, the author of the action, and flags like `includeDeleted`. You set them with `PolicyContext.run` or with `.policy()` on a query. Key: `policy-context`. More: [Pass the tenant and actor through the whole request](../policies/policy-context.mdx).

### Actor [#actor]

Whoever performs an action, a user or a service. The actor is passed in the policy context and recorded in the audit log next to the change. Key: `actor`. More: [Pass the tenant and actor through the whole request](../policies/policy-context.mdx).

### Audit [#audit]

A record of every data change in a separate collection: who changed what and when. Sensitive field values are masked in the audit. Key: `audit`. More: [Keep an audit log](../policies/audit.mdx).

### Untrusted input [#untrusted-input]

Values that came from the app's client. The `untrusted()` function keeps anyone from slipping a MongoDB operator into a filter through them and turning the condition into something else. Key: `untrusted-input`. More: [Accept a filter from a client request](../policies/untrusted-input.mdx).

### Policy violation [#policy-violation]

A `StrictModeError` with a reason code, for example `empty-filter`, `unknown-path`, or `tenant`. A policy rejected the operation before it reached the database. Key: `policy-violation`. More: [Policy violations](../reference/policies/violations.mdx).

### Strictness [#strictness]

Typemo's main principle. Anything that looks like a mistake (an unknown field, `undefined` in a filter, an empty filter in a write, a wrong type) becomes an error, not silent behavior. No option and no mode relaxes strictness. Key: `strictness`. More: [Strictness](../concepts/strictness.mdx).

## Collections and indexes [#collections-and-indexes]

### Index [#index]

A structure that speeds up search and enforces uniqueness. Indexes are described in the schema and created explicitly, on `init` or `syncAll`, not on the first query. Key: `index`. More: [Sync indexes](../collections/index-sync.mdx).

### Index sync [#index-sync]

Bringing the indexes in the database in line with the ones described in the schema. `syncIndexes` creates the missing ones and removes the extra ones, and `diffIndexes` only shows the difference. Key: `index-sync`. More: [Sync indexes](../collections/index-sync.mdx).

### Search index [#search-index]

An index for full-text and vector search that the server itself builds (Atlas Search and vector search). Key: `search-index`. More: [Define and sync search indexes](../collections/search-indexes.mdx).

### View [#view]

A read-only collection whose contents the server computes with a pipeline on every access. In Typemo a `TypedView` describes it. Key: `view`. More: [Read a predefined selection through a view](../collections/views.mdx).

### Materialized view [#materialized-view]

A pipeline result saved in an ordinary collection. It isn't recomputed on read, and a `refresh` call updates it. Key: `materialized-view`. More: [Save an aggregation result and keep it up to date](../collections/materialized-views.mdx).

## Change streams and observability [#change-streams-and-observability]

### Change stream [#change-stream]

A stream of events (`change stream`) in which the server reports inserts, updates, replacements, and deletes in a collection. The `Model.watch` method opens it, and it needs a replica set. Key: `change-stream`. More: [Watch for changes](../change-streams/watch.mdx).

### Resume token [#resume-token]

A token that every change stream event has. With it you can continue reading from the same place after a disconnect. Key: `resume-token`. More: [Watch for changes](../change-streams/watch.mdx).

### Operation events [#instrumentation]

The events Typemo sends to subscribers: the start, end, and error of an operation, driver commands, and the pool state. Monitoring integrations are built on them. Key: `instrumentation`. More: [Operation events](../observability/events.mdx).

### Subscriber [#subscriber]

Your function registered through `client.instrument` or `Typemo.instrument`. It receives operation events and passes them on to monitoring. Key: `subscriber`. More: [Operation events](../observability/events.mdx).

### OpenTelemetry [#opentelemetry]

The separate `@venloc/typemo-opentelemetry` package, which turns operation events into spans and metrics. The Typemo core doesn't depend on it. Key: `opentelemetry`. More: [OpenTelemetry](../observability/opentelemetry.mdx).

### Sentry [#sentry]

The separate `@venloc/typemo-sentry` package, which adds operation breadcrumbs and Typemo error context to Sentry. The core doesn't depend on it. Key: `sentry`. More: [Sentry](../observability/sentry.mdx).

## Errors and types [#errors-and-types]

### Typemo error [#typemo-error]

Any error from the library, a descendant of the `TypemoError` class. You catch them by class, for example `ValidationError` or `DuplicateKeyError`, and the original cause is in the `cause` field. Key: `typemo-error`. More: [Error handling](../errors/handling.mdx).

### Standard Schema [#standard-schema]

A common interface for validation schemas. You can pass a Typemo model wherever a schema from zod, valibot, or another library that supports it is expected. Key: `standard-schema`. More: [JSON Schema and Standard Schema](../schemas/json-and-standard-schema.mdx).

### JSON Schema [#json-schema]

A data description format MongoDB uses to check documents on the server side. Typemo generates it from a model's schema. Key: `json-schema`. More: [JSON Schema and Standard Schema](../schemas/json-and-standard-schema.mdx).

### Test data factory [#factory]

A function created by `defineFactory`. It sets a document's default values with a sequence number once, and a test specifies only what matters to it. It lives in `@venloc/typemo/testing`. Key: `factory`. More: [Test your app](../testing/testing-apps.mdx).

## Decorators [#decorators]

### Legacy decorators [#legacy-decorators]

Decorators in `experimentalDecorators` mode, which the `@venloc/typemo` core runs on. They need neither `emitDecoratorMetadata` nor `import "reflect-metadata"`, because the core keeps its own metadata. Key: `legacy-decorators`. More: [Installation and setup](../getting-started/installation.mdx).

### TC39 decorators [#tc39-decorators]

Decorators from the ECMAScript standard. There's a separate package for them, `@venloc/typemo-decorators`. You can't mix the two kinds in one project. Key: `tc39-decorators`. More: [Use TC39 decorators](../decorators-tc39/tc39.mdx).
