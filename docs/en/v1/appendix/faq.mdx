These are the questions people ask when they write Typemo code for the first time. What it doesn't have, why something is so strict, where to go for details. The answers are short, and each one leads to the page where the question is covered in full. The error texts and results come from a real MongoDB.

If your question is about a specific method, look at the end of its guide, in the "Troubleshooting" section. Errors are covered there as symptom, cause, and what to do.

## Do I need to install anything besides the Typemo package? [#dependencies]

Yes, the `mongodb` driver and the `bson` package. Typemo doesn't bring them along but declares them in `peerDependencies`. That way `ObjectId` from your code and from the library is the same class. `reflect-metadata`, where the core keeps its metadata, installs together with Typemo on its own. The list of packages and the `tsconfig` settings are in [Installation and setup](../getting-started/installation.mdx), and the versions in [Version compatibility](./versions.mdx).

## Do I need `reflect-metadata`? [#reflect-metadata]

No. The core keeps the schema metadata in it itself, in a mode that doesn't touch the global `Reflect`. So you don't write `import "reflect-metadata"`. You don't need the `emitDecoratorMetadata` flag either. You name each field's type explicitly, `@Prop(() => String)`, and Typemo doesn't read types from the compiler's metadata.

If `emitDecoratorMetadata` is on for other libraries, nothing breaks. The core's legacy decorators need only `experimentalDecorators`. Details and a tested `tsconfig` are in [Installation and setup](../getting-started/installation.mdx).

## Does Typemo work without a replica set? [#without-replica-set]

Not if you need transactions, change streams, or models with audit. For those the server requires a replica set and refuses otherwise. A replica set is several MongoDB servers holding copies of the same data, but one node is enough. You can check for it in advance, before the app starts. The [Transactions](../transactions/transactions.mdx) guide shows how, in the "A transaction doesn't start on a standalone server" section.

## Does Typemo work on Node.js? [#node-js]

It's only partly tested. The tests and the docs examples ran on Bun. On Node.js 24 with a real MongoDB, the built package passes only a short smoke test: create, read, update, populate, aggregation, and a transaction. Details and everything untested are in [Version compatibility](./versions.mdx#runtime).

## Can I describe schemas without decorators? [#schemas-without-decorators]

No. A schema in Typemo is a class with the `@Schema` and `@Prop` decorators. Both the types and the storage rules come from it, so there's no separate "schema dictionary".

There are two kinds of decorators, and you pick one for the whole project. The core works on legacy decorators, and there's a separate package for TC39 decorators. How to choose is covered in [Use TC39 decorators](../decorators-tc39/tc39.mdx) and in [Installation and setup](../getting-started/installation.mdx).

## Why did my data end up in the `test` database? [#test-database]

Because you didn't name a database. Typemo looks at the `dbName` option first, then at the name in the connection string, and if there's neither, it takes `test`, like the driver itself. In real projects it's better to name the database explicitly. The details are in [Connect to the database](../connection/connect.mdx#default-database).

## Why aren't collections and indexes created automatically, and why doesn't `unique` work? [#no-auto-create]

Typemo doesn't create anything in the database implicitly. Indexes appear when you call `connection.init()` or `connection.syncAll()` on startup or deploy. Until then, the `unique` index doesn't exist. Without `init`, two writes with the same value of a unique field both saved, and after `init` the second one failed with `DuplicateKeyError`. More in the [Sync indexes](../collections/index-sync.mdx) guide, in the "Uniqueness doesn't work" section.

## Why did `findOne` return `null` and `find` an empty array? [#null-vs-empty-array]

An empty result is normal, not an error, and a read says exactly that. `findOne` returns `null`, and `find` returns `[]`. If the document must exist, add `.orFail()`, and you get a `DocumentNotFoundError` instead of `null` or an empty array. It works with `find` too: an empty list with `.orFail()` becomes an error. The details are in the [Reading data](../queries/reading-data.mdx) guide and the [Reading](../reference/query/reading.mdx) reference.

## Why does `JSON.stringify` fail on a read result? [#json-stringify-fails]

In the `.lean()` result, int64 integers are `bigint`, which JSON can't handle, and you get `TypeError: JSON.stringify cannot serialize BigInt.` To send data to a client, read with `.plain()`, where `_id` and int64 are already strings. Why it works this way and what the options are is explained in [Reading data](../queries/reading-data.mdx) and [Send a document to the client](../documents/serialization.mdx).

## Why doesn't `updateOne({})` compile? [#empty-update-one]

One typo in the condition, and the operation would change or delete everything. For `updateOne` and `deleteOne` it would be an arbitrary document. That's why the empty literal `{}` is forbidden in every write method: `updateOne`, `updateMany`, `deleteOne`, `deleteMany`, `replaceOne`, and `findOneAnd*` won't compile with it.

The compiler tells you what to do right in the message, and the text depends on the method. For `updateMany` and `deleteMany` it's `an empty filter would affect every document; pass a filter, or Filters.all() to mean every document on purpose`. For the `One` forms and `findOneAnd*`, `would affect every document` is replaced by `would change or remove an arbitrary document`.

If the filter turns out empty only at runtime, a check at call time stops it with the same words: `StrictModeError: updateMany with an empty filter would affect every document; pass a filter, or Filters.all() to mean every document on purpose [empty-filter]`. If you mean to touch everything, say so explicitly with `Filters.all()` and no arguments. The details are in the [Empty filters in writes](../writes/empty-filters.mdx) guide.

## Why is `undefined` in a filter an error rather than "no condition"? [#undefined-in-filter]

If Typemo silently dropped such a condition, you'd get all users instead of a few. So `find({ title: undefined })` throws `QueryError: filter: undefined at "title" (use $exists: false / $unset; undefined is never a value)`. To find documents without the field, write `{ title: { $exists: false } }`. More in the [Filters](../queries/filters.mdx) guide and the [Strictness](../concepts/strictness.mdx) concept.

## Why is a typo in a field name an error? [#typo-in-field]

The compiler underlines an unknown field. And if the types are bypassed, Typemo throws an error at runtime: `StrictModeError: filter: "titel" is not a field of Account [unknown-path]`. That way a typo doesn't turn into a query that quietly finds nothing, and you don't have to hunt for the cause in the data. The [Strictness](../concepts/strictness.mdx) concept explains what else Typemo treats as an error and why.

## Does Typemo protect a `{ name: body.name }` filter from an operator sent by the client? [#operator-injection]

No. Say the client sends `{"name": {"$gt": ""}}`. Then the filter `find({ name: body.name })` gets the condition `{ $gt: "" }`. For a string field that's a valid condition of the right type, Typemo runs it, and the query returns all users instead of one. On three users it returned all three. Typemo can't tell a condition you wrote from one the client sent.

Here's how to protect yourself. Check that a string arrived, and wrap the client's data in [`untrusted`](../reference/policies/soft-delete-and-untrusted.mdx#untrusted). The query `find(untrusted({ name: body.name }))` stops before the database with the `StrictModeError` `untrusted value: "$gt" at "name.$gt" — an operator inside data from outside (query selector injection); validate the input and build the filter yourself [sanitize]`. The details are in the [Accept a filter from a client request](../policies/untrusted-input.mdx#operator-instead-of-value) guide.

## Can I relax strictness, like `strict: false` in Mongoose? [#relax-strictness]

No, neither with an option nor with a mode. That's by design: Typemo reports an error everywhere instead of behaving silently. What to do with data that doesn't fit the schema is covered in [Handle fields that aren't in the schema](../documents/unknown-fields.mdx). What to use instead of Mongoose features that aren't here is in [What Typemo doesn't have](../migration/missing-features.mdx).

## Why does a second `await` of the same query fail? [#second-await]

A write query runs once, because a repeat is almost always accidental. A second `await` of the same `updateOne` throws `QueryError: updateOne: this operation was already executed; build a new one, or run it again deliberately with exec({ force: true }) (a write runs once per builder)`. Build a new query or call `exec` with `force`. More in the [Update documents](../writes/update.mdx) guide.

## Does `insertOne` run hooks? [#insert-one-hooks]

Yes. `insertOne` and `insertMany` run document hooks the same way as [`create`](../reference/writes/writes.mdx#create). The `document.save` hook fired for `create`, for `insertOne`, and for `insertMany`. Writes by filter have their own operation hooks, `query.updateOne` and others. More in the [Hook into an operation](../hooks/operation-hooks.mdx) guide and the [`@Pre`, `@Post`, and `@PostError`](../reference/hooks/pre-post.mdx) reference.

## How do I catch a duplicate key error? [#catch-duplicate-key]

Catch `DuplicateKeyError` around the write itself. Don't check in advance whether such a document exists, because another client can insert the same one between the check and the write. The error hierarchy and how to turn errors into app responses are described in the [Error handling](../errors/handling.mdx) guide.

## Why is a hidden field missing from the response, or why didn't a mask work? [#hidden-field-missing]

A hidden field doesn't go into the response until you ask for it explicitly. That way a password hash doesn't leak by accident. Masks work only with the `.lean()` and `.plain()` results, not with a document, so `.mask()` on a document doesn't compile. The details are in the [Projections and the result type](../queries/projections.mdx), [Response masks](../queries/response-masks.mdx), and [Hidden and sensitive fields](../schemas/hidden-and-sensitive.mdx) guides.

## How do I type a function for both a populated and an unpopulated document? [#type-populated-or-not]

Until the reference is populated, the `author` field holds an identifier, and after that, the author itself. A plain `HydratedDoc<Post>` describes only the first case. For a function to accept both, declare the parameter as `AnyPopulationDoc<Post>` and narrow it with an `isPopulated` check. For a document without `populate` such a function returns `undefined`, and after `populate("author")`, the author's name.

The author may have been deleted, and then the populated reference is `null`. That's why the example has `?.`. More in the [Make sure a reference is populated](../populate/type-checks.mdx#accept-any-state) guide.

## What if I need a MongoDB feature Typemo doesn't have? [#missing-feature]

Go to the driver directly through `client.unsafeDriver()`. But you lose policies, masks, hooks, and inferred types. A driver write knows nothing about soft delete and tenants and won't roll back together with a Typemo transaction. When that's justified is covered in the [Driver access](../connection/driver-access.mdx) guide.

## Can I move from Mongoose gradually? [#gradual-migration]

Yes, a whole section is devoted to it: collection by collection, with both libraries at once. What's shared, what's different, and what's missing is in [Why switch](../migration/why.mdx). The mapping table of methods and options is in the [API mapping](../reference/migration/api-mapping.mdx) reference.
