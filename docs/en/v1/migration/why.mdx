Switching from Mongoose to Typemo is worth it if you're bothered by what Mongoose silently casts, drops, or lets through. Or if you want the model's types to come from a single description. If none of that bothers you, the switch gives you little and takes a lot of time. Below we'll go through what changes, what it costs, and when you're better off staying on Mongoose.

Typemo is a standalone library, not a layer on top of Mongoose. It works through the official `mongodb` driver and uses none of Mongoose's code. So the only fair comparison is by concrete differences, not by overall impression.

## What changes [#what-changes]

**You describe the document type once.** In Mongoose the schema lives apart from the TypeScript interface, and you have to keep them in sync by hand or infer types from the schema. In Typemo the schema is a class. [`@Schema`](../reference/schemas/schema.mdx#schema) and [`@Prop`](../reference/schemas/prop.mdx#prop) describe the fields, and the document type, the input type for `create`, and the result types all come from it. A document, the `.lean()` result, and the `.plain()` result are different types, and the compiler won't let you confuse an `ObjectId` with its string in an API response.

**Types check filters, projections, and updates.** A typo in a field, a value of the wrong type, or a `select` that mixes inclusions and exclusions is a compile error, not an empty result. The [Reading data](../queries/reading-data.mdx) and [Filters](../queries/filters.mdx) guides show exactly what gets checked.

**An error instead of silent behavior.** A numeric string doesn't become a number, and `undefined` doesn't turn into `null`. An empty update and an empty filter in `updateOne`, `deleteOne`, `deleteMany`, and other writes are rejected. The full list with reasons is in [Behavior differences](./behavior-differences.mdx). You can't turn strictness off, and that's a deliberate decision, not an oversight. If a switch exists, there's always a reason to flip it.

**Core policies instead of plugins.** Tenants (a field is marked with `@Tenant()`), soft delete, and audit apply to every operation of the model, including aggregation and populate. A hook can't get around them. More in [What data policies are](../policies/overview.mdx).

**Typed aggregation.** Every pipeline stage is a method, and the type of the result row changes after each stage. There are no raw stages, as [Your first aggregation](../aggregation/first-aggregation.mdx) explains.

**Only the latest versions.** Typemo supports only the latest MongoDB, driver, and `bson`, and carries no code for older versions.

## What switching costs [#migration-cost]

The time goes to four places.

You'll have to rewrite schemas as classes. Every field gets an explicit `@Prop(() => T)` type, and `Mixed`, `Object`, and `strict: false` fields are replaced with nested classes or `Spec.map`. The work is mechanical, but where schemas are large, there's a lot of it.

Code that relied on silent casting starts throwing errors. Often these are finds: someone else's data that used to get silently fixed is now visible. But you'll have to catch them, and you may need more tests than before.

Hooks and plugins get rewritten. A plugin function becomes an object, `next()` and `this` acting as a `Query` disappear, and hook events are named with a scope. Third-party Mongoose plugins won't work, see [What Typemo doesn't have](./missing-features.mdx).

You now manage indexes and collections yourself, and nothing is created on startup. `syncIndexes` drops extra indexes, so on a database shared with Mongoose run it with `dryRun`. And `connection.init()` won't stay quiet about a collection of the wrong shape. It throws `SyncError`.

You can move one collection at a time, as described in [Step-by-step migration](./step-by-step.mdx).

## When not to use it [#when-not-to-use]

**The app runs fine**, the schema hardly changes, and the document type doesn't cause bugs. Then you'd pay with rewritten schemas and tests for strictness you don't need.

**The data is essentially shapeless.** One collection holds documents of different kinds with no shared description, `Mixed` fields, arbitrary nested objects. Typemo will require a description for them. Without one you'll be working with the driver, not a model ([`client.unsafeDriver()`](../reference/connection/typemo-client.mdx#client.unsafe-driver)).

**You rely on the Mongoose plugin ecosystem**: third-party plugins for pagination, auto-increment, or encryption. Typemo has its own plugin system ([`@Plugin`](../reference/hooks/plugins.mdx#plugin)), and you'll have to replace the ready-made plugins or write them again.

**You need an old version of MongoDB or the driver.** Typemo doesn't support backward compatibility.
