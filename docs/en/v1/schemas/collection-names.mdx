title: Collection names

A model stores its documents in a **collection**, a named group of documents in the database. If you don't give a name, Typemo derives one from the class name. That's handy for a new database and risky for an existing one. Rename a class that has no explicit name, and the model quietly moves to a different, empty collection. So it's worth knowing how the name is derived and how to set it explicitly. Fields have the same story. A class property and a document field can have different names.

## What you need [#prerequisites]

The client from [Connect to the database](../connection/connect.mdx) and the bank models from the `accounts/*.ts` files.

## Quick start [#quick-start]

Without `collection`, the class name is lowercased and made plural by English rules. The [`collection`](../reference/schemas/schema.mdx#collection) option sets your own name.

## How the name comes from the class [#name-from-class]

The rule is simple: the class name in lowercase and in the plural. Compound names aren't split, so `BankAccount` becomes `bankaccounts`, not `bank_accounts`. The rules are the same as in Mongoose, minus its bugs, so existing collections keep their names. [`CollectionNaming.default`](../reference/schemas/collection-naming.mdx#collection-naming.default) applies them to any string, so you can check the result without creating a model.

<Snippet id="schemas/collection-names/name-from-class" title="accounts/names.ts" twoslash />

Uncountable words (`status`, `data`) and irregular forms (`people`) are taken into account. [`CollectionNaming.pluralize`](../reference/schemas/collection-naming.mdx#collection-naming.pluralize) puts a single word in the plural.

## Connect to an existing collection [#existing-collection]

If the data is already in the database under its own name, set that name explicitly. The model works with that collection, and renaming the class won't move anything. The name is checked when you describe the model. It must not be empty, contain `$`, or start with `system.`, since the server reserves such names. The error shows up right away, not on the first write. You can also run the same check yourself with [`CollectionNaming.check`](../reference/schemas/collection-naming.mdx#collection-naming.check).

## Give a field a different name in the database [#db-field-name]

The [`dbName`](../reference/schemas/prop.mdx#db-name) option stores a field under a different name. In code, filters, and results you write the property name, and in the database the field has its own name. This is for data you don't own. For example, the `email` property maps to the `e` field in documents that already exist.

<Snippet id="schemas/collection-names/db-field-name" title="accounts/client.ts" twoslash />

Two fields with the same `dbName`, or a `dbName` equal to another field's name, give a `ConfigurationError`. Two fields can't share one slot in a document.

## How to choose [#how-to-choose]

Ask yourself: **is there data already?**

- **No, the database is new**: the automatic name will do.
- **Yes**: always set `collection` and `dbName` explicitly.

You also need an explicit name wherever classes get renamed during refactoring. The collection name is part of a contract with the data, not with the code.

## When not to use it [#when-not-to-use]

You can't plug in your own naming function, such as `snake_case`. Neither the client nor the schema has an option that takes one. If you want a different rule, set `collection` in every class.

## Troubleshooting [#troubleshooting]

**The data "disappeared" after a class was renamed.** You renamed `Client` to `Customer`, and queries returned an empty list. Without an explicit name, the new class looks at the `customers` collection, while the data stayed in `clients`. Set `collection: "clients"` explicitly.

**An invalid collection name.** A name with `$` or `system.` is rejected when you describe the model: `ConfigurationError: Client: the collection name "a$b" cannot contain "$" or a null character`. Pick another name.
