Some fields naturally belong together. A shipping address is a city and a street, an order line is a product and a quantity. In MongoDB you keep such a group **inside** the owner document, not in a separate collection. Typemo describes it with a separate class, and there are two options.

- A **nested object** (`@Schema({ nested: true })`), with no identity of its own.
- A **subdocument** (a regular `@Schema()` that extends [`Entity`](../reference/schemas/base-classes.mdx#entity)), with its own `_id`.

The choice decides how you'll find and change the group. An address is changed as a whole or field by field, and nobody needs to look up "address number five". But an order line has to be found and removed by its identifier, so it needs an `_id`. [Work with nested objects](../documents/subdocuments.mdx) shows how to change such objects in a loaded document. Here we declare the schema.

## What you need [#prerequisites]

A model described as in [Define a model](./define-model.mdx). The examples build an online shop order and add an address and order lines to it.

## Quick start [#quick-start]

A nested object is a class with [`@Schema({ nested: true })`](../reference/schemas/schema.mdx#nested). The field in the owner document is declared with that class.

<Snippet id="schemas/nested-and-subdocuments/quick-start" title="orders/order.ts" twoslash />

In the database the address sits inside the order as an ordinary embedded document. You pass the field's value as a plain object, with no need to create an instance of the class. Below we'll cover checks, subdocuments with `_id`, and queries on nested paths.

## Check nested fields [#validate-nested]

A nested class is a full schema. Its fields have types, `required`, and the other options, the same as a document. The path to the field in an error starts with the owner field's name, so you can see right away where the problem is. An unknown field and `null` on a field without `nullable` won't pass either.

<Snippet id="schemas/nested-and-subdocuments/validate-nested" twoslash />

The object itself is optional as long as the owner field has no `required: true`. But if the object is passed, its required fields must be there. An address without a city won't save, while an order without an address is fine.

## Give a nested group its own `_id` [#nested-group-id]

Unlike an address, an order line needs to be found and changed by its identifier: remove one line, change the quantity in it. For that, don't mark the class `nested: true`. Make it extend `Entity` instead. Then Typemo creates an `_id` for each subdocument.

<Snippet id="schemas/nested-and-subdocuments/nested-group-id" twoslash />

You can also pass a subdocument's `_id` yourself, and it's saved as is. Remember that a subdocument has an `_id` only when its class extends `Entity` or declares the field itself. A regular `@Schema()` without `Entity` gets no `_id`, and a `@Schema({ nested: true })` can't have one at all. On the other hand, such a class, unlike a nested object, can have its own hooks. A nested object has no hooks, no discriminators, and no collection options.

As a standalone model, a class without an `_id` won't build (`a model needs an _id field`). A class with `nested: true` can't declare an `_id`, not even by extending `Entity`. That's a `ConfigurationError` (`NestedId: a nested object (no _id, no own hooks) — it declares _id`). You also can't use such a class as a model or give it collection options like `collection`.

## Query and update by a nested path [#nested-path]

You write the path to a nested field with dots. It works both in filters and in update operators, and Typemo checks both the path itself and the value type. A typo in a name or a value of the wrong type won't reach the database.

<Snippet id="schemas/nested-and-subdocuments/nested-path" twoslash />

Replacing a nested object as a whole is fully checked too. `$set: { shipTo: { street: "S" } }` won't pass, because the new object lacks the required `city`. Changing one field at the path `shipTo.city` leaves its neighbors alone. When several clients work with the document, that's safer than replacing the object.

## How to choose [#how-to-choose]

Ask yourself: **will you need to access this group separately, by an identifier?**

- **No** (an address, a first and last name, coordinates): a nested object with `nested: true`. It's simpler and doesn't store an extra `_id`.
- **Yes** (an order line, a comment, an attachment): extend `Entity`. Without an identifier you can't find a line and remove that exact one.
- **The group is embedded in many different documents, and you need a separate collection or queries against it as an entity of its own**: that's no longer a nested object but a separate model with a reference ([Reference other models](./references.mdx)).

## When not to use it [#when-not-to-use]

If the keys inside the object aren't known in advance, like grades by subject or settings by name, a nested class won't fit. Use [`Spec.map`](./maps.mdx). A list of groups of the same kind is an array of subdocuments ([Store lists of values and subdocuments](./arrays.mdx)). And data that grows without limit, like comments on a popular post, is better not embedded. A MongoDB document is limited to 16 MB, so move such data to a separate collection.

## Troubleshooting [#troubleshooting]

**An `_id` in a nested object.** A class with `nested: true` can't contain an `_id`, and the model won't build: `NestedId: a nested object (no _id, no own hooks) — it declares _id`. A nested object is by definition part of a document with no identity of its own. If you need an identifier, remove `nested: true`.

**A field's class without `@Schema`.** The field is declared with a class, but the class itself isn't marked. Building the model throws a `ConfigurationError` with the advice `decorate the class with @Schema()`. Every class used as a field type must be a schema.

**The object was replaced as a whole, and the neighboring fields vanished.** `$set: { shipTo: { city: "Rome" } }` replaces the whole address, and the street disappears. To change one field, write the path: `"shipTo.city"`.

<Callout type="migration">

In Mongoose you describe a nested object with a nested `{}` in the schema or with a separate schema, and a subdocument gets an `_id` automatically, which you turn off with the `_id: false` option. Typemo works the other way around. Only a class that extends `Entity` has an `_id`, and a nested object without identity is declared explicitly with `@Schema({ nested: true })`. Unknown fields of a nested object aren't dropped quietly. They give a `CastError`.

</Callout>
