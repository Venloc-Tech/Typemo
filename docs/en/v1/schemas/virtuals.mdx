A **virtual field** isn't in the database. It's computed on read. Typemo has two kinds.

- A class **getter** builds a value from the document's fields, for example a full name from the first and last names.
- A **virtual relation**, [`@Virtual`](../reference/schemas/virtual.mdx#virtual), loads documents of another model through a reverse reference. For example, all the posts of an author who has no list of posts of their own.

Why bother? So you don't store what you can compute. A copy goes stale, while a computed value is always fresh. Neither kind ends up in writes, in filters, or in a `.lean()` result.

## What you need [#prerequisites]

References as described in [Reference other models](./references.mdx). The examples build a blog with an author and their posts.

## Quick start [#quick-start]

A getter typed [`Computed<T>`](../reference/schemas/field-markers.mdx#computed) is a computed value, and `@Virtual` with the [`VirtualRef`](../reference/schemas/field-markers.mdx#virtual-ref) type is a relation.

<Snippet id="schemas/virtuals/quick-start" title="blog/author.ts" twoslash />

Below we'll go through each kind separately.

## Compute a value from fields [#computed-value]

A getter without a setter is a computed field. It needs no decorator, since the class already says it isn't data. The `Computed<T>` type helps the compiler tell a computed value from a stored one and keep it out of filters and writes. You cast the value with `as Computed<string>`, because the compiler won't turn a plain string into a marker type on its own.

A loaded document has the computed field, but by default it isn't included in results. Neither `.lean()`, nor `.plain()`, nor [`$toPlain()`](../reference/documents/document-api.mdx#to-plain) contains it until you ask for `{ virtuals: true }`. You can't assign a value to it.

<Snippet id="schemas/virtuals/computed-value" twoslash />

You can't query by a computed field, because it isn't in the database. The library says so outright instead of returning an empty result: `StrictModeError: filter: "label" is not a field of Author [unknown-path]`. Express the condition through the real fields the value is computed from.

## Load documents through a reverse reference [#populate-reverse]

The reference lives on the post, since the post stores `author`. To get an author's posts, you don't need to keep a list of identifiers on the author and maintain it. Describing the relation is enough. [`@Virtual`](../reference/schemas/virtual.mdx#virtual) names three things.

- The model: [`ref`](../reference/schemas/virtual.mdx#ref).
- The author's field to match on: [`localField`](../reference/schemas/virtual.mdx#local-field), usually `_id`.
- The post's field that holds the value: [`foreignField`](../reference/schemas/virtual.mdx#foreign-field).

The field itself stores nothing and is filled in only when you ask for `populate`.

<Snippet id="schemas/virtuals/populate-reverse" twoslash />

Without `populate` the field is `undefined`, and the library makes no extra queries. The `count: true` option puts in the number of documents instead of the documents themselves, and [`justOne`](../reference/schemas/virtual.mdx#just-one) puts in one document instead of an array. The flags in the `VirtualRef<M, JustOne, Count>` type must match the options, and the compiler checks that. [`options`](../reference/schemas/virtual.mdx#options), [`match`](../reference/schemas/virtual.mdx#match), and [`perDocumentLimit`](../reference/schemas/virtual.mdx#per-document-limit) set the relation's sort, limit, and filter.

## How to choose [#how-to-choose]

Ask yourself: **is the value computed from fields of the same document?**

- **Yes** (a full name, a total over lines): a getter with `Computed<T>`.
- **The value lives in other documents** (an author's posts, a comment count): `@Virtual`.
- **You need to query and sort by the value in the database**: a virtual field won't do. Store it as a real field and update it when things change.

## When not to use it [#when-not-to-use]

A value you filter by or build an index on must be in the database, and virtual fields have no paths there. For computations over a whole collection there's a pipeline ([Your first aggregation](../aggregation/first-aggregation.mdx)). And remember that a getter runs on every access. If the calculation is heavy, store the result in a field.

## Troubleshooting [#troubleshooting]

**A virtual field is missing from the response.** `author.label` is there, but `$toPlain()` doesn't have it. Computed values aren't included in serialization by default, otherwise readers using `.lean()` would find them missing. Pass `{ virtuals: true }`.

**`@Virtual` on a field of another type.** The field is declared as a string rather than `VirtualRef`, and the compiler stops with `@Virtual "posts": declare the field as VirtualRef<Model, JustOne, Count>`. Declare the field with the type `VirtualRef<Post>`.

**`@Prop` on a getter.** `@Prop` on a method or a getter gives a `ConfigurationError` when the class is declared: `G: @Prop on "x", which is a method or an accessor (getters are virtuals and need no decorator)`. Remove the decorator.

<Callout type="migration">

In Mongoose you describe virtual fields with `schema.virtual(...)`, including relations with `localField` and `foreignField`. In Typemo a class getter typed `Computed<T>` replaces a regular virtual, and the `@Virtual` decorator describes a relation with the same concepts: `ref`, `localField`, `foreignField`, `justOne`, `count`. Without `{ virtuals: true }`, virtual fields are included in neither `lean()` nor `$toPlain()`.

</Callout>
