**Typemo** is an ODM for MongoDB written in TypeScript. An ODM (object-document mapper) describes database documents as classes in your language and gives you read and write methods that understand those classes. In Typemo a class with decorators defines the schema. The library talks to the server through the official `mongodb` driver and has no protocol of its own.

Typemo rests on four decisions. Types are inferred from the class, strictness is always on, you get an error instead of silent behavior, and only the latest versions of the tools are supported. Below we go through each one and name the limits honestly: what Typemo can't do and what you'll have to check yourself.

## Types come from the class [#types-from-class]

Typemo has no separate "what a document looks like" interface sitting next to the schema. A class with decorators defines both the schema that checks data at runtime and the types the compiler sees. They have nowhere to drift apart. Say a bank account looks like this.

From this class the compiler infers the types of filters, updates, projections, and results. Your editor suggests field names, and the result type depends on how you read the data.

The first query selects two fields and returns a `.plain()` result. So the type holds only those fields and `_id`, and `balance` has become a `${bigint}` string you can hand straight to the client. The second query reads through `.lean()`, and `balance` stays a `bigint`. The type follows the query: what you selected and the form you read it in is exactly what it says. [How to read types in your editor](./reading-types.mdx) shows how to read hints like these, and [MongoDB data types](./bson-types.mdx) explains why there are several forms.

Decorators come in two kinds. The core `@venloc/typemo` uses legacy decorators, and the only thing they need in `tsconfig` is `experimentalDecorators`. The core doesn't ask the compiler for field types and stores its metadata itself. A separate package, `@venloc/typemo-decorators`, gives you the same decorators under the TC39 standard. All options and settings still live in the core. The decorator package changes only the syntax.

## Strict by default [#strict-by-default]

**Strictness** is the rule "if a query can't be run unambiguously, that's an error". Typemo won't let through an unknown field in a filter, `undefined` in place of a value, an empty filter in a delete, or a value of the wrong type. You can't turn this off, neither with an option nor with a setting, and a query with a mistake never reaches the server.

Why so strict? MongoDB itself accepts all of the above. A typo in a field name gives you an empty result instead of an error, `undefined` goes out as `null`, and `deleteMany({})` wipes the whole collection.

Strictness is checked twice. The compiler stops the mistake in your editor, and the runtime check catches the same thing in data the compiler never saw: a request body, a file, or a filter built on the fly. All the examples are on the [Strictness](./strictness.mdx) page.

## An error instead of silence [#error-not-silence]

Strictness is one case of a general principle. When the library can either stay quiet or speak up, it speaks up. Hence its own error hierarchy with fields to branch on (`reason`, `path`), with the server's original error kept in `cause`.

For example, a save that would erase fields unknown to the schema from the database doesn't drop them quietly. It throws [`UnknownFieldsError`](../reference/errors/data-errors.mdx#unknown-fields-error). Reads work the same way. [`.orFail()`](../reference/query/reading.mdx#or-fail) turns "nothing found" into a [`DocumentNotFoundError`](../reference/errors/query-errors.mdx#document-not-found-error). Without it, `findOne` honestly returns `null`, and the type warns you about it.

Know the cost of this principle up front. Code that "worked fine" in another library with a typo or an `undefined` will fail in Typemo. It's a hassle on day one, but a month later you won't be digging up corrupted data.

## Latest versions only [#latest-versions-only]

Typemo supports the latest versions of its tools and carries no code for old ones. Here's what was checked on September 26, 2026 and recorded in the repository's `VERSIONS.md`.

- The `mongodb` driver 7.6.0 and `bson` 7.3.3, both in peerDependencies with `^`.
- TypeScript 6.0.3.
- Bun 1.4.0.
- MongoDB: the preview 9.0.0-rc0 and the stable 8.3.11. The tests run against a real server.

There's no backward compatibility with earlier versions of the driver or the server, and nothing was tested on them. If you're on old versions, upgrade first. In return, the library has no "if the driver is old" branches, and its behavior fits on one page instead of a table of exceptions.

## What Typemo doesn't have [#not-in-typemo]

Limits matter as much as features. Here's what you won't find.

- **Schemas without a class.** A model is described only by a class with decorators. The core has no schema as an object or a JSON description, and the model's `schema` property only reads the description (see [The schema at runtime](../schemas/runtime-schema.mdx)).
- **Relaxed strictness.** No option allows unknown fields in a filter or an empty filter in a delete. To delete every document on purpose, there's the explicit `Filters.all` from [Empty filters in writes](../writes/empty-filters.mdx).
- **A protocol or driver of its own.** If Typemo lacks an operation you need, the driver itself is open to you, as [Driver access](../connection/driver-access.mdx) explains. Keep in mind that such calls bypass the library's policies and types.
- **Compatibility with other versions and other ODMs.** Typemo is written from scratch and doesn't copy Mongoose. If you're coming from there, read the "If you're coming from Mongoose" callouts carefully.

There are practical caveats too. Inferring types from classes puts load on the compiler, and in very large projects you'll notice it. The project's tests run in Bun, so on another runtime check your own build. Transactions and change streams need a replica set (several MongoDB servers holding copies of the same data, though one server is enough for transactions). That's how MongoDB itself works.
