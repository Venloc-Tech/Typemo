---
title: Type tests for your models
description: "Make the compiler hold the types of your models, queries, and responses, and check that wrong code doesn't build"
icon: ShieldCheck
---

Half the value of Typemo is in its types. The compiler stops a typo in a field name, a wrong value in a filter, or an extra field in a response. A type test pins that promise down. It fails not at runtime but when `tsc` runs, if the type of a model or a query changed in a way you didn't expect.

These tests run nothing and never touch the database. Only the compiler checks them, so they're fast and need no test database. Write them for models that a lot of code depends on, and for responses that leave your service.

## What you need [#prerequisites]

The account model below and a `tsc --noEmit` run over the test files. Unlike [tests of your app](./testing-apps.mdx), you don't need a server.

## Quick start [#quick-start]

You need a way to say "type A equals type B" so that a mismatch doesn't compile. Two lines do it, no library required.

<Snippet id="testing/type-tests/quick-start" twoslash />

`expectTypeOf` from `bun:test` and `vitest`, `tsd`, and similar tools work on the same principle. If your project already has one, use it. Below is what's worth checking.

## Check the type of a response [#check-response-type]

Say you send accounts out of your service and want to pin down the shape of the response. The type comes from the query itself, so check what the calling code will get.

<Snippet id="testing/type-tests/check-response-type" twoslash />

The `^?` hint shows the inferred type right in the docs. In your test an assertion takes its place. Check whatever matters to you: that `select` narrowed the response, that the hidden field `pin` didn't make it into the `.plain()` result, that `.orFail()` removed `null`. It's the same technique every time.

## Check that wrong code doesn't compile [#check-does-not-compile]

Sometimes you need to pin down the opposite, that a typo in a field stays an error. Tests use `// @ts-expect-error` for this. The compiler expects an error on the next line and fails itself if there isn't one.

<Snippet id="testing/type-tests/check-does-not-compile" twoslash />

The directive doesn't check which error happened. Any error will do. So write next to it what you expect ("a typo in the field name"). And don't put `@ts-expect-error` above a broad expression where a completely different part could fail.

## Check during the build [#check-at-build]

Put the type test files next to your regular tests and include them in `tsconfig` or in a separate `tsconfig.types.json`. Add `"typecheck": "tsc --noEmit"` to `package.json` and run it in CI along with the tests.

The test runner doesn't check types. `bun test` runs the code and skips the types, so without `tsc` a type test checks nothing.

## How to choose [#how-to-choose]

Ask yourself **which promise should break the build**.

- **The shape of a response you send to clients**: pin it with `Equal`.
- **A call that must stay forbidden**: `@ts-expect-error`.
- **Plain "it works"**: ordinary tests are enough.

## When not to use it [#when-not-to-use]

Don't test the types of Typemo itself, or obvious things like `string` being `string`. That's the library's job. Type tests are for your models, your public responses, and your wrappers around queries.

## Troubleshooting [#troubleshooting]

**A type test "passes", but `tsc` doesn't see it.** Either the file isn't in the `include` of your `tsconfig`, or you only run `bun test`. A separate `tsc --noEmit` run checks the types.

**`@ts-expect-error` is no longer needed.** The compiler reports `Unused '@ts-expect-error' directive` because the line stopped being an error. That means the type got looser than intended, and the promise is broken. Find the cause instead of deleting the directive.
