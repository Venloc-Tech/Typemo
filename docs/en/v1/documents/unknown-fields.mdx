---
title: Handle fields that aren't in the schema
description: "See stored fields the schema doesn't know, keep them when you save, and drop them only on purpose"
icon: FileWarning
---

Sometimes the database holds subdocuments with fields your schema doesn't have. Typemo won't lose them silently. [`unknownFieldsOf`](../reference/documents/unknown-fields.mdx#unknown-fields-of) shows such fields, and a save that would erase them ends with an [`UnknownFieldsError`](../reference/documents/unknown-fields.mdx#unknown-fields-error). If you're ready to let them go, pass `{ dropUnknownFields: true }` to [`$save`](../reference/documents/document-api.mdx#save).

Where does such data come from? The schema changed, but old documents stayed as they were. Or two versions of the app work with one database. Or another program writes to the collection. If Typemo erased these fields silently, someone else's data would vanish on the first harmless save. So by default it refuses.

## What you need [#prerequisites]

An order with a customer, lines, and an address. The model is in the [reference](../reference/documents/unknown-fields.mdx). The database holds an order written by an old version of the schema. Its first line has an `oldPrice` field, and its address has `legacyZip`.

## Quick start [#quick-start]

<Snippet id="documents/unknown-fields/quick-start" twoslash />

Below we cover when a save is safe, when it refuses, and what to do then.

## See unknown fields [#see-unknown-fields]

[`unknownFieldsOf`](../reference/documents/unknown-fields.mdx#unknown-fields-of) takes a document, a subdocument, or a collection and returns a list of paths with keys. The keys are remembered when the document is read, so there are no extra queries. Keys at the **root** of the document don't go into the list. A save doesn't rewrite them, so there's nothing to lose there. In `lean()` they're visible as is.

## Change a document safely [#safe-change]

Most changes don't touch unknown fields, because they write exact paths. That covers a subdocument field, `push`, `pull`, `pop`, and `shift`. So normal work with the document goes on, and the data of the old version stays in the database untouched.

There's one exception. If one save combines an edit of a field inside an array element with an operation on the array itself, like `push`, Typemo writes the whole array. Then the unknown fields of its elements are at risk. That's why the example below saves the field edits and the `push` separately.

<Snippet id="documents/unknown-fields/safe-change" twoslash />

## Understand why a save failed [#why-save-failed]

A save refuses if a subdocument with unknown fields **is written again as a whole**. That happens in three cases.

- After `reverse`, `sort`, `splice`, `clear`, or `replace` on an array.
- When a subdocument is replaced through [`$set`](../reference/documents/document-api.mdx#set) or `lines.set(index, …)`.
- On `clear()` of a `Map` of subdocuments.

Typemo tells you before contacting the database, and nothing goes to the database. You can see the refusal in advance without saving anything. [`$getChanges`](../reference/documents/document-api.mdx#get-changes) doesn't throw. It writes the error text under the `$problems` key at the subdocument's path (`lines.1`).

## Decide what to do [#choose-action]

There are three ways out.

- **Extend the schema.** If you need the field, add it to the class, and it becomes known.
- **Migrate the data.** Remove or move the extra keys with a separate migration script.
- **Accept the loss.** Pass `{ dropUnknownFields: true }`.

<Snippet id="documents/unknown-fields/choose-action" twoslash />

The dropped fields are removed both from the database and from the document instances. The address in the example didn't change, so its `legacyZip` is still there.

## How to choose [#how-to-choose]

Ask yourself **whether anyone besides the old code needs these fields**.

- **Yes, another version of the app or another program**: extend the schema, or don't rewrite these subdocuments.
- **No, it's leftovers from an old version**: clean up the data once with a migration instead of accepting the loss on every save.

## When not to use it [#when-not-to-use]

If the data is only read for display, you don't need this mechanism. [`.plain()`](../reference/query/reading.mdx#plain) and [`.lean()`](../reference/query/reading.mdx#lean) don't check unknown fields and save nothing. The mechanism matters when the document will be changed and saved.

## Troubleshooting [#troubleshooting]

**`dropUnknownFields` turned on "just in case".** If you pass `{ dropUnknownFields: true }` to every save, you're back to silent data loss, the very thing Typemo protects you from. Turn the option on only for a specific migration.

**A key is missing from `$toObject`, though the database has it.** Unknown keys don't get into the document or into `$toObject`, but they're visible in `lean()`. That isn't a loss. The key stays in the database until some save rewrites it.

## Coming from Mongoose [#from-mongoose]

<Callout type="migration">

In Mongoose with `strict: true`, fields that aren't in the schema are dropped on read and never reach the document, and replacing a subdocument silently erased them. Typemo has no such mode. Unknown fields are remembered, and a save that would lose them is an error.

</Callout>
