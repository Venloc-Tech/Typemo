This page covers every way to start a **pipeline**, a chain of **stages** through which MongoDB passes documents. It also covers the aggregation query methods, that is, what you get from [`Model.aggregate`](#model.aggregate) and what you can add to it. Database-wide aggregations (`Pipeline.database`, `Pipeline.admin`, `Pipeline.sessions`) are run by [`connection.aggregate`](../connection/connection.mdx#connection.aggregate) and [`client.aggregate`](../connection/typemo-client.mdx#client.aggregate). Their query is the same as the one from `Model.aggregate`. The stages themselves are described in the reference [Stages](./stages.mdx), and the expressions inside stages on the `expr-*` pages.

If you're starting out, read the guide [Your first aggregation](../../aggregation/first-aggregation.mdx) first. This page is a reference, the place you come back to for a detail.

All examples use one model, a shop order. It has required fields, a `BigInt` field (after aggregation it shows the difference between result kinds), an index on `status` (for the `hint`), and a hidden field `internalNote`.

<Snippet id="reference/aggregation/pipeline/intro" title="models/order.ts" twoslash />

The collection holds three orders. Alice, `paid`, 120, 10 points, note `vip`. Bob, `open`, 40, 5 points. Alice, `paid`, 60, 7 points. The results in the `// →` comments come from this data. The identifiers in them are shortened to `"…"`, because the database issues them anew every time the data is loaded.

The pipeline builder is immutable. Each stage returns a new builder, and the previous one stays as it was. The compiler catches mistakes in the shape of fields, and row types are computed by stage: after `group`, a row is no longer an order but a group. For the builder and its stages, see [Stages](./stages.mdx).

## Pipeline.from [#pipeline.from]

`Pipeline.from` starts a pipeline over a model's collection. That's how you build an aggregation ahead of time, separately from a query. You get a builder, add stages, and call [`.plan()`](#pipeline-builder.plan) at the end, which produces a ready plan for [`Model.aggregate`](#model.aggregate). You don't usually call `Pipeline.from` yourself. `Model.aggregate((p) => …)` does it for you and passes such a builder to the callback.

Pipeline rows start as the model's stored documents, but **without hidden fields** ([`Hidden`](../../schemas/hidden-and-sensitive.mdx)). A pipeline that silently read a hidden field would put a password or a note into a report, so Typemo removes such fields in the first stage. To keep a hidden field you need, name it in `options.include`.

<Snippet id="reference/aggregation/pipeline/pipeline-from" twoslash />

<Returns type="PipelineBuilder<…, &quot;collection&quot;, &quot;empty&quot;>">

An empty builder over the source's stored documents. While it has no stages, it has no [`.plan()`](#pipeline-builder.plan). The compiler rejects an empty pipeline.

</Returns>

<Params>
<Param name="source" type="EntityClass | Model" required>

An entity class or a model. The source sets the field types and the collection the pipeline reads from.

</Param>
<Param name="options.hint" type="string | { [path]: 1 | -1 | &quot;text&quot; | … }">

The index the server must use. Give a name (`"status_1"`) or a key specification (`{ status: 1 }`). The compiler checks the paths, and `Pipeline.from` also checks at run time that such an index is declared in the schema.

</Param>
<Param name="options.collation" type="CollationOptions">

The string sorting rule for the whole aggregation.

</Param>
<Param name="options.allowDiskUse" type="boolean">

Lets stages write temporary files to disk when memory runs out.

</Param>
<Param name="options.comment" type="string">

A comment on the command. It's visible in the server log and in the profiler. The query's [`.comment`](#comment) does the same.

</Param>
<Param name="options.batchSize" type="number">

How many documents the cursor gets in one exchange with the server. The query's [`.batchSize`](#batch-size) does the same.

</Param>
<Param name="options.bypassDocumentValidation" type="boolean">

Skips checking documents against the collection's validation rules when the `$out` and `$merge` stages write into it.

</Param>
<Param name="options.include" type="readonly HiddenPath[]">

Paths of hidden fields to keep in the rows. The compiler accepts only paths marked `Hidden` and adds them to the row type.

</Param>
</Params>

<FullType>

<Snippet id="reference/aggregation/pipeline/pipeline-from-2" />

</FullType>

### Hidden fields [#hidden-fields]

Without `include`, the hidden field is in the rows neither in the type nor in the data. With `include`, it appears in both.

<Snippet id="reference/aggregation/pipeline/hidden-fields" twoslash />

The same query without `include` would return this row without the `internalNote` key. You can't include a hidden field through `Orders.aggregate((p) => …)`, because the callback has no `options`. If you need it, build the plan with `Pipeline.from(…, { include })` and pass it to `aggregate`.

### Index hint [#index-hint]

`hint` is checked against the schema at the moment you call `Pipeline.from`, not when the query reaches the database. If the schema doesn't declare such an index, you get the error right away.

<Snippet id="reference/aggregation/pipeline/index-hint" twoslash />

A path that isn't in the model stops the compiler. If the path exists but has no index (`total` isn't indexed), Typemo stops it.

<Snippet id="reference/aggregation/pipeline/index-hint-2" />

Without this check, the server would reject the `hint`, and only at run time. The error would come from the database, not from the place where you wrote it.

## Pipeline.database [#pipeline.database]

`Pipeline.database` starts a pipeline that reads the whole database instead of a collection. You need it for aggregations that have no documents of their own. The [`documents`](./stages.mdx#documents) stage produces literal documents, and [`listLocalSessions`](./stages.mdx#list-local-sessions) and [`listClusterCatalog`](./stages.mdx#list-cluster-catalog) read internal server data.

Such a plan has no model, and [`Model.aggregate`](#model.aggregate) doesn't accept it. [`connection.aggregate`](../connection/connection.mdx#connection.aggregate) (this connection's database) and [`client.aggregate`](../connection/typemo-client.mdx#client.aggregate) (the client's default database) run it. It's an ordinary Typemo operation, with transactions, `timeoutMS`, Typemo errors, a cursor, and `explain`, but without hooks. For examples, see the guide [Database-level queries](../../aggregation/database-level.mdx).

<Snippet id="reference/aggregation/pipeline/pipeline-database" twoslash />

<Returns type="PipelineBuilder<never, &quot;database&quot;, &quot;empty&quot;>">

An empty builder not tied to a collection. A row starts as `never`, and the stages set the row types.

</Returns>

<Params>
<Param name="options" type="AggregateOptions<never>">

The same settings as in [`Pipeline.from`](#pipeline.from): `collation`, `allowDiskUse`, `comment`, `batchSize`, and `bypassDocumentValidation`. They go into the command as they are. `hint` and `include` make no sense here, because the plan has no schema to check them against.

</Param>
</Params>

<FullType>

<Snippet id="reference/aggregation/pipeline/pipeline-database-2" />

</FullType>

The database where the plan runs depends on what launched it. `connection.aggregate` takes its connection's database, and `client.aggregate` takes the client's default database. Pass such a plan to `Model.aggregate`, and you get an error instead of a read from someone else's database. The error text was obtained by running it.

<Snippet id="aggregation/system/troubleshooting" />

The internal stages are tied to the place they run, and the compiler checks this. [`documents`](./stages.mdx#documents) and [`listClusterCatalog`](./stages.mdx#list-cluster-catalog) are available in both `Pipeline.database()` and `Pipeline.admin()`. [`currentOp`](./stages.mdx#current-op) exists only in `Pipeline.admin()`, and [`listSessions`](./stages.mdx#list-sessions) only in `Pipeline.sessions()`.

## Pipeline.sessions [#pipeline.sessions]

`Pipeline.sessions` starts a pipeline over the `config.system.sessions` collection. The server accepts the [`listSessions`](./stages.mdx#list-sessions) stage only there. Over any other collection it answers `$listSessions may only be run against config.system.sessions`.

That's why `listSessions` exists only on `Pipeline.sessions()` and not on `Pipeline.from`, `Model.aggregate`, `Pipeline.database()`, or `Pipeline.admin()`. The compiler won't let you put a stage where the server would reject it anyway. After it, the ordinary stages are available (`match`, `project`, `sort`, `group`).

<Snippet id="reference/aggregation/pipeline/pipeline-sessions" twoslash />

`client.aggregate` and `connection.aggregate` run the plan. It always goes to `config.system.sessions`, no matter which connection you launch it from. In operation events, `collection` is `"system.sessions"` and `database` is `"config"`.

<Returns type="PipelineBuilder<never, &quot;sessions&quot;, &quot;empty&quot;>">

An empty builder tied to `config.system.sessions`. The plan is read-only and has no [`out`](./stages.mdx#out) or [`merge`](./stages.mdx#merge).

</Returns>

<Params>
<Param name="options" type="AggregateOptions<never>">

The same settings as in [`Pipeline.database`](#pipeline.database).

</Param>
</Params>

<FullType>

<Snippet id="reference/aggregation/pipeline/pipeline-sessions-2" />

</FullType>

Put `listSessions` in the wrong place or add a write, and the compiler stops you right away. The compiler produced these messages.

<Snippet id="reference/aggregation/pipeline/pipeline-sessions-3" twoslash />

The server doesn't write fresh sessions to `config.system.sessions` immediately, so on a freshly started server the result is empty. The [`listLocalSessions`](./stages.mdx#list-local-sessions) stage in `Pipeline.database()` shows the sessions that one node knows and hasn't written yet.

## Pipeline.update [#pipeline.update]

`Pipeline.update` builds a **pipeline update**. These are the stages that `updateOne` and `updateMany` accept instead of an ordinary document with operators. With it, a field is computed from other fields of the same document: double an amount, or join a name from two parts. An ordinary operator like `$set` can't do that.

In this mode the builder has only six stages: [`addFields`](./stages.mdx#add-fields), [`set`](./stages.mdx#set), [`project`](./stages.mdx#project), [`unset`](./stages.mdx#unset), [`replaceRoot`](./stages.mdx#replace-root), and [`replaceWith`](./stages.mdx#replace-with). It has no other methods, so the compiler won't let you add `group` where the server would reject it anyway.

<Snippet id="reference/aggregation/pipeline/pipeline-update" twoslash />

<Returns type="PipelineBuilder<StoredDocOf<Src>, &quot;update&quot;, &quot;empty&quot;>">

An empty builder in update mode. Take the result through [`.build()`](#pipeline-builder.build), not `.plan()`. It isn't an aggregation but a list of stages for an update command.

</Returns>

<Params>
<Param name="source" type="EntityClass | Model" required>

The entity whose document the pipeline updates. It's needed only for the type, and the rows are its stored documents.

</Param>
</Params>

<FullType>

<Snippet id="reference/aggregation/pipeline/pipeline-update-2" />

</FullType>

The model's [`updateOne`](../writes/writes.mdx#update-one) and [`updateMany`](../writes/writes.mdx#update-many) accept such a pipeline.

Before sending, Typemo checks the pipeline against the model's schema. The update stops with a Typemo error if the pipeline does an `unset` of a required field, sets a constant of the wrong type, loses an immutable field, or is empty. For example, `unset("title")` on a model with a required `title` gives `ValidationError: Validation failed: "title": update.0.$unset: the field is required; the pipeline would remove it [required]`, and an empty pipeline gives `QueryError: an update pipeline needs at least one stage`. All the checks are described in the reference [Pipeline updates](../writes/pipeline-updates.mdx#update-pipelines).

## Pipeline.view [#pipeline.view]

`Pipeline.view` builds a **view definition**: a pipeline stored on the server over another collection and read like an ordinary collection. A view stores not data but a way to get it.

You don't usually call `Pipeline.view` directly, because [`TypedView.define`](../collections/typed-view.mdx#typed-view.define) does it. The method is useful when you create a view yourself and want a checked definition.

The pipeline is checked against the view class. The rows must contain all the class's fields with compatible types, and if a field is missing or has the wrong type, the compiler names it. In view mode the builder has no [`out`](./stages.mdx#out) or [`merge`](./stages.mdx#merge), because a view can't write.

<Snippet id="reference/aggregation/pipeline/pipeline-view" twoslash />

<Returns type="ViewDefinition">

A frozen object with two fields. `viewOn` is the name of the source collection, and `pipeline` is an array of serialized stages. You can pass the object to the driver's `create` command. This method doesn't create the view collection itself.

</Returns>

<Params>
<Param name="view" type="EntityClass" required>

The view row class. It's needed for type checking and isn't used at run time.

</Param>
<Param name="definition.on" type="EntityClass | Model" required>

The source: the collection or another view that the pipeline reads.

</Param>
<Param name="definition.pipeline" type="(p) => ViewPipelineCheck<R, View>" required>

The callback receives an empty builder in view mode and returns a pipeline with at least one stage. If the pipeline's rows don't fit the class, the callback returns a description of the problem instead of a pipeline. [`ViewPipelineCheck`](#view-pipeline-check) does that, and the compiler stops the call.

</Param>
</Params>

<FullType>

<Snippet id="reference/aggregation/pipeline/pipeline-view-2" />

</FullType>

`ViewDefinition` is a public type with the fields `viewOn: string` and `pipeline: readonly PipelineStage[]`.

### The pipeline doesn't fit the view class [#pipeline-class-mismatch]

The view class describes the rows you'll read, so the pipeline must produce all its fields with compatible types. People usually go wrong in three ways: a class field gets lost in the rows, a field changes type, or `_id` disappears. The compiler produced the text of each error.

<Snippet id="reference/aggregation/pipeline/pipeline-class-mismatch" twoslash />

The first row lost `_id` (the class got it from `Entity`), the second lost `total`, and the third made `total` a string. The compiler answers each the same way: `Property 'error' is missing in type 'PipelineBuilder<…>' but required in type 'PathError<…>'`. The reason is written in the `PathError` itself: `the pipeline result does not match the fields of the view class: check the field "_id"` (in the second and third rows the field is named `"total"`).

You can't write a result in a view at all. In view mode the builder has no `out` or `merge`, so `p.out("copy")` doesn't compile, and a callback that returns a write gets the reason `a view pipeline cannot end with $out or $merge (MongoDB does not allow them in a view)`.

## ViewPipelineCheck [#view-pipeline-check]

`ViewPipelineCheck<R, V>` is the type [`Pipeline.view`](#pipeline.view) uses to decide what to return from the pipeline callback. If the pipeline's rows `R` fit the class `V`, the type equals `R` itself and nothing changes. Otherwise it equals a `PathError` with the reason text, and the compiler prints that text instead of a long intersection of the pipeline type with the error type. You don't need to read the type itself. It exists so the error shows "check the field "_id"" and not a wall of type output.

The type checks two conditions. The pipeline must not end with a write, because the server forbids `$out` and `$merge` in a view. And every field of the class must be in the pipeline's rows with a compatible type. `_id` is required if the class declares it (`Entity` provides it) and optional if it doesn't.

<FullType>

<Snippet id="reference/aggregation/pipeline/view-pipeline-check" />

</FullType>

A write target is also checked against the row's fields. For [`out`](./stages.mdx#out) and [`merge`](./stages.mdx#merge), the same field check applies to the target model.

## Pipeline.watch [#pipeline.watch]

`Pipeline.watch` builds a pipeline for a **change stream**. The rows of such a pipeline are driver events (`ChangeStreamDocument`), not model documents. That's why you can filter and rewrite events but can't group them.

Only [`match`](./stages.mdx#match), [`project`](./stages.mdx#project), [`addFields`](./stages.mdx#add-fields), [`set`](./stages.mdx#set), [`unset`](./stages.mdx#unset), [`replaceRoot`](./stages.mdx#replace-root), [`replaceWith`](./stages.mdx#replace-with), and [`redact`](./stages.mdx#redact) are available. You can put [`changeStreamSplitLargeEvent`](./stages.mdx#change-stream-split-large-event) at the very end.

<Snippet id="reference/aggregation/pipeline/pipeline-watch" twoslash />

An empty builder in change stream mode. The rows are change events of the source's documents.

</Returns>

<Params>
<Param name="source" type="EntityClass | Model" required>

The entity whose collection the change stream listens to.

</Param>
</Params>

<FullType>

<Snippet id="reference/aggregation/pipeline/pipeline-watch-2" />

## PipelineBuilder.plan [#pipeline-builder.plan]

`.plan()` finishes a top-level pipeline and returns an **aggregation plan** (`AggregatePlan`), a frozen object with the source, the stages, and the options. [`Model.aggregate`](#model.aggregate), [`connection.aggregate`](../connection/connection.mdx#connection.aggregate), and [`client.aggregate`](../connection/typemo-client.mdx#client.aggregate) accept it.

The method exists only on a builder that already has a stage, and only on those that run as a standalone aggregation: `Pipeline.from`, `Pipeline.database`, `Pipeline.admin`, and `Pipeline.sessions`. The plan knows neither a model nor launch parameters (`session`, `timeoutMS`), so it runs on any model of its collection. How it differs from the plan a query returns is explained in the section [The two plan forms](#plan-forms).

<Snippet id="reference/aggregation/pipeline/pipeline-builder-plan" twoslash />

<Returns type="AggregatePlan<Row>">

A frozen plan with the fields `op` (always `"aggregate"`), `target` (where the pipeline reads from), `pipeline` (the stages), and `options` (`hint`, `collation`, `allowDiskUse`, `comment`, `batchSize`, `bypassDocumentValidation`, and `include` from `Pipeline.from(…, options)`). `target` comes in three kinds: `{ kind: "collection", collection, entity, discriminator }`, `{ kind: "database", admin }`, and `{ kind: "sessions" }`. The row type (`Row`) lives only in the type and doesn't exist at run time.

</Returns>

<FullType>

<Snippet id="reference/aggregation/pipeline/pipeline-builder-plan-2" />

</FullType>

The compiler rejects an empty pipeline. If the builder comes from untyped code, Typemo itself throws the error.

<Snippet id="reference/aggregation/pipeline/pipeline-builder-plan-3" />

The server would reject an empty aggregation too, but the Typemo text names the reason and the cure.

## PipelineBuilder.build [#pipeline-builder.build]

`.build()` returns only the array of stages, without the source and options. You need it where the stages don't go into a Typemo aggregation: a sub-pipeline (`lookup`, `facet`), a view definition, an update or change stream pipeline, or the driver.

<Snippet id="reference/aggregation/pipeline/pipeline-builder-build" twoslash />

<Returns type="readonly PipelineStage[]">

A frozen array of serialized stages. Each stage is an object like `{ $match: … }`.

</Returns>

## Model.aggregate [#model.aggregate]

`Model.aggregate` runs an aggregation over the model's collection. It passes documents through a pipeline and returns the result rows. It's the most common path. For order reports, sums, grouping, and joining collections, you write a callback, and Typemo passes it a builder over the stored documents.

Like [`find`](../query/reading.mdx#model.find), the method doesn't go to the database right away. It returns an **aggregation query** (`AggregateQuery`) that goes to the server on `await`. You can add options to the query and get the result as an array, a cursor, the server's plan, or a result checked against a schema.

<Snippet id="reference/aggregation/pipeline/model-aggregate" twoslash />

<Returns type="AggregateQuery<Row>">

An aggregation query. After `await` you get an array of rows, and the compiler computes the row type by stage. The query is immutable: each method (`.plain()`, `.session()`, …) returns a new query, and the old one doesn't change.

</Returns>

<Params>
<Param name="build" type="(p) => StagedPipeline | TerminalPipeline | AggregatePlan" required>

A callback that receives an empty builder over the model's stored documents, or a ready plan from [`Pipeline.from`](#pipeline.from). The pipeline must have at least one stage. The [`out`](./stages.mdx#out) and [`merge`](./stages.mdx#merge) stages finish the pipeline and turn the query into a write, and such a query has no rows.

</Param>
<Param name="options.session" type="ClientSession | null">

An explicit session. `null` runs the query outside the current transaction. The [`.session`](#session) method does the same.

</Param>
<Param name="options.timeoutMS" type="number">

A client-side time limit in milliseconds. The [`.timeoutMS`](#timeout-ms) method does the same.

</Param>
<Param name="options.policy" type="PolicyValues">

Policy values for this aggregation: tenant, actor, and soft delete mode. The [`.policy`](#policy) method does the same.

</Param>
</Params>

<FullType>

<Snippet id="reference/aggregation/pipeline/model-aggregate-2" />

</FullType>

### Rows without a schema [#rows-without-schema]

A model's stored documents pass through the schema, but aggregation rows don't. The result of `group` or `project` has no class to build it from. So the values stay as the driver returned them: an identifier is an `ObjectId`, and the `points` field is a `bigint`. [`.plain()`](#plain) shows how to hand them to a client.

<Snippet id="reference/aggregation/pipeline/rows-without-schema" twoslash />

### One query, one run [#one-query-one-run]

A read query runs once per object. A second `await` of the same query returns the same rows and doesn't go to the database. To run it again, call [`.exec({ force: true })`](#exec).

<Snippet id="reference/aggregation/pipeline/one-query-one-run" twoslash />

### Another collection [#foreign-collection]

A plan is built over one collection. Give a model the plan of another collection, and the error comes right at the call, before any contact with the database. A model's policies belong to its collection and don't cover someone else's data. The texts differ for a plan of another collection, a database plan, and a sessions plan, and they were obtained by running them.

<Snippet id="reference/aggregation/pipeline/foreign-collection" />

[`connection.aggregate`](../connection/connection.mdx#connection.aggregate) and [`client.aggregate`](../connection/typemo-client.mdx#client.aggregate) run database and sessions plans. If the first argument is neither a callback nor a plan, the method throws a `QueryError`.

<Snippet id="reference/aggregation/pipeline/foreign-collection-2" />

### Transactions and policies [#transactions-and-policies]

Inside [`transaction`](../transactions/transactions.mdx#transaction), the query automatically runs in the transaction's session.

<Callout type="migration">

In Mongoose, `Model.aggregate` has no row types, the result is always `any[]`, and hidden (`select: false`) fields get into the pipeline as they are. In Typemo the row type is computed by stage, and the first stage removes hidden fields.

</Callout>

## .plain [#plain]

`.plain()` turns rows into ordinary objects that are safe to serialize to JSON and hand to a client. Identifiers, `bigint`, `Decimal128`, and `UUID` become strings, `Date` and `RegExp` stay, binary data becomes `Uint8Array`, and a vector becomes an array of numbers.

<Snippet id="reference/aggregation/pipeline/plain" twoslash />

An aggregation query has no `.lean()`, and doesn't need one. Aggregation rows are never model documents. They're always data as the driver returned it. There's only one other kind of result, `.plain()`.

<Returns type="AggregateQuery<PlainValue<Row>>">

A new query with the same pipeline. The rows are the `.plain()` result, and the row type is `PlainValue` of the previous one. A repeated `.plain()` returns the same query, so rows aren't converted twice. After it, [`.parse`](#parse), [`.expect`](#expect), and [`.cursor`](#cursor) are available.

</Returns>

<FullType>

<Snippet id="reference/aggregation/pipeline/plain-2" />

</FullType>

A row has no schema, so a stored `Map` field in it is an ordinary object, and `.plain()` leaves it an object. Only a schema can turn it into a `Map`. For the kinds of result, see the concept [How to read types in your editor](../../concepts/reading-types.mdx).

## .cursor [#cursor]

`.cursor()` returns rows one at a time as they're read from the database, instead of collecting the whole result into an array. You need it for large reports and exports: memory holds one row, not the whole result.

A cursor of rows. Its methods are described in the reference [Cursor](../query/cursor.mdx). If the query had [`.plain()`](#plain), [`.parse`](#parse), or [`.mask`](#mask), the cursor applies them to each row at the moment it reads it.

</Returns>

### A write through aggregation [#write-via-aggregation]

An aggregation that ends in [`out`](./stages.mdx#out) or [`merge`](./stages.mdx#merge) is a write, and Typemo treats it differently. A second `await` of the same query doesn't repeat the write but throws an error. A silent repeated write would erase or double the result.

<Snippet id="reference/aggregation/pipeline/write-via-aggregation" twoslash />

<Snippet id="reference/aggregation/pipeline/write-via-aggregation-2" />

If you really want to write again, say so explicitly: `write.exec({ force: true })`. The error names `aggregate`, the method you called.

## The two plan forms [#plan-forms]

In aggregation, "plan" names two different objects. They look alike, but you get them differently and use them for different things, so they're easy to mix up.

**`AggregatePlan`** is the pipeline plan. The builder's [`.plan()`](#pipeline-builder.plan) returns it. It holds the source (`target`), the stages, and the pipeline options, with no model and no launch parameters. That's why you can build a plan in one module and run it anywhere. A collection plan goes to a model of the same collection through [`Model.aggregate`](#model.aggregate), and a database or sessions plan goes through [`connection.aggregate`](../connection/connection.mdx#connection.aggregate) and [`client.aggregate`](../connection/typemo-client.mdx#client.aggregate).

**`AggregateExecutionPlan`** is the execution plan. The query's [`.build()`](#build) returns it once the pipeline is tied to a model. It holds the model's entity (`entity`), the stages (`pipeline`), the pipeline options (`aggregateOptions`), and the parameters of this run (`options`: `session`, `timeoutMS`, `policy`, `comment`, `batchSize`, and so on). The operation pipeline runs exactly this. The type is exported so a function can accept and return such a plan, but you rarely build one by hand.

<Snippet id="reference/aggregation/pipeline/plan-forms" twoslash />

The stages are the same in both plans. What differs is the wrapper and what's added to it. `AggregatePlan` has `target`, and `AggregateExecutionPlan` has `entity` instead. The pipeline options (`hint`, `collation`, `allowDiskUse`, and so on) live in `options` in the first and in `aggregateOptions` in the second, because `options` is taken by the launch parameters. There's no way back. You can't pass an `AggregateExecutionPlan` to `aggregate`, which accepts only an `AggregatePlan`.

<FullType>

<Snippet id="reference/aggregation/pipeline/plan-forms-2" />

</FullType>

A question tells you which plan you need: are you describing a pipeline or looking at what will run? If you're describing, take the `AggregatePlan` from `.plan()`. If you're debugging or writing a test for the parameters that went into the operation, look at the `AggregateExecutionPlan` from `.build()`. For a database plan (`connection.aggregate`), `entity` is an internal class named after the method called (`connection` or `client`), because such an aggregation has no model.

## When not to use it [#when-not-to-use]

Do you need model documents with methods and virtual fields, not report rows? Use [`find`](../query/reading.mdx#model.find), because aggregation doesn't return documents. For a simple count or a list of unique values, there are [`countDocuments`](../query/reading.mdx#model.count-documents) and [`distinct`](../query/reading.mdx#model.distinct), which are simpler and need no pipeline.

For a result that's stored permanently, see [`TypedView.define`](../collections/typed-view.mdx#typed-view.define) (a view that's computed on every read) and [materialized views](../collections/materialized.mdx) (the result is written to a collection).
