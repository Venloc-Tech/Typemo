A **contract** is a description of the shape of a response. You write it yourself, and Typemo compares it with what the query actually returns. You need a contract where the response shape is an agreement with other code, for example an API response body, a queue message, or the input of another service. Add a field to the model or change the query, and the response won't change unnoticed, because the contract won't allow it. There are two kinds of checks. At compile time, [`.expect`](#expect) and [`Contract.check`](#contract.check) compare the result type with your description and cost nothing at run time. At run time, [`.parse`](#parse) runs every row through a data validation schema.

If you're new to this, read the guide [Checking the response shape](../../queries/contracts.mdx) first. This page is the reference.

All the examples use one user model. It has a required name, an optional age, and a hidden password hash.

## .expect [#expect]

`.expect<Shape>()` compares a result row with the `Shape` description **exactly**. Fields, optionality, `null`, and value types must match at any depth. If everything matches, the query comes back as it was, and the result type doesn't change. If not, the call doesn't compile, and the error names the difference. At run time the method does nothing and costs nothing.

<Snippet id="reference/query/contracts/expect" twoslash />

`Selected<User, "name">` describes a `.plain()` result row with the `name` field and `_id`, which is always there. The query returned exactly that, so the check passes.

<Returns type="the same query">

The same builder, and the result type doesn't change. The method runs nothing.

</Returns>

<Params>
<Param name="Shape" type="type parameter" required>

The expected row. Any type works, most often [`Selected`](#selected), [`SelectedLean`](#selected-lean), or [`SelectedJson`](#selected-json).

</Param>
</Params>

### What the error shows [#error-contents]

The error names three kinds of differences. `missing` means the field is in the contract but not in the result. `extra` means the field is in the result but not in the contract. `mismatch` means the field is in both, but the type, `null`, or optionality differs. Paths are dot-separated, an array element is written as `[]`, and the result itself as `(root)`.

`extra` always counts as an error. TypeScript would silently drop an extra field when assigning a value, but a contract exists precisely so that an extra field doesn't get into the response unnoticed. Say the query also selected `age`, and the contract doesn't know about it.

<Snippet id="reference/query/contracts/error-contents" twoslash />

### Only for lean and plain [#expect.lean-and-plain-only]

A contract describes data, while a document is an object with methods. So `.expect` works on `.lean()` and `.plain()`, and doesn't compile on a document. For a document, check the result of its method: `Contract.check<Shape>()(doc.$toPlain())`, see [`Contract.check`](#contract.check).

## .parse [#parse]

`.parse(schema)` checks every row **at run time**. It protects you from data in the database that isn't what the type promises. An old version of the app, a script, or the driver directly could have written it. Any schema that follows the Standard Schema spec works (zod, valibot, arktype, or your own), that is, an object with a `"~standard"` field. The query result becomes whatever the schema returned, because a schema can not only check rows but also transform them.

<Returns type="ParsedQuery">

A query that gives the schema's result after `await`. For `find` it's an array, for `findOne` a row or `null`. If nothing is found, `null` stays `null` and the schema doesn't check it. The query is terminal. It has `exec`, `cursor` (for lists), and `expect`, and no other builder methods, because the query is fixed before parsing.

### Validation error [#validation-error]

If a row fails the schema, the query ends with a [`ValidationError`](../errors/data-errors.mdx#validation-error). There is one error for the whole query, and it holds the issues for all rows, with the path starting from the row number. Bob, without a name of the required length, is second, so his path starts with `1`.

<Snippet id="reference/query/contracts/validation-error" twoslash />

### Cursor [#cursor]

For lists, `.parse` has a [`.cursor()`](./cursor.mdx). Rows are checked as they're read, and the first invalid one ends the read with a `ValidationError` carrying the row number in the stream. The cursor is closed at that point.

### Only for lean and plain [#parse.lean-and-plain-only]

A document isn't plain data, so `.parse` works on `.lean()` and `.plain()`. On a document the method doesn't compile, and a call from code without types throws a `QueryError`.

<Snippet id="queries/contracts/troubleshooting-2" />

### When not to use it [#when-not-to-use]

If you trust the data in the database and only need to pin down the response shape, run-time checks are extra. Use [`.expect`](#expect), which is free. The schemas of model fields check the data you write, not the data you read. Typemo itself doesn't check rows on read.

## Contract.check [#contract.check]

`Contract.check<Shape>()(value)` compares a value with a description at compile time. It returns the same value, but typed as `Shape`. If the value's type doesn't match `Shape` exactly, the call doesn't compile. It's the same kind of check as [`.expect`](#expect), but for any value, not only a query result. It works especially well for documents: `Contract.check<Shape>()(doc.$toPlain())`.

<Snippet id="reference/query/contracts/contract-check" twoslash />

There are two pairs of parentheses on purpose. The first fixes the expected type, and the second takes the value, so TypeScript infers its type itself.

<Returns type="Shape">

The value you passed, without copying and without run-time checks.

## Selected [#selected]

`Selected<Entity, Fields, Overrides>` describes the row that [`.plain()`](./reading.mdx#plain) and `$toPlain()` return. `_id` is included by default, and in a `.plain()` result it's a string. `"-_id"` among the fields removes it. Fields are listed by name, and optional fields stay optional.

<Snippet id="reference/query/contracts/selected" twoslash />

The third parameter, `Overrides`, is for fields whose shape depends on the query. These are virtual references filled in through `populate`, and nested documents. In it you give the shape of the populated field, for example `{ author: Selected<User, "name" | "-_id"> }`. The override key must be one of the selected fields.

<FullType>

<Snippet id="reference/query/contracts/selected-2" />

</FullType>

`SelectedFields` is the names you can select. These are data fields, virtual references (with an override), getter virtual fields, and `"-_id"`. `SelectedOverrides` constrains the `Overrides` parameter. A key outside the selected fields turns into a readable error, `the override "…" is not one of the selected fields`.

## SelectedLean [#selected-lean]

`SelectedLean<Entity, Fields, Overrides>` describes the same for the `.lean()` result. Its values are as the driver returns them: `_id` is an `ObjectId`, 64-bit numbers are `bigint`, and `Map` fields are objects. A `.lean()` result has no getter virtual fields. Check against `.lean().expect<…>()`.

<Snippet id="reference/query/contracts/selected-lean" twoslash />

<FullType>

<Snippet id="reference/query/contracts/selected-lean-2" />

</FullType>

`SelectedLeanFields` is the allowed names for a `.lean()` contract. They are the same as in `SelectedFields`, minus the getter virtual fields.

## SelectedJson [#selected-json]

`SelectedJson<Entity, Fields, Overrides>` describes the same for the `$toJSON()` result. In it identifiers, dates, 64-bit numbers, and `Decimal128` are strings, and a `Map` is an object. Use it for API responses that you build from a document.

## Other types [#other-types]

`ContractCheck<Actual, Expected>` underlies all the checks. It gives `true` if the types match exactly, and otherwise a report like `{ missing: "email"; extra: "password" }`. `ContractMismatch` is the report itself, `ExpectRows` is the `this` parameter of the `.expect` method, and `ContractArgumentError` is a readable error for a wrong contract argument. You usually don't write them by hand. They show up in editor hints and in error texts.
