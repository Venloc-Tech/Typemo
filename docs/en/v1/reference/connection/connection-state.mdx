`ConnectionState` is the type of the client state, a string with five possible values. Read the current state through [`client.state`](./typemo-client.mdx#client.state), and get notified about changes through [`client.onStateChange`](./typemo-client.mdx#client.on-state-change). It's useful for readiness checks ("is the server available?"), metrics, and logs. You don't need to steer operations by it, because operations wait for the connection and report errors on their own.

If you're new here, read the guide [Connect to the database](../../connection/connect.mdx) first. This page is a reference.

Typemo derives the state from the driver's public topology events (`topologyDescriptionChanged`). One rule covers every topology: a single server, a replica set (several MongoDB servers holding copies of the same data, though one server is enough for transactions), a sharded cluster, and a load balancer. Typemo doesn't read the driver's internal fields.

## Transitions [#transitions]

A client starts in `idle`. `connect` moves it to `connecting`, a successful connection moves it to `connected`, and `close` makes it `closed` at any moment. With a real server the subscriber receives exactly this sequence. It doesn't get the initial `idle`, only the changes.

<Snippet id="reference/connection/connection-state/transitions" twoslash />

If the connection fails, the client goes back to `idle`. We pointed it at an address where nobody listens. The subscriber saw `connecting`, then `idle`, and `connect` finished with a `ConnectionError` with `failure: "server-selection"`. After that you can call `connect` again.

Between `connected` and `unavailable` the client switches by itself, on driver events. It moves to `unavailable` when the last server with data disappears, and back to `connected` when a server shows up. Topology events don't affect `idle` and `closed`. A client that never connected, or one that's already closed, stays as it was.

There's no separate "reconnecting" state, and `unavailable` plays that role. Operations don't fail right away in the meantime. They wait for the driver to select a server, within `timeoutMS`.

### When you don't need the state [#when-not-to-use]

To wait for the connection, call [`client.ready`](./typemo-client.mdx#client.ready). It waits for readiness and fails on a timeout, so you don't have to poll `client.state` in a loop. To find out whether the server supports transactions, use [`client.supportsTransactions`](./typemo-client.mdx#client.supports-transactions).
