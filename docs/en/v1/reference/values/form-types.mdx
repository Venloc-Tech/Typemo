The result of a query or a document method has not only data but also a type the compiler infers. This page describes the public types those results are built from. `Lean` stands for `.lean()`, `Plain` for `.plain()` and `$toPlain()`, `ObjectForm` for `$toObject()`, and `PlainJson` for `$toJSON()`. For input there are `CreateInput` and `UpdateInput`. Each form type has a single-value variant: `LeanOf`, `PlainOf`, `ObjectFormOf`, `JsonOf`.

If you only need to understand how the forms differ, read [Value forms](./value-forms.mdx). It has the table by MongoDB type. This page is the reference for the types.

You rarely have to write these types by hand. The result of a query is inferred, and you can take the type you need from it (`Awaited<ReturnType<typeof f>>`). Writing one out is needed when you declare a parameter or the return type of your own function.

The examples use a model with fields of different types (it's described on the [Value forms](./value-forms.mdx) page) and a hidden field `secret`.

The types on this page are [`HydratedDoc`](#hydrated-doc), [`Lean`](#lean), [`Plain`](#plain), [`ObjectForm`](#object-form), [`PlainJson`](#plain-json), the [single-value variants](#value-types), [`Int64String`](#int64-string), [`CreateInput` and `UpdateInput`](#create-input-update-input), and the [helper types](#helper-types).

---

## HydratedDoc [#hydrated-doc]

`HydratedDoc<T>` is the type of the document you get after an ordinary read. It's an instance of model `T` with typed collections (arrays, subdocuments, maps) and methods with the `$` prefix (`$save`, `$set`, `$toPlain`). It has no hidden fields, just as an ordinary read's response has none.

A document built from your data keeps the hidden fields. After `create()`, `insertOne()`, and `insertMany()` it's a [`NewDocument<T>`](#new-document), and after `new()` it's an [`UnsavedDocument<T>`](#unsaved-document). A `HydratedDoc<T>` parameter accepts a document from any of these places.

Only this form has methods, and only it knows what has changed. All the other forms are data without methods. The `Output<T>` type is the same thing under another name.

<Snippet id="reference/values/form-types/hydrated-doc" twoslash />

A document with fields that differ from an ordinary read has a different type, [`HydratedDocWith`](#hydrated-doc-with). It doesn't fit a `HydratedDoc<Reading>` parameter. A function that doesn't care whether a reference is loaded needs [`AnyPopulationDoc<T>`](../populate/populate-types.mdx#any-population-doc). For more, see the [Make sure a reference is populated](../../populate/type-checks.mdx) guide.

## HydratedDocWith [#hydrated-doc-with]

`HydratedDocWith<T, P>` is a document of model `T` where some fields differ from an ordinary read. The second argument `P` lists only those fields, in the form they're read. The other fields are the same as in `HydratedDoc<T>`.

That's how the editor shows three cases. The first is a hidden field requested with the `+` sign (`HydratedDocWith<Reading, { secret?: string }>`). The second is a reference loaded through populate (`HydratedDocWith<Post, { author: HydratedDoc<User> | null }>`). The third is a field narrowed by a `.where(…).in(…)` condition.

The methods of such a document work with the fields from `P`. `$set` on a loaded field accepts an identifier, `$toPlain()` removes the hidden field until you pass `{ hidden: true }`, and `$depopulate()` returns the document to `HydratedDoc<T>`.

If a part of the fields is selected, the first argument becomes the projection of the class itself. `Projected<Reading, "_id" | "label">` sets a list of fields, `Omit<Reading, "blob">` is an exclusion, and `Partial<Reading>` is a projection whose makeup the compiler doesn't know.

<Snippet id="reference/values/form-types/hydrated-doc-with" twoslash />

You write the type in a signature the way the hint shows it. More often you infer it from a query: `Awaited<ReturnType<typeof read>>`.

## NewDocument [#new-document]

`NewDocument<T>` is the type of a document you made yourself and wrote. It's returned by [`create`](../writes/writes.mdx#create), [`insertOne`](../writes/writes.mdx#insert-one), and [`insertMany`](../writes/writes.mdx#insert-many), and a document hook receives it too.

Unlike a read, nothing was dropped along the way. The passed values are in memory, so the type has the hidden fields. For a model with hidden fields the hint shows `HydratedDocWith<Reading, { secret?: string }>`, and for a model without them just `HydratedDoc<Reading>`. `$toObject()` includes hidden fields, and `$toPlain()` and `$toJSON()` don't, like for any document.

A document of this type fits anywhere `HydratedDoc<T>` is expected. The name is useful in the result type of your function that creates a document.

<Snippet id="reference/values/form-types/new-document" twoslash />

## UnsavedDocument [#unsaved-document]

`UnsavedDocument<T>` is the type of a document from [`Model.new`](../documents/model-document-methods.mdx#model.new) that isn't saved yet. It matches [`NewDocument<T>`](#new-document) but without the values of the first write. `createdAt` and `updatedAt` (the `Timestamped` class) and `__v` (the `Versioned` class) appear only at `$save`, so before it they're optional. `_id` and the defaults are there right away.

`$save()` returns the same document, but typed as saved. These fields are required in it.

<Snippet id="reference/values/form-types/unsaved-document" twoslash />

## Lean [#lean]

`Lean<T>` is the `.lean()` form. It holds only data, with virtual fields and methods removed. The value types don't change: `ObjectId`, `bigint`, `Binary`, and a map becomes a plain object `{ [key: string]: V }`.

Optional fields stay optional, the markers (`Hidden`, `Ref`, `Immutable`) are removed, and `_id` is an `ObjectId`. Hidden fields are in the `.lean()` result if the query selected them.

<Snippet id="reference/values/form-types/lean" twoslash />

`LeanOf<V>` is the same form for a single value. `LeanOf<Map<string, number>>` gives `{ [key: string]: number }`. You'll see this type in the hint of a `.lean()` result.

## Plain [#plain]

`Plain<T, H>` is the `.plain()` and `$toPlain()` form. In it, identifiers, `bigint`, `Decimal128`, and `UUID` are strings. `Date` and `RegExp` stay as they are, `Binary` becomes a `Uint8Array`, a vector becomes `number[]`, and a map becomes a `Map` with values in the same form.

The second parameter `H` decides whether to keep hidden fields. In the type itself the default is `true`, and `$toPlain()` and `.plain()` compute it themselves. Hidden fields drop out until you pass `{ hidden: true }`.

<Snippet id="reference/values/form-types/plain" twoslash />

`PlainOf<V, H>` is the same for a single value. `PlainOf<ObjectId>` gives `string`, and `PlainOf<Date[]>` gives `Date[]`. The `hidden` option works at any depth: in subdocuments, arrays, maps, and loaded references.

`.plain()` doesn't return hidden fields even if the query selected them with `select`. `.plain({ hidden: true })` and `.lean()` show them.

## ObjectForm [#object-form]

`ObjectForm<T, H>` is the `$toObject()` form. The data is the same as in `Lean`, but maps stay `Map` and BSON values stay as they are. Hidden fields are included here by default (`H` is `true`), because `$toObject()` hands the data to the application itself. `ObjectFormOf<V, H>` is the single-value variant.

<Snippet id="reference/values/form-types/object-form" twoslash />

## PlainJson [#plain-json]

`PlainJson<T, H>` is the `$toJSON()` form. `JSON.stringify(doc)` calls it too. All its values are ones JSON survives without loss. A `Date` is a string, `int64` is a decimal string, `Binary` is base64, and a map is an object.

`JsonOf<V, H>` is the single-value variant. `JsonOf<Date>` gives `string`, and `JsonOf<Map<string, ObjectId>>` gives `{ [key: string]: string }`.

<Snippet id="reference/values/form-types/plain-json" twoslash />

## Single-value types [#value-types]

`LeanOf<V>`, `PlainOf<V, H>`, `ObjectFormOf<V, H>`, and `JsonOf<V, H>` take the type of a field, not of a document, and return it in the form you need. They're useful when you write code over a field's value, for example a function that takes an identifier from a `.plain()` result.

<Snippet id="reference/values/form-types/value-types" twoslash />

## Int64String [#int64-string]

`Int64String` is the type `` `${bigint}` ``, that is the decimal notation of an integer. `.plain()` and `$toJSON()` return `int64` as a string, and the write methods accept it back. A value from a `.plain()` result can go into `create` and `updateOne` with no casts. The format of the string is checked not by the compiler but by Typemo at runtime.

<Snippet id="reference/values/form-types/int64-string" twoslash />

A string that isn't a decimal integer in the int64 range leads to a `CastError`. Which notations are allowed is written on the [Value forms](./value-forms.mdx#numbers) page.

## CreateInput and UpdateInput [#create-input-update-input]

`CreateInput<T>` describes what `create`, `insertOne`, and `insertMany` accept. Required fields are required. Fields with `?`, fields with a default (`Defaulted`), the tenant field, and array fields are optional. An array without `required` and without `default` becomes `[]` on create. The input has no virtual fields.

Values are accepted in their input form. In place of an `ObjectId` you can pass a string, in place of a `bigint` an `Int64String`, in place of a `Ref<M>` an identifier or the document itself, and in place of a `Map` a `Map` or an object. `undefined` doesn't count as a value, so just leave out a missing field.

`UpdateInput<T>` is the fields a write can assign. All of them are optional, and `_id` and immutable (`Immutable`) fields aren't among them. `Replacement<T>` is what `replaceOne` and `findOneAndReplace` accept. It's `CreateInput` without `_id` and without the service fields `createdAt`, `updatedAt`, and `__v`, which the core maintains ([`ServiceKeys`](#helper-types)).

<Snippet id="reference/values/form-types/create-input-update-input" twoslash />

`total` accepts the string `"9007199254740993"` in place of a `bigint`. `CreateInput` has an optional `_id`, while `UpdateInput` and `Replacement` don't, because a write can't change the identifier. `label` is the only required input field, because it's the only one declared with `required: true`. Without it the compiler stops the assignment.

<Snippet id="reference/values/form-types/create-input-update-input-2" twoslash />

The compiler says `TS2741: Property 'label' is missing in type '{ count: number; }' but required in type …` and lists the input fields.

`DocOf` is in the public API but belongs to aggregations. It's the type of the pipeline source's document without hidden fields (`DocOf<typeof User>`), not a general name for a document form. It's described in the [aggregation](../aggregation/index.mdx) section.

## When not to use these types [#when-not-to-use]

If you use a query's result in the same place the query runs, you don't need to name its type, because it's inferred. If a function has to accept the result of someone else's query, infer the type from the query (`Awaited<ReturnType<typeof f>>`) instead of writing it by hand. Then the type won't drift from the data.

To check the shape of a response at compile time and at runtime, there are [contracts](../query/contracts.mdx).

## Common mistakes [#common-mistakes]

### A plain type doesn't fit where JSON is expected [#plain-not-json]

`Plain<T>` isn't JSON. `Date`, `Uint8Array`, and `Map` stay in it. For a value that goes into `JSON.stringify`, use `PlainJson<T>` and `$toJSON()`.

### A hidden field vanished from the type [#hidden-not-in-type]

`Plain<T>` without a second argument includes hidden fields, while `$toPlain()` removes them. Don't write a variable's type by hand as `Plain<T>`, and let it be inferred from the call. Then the compiler accounts for `{ hidden: true }` itself.
