A field's TypeScript type doesn't say that the field is hidden, immutable, or a reference to another model. Those are properties of the schema, not of the values. To let the compiler know about them, Typemo uses **marker types**, wrappers like `Hidden<string>`. To TypeScript it's still a string, but with a tag that the result types are inferred from and the decorator options are checked against. Below is every marker type, along with the field types for vectors, int64 strings, and a document's collections.

A marker goes **together with an option** of [`@Prop`](./prop.mdx#prop). `Hidden<T>` goes with `hidden: true`, `Defaulted<T>` with `default`, and `Immutable<T>` with `immutable: true`. For `TenantField<T>`, the partner is the [`@Tenant()`](#tenant) decorator, and for `Discriminators<…>` it's the schema option [`discriminators`](./schema.mdx#discriminators). Break the pairing and the compiler answers with a message naming the field. The sections below have examples. The tags are optional members with symbol keys, so they don't show up in autocomplete, and any value of `T` is assignable to `T & Marker`. `null` and `undefined` don't get a marker, so `Defaulted<string | null>` is `(string & DefaultedMarker) | null`.

For guides with examples, see [Hidden and sensitive fields](../../schemas/hidden-and-sensitive.mdx), [Immutable fields](../../schemas/immutable.mdx), [Reference other models](../../schemas/references.mdx), and [Add computed fields and reverse references](../../schemas/virtuals.mdx).

## Defaulted [#defaulted]

`Defaulted<T>` means a default value is filled in when there's no value. The [`default`](./prop.mdx#default) option is its partner. For such a field, `create` doesn't require a value, and a value you read is always there.

<Snippet id="reference/schemas/field-markers/defaulted" twoslash />

The service fields of the base classes ([`_id`, `createdAt`, `updatedAt`, `__v`](./base-classes.mdx)) are declared as `Defaulted` too. The exception is the `_id` of [`EntityWithId`](./base-classes.mdx#entity-with-id) without `default`, which is required.

---

## Immutable [#immutable]

`Immutable<T>` means the value can't change after the document is created. The [`immutable`](./prop.mdx#immutable) option is its partner. The compiler keeps such a field out of an update's `$set`.

<Snippet id="reference/schemas/field-markers/immutable" twoslash />

The editor hint shows a plain `string | undefined`. The tags are hidden, but the compiler remembers them. That's why you can pass the value wherever a `string` is expected, while the field stays out of an update's `$set`. If you forget `immutable: true`, the compiler answers `@Prop "country": the field is Immutable<T>, add immutable: true`.

---

## Hidden [#hidden]

`Hidden<T>` means queries don't return the field until you select it explicitly. The [`hidden`](./prop.mdx#hidden) option is its partner. The tag removes the field from the default result type, so using `passwordHash` on an ordinary result doesn't compile.

<Snippet id="reference/schemas/field-markers/hidden" twoslash />

---

## Computed [#computed]

`Computed<T>` is the type a class getter without a setter returns. It's a computed value, and it isn't in the database. No decorator is needed, because the getter is a virtual field on its own. The tag tells a computed value apart from data. It stays out of filters and writes, and out of `$toPlain()` unless you ask for `{ virtuals: true }`.

<Snippet id="reference/schemas/field-markers/computed" twoslash />

The value isn't written to the database, and `lean()` doesn't contain it. The document stores only `_id`, `first`, and `last`. You get the value with a cast, `as Computed<string>`, because the compiler doesn't turn an ordinary string into a marker type by itself.

---

## VirtualValue [#virtual-value]

`VirtualValue<T>` is the type of a getter and setter pair in a class. It's a computed value you can assign to. The setter spreads the assigned value across the real fields.

<Snippet id="reference/schemas/field-markers/virtual-value" twoslash />

As with `Computed`, the value isn't stored. The database holds only the real fields `first` and `last`.

---

## Ref [#ref]

`Ref<M, Id>` is the identifier of a document of model `M` that a `populate` query can pull in. The second parameter is the `_id` type of the target model, `ObjectId` by default. The options [`ref`](./prop.mdx#ref), [`refPath`](./prop.mdx#ref-path), and [`refModel`](./prop.mdx#ref-model) are its partners. An array of references is written `Ref<M>[]`, and a map is written `Map<string, Ref<M>>`.

<Snippet id="reference/schemas/field-markers/ref" twoslash />

Instead of an identifier, you can pass the model's document itself into such a field. A document, a `.lean()` result, or a class instance all work. Its `_id` goes to the database, and that's how `create`, updates, filters, arrays of references, and `Map` values work. Typemo also accepts a string with an `_id` and casts it to the identifier type.

<Snippet id="reference/schemas/field-markers/ref-2" twoslash />

Assign a document directly to a field of a loaded document (`post.author = other`), and until you save, the field holds that document and `$getChanges()` shows the object. `post.$set("author", other)` puts the identifier into the field, and `$getChanges()` shows that. In both cases `$save()` writes the `_id`. You can't assign a `.lean()` result directly to the field, because the types don't allow it, but you can through `$set`.

An identifier doesn't combine with a field type lacking `Ref<M>` and options lacking `ref`. The errors are `@Prop "author": the field is Ref<Model>, add ref: () => Model` and `"ref" is set, but the field type is not Ref<Model>`.

---

## VirtualRef [#virtual-ref]

`VirtualRef<M, JustOne, Count>` is the type of a field that pulls in documents through a reverse reference and stores nothing. `M` is the model, `JustOne` means one document instead of an array, and `Count` means the number of documents instead of the documents themselves. The flags must match the [`@Virtual`](./virtual.mdx#virtual) options `justOne` and `count`. Such a field is declared without `@Prop`, and `@Prop` on it is an error (`a VirtualRef field is declared with @Virtual, not @Prop`).

<Snippet id="reference/schemas/field-markers/virtual-ref" twoslash />

---

## TenantField [#tenant-field]

`TenantField<T>` marks the field that carries the multi-tenancy [policy](./schema.mdx#tenant). The core writes the owner into it, so `create` doesn't require a value, and a read always contains it. You use the type together with the [`@Tenant()`](#tenant) decorator and the schema option `tenant`. `@Schema` checks that the type sits on exactly the field named in that option.

<Snippet id="reference/schemas/field-markers/tenant-field" twoslash />

The field is declared as a plain `string`, while the compiler requires `TenantField<T>`. The text is `@Schema: declare the tenant field as tenantId!: TenantField<T> — the core fills it, create() does not require it, reads always have it`. The type without the `tenant` option is an error too: `@Schema: "tenantId" is TenantField<T>, but the schema has no tenant option — add tenant: { field: "tenantId" } or use a plain type`. The type on a different field than the one the option names gives `@Schema: "owner" is TenantField<T>, but the tenant field is "tenantId"`.

---

## @Tenant [#tenant]

`@Tenant()` marks the tenant field in a class. Put the decorator next to [`@Prop`](./prop.mdx#prop) on a field of type [`TenantField<T>`](#tenant-field). The compiler sees the type and the runtime sees the decorator, which is how the schema finds the field the core writes the tenant to. Together with the [`tenant`](./schema.mdx#tenant) option, it's a required pair. A schema with `tenant` and a field without `@Tenant()` doesn't build.

<Snippet id="reference/schemas/field-markers/tenant" twoslash />

A property decorator with no arguments, `@Tenant()`. It records a tag in the class description and returns nothing.

### Errors [#errors]

The field type is checked at compile time. The compiler rejects `@Tenant()` on a field that isn't declared as `TenantField<T>`.

<Snippet id="reference/schemas/field-markers/errors" twoslash />

The compiler message is `@Tenant "title": declare the field as TenantField<T>`. The schema build finds the other violations, and all of them throw `ConfigurationError`.

- a field without the decorator: `Note: the tenant field "tenantId" must be marked @Tenant() (declare it @Prop(...) @Tenant() tenantId!: TenantField<T>)`
- a decorator without the option: `Note: @Tenant() on "tenantId", but the schema has no tenant policy — add tenant: true (or { field }) to @Schema`
- a decorator on two fields or on the wrong field: `Note: @Tenant() marks "tenantId", "owner"; only the tenant field "tenantId" may be marked`

A decorator on a static member, a method, or an accessor, and a repeated decorator on one field, also throw `ConfigurationError`. In the TC39 package `@Tenant()` works the same way, but you can't mix the two kinds of decorators.

## Discriminators [#discriminators]

`Discriminators<C>` is the type of the discriminator key in the **base** class, the one that lists its subclasses with the [`discriminators`](./schema.mdx#discriminators) option, for example `declare readonly __t?: Discriminators<Card | Transfer>`. The core writes the key itself and you can't change it, and the parameter `C` is the union of the subclass types. The read types through the base model build the union "base without a key, or any subclass" from it. In the subclasses themselves, you declare the key with the [`DiscriminatorValue`](#discriminator-value) type. For examples and errors, see the page [`@Discriminator`](./discriminator.mdx#discriminators).

---

## DiscriminatorValue [#discriminator-value]

`DiscriminatorValue<"circle">` is the type of the discriminator key in a subclass, `declare readonly __t: DiscriminatorValue<"circle">`. It's `Defaulted<Immutable<"circle">>`. The core writes the key itself, you can't change it, and the `.lean()` and `.plain()` results carry the literal. The declaration is required in every class with [`@Discriminator`](./discriminator.mdx#discriminator), and the decorator checks that the literal matches the value.

---

## Unbranded [#unbranded]

`Unbranded<T>` strips the field tags (`Defaulted`, `Immutable`, `Hidden`, `Computed`, `VirtualValue`, `TenantField`, `Discriminators`) from a type, for each member of a union. `Ref` stays, since a reference is part of the value's meaning. The type is for people who write their own wrappers over Typemo's types. In the example, assigning to `string | null` compiles because the `Hidden` tag is stripped and `null` stayed.

<Snippet id="reference/schemas/field-markers/unbranded" twoslash />

---

## Vector [#vector]

`Vector` is the type of a vector field. At runtime it's a `Binary` of subtype 9, and the tag is needed because a vector's `.plain()` result and JSON form is `number[]`, not bytes. The [`Spec.vector`](./types-and-spec.mdx#spec.vector) builder is its partner. Without the tag, a vector can't be told apart from an ordinary `Binary`. `Spec.vector(...)` requires the type `Vector` (`Spec.vector(...) needs the field type Vector`), and a field of type `Vector` requires `Spec.vector` (`a Vector field needs Spec.vector({ dtype, dimensions })`).

---

## Int64String [#int64-string]

`Int64String` is a decimal int64 string, the form of a `bigint` field in the `.plain()` result and in JSON. It's the template type `` `${bigint}` ``. TypeScript already rejects a fractional value, a value with a plus sign, or one with a leading zero at compile time, and the runtime `CastError` is stricter, also forbidding spaces, exponents, and prefixes. A string is accepted in place of `bigint` in writes, in filters, and in `$inc`, `$mul`, `$min`, and `$max`. A `number` passes into a `bigint` field only as a safe integer, otherwise you get `CastError` with a hint to use `5n` or `"5"`.

<Snippet id="reference/schemas/field-markers/int64-string" twoslash />

---

## A document's collection types [#document-collection-types]

A document stores arrays, maps, and subdocuments in its own strictly typed collections. You see these types in hints when you access a field of a loaded document. The methods and forbidden operations are described in the reference [Typed collections](../documents/typed-collections.mdx).

<Snippet id="reference/schemas/field-markers/document-collection-types" twoslash />

- `StrictArray<T>`: an array of values. It reads like an ordinary array and is written only through methods (`push`, `set`, `pull`, and others).
- `SubdocumentArray<T>`: an array of subdocuments. Besides the `StrictArray` methods, it has `create`, `id`, and `pull` by identifier.
- `TypedMap<V>`: a `Map<string, V>` that checks keys and values. It's written with the `set`, `delete`, and `clear` methods.
- `Subdocument<T>`: a subdocument or nested object, with fields and methods prefixed with `$`.

## When not to use it [#when-not-to-use]

You don't need markers in queries and results. Typemo strips them itself, and in `.plain()`, `.lean()`, and `$toObject()` a `Hidden<string>` field is just a `string`. `Unbranded` has no use in ordinary application code. If you want a computed value, write a getter with `Computed` rather than a field with `@Prop`.
