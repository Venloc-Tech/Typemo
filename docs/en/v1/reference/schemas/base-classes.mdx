Typemo doesn't add a document's service fields (`_id`, `createdAt`, `updatedAt`, and the version `__v`) to the schema behind your back. You get them by inheriting a base class. `Entity` gives `_id` of type `ObjectId`, `EntityWithId` gives an `_id` of another type (a string, a number, a `UUID`), `Timestamped` adds timestamps, and `Versioned` adds a version. The compiler, your editor's hints, and the result types all see these fields, so you don't declare them by hand in every model. Below are all four base classes and the types tied to them.

For an overview built around tasks, see the guides [Define a model](../../schemas/define-model.mdx), [Use your own `_id` type](../../schemas/custom-ids.mdx), and [Timestamps and versions](../../schemas/timestamps-and-versions.mdx). This page is the reference.

The examples use a post model with a single title, and the other fields come from the base classes. The results in `// →` come from a real MongoDB.

The base classes have no constructors or initializers. The core fills in the service fields on create and save. A base-class constructor wouldn't work here, because with `useDefineForClassFields: true`, redeclaring a field in a subclass would silently wipe the value the base set.

## Entity [#entity]

`Entity` is the base class for a document with an identifier. It gives an `_id` field of type `ObjectId`, generates the value if you don't pass one, and doesn't let you change it after creation. Almost every model inherits `Entity`, directly or through `Timestamped` and `Versioned`.

<Snippet id="reference/schemas/base-classes/entity" twoslash />

The type of the `_id` field is `Defaulted<Immutable<ObjectId>>`. You can leave it out on creation ([`Defaulted`](./field-markers.mdx#defaulted)), and you can't change it afterward ([`Immutable`](./field-markers.mdx#immutable)).

Need a different identifier, such as a string, a number, or a `UUID`? Inherit [`EntityWithId`](#entity-with-id) instead of `Entity`. It gives the same service field with the type you choose. A model without `_id` doesn't build and throws `ConfigurationError` (`Slug: a model needs an _id field (extend Entity or declare @Prop _id)`).

You can't declare `_id` with `dbName`, with `nullable` or as an array, or with `index` or `unique`. The server makes it unique anyway (`Slug._id: _id is always uniquely indexed by the server; remove index/unique`). This rule also covers an `_id` you declared by hand.

## EntityWithId [#entity-with-id]

`EntityWithId(() => Type, { default })` is the base class for a document whose `_id` isn't an `ObjectId`. It could be an external code such as an ISO country code, a `UUID`, a numeric counter, or a date. The function returns an abstract class with an `_id` field of the chosen type and registers it the way [`Entity`](#entity) does, as an immutable service field. It suits reference data with human-readable keys, documents whose identifier another system issues, and identifiers that must be unguessable. With `default`, the identifier is generated if you don't pass one. Without `default`, it's required.

The `_id` type runs through everything. It's read by [`IdOf<T>`](../values/form-types.mdx), [`findById`](../query/reading.mdx#model.find-by-id), references ([`Ref<M, Id>`](./field-markers.mdx#ref)), [`populate`](../populate/populate.mdx#populate), the targets of [`$out` and `$merge`](../aggregation/stages.mdx#out), and [`keysetPage`](../query/keyset.mdx#model.keyset-page). A string in `_id` stays a string everywhere.

<Snippet id="reference/schemas/base-classes/entity-with-id" twoslash />

An identifier with `default` can be left out. The [`Timestamped`](#timestamped) and [`Versioned`](#versioned) mixins wrap the result the same way as for `Entity`, and the nesting order doesn't matter.

<Snippet id="reference/schemas/base-classes/entity-with-id-2" twoslash />

<Params>
<Param name="type" type="() => IdSpec" required>

An arrow function that returns the `_id` type, like the first argument of [`@Prop`](./prop.mdx#prop). `String`, `Number`, `BigInt`, `Date`, `Types.UUID`, `Types.ObjectId`, `Types.Int32`, `Types.Double`, and `Types.Decimal128` work. The compiler rejects other types (`Boolean`, arrays, `Spec.*`). Passing anything other than a function throws `ConfigurationError`.

</Param>
<Param name="options.default" type="() => Id">

A function that creates an identifier for a document created without one, for example `() => new UUID()` or `() => crypto.randomUUID()`. With it, `_id` is optional in `create`, `insertOne`, and `insertMany`, and without it, `_id` is required. The core leaves an `_id` you pass as it is. If `default` isn't a function, you get `ConfigurationError`.

</Param>
</Params>

<Returns type="IdBase<Id, HasDefault>">

An abstract class with no constructor arguments and an `_id` field. Without `default`, its type is `Immutable<Id>`, and with `default` it's `Defaulted<Immutable<Id>>`, which is how `create` knows whether the identifier is required. `Id` is inferred from `type`. For `() => String` it's `string`, for `() => Types.UUID` it's `UUID`, and for `() => BigInt` it's `bigint`.

</Returns>

### The identifier is required [#id-required]

Without `default`, the compiler won't let you create a document without `_id`, and at runtime you get `ValidationError`.

<Snippet id="reference/schemas/base-classes/id-required" twoslash />

An empty string is valid for `String`, because MongoDB accepts it as an identifier. If an empty code is an error for you, check such values yourself.

### The identifier doesn't change [#id-unchanged]

As with `Entity`, `_id` is immutable here. An update that writes it doesn't compile, and at runtime it throws `StrictModeError` with the reason `immutable`. A replacement (`replaceOne`) shouldn't carry `_id` at all. The document keeps its identifier, and the filter selects it by `_id`.

<Snippet id="reference/schemas/base-classes/id-unchanged" twoslash />

A replacement with the same `_id` is rejected too, even if the value doesn't change. The error text is `a replacement of Country carries "_id": a replacement keeps the stored _id and cannot change it; leave "_id" out and select the document by _id in the filter [immutable]`.

### Errors [#errors]

The compiler rejects a type that isn't in `IdSpec`.

<Snippet id="reference/schemas/base-classes/errors" twoslash />

A wrong argument to the factory throws `ConfigurationError` when the class is declared: `EntityWithId: the spec of the id, as () => String` and ``EntityWithId: `default` is a function that generates the id``. If you pass the constructor itself instead of an arrow function (`EntityWithId(String)`), the factory stays quiet, and the schema fails to build when the model is created: `Country._id: the type thunk returned string, expected a type`. Redeclaring `_id` with another type in the class itself is also a `ConfigurationError` (`Country._id: redeclared with another type (number in Country, string in Identified)`).

## When not to use it [#entity-with-id.when-not-to-use]

If you want an ordinary generated identifier, inherit [`Entity`](#entity). An `ObjectId` is shorter than a `UUID`, sorts by creation time, and needs no setup. Use `EntityWithId` when the identifier comes from outside or has to look different. It doesn't support a compound `_id` object (`{ a, b }`), only the scalar types listed above.

## Timestamped [#timestamped]

`Timestamped(base)` adds the `createdAt` and `updatedAt` fields. It's a function that takes a class and returns the extended class: `Timestamped(Entity)`. `createdAt` is set once on creation and doesn't change. `updatedAt` is refreshed by every write that reaches the document. Those are `$save` with changes, `updateOne`, `updateMany`, `findOneAndUpdate`, a replacement, and an upsert.

<Snippet id="reference/schemas/base-classes/timestamped" twoslash />

The second result shows that `updatedAt` moved forward while `createdAt` stayed the same. `Posts.updateOne(...)` behaves the same way.

`updatedAt` moves on **any** write, not only a real change. Before the write, the core doesn't know whether the server will change anything. So a `$set` of the same value and an `$addToSet` of a value already in the array also update `updatedAt`, while the server reports `modifiedCount: 1` in such cases.

You can set the dates deliberately, and the type allows it. Both are optional on creation (`createdAt?: Date`, `updatedAt?: Date`), and an update can write `updatedAt`. The core leaves a date you set as it is, so history travels along with the data. You can't write `createdAt` after creation. The compiler rejects such an update, and at runtime you get `StrictModeError` with the reason `immutable`.

<Snippet id="reference/schemas/base-classes/timestamped-2" twoslash />

An update without an explicit `updatedAt` moved it forward, and `createdAt` stayed the same. `$save` doesn't overwrite an `updatedAt` you assigned in the document. Without an assignment, `$save` moves the date.

<Params>
<Param name="base" type="B extends EntityClass" required>

The class to extend. It's `Entity` or the result of another mixin, such as `Versioned(Entity)`. The nesting order doesn't affect the result.

</Param>
</Params>

<Returns type="Mixed<B, TimestampFields>">

An abstract class. It has everything `base` has, plus `createdAt: Defaulted<Immutable<Date>>` and `updatedAt: Defaulted<Date>`. Both fields are optional on creation, and you can pass your own date. On read they're always there.

</Returns>

## Versioned [#versioned]

`Versioned(base)` adds a numeric version field, `__v`. The core increments the version when a change depends on the position of array elements. Without it, two processes that change the same array by index at the same time would overwrite each other's work. Together with the schema option [`optimisticConcurrency`](./schema.mdx#optimistic-concurrency), the version protects the other saves too.

<Snippet id="reference/schemas/base-classes/versioned" twoslash />

The version went up after the array change and stayed the same after a change to an ordinary field. Without `optimisticConcurrency`, the version protects only positional array changes.

<Param name="base" type="B extends EntityClass" required>

The class to extend. It's `Entity` or another mixin.

</Param>

## Types [#types]

`Mixed<B, F>` is the result type of a mixin. It's an abstract instance constructor of `InstanceType<B> & F` together with the static members of `B`. It's written as an explicit type so the public API has no `any`. `TimestampFields` and `VersionFields` are the field interfaces of `Timestamped` and `Versioned`. For `EntityWithId`, the exports are `IdSpec` (the types allowed for `_id`), `EntityIdOptions<Id>` (the options), `IdBase<Id, HasDefault>` (the class the factory returns), and `EntityWithIdFactory` (the overloads of the function itself). All of these types are exported from `@venloc/typemo`.

## When not to use it [#timestamped.when-not-to-use]

You can't turn on timestamps and a version with a `@Schema` option. The decorator has no `timestamps` or `versionKey`, and the fields are declared only through base classes. If you need a different set of service fields or different names, declare the fields yourself with [`@Prop`](./prop.mdx#prop), for example `@Prop(() => Date, { default: () => new Date() }) createdAt!: Defaulted<Date>`. For an `_id` of another type there's no need to declare the field by hand, because there's [`EntityWithId`](#entity-with-id). Also, an `_id` declared by hand with `@Prop` doesn't get Typemo's protection against changes until you add `immutable: true`. Until then, only the server protects it.
