`SchemaInfo` is a **read-only** view of a model's schema. Your application, extensions, and integrations read it without reaching into the schema compiler's internals. At runtime it tells you a model's collection name, paths, indexes, and virtual fields. It also translates a path from your code into a database field name. Every model exposes it in its `schema` property.

For tasks, see the guide [The schema at runtime](../../schemas/runtime-schema.mdx). This page is the reference.

The examples use a user model. The `email` field is called `e` in the database, and the model also has a nested address and an array of tags.

<Snippet id="reference/schemas/schema-info/intro" twoslash />

`SchemaInfo` is an interface. The class that implements it isn't exported, so you work only with the fields and methods below. You can't change any values, because the schema is frozen once it's built.

---

## name [#name]

`name` is the model's class name.

<Snippet id="reference/schemas/schema-info/name" twoslash />

---

## collection [#collection]

`collection` is the collection name in the database. It matters for root documents and isn't used by nested schemas. How the name is built when no option is set is described in [`CollectionNaming`](./collection-naming.mdx).

---

## describe [#describe]

`describe()` returns a plain `SchemaDescription` object, a JSON description of the schema for test snapshots and debugging. Paths use the canonical code form (`address.city`, and `tags.$` for an array element). Each path has a kind (`kind`), a type (`type`), a database name (`dbPath`, when it differs), and flags (`flags`).

<Snippet id="reference/schemas/schema-info/describe" twoslash />

The description has the fields `name`, `kind` (`"document"` or `"nested"`), `collection`, and `discriminator` (`{ root, key, value }` on a discriminator class). Next come `discriminators` (the values of the hierarchy), `paths`, `indexes` (keys and options), and `searchIndexes`. The last one lists the Atlas Search indexes from `@SearchIndex`, each with a name and a definition in declaration order, and is an empty array without them. Then come `virtuals` (`populate:posts`, `getter:label`), `hooks` (the number of hooks by phase and event), and `ext`. A path's flags are written as one comma-separated string. They are `required`, `nullable`, `default`, `immutable`, `hidden`, and service flags like `service:id`.

<Returns type="SchemaDescription">

A plain schema description object.

</Returns>

## toDbPath [#to-db-path]

`toDbPath(path)` translates a path from your code into a database path, taking [`dbName`](./prop.mdx#db-name) into account at every level. Array positions (`0`, `$`) stay where they are. If the path isn't in the schema, the method returns `undefined` and doesn't throw.

<Snippet id="reference/schemas/schema-info/to-db-path" twoslash />

<Params>
<Param name="path" type="string" required>

A path from your code. An array position can be a number, `$`, `$[]`, or `$[name]`.

</Param>
</Params>

## ext [#ext]

`ext` holds the options of registered extensions at the schema level, as set in [`@Schema({ ext })`](./schema.mdx#ext). Without extensions it's an empty frozen object.

## extOf [#ext-of]

`extOf(path)` returns the extension options for a field, as set in [`@Prop({ ext })`](./prop.mdx#ext). You can write the path in any positional form (`items.3.price`, `items.$.price`). For an existing field without `ext` the method returns an empty object, and for a path that doesn't exist it returns `undefined`.

<Snippet id="reference/schemas/schema-info/ext-of" twoslash />

How extensions declare their options is covered in the guide [Add your own field and schema options](../../extensions/custom-options.mdx).

## Related types [#related-types]

`@venloc/typemo` exports the types the description refers to: `SchemaDescription`, `PathDescription`, `DiscriminatorInfo`, `CompiledIndex`, `HookTable`, `VirtualDefinition`, `PathKind`, and `ScalarType`. The last two list the kinds of path nodes and the scalar types. The `SchemaSource` type means "a model or its `schema`" (`SchemaInfo | { readonly schema: SchemaInfo }`). [`JsonSchemaGenerator` and `StandardSchema.of`](./json-and-standard-schema.mdx) accept it, and so do the collection manager's methods, so you can pass `SchemaInfo` to them directly.

## When not to use it [#when-not-to-use]

`SchemaInfo` only reads. You can't change the schema at runtime, because it's frozen when the model is built. To check a value against the schema, use the model's methods (`validate`, `castObject`) or [`~standard`](./json-and-standard-schema.mdx#standard-schema). For a collection validator, there's the [`validator`](./schema.mdx#validator) option.
