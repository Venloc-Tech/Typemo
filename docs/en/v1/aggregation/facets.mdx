The orders page in an admin panel shows three things at once: how many orders match the filter, the rows of the current page, and a breakdown by status. You could send three queries, but each would go over the data again. The [`facet`](../reference/aggregation/stages.mdx#facet) stage does it in one. You describe several **branches**, which are separate pipelines, and the server runs the incoming rows through all the branches in one pass. You get back **one** row, where each branch's name holds an array of its results.

The result type is inferred from the branches. Each branch has its own row type, and the compiler knows what sits under each name.

## What you need [#prerequisites]

The client from [Connect to the database](../connection/connect.mdx), running an aggregation from [Your first aggregation](first-aggregation.mdx), and an order model with the fields `customer`, `status`, `total`, and `placedAt`. The `orders` collection holds five orders.

- Two paid orders from `alice`, for 120 and 80.
- A paid order from `bob` for 50.
- A canceled order from `bob` for 200.
- A new order from `carol` for 30.

Below we'll cover how the result is shaped, what to do with an empty set, and what's forbidden in a branch.

## Get a summary and a page together [#summary-with-page]

`facet` always returns exactly one row, and the arrays in it are the branch results. So you read the result of `await` like this: `const [report] = await …`. All branches see the same incoming rows. Whatever you filtered with stages before `facet` reaches every branch.

Usually a shared [`match`](../reference/aggregation/stages.mdx#match) filter comes first, then `facet`. Then `total` and `page` are computed over the same set, and the number in `total` agrees with the rows in `page`.

<Snippet id="aggregation/facets/summary-with-page" title="orders/orders.service.ts" twoslash />

Notice `report?.count[0]?.n ?? 0`. If nothing matched the filter, the `count` branch is empty, since the `count` stage doesn't create a row with zero. The `rows` branch is empty too then. The `facet` row itself still exists, so `report` is defined, but `[0]` may be missing. The type reminds you of that.

## Break down by group [#group-by]

A branch can hold any stages except those forbidden inside `facet`: grouping, buckets, another count. That's how you build a filter sidebar with the number of products for each value.

<Snippet id="aggregation/facets/group-by" twoslash />

The `bySize` branch uses [`bucket`](../reference/aggregation/stages.mdx#bucket), the `byStatus` branch uses [`sortByCount`](../reference/aggregation/stages.mdx#sort-by-count). Both are covered in [Grouping and reports](grouping.mdx).

## What's not allowed in a branch [#branch-limits]

Stages that must come first or that write to the database don't work inside a branch. That's a nested `facet`, [`out`](../reference/aggregation/stages.mdx#out), [`merge`](../reference/aggregation/stages.mdx#merge), and stages allowed only at the start of a pipeline. You can't call `out` on a branch builder, because its type allows the call only at the top level of the pipeline, and the error shows up at compile time (`The 'this' context … is not assignable to method's 'this'`).

<Snippet id="aggregation/facets/branch-limits" twoslash />

A branch without stages throws a `ConfigurationError` when it's built, because an empty pipeline makes no sense. If there are no branches at all, you also get a `ConfigurationError`.

## How to choose [#how-to-choose]

Ask yourself whether you need several independent results over one set.

- **Yes**: `facet` saves passes over the data.
- **There's one result**: you don't need `facet`.
- **The branches work on different sets**, with different filters before grouping: several separate queries are simpler and often faster.

## When not to use it [#when-not-to-use]

For a total count without rows, use [`countDocuments`](../reference/query/reading.mdx#model.count-documents), and for pages without a summary, [`find`](../reference/query/reading.mdx#model.find) with [paging](../queries/sorting-and-pages.mdx). And remember that the whole `facet` result is one row, so cap the `rows` branch with `limit`.

## Troubleshooting [#troubleshooting]

**The result is read as an array of rows.** `await` returns an array with one row, not the branch results themselves. `report.count` won't compile on an array. Take the first row: `const [report] = await …`.

**A branch is empty, but the code expects a number.** `count` with no matches doesn't return a row with zero. The code `report.count[0].n` crashes, and with `noUncheckedIndexedAccess` it doesn't even compile. Write `report?.count[0]?.n ?? 0`.
